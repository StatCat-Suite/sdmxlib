# Issue #346: sdmx_ml31 is a 98% copy of sdmx_ml30 — the fork is what makes #345-shaped bugs cheap

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-19 |
| Closed | 2026-09-11 |
| Labels | `design` |

Measured with `difflib.SequenceMatcher` over the module sources:

| | 3.1 size | identical to 3.0 | ratio |
| --- | --- | --- | --- |
| `reader.py` | 1063 lines | **1050 (98%)** | 0.978 |
| `writer.py` | 949 lines | **898 (94%)** | 0.908 |

For contrast, the same comparison between 2.1 and 3.0 — a genuinely different
schema generation — is 45% and 31%. So ~1,950 of the ~2,000 lines under
`formats/sdmx_ml31/` are a copy.

A normalised-AST scan finds 35 function bodies that are structurally identical
between the two packages, including `read` itself at 32 statements.

The 3.1 reader's header is honest about it: *"Forked from the 3.0 reader at
parity."* The fork was a reasonable way to land 3.1 support. The question is
whether it stays.

## The cost, already paid once

#345 is a fork-shaped bug: two branches present in the 3.0 reader are absent
in the 3.1 one, the corresponding fixture was trimmed to match, and the
round-trip guard passed because both sides lost the same thing. Nothing about
that is specific to those two branches — every future fix to a shared code
path has to be applied twice, by someone who knows to look.

## What actually differs

Very little, and it is enumerable:

- module docstring and the `read`/`write` docstrings (version strings)
- 3.1 omits attributes 3.0 emits: `Categorisation/@version`,
  `DataConstraint/@role` — already declared in `formats/gaps.py`
- namespace URIs, already isolated in `namespaces.py` per package
- the two branches that should not differ at all (#345)

That is a parameter, not a fork: the shape is the same shape
`formats/sdmx_ml/_common.py` already exists to hold.

## Options

1. **Shared core parameterised by generation.** `_common.py` grows a v3
   reader/writer taking a namespace map plus a small "what this generation
   omits" set; `sdmx_ml30` and `sdmx_ml31` become thin. Biggest win, biggest
   change, and it wants doing before 3.2 rather than after.
2. **Keep the fork, add a drift guard.** A test asserting the two modules
   differ only in a known set of places — element vocabulary per fixture set,
   or the AST-level function inventory. Cheap, and would have caught #345.
3. **Keep the fork, accept the cost.** Defensible only if 3.1 is expected to
   diverge substantially from 3.0 soon.

Option 2 is worth doing regardless of 1, because it is what makes the
divergence *visible* rather than discovered.

Note `sdmx_ml21` is genuinely different (45%/31%) and is not part of this.

## The guard needed changing, and the way it needed changing is the interesting part

After the merge the body comparison says **nothing** about the reader: two
modules each holding one forwarding `read` are trivially identical, so all
thirteen assertions passed while the reader could be re-forked in two lines.
A guard that cannot fail is the thing this issue exists to prevent, so leaving
it would have been worse than not having it.

Replaced with two that assert the *shape*: each reader module defines only
`read` and imports the shared class, and `V3Reader` actually carries the
implementation rather than being an empty shell a thin pair would also satisfy.
Both sabotage-checked. The body comparison is now scoped to `writer.py`.

## Asking what the flags were found a silent data loss

Writing `DataConstraint(constraint_type=ACTUAL)` to 3.1 emits no `@role` —
correctly, 3.1 removed it — and reading it back gives **`ALLOWED`**, because
that is the model default. `unrepresentable(cc, "3.1")` reported nothing lost.

The sibling field was already declared. `release_calendar` is removed from 3.1
for the same reason — both moved to `AvailabilityConstraint` — and **that row's
own comment names this exact shape**: *"a drop the mechanism built to answer
for drops denied"*. `@role` was missed when it was written.

Declared now, with `carried` as "not the default" rather than "present":
`ALLOWED` survives the trip since it is what an absent `@role` reads back as,
so only `ACTUAL` is a loss. Reporting the default would make every constraint
look lossy.

## The flag set

| flag | 3.0 | 3.1 |
| --- | --- | --- |
| `categorisation_version` | yes | no |
| `data_constraint_role` | yes | no |
| `release_calendar` | yes | no |
| `dimension_constraint` | no | yes |

Booleans, so a call site reads as the capability it depends on and a 3.2 sets
flags rather than adding branches on a version literal.

Not a flag, deliberately: the version *grammar*. `check_writable(v, "3.0")` is
right for both — `model/version.py` declares two grammars and 3.1 shares 3.0's,
so a `"3.1"` there would raise on every artefact. Worth knowing, because the
3.1 writer passing `"3.0"` reads like a copy-paste bug and is not one.

## The guard changed shape again, and for the same reason as last time

Body comparison would now compare two modules each holding one forwarding call
and pass while saying nothing. Replaced with three things it could not say
before — the two from !487 extended to both halves, plus the one that matters:

**every flag has a matching `gaps.py` row, and every asymmetric gap has a
flag.** `V3Generation` tells the writer what to emit; `gaps` tells a caller
what will be lost. They are one fact stated twice, and drift between them is
precisely what hid the `@role` loss. Sabotage-checked both directions.
