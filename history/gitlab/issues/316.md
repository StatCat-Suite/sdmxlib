# Issue #316: derived round-trip guard: three 'declared in the model, never persisted' bugs shipped because an absence does not fail a test

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-14 |
| Closed | 2026-08-17 |
| Milestone | %17 Query DSL: a second backend, and the evidence the first one lacks |
| Labels | `model`, `needs-design`, `storage`, `tests` |

Three bugs of one shape shipped, and all three were found the same way — by
someone reading an inventory, not by anything going red:

| | what was declared | what happened |
| --- | --- | --- |
| !303 | `Facet.is_multilingual` | `metadata_attribute` had no column; the MSD writer never read the field |
| #307 | `Concept.parent_id`… | …did not exist; storage had the column and wrote a constant `NULL` |
| #309 | `DataProvider.contacts` | no table could hold them; the writer never looked |

In each case the field existed in the model, the format readers and writers
usually handled it correctly, and **storage silently dropped it**. A caller got
an artefact back that was a valid object and not the one they persisted.

## Why the suite could not see any of them

**An absence does not fail a test.** Every existing test asserts that what it
put in came back — over a fixture that did not happen to set the missing field.
Add a field nobody's fixture uses and it is invisible forever. `is_multilingual`
survived like that through 4,882 passing tests; the round-trip properties in
`tests/unit/test_properties_roundtrip.py` did not catch it either, because
their strategies build from the same model whose field nothing exercises.

They also each hid behind a *plausible* half-implementation:

- a column that exists and is never written (`concept.parent_id`)
- a column that does not exist on one of three tables carrying the same
  concept (`metadata_attribute`)
- a table keyed so only one of two owners fits (`agency_contact`)

None of those reads as broken from inside the module that owns it. Two were
only visible by comparing *sibling* relations against each other, which is
what `test_storage_schema.py` now does for the facet group.

## What to build

A derived round-trip guard: for every persistable artefact type, build an
instance with **every** field set to a distinguishable non-default value,
write it, read it back, and assert equality — with the field list derived from
`attrs.fields()` rather than hand-written, so a new field is covered the day it
lands.

`attrs` makes the raw material available:

```python
[f.name for f in attrs.fields(Concept)]
# ['id', 'name', 'description', 'core_representation', 'parent_id', 'annotations', 'uri']
```

The load-bearing part is **derivation**. A hand-listed round-trip test is what
already exists and is what missed all three: it can only cover the fields
someone thought of, and the bug is always the field nobody thought of.

## The hard parts, which are why this is an issue and not a patch

1. **Generating a non-default value per field type.** `str`, `int`, `bool` and
   `InternationalString` are easy; `Ref[T]`, `Representation` (a sum type),
   `ItemList[T]` and recursive trees are not. Hypothesis strategies already
   exist for most artefacts (`tests/support/strategies.py`) and may be the
   right source — but see the caveat below.
2. **A strategy that leaves a field unset reintroduces the hole.** This is a
   rule the query oracles already carry in writing ("a strategy that leaves a
   field unset makes every predicate over it vacuous"). Any strategy reused
   here needs auditing for that, or the guard inherits the blind spot it
   exists to remove — `data_structures()` draws component facets with
   `for_component=True`, which omits `is_multilingual`, so it would *not* have
   caught !303's bug.
3. **Fields that legitimately do not round-trip.** Some are derived at write
   time (`depth`, `ancestor_ids`), some are resolution state. Those need an
   explicit, reasoned allow-list — and the allow-list must be small enough to
   read, or it becomes the place bugs hide.

## Related

- The facet fix (!303) added `test_storage_schema.py` guards that compare the
  three representation-bearing tables **against each other**. That catches
  drift between copies, which a round-trip cannot see. This issue is the
  complement: it catches a field with no storage at all, which comparing
  copies cannot see.
- #315 (`MetadataProvider`) is likely a fourth instance of the same shape.
  Worth checking whether this guard, had it existed, would have flagged it.
