# Issue #132: perf: explore lxml iterparse for streaming SDMX-ML parse

| | |
| --- | --- |

## Context

Surfaced by the pre-release XML perf audit (MR after !98). The current reader uses \`etree.parse(...)\` which builds the full DOM in memory before our Python code walks it. For large messages this peaks memory at roughly 2× the document size and gates wall-time on the full-tree build.

\`etree.iterparse\` is the streaming alternative: process elements as they arrive, then ``el.clear()`` to free them. Standard pattern in lxml-heavy projects (e.g. the ECB SDW API stack uses this).

## Why it's worth investigating

- **Memory**: peak RSS proportional to the largest single-element subtree (a codelist, say) rather than the whole message. For 100 MB+ messages this matters.
- **Wall**: skipping the second-pass walk shaves some time. Bigger win on parse-and-discard flows (e.g. registry indexing) where we don't need the full message held in memory.
- **Streaming**: enables future API where callers consume artefacts as they arrive — useful for HTTP streaming reads from REST endpoints.

## Why we haven't done it

The current code does subtree \`findall\` patterns (\`container.findall(s("Codelist"))\` then per-codelist \`findall(s("Code"))\`). \`iterparse\` requires inverting control flow — accumulate elements until the closing tag of the artefact type, dispatch, then clear. The shared \`_common.py\` helpers (\`read_codelists\`, \`read_dataflows\`, etc.) would need to be refactored to be invoked per-element from the streaming dispatcher.

## Proposed shape

1. Add an \`etree.iterparse(source, events=("end",), tag=...)\` driver in \`sdmx_ml/_common.py\` keyed by the high-level container tags (\`Codelists/Codelist\`, \`Concepts/ConceptScheme\`, \`DataStructures/DataStructure\`, etc.).
2. Existing per-artefact reader functions take an already-located element and return the model object — they're mostly already structured this way.
3. Add \`el.clear()\` after each artefact is fully read.
4. Keep the existing \`etree.parse\` driver as the default; offer \`stream=True\` as an opt-in for large-message workflows.

Or: replace the existing driver entirely once the streaming version is proven on every fixture.

## Acceptance

- Parse benchmark on the 3.8 MB ESTAT fixture: peak RSS halved (memray watermark drops).
- Wall time: within ±5% of current (streaming has small overhead but avoids the second-pass walk; net should be at-par or better).
- All 8 SDMX-ML 3.0 fixtures still round-trip semantically identical.

## Surfaced by

Pre-release perf audit. Bench/parse profile showed lxml building the tree at the C level is fast; the Python walk dominates. iterparse may not move wall much for messages our current bench covers but is a strong move for the 100MB+ case.
