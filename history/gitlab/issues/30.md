# Issue #30: Redesign: Registry as SDMX IM artefact store, RestRegistry as HTTP client

| | |
| --- | --- |
| State | closed |
| Opened | 2026-04-01 |
| Closed | 2026-04-01 |

## Summary

Major design realignment to match the SDMX IM more faithfully.

## Changes

**Naming:**
- `Registry` becomes the pure in-memory SDMX artefact store (the SDMX IM concept)
- Current `Registry` → `RestRegistry` (HTTP client that populates a Registry)
- `FmrRegistry` stays as FMR-specific subclass of `RestRegistry`

**Model layer:**
- Drop `frozen=True` from all domain objects and `Ref` — immutability by contract not force
- Keep `slots=True` for performance
- Add `HasUrn` protocol — anything with `.urn` can be used where a Ref target is needed
- `Ref` accepts `HasUrn | SdmxUrn` at construction
- `Ref._resolved` is a plain mutable field set at registration time

**Registry semantics:**
- `reg.add(artefact)` — walks Ref fields, interns (one Ref object per URN), fills `_resolved` bidirectionally
- `reg.add_all([...])` — bulk, order-independent
- Edge identity: same URN → same Ref object (matches SDMX IM graph semantics)
- Node state: PRESENT / RESOLVED
- Pure domain — no network

**Format layer:**
- Readers accept optional Registry — interns Refs at parse time
- `Registry.load()` / `Registry.save()` convenience methods

## Motivation

The current design treats the REST session as the primary context. The SDMX IM says a Registry IS the artefact store — the REST connection is just one way to populate it. This enables local construction, multi-source graphs, and clean separation of network from domain concerns.
