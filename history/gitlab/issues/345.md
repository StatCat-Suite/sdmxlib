# Issue #345: SDMX-ML 3.1 silently drops RepresentationMap data-type endpoints and Level/CodingFormat, and gaps.py says nothing is lost

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-19 |
| Closed | 2026-08-19 |
| Labels | `bug` |

Found by a structural-duplication scan during the %17 review. Verified in both
directions; nothing here is inferred.

## The data loss

```python
# a document the 3.1 XSD accepts
<str:RepresentationMap agencyID="AG" id="RM" version="1.0">
  <str:SourceDataType>String</str:SourceDataType>
  <str:TargetDataType>String</str:TargetDataType>
  ...
```

| | reads `SourceDataType` | reads `Level/CodingFormat` |
| --- | --- | --- |
| `sdmx_ml30.reader` | ✅ `MapDataType('String')` | ✅ `Facet(max_length=3)` |
| `sdmx_ml31.reader` | ❌ `None` | ❌ `None` |

The writers match: `sdmx_ml30.writer` emits both, `sdmx_ml31.writer` emits
neither. So a 3.1 document round-trips lossily, **and** a model built from a
3.0 document loses those fields when written as 3.1.

Both elements are declared in the vendored 3.1 XSD:

- `tests/schemas/sdmx_ml31/SDMXStructureStructureMappings.xsd:390` —
  `<xs:element name="SourceDataType" type="common:DataType"/>`
- `tests/schemas/sdmx_ml31/SDMXStructureHierarchicalCodelist.xsd:153` —
  `<xs:element name="CodingFormat" type="CodingTextFormatType" minOccurs="0">`

So this is not a 3.1 spec change. It is a gap in the fork.

## `gaps.py` says nothing is lost

```python
sl.unrepresentable(rm, "3.1")   # () — "nothing will be dropped"
sl.unrepresentable(h,  "3.1")   # ()
```

That module exists so drops are *answerable in advance*, and its own docstring
says **"dropping is the one that burns an author"**. Here the drop happens and
the declaration denies it, which is worse than an undeclared gap: a caller who
does the right thing and asks gets told they are safe.

## Why nothing caught it

The 3.1 reader's header says *"Forked from the 3.0 reader at parity."* The
fixtures were forked too, and trimmed in the same places:

```
3.0  with_representation_map_variants.xml → SourceCodelist ×2, TargetDataType ×1
3.1  with_representation_map_variants.xml → SourceCodelist ×1   (no *DataType)
```

A fixture named `..._variants` that omits the variant in question. The
round-trip guard then passes because both sides lost the same thing — the
fixture-level form of *"a strategy that leaves a field unset makes every
predicate over it vacuous"* (CLAUDE.md, Differential properties, rule 4).

`CodingFormat` appears in **no fixture in any generation**, so 3.0's support
for it is unguarded too — it works today by accident, not by test.

## Scope

- Port the two branches into `sdmx_ml31/reader.py` and `writer.py`.
- Add `SourceDataType` / `TargetDataType` to the 3.1 fixture and
  `CodingFormat` to a 3.0 *and* a 3.1 fixture.
- A guard that the two fixture sets do not diverge in *coverage* — the
  mechanism that produced this. Comparing the element vocabulary of the 3.0
  and 3.1 fixture directories would have caught it as a diff.
- See #346 for the fork itself, which is why this class of bug is cheap to
  create here.
