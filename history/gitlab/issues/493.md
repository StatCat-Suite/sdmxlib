# Issue #493: Large reads spend 35% (3.13) to 58% (3.14) of their time in the cyclic GC

## Problem

On large reads, a third or more of the time goes to CPython's cyclic garbage collector, not to sdmxlib. On Python 3.14, the version we now require, the share is larger again. A reader builds hundreds of thousands of objects that are not reference cycles, and the collector repeatedly scans them looking for cycles.

For the 500,000-code synthetic codelist read as SDMX-JSON (`bench/compete/cache/scale/synthetic-500000-2.0.json`), measured on uv's CPython builds with interleaved runs and the best of 3:

| | GC on | GC off | GC's share |
| --- | --- | --- | --- |
| Python 3.13.13 | 1,454 ms | 1,072–1,082 ms | 35% |
| Python 3.14.8 | 1,696–1,711 ms | 1,078 ms | 58% |

**With the collector off, 3.13 and 3.14 are identical.** The 3.14 slowdown on large reads is all GC.

## How this was found: what the 3.14 migration (!631, !632) did to speed

`just bench-compete` and `just bench-compete-scale` were run with alternating repeats. The competitor versions were identical across runs (sdmx1 2.27.0, pysdmx 1.21.0), as were lxml, duckdb, msgspec and attrs.

- **Our code: neutral.** Pre-migration code (9378b97) against current main (3d9e2e4), both on the same 3.14 interpreter, differ by at most ±2% on every operation.
- **The interpreter build: 4–10% from Homebrew alone.** Homebrew's CPython 3.14.8 is slower than uv's 3.14.8 on identical code: sdmxlib +0–12%, pysdmx +5–16%. Use uv's managed Python for development and benchmarks.
- **3.13 → 3.14 on uv's builds:**
  - writes are flat or faster (−1 to −10%);
  - small and medium reads are 0–9% slower;
  - large reads grow worse with size. At 500,000 codes: JSON read +27%, 2.1 read +8%, 3.0 read +13%. pysdmx's large XML reads lose 10–12% the same way.

  That size dependence is what pointed at the collector. The table above confirms it.

## Options

All of these need the usual perf evidence: interleaved A/B/A runs, plus retained and peak memory before and after.

1. **Pause the collector while a reader builds**, then restore it. This saves about 26% (3.13) and 37% (3.14) on a large read. But `gc.disable()` is process-global: in a threaded server, one parse pauses collection for every thread, and two overlapping parses can re-enable it under each other. It needs a reference-counted, thread-safe guard (pause on 0 → 1, restore on 1 → 0), never a bare `disable()`/`enable()` pair. Peak memory rises by whatever cycles accumulate during the read, which needs measuring. Cyclic garbage from other threads waits until the guard releases.
2. **Raise the generation-0 threshold for the duration of a read** (`gc.set_threshold`). It is just as process-global as option 1, and its gain needs measuring.
3. **`gc.freeze()` for long-lived artefacts.** It moves current objects to a permanent generation that is never scanned. This is safe with threads and right for a serving process that caches large artefacts, such as `LocalRegistry`'s resolve cache holding `H_CP_GEO_FED`'s 499,138 nodes. It does not help the read itself.
4. **Fewer collector-tracked objects per item.** Tuples and dicts holding only atomic values are untracked, but slotted attrs instances are always tracked. Fewer container objects per code, such as a shared empty `InternationalString` or `Annotations` (#377 did some of this), shrink every scan.

Options 3 and 4 are safe. Option 1 is the big win, but it needs a careful concurrency design. Whichever lands, guard it with a count rather than a clock, for example by asserting with `gc.callbacks` that no collection runs during a guarded read.

Related: #466 (SDMX-JSON read gap to pysdmx). Part of that gap may be the same collector cost, since msgspec structs are untracked when they hold no containers, while attrs instances are always tracked.
