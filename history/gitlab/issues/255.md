# Issue #255: code_query folds accents and punctuation in label search; hierarchy_query does not

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-09 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `design`, `dsl`, `needs-design` |

Surfaced while writing the #249 oracle: the two query DSLs match natural-language labels by different rules, and neither says so at the API surface.

## The asymmetry

`code_query` folds accents and punctuation on both sides before the `ILIKE` (`_label_norm` / `_label_match_sql`), for `name[lang]`, annotation titles and annotation texts. `hierarchy_query` emits a plain `ILIKE` for the same three fields.

Measured, same three labels loaded into each artefact:

| Filter | `code_query` | `hierarchy_query` |
| --- | --- | --- |
| `name["en"].contains("Montreal")` vs *Montréal* | `['MTL']` | `[]` |
| `name["en"].contains("Trois Rivieres")` vs *Trois-Rivières* | `['TR']` | `[]` |

The `code_query` behaviour is deliberate and well argued — the comment above `_LABEL_NORM_REGEX` explains why `\p{P}\p{Z}` rather than `[^a-zA-Z0-9]` (it preserves Inuktitut syllabics and every other non-Latin script). Nothing suggests the hierarchy side was a decision at all; the two emitters were written at different times and the fold was only added to one.

This matters because the two DSLs are presented as siblings — `hierarchy_query`'s own module docstring says it "mirrors `code_query`" — so a user who learns accent-insensitive search on a codelist gets silently different results against a hierarchy holding the same labels.

## Second, smaller finding

The `_LABEL_NORM_REGEX` comment offers `"St Johns" ~ "St. John's"` as a worked example. It does not hold:

```python
lazy.codes.filter(code.name["en"].contains("St Johns")).ids()   # [] — label is "St. John's"
```

*St. John's* folds to `St John s` (the apostrophe is punctuation, so it becomes a space), while the needle folds to `St Johns`. Substring fails. The *Montréal* and *Trois-Rivières* examples in the same comment do work; only the possessive one does not. Either fix the comment or decide that intra-word punctuation should be deleted rather than spaced — which is a different fold, and would also change `Trois-Rivières`.

## The decision

Pick one and write down why:

- **A. Fold in both.** Move `_label_norm` / `_label_match_sql` to a shared home and use it for `hierarchy_query`'s `_NameField`, `_AnnotationField` and `_AnnotationTextField`. Consistent, and the argument for folding is no weaker on a hierarchy node than on a code — hierarchy nodes carry the same place names.
- **B. Fold in neither, and expose the fold explicitly.** A separate `.matches(...)` or a `fold=` keyword, so the caller chooses. Defensible on the grounds that a silently accent-insensitive `contains` is surprising, and it keeps the index-friendly path available.
- **C. Keep the difference,** and document it prominently on both accessors. Hard to argue for, but if there is a reason — index shape on `hierarchy_node`, say — it belongs in the record.

Note the sharing in A has a cost worth naming: `sdmxlib.sql` already exists as the shared-SQL-primitives home, so that is where a shared `_label_norm` goes, and putting it there makes the fold part of the cross-library surface pinaxlib sees.

## Test gates

- `tests/support/oracle._label_matches` currently documents the asymmetry and points here; `tests/support/hierarchy_oracle._matches` models the plain `ILIKE`. Whichever option wins, both oracles change and the two `test_name_predicates_agree_with_oracle` properties keep them honest.
- An explicit example test with a real accented label in both DSLs, so the chosen semantics is pinned by something a reader can see, not only by a generative property.
- If A: the `St Johns` example either passes or leaves the comment.
- Add the accented/punctuated cases to the strategies — `international_strings` draws from a UTF-8 alphabet, so accents occur, but nothing currently guarantees an example that *only* differs by a diacritic.
