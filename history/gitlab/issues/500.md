# Issue #500: bench-compete reports sdmxlib's unchecked writes as INVALID without saying the default would refuse them

## Problem

`just bench-compete` times each writer alone, so it calls `serialize(message, version=fmt, validate=False)` (`bench/compete/libs.py:160`). It then checks each output against the schema and prints `INVALID` (`libs.py:317`).

For sdmxlib, that reports a file the library would never write with its defaults. On BIS's corpus:

```
codelist      sdmxlib -> 3.0   2.2 MB  INVALID: … Element '…}Parent': [facet 'pattern'] …
```

This is BIS's `_T` (SDMX's "total") as a parent. SDMX-ML 3.0.0 types `<Parent>` as an NCName (a schema erratum, fixed in 3.1), and #432's `_check_code_parents_in_30` refuses this exact case by default, pointing at 3.1 or 2.1. The line reads as "sdmxlib writes schema-invalid 3.0", which is false. It was misread exactly that way on 2026-10-19: a bug was nearly filed, and #492's closing note had to be corrected.

`just bench-compete-scale` already does the right thing: it writes with the default `serialize` and prints `sdmxlib will not write SDMX-ML 3.0: <reason>` (`scale.py:142-146`).

## Fix

Keep the unvalidated write for timing. For sdmxlib's output, also ask whether the default `serialize` would refuse it, and say so instead of `INVALID`. For example:

```
codelist      sdmxlib -> 3.0   refused by default: 1 codelist has a parent SDMX-ML 3.0 cannot name (#432)
```

Keep `INVALID` for output that the default *would* write and that still fails the schema. That is a real writer bug, and the report has to stay able to show it.

## Done when

- The BIS report's sdmxlib 3.0 codelist line says "refused by default" and gives the reason.
- A test, or a sabotage run, shows `INVALID` still appears for an sdmxlib output that validates by default but fails the schema. The guard has to stay able to fail.
- The README's description of the Output section says what the two labels mean.
