# Issue #416: Organisation-scheme version is 1.0 in every format, but SDMX-JSON writes any value and 3.x silently drops it for MetadataProviderScheme

| | |

| State | closed |

| Milestone | %20 3.x-native model: hold all of 3.x, project to 2.1, validate at ingest |
| Labels | `bug`, `conformance`, `json` |

## Summary

An organisation scheme's version is `"1.0"` in **every** SDMX format, but the
model accepts any version. The writers handle this inconsistently:

| scheme | SDMX-ML 2.1 | SDMX-ML 3.0 / 3.1 | SDMX-JSON 2.0 / 2.1 |
|---|---|---|---|
| `AgencyScheme` v2.0 | refused ✅ | refused ✅ | **written, schema-invalid** |
| `DataProviderScheme` v2.0 | refused ✅ | refused ✅ | **written, schema-invalid** |
| `MetadataProviderScheme` v2.0 | refused (no 2.1 form) ✅ | **written; version silently becomes `1.0`** | **written, schema-invalid** |

Measured against `main` @ `6cf7bc5` with the raw writers from
`tests/unit/test_wire_conformance_gate.py` (`_WRITERS`, `_is_schema_valid`),
then read back with `parse`.

## Why: the schemas agree on one value

- **2.1** — `SDMXStructureOrganisation.xsd` gives the scheme types
  `version fixed="1.0"` (and `isFinal fixed="false"`).
- **3.0 / 3.1** — `@version` is `use="prohibited"`, so the reader supplies `1.0`.
- **SDMX-JSON 2.0 and 2.1** — `MaintainableWithoutVersionType` gives
  `"version": {"const": "1.0"}`. All five organisation-scheme types
  (agency, data provider, data consumer, metadata provider, organisation unit)
  derive from it.

## Two comments are wrong

`model/validation.py` around line 2019, in the #230 check:

> SDMX-JSON has no such restriction and round-trips the version untouched.

The issue message makes the same claim: `"SDMX-JSON preserves it"`. The JSON
schema's `const` says otherwise. JSON round-trips the value *because* the JSON
writer applies no check, and the document it produces is invalid.

The #230 check also iterates only `(*msg.agency_schemes, *msg.data_provider_schemes)`.
`MetadataProviderScheme` arrived later and was never added, which reopens
the silent loss #230 fixed. Reading the version back returns `1.0` from a
schema-valid document, so no test can see it.

## Proposed fix

This rule does not depend on the format, so the place to enforce it is
**construction / `Registry.add`**, not the writers. The precedent already
exists: `_FIXED_SCHEME_IDS` pins these schemes' **ids**
(`AGENCIES`, `DATA_PROVIDERS`, `METADATA_PROVIDERS`) in `validate()`, at
ingest. The version is pinned by the same schema mechanism and belongs beside it:

```python
_FIXED_SCHEME_VERSION = "1.0"   # 2.1 fixed=, 3.x prohibited, JSON const
```

- Refuse `version != "1.0"` in `validate()` for every organisation-scheme type.
  Better still, drop `version` from the constructor so the bad state cannot be built.
- Delete the per-format check, or keep it only as a guard, and correct both comments.
- Reader side: a 2.1 document cannot carry anything else, and a 3.x or JSON
  document that does carry something else is invalid, so readers stay tolerant
  and normalise to `1.0` with a warning.

Part of the "3.x-native model" milestone. See the tracking issue for how this
case fits the wider question of which state the model should refuse at ingest.
