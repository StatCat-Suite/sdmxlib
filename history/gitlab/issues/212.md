**Phase 1**, runs parallel to the mutation pilot (#test-3). Everything here is measurable; no judgement calls about test *quality* (that is #test-4).

## Baseline as measured today

- 94 unit-test files, ~1900 unit tests; 2583 collected under `-m "unit or docs"`, 50 s wall.
- **91% line coverage** (`fail_under = 80`).
- **0 test classes** — CLAUDE.md's plain-function rule is fully honoured.
- Only **5 of 94** files use mocks. Tests are overwhelmingly real-object based, which is why mutation testing and property testing are both viable here.
- Only **20 of 94** files use `parametrize`.

## 1. Coverage gaps need verdicts, not reflex

| Module | Cov | Likely verdict |
| --- | --- | --- |
| `api/registry.py` | **52%** | network-facing; how much is genuinely exercised only by `live` tests? |
| `api/client.py` | **57%** | same |
| `catalog.py` | **69%** | *not* network-bound — probably a real gap |
| `data_store.py` | 77% | Protocol; may be structurally uncoverable |
| `sdmx_ml31/reader.py` | 78% | near-duplicate of ml30 (82%) — the same branches are untested in both |
| `model/convert.py` | 81% | public `to_dict`/`from_dict` API |

Deliverable is a **verdict per module**, not a coverage number: *covered by live tests* / *genuinely untested* / *unreachable*. Raise `fail_under` only where a verdict says the gap is real and has been closed.

The ml30/ml31 pair is the interesting one — the readers are near-duplicates and so are their tests, so a gap in one is a gap in both. Worth checking whether the untested branches are the *same* branches.

## 2. Assertion-free tests — 19 of them

```
tests/unit/test_validation.py   13   (test_validate_*_no_raise, test_*_pattern_valid)
tests/unit/test_storage_writers.py, test_representation.py, …
```

Most are legitimately "this must not raise" — that *is* the assertion. But it is invisible to a reader and to any tooling. Give each a verdict: make the intent explicit (a comment, or asserting the returned value), or delete if redundant. Do not mass-rewrite.

## 3. `_structure_ingest` is never named in any test

236 statements, 89% covered — entirely transitively, through the SDMX-JSON reader tests. Covered is not the same as tested: no test names the module, so nothing pins its behaviour independently. Decide whether that is acceptable (it is an internal seam) or whether it wants direct tests.

## 4. Suite runtime is dominated by two tests

```
17.35s  test_concurrent_reads.py::test_concurrent_get_identity_mixed_urns
15.99s  test_concurrent_reads.py::test_concurrent_get_cache_hit_invariant
```

33 s of a 50 s suite. Everything else is under a second. These are worth keeping — concurrency invariants are exactly what you cannot test any other way — but they should carry their own marker so the inner dev loop and the mutation runs (#test-3) can deselect them without deselecting correctness.

## Test gates

- A written verdict for every module below 90%, in the MR description.
- A marker separating the slow concurrency tests; `just test` timing recorded before/after.
- No net loss of assertions.
