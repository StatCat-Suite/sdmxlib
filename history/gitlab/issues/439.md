## Summary

The model and the store key nested items by their **leaf** id, but SDMX identifies them by **path**. A valid artefact that repeats an id in a different branch is refused.

Found by the registry sweep (!516):

| kind | example | what repeats |
|---|---|---|
| Category | `ESTAT:popul(1.0)` | `hsw_ac` four times, e.g. `…hlth.hsw.hsw_apex.hsw_ac` and `…labour.employ.lfso.lfso_20.hsw_ac` |
| MetadataAttribute | `BIS:DP_NEWS(1.0)` | `URL` under both `IMAGE` and `LINK` |
| Hierarchy node | BIS 6, ECB 27, OECD 22, IMF 31 hierarchies | e.g. BIS numbers nodes per level (`1`, `1/1`, `1/2/1`); OECD `MR` at the root and under `TYPO_METRO` |

Category and MSD: **DuckDB primary-key violation** at `add` (one each). Hierarchies: refused by `validate()` ("duplicate node id"). Across all four registries there are **zero sibling duplicates**; every repeat is in another branch.

## What SDMX allows

- Nested Category and MetadataAttribute URNs are dot-paths. The XSD unique constraints are sibling-scoped (`Category_UniqueCategory`, selector `structure:Category`).
- Hierarchies, 2.1: sibling-only (`SDMXStructureHierarchicalCodelist.xsd:43,84,152`). So BIS, ECB and OECD's 2.1 data is **valid and we refuse it**.
- Hierarchies, 3.0/3.1: `Hierarchiy_UniqueHierarchicalCode` (`sdmx_ml30/SDMXStructure.xsd:685-688`) selects `.//structure:HierarchicalCode`, i.e. descendant-wide. So IMF's 3.0 data **is** invalid there, and our rule matches the 3.0 schema.

## Root cause

- Storage: `UNIQUE (scheme_urn, category_id)` (`schema.py:285`), `UNIQUE (msd_urn, attribute_id)` (`:532`), `UNIQUE (hierarchy_urn, node_id)` (`:505`); URNs built as prefix + leaf id (`writers.py:1171,1324,1874`); parent columns hold a leaf id.
- Model: `CategoryScheme._flat` / `_parent_of`, `item_ref(...)` and `Hierarchy.codes`' id index (`model/hierarchy.py:214-226`) are keyed by bare id.
- Validation: `_validate_hierarchy` (`model/validation.py:688`) checks duplicates over the flattened node list.

## Fix direction

- Key nested items by path, in the model's indexes and in storage (URN = prefix + dotted path; parent = parent's path; uniqueness on `(scheme, parent_path, id)`).
- Hierarchy uniqueness: sibling-scoped in `validate()` (format-independent), and the descendant-wide rule becomes a 3.0/3.1 serialisability check: format-dependent, so it belongs at the writer (#419's split).
