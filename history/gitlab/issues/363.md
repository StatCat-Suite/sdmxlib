# Issue #363: Release blocker? select() names frame columns after the storage column, not the accessor

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |

Raised while assessing whether the breaking release has an obvious missing
piece. This is the one I would want settled first, because it is user-visible in
the commonest call in the DSL and expensive to change afterwards.

## What a caller sees

```python
df = reg.query(sl.q.code).select(sl.q.code.id, sl.q.code.urn).collect()
df.columns          # ['code_id', 'code_urn']  — not ['id', 'urn']
df["id"]            # KeyError
```

Same for the artefact roots:

```python
reg.query(sl.q.codelist).select(sl.q.codelist.id, sl.q.codelist.agency).collect()
# ['resource_id', 'agency_id']
```

There is an escape — `select(id=sl.q.code.id)` names it `id`, and keyword and
positional forms can be mixed — but the **default** is the storage name.

## How widespread

Enumerated across all 34 query roots: **29 distinct accessor→column mismatches**,
and they are on the most-used accessors.

| Accessor | Projects as | Relations |
|---|---|---|
| `id` | `resource_id` | 17 |
| `type` | `artefact_type` | 17 |
| `id` | `code_id` / `concept_id` / `category_id` / `node_id` / `agency_id` / `provider_id` / `component_id` / `group_id` / `attribute_id` / `annotation_id` | 1 each |
| `urn` | `code_urn` / `concept_urn` / `node_urn` / … | 1 each |
| `position` | `ordinal` | 3 |
| `position` | `sibling_index` | 1 |
| `role` | `component_type` | 1 |
| `kind` | `value_kind` | 1 |
| `index` | `region_idx` | 1 |
| `source` / `target` | `source_value` / `target_value` | 1 each |
| `component` | `component_id` | 1 |

## It is a decision, not an oversight

`AnyCol.projected_name` states the reasoning:

> The physical column for everything structural: `q.code.id` reads `code_id` and
> projects as `code_id`, so a caller replacing a hand-written `SELECT code_id …`
> gets a frame that needs no renaming.

That is a real audience — someone migrating raw SQL to the DSL — and the choice
serves them well.

**But the same property applies the opposite rule one class down.** `ObsCol`
overrides `projected_name` to return the SDMX component id, and says why:

> the physical name is an implementation detail of the binding: a caller writes
> `obs.col("REF_AREA")` and getting back a column called `GEO` leaks the layout

Both arguments are good. They point in opposite directions, and the library
currently applies one to observations and the other to structure. A caller
selecting from both in one session sees both conventions.

## Why it belongs in this release

* It is in the return value of `select().collect()`, the DSL's main terminal.
* Changing it later breaks every consumer's dataframe code — column access is
  string-keyed, so it fails at runtime, not at type-check.
* The DSL is what the breaking release is *for*. Shipping a surprise in its most
  common path, then fixing it in the next major, is two migrations for one API.

## Options

1. **Project the accessor name.** `q.code.id` → `id`, `q.dsd.type` → `type`.
   Matches the observation rule, matches what the caller wrote. Collides when
   two relations in one projection both expose `id` — but `select()` already
   refuses duplicate output names, so the collision is reported rather than
   silent, and the keyword form resolves it.
2. **Keep storage names**, and document the keyword form as the way to get
   pretty ones. Zero work, and the raw-SQL migration path stays seamless.
3. **Split the difference**: accessor name for `id`/`urn`/`type` (the 29 are
   dominated by these), physical elsewhere. Hard to explain, probably worst.

I lean (1) — the observation path already made this call, and "the column is
named what you asked for" is the polars/SQLAlchemy convention — but it is a
judgement about who the DSL is for, which is the maintainer's to make.
