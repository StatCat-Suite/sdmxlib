# Issue #494: Fold oracles decompose Hangul syllables that DuckDB's strip_accents keeps whole; the sweep never reached them

## Problem

Both fold oracles (`tests/support/oracle.py` and `tests/support/hierarchy_oracle.py`) disagree with DuckDB's `strip_accents` on all **11,172 Hangul syllables** (U+AC00–U+D7A3). `_label_norm` NFD-decomposes a syllable into its conjoining jamo, while DuckDB leaves it whole:

| | 한 (U+D55C) |
| --- | --- |
| `oracle._label_norm` / `hierarchy_oracle._label_norm` | U+1112 U+1161 U+11AB |
| DuckDB `strip_accents` | U+D55C |

This changes a predicate's answer. With the label `한국` and the needle `하` (U+D558, whose NFD is U+1112 U+1161, a prefix of 한's jamo), a folded `contains` gives **oracle `True`, DuckDB `False`**. A whole-syllable needle still agrees, because both sides fold the same way.

## Why no test caught it

`test_oracle_fold.py` checks each oracle against `strip_accents` character by character, but its sweep stops at U+2FFF:

```python
_SWEEP = [chr(i) for i in range(0x20, 0x3000) if chr(i).isprintable()]
```

Hangul starts at U+AC00, so the guard never reached it. Swept over every printable code point instead, the oracles disagree on exactly these 11,172 characters. That is true on Python 3.13 as well, so this is pre-existing and not caused by the 3.14 move. On 3.14, 60 further code points that Unicode 16 added also disagreed; !631 modelled those.

The property tests can reach it. Code names are drawn from `_XML_SAFE_TEXT` (`st.text` over any UTF-8 character), so a folded-label property at 20x width can draw a Hangul label, and then a needle that disagrees. When it fails, the bug will be in the oracle, not the compiler. This is the failure mode CLAUDE.md's oracle rules warn about.

## Proposal

- **Model DuckDB's behaviour in both oracles, each restating it independently** (rule 1): a precomposed Hangul syllable is left whole, not decomposed. That is the same per-character exception !631 added for the Unicode 16 code points.
- **Widen `_SWEEP` to every printable code point.** The fold oracle over all ~285,000 takes about 0.6 s in one DuckDB round trip. That makes the guard total, so the next gap of this kind fails here rather than in a property at 20x.
