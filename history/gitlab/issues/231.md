**Phase 5.** The last unextracted constraint kind: `xs:unique` identity constraints. On types sdmxlib models — **37** in 2.1, **42** in 3.0, **43** in 3.1.

## Why these are easy to miss

An identity constraint sits *beside* the element declaration rather than inside the type, so reading the type tells you nothing about it. Nothing in the model hints the field is limited either. `DataConstraint_CubeRegionInclusion` — at most one `CubeRegion` per `include` value — was found in milestone 10 only because a generated constraint happened to draw two regions with the same flag, and it exists in 3.0/3.1 but not 2.1, so it is also version-specific in a way nothing else signals.

## Scope honestly: this is an audit, not 42 known bugs

Spot-checking two of them showed both are **already enforced**: a `Codelist` with two codes sharing an id and an `AgencyScheme` with two agencies sharing an id are each refused by `validate` today. Item-id uniqueness is broadly covered.

So the expected yield is a minority of the list — constraints on something other than item ids, like the CubeRegion one. Do not open this expecting 42 fixes; open it expecting a complete list where today there is none, and some number of real gaps in the residue.

## The test

Extract `(owning type, constraint name, selector xpath, field xpaths)`, resolve each to a model-level statement, and check it. Where a constraint is already covered by an existing rule, say which rule — that mapping is the deliverable as much as any new check, because it is what makes the next schema refresh cheap to re-audit.

## Done when

Every `xs:unique` on a modelled type is either enforced, mapped to the existing rule that covers it, or listed as not-applicable with a reason.
