The four query DSLs have a composition law per clause and no stated principle. #264's design review found that the laws are *already* consistent — they just were not written down, so each new clause has been a fresh argument.

## The principle

> **Every composition call refines the query. Nothing a later caller adds can undo what an earlier call established.**

That is #260's reasoning for `limit`, generalised. It already explains most of the surface, including two errors that until now looked like ad-hoc usability guards:

| clause | law | why |
| --- | --- | --- |
| `filter(p)` | AND | narrows rows |
| `limit(n)` | `min` | lowers the ceiling |
| `offset(n)` | `max` | raises the floor (#264) |
| `select(...)` | not a row refinement -> returns `FrameQuery`; `.filter()` on it raises |
| `group_by(...)` | not a refinement, changes shape -> raises after `sort_by`/`limit` |

Both existing errors fall out of the principle rather than being bolted on, which is the test of whether a principle is real.

## The scope exclusion, which matters

**Ordering is not governed by refinement.** Refinement is a statement about which rows come back; `sort_by` does not change that. Applying the principle to it by symmetry was a category error and produced a live bug — see the `sort_by` issue.

**Filters are one-way and stay that way.** No peer offers un-filtering: Django has no `.unfilter()`, and SQLAlchemy's `where(None)` compiles to `AND NULL`, which is a slot accepting garbage rather than a reset. Widening a scoped query is security-adjacent, so the absence is correct here too.

## Why a property and not a docstring

Nothing today asserts the general law. `narrow_limit` has a unit test; the invariant it is an instance of has nothing, so a new clause can violate it silently.

The property, over all four DSLs:

- **Monotonicity.** For any query `q` and any row-set composition call `c`, `rows(c(q))` is a subset of `rows(q)`.
- **Order independence.** For any two row-set calls `c1`, `c2`, `rows(c1(c2(q))) == rows(c2(c1(q)))` — except where the pair is guarded, in which case both orders raise.
- **Idempotence.** `c(c(q)) == c(q)` for `limit`, `offset`, `filter`.

Generated over the existing `_paired_tree` predicates plus drawn limits/offsets, in the differential-property files.

## Prior art, for the record

Among declarative peers exactly one law is unanimous — `filter` = AND (SQLAlchemy, Django, ibis). `order_by` is append / replace / **prepend** respectively; `limit` is last-wins / clamp / nest. There is nothing to copy, which is why an internal principle is needed rather than a reference.

## Scope

- The principle in `_query_common`'s module docstring and in `docs/design/`, with the scope exclusion for ordering stated explicitly.
- The cross-DSL property.
- Each guard raise cross-referenced to the principle, so the next one is derived rather than argued.
