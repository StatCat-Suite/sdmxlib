# Issue #305: A DataStructure holding a MeasureDimension cannot be serialised at all — AttributeError, every version

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-11 |
| Closed | 2026-08-11 |
| Labels | `bug` |

Found while auditing `xs:unique` constraints for #231, and out of that issue's scope.

## Reproduction

```python
cs    = ConceptScheme(id="CS", maintainer="AG", version="1.0", name={"en": "c"},
                      concepts=[Concept(id="M1", name={"en": "m1"})])
csref = Ref[ConceptScheme].unresolved(SdmxUrn.parse(".....ConceptScheme=AG:CS(1.0)"))
dsd   = DataStructure(id="DSD", maintainer="AG", version="1.0", name={"en": "d"},
                      dimensions=[MeasureDimension(id="M1", concept=cref, representation=csref)])

serialize(StructureMessage(concept_schemes=[cs], data_structures=[dsd]), version="2.1")
# AttributeError: 'MeasureDimension' object has no attribute 'enumeration_format'
```

Not a `ValidationError` — an `AttributeError` out of the validation layer. It happens for **any** DSD containing a `MeasureDimension`, whatever its representation, in every version.

## Cause

`MeasureDimension` deliberately is *not* a `Component` subclass. Its docstring says so and gives the reason: its representation is a ConceptScheme, not a Codelist, and narrowing a mutable attribute in a subclass is unsound. So it carries no `enumeration_format` field.

Everything that walks DSD components assumes otherwise:

```
model/validation.py:1156,1183            component.enumeration_format
formats/sdmx_ml21/writer.py:183          dim.enumeration_format
formats/sdmx_ml30/writer.py:520          dim.enumeration_format
formats/sdmx_ml31/writer.py:528          dim.enumeration_format
formats/sdmx_json/_structure_dto.py:532  dim.enumeration_format
```

Validation raises first, so the writers have presumably never been reached with one.

## Why it was never noticed

No fixture or strategy builds a `MeasureDimension`. The class is modelled, exported, and documented, and nothing exercises it end to end — so a type that cannot be written at all looked fine.

`MeasureDimension` is 2.1-only in SDMX terms (3.0 replaced it with the measure list), which probably explains the low traffic, but the crash is version-independent because it fires in shared validation before any writer is chosen.

## Scope

- Decide whether the walkers should use `getattr(component, "enumeration_format", None)` or whether `MeasureDimension` should grow the field as `None`. The first is a one-line change per site and keeps the model honest about what the class is; the second is fewer sites but re-introduces a field the class deliberately does not have.
- Then check the writers actually emit a valid `<structure:MeasureDimension>`, since none of them can have been exercised.
- A round-trip test and a strategy that builds one, so this cannot regress silently again.

## Related

- #231 — the audit that found it. Its `('@type',)` constraint (`SingleMeasureDimension`: at most one `MeasureDimension` per 2.1 `DimensionList`) is currently **unreachable** because of this crash, and is recorded that way rather than as enforced.

## Comments

### 2026-08-11

Closed by !300, but the issue title and body are wrong and should be read with this correction.

**The report was mine and it was wrong.** The reproduction put the `MeasureDimension` in `dimensions`, which is typed `ItemList[Dimension]`; there is a dedicated `measure_dimension` slot. Used as designed the component wrote valid SDMX-ML 2.1 and round-tripped the whole time. "Cannot be serialised at all" was never true.

What *was* true, and is now fixed:

1. **Misuse crashed instead of explaining.** Putting it in `dimensions` raised `AttributeError: no attribute 'enumeration_format'` from inside validation. `MeasureDimension` deliberately is not a `Component` — 2.1's `MeasureDimensionRepresentationType` permits only `<Enumeration>`, so the field has no meaning on it. Walkers now tolerate its absence and the misplacement is refused with a message naming the right slot.

2. **The 3.x and JSON writers dropped it silently** — the defect actually worth having found. SDMX 3.0 removed the cross-sectional measure dimension and the 3.0/3.1 schemas have no such element, so the writers emitted a valid document one component short, and the round trip returned a DSD without it. No error anywhere. Now refused, like other downgrade hazards.

The scope section here proposed `getattr` vs adding the field to the class; `getattr` was correct, and the schema is the reason rather than taste. The "check the writers actually emit a valid `<structure:MeasureDimension>`" item resolved differently: the 2.1 writer already has a dedicated `_write_measure_dimension` that never touches `enumeration_format`, so only validation was crashing.

Also worth recording, since it is the reusable lesson: the audit that produced this issue found a real bug, but my reproduction reached it by misusing the API, and I wrote the issue from the traceback rather than from the supported shape. Re-measuring the premise before fixing is what caught it — the same step that has now corrected six issues in this milestone run.
