# Issue #262: dsl-12: give the query DSLs real And/Or/Not instead of a per-field negate flag

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `dsl`, `needs-design`, `type::feature` |

`filter()` only ANDs. Negation is a `negate: bool` field on two predicate kinds. There is no disjunction anywhere in either query DSL.

## What is actually missing

```python
@attrs.frozen
class _Eq(Predicate):
    field: _FieldExpr
    value: object
    negate: bool = False       # -> "!=" instead of "="

@attrs.frozen
class _IsNull(Predicate):
    field: _FieldExpr
    negate: bool = False       # -> "IS NOT NULL"
```

That is the whole of negation. Three consequences:

1. **`_StringMatch` has no flag**, so `~code.id.contains("X")` cannot be expressed at all. Negation is available for two of the ten predicate kinds — the same field × operation patchwork as #259, in a different guise.
2. **No `Or`.** Combined with the absence of `is_in` (#261), the DSL cannot express "A or B" by any route.
3. **The flag is redundant.** Measured in DuckDB against a table containing a NULL:

   ```
   a = 'x'            -> ['x']
   a <> 'x'           -> ['y']
   NOT (a = 'x')      -> ['y']      <- identical
   ```

   `NOT (p)` and `<>` select the same rows, so a `Not` node subsumes the `_Eq` flag with no semantic loss. Emitting `<>` can stay as a compiler-level rewrite (it is index-friendlier); it just stops being the API shape.

So the flag is not only inelegant, it is an incomplete encoding of a general operation.

## Hard prerequisite: #254

**Do not start this before #254 lands.** Annotation predicates currently compile to `JOIN sdmx.annotation`, and a JOIN is applied *before* the `WHERE`. Any predicate that reaches the row set by filtering the join cannot be placed under an `OR`:

```sql
-- WRONG: the inner join has already dropped rows with no 'note' annotation,
-- so they can never satisfy the left-hand branch either.
FROM sdmx.code c JOIN sdmx.annotation a ON ...
WHERE (c.code_id = 'A' OR a.title = 'x')
```

The same argument applies to `NOT`. #254 rewrites those predicates as correlated `EXISTS`, which composes correctly under any boolean operator. That issue is currently justified only by row duplication; this is the second and larger reason to do it.

## Design decisions

**Operator surface.** `&` / `|` / `~` on `Predicate` is the ecosystem idiom (polars, SQLAlchemy, Django `Q`). One footgun to document loudly: Python binds `&` and `|` *tighter* than `==`, so

```python
code.id == "A" | code.id == "B"     # parses as code.id == ("A" | code.id) == "B"
(code.id == "A") | (code.id == "B") # correct
```

polars and pandas both live with this and both document it. Consider whether `Predicate.__or__` should raise a targeted error when handed a non-`Predicate`, so the mistake reports itself instead of producing a `TypeError` from `str.__or__`.

**NULL semantics — the decision that matters.** `~p` will compile to SQL `NOT (p)`, which is *not* set complement. Measured:

```
(a = 'x') OR NOT (a = 'x')   -> ['x', 'y']      -- the NULL row is in neither branch
all rows                     -> ['x', 'y', NULL]
```

So `filter(p)` and `filter(~p)` do not partition the query. That is standard SQL three-valued logic and is almost certainly the right choice — the alternative, an anti-join set complement, is expensive and would surprise anyone who knows SQL — but it must be **documented on `__invert__`**, because it is the single most likely source of a "where did my rows go" bug report.

Note for whoever writes the laws: the testing proposal this came from claims `Not(Not(x)) ≡ x` is "expected to fail on nullable columns". Measured, it does **not** fail — `NOT` is an involution in three-valued logic, and `NOT (NOT (a = 'x'))` returns `['x']`. The law that genuinely fails is **excluded middle**, `p | ~p ≡ everything`. Assert the first as a law and the second as a documented non-law.

**Scope of `Or`.** Decide whether `|` is available across *any* two predicates or only within one field. Cross-field OR (`(id == "A") | (depth == 2)`) is the general case and is what makes the compiler tree-shaped; there is no reason to restrict it once #254 removes the JOINs.

## Scope

- `_And` / `_Or` / `_Not` predicate nodes in both `code_query` and `hierarchy_query`, with `__and__` / `__or__` / `__invert__` on the `Predicate` base.
- Recursive emission in `_emit_predicate` — parenthesise and concatenate params in emission order. The existing `(clause, params)` contract already supports this; the reason it does not work today is the JOIN side-effect, not the return shape.
- `CompileContext` is public (`sl.CompileContext`) and `Predicate.to_sql(ctx)` is its documented hook, so new node types are additive for downstream consumers — but check whether pinaxlib pattern-matches on sdmxlib predicate classes before assuming that.
- Keep `!=` / `is_not_null` as sugar for `~(...)`, or remove them. Either is defensible; having both an operator and a flag for the same thing is what this issue is retiring.
- `filter(a).filter(b)` stays equivalent to `filter(a & b)` — that is already an asserted property in both files and must keep passing.

## The testing payoff

This is what makes the generative suites meaningfully stronger, and it is worth stating because it is most of the return on the work:

- **A recursive Hypothesis strategy over the predicate tree** becomes possible. Today the strategies can only draw a flat conjunction, which is why #248/#249 test each predicate kind in isolation rather than in combination. Operator-precedence and parenthesisation bugs are invisible to a flat generator.
- **Real algebraic laws** to assert against the oracles: commutativity and associativity of `&` / `|`, distributivity, De Morgan, double negation, absorption. #260 lists the flat-conjunction subset available today; this unlocks the rest.
- The oracles already have the shape for it — both are `Callable[[row, rows], bool]` closures, so `And` / `Or` / `Not` are three trivial combinators on top.

## Test gates

- Differential properties over a *recursive* generated predicate tree, not just flat conjunctions.
- De Morgan, associativity, distributivity, double negation asserted as laws.
- Excluded middle asserted as an explicit **non**-law, with the NULL row named, so the documented semantics is pinned by a test rather than only by prose.
- Every predicate kind, including the JOIN-derived annotation ones, exercised under both `Or` and `Not` — the case that is wrong today and the reason #254 comes first.
- `test_every_predicate_kind_is_covered` in both files updated for the three new kinds.

### Scope is now larger than "both `code_query` and `hierarchy_query`"

Since this was written, %15 added two more query DSLs and %14 added an
aggregate predicate. All five now need the combinators, and all five compile
through the shared machinery in `model/_query_common.py`:

| class | module |
| --- | --- |

The good news is that this is *less* work than five times the original, not
more: #267 moved the whole `Predicate[R]` hierarchy into `_query_common`, so
`__and__` / `__or__` / `__invert__` go on the shared generic base once, and
`_And` / `_Or` / `_Not` are shared nodes. Only the per-DSL `_EMITTERS` tables
need the recursive arms.

`AggPredicate` is a separate type by design (#275) so an aggregate cannot reach
a `WHERE`; decide explicitly whether it gets its own combinators for `HAVING`
or is left alone.

### `model/expr.py` is not in scope here and should be

`ItemPredicate` — the in-memory predicate behind `item("x")`, used by
`ItemList.filter` — has `__invert__` and nothing else, the same gap in a
different place. It is much cheaper than the SQL side (it wraps a callable, so
`__and__` is two lines and cannot diverge from a compiler), and #251 has just
added the double-negation law and the partition law that the rest of the
algebra would extend.

Either fold it in here or split it; what it should not be is a fourth issue
observing the absence.

### One correction to the laws section

#251 measured that `~~p ≡ p` holds for `ItemPredicate` in memory, consistent
with this issue's finding that `NOT` is an involution in three-valued SQL. The
law that fails remains excluded middle. Nothing here changes — recorded so the
in-memory and SQL sides are known to agree.
