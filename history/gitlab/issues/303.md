# Issue #303: mutmut books surviving validation mutants as timeouts — 283 of them, and they are not hangs

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-11 |
| Closed | 2026-08-11 |
| Labels | `tests` |

Split out of #252, which conflated three things. This is the blocker: until it is resolved, mutation scores over anything the DuckDB-touching tests reach are unreliable and a full run does not finish in a working day.

## Symptom

Re-baseline of the existing six-module scope, after the fork-safety fix in !294:

```
                 pre-fix     post-fix (stopped at 89%, 4h04m)
survived            147                                  150
timeout             356                                  310
  validation        353                                  283
  collections         3                                    3
segfaults          many                                    0
```

Survivors plateaued at 150 three hours before I stopped it; every remaining mutant was a validation timeout burning its full budget (40 mutants advanced in the last 45 minutes).

Note the fork-safety fix made wall-clock **worse**: a segfaulting child used to die instantly, and now runs to its budget. Scores became trustworthy; runtime did not.

## They are not hangs

`x__validate_hierarchy__mutmut_2` applied by hand — it replaces a `prefix` argument with `None`:

```
53 covering tests, all pass, 2.13 s
```

So it is a **survivor**, and the child is burning its full 45 s budget doing 2 s of work.

## Rejected by measurement

Each of these was a working hypothesis at some point:

| hypothesis | test | result |
| --- | --- | --- |
| the mutant hangs | apply by hand, run covering set | 53 pass in 2.13 s |
| parallel contention | 8 concurrent copies of the set | 6 s, against a 45 s budget |
| DuckDB threads x `fork()` | force `SET threads=1` in conftest | unchanged, 14/14 timeout |
| escalation to full suite | read `PytestRunner.run_tests` | passes only covering tests, with `-x` |
| fork + DuckDB deadlock | isolated fork probe | 5 ms |
| import cost | time both modules | identical, ~0.15 s |
| per-child startup | mutmut forks; budget vs measured | budget is ~30x the test time |

## Reproducer

```
just mutate-module sdmxlib.model.validation.x__validate_hierarchy
# 14 mutants, 93 s, 14/14 timeout
# covering set standalone: 53 tests, 2.13 s
# budget: (2.0 + 1) * 15 = 45 s
```

The budget formula is `wall = (estimated_time_of_tests + timeout_constant) * timeout_multiplier`, currently `(est + 1.0) * 15`.

## Next step

`debug = true` in `[tool.mutmut]` prints the actual pytest invocation and exit code per child. Deferred so far only because changing that block alters the config fingerprint and forces a full stats recollection before it tells you anything — budget a few minutes before the first useful line.

Worth checking in the same pass whether `timeout_constant` is simply too small for functions with tiny covering sets. A flat allowance large enough to cover a full-suite run would make the classification correct at the cost of slower genuine hangs, which may be the right trade given no genuine hang has yet been observed.

## Out of scope

The three `collections.py` timeouts (`to_itemlist_opt`) behave identically and are presumably the same cause; fixing this should fix those. No separate issue.
