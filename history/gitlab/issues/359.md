# Issue #359: Twenty register entries were the fixture setting both sides of an SDMX choice

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-21 |

Hunting real registry examples for #355's remaining fields disproved five of
them outright — twenty register entries across the four formats.

## What happened

SDMX types both `AttributeRelationship` and `ConstraintAttachment` as **choices**:

* an attribute relates to dimensions, **or** the measure, **or** a group, **or**
  the dataflow;
* a constraint attaches to a dataflow, **or** a structure, **or** a provision
  agreement, **or** a provider.

`tests/support/maximal.py` set every member of both at once, in pursuit of being
maximal. A writer given that input can only emit one, and does — correctly. The
census read the other members coming back empty and registered five losses:

    data_structures.attributes[].related_measure
    data_structures.attributes[].related_group
    constraints.attachment.data_structure
    constraints.attachment.provision_agreement
    constraints.attachment.data_provider

× four formats = twenty entries, none of them real.

## How it was caught

By going looking for real examples, as the follow-up to #355 intended. BIS
publishes both shapes: `datastructure/BIS/all` has attributes related to a
measure and attributes related to a group, and `contentconstraint/BIS/all`
attaches constraints to things other than dataflows. Both round-trip with **zero**
differences.

That contradicted the register, so one of them was wrong. The fixture was.

## Fixed

The fixture now uses one attribute per relationship kind and one constraint per
anchor. Both BIS sources joined the real-world corpus, so the round-trip is
locked in by real data rather than only by the fixture.

## What survived

One real limit, previously masked by the false entry next to it: in 3.0/3.1 and
SDMX-JSON, an attribute related to a **measure** loses the measure's identity.
SDMX 3.0's `AttributeRelationshipType` offers Dataflow / Dimension / Group /
Observation and `<Observation/>` is `common:EmptyType` — there is no measure
reference in the type at all. Declared in `gaps.py`. 2.1 carries it fine.

## The lesson, and it is the third time

"Maximal" has to mean maximal *within the grammar*. This is the same mistake as
the `Level.coding_format` one already commented in the fixture (that type is a
restriction of the ordinary facet type), and as the `date`-vs-`datetime` and
wildcard-URN ones from #354. A fixture that ignores the grammar tests the writer
against input no conformant document could carry, and every "loss" it reports
there is noise.

The general form worth watching for: **any XSD `<xs:choice>` is a place the
fixture can lie.** Worth a sweep of the remaining register for the same shape.
