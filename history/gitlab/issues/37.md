## Summary

This issue proposes adding a lazy graph traversal API to sdmxlib's `LocalRegistry`, inspired by the design being developed in pinax. The pattern combines Gremlin-style sub-traversals with Polars-style expression composition, enabling efficient structural queries without N+1 problems.

## Core Concepts

### 1. Scopes — lazy graph positions

Navigation returns scope objects that carry a position in the SDMX structural graph without executing SQL:

```python
reg = sdmxlib.LocalRegistry(conn)

# Navigation is lazy — no SQL
reg.codelists                           # CodelistsScope
reg.codelists["CL_GEO"]                # CodelistScope
reg.codelists["CL_GEO","ON"]          # CodeScope

# Only .collect() hits the DB
codes = reg.codelists["CL_GEO"].collect()  # → ItemList[Code]
```

### 2. `each()` — sub-traversal expressions

`each("edge")` creates a context-free expression describing a traversal from the current scope position. Strings are edge labels, methods are operations:

```python
from sdmxlib.expr import each

# Expressions are data — no SQL, no connection
each("codes").count()                              # count codes in a codelist
each("codes").filter(is_leaf=True).count()          # filtered count
each("dataflows", "dsd", "dimensions").count()      # multi-hop
```

### 3. Expression consumers — `.enrich()`, `.filter()`, `.sort_by()`

Expressions are passed to scope methods that determine how they're used:

```python
# Enrich: add computed fields (supports **kwargs for naming)
reg.codelists.enrich(
    n_codes=each("codes").count(),
    has_hierarchy=each("hierarchy").exists(),
).collect()
# → ItemList where each codelist has .n_codes and .has_hierarchy

# Filter: keep items matching a graph condition
reg.codelists.filter(
    each("codes").count() > 100,
).collect()

# Sort: order by a graph computation
reg.codelists.sort_by(
    each("codes").count(), desc=True,
).collect()

# Compose: chain operations (all lazy until .collect())
reg.codelists \
    .filter(each("codes").exists()) \
    .enrich(n=each("codes").count()) \
    .sort_by(each("codes").count(), desc=True) \
    .collect()
```

### 4. `.collect()` as the universal terminal

Following Polars convention, `.collect()` is the explicit materialization step. All navigation and chaining is lazy.

## Design Influences

- **Gremlin**: sub-traversals as independent computations per node (`project().by(__.out().count())`)
- **Polars**: expressions as composable objects, `**kwargs` for naming, `.collect()` as terminal
- **Django ORM**: `.annotate()` for computed fields (we call it `.enrich()`)
- **DuckPGQ**: SQL/PGQ pattern matching as optional compilation target

## Relationship to pinax

pinax is developing this pattern first for catalog traversal (themes, datasets, codelists). The expression types (`each()`, `TraversalExpr`, etc.) and scope patterns should ideally live in sdmxlib so both libraries share the same traversal language. sdmxlib's structural graph (codelists → codes, DSDs → dimensions → codelists, concept schemes → concepts) is the natural home for this API.

## Open Questions

- Should the expression types live in sdmxlib or in a shared package?
- Can `ItemList` be extended to carry enrichment fields, or do we need a new result type?
- Should `LazyCodelist` / `LazyItemList` be refactored to use scopes internally?
