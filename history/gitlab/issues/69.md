## Comments

### 2026-08-20

**Audit note — still valid, with fresh evidence on both halves.**

Confirmed against current `main`: `AvailabilityConstraint` is not modelled. The
only trace is three comments in `formats/sdmx_ml31/writer.py` saying so.

Two findings from the IM-coverage audit that bear on the priority here.

### The semantics are already covered; the artefact is not

3.1's `AvailabilityConstraintType` is `ConstraintAttachment` + `CubeRegion` —
nothing else. That is exactly what `DataConstraint(constraint_type=ACTUAL)`
carries today, and what `builders/contentconstraint.build_component_availability`
already produces. So the split this issue describes is, for our purposes,
missing only the 3.1 `<AvailabilityConstraints>` section as a distinct read/write
path — not a new information model.

That is a smaller job than the design doc implies, and it changes the shape of
the work: mostly a writer section, a reader, and a decision about whether
`DataConstraint` with `role=Actual` should *become* an `AvailabilityConstraint`
on 3.1 output.

### Nobody publishes one

`https://registry.sdmx.org/sdmx/v2/structure/availabilityconstraint/*/*/*`
returns 200 with an **empty** `<Structures>` payload. Neither pysdmx nor sdmx1
models the type. So there is no live document to validate against and no
interoperability partner — the same position as `Process` (#361) and most of the
other unmodelled artefacts.

Worth doing when a downstream consumer (pinax) actually needs the 3.1
availability resource, rather than for spec completeness.

### Also relevant

#355 registers `DataConstraint.reference_period` and `release_calendar` as
round-trip losses; `release_calendar` is a declared 3.1 limit because the element
was removed from `DataConstraintType` entirely (#345). Whoever picks up the 3.1
constraint split should read that register first — it is the current list of what
survives a constraint round-trip and what does not.

### 2026-10-15

Status after milestone 20 (2026-10-15), which built the model part of this design, differently in one respect:

- **Done, differently:** #421's constraints row kept `DataConstraint.role` as the canonical form. It did not make the role implicit in a separate type. It added a non-maintainable `AvailabilityConstraint` value class, read and written in SDMX-ML 3.1, in its own `availability_constraints` slot.
  - An Actual `DataConstraint` that fits is converted on a 3.1 write; the loss of its identity is a declared gap.
  - An `AvailabilityConstraint` is left out of 2.1, 3.0, JSON and storage, as a declared gap.
  - See !578 (attachment constraints, release calendar) and !579 (AvailabilityConstraint).
- **Not done:** the REST availability resource, the query DSL exposure, and the storage and indexing split described here.

Kept open in the backlog for those parts. If this is picked up, re-read the model sections against what !579 shipped first.
