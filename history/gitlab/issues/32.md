# sdmxlib v3 — REST Query DSL Specification

## Overview

This document specifies the design of the REST query layer for sdmxlib v3.
It covers the user-facing query API (`browse`, `fetch`, `resolve`), the
internal engine that maps these to SDMX REST wire protocol parameters, and
version negotiation between REST API v1.5 (SDMX 2.1) and v2.x (SDMX 3.0).

The guiding principles are:

- **Power-user focused with ergonomic, non-legacy design.** We do not ape
  SDMX parameter names at the user API level. The wire protocol details
  (`detail`, `references`, URL schemes) are engine-internal.
- **Semantic methods over overloaded parameters.** Qualitatively different
  operations get different method names. Parameters are reserved for
  quantitative/modal differences within the same semantic operation.
- **The Registry type hides wire-level concerns.** Users write the same
  `browse`/`fetch`/`resolve` calls regardless of whether the endpoint
  speaks REST API v1.5 or v2.x.

---

## Query Entry Points

Two entry points on `RestRegistry` (and `FmrRegistry`) produce two
different query builder types:

```python
# Point lookup — returns GetQuery[T]
q = reg.get(sl.DataStructure, agency="ECB", id="ECB_EXR1")

# Collection browse — returns Query[T]
q = reg.query(sl.Dataflow, agency="ECB")
```

### `GetQuery[T]`

Returned by `reg.get()`. Identifies a single artefact by type, agency, id,
and optionally version. Exposes three terminal methods: `fetch()`,
`resolve()`, and inherits no collection-level operations.

### `Query[T]`

Returned by `reg.query()`. Identifies a collection of artefacts by type and
optional filters (agency, etc.). Exposes `browse()`, `fetch()`, `resolve()`,
plus collection operations like `filter()` and `sort_by()`.

---

## Terminal Methods: Browse → Fetch → Resolve

Three methods form an escalation of commitment. Each maps to a specific
combination of the SDMX REST `detail` and `references` wire parameters.

### `browse() -> ArtefactList[T]`

**Available on:** `Query` only (not `GetQuery` — browsing a single known
artefact is meaningless).

**Semantics:** Returns lightweight identity-only stubs for cataloguing what
exists. Each artefact in the result has its identity fields populated (id,
agency, version, name) but internal item collections are empty. Refs are
URN-only.

**Wire mapping:**
- `detail=allstubs`
- `references=none`

**Use case:** "Show me all the dataflows at ECB" or "list all codelists
maintained by SDMX" — the user wants to scan a catalogue and pick items
for deeper inspection.

```python
for df in reg.query(sl.Dataflow, agency="ECB").browse():
    print(df.id, df.name.get("en"))
    # df.structure is Ref[DataStructure] — URN only
    # df internals are stubs (no dimensions, etc. on the DSD)
```

### `fetch() -> T` (GetQuery) / `ArtefactList[T]` (Query)

**Available on:** Both `GetQuery` and `Query`.

**Semantics:** Returns full artefacts with all internal structure populated
(dimensions, attributes, codes, concepts, etc.), but cross-artefact `Ref[T]`
fields are unresolved URNs. No graph traversal occurs.

**Wire mapping:**
- `detail=full`
- `references=none`

**Use case:** You want the complete artefact for local inspection or to add
to a `Registry` manually, without pulling in its entire reference graph.

```python
dsd = reg.get(sl.DataStructure, agency="ECB", id="ECB_EXR1").fetch()
dsd.dimensions["FREQ"]               # Dimension — populated
dsd.dimensions["FREQ"].codelist      # Ref[Codelist] — URN only, unresolved
dsd.dimensions["FREQ"].codelist()    # raises UnresolvedRef
```

### `resolve() -> T` (GetQuery) / `ArtefactList[T]` (Query)

**Available on:** Both `GetQuery` and `Query`.

**Semantics:** Returns full artefacts with Refs transitively resolved. The
server bundles referenced artefacts (codelists, concept schemes, etc.) into
the response. All `Ref[T]` fields in the returned graph are resolved and
callable.

**Parameters:**

- `partial: bool = True` — When `True` (the default), referenced ItemSchemes
  (codelists, concept schemes) may be trimmed by the server to only include
  items allowed by applicable ContentConstraints. When `False`, referenced
  ItemSchemes are delivered in full regardless of constraints.
- Positional `type[T]` argument for selective resolution — resolve only Refs
  of a specific artefact type, leaving others as URN-only.

**Wire mapping:**

| Call | `detail` | `references` |
|------|----------|-------------|
| `resolve()` | `referencepartial` | `descendants` |
| `resolve(partial=False)` | `full` | `descendants` |
| `resolve(sl.Codelist)` | `referencepartial` | `codelist` |
| `resolve(sl.Codelist, partial=False)` | `full` | `codelist` |

**Design rationale for `partial=True` as default:**

The `referencepartial` wire parameter is strictly better than `full` when
ContentConstraints exist (dramatically smaller responses — e.g. 200KB vs
100MB for large OECD codelists) and harmless when they don't (the server
returns full codelists if no constraints apply). The constrained codelists
are also semantically more useful for the dominant use case (building data
queries, showing users what codes they can actually select).

The `partial=False` opt-in serves the minority use case of metadata auditing,
codelist comparison, or codelist browsing where the user needs every code
regardless of constraints.

**Design rationale for `partial` as the parameter name:**

The SDMX standard uses "partial" as the native term — `is_partial` is a flag
on ItemSchemes in the wire format and in domain models (pysdmx's `Codelist`
has `is_partial: bool`). The wire parameter is `detail=referencepartial`.
Using `partial` keeps the vocabulary aligned with the standard for users who
dig deeper.

The ergonomics work because the default (`partial=True`) is invisible — users
just call `.resolve()`. The only time the parameter appears is when opting
out: `.resolve(partial=False)` reads clearly as "I don't want partial
codelists."

```python
# Default: constrained/partial — the common case
dsd = reg.get(sl.DataStructure, agency="ECB", id="ECB_EXR1").resolve()
dsd.dimensions["FREQ"].codelist()    # Codelist — resolved, possibly trimmed
dsd.dimensions["FREQ"].codes         # ItemList[Code] — only allowed codes

# Full: unconstrained — metadata audit mode
dsd = reg.get(sl.DataStructure, agency="ECB", id="ECB_EXR1").resolve(partial=False)

# Selective: only resolve codelist refs
dsd = reg.get(sl.DataStructure, agency="ECB", id="ECB_EXR1").resolve(sl.Codelist)
```

## Registry Construction and API Version Handling

### User-facing construction

```python
# Explicit URL + API version
with sl.RestRegistry("https://data-api.ecb.europa.eu/service", api="2.1") as reg: ...
with sl.RestRegistry("https://registry.sdmx.org/sdmx/v2/", api="3.0") as reg: ...

# Known provider shorthand (from provider dict)
with sl.RestRegistry.ecb() as reg: ...

# FMR-specific (different behavioural subtype)
with sl.FmrRegistry() as reg: ...  # defaults to SDMX Global Registry
with sl.FmrRegistry("https://my-fmr.example.com/sdmxapi/rest") as reg: ...
with sl.FmrRegistry(auth=sl.BearerToken("eyJ...")) as reg: ...
```

### Provider dict

sdmxlib ships a dict of known providers with pre-configured endpoint URLs,
API versions, and any provider-specific quirks (similar to sdmx1's
`sources.json`). The `api` parameter can be omitted for known providers.

### Registry type hierarchy

- `RestRegistry` — standard SDMX REST endpoints (ECB, Eurostat, OECD, etc.)
- `FmrRegistry` — Fusion Metadata Registry (structural metadata only, no
  data queries, has extra registry-management endpoints)
- Additional subtypes can be added to capture provider-specific quirks
  without polluting the base classes.

## Engine Internals (Not User-Facing)

### URL Builder Strategy

The engine uses a URL builder that knows how to construct v1.5 or v2.x URLs
from the same semantic query parameters. The `api` version on the registry
selects the strategy.

**v1.5 URL scheme (SDMX 2.1):**
```
{base}/{artefact_type}/{agency}/{id}/{version}?detail={detail}&references={references}
```
Example: `https://data-api.ecb.europa.eu/service/datastructure/ECB/ECB_EXR1/1.0?references=descendants&detail=referencepartial`

**v2.x URL scheme (SDMX 3.0):**
```
{base}/structure/{artefact_type}/{agency}/{id}/{version}?detail={detail}&references={references}
```
Example: `https://registry.sdmx.org/sdmx/v2/structure/datastructure/ECB/ECB_EXR1/~?references=descendants&detail=referencepartial`

**Key differences the builder must handle:**

| Concern | v1.5 | v2.x |
|---------|------|------|
| URL prefix | `/{artefact_type}/` | `/structure/{artefact_type}/` |
| Wildcard (any) | `all` | `*` |
| Wildcard (latest version) | `latest` | `~` |
| Default response format | SDMX-ML 2.1 | SDMX-JSON 2.0 |
| Multi-value separator | `+` | `+` (same) |
| Unified cross-type query | not available | `/structure/{agency}` |
| `as_of` parameter | not available | supported |

### Format Negotiation

The engine sets the `Accept` HTTP header to request the preferred response
format and routes response bytes to the appropriate parser.

For v1.5 endpoints, the default response is SDMX-ML 2.1 (XML). The engine
should prefer XML here as it's the most reliably implemented.

For v2.x endpoints, the default response is SDMX-JSON 2.0. The engine can
request SDMX-ML 3.0 via content negotiation if needed.

The parser layer (`sdmxlib/formats/`) already handles both SDMX-ML versions
and SDMX-JSON. The engine just needs to route correctly.

### Wire Parameter Mapping

The engine translates the semantic methods into wire parameters:

```python
# Internal mapping (not user-facing)
BROWSE_PARAMS  = {"detail": "allstubs",           "references": "none"}
FETCH_PARAMS   = {"detail": "full",               "references": "none"}
RESOLVE_PARAMS = {"detail": "referencepartial",   "references": "descendants"}
RESOLVE_FULL   = {"detail": "full",               "references": "descendants"}

# Selective resolve: references= is set to the artefact type name
# e.g. resolve(sl.Codelist) -> references="codelist"
```

### Registry Accumulation

All fetched artefacts accumulate in the `RestRegistry`'s internal `Registry`
store (`reg.registry`). This enables cross-request Ref resolution — a
codelist fetched in one query can resolve a Ref encountered in a later query.

The engine interns all artefacts from every response into the registry,
regardless of which method was called. Even `browse()` stubs get interned
(as partial identity objects) so that URN lookups can find them.

## Design Decisions Log

### Methods over parameters for qualitative differences

`browse()`, `fetch()`, and `resolve()` are separate methods rather than
modes on a single method because they return qualitatively different objects:
- `browse()` returns hollow stubs (identity only, no items)
- `fetch()` returns full artefacts with unresolved Refs
- `resolve()` returns full artefacts with resolved Refs

Collapsing these into a single method with a mode parameter (e.g.
`fetch(mode="browse")`) would force the return type to be a union or would
hide important semantic differences behind a string. Separate methods make
the type signatures clean and the intent explicit.

### `partial` parameter for quantitative differences

The `partial` flag on `resolve()` is a parameter rather than a separate
method because it does not change the return type or the shape of the object
graph. Both `resolve()` and `resolve(partial=False)` return the same `T`
with the same Refs resolved — the only difference is how many items appear
in referenced ItemSchemes. This is a quantitative/modal difference, not a
qualitative one.

### `partial=True` as default

`referencepartial` on the wire is strictly better when ContentConstraints
exist and harmless when they don't. It is both a performance optimization
(smaller payloads) and semantically more useful for the dominant use case
(building data queries with only valid codes). The `partial=False` escape
hatch serves the minority metadata-audit use case.

### `browse()` only on `Query`, not `GetQuery`

Browsing a single known artefact by its full identity is meaningless — if
you know the agency, id, and version, you already know it exists. `browse()`
is a collection operation for discovering what's available.

### API version hidden inside the engine

Users write identical `browse()`/`fetch()`/`resolve()` calls regardless of
whether the endpoint speaks v1.5 or v2.x. The `api` parameter at
construction time selects the URL builder and format negotiation strategy.
The only v2-specific feature that could leak is `as_of` (time travel); if
used against a v1.5 endpoint, the engine should raise an informative error.

### `RestRegistry` vs `FmrRegistry` for behavioral polymorphism

FMR endpoints have different capabilities (no data queries, extra registry
management APIs) and defaults. Rather than parameterizing `RestRegistry`
with capability flags, separate types capture the behavioral difference.
Additional subtypes can be added for other provider-specific quirks.

## Open Questions / Future Work

- **`Query` filtering and sorting:** The `Query` type exposes `.filter()`
  and `.sort_by()` for client-side refinement of collection results. The
  exact signatures are not specified here.
- **Availability queries:** SDMX has a separate `/availability/` endpoint
  for discovering what data exists for a structure. This is not covered in
  this spec but would likely be a method on `RestRegistry` or on a
  `Dataflow` object.
- **Pagination:** Large collection queries may need pagination support.
  The SDMX REST v2 spec supports `offset` and `limit` parameters. This
  should be handled transparently by the engine (async iteration or
  explicit page control).
- **`as_of` (time travel):** v2-only feature. Needs a decision on where
  it surfaces — likely as a parameter on `GetQuery` construction or on
  the terminal methods.
- **Async support:** The README shows sync context managers. Whether to
  also offer async variants (or go async-first) is not covered here.
