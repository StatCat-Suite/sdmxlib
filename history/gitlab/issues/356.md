# Issue #356: SDMX-ML 2.1 writer emitted <MetadataStructures> out of sequence

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |

Found by the real-world round-trip corpus, against a live IMF metadata
structure. Fixed in the same MR; filed for the record because the failure mode
is worth naming.

## The bug

2.1's `StructuresType` fixes the order of the sections inside `<Structures>`:

    OrganisationSchemes, Dataflows, Metadataflows, CategorySchemes,
    Categorisations, Codelists, HierarchicalCodelists, Concepts,
    MetadataStructures, DataStructures, StructureSets, ...

The writer's `_SECTIONS` table had `MetadataStructures` **third**, immediately
after `Metadataflows`. So any message carrying an MSD *together with* a
codelist, concept scheme, category scheme or hierarchy emitted its sections out
of order, and the document was rejected by the XSD:

    Element 'Concepts': This element is not expected. Expected is one of
    ( DataStructures, StructureSets, ReportingTaxonomies, ... )

An MSD on its own was fine, which is why it survived.

## Why nothing caught it

Every 2.1 fixture with an MSD had *only* an MSD. The order constraint is
invisible until two sections coexist, and no synthetic fixture combined them —
the maximal fixture added in #354 does, but it round-trips through the model and
the XSD check there runs on a different path.

A real `metadatastructure?references=all` response arrives with its concept
scheme attached, which is the ordinary shape from any provider. This is exactly
the class of defect the real-world corpus was added to find: not an exotic
field, just a combination no fixture author thought to build.

## Fix

Move the entry to between `Concepts` and `DataStructures`, where the XSD
sequences it. Guarded by `test_what_we_write_back_is_schema_valid[imf-msd]` in
`tests/integration/test_roundtrip_real_world.py` — reverting the fix reproduces
the failure.
