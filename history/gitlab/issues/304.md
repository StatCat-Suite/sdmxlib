## Scope, with counts re-measured

#252 was written when the DSL was laid out differently and its numbers have drifted about 50%. %14 moved the shared machinery into `_query_common.py`, which is now the largest module in the DSL and the one **every** predicate routes through — the boolean combinators, `canonical_key`, the slice guards, `CompileContext`, `advance_window`:

| module | #252 said | actual |
| --- | --- | --- |
| `code_query.py` | 509 | 340 |
| `hierarchy_query.py` | 504 | 371 |
| **`_query_common.py`** | *not named* | **691** |
| `artefact_query.py` | — | 329 |
| `metadata_query.py` | — | 275 |

Adding only the two modules #252 named would mutation-test the smaller halves and leave the shared compiler with no evidence at all. `just mutate-scope` prints this, so it does not drift silently again.

Current `only_mutate` is 923 statements. The three core query modules are **1,402**, so this more than doubles the scope.

## The comparison #218 asked for

> *do property-based tests kill more mutants than example-based ones?* Same modules, same mutants, different suite.

`code_query.py` and `hierarchy_query.py` are the cleanest available instances — both gained their property files in single identifiable changes (#217, #248). Run the mutants with the property files deselected, then included, and report both numbers. This is the prize; the scope extension is the means.

## Scope of work

- Add `code_query.py`, `hierarchy_query.py` and `_query_common.py` to `only_mutate`. Consider `artefact_query.py` / `metadata_query.py` separately — note `metadata_query` has **no** property tests at all (#302), so mutating it now would measure their absence rather than their quality, which is the same mistake #218 avoided when it left the compilers out originally.

- Triage every survivor as *real gap* / *equivalent* / *won't fix*, per #218's ruling that the triage is the artifact and the percentage is not.
- Record a baseline score per newly adopted module so drift is visible.

## Caveats that must be stated with any score

- `mutate_only_covered_lines = false` is forced off by a duckdb/`_duckdb` import interaction, so uncovered lines produce uninteresting survivors.
- `pytest_add_cli_args = ["-m", "unit and not slow"]` excludes the concurrency tests.
- Editing `[tool.mutmut]` forces a full stats recollection — budget for it, and do not time a scoped run across a config change (this invalidated one of #252's experiments).

## Explicitly out of scope

No mutation job in CI. No mutation-score merge gate. Both ruled out in #218; nothing here reopens them.

## Blocked on #303

The existing 923-statement scope currently takes ~4.5 h and does not finish in a working day, because 283 surviving `validation.py` mutants are mis-booked as timeouts and burn their full budget. Adding 1,402 statements of **DuckDB-executing** code to that would multiply a broken measurement, and #218's comparison would not be measurable at all.

Do #303 first. Then this becomes a straightforward run-and-triage.

## Also worth knowing

Three bugs of mine in `mutate_union.py` before it worked, all now fixed and
commented, because each is a trap for the next person:

- no `shutil.rmtree(mutants/)` between groups — the cache is keyed on the old

### 2026-08-17

**Triage installment 1 — `_window`** (!330, `692e1ae`).

First, the baseline that matters. Against the **whole** unit suite, `_compile.py` is **1,290 mutants, 1,127 killed (87.4%), 163 survived, 0 timeouts, 0 no-tests**. The two-arm comparison's "196 neither arm killed" overstated the gap — 33 of those die to test files in neither arm. Quote this number, not that one.

`_window` held the largest cluster (23) and turned out to contain **a defect, not a test gap**.

`col.count().over(...)` compiled to `count(*)` for every windowed count. The counted column was dropped from the SQL *while its bind parameters were still emitted*, so `description["en"].count().over(...)` died with `Parameter argument/count mismatch`, and counting any nullable column silently included its NULLs. The comment justified it — the fan-out marker is not a real column — but the premise is false: the marker's path is to-many by construction and `_flat_reference` refuses that before a window is built, so it never reaches `_window`. It survived because the one test counted `id`, where the two forms agree.

Once corrected, the `count` branch said exactly what the `else` said, and two further mutants survived on being unable to tell a branch from its fall-through. Duplicate branch, deleted.

Three windowed forms had **no test at all**: `n_unique().over()`, `list().over()`, `lead(offset)`. Each pins something real — the DISTINCT form plus the rename to `count` (DuckDB has no `n_unique`), the ORDER BY exclusion that stops `list` becoming a running list, and an offset that at 1 is indistinguishable from plain `lead`.

**Result: 1,127 → 1,147 killed, survivors 163 → 143, no regressions.** 18 of the 20 newly killed were in `_window` (23 → 5).

The five left are classified in `docs/design/mutation-evidence.md`: three equivalent under SQL's case-insensitivity (`COUNT`, `desc`), and one dead sort fallback whose removal needs a signature change a triage should not smuggle in.

**Remaining clusters**: `_facet_clause` (12), `_constraint_clause` (12), `_after_sql` (10), `compile_projection` (10), then a long tail. One cluster in, the rate is roughly one real defect and four missing tests per 23 mutants read.
