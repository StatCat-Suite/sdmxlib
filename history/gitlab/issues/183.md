Milestone: SDMX-JSON dict+orjson → msgspec. Migrate the data-message JSON path (`data_v1.py`, `data_v2.py`, `_data_common.py`) using the approach validated in #179.

## Scope
- Observation-batch serialization currently via `orjson.dumps(..., OPT_SERIALIZE_NUMPY)` → msgspec + the numpy `enc_hook` from #179.
- The chunked/streaming writers (fragment concatenation) → the msgspec streaming pattern from #179.
- `orjson.loads` on the data read paths → `msgspec.json.decode`.

## Test gates
- Data roundtrip (v1 + v2) tests pass; streaming output byte-parity with current.
- **Perf no-regression** on large observation payloads — guard with a benchmark assertion (time or a structural count), since this is the hot data path.
- numpy dtypes (int/float/datetime) serialize identically to the orjson path.

**Depends on:** #179 (data-plane investigation — MUST land its validated approach first).

## Comments

### 2026-07-22

## Scope simplified per #179's findings

The de-risking (#179) concluded the data path is a **straight swap**, not the feared numpy/streaming rework:

- **No `enc_hook` needed** — observation values are Python-native (Polars `.to_list()`), so `msgspec.json.encode` handles them directly, byte-identical to orjson. Just **drop the `OPT_SERIALIZE_NUMPY` option** in `_data_common.encode_batch`.
- **Streaming unchanged** — `msgspec.json.encode` returns `bytes`; the brace-strip fragment splice works identically. `data_v1.py`/`data_v2.py` need only their `orjson.dumps`/`orjson.loads` calls swapped.
- **Perf**: +1–3% on the pinned shapes (within the ≤5% gate) — see #179.

So this issue is now: mechanical `orjson → msgspec` swap across `_data_common.py`, `data_v1.py`, `data_v2.py`, plus the existing data-writer roundtrip + `test_data_writers.py` no-regression assertion. If a future producer surfaces a genuinely numpy value into the observations dict (none in current shapes), add a one-line `enc_hook` then.

### 2026-08-06

Closing as **already done** — with one gate resolved differently than written, which is worth recording.

`data_v1.py`, `data_v2.py` and `_data_common.py` encode through the shared `_dto.ENCODER` and read through `msgspec.json.decode(..., type=...)`. No `orjson` in `src/`.

**The numpy `enc_hook` was never needed.** The issue assumed `orjson.dumps(..., OPT_SERIALIZE_NUMPY)` had to be replaced by the enc_hook from #179. Instead the batch path yields Python-native scalars before encoding — `_data_common.py` carries the comment saying so — and `ENCODER` is a plain `msgspec.json.Encoder()` with no hook. Same outcome by a different route; noting it so nobody goes looking for a hook that does not exist.

The read side was finished in !210 under #200: both `_load` functions now decode into per-version envelope Structs rather than `dict[str, Any]`. That change also fixed two real defects on this path — a value entry of `{"id": null, "name": ...}` decoding to the literal string `"None"` as a dimension value, and the v1 reader raising `AttributeError` in violation of its documented `Raises: ValueError`.
