# Issue #385: try a trusted construction path in the readers — converters are 2.5x, and attrs itself is not the cost

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-27 |
| Closed | 2026-08-28 |
| Milestone | %18 Read-path performance: what the synthetic benchmarks could not see |
| Labels | `design`, `perf` |

An experiment, not a proposal. It has a measured upper bound, a cheap way to
try it, and a clear condition for abandoning it — all three stated below so
that "we tried it and it wasn't worth it" is an acceptable and *recordable*
outcome rather than a wasted branch.

## What prompted it

Asking what `attrs` costs the read path, and finding the premise wrong. On
identical 5-field shapes, 500,000 objects:

| | µs/obj |
| --- | --- |
| **attrs `@define` + converters — what `Code` is** | **0.444** |
| attrs `@define`, no converters | 0.176 |
| `dataclasses.dataclass(slots=True)` | 0.172 |
| hand-written `__slots__` class | 0.178 |
| `typing.NamedTuple` | 0.207 |
| `msgspec.Struct` | 0.138 |
| `msgspec.Struct(frozen=True, gc=False)` | 0.061 |

**attrs is already at hand-written speed.** 0.176 against 0.178 for the class
you would write by hand. There is nothing to win by replacing it as a class
builder, and an earlier claim in %18 that "attrs costs 4.2x a plain slots
class" was a mis-attribution: it compared `Code`, which has converters, against
a bare slots class and blamed the whole gap on attrs.

The gap is the **converters** — 0.444 vs 0.176, about 2.5x.

## Why the converters are doing nothing here

`Code` converts three fields:

| field | converter | what it is for |
| --- | --- | --- |
| `name` | `to_istring` | accept a plain `dict` from a user |
| `description` | `to_istring` | same |
| `annotations` | `_to_annotations` | accept a `list[Annotation]` |

All three exist for the **public** API, where `Code(id="ON", name={"en": "Ontario"})`
should work. The storage readers never use that latitude: `resolve.py` and
`readers.py` already hand over an `InternationalString` and an `Annotations`,
because they built them one line earlier. So on the read path every converter
is an identity function called 579,951 times.

## The experiment

A trusted construction path — `__new__` plus `object.__setattr__` — used *only*
by the storage readers, with the validating constructor unchanged and still the
public entry. #154's option 1 sketches the same idea.

Measured on the real `Code` class, 500,000 objects:

| | µs/obj |
| --- | --- |
| `Code(...)` today | 0.450 |
| `__new__` + `object.__setattr__` | **0.332** |

and the result compares equal to the validating constructor's output.

**Upper bound on the whole thing: ~0.12 µs/object.** On `CL_GEOGRAPHY` that is
**~68 ms of a 2.10 s read — about 3%.** On `H_CP_GEO_FED`'s 499,138
`HierarchicalCode`s, which have more converted fields, plausibly more; that is
the number the experiment is really for.

## Why it might not be worth it, stated up front

- **3% is not much**, and the same read has a 2.19 s item in it (#378). This
  should not be done before that.
- **It creates a second way to build a domain object**, and the two can drift.
  `HierarchicalCode` gaining a field would need both paths updated, and only
  one of them has a constructor signature to forget.
- **It bypasses more than converters.** `object.__setattr__` skips whatever
  `on_setattr` does, which today is converters and tomorrow might be a
  validator someone reasonably expects to run.

Point three is shared with #384 and the two should be decided together — both
are "the reader knows more than the constructor does", and two different
answers to that would be worse than either.

## How to try it, and when to stop

1. One reader first — `resolve.resolve_code_keys`, the one with a measured
   baseline. Not all of them.
2. Guard with a **generated** differential: for every attrs class the trusted
   path is used for, build the same object both ways and assert equality, field
   by field. Same shape as `tests/unit/test_refshape_agrees_with_reflection.py`,
   and it is what makes the second construction path defensible rather than a
   liability.
3. Measure on the bundle.

**Abandon if the bundle saving is under ~150 ms**, and record the number here.
A second construction path is a permanent maintenance cost; 3% of one read does
not buy it.

## Not in scope

`msgspec.Struct` at 0.061 µs — 2.9x faster again, and already a dependency. It
is a different and much larger question: no converters at all (the burden moves
to every caller), a different equality and inheritance model, and `gc=False`
doing most of the work, which opts the object out of cycle collection. Recorded
here only so the number is not lost. It is not this issue.

## Comments

### 2026-08-28

Tried, measured, **not worth it** — recording the number, which is what this
issue asked for.

## The measurement

Fairly compared on `HierarchicalCode` (10 fields, 5 of them converted), 499,138
objects, values already of the right type:

| | µs/obj |
| --- | --- |
| `HierarchicalCode(...)` — the validating constructor | 0.69 |
| `__new__` + `object.__setattr__` | **0.48** |

**105 ms** projected on `H_CP_GEO_FED`, and ~68 ms on `CL_GEOGRAPHY`'s
579,951 `Code`s. The stop condition set here in advance was ~150 ms, so this
is below the line.

The result compares equal to the validating constructor's, so the approach
works; it just does not buy enough. A second way to build a domain object is a
permanent maintenance cost — two paths that can drift, and only one of them has
a constructor signature to forget — and ~100 ms of a 8.5 s read does not pay
for it.

## One thing worth knowing if this is ever revisited

The first attempt measured the trusted path as **slower** — 1.05 µs against
0.69. The harness was filling the remaining fields through a
`for f in FIELDS: if not hasattr(o, f)` loop, which attrs' generated `__init__`
does not pay for. Setting all ten fields explicitly is what produced the 0.48
figure.

So the honest framing is: attrs' generated `__init__` is *fast enough that a
naive bypass loses to it*. Anything here has to set every field unconditionally
and inline, which is also the version that is most likely to drift when a field
is added — the maintenance cost and the performance are pulling the same way.

## What this does not change

The finding that prompted the issue still stands and is still the useful part:
**attrs is not the cost.** `@define` without converters is 0.176 µs/obj against
0.178 for a hand-written `__slots__` class. The 2.5x gap to `Code`'s 0.444 is
the converters, and the way to avoid paying for them turns out not to be
bypassing the constructor.

Closing as measured-and-declined. #384 took the adjacent case — the *assignment*
path, where the same converters run on a value built one line earlier — and
that one was worth doing: 10.2x, and it needed no second construction path.
