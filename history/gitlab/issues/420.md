# Issue #420: Version and finality: model 3.x semantics and project to 2.1 (the two grammars disagree in both directions)

| | |

| State | closed |

| Closed | 2026-10-11 |

| Labels | `breaking-change`, `design`, `model`, `needs-design` |

## Why this is foundational

Every maintainable artefact's identity is `(agency, id, version)`. The version
string appears in every URN and every reference, and it is the sort key for
"latest". SDMX 2.1 and 3.x disagree about both the **grammar** and the
**meaning** of that string. Today the model stores the 2.1 meaning
(`version` plus `is_final`) beside a grammar that is neither format's
(`_check_version` accepts the union of both, which also lets through
`1.2.3.4-draft`, a version neither grammar accepts).

The stated goal is a 3.x-native model that projects down to 2.1. Under
that goal, version and finality have to be modelled the 3.x way, and 2.1
becomes a projection with declared losses.

## The grammars

| | SDMX-ML 2.1 | SDMX-ML 3.0 / 3.1 | SDMX-JSON structure 2.0 / 2.1 | SDMX-JSON metadata 2.0 / 2.1 |
|---|---|---|---|---|
| pattern | `[0-9]+(\.[0-9]+)*` | legacy `N(.N)?` **or** semver `N.N.N(-pre)?`, no leading zeros | same as 3.0 | **semver only** |
| `1.0` | ✅ | ✅ (legacy) | ✅ | ❌ |
| `1.0.0` | ✅ | ✅ | ✅ | ✅ |
| `1.03` | ✅ (≡ `1.3` per the spec prose) | ❌ | ❌ | ❌ |
| `1.2.3.4` | ✅ | ❌ | ❌ | ❌ |
| `1.0.0-draft` | ❌ | ✅ | ✅ | ✅ |
| finality | `isFinal` attribute (fixed `false` on organisation schemes) | none: expressed by the version (a prerelease suffix is a draft) | none | none |

Neither grammar contains the other (`model.version.compliance` documents
this). The JSON metadata column is why a real `MetadataSet` published at
`1.0` cannot be written to SDMX-JSON (#234).

## What is broken or lossy today

- `is_final=True` → 3.x: declared drop for every maintainable. The 3.x
  document cannot say "final" except through the version, and the writer does
  not translate.
- 3.x `1.0.0-draft` → 2.1: refused. The natural projection is
  `version=1.0.0, isFinal=false`, but that collides with a real `1.0.0`.
- 2.1 `1.03` / `1.2.3.4` → 3.x: refused. `1.03` has a lossless 3.x
  spelling (`1.3`); `1.2.3.4` has none.
- Organisation schemes: version fixed at `1.0` everywhere (see #416).
- JSON writer: no grammar check at all (see #417).

## Design options

**A. Structured version, 3.x semantics** (recommended starting point)

```python
@frozen
class Version:
    major: int
    minor: int
    patch: int | None        # None ⇒ legacy two-part form
    prerelease: str | None   # semver extension; 3.x "draft"
```

- `is_final` becomes **derived** (`patch is not None and prerelease is None`)
  instead of stored. The 2.1 projection writes `isFinal` from it.
- 2.1 ingest: `1.03` is normalised to `1.3`. URN identity changes, so
  every reference to `…(1.03)` in the same registry must be rewritten in one
  pass, and the original string is kept as provenance for round-trip.
  `1.2.3.4` is refused at ingest, or stored with `legacy_2_1=True` and marked
  unprojectable to 3.x.
- 2.1 `isFinal=true` on a two-part `1.0`: 3.x semantics cannot say "final
  legacy version". Options: promote to `1.0.0`, or keep a provenance flag.
  **Needs the spec reading:** SDMX 3.0 Section 6 (versioning) on whether
  legacy-form versions are mutable.

**B. Keep the string, add a provenance flag**: `version: str` plus
`version_grammar: Literal["2.1", "3.0", "both"]` set at ingest.
This is cheaper and keeps today's behaviour, but the union grammar and
`is_final` stay in the model, so it does not meet the 3.x-native goal.

**C. Store-both**: carry 2.1 `(version, is_final)` and 3.x `version`
side by side. This is maximally lossless, but there are two sources of truth
for identity. Not recommended.

## Decisions needed (before any code)

1. Is `is_final` stored or derived?
2. Is `1.03` normalised at ingest, kept verbatim, or refused?
3. Is `1.2.3.4` refused at ingest or stored as 2.1-only?
4. How does a `-draft` version project to 2.1: refused, or `isFinal=false` with the suffix stripped and a collision check?
5. Does `MetadataSet.version` follow the same type with a "semver required" projection to JSON?
6. Ordering: `version.max()` (#351) and "latest" resolution (#311) must use the structured comparison, including prerelease precedence.

### 2026-10-09

## `VersionFormatError` and the wire gate

The new gate over populated artefacts (`m20/conformance-populated`) writes a codelist at `1.2.3.4` to 3.0, and one at `1.0.0-draft` to 2.1. Both are refused with `VersionFormatError`, which is deliberately *not* a `ValidationError`: `model/version.py` treats a version as a fact about the conversion, not a defect in the artefact.

The bare gate's rule is that a refusal is a `ValidationError`, so a caller can inspect `.issues` (`test_refusals_are_validation_errors`). The bare cases all use `1.0`, so the two rules never met until now. The new gate accepts both as a refusal and writes down why.

Question for this issue: once the version model is reworked, should a version refusal carry `.issues` like every other refusal, for example as a `ValidationError` subclass, so one `except` covers "cannot write this"?

Also from the sweep: **reference** versions are not checked at all (#429). The same grammar question applies to refs, which today are written invalid rather than refused.
