## Why the current scope may be drawn in the wrong place

`pyproject.toml`'s `only_mutate` is six modules:

```
model/urn.py  model/istring.py  model/expr.py
model/representation.py  model/collections.py  model/validation.py
```

The stated rationale is sound — "pure, fast, and already claim high coverage … is a fully covered module actually pinned?" — and #218 chose adopt-narrowly on the pilot's numbers. But the selection was made when the query compilers had no property tests at all, so including them would have measured the absence of tests rather than the quality of tests. That is no longer true.

The result today is that **no SQL-compiling code in the library has any mutation evidence**. `code_query.py` (509 statements) and `hierarchy_query.py` (504) are together larger than the entire current mutation scope, and they are the modules where a wrong comparison operator produces a plausible-looking wrong answer rather than a crash — the exact failure mode mutation testing detects and coverage does not.

## The comparison #218 asked for

> *do property-based tests kill more mutants than example-based ones?* Same modules, same mutants, different suite. If they do, that is the strongest available argument for spending effort on properties rather than more examples.

`code_query.py` is now the cleanest available instance of that experiment, and after #dsl-1 `hierarchy_query.py` becomes a second one where the properties arrived in a single identifiable change. Run the mutants against the suite with the new property files deselected, then with them included, and report both numbers.

## Scope

- Add `model/code_query.py` and `model/hierarchy_query.py` to `only_mutate`; consider `api/query.py` and `api/filters.py` in the same run.
- Note the wall-clock constraint honestly: the pilot took ~11 min against six pure modules, and these add ~1000 statements of DuckDB-executing code. Measure the run time and, if it is unworkable as one job, split the scope rather than silently sampling — `just mutate` already accepts `*ARGS`, and #218's "if A or B" list called for a path-scoped recipe that does not exist yet. Add it.
- Two caveats that will distort the score and must be stated with it:
  - `mutate_only_covered_lines = false` is forced off by a duckdb/`_duckdb` import interaction, so uncovered lines produce uninteresting survivors.
  - `pytest_add_cli_args = ["-m", "unit and not slow"]` excludes the concurrency tests.
- Triage every survivor as *real gap* / *equivalent* / *won't fix*, per #218's ruling that the triage is the artifact and the percentage is not.
- Record the baseline score per newly adopted module so drift is visible.

## Explicitly out of scope

- No mutation job in CI. No mutation-score merge gate. Both were ruled out in #218 and nothing here reopens them.

## Test gates

## Comments

### 2026-08-11

Started this. The tool-repair half is merged as !293; the scope half needs a decision, because two of the issue’s premises no longer hold.

## 1. `just mutate` was broken, so there was no baseline to extend

Six tests read files by working-directory-relative paths, and mutmut runs pytest from a `mutants/` tree containing only copies of `src/` and `tests/`. The read happened at import time, so it aborted the run at the stats pass — **zero mutants ran, from #265 until now**. Fixed in !293 with `tests/support/repo.ROOT` and a static guard.

Worth noting *why* it survived: mutation is deliberately outside `just ci`, so between #265 and this issue nothing ran that could have noticed. That is the same shape as the ruff-warnings problem CLAUDE.md records — a check that cannot fail is a check nobody acts on. Not an argument for putting mutation in CI (#218 ruled that out and this does not reopen it), but the breakage class is real and now guarded.

## 2. The statement counts moved, and the biggest module is one the issue does not name

| module | this issue says | actual |
| --- | --- | --- |
| `code_query.py` | 509 | **340** |
| `hierarchy_query.py` | 504 | **371** |
| `_query_common.py` | — | **691** |
| `artefact_query.py` | — | 329 |
| `metadata_query.py` | — | 275 |

The compilers did not shrink by deletion — #262 / #268 / #293 / #295 and the rest of %14 moved the shared machinery into `_query_common.py`, which is now the largest module in the DSL and the one **every** predicate routes through: the boolean combinators, `canonical_key`, the slice guards, `CompileContext`, `advance_window`. Adding only the two modules named here would mutation-test the smaller halves and leave the shared compiler with no evidence at all.

## 3. The wall-clock premise is stale by an order of magnitude, and 37% of mutants time out

First clean run of the existing six-module scope:

```
~960 mutants     3.3 hours     (the issue cites an ~11 min pilot)
  killed   ~457
  survived  147     consistent with the ~150 #253 triaged — baseline has not drifted
  timeout   356     ← 353 of them in validation.py alone
```

The timeouts are the problem, and I could not explain them. Ruled out:

- **Import cost.** `validation` and `collections` import in the same ~0.15 s; polars alone is 0.04 s.
- **Per-child startup.** mutmut `os.fork()`s, so children pay no import cost, and the budget — `(est_test_time + timeout_constant) * 15` — is roughly 30x the measured test time. A full run of `test_collections.py` is 0.03 s against a ~15 s limit.
- **Mutant severity.** A sampled timeout is `to_itemlist_opt`’s `or` → `and`, which should die instantly.

What fits the *distribution* is that timeouts track how much DuckDB the covering tests touch: `validation.py` is reached from `test_federated_catalog`, `test_data_store_inspect`, `test_builders_*`, all of which build registries; `collections.py`’s own tests touch none and produced 3 timeouts against 15 survivors. A fork() in a process holding DuckDB’s background threads deadlocking the child would explain it, and `pyproject.toml` already documents a *different* duckdb/mutmut interaction (`mutate_only_covered_lines` must stay false). **I have not proven this** — stating it as the leading hypothesis, not a finding.

## Why that decides the scope question

This issue’s central move is adding the **DuckDB-executing** compilers. If timeouts do track DuckDB use, extending scope produces mostly timeouts, the score is noise, and #218’s properties-vs-examples comparison — the actual prize here — is not measurable at all. Extending scope first would burn ~8–10 h to learn that.

## Proposed split

- **This issue** narrows to: diagnose the timeout regime, and add the path-scoped `just mutate` recipe it already asks for (needed regardless, since mutmut has no path flag — selection is `only_mutate` plus mutant-name arguments).
- **A follow-up** does the scope extension and the before/after property comparison, once a mutation run over DuckDB-touching code is known to produce signal.

Happy to proceed either way — say if you would rather push straight through to the extension and take the timeouts as they come.

**The uncomfortable part: fixing fork-safety made the run slower.** Pre-fix, a segfaulting child died instantly; now those same mutants run to their full budget. The segfaults were masking the real cost. Scores are now trustworthy; wall-clock got worse.

## The remaining 283 are not hangs

Applied `x__validate_hierarchy__mutmut_2` by hand: its 53 covering tests **all pass in 2.13 s**. So it is a survivor being booked as a timeout, and the child is somehow burning 45 s doing 2 s of work.

Rejected by measurement, each one a hypothesis I held at some point:

| hypothesis | test | result |
| --- | --- | --- |
| the mutant hangs | apply by hand, run covering set | 53 pass in 2.13 s |
| parallel contention | 8 concurrent copies of the set | 6 s, vs a 45 s budget |
| DuckDB threads × `fork()` | force `SET threads=1` in conftest | unchanged, 14/14 timeout |
| escalation to the full suite | read `PytestRunner.run_tests` | passes only the covering tests, with `-x` |
| fork + DuckDB deadlock | isolated fork probe | completes in 5 ms |

Two earlier hypotheses died the same way: import cost (identical between modules) and per-child startup (mutmut forks; the budget is ~30x the measured test time).

## Reproducer

```
just mutate-module sdmxlib.model.validation.x__validate_hierarchy
# 14 mutants, 93 s, 14/14 timeout
# covering set standalone: 53 tests, 2.13 s;  budget (2.0 + 1) * 15 = 45 s
```

Next thing I would try is `debug = true` in `[tool.mutmut]` to print the actual pytest invocation and exit code per child — deferred only because it changes the config fingerprint and so costs a full stats recollection before it tells you anything.

## Consequence for the original scope question

Unchanged and now firmer: **do not extend scope yet.** The existing 923-statement scope cannot finish in a working day, and the reason is a harness artefact rather than anything about the code. Adding ~1,400 statements of DuckDB-executing compiler — including `_query_common.py` (691), which this issue still does not name — would multiply a broken measurement.

`#218`’s properties-vs-examples comparison remains the prize and remains unmeasurable until this is resolved.

### 2026-08-11

## Split, and closing

This issue carried three separable things and the middle one turned out to be a blocker for the other two. Splitting so the finished work can close and the blocker is tracked on its own.

**Done here, merged:**

- !293 — `just mutate` aborted at collection and had done so since #265. Six cwd-relative file reads; mutmut runs pytest from a `mutants/` tree with no `docs/`. Zero mutants had run for several milestones. Fixed with `tests/support/repo.ROOT` plus a static guard.
- !294 — 356 "timeouts" were macOS fork-safety segfaults. `getproxies()` reaches SystemConfiguration, which is not fork-safe; an `httpx.Client` in a forked child kills the interpreter, and mutmut books a dead child as a timeout. Scores were wrong in *both* directions, since a segfaulting child exits nonzero and also reads as a kill.
- !295 — `just mutate-module` and `just mutate-scope`, the path-scoped recipe this issue asked for, plus both traps written into the justfile.

**Split out:**

- **#303** — the 283 surviving `validation.py` mutants booked as timeouts. Not hangs: one applied by hand has 53 covering tests that all pass in 2.13 s against a 45 s budget. Seven hypotheses rejected by measurement, with a 93 s reproducer. This is the blocker.
- **#304** — the scope extension and #218's properties-vs-examples comparison, with statement counts re-measured. Blocked on #303.

**The finding worth carrying out of this issue:** its own premise had drifted ~50%. `code_query.py` is 340 statements, not 509; `hierarchy_query.py` 371, not 504; and the missing 691 are in `_query_common.py`, which this issue never named and which every predicate now routes through. Extending scope to the two named modules would have tested the smaller halves and missed the shared compiler entirely. `just mutate-scope` now prints this so it cannot drift silently again.

Second finding, less comfortable: fixing fork-safety made the run **slower** — 3.3 h to ~4.5 h projected — because segfaulting children used to die instantly and now burn their full budget. The segfaults were masking the real cost.
