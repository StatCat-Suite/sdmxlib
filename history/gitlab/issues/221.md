# Issue #221: validate() accepts maintainable and agency ids the XSD rejects

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-06 |
| Milestone | %10 Testing: audit, properties, and mutation |
| Labels | `bug` |

`validate()` applies the permissive `IDType` pattern to every id. The SDMX XSDs use **three** id types, and two of the positions sdmxlib validates loosely are restricted. The consequence is that `serialize(msg, validate=True)` — the default, which reads as a promise the output is valid — can emit SDMX-ML that fails XSD validation.

## The disagreement

Measured against the vendored 2.1 XSD:

| Codelist id | Agency id | Code id | `validate()` | XSD |
| --- | --- | --- | --- | --- |
| `CL_OK` | `AGENCY` | `CODE_OK` | passes | valid |
| **`0LEAD`** | `AG` | `C` | passes | **INVALID** |
| **`A@B`** | `AG` | `C` | passes | **INVALID** |
| **`A$B`** | `AG` | `C` | passes | **INVALID** |
| `CL` | **`0AG`** | `C` | passes | **INVALID** |
| `CL` | `AG` | `0CODE` | passes | valid |
| `CL` | `AG` | `C@D` | passes | valid |

Note the last two rows: for **item** ids the current pattern is correct. This is not "the regex is too loose everywhere".

## The three types

```
IDType              [A-Za-z0-9_@$\-]+                              items: Code
NCNameIDType        [A-Za-z,A-Za-z0-9_\-]*                        maintainables, components, Concept
NestedNCNameIDType  [A-Za-z,A-Za-z0-9_\-]*(\.[A-Za-z,...]*)*     agencyID
```

`NCNameIDType` exists because those ids become XML element and attribute names in structure-specific schemas, so they must be valid XML NCNames — hence "starts with a letter" and no `@` or `$`. The XSD documents this on `ComponentBaseType`.

`validation.py` currently has:

```python
# SDMX 2.1 / 3.0 formal type patterns from SDMXCommonReferences.xsd:
#   IDType:       [A-Za-z0-9_@$-]+
_ID_PATTERN = r"^[A-Za-z0-9_@$-]+$"
_AGENCY_PATTERN = r"^[A-Za-z0-9_@$-]+(\.[A-Za-z0-9_@$-]+)*$"
```

The `IDType` transcription is **correct** — the comment is not wrong about what it quotes. The bug is that `IDType` is the wrong type for the positions it is applied to.

## A subtlety worth not missing

**Concept ids are `NCNameIDType`, Code ids are `IDType`.** Verified empirically, since the two are easy to assume identical:

```
id=OK       Code=valid    Concept=valid
id=0LEAD    Code=valid    Concept=INVALID
id=A@B      Code=valid    Concept=INVALID
```

Same reason: a concept id can become a component id, and component ids become XML names.

## Scope

- `_check_id` needs to know which kind of id it is checking. Maintainables, components and Concepts get `NCNameIDType`; Codes keep `IDType`.
- `_check_agency_id` gets `NestedNCNameIDType`.
- Worth auditing the remaining item types (Category, DataProvider, ...) the same way rather than assuming.

## Backwards compatibility

This makes `validate()` **stricter**, so artefacts that pass today may start failing. That is the point — they were already unserialisable to SDMX-ML — but it is a behaviour change and the error message should say why, naming the id type and the position.

Worth checking the checked-in fixtures still validate before landing.

## Test gates

- The table above becomes a test, asserting `validate()` and XSD agree in both directions.
- A property: for any artefact the strategies generate, `validate()` passing implies the SDMX-ML output is XSD-valid. That is the invariant this issue is really about, and `tests/support/strategies.py` already models the three id types.

## Provenance

Found by the #216 generative round-trip properties: schema validation rejected a generated codelist whose id was `0`, which `validate()` had accepted. The strategies were then corrected to follow the XSDs, which is why they now distinguish `sdmx_ids()` from `ncname_ids()`.
