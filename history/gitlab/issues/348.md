## Re-measured

Synthetic census-shaped geography, sized to the report: `H_CP_GEO_POPCTR`
264,269 nodes, five hierarchies, `sdmx.hierarchy_node` at 1,577,601 rows
(reporter: 266,966 / 1,790,867). DuckDB in-process.

| operation | reported | `main` today | your hand SQL |
| --- | --- | --- | --- |
| descendants of a CMA | 1.38 s | **48 ms** | 15 ms |
| intersect two subtrees | 0.39 s | **52 ms** | 22 ms |

The row that hurt is ~940× faster and now beats the hand-written SQL by 3×,

`VARCHAR[]`.

## Against the four asks

**1. Id-only iteration — done, and iteration is now refused outright.** Since
#306 a query is not iterable at all:

```python
for n in h.nodes: ...
# TypeError: a query is not iterable — it is a plan, and iterating would run
# it without saying so. Use .collect() ...
```

so the shape in this report cannot be written any more. `.ids()` returns
`list[str]` with no `HierarchicalCode` built, `.count()` is one `COUNT(*)`, and
`.select(q.hcode.id, q.hcode.depth).collect()` gives a chosen column subset.

**2. Set-based primitives — present.** `intersect` / `difference` compile to
set operations rather than being assembled by the caller;
`ancestor_at(level)` is `ancestor_at_level_map`; `descendants_at_level`
composes rather than needing its own name:

```python
h.narrower_transitive("CA").filter(q.hcode.level.id == "DA").ids()
```

**3. `inherit_along_broader` — already pushed down.** SQL on `LazyHierarchy`,
not a tree walk. (The eager `Hierarchy` still walks in Python, correctly — it
has no database.)

**4. Frame surface — `.collect()` on a projection or on `ancestor_at` returns
a `polars.DataFrame`.** `ancestor_at(...).collect()` is `(node_id, rollup_id)`
ready to join, and is the fastest of the shapes above.

## On the memory point

This is the part worth acting on regardless of the timings: `.ids()`,
`.count()` and `.collect()`-to-a-frame keep rows in the engine, so the class of
failure described — Python heap outside DuckDB's `memory_limit` — goes away
with the call shape rather than needing a new feature. The 264k-node map that
was 266,966 Python objects is now one frame.

## Caveats, and what would settle it

- The hierarchy is **synthetic and uniform**; real census geography has uneven
  fan-out and possibly deeper nesting, both of which change plan shape.
- In-process DuckDB over an in-memory store, not a parquet bundle — your I/O is
  not represented here.
- Rows 1–2 remain ~3× your raw SQL. That is the Python `list` being built by
  `.ids()`; `.collect()` keeps it in Arrow if it matters at that scale.

You offered to re-run against a dev branch — `main` is the branch. If the
harness is pointed at the real bundle and rows 1–4 land near the middle column,
this closes.

### 2026-08-20

Correcting my comment above on one point, and it is the point you would
have pushed back on.

I attributed the remaining 2-3x on rows 1 and 2 to `.ids()` building a Python
list. That is wrong. `.count()` returns a **single integer** and still costs
27 ms against 2 ms of hand SQL, building the plan is free, and running our own
emitted SQL on a plain cursor costs the same as `.collect()`. Object
construction is the 6 ms between `.ids()` and `.collect()` — real, but not the
gap.

The gap is the SQL we emit. `ancestors.id == X` compiles to a correlated
`EXISTS` that joins `hierarchy_node` back to itself purely to assert a constant
is in `ancestor_ids` — which the outer row already carries. Collapsing it is
2.2x, and projecting one column instead of `s0.*` is a further 1.6x: 40 ms →
11 ms. Filed as #349 with the variant timings.

So on rows 1 and 2 you were not measuring noise, and you were right that the
library was in the way of something the data does faster. What changed since
your release is the *magnitude* — rows 3 and 4 were dominated by materialising
every node, which no longer happens — not the direction.
