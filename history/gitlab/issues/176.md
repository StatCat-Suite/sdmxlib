## Type the SDMX-JSON parse boundary (currently `Any`)

The real unchecked `Any` on the JSON side isn't the writers (those *build* dicts —
`Any` is honest there, a recursive JSON type is counterproductive; see the
mutable⟹invariant discussion). It's the **reader/parse boundary**: functions that
take `orjson.loads(...)` output — genuinely `Any` — and navigate it to construct
domain objects.

### The spectrum (pick per call-site, not globally)

| Tool | When | Navigation cost |
| --- | --- | --- |
| `Any` (today) | escape hatch | none, unchecked |
| `object` + narrow | heterogeneous, shallow | isinstance per step |
| recursive `JSONRO` (PEP 695, covariant `Mapping`/`Sequence`) | genuinely open/unknown JSON shape | isinstance per step, but *typed* |
| `TypedDict` (+ `NotRequired`) | **known** shape (SDMX-JSON 2.0 is spec'd) | typed key access, **no ceremony** — cast the top once |
| parse to a domain object | core model / rich navigation | n/a (already the library's job) |

### Recommendation to evaluate
Since SDMX-JSON message shapes are **known** (the spec), `TypedDict` per section
(meta / data / structures / dataSets) is likely the ergonomic sweet spot for the
parse boundary — typed `payload["data","structures"]` without narrowing at every
level — rather than a generic recursive `JSONRO`. Reserve recursive `JSONRO` for
the genuinely-open bits (arbitrary annotation payloads, vendor extensions).

`orjson.loads -> Any` is the seam: assert/cast to the TypedDict/JSONRO once at the
top of each reader, then navigate typed.

### Out of scope / related
- Writer build-dicts stay `dict[str, Any]` (SERIAL_DICT — building is invariant-hostile).
- #169 (resolution `index`) is unrelated — it's a URN→domain-object map, not JSON.
- Bigger design question this raises: **when to keep a strongly-typed opaque tree
  vs parse to a domain object** (pass-through / extension payloads / lossy-model
  round-trip fidelity). To be discussed / captured separately.

## Comments

### 2026-08-05

Closing — overtaken by the msgspec migration. The remaining work is folded into #200.

**The premise is gone.** This issue names `orjson.loads(...) -> Any` as the seam to fix. `orjson` is no longer a dependency; the only occurrences left in `src/` are migration comments. CLAUDE.md now states that neither orjson nor stdlib `json` should appear in `formats/sdmx_json/`.

**The recommendation was superseded by something stronger.** The proposal was a `TypedDict` per message section, so `payload["data","structures"]` could be navigated typed. The reader now does:

```python
dtos = msgspec.convert(data.get("codelists") or [], type=list[CodelistJson])
```

A `TypedDict` only *annotates* a shape — it asserts and hopes. `msgspec.convert(..., type=...)` **validates** on decode and rejects a payload that does not match. Implementing this issue as written would now be a downgrade, not an improvement.

**What actually survives** is narrower than this issue, and is the pattern CLAUDE.md calls out — *"a bare `msgspec.json.decode(b)` returns `Any` (pass `type=...`)"*:

* `formats/sdmx_json/reader.py:317`
* `formats/sdmx_json/metadata.py:211`

```python
doc = msgspec.json.decode(data)          # -> Any
payload: dict[str, Any] = doc.get("data") or {}
```

The **envelope** — `{"$schema": …, "meta": …, "data": …}` — is still decoded untyped and navigated by hand. Everything inside `data` is already typed via Structs. So the fix is one envelope Struct per message kind, decoded with `type=`, which removes both `Any`s and lets the `$schema` discrimination be typed as well.

Worth noting the `payload: dict[str, Any]` annotation is doing its documented job — confining the `Any` to that line rather than letting it ride outward. This is contained, not leaking, which is why it is a tidy-up rather than a defect.

Folded into #200 (known-shape payloads → typed), where it belongs alongside the rest of that census.
