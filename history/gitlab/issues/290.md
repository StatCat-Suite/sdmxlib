# Issue #290: ItemList.__hash__ / ArtefactList.__hash__ are declared but raise for every domain item type

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-21 |
| Labels | `model`, `type::bug` |

Found during #253's mutation triage, as the explanation for a mutant that
could not be killed.

`ItemList.__hash__` and `ArtefactList.__hash__` both do:

```python
def __hash__(self) -> int:
    return hash(self._items)
```

`_items` is a tuple of domain items, and every domain item is an attrs
`@define` class — mutable, therefore unhashable. So:

```
hash(ItemList([Code(id="A", name={"en": "a"})]))  -> TypeError: unhashable type: 'Code'
hash(ItemList([Level(id="L", name={"en": "L"})])) -> TypeError: unhashable type: 'Level'
hash(ItemList([]))                                -> works
```

Only the **empty** list hashes. The classes advertise hashability they cannot
deliver for any type they are actually parameterised with.

## How it surfaced

The mutant `hash(self._items)` → `hash(None)` survives, and re-running
mutation after months of test work did not kill it. The reason is not a
missing test in the ordinary sense: **no test calls `hash` on a populated
`ItemList` because doing so raises**, so there is nothing for a mutant to
break. The mutant is arguably an improvement, since a constant at least
returns.

## Why it matters

Declaring `__hash__` is a claim. A caller who reads the class as hashable —
putting an `ItemList` in a `set`, or using one as a dict key to memoise
something per-collection — gets a `TypeError` at runtime, from a method that
exists specifically to support that use.

Nothing in `src/` calls it today, which is why it has gone unnoticed.

## Options

1. **Hash the ids** — `hash(tuple(item.id for item in self._items))`. Cheap,
   consistent with `__eq__`? *Check that first*: a hash must not distinguish
   values `__eq__` considers equal, and `__eq__` compares items, not ids.
2. **Drop `__hash__`** (set it to `None`). Honest, and makes the failure a
   clear "unhashable type: ItemList" at the collection level rather than a
   confusing one about `Code`.
3. **Freeze the item types.** Largest reach, and probably wrong — the domain
   model is deliberately `@define`.

Option 2 is the smallest correct step; option 1 needs the `__eq__` consistency
question answered before it can be considered.

## Test gate

`tests/unit/test_collections_mutant_gaps.py::test_itemlist_hash_raises_for_every_domain_item_type`
pins today's behaviour, so whichever option is taken shows up as a visible diff
there. The equivalent-mutant record in `docs/design/mutation-testing.md` points
at this issue.
