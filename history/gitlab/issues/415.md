# Issue #415: Temporal query columns compare tz-aware literals in the session's zone, and == refuses a datetime

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-05 |
| Closed | 2026-10-06 |
| Labels | `bug`, `dsl` |

## Summary

`Temporal` query columns (`q.<artefact>.valid_from` / `valid_to`) don't normalise their literals to the store's naive-UTC convention (#321, `storage/_time.py`). A tz-aware `datetime`, which is what `reg.get(urn).valid_from` hands back, is converted by DuckDB to the **session's local time zone** before it's compared. So the answer depends on the machine running the query. Separately, `==` / `!=` refuse a `datetime` outright, because `Temporal` inherits `Num`'s integer-literal check.

Found while checking #411's `InSet` → `= ANY(?)` change for type edge cases. Reproduces identically on `main` before that change, so it's independent of it.

## Repro

DuckDB session `TimeZone` here is `America/Toronto` (UTC-5 in January).

```python
from datetime import UTC, datetime
import sdmxlib as sl
q = sl.q

cls = [sl.Codelist(id=f"CL{i}", maintainer="AG", version="1.0", name={"en": "x"},
                   valid_from=datetime(2020 + i, 1, 1, tzinfo=UTC),
                   codes=[sl.Code(id="R", name={"en": "r"})]) for i in range(4)]
with sl.LocalRegistry(":memory:") as reg:
    reg.add_all(cls)
    aware, naive = datetime(2021, 1, 1, tzinfo=UTC), datetime(2021, 1, 1)
    rows = lambda p: len(list(reg.query(q.codelist).filter(p).collect()))

    rows(q.codelist.valid_from.is_in([naive]))   # 1  ✓
    rows(q.codelist.valid_from.is_in([aware]))   # 0  ✗ want 1
    q.codelist.valid_from == aware               # TypeError: valid_from holds int, got datetime.
    rows(q.codelist.valid_from < datetime(2022, 1, 1, tzinfo=UTC))  # 2, right only by luck
```

| predicate | result | want |
| --- | --- | --- |
| `is_in([naive])` | 1 | 1 |
| `is_in([aware])` | **0** | 1 |
| `== aware` / `!= aware` | **`TypeError`** | a predicate |
| `< aware` | 2 | 2, but compared 5 h off |

## Two defects

1. **Literals aren't normalised.** `storage/_time.py`'s rule is *naive in → aware out*: writers strip the zone after converting to UTC, readers label the result UTC. Query literals skip the "in" half, so an aware value reaches DuckDB, which converts it to session-local time. With the session on UTC-5, `2021-01-01T00:00Z` is compared as `2020-12-31T19:00`, which matches nothing stored at midnight UTC and shifts every range boundary by 5 h. `<` looked right in the repro only because no stored value falls in the 5-hour gap. On a UTC machine (CI, most containers) every case passes, which is how this hides.
2. **`Temporal` inherits `Num.__eq__` / `__ne__`**, whose `_check_literal(self, "int", other)` rejects a `datetime`. The ordering operators evidently don't check, which is why `<` accepts one. So `valid_from == x` is a `TypeError` while `valid_from < x` runs (with defect 1).

## Fix sketch

- Give `Temporal` its own literal check (accept `datetime`, reject `int`), and normalise every literal it receives — in `==`, `!=`, the ordering operators and `is_in` — to naive UTC through the `storage/_time.py` helper writers already use. An aware value is converted to UTC and then has its zone stripped; a naive value is taken as UTC, as the store does.
- Guard it with a test that sets the DuckDB session `TimeZone` to something far from UTC (e.g. `Pacific/Kiritimati`, UTC+14) so the shift is unmissable. Assert each operator against the hand-computed rows for both aware and naive literals. Watch it fail on current `main` first: on a UTC session it can't.
- Check the oracle-backed properties (`tests/support/oracle.py`) and the misuse inventory (`test_query_misuse.py`) for `Temporal`. If temporal predicates have no differential property, that's the gap that let this through.
