# Issue #292: dsl-23: no way to ask whether an annotation type is present at all

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `dsl`, `type::feature` |

Every annotation predicate is *scoped to an existing annotation*, because they all compile to an `EXISTS` carrying a condition on `title` or `text`. There is no predicate that carries no condition, so "has an annotation of this type" and its negation are unreachable.

Measured on a three-code codelist — `A` has a `note` with a title, `B` has a `note` with a NULL title, `C` has no `note` at all:

```
code.annotations["note"].is_null()        -> [B]       # has a note whose title is NULL
code.annotations["note"].is_not_null()    -> [A]       # has a note with a title
~code.annotations["note"].is_not_null()   -> [B, C]  # NOT the above
wanted: has no note at all                -> [C]       # unreachable
```

The emitted SQL for the first is:

```sql
EXISTS (SELECT 1 FROM sdmx.annotation c_ann
        WHERE c_ann.owner_urn = c.code_urn AND c_ann.annotation_type = ?
          AND c_ann.title IS NULL)
```

so `is_null()` reads as "the annotation exists and its title is NULL", not "the annotation does not exist". Both readings are defensible; the DSL only offers the first and does not say so.

## Why this surfaced now

Found while auditing the field × operation matrix for #259. It is not a totality problem — every one of these compiles and returns a correct answer to the question it actually asks — so it is filed separately rather than folded in.

It is also newly *worth* fixing: before #262 there was no `~`, so even with an existence predicate the complement would have been unreachable. `~code.annotations["note"].exists()` works the moment `exists()` does, and `NOT EXISTS` is total, so it genuinely complements (unlike `~` over a nullable column).

## Scope

- `exists()` on `AnnotationRef`, emitting the same correlated `EXISTS` with no condition on the value.
- Decide whether `is_null()` keeps its current existence-scoped meaning. It should — changing it would make `p` and `~p` disagree with `!=`, and the oracles model the current semantics deliberately (CLAUDE.md, "annotation predicates as existence-scoped"). But the docstring must say which question it answers, because the name suggests the other one.
- Same question for `sl.artefact.annotations` and `node.annotations`, which share the ref class.

## Test gates

- `exists()` / `~exists()` partition the rows — assert on the same three-code shape above, since `C` is the row every current spelling misses.
- Differential property: the oracles gain an existence predicate, matching on `any(a.type == t for a in code.annotations)`.
- `is_null()` behaviour unchanged, with a test naming the question it answers.
