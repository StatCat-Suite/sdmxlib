# Issue #222: code_query: id equality is case-sensitive but contains() is not

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-11 |
| Labels | `design` |

Within one accessor, `==` and `.contains()` disagree about case:

```python
code.id == "F"           -> ['F']                  case-SENSITIVE
code.id.contains("F")    -> ['F', 'f', 'CL_FREQ']  case-INSENSITIVE
code.id.contains("freq") -> ['CL_FREQ']            case-INSENSITIVE
```

`_Eq` compiles to `=`; `_StringMatch` compiles to `ILIKE`. Both are reasonable in isolation, and neither is documented, so a caller has no way to predict which they get.

The practical shape of the surprise: `code.id == "cl_freq"` finds nothing while `code.id.contains("cl_freq")` finds `CL_FREQ`. SDMX ids are case-sensitive per the spec (`IDType` permits both cases and treats them as distinct), so two codes `F` and `f` can legitimately coexist — and `contains("F")` returns both.

## Where it comes from

`code_query._emit_string_match` uses `ILIKE` for id fields, with a comment explaining the *accent*-folding decision but not the case one:

```python
# ID fields (code_id / parent_id) keep the plain ILIKE — codes and DGUIDs are
# ASCII identifiers, so folding them is a no-op that only defeats indexes.
```

"folding is a no-op" is about accent-normalisation, which is true. Case-insensitivity is a separate consequence of `ILIKE` that the comment does not address, and it may simply not have been a decision.

## The options

1. **Make substring matching case-sensitive for ids** (`LIKE`), consistent with `==`. Correct per the spec; a search-like API becomes stricter.
2. **Keep `ILIKE` and document it**, as deliberate convenience for interactive search. Then `==` staying case-sensitive is still an inconsistency to explain.
3. **Make it explicit** — e.g. `contains(value, *, ignore_case=False)` — and pick a default.

I have no strong view; the point of the issue is that it is currently accidental rather than chosen. The same applies to `hierarchy_query`, which uses `ILIKE` for `node_id`, `parent_node_id`, `level_id` and `code_urn`. `code_urn` is the interesting one: URNs are case-sensitive identifiers, so case-insensitive matching there is harder to defend than on a label.

## Not affected

Label fields (`name[lang]`, annotation title/text) are deliberately accent- *and* punctuation-insensitive via `_label_match_sql`, which is documented and clearly intended. This issue is only about **id-like** fields.

## Test gate

Whatever is chosen, `tests/support/oracle.py` must be updated to match — it currently models the *observed* behaviour (case-insensitive `contains`, case-sensitive `==`) so the #217 differential properties pass against today's implementation. A change here should flip that model and the properties should follow.

## Provenance

Found by the #217 differential properties: Hypothesis generated a codelist containing both `F` and `f`, and the SQL and the pure-Python oracle disagreed. That is precisely the class of input a fixture author would not think to write.

## Comments

### 2026-08-11

Resolved as **option 1 + 3 combined**, but reframed: case is not a separate question from #255 — it is the rung #255 left out.

## The premise, re-measured

The issue’s code citation is stale (#255 restructured `_emit_string_match`), and its “Not affected: label fields” is stale too. After #255 removed the *implicit* label folds, labels case-fold exactly as ids do. It was never an id-field quirk: **every string match, on every field, in all four DSLs**, with no way to ask for a case-sensitive one.

Two measurements decided the shape:

- The insensitive default is also the **expensive** one — 500k labels, `ILIKE` 8.66 ms vs `LIKE` 0.97 ms. Callers pay 9x for a fold nobody asked for.
- Inserting a case rung keeps the ladder monotone: `plain ⊆ caseless ⊆ unaccented ⊆ folded`, strengthening the 3-term subset property #255 already asserts.

So `Fold.NONE` folded case — the floor of the ladder was not a floor and its name was a lie.

## Peers

Unanimous, and the *mechanism* mattered more than the default. SQLAlchemy has two:

```
(a) i-prefixed op       c.icontains(x)                     -> ILIKE
(b) .collate(modifier)  c.collate("NOCASE").contains(x)    -> (v COLLATE "NOCASE") LIKE
                        c.collate("NOCASE") == x           -> (v COLLATE "NOCASE") =
```

(a) is what everyone uses **when case is the only axis** — polars `(?i)`, Django `__icontains`, pandas `case=`. None of them has an accent or punctuation fold at all. When strength is multi-valued, SQLAlchemy switches to a modifier chained before the op — structurally our `.unaccented.contains(...)`. So the chain shape is precedented for exactly our situation, and it settles `==` too.

## Shipped

| Spelling | Ignores | Available on |
| --- | --- | --- |
| `id.contains(x)` | nothing (`LIKE`) | every string ref |
| `id.caseless.contains(x)` | case (`ILIKE`) | every string ref |
| `name[l].unaccented...` | case + diacritics | label refs |
| `name[l].folded...` | + punctuation | label refs |

`.caseless` also carries `==` / `!=`; the accent rungs still do not (#255’s call, left standing). `is_in` stays exact — no peer offers a caseless membership test.

Equality compiles to `COLLATE NOCASE =`, not `ILIKE`. An equality operand is not a pattern: `ILIKE` is the obvious shortcut and is silently wrong, because `_` and `%` in a caller’s id become wildcards, so `id.caseless == "CL_FREQ"` would also match `CLxFREQ`. SDMX ids contain `_` constantly.

## Two defects found on the way

1. **The oracles were already wrong about case.** They modelled `ILIKE` with `str.casefold`. DuckDB’s `ILIKE`, `COLLATE NOCASE` and `lower()` agree with each other and all three disagree with casefold on `Straße`/`STRASSE` and `ﬁle`/`FILE`. It never failed because a generated needle is a slice of the generated value, so the fold cancels. Now `str.lower`, with the residual `İ` divergence pinned as examples in `test_case_ladder.py` rather than modelled.

2. **`code_query`’s differential had no power over case.** A probe reverting the default to `ILIKE` left it green — only the *hierarchy* property and the hand-written tests caught it. Its needles come from the same alphabet as the values, so they differ in more than case and the fold never changes an answer. Both suites now draw case-mutated needles.

## Guards

- `test_case_ladder.py` — 11 examples: the reported asymmetry, the ladder, `NULL` under `caseless !=`, the wildcard-stays-literal case, and the Python/SQL divergence table.
- `test_caseless_predicates_agree_with_oracle` in both property files, needles case-mutated so the rungs can actually disagree. Discrimination-probed both ways.
- Subset property extended to four terms. Note it cannot catch a *missing* fold (the chain stays monotone), so the differential carries that.
- SQL corpus: 14 lines, all `ILIKE`→`LIKE`, nothing else. Caseless entries added so the new rung is guarded too.
