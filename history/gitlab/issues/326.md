# Issue #326: n_unique carries a polars name with SQL null semantics — len(unique()) != n_unique()

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-17 |
| Closed | 2026-08-19 |
| Labels | `design`, `dsl` |

Surfaced by adding `Col.unique()` (!334), which made a pre-existing divergence visible rather than creating it.

## The disagreement

```
column values: [NULL, 'W', 'W']

sdmxlib   unique()   -> ['W', NULL]      n_unique() -> 1
polars    unique()   -> ['W', None]      n_unique() -> 2
```

polars is self-consistent — a null is a value, so `len(s.unique()) == s.n_unique()` always holds. Ours is not: `unique()` compiles to `list(DISTINCT x)`, which keeps the null, and `n_unique()` compiles to `count(DISTINCT x)`, which does not count it. **DuckDB's two functions disagree with each other**, and we inherited both.

So a caller can write `col.unique()` and `col.n_unique()` on the same column and get answers that differ by one, with nothing in either name suggesting why.

## Why it matters more than it looks

Both names are polars'. CLAUDE.md's rule is that when a DSL decision has a counterpart in polars or SQLAlchemy we check it — and this is a case where we took the name and not the semantics. `list()` already keeps nulls, so `unique()` keeping them is consistent with the rest of *our* language too; `n_unique()` is the odd one out on both counts.

## Options

1. **Move `n_unique` to polars semantics.** `count(DISTINCT x) + CAST(bool_or(x IS NULL) AS INT)`, or equivalently the length of the distinct list. Makes the pair coherent and matches the name's origin. Costs a behaviour change to a shipped API (pre-stability, so no shim) and a slightly more expensive aggregate.
2. **Move `unique` to SQL semantics** — drop nulls. Cheap, but then `unique()` disagrees with both `list()` and polars, and the language has two different null rules for collecting versus deduplicating.
3. **Document the split and keep both.** Defensible only if someone can say what the SQL rule buys a *user*.

1 looks right; the argument against is that no consumer has asked, and the aggregate gets slower for everyone to fix an inconsistency at the null edge.

## Guard

`test_unique_is_null_aware_and_n_unique_is_not` in `tests/unit/test_query_select.py` asserts today's behaviour and cites this issue, per the oracle rule that a surprise is modelled and pointed at rather than smoothed over. Whichever option wins, that test is where it lands.
