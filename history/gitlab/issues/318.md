# Issue #318: detail= has no model in the path language: every REST fetch is detail=full, and browse()'s cheap listing is gone

| State | closed |

Fallout from #312 / !314, recorded rather than absorbed.

`_closure` derives `references=` from the relations a query reaches, and §11
argued the same instinct for projection. **`detail=` got no such treatment.**
`_rest.Request.detail` is `"full"` for every request the planner issues.

## What was lost

The retired `reg.query(T).browse()` asked for `detail=allstubs` — identity
fields only, collections empty — and the cookbook recommended it as *"the
fastest way to list what a registry contains"*. The replacement,

```python
reg.query(sl.q.dataflow).filter(sl.q.dataflow.agency == "ECB").ids()
```

asks for the same set at `detail=full`. It is the query most likely to be
someone's first, and it now downloads every component and annotation of every
dataflow to print a list of ids.

Unmeasured, deliberately — the point of this issue is that nobody has looked.
For scale, `/dataflow/ECB?detail=full` is 38.6 KB for 102 dataflows (§11), so
the *stub* saving on that particular call is probably small. It will not be on
a resource whose artefacts carry items.

## What the answer probably looks like

The same shape as `references=`, and the machinery is already there:

- A query whose closure names only spine columns — `id`, `agency`, `version`,
  `name` — can be served by `allstubs`.
- Anything reaching a contained relation (`dimensions`, `codes`, `annotations`)
  or a crossed one needs `full`.
- `Frame`'s projected paths feed in the same way §11 describes.

So plausibly `detail_for(root_table, paths)` beside `references_for`, sharing
`closure()`.

## Why it needs care rather than a patch

**The failure mode is the silent one.** A query served at `allstubs` when it
needed `full` evaluates against empty collections and answers *nothing*, with
no error — the same silence §13 was written about, and the reason
`references=` is derived rather than chosen. Getting `detail=` wrong is
exactly as quiet.

Two things to establish before implementing:

1. **What `allstubs` actually omits, per service.** The spec says identity
   fields; whether every implementation agrees is a question for recorded
   responses, not for reading. `references=` was pinned to the wire for this
   reason (`test_the_depth_rule_matches_what_the_wire_returns`).
2. **Whether `detail` and `references` interact.** `detail=referencepartial`
   already appears in the client's presets alongside `references=descendants`,
   and the two are not obviously independent — a stub *plus* descendants may
   mean something other than the sum.

## Gates

- Derived from the closure, not chosen by the caller — same rule as
  `references=`.
- Pinned to a recorded response: fetch at `allstubs` on purpose and assert
  what a query over a contained relation then answers.
- The differential in `tests/unit/test_query_rest_executor.py` extends to it:
  a store filled from a stub fetch must answer what a complete one does, or
  the derivation asked for too little.
