# Issue #241: DataConstraint cannot hold a DataKeySet, so 3.0 documents carrying one lose it

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Labels | `bug` |

`DataConstraint` has no field for `<str:DataKeySet>`, so a schema-valid document carrying one loses it on read — silently, with no error.

## Reproduction

A minimal 3.0 constraint with an explicit key set, validated against the vendored XSD before parsing:

```
input is schema-valid 3.0
round-trip: 4 missing, 0 changed
   lost DataKeySet
   lost Key
   lost KeyValue|id=FREQ
   lost Value
```

`DataConstraintType` is `DataKeySet | CubeRegion`; sdmxlib models only the second. The same applies in 2.1, where `ContentConstraintBaseType` also carries `DataKeySet`.

It has gone unnoticed because no checked-in fixture puts a key set inside a data constraint — the only `DataKeySet` in the corpus is on an `AttachmentConstraint`, which *is* modelled with a `data_keys` field.

## Consequences beyond the loss itself

**1. An unnecessary refusal.** `validation._UNWRITABLE` refuses `attachment_constraints` on 3.0/3.1/JSON on the grounds that "SDMX 3.0 removed AttachmentConstraint; use a DataConstraint". That message is right about the format and wrong about what sdmxlib can do with it — the advice cannot be followed, because `DataConstraint` cannot hold the key set that gives an AttachmentConstraint its content.

2.1 carried *two* constraint artefacts, `ContentConstraint` and `AttachmentConstraint`, and 3.0 unified them into one `DataConstraint` with a `role`. That is a unification, not a reduction: everything an AttachmentConstraint says is expressible in 3.0. Once `DataConstraint.data_keys` exists, a 2.1 AttachmentConstraint could be *converted* on 3.x write rather than refused, which is both lossless and what the TWG intended.

**2. It weakens a claim made elsewhere.** Several places in the codebase and issue tracker reason from "3.0 removed X" to "X has no 3.0 representation". For constraints that inference is false. It happens to be true for the `StructureSet` / `HierarchicalCodelist` *grouping*, which really has no 3.x equivalent — but the two cases should not be treated alike, and currently they are.

## Suggested shape

1. Add `data_keys: tuple[DataKey, ...]` to `DataConstraint`, mirroring `AttachmentConstraint`.
2. Read and write it in 2.1, 3.0, 3.1 and SDMX-JSON.
3. Reconsider the `attachment_constraints` entry in `_UNWRITABLE`: with the field in place, converting to a `DataConstraint` is lossless and strictly better than refusing.
4. Add a fixture carrying a key set in a data constraint, so the document-fidelity harness covers it — its absence is why this survived.

## Note

Found while answering "did SDMX 3.0 make the model less expressive?" The answer is mostly no — most dropped 2.1 constructs were relocated (MSD targets moved to `Metadataflow`/`MetadataSet`) or unified (this case). The grouping containers are the one genuine reduction.
