# Issue #310: qualify(): call order does not decide the window's input set, and the docstring said it did

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-14 |
| Closed | 2026-08-14 |
| Labels | `design`, `dsl`, `type::bug` |

`Query.qualify`'s docstring claimed the clause order decides which set the
window is computed over:

> a rank is computed over whatever set precedes it, so
> `filter(agency == "X").qualify(rank == 1)` ranks within ESTAT while the
> other order ranks across everything and then keeps the ESTAT winners.
> Both are meaningful and they differ, so the DSL names the stage rather
> than leaving it to call order.

**They do not differ.** Every clause compiles into one `SELECT`, and SQL
evaluates `WHERE` before the window, so `filter` always runs first whatever
the call order. Both spellings emit byte-identical SQL.

## The discriminating case

Partitioning by `id` alone, with a globally-newer OECD version, "rank across
everything then keep ESTAT" must return **nothing** — ESTAT's row is not
rank 1 globally:

```python
latest = q.dataflow.version.rank(descending=True).over(q.dataflow.id) == 1

reg.query(q.dataflow).qualify(latest).filter(q.dataflow.agency == "ESTAT")
# documented: []        (ESTAT loses to OECD 9.0 globally)
# actual:     [ESTAT 1.0]
```

Caught while writing the cookbook entry for #278 — the example was written
from the docstring, and the fixture that would make the contrast visible made
it disagree instead.

## Why it matters

This is the failure mode %15's refinement principle exists to prevent, in its
worst form. The order does not silently change the answer; the *documentation*
says it does, so a caller writing the second spelling gets a plausible answer
to a question they did not ask, with nothing to indicate it.

## Done in !302

The false claim is removed from both the docstring and
`docs/cookbook/discovery.md`, and
`test_filter_before_and_after_qualify_are_the_same_query` pins the real
behaviour on the discriminating fixture — so this issue is about the missing
*capability*, not about a live wrong claim.

## What is actually open

Two candidates, and they are not exclusive:

1. **Refuse `filter()` after `qualify()`**, the shape `_refuse_after_slice`
   already uses. Only the expressible reading can then be written, and the
   refusal can name the other one. Small, and consistent with how the DSL
   handles every other ambiguous sequence.
2. **Implement the subquery wrapper** —
   `SELECT * FROM (SELECT *, rank() OVER (...) rn ...) WHERE rn = 1 AND ...` —
   which makes the second reading expressible. This is the compiler obligation
   §4 of `docs/design/query-language.md` already leaves open for backends
   without native `QUALIFY`, so the two wants coincide.

My inclination is (1) now and (2) when a backend forces it, but the refusal
message should not promise a spelling that does not exist yet.

### 2026-08-14

Worked this, and **the capability is not missing** — which makes this issue's
own framing wrong, mine included.

## The second reading is already expressible

"Rank across everything, then keep the matches" is a *different query*, not a
different call order, and nesting spells it:

```python
ranked = reg.query(q.dataflow).qualify(latest).select(urn=q.dataflow.urn)
reg.query(q.dataflow).filter(q.dataflow.urn.is_in(ranked), q.dataflow.agency == "ESTAT")
```

On the discriminating fixture (OECD 9.0 globally newest, ESTAT 1.0) this
returns `[]`, where the flat spelling returns the ESTAT row. Verified, and
pinned in `test_the_global_reading_is_reachable_by_nesting`.

That is the same shape filter-after-slice already uses, for the same stated
reason: when two readings are both meaningful, the DSL spells them
differently rather than making one depend on call order.

## So the fix was documentation, not machinery

- `Query.qualify`'s docstring and `docs/cookbook/discovery.md` now carry the
  nesting recipe, and both record that the old claim was false.
- Two tests: one pinning that the call orders emit identical SQL, one pinning
  that the nested spelling gives the *other* answer. The second is what makes
  the first safe to state.

## Why option 1 (refuse `filter()` after `qualify()`) was rejected

It looked right — it is exactly the `_refuse_after_slice` shape — but the
parallel breaks on the thing that matters. Filter-after-slice returns
**different rows** from slice-after-filter, so picking one silently is a wrong
answer and the guard prevents a defect. Filter-after-qualify returns the
**same rows** either way. A refusal there would fire on a correct,
unambiguous query — breaking the ordinary case where a helper qualifies and
its caller narrows — to prevent a misunderstanding rather than a defect.

It would also add a carve-out to a law that currently has exactly one:
"every ordering either commutes or is refused". This pair *commutes*. The law
is satisfied, and refusing a commuting pair weakens it.

## Why option 2 (subquery wrapper on filter-after-qualify) was rejected

It would make the documented-but-false semantics true by making call order
significant — introducing a second order-sensitive pair into a language whose
composition is otherwise declarative. The wrapper is still wanted for a
backend without native `QUALIFY` (§4 of `docs/design/query-language.md`), but
that is about *where* a query runs, not about what call order means.

## Proposed close

The defect — a docstring asserting semantics that did not exist — is fixed,
and the capability it pointed at works and is now findable. Closing unless
the reasoning above is wrong somewhere.
