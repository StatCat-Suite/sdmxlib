## Comments

### 2026-08-17

**`sum`, `mean`, `min`, `max` landed** in !337 — #297 staging step 3.

Named for polars like the rest of the set, so `mean` compiles to SQL's `avg` the way `n_unique` compiles to `count(DISTINCT …)`.

Answers to the three open questions in this issue:

**Where do they refuse?** Not at compile time. The path language carries no column types — there is no equivalent of #272's literal checking in `query/`, and `schema.py` reflects column *names* only. So `sum` over text is refused by DuckDB (`No function matches the given name and argument types 'sum(VARCHAR)'`), which names the function and the type and is enough to act on. Documented in the docstring, the cookbook page and a test rather than left to be discovered. **This issue stays open for that question** — whether the compiler should know column types is a real design choice with more uses than this one.

**Null semantics.** SQL and polars agree: nulls are skipped, not counted as zero, so the mean of `[10, NULL]` is 10. Asserted rather than assumed, precisely because #326 records a case where the two disagree — a facet's `max_length` is the nullable numeric column that can show it.

**`min`/`max` turned out not to be numeric aggregates at all.** Both SQL and polars order text, so they are usable on structural metadata where `sum`/`mean` are not: `children.id.min()` is a code's alphabetically first child. That is a better answer than the issue anticipated and is now what the cookbook leads with for structural use.

One thing worth recording beyond the issue's scope: the windowed forms emit **no window `ORDER BY`**, joining the existing aggregates. `sum(v) OVER (PARTITION BY g ORDER BY v)` is a *running* total, so without that, `x.sum() / x.sum().over()` — %15's percent-of-total — would be a share of a prefix. The exclusion set is now a named constant carrying that reasoning.

Still open here: **the ordered aggregate** (`any_value(x ORDER BY y)`), which both consumers write and which needs the naming decision against polars' `first`/`last` and SQL's `first_value`/`arg_min`/`arg_max`.

### 2026-08-20

**Audit note — mostly landed since this was filed.**

The title says "no sum/avg/min/max, and no ordered aggregate". Measured against
current `main`, the first half is no longer true. Every column type carries:

`count`, `sum`, `mean`, `min`, `max`, `n_unique`, `list`, `unique`

plus the window functions `rank`, `dense_rank`, `lag`, `lead`, `row_number`, and
`Agg.over` / `Agg.desc` for framing and ordering. `version.min()` / `max()` were
fixed in #351 to compare by version-sort rather than as text.

So the aggregate set is no longer thin. What remains open, if anything, is the
*ordered aggregate* half — an aggregate whose result depends on a sort within
the group (`first`/`last` by an ordering, or `list` with an explicit order). If
that is still wanted it deserves restating on its own terms, since the issue as
written now reads as fixed.

Worth deciding before the API freeze rather than after: adding an aggregate is
additive and safe, but if `list()` should have taken an ordering argument from
the start, that is a signature change.

Related: #341 asks what `list()` / `unique()` should answer for an empty
fan-out, which is the other unsettled thing about the same two methods.
