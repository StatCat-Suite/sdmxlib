# Issue #399: get(SdmxUrn.parse(...)) types as LazyCodelist whatever the URN names — #397's overloads and Any

| | |
| --- | --- |
| State | closed |
| Opened | 2026-09-08 |
| Closed | 2026-10-07 |

A known limitation introduced by #397 (!472), documented in
`LocalRegistry.get`'s docstring but not tracked anywhere. Filing it so the
trade-off is revisitable rather than only discoverable by reading the method.

## The behaviour

```python
reveal_type(reg.get(SdmxUrn.parse(text)))          # LazyCodelist | None
reveal_type(reg.get(artefact_urn(some_dataflow)))  # LazyCodelist | None
reveal_type(reg.get(DataStructure.urn_for(...)))   # DataStructure | None  ✓
```

The first two are wrong for any URN that does not name a codelist, and
confidently so — the runtime class for a parsed DSD URN is `DataStructure`
while the declared type says `LazyCodelist`.

`Any` matches every overload and the first one wins. Both entry points return
`SdmxUrn[Any]` deliberately: CLAUDE.md keeps that on `parse()` because it feeds
`Ref.unresolved(urn) -> Ref[T]`, which needs the bivariance, and narrowing it
once before "caused 23 errors elsewhere" (#286). `artefact_urn` returns `Any`
for the same reason.

## Why the ordering is what it is

Measured both ways:

| overload order | `SdmxUrn[Codelist]` | `SdmxUrn[Any]` |
| --- | --- | --- |
| generic first | `Codelist` — the lie #397 removed | `Any` ✓ |
| specific first (shipped) | `LazyCodelist` ✓ | `LazyCodelist` ✗ |

Neither is right for both, and the shipped order is the lesser evil:

* The explicit spelling — `Codelist.urn_for(...)` — is the common one, and
  generic-first sends it back to declaring `Codelist` for a `LazyCodelist`,
  which is the silent lie #397 existed to remove. That one *stays* wrong
  through any amount of correct-looking code.
* The `Any` case fails **loudly** instead: the first attribute that is not on
  a codelist is a type error, which points at the problem rather than hiding
  it.

## Scope

Four call sites today (`tests/unit/test_data_store_sort_order`,
`test_roundtrip_derived`, `test_storage_timestamps` ×2), all of which now
narrow with an `isinstance` because #347 made them visible. The exposure is
larger than that count: any caller holding a URN it parsed or derived from an
artefact hits it, and gets a plausible-looking type back.

## Options

1. **Leave it, as now.** Documented in the method; the wrong case is loud. Zero
   cost, and the trade-off is recorded.
2. **Narrow `SdmxUrn.parse` to `SdmxUrn[object]`.** `get(parse(...))` then
   picks the generic overload and answers `object | None` — honest, and a
   caller narrows. Cost is #286's 23 errors, which would need re-measuring;
   CLAUDE.md's stated reason for `Any` there is the `Ref.unresolved`
   bivariance, so this needs checking against that specifically rather than
   assumed still true.
3. **Drop the overloads, keep #397's runtime half.** `get` goes back to one
   signature; the lazy classes still refuse `codes` / `tree` / `descendants`
   by name. Loses the static half for every caller to fix one case.
4. **A separate entry point for the untyped case** — `get_any(urn)` declared
   `-> object | None`, with the overloads left for typed URNs. Two names for
   one operation, which the naming rule argues against, but it does make the
   distinction the caller actually has.

(1) is the current state and defensible. (2) is the only one that fixes the
case without giving anything back, and turns on a measurement that is now four
milestones old.

## There is no narrow fix, which the description left open

Confirmed rather than assumed: **you cannot overload against `Any`**. It
matches every overload and the first one wins, so no reordering, no extra
overload and no more specific parameter type can catch the `SdmxUrn[Any]` case.
Option 3 (drop the overloads) and option 4 (`get_any`) both give something back
or add a second name; option 2 is the only one that fixes it, exactly as the
description says.

## What the 53 actually are, and why it is not a big pass in disguise

Every one is the same shape:

```python
Ref[Concept].unresolved(SdmxUrn.parse(concept_urn_str))
```

The call site **already states the type** by parameterising `Ref`. `Any`
launders it; `object` does not, because `SdmxUrn`'s phantom is *covariant* —
`SdmxUrn[object]` is the widest type and nothing narrower accepts it. That is
the whole error class, in `src` and in `tests` alike.

So the fix is the witness pattern `SdmxUrn.make[U]` already uses and CLAUDE.md
already recommends — a witness-carrying parse:

```python
@overload
def parse(cls, urn: str) -> SdmxUrn[object]: ...
@overload
def parse(cls, urn: str, artefact_type: type[U], /) -> SdmxUrn[U]: ...
```

## Plan, when it is scheduled

1. **`Ref.unresolved` returns the class's own `T_co`** rather than binding a
   fresh `U` from the urn. Measured: **53 → 28 basedpyright, 29 → 5 pyrefly**,
   on its own. It matches the `Ref[Concept].unresolved(...)` idiom the code
   already writes and the rule CLAUDE.md's test-style section already states.
   Costs one suppression *inside* `unresolved` — you cannot construct a
   `Ref[T_co]` from a covariant position — which needs approval on its own
   terms.
2. **Witness overload on `parse` / `parse_item`**, then the witness added at
   the ~28 remaining sites. Mechanical, and each one gains real checking where
   it currently launders `Any`.
3. **CLAUDE.md**, whose typing section currently *justifies* the `Any` on
   `parse` by the `Ref.unresolved` bivariance. Step 1 removes that
   justification, so the guidance has to move with the code or it becomes the
   next stale rule.

Not folded into this session: it is milestone-shaped, and a rushed typing pass
is how the 59 dead suppressions #347 cleaned up got there in the first place.

Option 1 remains defensible meanwhile, for the reason the description gives —
the wrong case fails loudly at the first attribute that is not on a codelist,
rather than staying wrong through correct-looking code.

### 2026-09-28

Re-measured this, and the diagnosis in the description is wrong in one load-bearing
place: **`Any` matching every overload with the first one winning is basedpyright's
behaviour, not the typing spec's.** The ordering is not the trade-off it looks like.

## Step 5, and a nested `Any`

The spec's overload algorithm, step 5: when more than one overload still matches and
"the return types are not equivalent, overload matching is ambiguous. In this case,
infer a return type that is assignable to each of the remaining return types". It
applies to an argument type that *contains* `Any` — the spec's own example is
`list[Any]`, and `SdmxUrn[Any]` is the same shape.

`get` has two lazy-root overloads with different return types, so the spec answer for
`SdmxUrn[Any]` is gradual. On 25 lines with no sdmxlib in them:

| argument | spec | basedpyright 1.39.9 (pyright 1.1.411) | pyrefly 1.2 |
| --- | --- | --- | --- |
| `Box[Any]`, two specific overloads differing | gradual | **`LazyA`** — first match | `Any` |
| bare `Any`, same shape | gradual | `Unknown` | `Any` |

So basedpyright applies the rule for an argument that *is* `Any` and skips it for one
nested in a generic. pyrefly is already honest here; basedpyright is the source of
truth for `just check`, which is why the wrong type is the one a caller sees.

## Option 2, measured

Narrowing `SdmxUrn.parse` to `SdmxUrn[object]`: **52 basedpyright + 27 pyrefly**
findings. The description's "23 errors elsewhere" from #286 is now 52 — `tests/`
entering basedpyright's scope in #347 is the growth.

Every one is the same fact, not 52 independent problems: `Ref` is invariant by design
(#289), so `Ref[object]` does not go where `Ref[Codelist]` is wanted. The sites are
readers parsing a URN they know names a codelist and handing it to a typed field —
correct code, 52 times. It would take ~50 casts to work around another tool's bug, so
option 2 stays rejected, now with a current number rather than a stale one.

The description's claim about **ordering** checks out, though: putting the generic
overload first gives `Any | None` for the ambiguous case *and* `Codelist | None` for a
codelist URN, which is the silent lie #397 removed. That is the sabotage check for the
new probe, so it is now asserted rather than remembered.

## What landed (!493)

No behaviour change in `src/`. Two guards, so the conclusion stays checked:

- `tests/typing/probe_urn_any.py` pins the declared types **including the wrong one**,
  states in its first paragraph that it does so deliberately, and lists the three
  deletions that come due when basedpyright conforms.
- `tests/unit/test_overload_any_ambiguity.py` runs both checkers on the repro, pins
  each answer, and asserts they genuinely disagree — so a resolution in either
  direction fails a test instead of passing unnoticed.
- `LocalRegistry.get` and `SdmxUrn.parse` carry the measurement, so the next reader
  does not start from #286's 23.

Leaving this open: the caveat is still in the code, and the upstream report is unfiled.
What it no longer needs is a decision between the four options.

> contains `Any` rather than being `Any`**
>
