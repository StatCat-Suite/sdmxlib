#248 / #249 gave the two *structural* query DSLs oracle-backed differential properties. The **data plane** — the builder that actually turns SDMX query parameters into `SELECT … WHERE col IN (?)` over an observation table — has none.

## The builder in question

```
key + c[...] params  --parse_components-->  ComponentFilter  --to_where_clauses-->  fragments + params
                                                             --_build_query------->  SELECT ... FROM ... WHERE ... ORDER BY ... LIMIT ?
```

| Module | Statements | Line cov | Differential tests |
| --- | --- | --- | --- |
| `sdmxlib/rest.py` | 69 | 100% | none |
| `sdmxlib/local/data_store.py` | 234 | 84% | none |
| `sdmxlib/local/sql.py` | 52 | 100% | none |

100% line coverage on `rest.py` and the empty-`IN ()` bug (#256) sat in it untouched. That is the same lesson as `code_query`, on a module nobody had pointed a generative test at.

This layer is *more* differential-testable than the structural DSLs, not less: the answer to "which observations match this filter" is a Polars expression over the same frame the fixture built.

## Reference interpreter

A naive Polars evaluator over the frame, optimised for obvious correctness and never for speed:

- AND across components, OR within a component — that is the whole semantics. There is no `Or` or `Not` combinator to model; do not build a recursive ADT interpreter for expressiveness the IR does not have.
- `None` on a dimension is a wildcard.
- `SqlRelation` values resolve to the id set the relation produces, so a `CodeQuery`-backed hierarchy slice can be compared against the oracle's own set.

Same discipline as the two existing oracles: it shares no code with `rest.py`, and it states what the library does rather than what it should.

## Fixture

A cartesian product of small codelists (2–4 codes per dimension, so the table stays in the low hundreds of rows), registered as a Polars frame rather than issued as `CREATE TABLE`. The product matters for two reasons: the expected result of any filter combination is trivially computable, and no accidental correlation between dimensions can mask a bug.

**Include at least one nullable attribute.** Three-valued logic under `NOT IN` / `<>` is where SQL builders most reliably diverge from the naive reading, and a fixture with no NULLs will never show it. We already learned the shape of this on the structural side — `parent_id != x` excludes roots because `NULL != ?` is `NULL` — and the same trap exists here for attribute filters.

Check for overlap with `tests/bench/fixtures.py` before writing a new one; the bench harness already materialises observation frames and may be the right thing to lift from.

## Properties

- **Differential** — for every generated `ComponentFilter`, the rows DuckDB returns equal the rows the Polars interpreter selects. Compare sorted frames on all columns.
- **Executes at all** — every generated filter's SQL runs without raising. This is the general form of #256 and is where that guard belongs.
- **Param/placeholder alignment** — the count of `?` in the emitted SQL equals the length of the params list. A drift here is the classic bug this layer is exposed to, because `_build_query` concatenates params from three sources (`where`, `component_filter`, `limit`) and a `SqlRelation` splices *its* binds into the middle.
- **Monotonicity** — widening a component's OR-set never shrinks the result; adding a component never grows it.
- **Wildcard identity** — a filter of all-`None` returns the whole table, and `is_wildcard` agrees with that.
- **`limit(n)` is a prefix** of the unlimited, ordered query — stated as a prefix rather than a length so a `LIMIT` applied before the `ORDER BY` fails.

## Risks

- **`SqlRelation` makes the params list order-sensitive in a way the structural DSLs are not.** Generate filters mixing eager lists and relations in both orders; that interleaving is the point.
- **Do not test against a live DuckLake catalog here.** Registered Polars frames cover the semantics; catalog integration is a separate and much smaller suite. Equally, do not mock the connection — in-memory DuckDB is sub-millisecond and a mock would only test the builder against a fictional dialect.

## Test gates

- Differential property over generated `ComponentFilter`s, including empty, wildcard, single-value, all-values and relation-valued components.
- At least one nullable attribute in the standard fixture, with the NULL semantics of attribute filtering written down in the interpreter's module docstring — expect to discover the library has not decided it.
- Placeholder/param alignment asserted on every generated query.
- Coverage for `local/data_store.py` reported before and after.
