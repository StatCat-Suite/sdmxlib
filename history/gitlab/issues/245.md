# Issue #245: MSD targets relocated from the structure to the flow: decide the 2.1 <-> 3.0 story

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Milestone | %12 Cross-version conversion: convert what converts, refuse only what cannot |

A 2.1 `MetadataStructure` cannot make the trip to 3.0 and back, and a 3.0 one cannot be written as 2.1 at all (#235). Both stem from the same relocation, which is worth stating precisely because it is *not* a deletion.

## What moved where

```
2.1  MetadataStructureComponentsType : MetadataTarget, ReportStructure
3.0  MetadataflowType                : Target
3.0  MetadataSetType                 : MetadataProvisionAgreement | Metadataflow, Target, Attribute
```

2.1 declares, in the **structure**, what kinds of thing the metadata may describe, and groups attributes into `ReportStructure`s each naming its targets. SDMX 3.0 moved that question out of the structure: a `Metadataflow` declares its `<Target>`s, and a `MetadataSet` names the actual targets it reports against.

Arguably a better model — targets are a property of the flow and the instance, not of the attribute schema. But it means the information has no MSD-level home in 3.0, so the conversion is not local to one artefact.

## Why each direction is blocked

**2.1 → 3.0.** The MSD's target declarations must land on a `Metadataflow`. If the 2.1 message carries an MSD with no metadataflow — legal, and the case in `tests/fixtures/sdmx_ml21/with_metadata_structure.xml` — there is nowhere in 3.0 to put them. The `ReportStructure` grouping (which attributes belong to which report) has no 3.0 equivalent either; 3.0's MSD is a single attribute tree.

Currently sdmxlib reads the attributes and drops the layer (#236), which is why this direction *appears* to work.

**3.0 → 2.1.** The reverse needs a `MetadataTarget` and a `ReportStructure` to exist, and the model carries neither, so writing refuses (#235).

## Options

1. **Leave both refused, document the asymmetry.** 2.1 reference metadata is rare. Cheapest, and honest.
2. **Model the 2.1 layer** as optional concepts populated on 2.1 read and used on 2.1 write, ignored by 3.x. This is #235's option 3. It makes 2.1 → model → 2.1 exact and leaves 2.1 → 3.0 → 2.1 still lossy, since the intermediate 3.0 document cannot carry the layer.
3. **Synthesise on conversion**: when writing 2.1 from a 3.0-shaped MSD, generate one `MetadataTarget` and one `ReportStructure` containing all attributes. Produces valid 2.1 that means roughly the right thing, but invents structure — and a 3.0 → 2.1 → 3.0 trip would not return the input.

Option 2 fixes the same-version case, which is the one #237 actually requires. **No option makes 2.1 → 3.0 → 2.1 exact**, because the intermediate cannot hold the layer — so this should be recorded as a permanent cross-version boundary alongside the grouping containers, rather than left looking like unfinished work.

## First step regardless

Whichever is chosen, `with_metadata_structure.xml` should stay in the cross-version harness as a declared block, so the boundary is asserted rather than assumed.
