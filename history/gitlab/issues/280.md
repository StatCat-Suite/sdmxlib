Split out of #276, which covered the artefact spine and deliberately stopped
short of this.

`sdmx.dsd_component` is **21 of the 113 hand-written sites** — the largest
single table after the spine. What consumers ask it: "which dimensions does
this flow have", "which codelist enumerates dimension X of dataflow Y",
"every dataflow × dimension × codelist as a frame", joined at catalogue scale.

## What #276 already covers, and what it does not

`sl.artefact.uses_concept(...)` and `sl.artefact.uses_codelist(...)` answer the
**discovery half** — "which dataflows use REF_AREA" — by compiling an `EXISTS`
through `dataflow ⋈ dsd_component`. That was the highest-value slice and it is
done.

What is missing is the **projection half**: getting component rows *out*, as a
frame, across many DSDs at once. There is no way to ask

```python
# every dimension of every ESTAT dataflow, with its codelist — as one frame
```

without dropping to SQL, and `dsd.dimensions` only answers it for one resolved
DSD at a time — which is exactly the 800-resolutions problem #276 was about.

## Why this is a genuine second row kind

Unlike the thirteen artefact extension tables, `dsd_component` has a real field
surface of its own — ~24 columns: `component_id`, `component_type`, `position`,
`concept_urn`, the `repr_*` facet group, `usage_status`, `attachment_level`,
`attachment_group`, `related_dimensions`, `related_measure`, `measure_usage`,
`concept_roles`. None of that is on the spine.

It is also **scoped**, like `code` and `hierarchy_node` and unlike the spine:
components belong to one `dsd_urn`. So it is the same shape as the two existing
scoped DSLs, and should reuse `_query_common` wholesale — a `ComponentRow`, its
fields, an accessor, a query class. Note #276 removed `scope_column` from
`RowKind` as unread; if this DSL wants it, add it back deliberately rather than
by reflex.

## The design question

**Where does the query hang, and is it one entry point or two?**

- `dsd.components` — per-DSD, mirrors `cl.codes` and `h.nodes`. Natural, but
  it is the *resolved-artefact* path again and does not answer catalogue-wide
  questions.
- `reg.components()` — catalogue-wide, filterable by `dsd_urn`, `dataflow`,
  `component_type`. This is what the 21 sites actually want.
- Both, with the first a scoped special case of the second.

Related: should a component query be reachable *from* an artefact query, so
`reg.artefacts(Dataflow).components()` gives the components of the matched
flows? That is the join the survey writes by hand most often, and it is the
composition #275's `SqlRelation` was built for — an `ArtefactQuery` is already
a one-column URN relation.

## Scope

- `ComponentRow` + fields + accessor, reusing `_query_common`.
- Catalogue-wide entry point; decide on the per-DSD one.
- Composition from `ArtefactQuery`, if the design above holds up.
- Representation facets are a sub-surface (`repr_kind` + eight `repr_*`
  columns); consider whether they are fields or a nested accessor.

## Test gates

- Differential properties against the in-memory `dsd.dimensions` /
  `dsd.attributes` / `dsd.measures` for a resolved DSD — a good oracle for the
  same reason `get_all` was in #276: a shipped code path, not test-only code.
- The catalogue-scale join covered end to end.
- A spy test that the frame is one statement, matching #275/#276.
- **Cookbook**: extend `discovery.md`, which currently says component-level
  questions are not here yet.
