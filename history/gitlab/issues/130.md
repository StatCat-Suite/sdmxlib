# Issue #130: model: extend ConstraintAttachment with DataProvider attachment kind

## Context

Surfaced by the SDMX-JSON 2.1 schema-variant audit (MR !98).

\`DataConstraintAttachmentType\` in the spec is a oneOf over four variants:

- \`dataProvider\` — attaches the constraint to a specific data provider (when only one provider is constrained)
- \`dataStructures\` — array of DSD URNs
- \`dataflows\` — array of Dataflow URNs
- \`provisionAgreements\` — array of PA URNs

Our model's \`ConstraintAttachment\` (src/sdmxlib/model/constraint.py) has fields for the latter three but no \`data_provider\` field, so the spec variant is unreachable from sdmxlib state.

## Why this matters

Real-world SDMX 3.x payloads that constrain a single provider's data submissions use the dataProvider attachment. We currently can't model or emit those.

## Proposed shape

Add ``data_provider: Ref[DataProvider] | None = None`` to \`ConstraintAttachment\`. Wire through the SDMX-ML readers/writers (2.1, 3.0, 3.1) and the SDMX-JSON writer/reader, mirroring the existing three fields:

\`\`\`python
@define
class ConstraintAttachment:
    dataflow: Ref[Dataflow] | None = None
    data_structure: Ref[DataStructure] | None = None
    provision_agreement: Ref[ProvisionAgreement] | None = None
    data_provider: Ref[DataProvider] | None = None  # NEW
\`\`\`

Validation: at most one of the four is set (same invariant as today, extended).

## Acceptance

- New \`data_provider\` field round-trips through XML 2.1, 3.0, 3.1, and JSON.
- The pre-release audit's \`DataConstraintAttachment: dataProvider\` gap closes — variant exercised by at least one fixture.
- Existing tests still green.
