## Comments

### 2026-08-27

The lossiness in §1 was inferred when this was filed. The #379 tier now
demonstrates it, and it is worse than "carries only an id" — it is *every*
node, and the guard has to say what the level must **be**, not just how many
get built.

`test_collect_and_materialize_agree_on_a_nodes_level`, on the 28-node
`H_CP_GEO_HCCSS`, fails on all 28:

```
collect():     Level(id='Country', name=InternationalString())
materialize(): Level(id='Country', name=InternationalString(en='Country', fr='Pays'))
```

So `q.hcode…collect()` returns nodes whose `level` has no name, description or
index, while the same node through `materialize()` has all three. That is a
**correctness** difference between two routes to the same row, not only a cost.

It also changes what a fix has to do. A count assertion alone
(`test_collect_builds_no_level_per_row`: 28 built, 5 declared) would be
satisfied by memoising the object built today — which would keep the bare
`Level` and make the disagreement permanent and cheap. The fix has to reach the
hierarchy's declared levels, as `LazyHierarchy.materialize()` does via
`levels_by_id`; `resolve.hcodes_by_urn` has no such map in hand, which is
presumably why the site looks the way it does.

Both assertions are in `tests/bench/test_bundle_reads.py` and fail on `main`
today.
