# Issue #340: a REST query answers from the whole store, not from its own fetch (design §5.13)

Design §5.13, **decided but not built**. Recording the decision, the evidence,
and the two viable implementations, because the decision was the hard part and
should not be re-litigated.

## Decided

* **A query answers only from rows its own fetch wrote.**
* **Version behaviour follows from that**: if the request asked `latest`, the
  query reports what `latest` returned, rather than every version the store
  happens to hold.

## Measured, on `main`

Two distinct symptoms. A provider serving only `CL_LIVE`, against a `store=`
that still holds a withdrawn `CL_RETIRED`:

```
provider serves: ['CL_LIVE']
query answers:   ['CL_LIVE', 'CL_RETIRED']
```

And with two versions in the store while the request asks `latest`:

```
request: version=latest   ->  CL_V(2.0)
query:   [CL_V(1.0), CL_V(2.0)]
```

Both are wrong answers with no signal. Note what is **not** broken: a
*filtered* query is fine, because the predicate re-applies locally over the
materialised rows, so an earlier question's rows are filtered back out. The
hole is unfiltered scans and projections.

## Why this is not a small change

The obvious implementation — `WHERE fetched_at >= <the fetch's timestamp>` —
does not fit the execution order. Terminals compile first and fetch second
(`compiled = self.to_sql()`, then `self._cursor()` runs the `prepare` hook), so
the watermark does not exist when the SQL is built. `to_sql()` is contractually
non-executing and its output is documented as handable to another library, so
neither triggering the fetch inside it nor emitting a sentinel parameter is
acceptable.

Two designs that do fit:

**1. A membership table.** `fetch_into` writes `(fetch_key, urn)` into
`sdmx.fetch_scope`; a scoped query adds
`urn IN (SELECT urn FROM sdmx.fetch_scope WHERE fetch_key = ?)`. The key is
`canonical_key(plan)`, which *is* known at compile time, so nothing reorders.
Costs a table, its writes, and a bound on its growth.

**2. Reorder terminals to fetch before compiling.** `_cursor()` returns the
watermark, and compilation takes it as a predicate. No new storage — the
`fetched_at` column added in !375 already carries what is needed — but it
touches all ~12 terminal call sites and changes an ordering several of them
rely on.

Either way the fetch cache must carry the scope alongside the key: a cached
question re-runs its query without re-fetching, so a scope derived from "rows
written just now" would filter to nothing and return **empty** — the same
silent-empty failure mode `detail=allstubs` had in !377, and the reason that
one grew a key.

## Acceptance

- a test where the provider withdraws an artefact the store still holds, and
  the query reports the provider's answer
- a test where the store holds two versions and a `latest` request reports one
- a cached question (second terminal over the same query) still answers, and
  answers the same — the empty-result trap, guarded
- `LocalRegistry` queries unaffected: they have no fetch, so nothing to scope
