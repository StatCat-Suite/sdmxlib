# Issue #291: Query[T].filter mutates in place, so two branches off one query silently AND together

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-14 |
| Labels | `api`, `type::bug` |

Found while writing #251's properties, which have to work around it.

`Query[T].filter` / `sort_by` / `limit` **mutate the receiver** and return
`self`:

```python
def filter(self, predicate: Callable[[T], bool]) -> Self:
    """Add a client-side filter predicate."""
    self._filters.append(predicate)
    return self
```

So branching off a base query does not branch:

```python
base = reg.query(sl.Dataflow, agency="ESTAT")
annual  = base.filter(lambda d: d.id.startswith("A"))
quarterly = base.filter(lambda d: d.id.startswith("Q"))

annual is base       # True
annual.fetch()       # [] — both predicates are on the same object
base.fetch()         # [] — including on `base`
```

The result is empty rather than wrong-looking, which is the good case. The bad
case is two filters that happen to be compatible: the caller gets a plausible
narrower answer and never learns that `base` was mutated underneath them.

## Why this is worth deciding

The same library's other query types are **immutable**:

```python
cl.codes.filter(sl.code.id == "A") is not cl.codes   # True — attrs.evolve
```

`CodeQuery`, `HierarchyNodeQuery`, `ArtefactQuery`, `MetadataValueQuery` and
`FrameQuery` are all frozen records that evolve. `Query[T]` — which is the one
in CLAUDE.md's "Common patterns", i.e. the one a user meets *first* — is the
only one that mutates. Two query APIs, opposite aliasing semantics, and neither
docstring mentions which it is.

#260 settled the analogous question for `limit` composition by deciding and
documenting rather than leaving it implicit. This is the same shape and
deserves the same treatment.

## Options

1. **Make it immutable** — return a copy with the predicate appended, matching
   the five DSL query classes and the principle of least surprise for a fluent
   API in this codebase. Cost: a caller relying on `q.filter(...)` mutating a
   variable they still hold gets a behaviour change.
2. **Keep mutation, document it loudly** — the method says "Add", and returning
   `self` is a legitimate builder idiom. Cost: the inconsistency stands and the
   aliasing trap stays live.

Option 1 is the one that matches everything else in the library.

## Test gate

#251 pins the current behaviour, so whichever option is taken shows up as a
visible diff. Its properties construct a fresh `Query` per example rather than
branching, with a comment pointing here — worth revisiting when this is fixed,
since a branching property is the natural way to state commutativity.
