## Comments

### 2026-08-20

**Audit note — half of this exists already, privately and incompletely.**

`model/validation.py::_collect_refs(artefact, prefix)` walks an artefact's attrs
fields and yields `(path, Ref)` pairs. That is the generic core this issue asks
for, and it works — `validate_references` and `_check_latest_refs` both rely on
it.

Two things stop it being the answer:

**It is in the wrong place and private.** It lives in `validation.py` because
that is who needed it first. A server synthesising `references=*` responses —
the motivating caller in the description — would be reaching into another
module's private function. Per CLAUDE.md's rule 3/4 this is either a public
property on the artefact or a plainly-named function in a private module; today
it is neither.

**The recursion is hand-listed and covers two types.** After the generic attrs
walk it descends only into `DataStructure` (dimensions, attributes, measures)
and `Hierarchy` (codes). Every other maintainable gets its own top-level `Ref`
fields and nothing below them — so a `MetadataStructure`'s nested
`MetadataAttribute` children, a `Codelist`'s extensions, a `StructureMap`'s
component maps and a `DataConstraint`'s attachment anchors are all invisible to
it. For validation that is survivable, since those paths have their own checks.
For "walk this artefact's outgoing references" it is wrong in a way the caller
cannot see.

So the work is smaller than the description implies and differently shaped:
generalise the descent (the item collections are discoverable from the attrs
fields, same as the `Ref` fields are), then decide the public surface. Worth
pairing with the `metadata_provision_agreements` and `Process`-shaped additions,
since each new artefact silently widens the gap between what `_collect_refs`
covers and what exists.
