# Issue #358: Should SDMX-JSON carry isFinal at all?

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |

Open question, not a bug report. Raised while fixing #357 and deliberately not
decided there.

Our SDMX-JSON writer emits an `isFinal` key for every maintainable, and #159
added reader support for it on purpose — `test_json_is_final_round_trips` and
three sibling tests assert it.

But the official SDMX-JSON structure schema
(`sdmx-twg/sdmx-json`, `structure-message/tools/schemas/`) contains **zero**
occurrences of `isFinal`, against twelve each of `validFrom` and `validTo`.
SDMX-JSON encodes the SDMX 3.0 information model, and 3.0 removed `isFinal`
from every maintainable — which is exactly why it is a declared `gaps.py` limit
for SDMX-ML 3.0/3.1.

So we are writing a non-standard key that only our own reader understands.

Two self-consistent positions:

1. **Keep it.** It is a harmless private extension, JSON tolerates unknown keys,
   and it round-trips more of the model than the standard allows. This is the
   status quo and what #159 chose.
2. **Drop it.** Match the standard and the 3.0/3.1 treatment, declare
   `is_final` a limit for SDMX-JSON, and stop emitting a key no other consumer
   reads.

I started implementing (2) while fixing #357, then reverted it: #159 decided
this deliberately, four tests encode that decision, and it is a behaviour change
that should be chosen rather than arrive as a side effect of a different fix.

What #357 did instead was make the existing choice **consistent** — the writer
emitted it for every maintainable while the reader read it for only some, which
was defensible under neither position.

If (2) wins, `gaps.py` needs `json` added to `TARGETS` first; #355 already notes
that SDMX-JSON limits have nowhere to be declared today.
