# Issue #322: annotations are lost on Codelist and Hierarchy — the two types read back through a Lazy proxy

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-17 |
| Closed | 2026-08-17 |
| Labels | `storage`, `type::bug` |

Found by the derived round-trip guard (#316) on its first run.

Twelve of fourteen maintainables keep their annotations through a store/load
round-trip. Two do not:

```
annotations kept: Categorisation, CategoryScheme, ConceptScheme, DataConstraint,
                  DataStructure, Dataflow, HierarchyAssociation,
                  MetadataProvisionAgreement, MetadataStructure, Metadataflow,
                  ProvisionAgreement, RepresentationMap
annotations LOST: Codelist, Hierarchy
```

Those two are exactly the types `get()` returns through a lazy proxy —
`LazyCodelist` and `LazyHierarchy` — which is unlikely to be a coincidence.

## Two failures, and the first hides the second

```python
back = reg.get(Hierarchy.urn(...))
back.annotations            # AttributeError: 'LazyHierarchy' has no attribute 'annotations'
back.materialize().annotations   # Annotations([]) — actually empty
```

1. The lazy proxies do not expose the attribute at all, so the first thing a
   caller meets is an `AttributeError` rather than a wrong value.
2. Materialising does not recover them either, so this is a genuine loss and
   not merely a hole in the proxy's surface.

Comparing each proxy against the artefact it stands for:

```
LazyHierarchy  missing vs Hierarchy: ['annotations', 'tree']
LazyCodelist   missing vs Codelist:  ['annotations', 'extensions']
```

`tree` and `extensions` have named replacements on the proxy (`nodes`, and
extensions are not modelled in storage), but `annotations` has none.

## Why nothing caught it

The same reason as !303, #307 and #309: no fixture set the field, and an
absence does not fail a test. The annotation *writer* is shared and works —
which is why the other twelve pass — so the gap is on the read side, in the
proxy and in what `materialize()` reconstructs.

## Gates

- Round-trip an annotated artefact of **every** persistable type, derived from
  `_WRITER_DISPATCH` rather than listed, so a new type is covered on arrival.
- A proxy exposes every non-private field of the artefact it stands for, or
  names its replacement explicitly. That comparison is two lines of `attrs`
  and would have caught both halves.

## Comments

### 2026-08-17

The derived guard (#316) shows this is not only `annotations`, and not only the proxy's *surface*.

```
LazyCodelist.uri            -> 'http://e/u'      (the proxy reads the spine)
materialize().uri           -> None              (the reconstruction drops it)
```

So the two paths disagree: reading a field off the proxy gives the right answer and materialising the same artefact gives a different one. That is worse than either being wrong consistently, because a caller who materialises for unrelated reasons silently changes what they get.

Whatever fixes `annotations` should be checked against `uri` on the same path — both are spine columns the proxy can see and the reconstruction cannot.

### 2026-08-17

Wider than annotations and uri: `materialize()` drops **every** spine field the proxy reads.

Measured on a `Codelist` with all four set:

```
             proxy                        materialize()
valid_from   2021-02-03 04:05:06+00:00    None
valid_to     2021-02-03 04:05:06+00:00    None
uri          http://e/u                   None
```

So this is one cause with several symptoms rather than a per-field oversight: the reconstruction `materialize()` performs is not reading the spine row the proxy already has. Fixing it should close `annotations`, `uri`, `valid_from` and `valid_to` together, and the #316 guard will say so — its `KNOWN_LOSSES` entries for all four are expected to be deleted in one go.

Surfaced while fixing #321: the timezone handling is now correct, and the guard still failed on `Codelist`/`Hierarchy` because it compares the materialised artefact. `r.get(...).valid_from` returns the right instant; `r.get(...).materialize().valid_from` returns `None`.
