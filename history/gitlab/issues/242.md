# Issue #242: Cross-version round-trips: shrink refusals to the ones SDMX forces

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Milestone | %12 Cross-version conversion: convert what converts, refuse only what cannot |

The tracking issue for milestone 12, and the measurement that scopes it.

## The goal

`2.1 -> 3.0 -> 2.1` should return the document it started with, except where SDMX itself makes that impossible. Where it is impossible, the current behaviour — an explicit `ValidationError` naming what cannot be represented — is correct and stays. This milestone is about shrinking the set of refusals down to the ones the standard forces.

Distinct from #237, which is the *same-version* rule (`D -> model -> D`). That one is nearly closed for SDMX-ML; this is the harder cross-version case, where the intermediate document is the bottleneck rather than the model.

## Measured starting point

Running `2.1 -> 3.0 -> 2.1` over the checked-in 2.1 corpus:

| fixture | result |
| --- | --- |
| `complete.xml` | **blocked** going to 3.0 — `structure_sets` |
| `minimal.xml` | **blocked** going to 3.0 — `structure_sets` |
| `with_hierarchy.xml` | **blocked** going to 3.0 — `hierarchical_codelists` |
| `with_metadata_structure.xml` | **blocked** returning to 2.1 — the MSD reporting layer |
| `ecb_data_structure.xml` | survives — 14 lost, 1 changed |
| `ecb_dataflow.xml` | survives — 14 lost, 1 changed |

## What is fundamental and what is ours

**Fundamental — stays a refusal.** `StructureSet` and `HierarchicalCodelist` assert "these artefacts belong together, under this id and name". SDMX 3.0 removed the containers and has no way to express the grouping. No converter can fix this: the intermediate is a *3.0 document*, so anything 3.0 cannot carry is gone before the return trip. Model-level conversion does not help, because the wire format is the bottleneck.

That is one blocker, affecting three of the four blocked fixtures.

**Ours — removable.** Everything else:

- The 14 lost `<EnumerationFormat>`s are not a format limitation at all. The field exists on the model and is wired into the 2.1 reader and writer only, so a trip through 3.0 drops it. → this milestone's first issue.
- `AttachmentConstraint` is refused on 3.0 with the advice "use a DataConstraint" — advice that cannot be followed, because `DataConstraint` has no `data_keys` field (#241). 2.1 carried *two* constraint artefacts and 3.0 unified them into one with a `role`; the conversion is available and unimplemented.
- The MSD reporting layer relocated rather than vanished: 3.0 moved targets to `Metadataflow` and `MetadataSet`. Whether that relocation can be automated is the open question.

## The return trip is the hard half

Forward conversion is mostly mechanical. Coming back is where the design work is, because 3.0 unified things 2.1 kept apart:

- a 3.0 `DataConstraint` carrying only a key set could have been a 2.1 `ContentConstraint` **or** an `AttachmentConstraint`, and nothing in the document says which;
- 3.0 targets sit on the `Metadataflow`, so returning them to an MSD requires knowing which flow's targets belong to which structure — and if the 2.1 message had an MSD with no Metadataflow, 3.0 has nowhere to put them at all.

Round-tripping therefore needs either a discriminator carried through the intermediate document, or an accepted asymmetry stated up front. That decision belongs in the individual issues, not here.

## Guard

A cross-version fidelity harness should exist alongside the same-version one, so this table is regenerated rather than remembered — and so a conversion that starts silently losing something fails rather than quietly widening the gap.

## Closing measurement

The starting table in the description was produced by a throwaway script. This one is read off `tests/unit/test_cross_version_fidelity.py`, which asserts every entry on each run — a hop that stops being blocked, or starts being lossy, fails the suite.

**50 hops: 25 convert, 23 blocked, 2 lossy.** At the start, of the six 2.1 fixtures measured, four were blocked and two survived with 14 losses each.

### What closed the gap

- **#243** — `enumeration_format` was wired into the 2.1 reader and writer only. Now carried in every format; that is the 14 losses.
- **#244** — `AttachmentConstraint` was refused on 3.x with advice that could not be followed. 3.0 *unified* the two 2.1 constraint artefacts rather than deleting one, so it is now converted to the `DataConstraint` it equals (which needed #241, a `DataKeySet` on `DataConstraint`).
- **#245** — the MSD reporting layer. Settled as fundamental after modelling it: a 2.1 MSD now round-trips *within* 2.1, and cannot survive a hop because the intermediate 3.x document has nowhere to put the layer. The wire format is the bottleneck, so no amount of modelling helps.
- **#238** — `@uri`, declared on `IdentifiableType` and therefore 40 model classes. Read by nothing, written by nothing.
- **#246** — the harness itself, which is what turned this from a remembered table into an asserted one.

Two things surfaced only once the harness ran end to end, both fixed under this issue rather than filed:

- `_UNWRITABLE["2.1","structure_maps"]` refused every structure map, reasoning that 2.1's ComponentMap `<Ref>` needs a class/package/containerID "that ComponentMap does not carry". True of the map, false of the message — all three are recoverable from the structure the map names. 2.1 now writes structure maps and refuses only what cannot be derived.
- Two `_BLOCKED` entries blamed the StructureSet grouping when the obstacle was a wrapper *sdmxlib itself invented* on the downgrade leg. It is now marked synthetic and dropped on read, so a 3.0 map document survives `3.0 -> 2.1 -> 3.0` intact.

One defect found on the way, and worth naming because the harness could not see it: the 2.1 representation-map writer emitted regex and index mappings as literal `<CodeMap>` pairs, so `^M-[0-9]+$` came back as a *code* by that name. Not a loss — a document asserting a mapping the source never made. Refused now.

### Guard

`test_cross_version_fidelity.py` regenerates this table on every run, and `test_document_fidelity.py` covers the same-version rule (#237) — its `_KNOWN_LOSSY` is now empty.
