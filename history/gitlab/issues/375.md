## What it is worth

`H_CP_GEO_FED` x `H_CP_GEO_POPCTR`, both rooted at Canada — 499,137 and 266,965 nodes in, 265,939 out:

| | wall | peak Python heap |
| --- | --- | --- |
| two id lists, intersected in Python | 235.6 ms | **+80.7 MB** |
| one statement, `count()` | 54.7 ms | **+0.0 MB** |

The heap column is the argument this issue makes and the one that survived #349, so it is the one measured.

## Two things the description could not have known

**`order_by(None)` on the operand.** A bare `select()` carries the root-key tiebreak into the subquery, and a relation used for *membership* has no use for an order. `is_in` receives compiled SQL through the `SqlRelation` protocol and cannot strip it, so the operand declines it at the source — 87.6 ms to 77.5 ms, ~12%, free. That spelling landed in !454 (#389) for an unrelated reason.

**The pair named in #348 is degenerate.** `H_CP_GEO_ADMINISTRATIVE` x `H_CP_GEO_POPCTR` share **exactly their root** — the intersection is 0, which is why the description says it "returns 0 rows". A test built on that pair would pass against an implementation that returned nothing, so both the unit fixture and the executable doc example overlap non-trivially on purpose, and the measurements use `H_CP_GEO_FED` (265,940 shared nodes with POPCTR).

## Also recorded

`Query.intersect` exists and is **not** this: it is a semi-join on the row key, and two hierarchies place the same code under different node URNs, so it answers nothing here. Said in the cookbook so the next reader does not reach for it.
