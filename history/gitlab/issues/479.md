# Issue #479: A data key set with isIncluded=false is read as included

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-16 |
| Closed | 2026-10-16 |
| Milestone | %21 Conformance evidence: what the green checks do not prove |

Found while surveying the SDMX-JSON readers for #474.

**What happens.** `DataKeySet/@isIncluded` (SDMX-ML 2.1 and 3.x) and `dataKeySets[].isIncluded` (SDMX-JSON) are required, and `false` means *these keys are excluded*. No reader reads it: `read_data_key_set` flattens every key set into `DataConstraint.data_keys` (its docstring: "nothing in either schema gives the grouping meaning beyond `isIncluded`, which sdmxlib does not model separately"), and every writer emits `isIncluded="true"`.

So a constraint excluding keys reads as one *allowing* them — the opposite of the document — and nothing is lost, refused or assumed. Measured on the maximal message with the first key set set to `isIncluded="false"`: 2.1 and 3.0 both read it back with `lost=[]`, `refused=()`, the key present as allowed.

**The same defect, fixed once already.** A cube region's `include="false"` used to read as included; #422 modelled `KeyValue.include` / `ComponentValueSet.include` and `CubeRegion.allows` honours it. A data key needs the same: an `included` flag per key (or per key set), read and written by every format, honoured wherever keys are evaluated, and carried by storage.

**Until modelled**, the honest minimum is a `LOSSES` row for `isIncluded="false"`, so `lossless=True` refuses the document rather than inverting it.
