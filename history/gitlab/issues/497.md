# Issue #497: An attribute with an empty related_measures writes an empty measure relationship that 3.x and SDMX-JSON reject

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-19 |
| Closed | 2026-10-19 |

## Problem

A DSD attribute whose `related_measures` is an **empty tuple** is written as an empty measure relationship. Every SDMX format except 2.1 rejects that, and nothing refuses it before the write: `validate()` passes on `main`, and `serialize` emits the document.

| `related_measures` | 2.1 | 3.0 | 3.1 | SDMX-JSON |
|---|---|---|---|---|
| `()` | valid | **invalid** | **invalid** | **invalid** |
| `None` | valid | valid | valid | valid |
| `("OBS_VALUE",)` | valid | valid | valid | valid |

- **SDMX-ML 3.0 / 3.1** write `<str:MeasureRelationship/>`. The XSD requires at least one `<Measure>` child ("Missing child element(s). Expected is ( Measure )").
- **SDMX-JSON** writes `"measureRelationship": []`, which fails the structure schema at the attribute.
- **SDMX-ML 2.1** has no measure relationship, so nothing is written.

The model stores `()` as given (`_to_ids_opt` keeps it), so the empty tuple and `None` are two distinct states that every writer but 2.1 treats differently.

## Reproduce (on `main`, efc1c2c)

```python
import sdmxlib as sl
from tests.support.factories import concept_ref

dsd = sl.DataStructure(
    id="D", maintainer="AG", name={"en": "d"},
    dimensions=[sl.Dimension(id="FREQ", concept=concept_ref("FREQ"))],
    attributes=[sl.Attribute(id="A", concept=concept_ref("A"),
                             attachment=sl.AttachmentLevel.OBSERVATION, related_measures=())],
    measures=[sl.Measure(id="OBS_VALUE", concept=concept_ref("OBS_VALUE"))],
)
sl.validate(dsd)                                            # passes
sl.serialize(sl.StructureMessage(data_structures=[dsd]), version="3.0")
# -> <str:MeasureRelationship/>, rejected by the SDMX-ML 3.0 XSD
```

## How it was found

Making `test_wire_conformance_populated`'s measure variants valid under #492 stage 2 part 3 (!646): removing `OBS_VALUE` left an attribute related to no measure. The test now relates it to `None` instead, and the gap remains.

## Options

1. **Treat an empty relationship as none.** Have the converter map `()` to `None`, so the model cannot hold the two states apart. Simplest, if SDMX gives "related to no measure" no meaning distinct from absent.
2. **Refuse it as the DSD is built.** Add a whole-artefact rule beside the one that already refuses a series attachment naming no dimension: an empty measure relationship has no form in 3.x or SDMX-JSON. The model keeps the distinction, and construction says it cannot be written.
3. **Have the writers omit an empty relationship.** This keeps the write valid, but a round trip would turn `()` into `None` silently.

I lean towards (1) or (2), depending on whether `()` should mean anything at all. The same question may apply to the other id-tuple relationships (`related_dimensions` for a series attachment is already refused when empty).

## What the IM and the other two libraries say

**The IM** (SDMX 3.1, Section 2, lines 1402–1408): a `MeasureRelationship` "relates a DataAttribute to **one or more** Measures", and "Lack of the MeasureRelationship defaults to a relationship to **all** Measures". So there are only two states: some named measures, or none stated, which means all of them. "Related to no measure" cannot be expressed. The schemas agree:
- SDMX-ML 3.0 `MeasureRelationshipType` requires at least one `<Measure>`.
- SDMX-JSON 2.0 and 2.1 give `measureRelationship` `"minItems": 1`.

**pysdmx 1.20** has no relationship field. It folds related measures into the attribute's `attachment_level` string as comma-separated ids, so it cannot store an empty list, and its writers either list measures or omit the element.

**sdmx1 2.28** has a `MeasureRelationship` class with no fields: it does not record which measures. Its 3.0 reader never reads the element, so measure relationships are dropped on read.

## Decision

**Option 2, as a field validator.** Whether `related_measures` is valid depends on its value alone, so it fits #492 stage 1's pattern: `model/_rules.py` refuses an empty tuple as it is set, and `None` keeps meaning "every measure".

Options 1 and 3 are ruled out by the IM's default. Mapping `()` to `None`, or omitting the element on write, would silently widen "no measure" to "every measure".

`related_dimensions` needs nothing new: a series attachment naming no dimension is already refused.
