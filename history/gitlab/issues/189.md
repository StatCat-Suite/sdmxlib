# Issue #189: Derive DSD→MSD metadata association from declared Metadataflow/MPA targets (not just populated MetadataSets)

Follow-up to #162.

## Context

`builders/metadata_annotation.build_dsd_metadata_map` (shipped in #162)
derives the DSD↔MSD reference-metadata association from **populated
`MetadataSet.targets`** — the concrete reports actually filed against a
dataflow.

In native SDMX 3.0 the *structural declaration* of what a metadata
product may describe lives on the **Metadataflow** (`targets`) and can be
further restricted by a **MetadataProvisionAgreement** — independent of
whether any MetadataSet has been reported yet. The canonical
"which MSD applies to this dataflow" is that declared target set. See the
SDMX 3.0 major-changes note: the Metadata Target moved off the MSD onto
the Metadataflow / Metadata Provision.

## Blocker discovered in #162

`Metadataflow.targets` and `MetadataProvisionAgreement.targets` are
**not persisted** by the storage layer today:

- `storage/writers.py::put_metadataflow` inserts only `(urn, msd_urn)` and
  the `structure` ref — `mdf.targets` is dropped.
- `put_metadata_provision_agreement` has no targets column; the
  `metadata_provision_agreement` table is `(urn, metadataflow_urn,
  metadata_provider_urn)` only.
- `_read_metadataflow` reads only `msd_urn`, so `Metadataflow.targets`
  reconstructs empty.

## Work

1. Persist `Metadataflow.targets` and `MetadataProvisionAgreement.targets`
   (schema + writers + readers). Likely a `metadataflow_target` table (or
   reuse `artefact_ref` with a `target` role), plus MPA target rows.
2. Extend `build_dsd_metadata_map` to union the declared-target path with
   the existing populated-set path (dedup by `(dsd_urn, msd_urn)`).
3. Tests: round-trip persistence of targets; derivation from a
   Metadataflow that declares a concrete dataflow target with **no**
   MetadataSet reported.

Wildcard target matching is tracked separately (see the wildcard issue).
