Housekeeping follow-up surfaced during MR !62 (HierarchicalCodelist coverage).

## Context

Our vendored XSDs are \`v2.1\` and \`v3.0.0\`. Upstream \`sdmx-twg/sdmx-ml\` published \`v3.1.0\`.

Our domain model is already partially 3.1-shaped (e.g. \`Hierarchy.levels\` and \`HierarchicalCode.level\` — see comment in \`src/sdmxlib/model/hierarchy.py:1-6\`). The 3.0 serializers don't round-trip those fields; nothing in our pipeline currently validates output against 3.1.

## Scope

1. Vendor \`tests/schemas/sdmx_ml31/\` from upstream \`v3.1.0\` tag — mirror the 3.0 layout, update \`tests/schemas/VERSION\` and \`tests/schemas/README.md\` with the refresh procedure.
2. Add a 3.1 session-scoped fixture and \`compile_structure_schema(\"3.1\")\` in \`tests/support/xsd.py\`.
3. Re-run our 3.0 writer output through the 3.1 XSD as a forward-compat smoke test. Expect green — flag any divergences.
4. Open follow-up issues for the gaps:
   - Level round-trip in 3.0 / future 3.1 hierarchy writer
   - SDMX 3.0 dropped \`HierarchicalCodelist\` for a standalone \`Hierarchy\` artefact + \`HierarchyAssociation\` (we currently only round-trip the 2.1 HCL wrapper)
   - RepresentationMap \`ValueMappingType\` 3.1 extensions (regex source/target, per-mapping validity dates)
   - New 3.1 containers we don't model: \`GeographicCodelist\`, \`GeoGridCodelist\`, \`HierarchyAssociation\`, \`NamePersonalisationScheme\`, \`OrganisationUnitScheme\`, \`MetadataConstraint\`, \`MetadataProviderScheme\`, \`MetadataProvisionAgreement\`, etc.

## Out of scope (for this issue)

- Implementing a 3.1 writer/reader.
- Adding any new model types — track those as separate items after the gap audit lands.

## Done when

- [ ] 3.1 XSDs vendored + attribution updated.
- [ ] 3.1 schema compiles via the helper.
- [ ] Forward-compat smoke test on our existing 3.0 writer outputs.
- [ ] Gap audit filed as one or more new milestone issues.
