3.1 model audit follow-up. Verified in #112.

## Semantic gap

3.1 \`DataflowType\` adds an optional single \`<DimensionConstraint>\` element holding 1+ \`<Dimension>id</Dimension>\` children. Real domain content: it declares **the Dataflow's committed dimension surface**, independent of future DSD growth.

Per the XSD docs:

> \"Specifies the fixed list of Dimensions (by ID) to which a Dataflow may be constrained. This is a required property if the DataStructure defines itself as an evolving structure, indicating that it can change dimensionality under a minor version change, and if the Dataflow references that DataStructure using a wildcarded minor version number. New minor DSD version can so still be used by this Dataflow even if that DSD version defines new additional dimensions. Dimensions not listed should not be used in Datasets for this Dataflow. The Time Dimension is not to be listed.\"

This is the evolving-DSD pattern: a DSD can grow new dimensions in minor versions; a Dataflow with a wildcarded version pin to that DSD must declare which dimensions it commits to using.

## Action

Add to \`src/sdmxlib/model/dataflow.py\`:

\`\`\`python
dimension_constraint: tuple[str, ...] = ()  # dimension ids
\`\`\`

3.0 and 2.1 writers ignore it (the element doesn't exist in those XSDs). 3.1 writer (eventual) emits the \`<DimensionConstraint>\` block when non-empty.
