## Summary

A code whose parent's id does not start with a letter (`_T`, the SDMX convention for "total") writes valid SDMX-ML 2.1 and 3.1 but **invalid 3.0**, with no refusal.

Found by the registry sweep (!516), at every registry that has code hierarchies: OECD **18,562**, FMR 1,479, IMF 433, BIS 50. The registries' own 3.0 documents carry the same `<str:Parent>_T</str:Parent>`.

## Schema: a 3.0.0 erratum

- 3.0.0 types `Code/Parent` as `common:SingleNCNameIDType`, pattern `[A-Za-z,A-Za-z0-9_\-]*` (`SDMXStructureCodelist.xsd:77`).
- But 3.0.0 `CodeType` does not narrow `@id`: it inherits `common:IDType`, `[A-Za-z0-9_@$\-]+` (`SDMXStructureBase.xsd:49`). So `<Code id="_T">` is valid 3.0.0 and a child of it cannot be written validly.
- 3.1.0 fixed it (`Parent type="common:IDType"`). 2.1's `LocalCodeReferenceType@id` is `IDType`.
- Concepts are consistent (their `@id` is `NCNameIDType` too); only codes are affected.

Writer: `_v3_writer.py:228-229` writes `parent_id` as text.

## Fix direction

No id rewrite: there is no lossless form. Either declare it in `gaps.py` (target `3.0`, carried when a code's `parent_id` fails the pattern, reason naming the erratum fixed in 3.1), or refuse it for 3.0 in `check_serialisable`. Either way the 3.0 writer stops emitting it silently; the user's way out is 3.1.

## Gate

`code_parent_leading_underscore` (3.0) is in `KNOWN_INVALID` against this issue.
