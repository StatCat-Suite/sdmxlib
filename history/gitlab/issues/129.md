## Remaining shape mismatches against \`sdmx-json-structure-schema.json\` v2.1.0

### 1. DSD: \`attributeList\` / \`dimensionList\` / \`timeDimension\` child shapes

\`AttributeListType\` per spec has \`attributes\` as a valid property — but our writer-produced object fails validation cascading from individual attributes. The actual root-cause errors look like:

\`\`\`
/data/dataStructures/0/dataStructureComponents/attributeList/attributes/0:
  {'id': 'OBS_STATUS', 'usage': 'optional', 'conceptIdentity': '...', ...}
\`\`\`

…and the dimensionList errors:

\`\`\`
/data/dataStructures/0/dataStructureComponents/dimensionList/timeDimension/localRepresentation:
  'format' is a required property
/data/dataStructures/0/dataStructureComponents/dimensionList/timeDimension/localRepresentation:
  Unevaluated properties are not allowed ('textFormat' was unexpected)
\`\`\`

So \`localRepresentation\` should emit \`format\`, not \`textFormat\`. Time dimension may also need a different shape — \`conceptIdentity\` / \`localRepresentation\` flagged as unexpected.

Need a per-component-type survey of the SDMX-JSON 2.1 component schemas (\`AttributeType\`, \`DimensionType\`, \`TimeDimensionType\`, \`MeasureType\`) and a fixup of \`_write_dimension\` / \`_write_time_dimension\` / \`_write_attribute\` / \`_write_measure\`.

### 2. \`DataConstraintType\`: \`constraintAttachment\`, \`type\`, \`cubeRegions\` shape

\`\`\`
/data/dataConstraints/0: Unevaluated properties are not allowed (
  'constraintAttachment', 'cubeRegions', 'referencePeriod', 'releaseCalendar', 'type' were unexpected
)
/data/dataConstraints/0/constraintAttachment:
  {'dataflow': 'urn:sdmx:org.sdmx.infomodel.datastructure.Dataflow=TEST:DF_TEST(1.0)'}
  is not valid under any of the given schemas
\`\`\`

Per the schema:

- \`DataConstraintType\` has \`constraintAttachment\`, \`dataKeySets\`, \`cubeRegions\` as own properties — so the field names are right; the contents must be wrong.
- \`constraintAttachment\` content (\`{dataflow: <urn>}\`) doesn't match the expected schema (needs investigation — likely an array of refs or a different key like \`dataflows\`).
- \`type\` (we emit "Allowed" / "Actual") is unexpected — schema may use \`role\` instead, matching SDMX 3.0+ ML convention.
- \`releaseCalendar\` not in the 2.1 JSON spec (matches the 3.0 ML drop).

### 3. \`structureSets\` at \`/data\` is rejected

\`\`\`
/data: Unevaluated properties are not allowed ('structureSets' was unexpected)
\`\`\`

The 2.1 JSON spec exposes each map kind as its own top-level array under \`data\` (e.g. \`representationMaps\`, \`structureMaps\`, etc.), mirroring the SDMX-ML 3.0 split. Our writer synthesises a \`structureSets\` wrapper at the JSON layer — needs distribution into the kind-specific arrays.
