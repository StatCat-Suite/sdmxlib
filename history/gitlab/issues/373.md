# Issue #373: Every aggregate over a fan-out is unconditional — `list(...)` cannot be restricted

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-25 |
| Closed | 2026-08-25 |

## The gap

An aggregate over a to-many edge collects the whole fan-out or nothing. There is no way to say *which* children it collects.

```python
c = q.dsd.components
reg.query(q.dsd).select(ids=c.list(c.id))
# ['FREQ', 'GEO', 'OBS_STATUS', 'OBS_VALUE']

reg.query(q.dsd).filter(c.any(q.component.role == "Dimension")).select(ids=c.list(c.id))
# ['FREQ', 'GEO', 'OBS_STATUS', 'OBS_VALUE']    <- unchanged
```

`filter` selects **which DSDs come back**, never which children get collected — correctly, that is what a row filter means. Rooting at the child gives the rows but loses the grouping. So *"list the dimensions of each DSD"* is not expressible, and neither is "how many dimensions", "the annotations of type X on each code", or "the codes under CA in each flow's applicable hierarchy" (#372 stage 3).

It affects every aggregate: `list`, `unique`, `count`, `n_unique`, in both spellings — dotted-through (`fan.col.list()`) and fan-out-level (`fan.list(cols)`).

## Precedent

Unanimous across the three implementations CLAUDE.md names as checks:

| | spelling |
| --- | --- |
| SQL / DuckDB | `list(x) FILTER (WHERE p)` |
| polars | `pl.col("x").filter(cond).sum()` |
| Django | `Count("x", filter=Q(...))` |
| SQLAlchemy | `func.count().filter(...)` |

## Shape: a keyword, not a chained `.where()`

A chained `fan.where(p)` returning a filtered fan-out reads well and is wrong for this language: it would immediately produce two spellings of things that already exist.

```python
c.where(p).any()    ==  c.any(p)
c.where(p).every()  ==  c.every(p)
```

The existing design already puts predicates *inside* the operation — `.any(*preds)`, `.every(*preds)` — so the consistent extension is a keyword on the aggregate, which is Django's shape too:

```python
c.list(c.id, where=q.component.role == "Dimension")
c.count(where=q.component.role == "Dimension")
q.dsd.components.concept.id.list(where=q.component.role == "Dimension")
```

One spelling per idea, no new object, and `.any()`'s existing grouping rule — *predicates inside one call land on one child* — carries over unchanged.

**`where=` rather than `filter=`**, despite Django, because `Query.filter()` here means something else: refining which rows come back, AND-chained by a law with property tests behind it. Reusing the word for "restrict this aggregate's children" invites conflating the two.

## Semantics to pin

- **No matching children** -> `[]` for `list`/`unique`, `0` for `count`/`n_unique`. Consistent with the existing "a leaf collects to `[]`, never None" rule, and the surprising half, so it wants a test rather than a docstring.
- **Several predicates** land on one child, exactly as `.any(p, q)` does.
- **A predicate crossing another fan-out** inside `where=` compiles to a correlated `EXISTS`, same as anywhere else.

## Cost

Contained: `Agg` gains a predicate field, `_compile._agg_subquery` emits the restriction into the subquery's `WHERE`, and nested predicates already compile through the same machinery. The differential oracles need the filtered forms, which is where the real work is — a filtered aggregate is exactly the kind of thing where a hand-checked expectation and the implementation can agree while both being wrong.

## Why now

#372 stage 3 wants "the codes under CA per flow" and would otherwise be built as a bespoke second view. This closes it as a language feature instead, and it is wanted well beyond hierarchies.
