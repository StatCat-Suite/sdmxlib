# Issue #52: Federation v0.16 follow-ups: async, multi-source Session, richer browse + drift

| | |
| --- | --- |
| State | closed |
| Opened | 2026-04-30 |
| Closed | 2026-10-21 |

Federation work shipped across phases A–F (issues #46 + #47) deliberately deferred a handful of items so each landing stayed tight. Capturing them here so they don't get lost.

Each item is independent — pick them up in any order.

## 1. Async batch fetcher for parallel transitive resolves

**Source:** Phase C step 5 (cache-mode federation). Plan called for `httpx.AsyncClient`-based batch fetching with a bounded concurrency cap (8–16). Replaced in v0.16 by the simpler `materialise_to`-as-cache design which handles the common case (re-fetches skip HTTP), but transitive resolves that touch N first-time URNs still hit the network sequentially.

**Why deferred:** Pure perf, not correctness. Materialise-through cache covers warm paths.

**Why follow up:** Issue #46 calls async batch "the difference between fine and unbearable" for cold-path transitive resolves. The natural caller is `FederatedRegistry` — when a single `resolve()` triggers Refs across 3–5 distinct registries, parallel fetch is the win.

**Sketch:**
- New `src/sdmxlib/api/_async_client.py` mirroring `SdmxClient` over `httpx.AsyncClient`.
- `FederatedRegistry.resolve_many(urns: Sequence[SdmxUrn]) -> dict` using `asyncio.run` internally; sync surface preserved.
- Concurrency cap configurable, default 8.

## 2. Session multi-source identity-map keying

**Source:** Phase C step 3 (Session source-tagging).

**Why deferred:** Each `RestRegistry` today owns its own `Session`, so the identity map is single-source by construction — no collision risk. Phase C added a `RuntimeWarning` at the storage layer when two sources publish the same URN to the same local store.

**Why follow up:** Once `FederatedRegistry` (Phase D) shares Session state across sources — e.g. for cross-source ref interning — keying `Session._map` only by URN means the second source silently shadows the first. Per #46's pitfall "Identity collisions across registries", the fix is keying on `(urn, source_registry)`.

**Sketch:**
- `Session.ingest(msg, *, resolved, source: str | None = None)`.
- `Session._map: dict[tuple[str, str | None], Any]`.
- `Session.get(urn, *, source: str | None = None)` — when source omitted, return any match.

## 3. Cross-source browse for remote-only dataflows

**Source:** Phase F (`FederatedCatalog.browse`). v1 only enumerates locally-bound dataflows.

**Why deferred:** Browsing remote-only dataflows requires a richer Registry protocol — today's `Registry.get(urn)` + `__contains__` Protocol can't list "everything in this registry." `RestRegistry` has `query(type, *, agency).browse()`; `LocalRegistry` and `InMemoryRegistry` have `get_all(type)`. These have different shapes.

**Why follow up:** Coverage-gap detection from #47 — "which upstream dataflows don't have a local binding?" — needs the cross-source list. The catalog's `browse()` is the natural place.

**Sketch:**
- Either: broaden the Registry Protocol with `list(type) -> Iterable[Stub]`, OR
- Add an opt-in `ListableRegistry` Protocol that `FederatedCatalog.browse(include_unbound=True)` consumes via duck typing.
- `DataflowEntry.binding` becomes `DataflowBinding | None`; remote-only entries get `None`.

## 4. Codelist content diffs in `validate_binding`

**Source:** Phase F (drift validation). v1 reports three kinds: `dataflow_missing`, `dsd_unresolvable`, `structural_version_drift`. The version pin alone catches the operational case (re-bind on republish).

**Why deferred:** Detailed codelist diffs (added codes, removed codes, renamed labels, dimension reorder, dimension addition/removal) are a much larger surface — the validation matrix #47 enumerates is non-trivial and each entry needs its own test cases.

**Why follow up:** When the version pin says "drift" but you want to know "is the data still queryable" — the detailed view is what tells you whether to re-ingest, re-label, or just re-bind.

**Sketch:**
- New `DriftIssue.kind` values: `codelist_codes_added`, `codelist_codes_removed`, `codelist_codes_renamed`, `dsd_dimensions_added`, `dsd_dimensions_removed`, `dsd_dimensions_reordered`.
- Each carries enough detail (code id, before/after labels, dimension id) to drive UI / programmatic decisions.
- Walk the binding's known dimensions/measures/attributes against the current DSD; for each enumerated component, walk its codelist.
- Recommend: keep a fast-path that short-circuits when `structural_version` matches.

## 5. (Lower priority) HTTP-level cache via hishel

**Source:** Phase C step 4 (originally planned). Replaced by `materialise_to` as the cache.

**Why deferred:** `materialise_to` handles "same URN already fetched" without HTTP. Hishel adds ETags / Last-Modified / true RFC-9111 caching on top, useful for `(latest)` URNs and other server-driven cache hints.

**Why follow up:** Tighter HTTP semantics for `(latest)` URNs; reduces unnecessary 200s when the upstream serves 304. Lower priority — only matters at scale, doesn't block any user.

---

Each item is shippable independently. None require coordinating across phases. Suggested order: 4 (drift detail, no new infra) → 1 (async batch, biggest perf win) → 3 (cross-source browse, needs Protocol decision) → 2 (Session keying, only matters once 3 lands) → 5 (hishel, opportunistic).
