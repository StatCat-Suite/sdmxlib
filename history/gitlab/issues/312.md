# Issue #312: §4: compile the path language to a second backend, with a capability model that refuses rather than fetches

| | |

The path language compiles to DuckDB and only DuckDB. §4 of
`docs/design/query-language.md` designs the rest and none of it is built —
which leaves #306's central claim untested.

> **where a query runs is a property of the backend rather than of the
> language**

That is the argument that overturned the earlier no-IR decision in
`query-composition.md`: that decision was about *what a query can say* and was
right on its premise; multi-backend asks *where it runs*. With one backend the
new premise is asserted, not demonstrated.

## The architecture, from §4

**DSL → IR → per-backend capability declaration → pushdown with a local
residual** — Calcite's adapter model, Trino's `applyFilter` / `applyLimit`,
Spark's `SupportsPushDownFilters`, ibis's backend compilers.

```
IR:  Scan(dataflow) │ Filter(agency) │ Filter(EXISTS concept) │ Nest(components)

FMR REST   pushes    /dataflow/ESTAT?references=children
           residual  the concept EXISTS, evaluated locally
DuckDB     pushes    all of it, one statement
```

The node set is small because the schema is fixed: `Scan`, `Filter`,
`Project`, `Join(edge)`, `Nest` / `Explode`, `Aggregate`, `Sort`, `Limit`.

## What already exists

- **Strict laziness**, which §4 calls the precondition — a planner cannot push
  what has already been evaluated. Done in #306: no `__iter__`, no `__len__`,
  no `__contains__`, and `explain()` describes what *will* happen.
- **The cross-backend bridge.** `Session.value_set` (#271) registers a set as
  an Arrow relation at ~48 µs regardless of size — measured during #306's
  resolver work, where binding 10k values cost 1269 ms against 33.6 ms
  registered. `FederatedCatalog.from_parts(structural=, bindings=, data=)` is
  already the topology.
- **The declared edge graph**, which is the IR's `Join(edge)` node in all but
  name.

What is missing is the planner and the capability model.

## Refuse rather than silently fetch — the safety property

This is the part the design flags as safety-critical, and it is the reason
this is a milestone rather than a feature:

> Partial pushdown has one catastrophic failure mode.
> `filter(name.contains("price"))` cannot push to REST, so the residual means
> fetching every dataflow and filtering locally — the 800-resolutions problem,
> arrived at silently.

The planner must **refuse and explain**. Erring permissive restores the exact
problem %15 exists to remove, and does it invisibly. That matches how the
library already handles unrepresentable states: a valid result or an error
naming the problem, never a plausible-looking wrong one (#233, #305, %11).

An `explain()` showing what pushes and what does not is the other half — the
same instinct as the `sql_corpus` and the mutation benchmarks, making the
machine's decision inspectable.

## Scope

- The IR, and `Query` compiling to it rather than straight to SQL.
- A capability declaration per backend, and the planner that reads it.
- The DuckDB backend re-expressed through it — a no-op in behaviour, and the
  proof the IR loses nothing. `sql_corpus` is the regression evidence.
- The SDMX REST backend: agency/id/version push, everything else residual or
  refused. §4 notes the structure plane pushes only those three, which is
  still well-aimed since #276 found most of its 76 spine sites are exactly
  that.
- `explain()` reporting the split.

## Gates

- The refusal is the load-bearing test: a query whose residual would be
  unbounded must raise, and the message must name what could not be pushed.
- Differential: the same query against DuckDB and against a cassette-replayed
  REST backend returns the same artefacts.
- No silent widening — a property that a pushed filter plus its residual
  selects exactly what the local-only evaluation does.

### 2026-08-14

Design written: `docs/design/query-pushdown.md`. It follows §4 except in one
place, and that place changes the size of this issue.

## `Query` is already the IR

§4's node set — `Scan`, `Filter`, `Project`, `Join(edge)`, `Nest`, `Aggregate`,
`Sort`, `Limit` — already exists, as fields or as declared edges:

| §4 node | where it lives today |
| --- | --- |
| `Scan` | `Query.root` (accessor + `__constraint__`) |
| `Filter` | `Query.predicates` |
| `Join(edge)` | `query/_edges.py`, cardinality derived |
| `Sort` | `order_keys` / `default_order` |
| `Limit` | `limit_n` / `offset_n` / `cursor` |
| `Project`, `Aggregate`, `Nest` | `Frame.items`, `Frame.group_keys` |

Measured on the class: **8 of `Query`'s 10 attrs fields are the plan**; the two
that are not are `_conn` and `_resolve`. And `_compile.py` is already the
DuckDB backend — a function from that plan to a statement.

So building a structure beside `Query` means two descriptions of one thing plus
a translation, which is the duplication this milestone has spent its length
removing. What is missing is smaller than an IR:

1. `Query` mixes the plan with DuckDB wiring.
2. No backend can declare what it pushes.
3. No planner splits one against the other.

The objection is in the doc rather than waved off: an IR earns its keep with
transformations to apply or several frontends to normalise. We have one
frontend, and DuckDB reorders better than we would. If a second frontend
appears, revisit — extracting `Plan` is the same first step either way.

## The refusal rule

Refusing on *any* residual is too strict; it would reject `agency == "ESTAT"`
plus a local name filter, which is fine over a few hundred rows. Always
fetching is the catastrophe. So the rule is boundedness:

> A residual is admissible only over a **bounded** scan — one the user could
> reasonably have issued as a request in its own right.

Decidable from the URL, because
`/structure/{resource}/{agency}/{id}/{version}` is the entire filter surface:
type alone scans every agency → refuse; type + agency is an ordinary request →
allow. **A residual requires that `agency` was pushed.** No threshold to tune,
which is where this kind of rule usually rots.

Two consequences worth naming:

- **`limit` cannot be pushed past a residual.** Fetch 10 then filter yields
  fewer than 10, silently — the same reasoning `_refuse_after_slice` already
  applies inside one backend.
- **`references=` is not a filter.** It changes what comes back *with* each
  artefact, not which artefacts come back, so it belongs to the resolver. That
  looks like the easiest mistake available here.

## Staging

1. Extract `Plan` — behaviour-preserving; `sql_corpus` diff must be empty.
2. `Capability` + DuckDB declaring everything; route compilation through the
   planner. Again a no-op, again the corpus is the evidence.
3. The planner and the refusal, against a fake narrow backend. No network, and
   this is where the safety-critical logic gets its properties.
4. The REST backend, cassette-replayed and differential against DuckDB.

Steps 1–3 are worth having without a second backend: they make the DuckDB path
declarative and the refusal testable. That is also what !304's corpus was
rebuilt for.

## Still open

- Does `Frame` push at all? REST returns artefacts, not columns, so a
  projection there is necessarily local — possibly *unavailable* rather than
  residual.
- Federation routes by agency, and agency is exactly the bounding constraint.
  Those look composable; nothing prototyped.
