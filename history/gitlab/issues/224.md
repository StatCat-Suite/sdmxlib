# Issue #224: DataStructure: six ways to build an artefact no SDMX format can validly serialise

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-06 |
| Milestone | %10 Testing: audit, properties, and mutation |
| Labels | `bug` |

Extending the #223 schema oracle to `DataStructure` — the **first** artefact type beyond Codelist and ConceptScheme to be put through generative schema validation — produced six ways to build an in-memory artefact that no SDMX format can validly serialise. All six are silent: every writer emits the document, and `validate()` accepts the artefact.

Each was confirmed by hand against the vendored XSDs, independently of the generator.

## 1. `ConceptIdentity` is required, and no writer supplies it

**Rejected by all four formats.** The XSD sequence for a component is `Annotations?, ConceptIdentity, LocalRepresentation?` — `ConceptIdentity` is mandatory.

`Dimension.concept` / `Attribute.concept` / `Measure.concept` all default to `None`, `validate()` does not require one, and the writers omit the element. So:

```python
DataStructure(id="DSD", maintainer="AG", version="1.0", name=...,
              dimensions=[Dimension(id="FREQ")], measures=[Measure(id="OBS_VALUE")])
```

serialises to XML and JSON that fail schema validation in **2.1, 3.0, 3.1 and SDMX-JSON**. This is the most consequential of the six: a DSD assembled in code without concepts looks fine and is unusable.

## 2. Four `DataType` members are in no schema enumeration

`Attachment`, `ReportingHour`, `URL`, `Year` appear in none of the 2.1 / 3.0 / 3.1 `DataType` enumerations (44 values each; sdmxlib has 43).

They look like near-misses for values that do exist — `URI`, `GregorianYear` — but that is a judgement for whoever owns the enum. `Facet(type=DataType.URL)` currently emits invalid XML in every version.

## 3. `XHTML` is valid in 3.0/3.1 and invalid in 2.1 at component level

2.1 restricts a component's `TextFormat` to `SimpleDataType` — 39 of the 44 values, excluding `XHTML`. A 3.0 DSD carrying it cannot be downgraded to 2.1. A genuine version-conversion hazard, distinct from #2.

## 4. Facet numeric bounds are emitted as `str()`, which `xs:decimal` rejects

`_xsd_num` formats with `str()`, and Python switches to exponent notation below ~1e-4:

```
Facet(end_value=3.359122329597789e-33)  ->  endValue="3.359122329597789e-33"
xs:decimal: invalid
```

Affects `maxValue`, `minValue`, `startValue`, `endValue` in every SDMX-ML version.

## 5. `decimals` / `maxLength` / `minLength` are `xs:positiveInteger`

`Facet(decimals=0)` is constructible and emitted; 0 is not a positive integer.

## 6. `isMultiLingual` is not allowed on a component's `TextFormat` in 2.1

The writer emits it unconditionally from the `write_text_format` table.

## 7. SDMX-ML 2.1 fixes the primary measure id to `OBS_VALUE`

The XSD pins `PrimaryMeasure/@id` to that value. SDMX 3.0 permits arbitrary measure ids, so any 3.0 DSD with a differently-named measure produces invalid 2.1 output. Same class as #3: a downgrade that cannot succeed and does not say so.

## Where the fix belongs

Mostly `validate()` — it is already the seam `serialize()` calls by default, and #221 is about to extend it for id types. Items 1, 2, 5 and 7 are validation rules. Item 4 is a writer formatting fix (`_xsd_num`). Items 3 and 6 are version-conditional and only detectable when the target format is known, so they belong in the writer or in a `serialize`-time check.

## Interim state

`tests/support/strategies.py` generates the conformant subset so the #223 properties can proceed, with each restriction commented and pointing here. Those comments are the regression risk: if this issue is fixed, the restrictions should be relaxed and the properties will then cover the previously-broken cases.
