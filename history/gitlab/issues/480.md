# Issue #480: The message header is not read: Sender, Receiver, Source and the rest are dropped silently

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-16 |
| Closed | 2026-10-20 |
| Milestone | %21 Conformance evidence: what the green checks do not prove |

Found while closing the frame for #447.

**What happens.** The SDMX-ML readers do not read `mes:Header` at all, and `StructureMessage` has no header. Everything a document says there is dropped on read without a report:

- `ID`, `Test`, `Prepared`;
- `Sender` / `Receiver`, with their `Name` and `Contact`;
- `Source`, `Extracted`, `EmbargoDate`, `ReportingBegin` / `ReportingEnd`;
- in 3.x, the `Structure` references and `DataProvider`.

The writers then emit a minimal header of their own. The SDMX-JSON `meta` object fares the same way.

**Why it surfaced now.** #447 checks the header's *structure* (a stray element there is refused by its place), which put the header's elements in the generated table. The element and attribute censuses then asked why ~20 allowed header pairs per version are never written. They are classified against this issue until it decides.

**Peers.** sdmx1 models `Header` (`id`, `prepared`, `sender`, `receiver`, `source`, `test`, …) on every message, and pysdmx has a `Header` too.

**Decision needed.** Either model the header (a `Header` on `StructureMessage`/`MetadataMessage`, read and written by every format, round-tripped), or declare it envelope metadata the library deliberately does not hold. In the second case it should still be reported, e.g. as a `ReadGap`, so `lossless=True` refuses a document whose header it drops.

## Comments

### 2026-10-20

**Decisions (2026-10-20):**

1. **Model the full header for the messages we read and write.** A structure message's header allows seven elements: `ID`, `Test`, `Prepared`, `Sender`, `Receiver*`, `Name*` and `Source*`. A party is an `id` with `Name*` and `Contact*`, and the sender can also carry a `Timezone`. A metadata message adds `Structure`, `MetadataProvider` (`DataProvider` in 2.1), `DataSetAction`, `DataSetID` and `Extracted`.
   - Model all of them on `StructureMessage` and `MetadataMessage` (`None` when the document has none). Round-trip them in SDMX-ML 2.1, 3.0, 3.1 and SDMX-JSON's `meta`. Reuse the existing `Contact`.
   - The data-message-only fields (`ReportingBegin/End`, `EmbargoDate`) are out of scope: sdmxlib never reads or writes data messages.
   - This beats both peers. pysdmx keeps one name per party (English preferred) and no contacts. sdmx1 keeps one receiver, and neither keeps the message `Name`.
2. **With no header, writes keep today's fixed placeholders** (`ID=SDMX_MSG`, `Prepared=2000-01-01T00:00:00`, `Sender id="sdmxlib"`). The same message serialises to the same bytes, which golden tests and #503's minimal canonical output rely on. A caller who wants a real header sets one.

The header censuses' rows classified against this issue move to read and written when it lands.
