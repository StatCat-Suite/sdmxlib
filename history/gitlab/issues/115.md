Carved out from **#97**. The original audit lumped \`AttachmentConstraint\` together with the constraint-role coverage gaps, but \`AttachmentConstraint\` is a different artefact kind that we don't model at all — it deserves its own scope.

## What it is

Per \`SDMXStructureConstraint.xsd\` (v2.1 only), \`AttachmentConstraint\` is a top-level maintainable inside \`<str:Constraints>\` alongside \`ContentConstraint\`. Unlike ContentConstraint (which we now model as \`DataConstraint\`), AttachmentConstraint expresses *attachment* relationships between artefacts — restricting where particular components can appear.

SDMX 3.0 dropped \`AttachmentConstraint\` entirely from the structure namespace, so this is a 2.1-only concern. 3.0 / 3.1 expresses the same semantics through other mechanisms (e.g. \`MetadataConstraint\`).

## Why it didn't surface in the round-trip pass

The 2.1 reader currently parses only \`<ContentConstraint>\` children of \`<Constraints>\` and ignores \`<AttachmentConstraint>\` entries. The 2.1 writer doesn't emit any. So real 2.1 messages carrying AttachmentConstraints silently lose those artefacts.

## Action

- Add \`AttachmentConstraint\` class to \`model/constraint.py\` (alongside \`DataConstraint\`).
- Add \`attachment_constraints: ArtefactList[AttachmentConstraint]\` slot on \`StructureMessage\` (or merge with the constraints slot if the shapes are similar enough).
- Wire the 2.1 reader to parse \`<str:AttachmentConstraint>\` siblings of \`<str:ContentConstraint>\`.
- Wire the 2.1 writer to emit them.
- 3.0 / 3.1 serializers silently drop (no XSD equivalent).
- Fixture exercising the new path.

## Out of scope

- Modelling \`MetadataConstraint\` (3.0+ analogue) — that's the next layer.

## Done when

- [ ] \`AttachmentConstraint\` round-trips through a 2.1 fixture validated against the XSD.
- [ ] 3.0 writer drops the field cleanly (or refuses, by design).
