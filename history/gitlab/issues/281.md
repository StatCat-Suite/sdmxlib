Split out of #276, which anticipated this wanting its own issue.

`metadata_set` / `metadata_target` / `metadata_value` are **13 of the 113
hand-written sites**. The questions: "what reference metadata is attached to
this dataflow", "which artefacts have a COVERAGE statement", "give me every
reported QUALITY.* value as a frame".

## A finding that changes the framing

#276 assumed this was "a tree of reported values, a different shape from the
artefact spine" and deferred it on that basis. **That is only true at the model
layer.** In storage it is already flat:

```sql
CREATE TABLE metadata_value (
    set_urn         TEXT NOT NULL,
    attribute_path  TEXT NOT NULL,   -- dotted, e.g. "QUALITY.COVERAGE"
    sibling_index   INT NOT NULL,    -- disambiguates repeated attributes
    value_kind      TEXT,            -- 'scalar' | 'i18n'
    scalar          TEXT,
    i18n            MAP(VARCHAR, VARCHAR),
    PRIMARY KEY (set_urn, attribute_path, sibling_index)
);
```

The `ReportedAttribute` recursion is *reconstructed* at the model layer from
`attribute_path`. So a query DSL over this is an ordinary scoped relation —
scoped by `set_urn`, exactly like `code` is by `codelist_urn` — and the
prefix-matching that a dotted path invites (`QUALITY.*`) is a `LIKE`, which the
`_label_match` machinery already emits.

That makes this **easier than #276 assumed**, and it should be re-scoped
accordingly rather than treated as a research problem.

## Shape

Probably two related things, and deciding whether they are one query or two is
the design work:

1. **A value query** over `metadata_value`, scoped to a set: filter by
   `attribute_path` (equality and prefix), project `scalar` / `i18n[lang]`,
   aggregate. Reuses `_query_common` wholesale.
2. **A reach from the artefact side** — "which artefacts have metadata saying
   X" — which goes `artefact ← metadata_target ← metadata_set → metadata_value`.
   That is a relationship predicate on `ArtefactQuery`, in the same family as
   #276's `uses_concept`, e.g. `sl.artefact.has_metadata("QUALITY.COVERAGE")`.

(2) is the discovery question and is probably the higher-value half, matching
how #276 found the `uses_*` predicates outranked a full component DSL.

## Prior art in the codebase

`Registry.metadata_for_target` and `Registry.metadata_report` already answer
the single-artefact case by resolving. They are the natural **oracle** for
differential properties, the same role `get_all` played in #276 — and the
question of whether the DSL should replace or complement them is part of the
design.

## Watch out for

- `metadata_declared_target` is a *different* table from `metadata_target`:
  declared (structural, possibly wildcarded — `Dataflow=ESTAT:CPI(*)`) versus
  populated. The schema comment is explicit that wildcards keep the declared
  one out of the resolved ref graph. A query must not conflate them.
- `value_kind` distinguishes `scalar` from `i18n`, and XHTML is `i18n` with
  markup — indistinguishable except via the MSD's data type. A `value[lang]`
  accessor needs to decide what it does for a scalar-kind row.
- `sibling_index` means repeated attributes are sibling rows, never a list —
  consistent with the model (CLAUDE.md's MetadataSet glossary), and a query
  that assumed uniqueness on `attribute_path` would silently drop repeats.

## Test gates

- Differential properties against `metadata_for_target` / `metadata_report`.
- Repeated attributes (`sibling_index > 0`) covered explicitly — the case a
  path-keyed query is most likely to get wrong.
- Prefix matching on `attribute_path` against a hand-built expectation,
  including the LIKE-metacharacter case that bit `code_query` in #222.
- **Cookbook**: extend `reference_metadata.md`, or a discovery section.
