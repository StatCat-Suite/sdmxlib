# Issue #395: Six artefact types have no storage kind — three deferred deliberately, three never raised

| | |
| --- | --- |
| State | closed |
| Opened | 2026-09-06 |
| Closed | 2026-09-08 |
| Labels | `design`, `storage` |

Six `StructureMessage` slots hold artefact types with no `ArtefactKind`, so
`Registry.add` refuses them:

```python
>>> reg.add_all([structure_map])
TypeError: Unsupported artefact type: StructureMap
```

| type | what it is | why it is not stored |
| --- | --- | --- |
| `StructureMap` | **3.0** — supersedes 2.1's `DataStructureMap` / `DataflowMap` | "no caller-driven storage need yet" |
| `ConceptSchemeMap` | **3.0** | same |
| `CategorySchemeMap` | **3.0** | same |
| `AttachmentConstraint` | 2.1; 3.0 unified the concept into `DataConstraint` | never raised |
| `StructureSet` | 2.1 container; 3.0 promoted its members to top level | never raised |
| `HierarchicalCodelist` | 2.1 container; ditto | never raised |

The first three are recorded, and the reasoning is sound —
`storage/schema.py`, Layer 9:

> Currently only RepresentationMap (the 3.0 successor to the 2.1 CodelistMap)
> is persisted — the other map kinds (ConceptSchemeMap, CategorySchemeMap,
> StructureMap) have no caller-driven storage need yet.

This issue is not a claim that the deferral was wrong. It is the question of
whether the need has arrived, and a record of what the deferral costs now that
it has a user-visible edge.

## What it costs

`parse(xml, registry=...)` refuses an entire message carrying any of the six —
see #394, which is about that behaviour regardless of how this issue lands.
So the deferral is no longer free: it is the difference between "we do not
index these" and "we cannot read a document that contains one".

## None of them resists storage

Worth stating, because "not persisted" reads like "cannot be persisted":

- **The three maps are 3.0 artefacts**, siblings of `RepresentationMap`, which
  *is* stored. `representation_map` + `value_map` are two small tables; the
  others are the same shape with different endpoints. `StructureMap` is the
  only one with real substance — a list of `ComponentMap`s — and that is one
  child table.
- **The two containers** are `MaintainableArtefact`s holding a name and a list
  of refs. `sdmx.artefact` and `artefact_ref` already hold exactly that. Their
  own docstrings say sdmxlib models them "as a peer that *references*" its
  members precisely so the grouping is one row rather than denormalised.
- **`AttachmentConstraint`** is the only one needing thought: 3.0 folded it
  into `DataConstraint`, so it is either its own kind or a `DataConstraint`
  with a role. That is a modelling decision, not a table.

## Order, if it is done

1. **The two containers** — cheapest, and they close #394's validation half in
   fact rather than by exception. Refs only, no new child table.
2. **`ConceptSchemeMap` and `CategorySchemeMap`** — `representation_map`'s
   shape with different endpoints.
3. **`StructureMap`** — plus a `component_map` child table.
4. **`AttachmentConstraint`** — decide the 3.0 unification first; possibly out
   of scope and better left refused with a message that says so.

Each kind needs the same five things `RepresentationMap` has: a table in
`storage/schema.py`, an `ArtefactKind` entry, a writer, a reader, and — if it
should be queryable — an `Edge` in `query/_edges.py` and an accessor.

## Acceptance

- For each of the six, a recorded decision: **stored** (with the five pieces),
  or **still deferred** with the reason and a refusal that says so.
- A round-trip test per kind that lands: write, read, compare — the shape the
  existing kinds are held to.
- Whatever stays deferred is refused *by name and with a reason*, not by a
  bare `Unsupported artefact type` — that part is #394 and can land first.

## Comments

### 2026-09-06

## Step 1 done in !467 — and it was not optional

`HierarchicalCodelist` and `StructureSet` now have storage kinds.

**!466 broke SDMX-ML 2.1 ingest and this was the fix.** 2.1 has no way to write
a `<str:Hierarchy>` except inside a `<str:HierarchicalCodelist>`, so every 2.1
document carrying a hierarchy carries the container too. Once #394 completed
`all_artefacts()`, storage saw the container for the first time and refused it,
so `parse(xml, registry=…)` refused the whole document — correct by #394's
rule, and a worse outcome than the silent drop it replaced.

So the deferral recorded in `storage/schema.py` did have a cost after all, and
the forcing function arrived from an unexpected direction: not a caller asking
to query these, but a caller unable to read an ordinary file.

`tests/unit/test_parse_with_registry.py` never parsed a hierarchy fixture into
a registry, which is why `just ci` stayed green through the break. It does now.

## No schema change was needed

As the description guessed: each container is a maintainable plus lists of
refs, and `artefact` + `artefact_ref` already hold that. `artefact_ref.role`
carries the field name — which is what keeps `StructureSet`'s two lists from
merging on read — and `ordinal` preserves order, since the model stores a
tuple.

Round-tripped: the container's own name survives, which is #239's case (lost at
parse, then lost again at storage), and `StructureSet.maps` and
`.related_structures` come back separately.

## A typing note for whoever does steps 2–4

`_read_container[T](…, cls: type[T])` looked like the obvious way to share the
reader and **both checkers refused it, from opposite directions**: pyrefly
called the `cls(…)` result an implicit `Any`, and adding the generic to satisfy
it then hid the constructor from basedpyright, which could not see
`description` or `annotations` as parameters. The shape that works is to share
the *ref reading* and construct each class where its fields are known — two
four-line calls both checkers verify, no suppressions, `Any` ratchet unmoved.

## Remaining, unchanged

2. `ConceptSchemeMap` and `CategorySchemeMap` — `representation_map`'s shape
   with different endpoints.
3. `StructureMap` — plus a `component_map` child table.
4. `AttachmentConstraint` — decide the 3.0 unification first.

All four keep their `_NOT_PERSISTED` entries, so they refuse by name with a
reason. #394's refusal tests moved onto `StructureMap`, since asserting a
refusal on a type that had just become storable would have quietly stopped
testing anything.

Unlike the containers, none of these four is currently blocking a document from
being read: they appear in messages a producer *chooses* to write, not in every
2.1 file with a hierarchy. So the original "no caller-driven storage need yet"
still stands for them, and the next step should be driven by a caller rather
than by this issue's existence.

Steps 2 and 3 landed in !474. All three map kinds persist now, so the six

| type | decision |
| --- | --- |
| `HierarchicalCodelist` | **stored** (step 1, !4xx) |
| `StructureSet` | **stored** (step 1) |

| `CategorySchemeMap` | **stored** — `category_scheme_map` + `item_map` |
| `StructureMap` | **stored** — `structure_map` + `component_map` |
| `AttachmentConstraint` | **deferred**, refusing by name with its reason |

## The estimate was wrong in a useful direction

This issue expected `StructureMap` to be the expensive one — "plus a
`component_map` child table". It is not: `ItemMap` and `ComponentMap` are
both `(source_id, target_id)`, so the three writers differ only in table
names. The real cost was in the *edges*, not the tables.

## Two decisions, both from precedent rather than taste

* **One parent table per kind.** `metadata_provider`'s comment already argues
  this for its own case — separate artefacts, and an edge resolving to "a map"
  resolves to nothing in particular.
* **One `item_map` for both scheme maps**, because their `maps` really is the
  same class, the way `organisation_contact` serves two organisation kinds.
  `StructureMap.maps` is `ComponentMap` and gets its own table.

The shared table needed one correction the precedent does not cover:
`organisation_contact`'s two inbound edges work because its owners are
*different tables*. Both scheme maps live in `artefact`, so two edges there
are both `artefact.item_maps` and the reverse hop is ambiguous. One edge
serves both; each accessor's `__constraint__` picks the kind.

## Two stale `_NOT_PERSISTED` entries, removed

`StructureSet` and `HierarchicalCodelist` became storable in step 1 and stayed
listed as refused — dead, because `put_artefact` finds a writer first and
never reads the table, but one dispatch change from printing a reason that is
not true. `test_the_refusal_table_matches_the_dispatch` now compares the table
against both dispatch tables in **both** directions.

Related: `test_storage_query_bounds`'s refusal tests had moved to
`StructureMap` when the containers became storable, carrying a comment warning
about that exact risk. Third move; they are on `AttachmentConstraint` now, and
the drift is guarded rather than commented.

## What is left

Only step 4, and it is a *modelling* question rather than a storage one: 3.0
folded `AttachmentConstraint` into `DataConstraint`, so it is either its own
kind or a `DataConstraint` with a role. Nothing here answers that, and this
issue's own acceptance is already met for it — deferred, with the reason, and
refused by name.

Closing on that criterion seems right, with the unification raised separately
if a caller wants it. Leaving it open in case you would rather step 4 land
here.
