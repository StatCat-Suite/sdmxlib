# Issue #39: ContentConstraint should be renamed DataConstraint (SDMX 3.0 IM alignment)

| | |
| --- | --- |
| State | closed |
| Opened | 2026-04-21 |
| Closed | 2026-04-22 |

## Summary

`sdmxlib/model/constraint.py` uses `ContentConstraint` — the SDMX 2.1 name — but the library's stated IM target is SDMX 3.0.  In SDMX 3.0, `ContentConstraint` was retired and replaced by two separate artefacts:

- **`DataConstraint`** — constrains valid key combinations for a dataflow (what `ContentConstraint` currently models)
- **`MetadataConstraint`** — constrains metadata set content

The `ActualConstraint` / `AllowedConstraint` specialisation that existed in 2.1 was also removed; the role is now expressed via the `constraint_type` field (currently present as `constraint_type: str = "Allowed"`).

## Current state

```python
# sdmxlib/model/constraint.py
class ContentConstraint(MaintainableArtefact):
    sdmx_package: ClassVar[str] = "registry"
    sdmx_class: ClassVar[str] = "ContentConstraint"
    constraint_type: str = "Allowed"
    attachment: ConstraintAttachment = ...
    regions: tuple[CubeRegion, ...] = ()
    ...
```

The class structure and semantics are correct for the data-constraint use case. Only the naming is misaligned.

## Proposed change

- Rename `ContentConstraint` → `DataConstraint`
- Add a stub `MetadataConstraint` (or at minimum a placeholder) to complete the 3.0 pair
- Update `sdmx_class` to `"DataConstraint"` so serialisation round-trips correctly against 3.0 wire format
- Keep a `ContentConstraint = DataConstraint` alias (or handle in the 2.1 reader) so the 2.1 parser continues to work without breakage

## Reference

- SDMX 3.0 Major Changes: https://sdmx.org/wp-content/uploads/SDMX_3-0-0_Major_Changes_DRAFT-1-0.pdf (section on Constraint restructuring)
- SDMX 3.0 Section 6 IM: https://sdmx.org/wp-content/uploads/SDMX_3-0-0_SECTION_6_FINAL-1_0.pdf
