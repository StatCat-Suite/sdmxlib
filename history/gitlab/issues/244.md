# Issue #244: Convert AttachmentConstraint to DataConstraint on 3.x write instead of refusing

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Milestone | %12 Cross-version conversion: convert what converts, refuse only what cannot |

`validation._UNWRITABLE` refuses `attachment_constraints` on 3.0, 3.1 and SDMX-JSON with the message *"SDMX 3.0 removed AttachmentConstraint; use a DataConstraint"*. That message is right about the format and wrong about what sdmxlib can do — the advice cannot be followed, because `DataConstraint` has no `data_keys` field (#241).

SDMX 3.0 **unified** two artefacts rather than deleting one. 2.1 carried both:

```
2.1  ContentConstraintBaseType    : ConstraintAttachment, DataKeySet, MetadataKeySet, CubeRegion, MetadataTargetRegion
2.1  AttachmentConstraintType     : ConstraintAttachment, DataKeySet, MetadataKeySet
3.0  DataConstraintBaseType       : ConstraintAttachment, ReleaseCalendar
3.0  DataConstraintType           : DataKeySet, CubeRegion
```

Everything an `AttachmentConstraint` says is expressible as a 3.0 `DataConstraint`. The refusal is ours, not the standard's.

## Depends on #241

`DataConstraint.data_keys` has to exist first. That issue stands on its own — without the field, a **3.0 document carrying a `DataKeySet` already loses it silently**, which is a same-version defect independent of any conversion.

## Work

1. (#241) Add `data_keys` to `DataConstraint`; read and write it in all four formats.
2. On a 3.x or JSON write, convert an `AttachmentConstraint` into a `DataConstraint` rather than refusing: carry the attachment and the key set across, with `constraint_type` set to whatever the 2.1 artefact implied.
3. Remove `attachment_constraints` from `_UNWRITABLE` for those three targets. `test_unwritable_lists_exactly_what_each_writer_drops` will fail until the entry goes, which is the intended prompt.

## The return trip needs a decision

Forward is mechanical. Backward is not: a 3.0 `DataConstraint` carrying only a key set could have been a 2.1 `ContentConstraint` **or** an `AttachmentConstraint`, and the 3.0 document does not say which. Three options, in preference order:

1. **Always return a `ContentConstraint`.** Simple, and correct for the common case. `2.1 -> 3.0 -> 2.1` then changes the artefact *kind* for what began as an AttachmentConstraint, which the fidelity harness will report as a difference — so it needs recording as a declared asymmetry rather than passing silently.
2. **Carry a discriminator through the 3.0 document**, as an annotation. Makes the round-trip exact, but writes something into the intermediate that no other SDMX tool will understand, and it is not really SDMX. A hack that shows up in output other people read.
3. **Keep the model distinction and accept the asymmetry**, documenting that an AttachmentConstraint survives 2.1 -> 3.0 but returns as a ContentConstraint.

Option 1 with an explicit `KNOWN_GAPS`-style entry is probably right: the conversion is lossless in *content*, and only the artefact kind is ambiguous. But that is a judgement about what "the same document" means, and it should be made deliberately rather than discovered when the harness reports it.

## Note on 3.0 `MetadataKeySet`

2.1's constraints also carry `MetadataKeySet`, which 3.0 moved to the separate `MetadataConstraint` artefact — an artefact sdmxlib does not model. A 2.1 constraint carrying one is therefore still not fully convertible. Worth checking whether any real 2.1 output uses it before deciding if that matters.
