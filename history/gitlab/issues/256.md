# Issue #256: ComponentFilter emits 'col IN ()' for an empty OR-set, and empty means two different things

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-09 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `bug`, `dsl`, `validation` |

`ComponentFilter` with an empty OR-set emits `col IN ()`, which DuckDB rejects — and the empty set has two contradictory meanings in the same module.

## Reproduction

```python
>>> import sdmxlib as sl
>>> sl.ComponentFilter(dimension_ids=["GEO"], dimensions=[[]]).to_where_clauses({"GEO": "geo"})
(['geo IN ()'], [])
```

```
duckdb.ParserException: Parser Error: syntax error at or near ")"
LINE 1: SELECT * FROM obs WHERE geo IN ()
```

Same on the attribute path: `attributes={"OBS_STATUS": []}` yields `obs_status IN ()`.

`ComponentFilter` is public — exported from `sdmxlib/__init__.py` and named in `__all__` — so this is reachable from the documented surface, not only from internals.

## The semantics question underneath

`parse_components` already decided what an empty list means, in the other direction:

```python
# Empty list values are treated as "no constraint" and dropped.
if isinstance(value, list) and not value:
    continue
```

So going through the parse layer, an empty OR-set means **match everything**. Constructing the same filter directly, it means `IN ()` — a crash, but the natural reading of an empty OR-set is **match nothing**. Two contradictory answers to the same question, one of them a syntax error, in one module.

Pick one and enforce it in both places:

- **A. Empty means "no constraint" (match everything).** Consistent with `parse_components` today. Then `__attrs_post_init__` should normalise `[]` to `None` on construction so `to_where_clauses` never sees it, and `is_wildcard` reports correctly.
- **B. Empty means "no value permitted" (match nothing).** Arguably the more honest reading — the user asked for the empty set of codes — and it makes `parse_components`'s drop a silent widening of the user's query, which is the sort of thing that returns a full table scan when the caller expected zero rows. Then `_emit_in_clause` emits `FALSE` (or `1 = 0`) and `parse_components` stops dropping.
- **C. Reject at construction.** Cheapest, and defensible for a value type — but it pushes the decision onto every caller and does not resolve what `parse_components` should do.

B is the one worth arguing for and A is the one that matches current behaviour, so this needs a decision, not just a patch.

## Why line coverage did not catch it

`src/sdmxlib/rest.py` is at **100% line coverage**, 69 statements. `_emit_in_clause` runs on every test that filters anything; nothing exercises it with an empty list. This is the milestone's premise in miniature — a fully covered module with an unexercised behaviour.

## Scope

- Decide A / B / C and record the reasoning in the `ComponentFilter` docstring, which currently describes neither.
- Make `parse_components` and direct construction agree.
- Property: for every generated `ComponentFilter`, `to_where_clauses` output must execute against DuckDB without raising. That is the general form of this bug and it belongs in the data-plane differential work (#258), so land the guard there rather than as a single example.
- Check the `SqlRelation` branch while you are in `_emit_in_clause`: `IN (<subquery>)` where the subquery returns no rows is fine, but a relation whose `to_sql()` returns an empty string is not, and nothing rejects that today.

## Test gates

- An example test per decision branch, asserting the emitted fragment *and* that it executes.
- `parse_components` and `ComponentFilter(...)` produce the same filter for the same empty input.
- No path from public API produces SQL that fails to parse.
