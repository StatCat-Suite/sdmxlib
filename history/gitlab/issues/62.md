# Issue #62: ComponentFilter: accept SQL-relation values for hierarchy-traversal filters

| | |
| --- | --- |
| State | closed |
| Opened | 2026-05-02 |
| Closed | 2026-05-02 |

Follow-up from #58's refinement comment.

## Problem

`ComponentFilter` (v0.18.0, `src/sdmxlib/rest.py`) accepts only eager lists of code values:

```python
@frozen
class ComponentFilter:
    dimensions: list[list[str] | None]
    attributes: dict[str, list[str]]
```

For hierarchy-traversal filters this is awkward. The driving real-world case: "all dissemination areas in Ontario" resolves via `Codelist.narrower_transitive("<ontario>")` to ~50k REF_AREA codes. The current path:

1. Materialise the codelist hierarchy into a Python list of 50k strings.
2. Pass it to `parse_components(...)` as `{"REF_AREA": codes}`.
3. `to_where_clauses` emits `WHERE REF_AREA IN (?, ?, …×50000)` with 50k bind parameters.

DuckDB handles this, but:
- It's gross.
- Other backends (Postgres, BigQuery) have bind-parameter caps (often 32k or lower).
- `LazyCodelist` already compiles `narrower_transitive` into a SQL subquery — we're throwing that away to materialise.

## Proposal

Widen `ComponentFilter` filter values to accept either form:

```python
# eager — today's behaviour, unchanged
cf.dimensions["REF_AREA"] = ["A0001", "A0002", ..., "A50000"]

# SQL relation — new
cf.dimensions["REF_AREA"] = lazy_cl.narrower_transitive("ON_CODE")
```

The streaming-query SQL builder (`local/_data_store.py:_build_query`) detects a SQL-relation value and emits:

```sql
WHERE REF_AREA IN (<lazy-codelist subquery>)
```

against the same DuckDB connection — no materialisation, no parameter binding for the 50k codes.

## Design surface

The non-obvious calls:

1. **Where does the abstraction live?**
   - Pragmatic: `ComponentFilter` accepts `list[str] | LazyCodelist`. Direct, but couples the model layer to a storage type.
   - Generic: introduce a `SqlRelation` Protocol in `data_store.py` (something like `to_sql() -> tuple[str, list[object]]` returning a SQL fragment + bind params for the subquery). Backends implement it. `ComponentFilter` accepts `list[str] | SqlRelation`.
   - The Protocol approach future-proofs against other lazy producers (federation queries, polars LazyFrame as a relation, future backends).

2. **Does this affect both `dimensions` and `attributes`?**
   - The comment says yes — both should accept either form. Same plumbing, same translation step.

3. **Does `parse_components` itself need to know?**
   - Probably not — it just stores values. The translation to SQL happens in `to_where_clauses` / `_build_query`.

4. **Cross-connection subqueries**
   - The DuckDB lazy-codelist subquery only works if it's on the same connection as the data scan. `DuckDBDataStore` shares a connection with `LocalRegistry` (which owns the codelists), so this composes today. Document the constraint.

5. **Does the catalog API need a convenience like `catalog.lazy_codelist(cl)`?**
   - The comment hints at this. Worth bundling so users don't have to reach into `storage.lazy` directly.

## Acceptance

- [ ] `ComponentFilter` filter values widened to `list[str] | <relation type>` for both `dimensions` and `attributes`.
- [ ] `DuckDBDataStore` SQL builder emits `IN (<subquery>)` for relation values, falling back to `IN (?, ?, ...)` for lists.
- [ ] Test: a 50k-element relation filter produces a single bind-parameterless `IN (SELECT …)` clause and returns the right rows.
- [ ] Test: mixed eager + relation values across dimensions compose correctly (one dim eager, another lazy).
- [ ] Cookbook entry in `docs/cookbook/rest_facade.md` shows the lazy form as the recommended path for hierarchy traversals.

## Comments

### 2026-05-02

Closed in v0.19.0 (commit 087766d).

Implementation:

- New SqlRelation Protocol in sdmxlib.data_store (runtime_checkable, single to_sql() → (str, list[object]) method).
- CodeQuery now satisfies SqlRelation via .to_sql() — compiles to SELECT c.code_id without executing.
- ComponentFilter dimension and attribute values widened to list[str] | SqlRelation. SQL builder dispatches: lists become IN (?, ?, ...), relations become IN (<subquery>) with the relation's binds spliced inline.
- parse_components accepts mixed forms in component_filters dict. Mixing a dotted-key segment with a relation on the same key dimension raises ValueError (relations don't merge with eager lists).
- Cookbook entry under 'Filtering by hierarchy: lazy SQL relations' in docs/cookbook/rest_facade.md.

Acceptance:

- ✅ ComponentFilter values widened to list[str] | SqlRelation for both dimensions and attributes
- ✅ DuckDBDataStore SQL builder emits IN (<subquery>) for relations, IN (?, ?, ...) for lists
- ✅ Test test_query_lazy_relation_avoids_parameter_explosion verifies a relation produces 1 fragment with ≤5 binds (vs. N binds for materialised list)
- ✅ Test test_query_with_lazy_codelist_relation_filter exercises end-to-end LazyCodelist.narrower_transitive → catalog.query path
- ✅ Cookbook documents the lazy form as recommended for hierarchy traversals

The SqlRelation Protocol approach (vs. concrete LazyCodelist coupling) keeps the door open for other lazy producers (alternative backends, polars LazyFrame, federation queries). Single-connection constraint documented in cookbook + Protocol docstring.
