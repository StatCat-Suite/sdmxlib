# Issue #334: REST fetch serves only the structure plane — no /metadata requests

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-18 |
| Closed | 2026-08-19 |
| Labels | `design` |

`query/_rest.Request.path` is hardcoded:

```python
@property
def path(self) -> str:
    return f"structure/{self.resource}/{self.agency}/{self.resource_id}/{self.version}"
```

SDMX REST 3.0 routes three ways — `/structure`, `/data`, `/metadata` — and the
planner can only build the first.

## Effect

Seven of the 34 `sl.q` relations are metadata-plane: `metadata_set`,
`metadata_target`, `reported_attribute`, `msd`, `metadataflow`,
`metadata_attribute`, `metadata_provision_agreement`. A query over any of them
works against a `LocalRegistry` and cannot fetch against a `RestRegistry` —
there is no request to issue.

This is not a plane the query language separates on purpose: the edge graph
wires metadata relations onto the same `artefact` spine as structural ones
(`Edge("spine", "metadata_set", "urn", "artefact", "urn")`), so a single path
can start at `q.metadata_set` and end at a codelist. Locally that traversal is
ordinary. Remotely, half of it is unfetchable.

## Change

- `Request` grows the plane, or a sibling type for `/metadata`.
- `_closure` decides which plane each scan needs, from the relation.
- A path crossing planes needs requests on both — worth a test that the
  crossing case issues two.
