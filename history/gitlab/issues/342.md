# Issue #342: a to-many projection is refused at collect(), a projected filter at the call — same page, two moments

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-19 |
| Closed | 2026-08-20 |
| Labels | `design`, `dsl` |

Found while writing doc tests for `docs/cookbook/structures_as_frames.md`,
whose "What gets refused" section presents these side by side as if they
behaved the same way. They do not.

```python
cl.codes.select(sl.q.code.id).filter(sl.q.code.depth == 0)
# TypeError at the call — nothing has run

cl.codes.select(sl.q.code.annotations.title)
# ...returns a Frame. The PathError arrives at .collect()
```

The page showed the second error on the `select()` line, which is where a
reader would expect it and where it does not happen. Corrected there; this is
about whether the *behaviour* should agree rather than the prose.

## Why it is defensible as-is

The path is compiled when the query runs, so a to-many projection is caught
then — consistent with "a query is a plan, and nothing runs until a terminal".
Filtering a projection is a *composition* error: `Frame` has no `filter`, so
the refusal is structural and cannot be deferred.

## Why it might not be

The to-many-ness of `annotations` is a property of the declared edge graph and
is known when `select()` is called — nothing about it needs the database. A
caller building a query interactively gets one refusal immediately and the
other only when they run it, with no rule to predict which.

`_joins.PathError` is already raised eagerly elsewhere: `q.codelist.codes.id`
in a *filter* position refuses at construction. So the language does not have a
single rule here either way.

## Options

1. **Refuse eagerly in `select()`** — check the path's cardinality when the
   column is accepted. Makes the two neighbours agree, and moves an error from
   run time to build time, which is the direction this language usually
   prefers.
2. **Leave it, and say so.** Document that path errors are execution-time and
   composition errors are call-time. Cheap, and the page now carries a version
   of this.

Option 1 has a cost worth naming: `select()` would gain a check that walks the
path, and `to_sql()` already does that walk — two places that must agree about
cardinality, which is the shape of drift the edge graph exists to prevent.

## Acceptance

- one stated rule for when a path error surfaces, in the query-language design
  doc
- `structures_as_frames.md`'s two refusals either agree, or the page explains
  why they differ (it currently does the latter)
