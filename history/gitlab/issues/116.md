# Issue #116: perf: intern language codes in InternationalString to cut XML parse allocations

| | |
| --- | --- |
| State | closed |
| Opened | 2026-05-31 |
| Closed | 2026-06-01 |
| Labels | `perf` |

## Context

Surfaced by the new Phase 1 bench suite (MR !79). \`pytest-memray\` on \`parse[large-2.1]\` shows \`read_istring\` (\`src/sdmxlib/formats/sdmx_ml/_common.py:142\`) as the dominant allocator at the watermark — **~1.0 MiB** of the 2.2 MiB total.

Each artefact name / description becomes an \`InternationalString\` (dict-like). The bilingual fixture has \`{"en": "...", "fr": "..."}\` repeated across every codelist, code, dimension, concept, dataflow — thousands of dict entries, all keyed by the same handful of two-letter lang codes.

## Why this matters

- Real-world Eurostat / ECB messages use 5+ languages → linear scale of this cost.
- It's a pure-Python allocation pattern (PyDictKeysObject + PyUnicode for each key).
- Lang codes are a tiny finite set (\`en\`, \`fr\`, \`de\`, \`es\`, BCP-47-coded variants like \`en-GB\`) — perfect intern candidates.

## Proposed fix

Intern lang keys at the read site. Either:

1. \`sys.intern(lang)\` inside \`_to_istring\` / \`read_istring\` — cheap, language-agnostic.
2. Module-level cache keyed by lang code with stable string identity.

(1) is simpler and gets us most of the win.

## Estimated impact

Per the memray sample on \`large-2.1\` (500 dataflows, 10 dims, 200 codes/dim): expect 200–400 KiB watermark reduction, no functional change. Bench harness will quantify exactly.

## Acceptance

- \`just bench\` shows \`parse[large-*]\` wall unchanged or faster.
- \`just bench-mem\` shows \`read_istring\` peak drops to a residual (the \`dict\` itself, not the keys).
- No behavioural change — \`istring["en"]\` continues to work; \`InternationalString.__eq__\` semantics preserved.
