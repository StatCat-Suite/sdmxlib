### 2026-08-10

## Two premises moved before this was started

**The third scope bullet is now dead.** It says:

> Decide whether `sort_keys` is order-sensitive. It is — `sort_by(id).sort_by(depth)` differs from the reverse

#294 made `order_by` **replace**, so measured today:

```
q.order_by(code.id).order_by(code.depth).order_keys == q.order_by(code.depth).order_keys   ->  True
```

Chained calls no longer compose at all. Order-sensitivity survives only *within* one call — `order_by(a, b)` differs from `order_by(b, a)` — so the bullet is still directionally right (do not sort the key list) but its example and reasoning need rewriting. Also note the field is now `order_keys`, and `sort_by` is `order_by` (#295).

**The trap named in the issue is now a property, and still has the hole the issue describes.** `test_every_ordering_either_commutes_or_is_refused` (#293) asserts commutativity *by result* across every clause pair. That is exactly the "passes forever while the key stays broken" shape — worth extending to identity once `canonical_key()` exists, rather than adding a separate test.

## Confirmed still true, and tractable

```
q.filter(code.id == "A").filter(code.depth == 0)
q.filter(code.depth == 0).filter(code.id == "A")
  same rows : True
  same SQL  : False
  IR equal  : False

is_in(["A","B"]) == is_in(["B","A"])  ->  False
```

Predicates are frozen attrs: hashable, and sortable by a derived key `(type name, fields)` — **not** by `<`, which is unimplemented on them, so the sort needs an explicit key function. Nothing but the emitted clause order reads predicate order today, so canonicalizing at construction costs no fidelity that anything consumes.

## One consequence to expect

Canonicalizing predicate order **will change `tests/support/sql_corpus.py` output**. Every change in this milestone so far has had a byte-identical corpus; this is the first where a non-empty diff is correct. Check the diff contains only clause reordering.

## Verdict for #273

Attempted as #273 asked: canonicalization fits in the existing query object and needs no separate IR. Recorded in `docs/design/query-composition.md`.

### 2026-08-10

## Correction to my earlier note: no corpus diff after all

I predicted this would produce the first non-empty `sql_corpus` diff in the milestone. It does not — **the corpus is byte-identical** — because the design that would have caused it was abandoned on measurement.

## Canonical in the key, not at construction

The scope says "impose a total order on `predicates` at construction". Implemented that way first. Measured:

| | main | construction-time canonicalisation |
| --- | --- | --- |
| `is_in`, 5000 members | 115 us | **13.3 ms** (116x) |
| `is_in`, 100 members | 7.6 us | 279 us (37x) |
| chain of predicates | 11.5 us | 59.7 us (5x) |
| single predicate | 2.7 us | 6.7 us (2.4x) |

Every construction paid for a full recursive key build, on the path #271 already flags as hot. Moving the canonicalisation into `canonical_key` puts the cost on the caller who wants a key, and only then: benchmarks are now **identical to main**.

The trade, which is the one thing here worth arguing with: `filter(a).filter(b)` and `filter(b).filter(a)` still differ as *values* and still emit clauses in different orders. They agree on `canonical_key()`, which is what the issue asked for and what a cache uses. If IR-level equality turns out to matter for its own sake, that is a separate decision with a known price.

## A bug shipped and caught inside the change

The first `canonical_key` keyed query objects **on their own compiled SQL**. `CodeQuery` satisfies the `SqlRelation` protocol — it has `to_sql` and `columns` — so a `runtime_checkable` isinstance matched before the attrs branch, and that SQL is emitted with `omit_order=True`. Two queries differing only in `order_by` produced the *same key*: a cache would have served one page order for another, which is exactly this issue's failure mode, reintroduced by the fix for it.

Caught because the test asserts the order-sensitive case instead of assuming it. Reintroducing it now fails three tests.

## Scope items, resolved

- **Predicates**: canonical in the key. ✔
- **`InSet.values`**: sorted and deduplicated in the key. ✔
- **`order_keys` must not be sorted**: correct, and now asserted. `_COMMUTATIVE_FIELDS` is keyed on `(class, field)` rather than field name so adding `order_keys` by carelessness is not a one-word mistake. The bullet's example is stale — #294 made chained `order_by` *replace*, so `order_by(id).order_by(depth)` is just `order_by(depth)`.
- **Expose the result**: `canonical_key()` on all four query classes. Determinism across processes is asserted through a real subprocess boundary under three `PYTHONHASHSEED` values, which no in-process test can check.

## Also worth having

`with_annotations("a", "b")` and `("b", "a")` now key alike too — same argument, and it was free once the machinery existed.
