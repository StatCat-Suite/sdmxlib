# Issue #271: dsl-20: a 5000-code is_in emits 15KB of SQL and 5001 binds

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-11 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `design`, `dsl`, `perf` |

`is_in` with a large set emits one bind per element. Measured on `main`:

| set size | emitted SQL | binds | compile |
| --- | --- | --- | --- |
| 1 | ~180 chars | 2 | 4.5 µs |
| 100 | ~600 chars | 101 | 6.7 µs |
| **5000** | **15,076 chars** | **5001** | **114 µs** |

5000 codes is not a stress test — it is an ordinary SDMX code set. CL_GEO-scale codelists are larger.

## Three costs, not one

- **Plan quality.** A 5000-element `IN` list is a worse input to the optimizer than a semi-join against a registered relation.
- **SQL text size.** 15 KB of statement per query, which matters if it is logged, traced, or shipped over MCP.
- **Cache key size.** Under #270 the code set becomes part of the query identity. As a literal list that is 15 KB of key material; as a registered relation it is one hashable reference.

The third is the one that compounds with #270 and is easy to miss.

## We already have the mechanism

`is_in` accepts a `SqlRelation` (#261), which compiles to `IN (<subquery>)` with only the relation's own binds spliced:

```python
cl.codes.filter(code.id.is_in(other.narrower_transitive("CA")))
```

What is missing is the **eager** path taking it automatically: above some width, register the values as an Arrow table and semi-join rather than expanding placeholders.

## Scope

- A threshold above which an eager `is_in` registers its values instead of expanding. Roughly 100 is the conventional figure; pick it from a measurement on this codebase rather than from folklore — the benchmarks in `tests/bench/test_query_dsl.py` already parametrise `is_in` at 1 / 100 / 5000 for exactly this.
- Configurable, because the right value depends on whether the caller cares about plan quality or statement size.
- Registration needs a lifetime. A temp relation on the store's connection has to outlive compilation and be cleaned up; that is the design question, not the threshold.
- Interaction with `to_sql()`: it currently returns `(sql, params)` with no side effects. A registering path either performs a side effect at compile time — which breaks that contract and #270's canonicalization — or defers registration to execution, which means `to_sql()` alone can no longer be executed by a caller. **Decide this before implementing**; it is the real content of the issue.

## Test gates

- Below the threshold, emitted SQL is unchanged (the `sql_corpus` harness covers this).
- Above it, bind count is bounded and independent of set size.
- Differential property: the same rows either side of the threshold, since the boundary is now a behavioural cliff.
- Benchmarks re-run against the !257 baseline; the point of the change is the 5000 case, so it must show there.
