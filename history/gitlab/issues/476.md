# Issue #476: SDMX-ML 2.1: a <Ref> without @version reads as latest; the XSD defaults it to 1.0

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-16 |
| Closed | 2026-10-16 |
| Milestone | %21 Conformance evidence: what the green checks do not prove |

Found while classifying every defaulted attribute read for #474.

**What happens.** A 2.1 `<Ref>` without `@version` (or `@maintainableParentVersion` for an item/child ref) is read as version `latest` — a late-bound reference:

- `formats/sdmx_ml/_common.py` `ref_el_to_urn`: `ref_el.get("version", "latest")`, `ref_el.get("maintainableParentVersion", "latest")`
- `formats/sdmx_ml21/reader.py` hierarchical-code ref: `ref_el.get("maintainableParentVersion", ref_el.get("version", "latest"))`

**What the schema says.** Every concrete ref type in `SDMXCommonReferences.xsd` declares the default: `MaintainableRefBaseType`, `ItemSchemeRefBaseType`, `StructureOrUsageRefBaseType`, `StructureRefBaseType`, `StructureUsageRefBaseType` → `version default="1.0"`; `ChildObjectRefBaseType`, `ContainerChildObjectRefBaseType`, `ItemRefBaseType`, `ComponentListRefBaseType`, `ComponentRefBaseType` and every concrete item ref type → `maintainableParentVersion default="1.0"`. Only the abstract `RefBaseType` has none. So `<Ref agencyID="ECB" id="CL_FREQ"/>` names `CL_FREQ(1.0)`, and the reader resolves it as whatever is latest. The same class of defect as #475: the schema's default is the standard's own answer.

**Ecosystem.** sdmx1 reads the omission as unspecified (`None`); pysdmx uses `"1.0"` in places (HCL). No consensus to follow, so the XSD decides.

**Exposure.** 0 of 375 `<Ref>`s across the 2.1 fixtures omit a version, so this is latent, not observed — but a document that does gets a silently different resolution, not an error.

**Fix.** Read the XSD default (`"1.0"`) at the three sites. 3.x is unaffected: its references are URNs, which always carry a version. The #474 census guard (`tests/unit/test_reader_defaults_census.py`) pins these sites to this issue until fixed.
