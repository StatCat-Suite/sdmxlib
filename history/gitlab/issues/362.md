# Issue #362: MetadataProvisionAgreement is half-wired: modelled and storable, no StructureMessage slot

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |

Found while auditing SDMX IM coverage for the #361 scoping.

`MetadataProvisionAgreement` is a `MaintainableArtefact` in
`model/metadata_provision.py`, is exported from `sdmxlib`, and has an
`ArtefactKind` entry in `storage/_kinds.py` — so it can be written to and read
from the DuckDB store.

But its `msg_field` is `"metadata_provision_agreements"`, and
`StructureMessage` has no such slot:

    >>> StructureMessage.containing(mpa)
    TypeError: MetadataProvisionAgreement maps to slot
    'metadata_provision_agreements' which is not a StructureMessage field

Consequences:

* `StructureMessage.containing()` raises for it — a REST handler returning one
  cannot build a message.
* No structure reader or writer handles it. Grepping `formats/` finds it only
  in `sdmx_ml30/metadata.py` and `sdmx_json/metadata.py`, which are the
  *metadata-message* path, not the structure path.
* `Session.ingest` walks `msg.all_artefacts()`, so one can never be interned
  from a structure message.

It is a top-level `<MetadataProvisionAgreements>` section in both the 3.0 and
3.1 `StructuresType` sequences, so the wire format has a place for it.

The failure is at least loud — `containing()` names the missing slot rather
than silently dropping it, which is the check added for exactly this shape.

## Also worth noting

The gap escaped my earlier IM-coverage audit because that audit keyed on
`StructureMessage` slots, and this artefact has none. Keying on
`MaintainableArtefact` subclasses instead found it. The corrected count is
**19 of 37** SDMX-ML 3.1 top-level artefact types modelled, not 18.

`MetadataSet` is in the same position and is *correct* — it belongs to
`MetadataMessage`, which does have the slot.

## Fix

Add the `metadata_provision_agreements` slot to `StructureMessage`, include it
in `all_artefacts()`, and wire the structure readers/writers for all three
SDMX-ML versions plus SDMX-JSON. Adding it to `tests/support/maximal.py` then
brings it under the #354 field census automatically.

A cheaper interim step, if the wire support is not wanted yet: a test asserting
every `msg_field` on a `MaintainableArtefact` subclass names a real slot on one
of the two message types. That turns this class of half-wiring into a failure
at the point it is introduced rather than at the point someone calls
`containing()`.
