Investigation/spike (milestone: SDMX-JSON dict+orjson → msgspec). **This gates whether orjson can be removed entirely.** The data-JSON path is the only place orjson does things msgspec doesn't do out of the box.

## The two hazards
1. **numpy serialization.** `_data_common.py` dumps observation batches with `orjson.OPT_SERIALIZE_NUMPY` — orjson natively serializes numpy arrays/scalars. msgspec has **no** native numpy support; it needs an `enc_hook`. Question: can an `enc_hook` (numpy → list/scalar) match orjson's throughput on large observation batches, or is it a regression?
2. **Streaming/chunked output.** `data_v1.py` / `data_v2.py` build JSON incrementally by concatenating byte fragments (`orjson.dumps(head)[:-1] + b',...'`). Determine the equivalent msgspec pattern (`Encoder().encode` into fragments) without buffering whole payloads.

## Deliverable
- A validated approach (enc_hook + streaming pattern) **with a benchmark** vs the current orjson data path on a large observation payload, **or**
- A documented blocker — in which case the milestone goal narrows to \"orjson only in the data streaming path\" and issue \"Remove orjson\" is rescoped.

## Conclusion: data plane migrates cleanly — **no blocker, orjson can be fully removed**

Spiked the full streaming data-writer path (v2) with orjson swapped for msgspec, on the pinned shapes.

### Q: is numpy necessary?  → **No.**
The observation values are already Python-native — `encode_batch` builds `rows`/`keys` via Polars `.to_list()`, which yields `float`/`str`/`int`/`None`, not numpy. `msgspec.json.encode` handles them with **no enc_hook** and produces **byte-identical** output. `orjson.OPT_SERIALIZE_NUMPY` is unneeded here (defensive leftover); dropping it changes nothing. (The observation value-space is numeric measures + enumerated int positions + colon-joined key strings + None — no numpy, no datetime; TIME_PERIOD is a code string, not a datetime.)

### Q: can msgspec do the streaming?  → **Yes.**
`msgspec.json.encode(d)` returns `bytes` like `orjson.dumps`, and the brace-strip fragment (`encode(d)[1:-1]`) is byte-identical. The whole fragment-concatenation streaming pattern in `data_v1.py`/`data_v2.py` works unchanged.

### Perf (full write_v2 path, real batches)
| shape | orjson | msgspec | Δ | output |
|---|---|---|---|---|
| dot_stat ~50k | 14.08 ms | 14.45 ms | +3% | byte-identical |
| large_100k | 28.66 ms | 28.98 ms | +1% | byte-identical |

Within noise, inside the ≤5% acceptance gate. Byte-identical output on real batches is the strong signal: no numpy is actually flowing, and the streaming splice is unaffected.

### Decision
**Full orjson removal is feasible.** #183 (data v1+v2 migration) is a straight `orjson.dumps(..., OPT_SERIALIZE_NUMPY)` → `msgspec` swap; drop the numpy option. #185 (remove orjson) is unblocked — no "keep orjson for the data path" carve-out needed. The only residual note for #183: if a future producer path ever surfaces a genuinely numpy-typed value into the observations dict (not seen in any current shape), add a one-line `enc_hook`; the perf headroom (+1–3%) leaves room for it.

Spike scripts: `scratchpad/data_msgspec_spike.py`, `scratchpad/data_full_writer_spike.py`.
