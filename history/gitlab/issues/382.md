# Issue #382: %18's "collect() within 5x of ids()" criterion is unreachable by construction — replace it

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-27 |
| Closed | 2026-09-05 |
| Milestone | %18 Read-path performance: what the synthetic benchmarks could not see |
| Labels | `docs`, `dsl`, `perf` |

%18 states, as one of its success criteria:

> `q.code…collect()` and `q.hcode…collect()` are within **5x** of their
> `.ids()` cost, rather than the current 38x and 46x.

I wrote that, and it is not reachable — not because `collect()` is too slow,
but because the two terminals do different amounts of *work*, and the ratio
was never a measure of the thing it was supposed to measure.

## Why the ratio cannot close

`.ids()` fetches one `VARCHAR` column. `.collect()` fetches every column,
including two `MAP(VARCHAR, VARCHAR)` labels that cost 750 ms to turn into
Python dicts (#380), and runs a second query for annotations that costs
1109 ms (#381). A `collect()` with **zero** object-construction overhead —
free `Code.__init__`, free istrings — would still be an order of magnitude off
`.ids()`, because it has to materialise data `.ids()` never touches.

Measured on `CL_GEOGRAPHY`, 579,951 codes, one predicate, five terminals:

| terminal | ms |
| --- | --- |
| `.count()` | 21.8 |
| `.ids()` | 99.9 |
| `.frame()` → polars | **161.2** |
| `.collect()` | 3336 |

The decomposition of that 3336: ~430 ms is SQL execution (12%); the rest is
the Python boundary — 916 ms `fetchall` (#380), 1109 ms annotations (#381),
642 ms building the objects, ~600 ms assembly.

So the 5x target measures "how much more does `collect()` fetch than `ids()`",
dressed up as "how expensive is object construction". Those are different
questions and only the second is the milestone's subject.

## What to replace it with

Two candidates, both better than the ratio and neither obviously best:

1. **Per-row budget** — µs per object built, isolating construction from
   fetch. Today `collect()` is 5.8 µs/code end to end, of which 1.1 µs is
   `Code.__init__` over already-fetched rows and 0.19 µs is the interpreter
   floor for building a bare tuple from the same row. A budget stated against
   the 1.1 µs figure measures the thing %18 is actually about. Needs the fetch
   and build separated in the benchmark, which #380 asks for anyway.
2. **A ratio against `.frame()`**, not `.ids()`. `.frame()` fetches the same
   columns and is 161 ms, so `collect() / frame()` = 21x *is* an
   object-construction number, with the fetch cost on both sides. Cheap to
   state, no new instrumentation, and it goes down only when construction gets
   cheaper.

(2) is the smaller change and might be enough on its own.

## And the guidance the numbers actually support

`.frame()` returns all 579,951 codes as a polars DataFrame in **161 ms**. That
is the frame-returning surface #348 asked for, it already exists, and nothing
in the docs points a consumer at it when they reach for `.collect()` on a
large relation. Whatever criterion replaces the 5x, the cookbook should say
plainly: **`collect()` is for object graphs, `frame()` is for volume.** #348's
consumer measured `collect()`, concluded the library was in the way, and
dropped to `conn.execute` — with `.frame()` sitting one method away.

That guidance is free, true today, and probably worth more than either
criterion.

## Also

`tests/bench/test_bundle_reads.py::test_collect_stays_within_5x_of_ids`
carries `xfail(strict=True)` against this criterion. It is asserting something
unreachable, so it should be replaced rather than left to xfail forever — a
permanent xfail is a test that has stopped being a question.

## Acceptance

- %18's success criteria no longer contain the 5x ratio.
- The replacement is stated against something `collect()` can actually reach,
  with the number it is at today recorded next to it.
- `test_collect_stays_within_5x_of_ids` is replaced, not re-marked.
- The cookbook says which terminal to use at which scale.

## Comments

### 2026-09-05

Landed in !455.

Re-measured first — the table in the description predates #377, #380, #381 and #349, all of which have since landed:

| | rows | `.ids()` | `.frame()` | `collect()` | `collect(annotations=False)` |
| --- | --- | --- | --- | --- | --- |
| `q.code` | 579,951 | 103 ms | 158 ms | 2372 ms — **15.0x** | 1196 ms — **7.6x** |
| `q.hcode` | 499,143 | 94 ms | 176 ms | 2311 ms — **13.2x** | 2264 ms — **12.9x** |

Took direction (2), the ratio against `.frame()`, **plus a second bound the issue could not state because #381 had not landed yet.** With `annotations=False` there is exactly one query on each side reading the same columns, so `collect(annotations=False) / frame()` is the construction tax alone — a regression there is a per-row cost rather than a heavier read. Bounded at **20x** and **16x**.

The gap between the two ratios is itself informative: the annotation read is half of `q.code`'s collect and almost none of `q.hcode`'s, whose nodes carry hardly any. That is also why the bounds are generous and deliberately not per-accessor — how far apart they sit is a property of how many annotations a bundle carries, and the tier runs against whatever bundle it is pointed at.

**Verified as a guard rather than as a green.** With both bounds dropped to 5 it fails on the real bundle with `code: collect() is 15.5x frame() (2.44s vs 0.16s), over the 5x bound`. The module docstring's rule — a guard that has only ever passed is not known to be a guard — applies to a replacement as much as to a new one.

**One thing found on the way:** `query_tutorial.md` §3 listed `.collect()` as returning a `polars.DataFrame`. That is `select(...).collect()`, not the bare terminal — so the confusion this issue describes was sitting in the tutorial's own terminal list. Fixed, and both that page and `cookbook/discovery.md` now carry the table and the rule: **`collect()` is for object graphs, `frame()` is for volume.**

All four acceptance criteria met. %18's criteria are edited on the milestone: the 5x bullet is gone, and the replacement records what the milestone actually moved (`q.code…collect()` 3.99 s → 2.37 s, `q.hcode…collect()` 4.92 s → 2.31 s) next to the bound rather than only the bound.
