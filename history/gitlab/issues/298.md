# Issue #298: store: no epoch a consumer can compose into a cache key

| | |
| --- | --- |
| State | closed |

| Milestone | %25 Serving SDMX-REST from a local store |
| Labels | `design`, `storage` |

Split out of #270. `canonical_key()` identifies a *query*; it deliberately says nothing about which store the query runs against or what is in it. Measured:

```
two Registry instances, same codelist URN, different codes
  rows        : ['A', 'B']  vs  ['X', 'Y', 'Z']
  same key?   : True
```

That is the right boundary for the key — a connection has no stable cross-process identity, and baking one in would destroy the determinism that makes the key persistable. So a cache key is a **pair**:

    (datasource identity and epoch, query.canonical_key())

We supply the second half. **We supply nothing for the first**, and the consumer cannot construct it reliably on its own: two connections to the same file are the same store, `:memory:` connections never are, and neither fact is visible from a `DuckDBPyConnection`.

## What exists today

`sdmx._meta` is a two-column key/value table holding exactly one row, `schema_version = 2.5`. There is no slot for "when did the content last change".

## What a consumer needs

An **epoch**: a value that changes whenever anything a query could read changes, and is stable otherwise. Enough for `(epoch, canonical_key)` to be a sound cache key.

Options, uncosted:

- **A. Monotonic counter in `_meta`**, bumped by every writer in `storage/writers.py`. Simple; needs every write path to remember, which is the usual way this rots.
- **B. Content hash** of the artefact table. Correct by construction, costs a scan.
- **C. DuckLake / catalog snapshot id** where the store is DuckLake-backed — it already versions, and this may be free.
- **D. Per-artefact epoch** rather than store-wide, so a codelist write does not invalidate dataflow queries. More useful, more bookkeeping.

Plus a **store identity** distinct from the epoch, so two different databases never collide even at the same epoch. A UUID written at `create_schema` time would do it and is cheap.

## Test gates

- Two stores, same content, different identities: keys must differ once composed.
- One store, a write between two reads: epoch must change.
- No write: epoch must not change — otherwise the cache never hits, which is the failure that looks like success.

## Prerequisite

Confirm a consumer actually wants this before building it. `sdmxlib-rest` is the caching consumer named in #270; ask what it keys on today.
