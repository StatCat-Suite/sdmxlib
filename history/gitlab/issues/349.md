# Issue #349: the DSL emits a redundant EXISTS for ancestor hops, and .ids() selects every column — 3.6x on hierarchy walks

Split out of #348. That issue's headline row (a 220 s ancestor-map) is gone,
but two of its four rows still show us **2-3x slower than the hand-written SQL
they replace**, and I attributed that to result-building in a comment on #348.
That was wrong. Measured, it is the SQL we emit.

## Where the time goes

264,269-node hierarchy, DuckDB in-process, `narrower_transitive` of a 1,000-node
subtree. Best of 5.

| | ms |
| --- | --- |
| `.count()` — returns a single integer | 27.4 |
| `.ids()` — returns 1,000 strings | 30.1 |
| `.collect()` — returns 1,000 `HierarchicalCode` | 35.9 |
| building the plan, never running it | 0.0 |
| **the DSL's own SQL, on a plain cursor** | **39.9** |

`.count()` returns *one integer* and still costs 27 ms, and running our emitted
SQL by hand costs the same as `.collect()`. So this is not object construction
and not the execution harness — object construction is the 6 ms between
`.ids()` and `.collect()`, and it is the only part I got right.

## The SQL

```sql
SELECT s0.* FROM sdmx.hierarchy_node s0
WHERE (s0.hierarchy_urn = ?
   AND EXISTS (SELECT 1 FROM sdmx.hierarchy_node s1
                WHERE (s1.hierarchy_urn = s0.hierarchy_urn
                  AND s1.node_id = ANY(s0.ancestor_ids)
                  AND s1.node_id = ?)))
ORDER BY s0.node_urn NULLS LAST
```

| variant | ms |
| --- | --- |
| as emitted | 40.0 |
| same, `ORDER BY` removed | 39.8 |
| **`EXISTS` collapsed to `? = ANY(s0.ancestor_ids)`** | **18.1** |
| collapsed, and projecting `node_id` instead of `s0.*` | **11.1** |

The `ORDER BY` is free. The other two are 2.2x and a further 1.6x — 3.6x
together, which closes most of the gap #348 reports on its first two rows.

## 1. The correlated `EXISTS` is redundant here

`ancestors.id == X` is a to-many hop, and `_compile.py` renders a to-many hop
as a correlated `EXISTS` — correctly, in general. But this hop's target is
`hierarchy_node.node_id`, and `ancestor_ids` **is a list of `node_id`**. So the
subquery joins a table solely to assert that a constant appears in an array the
outer row already carries. `? = ANY(s0.ancestor_ids)` says the same thing.

The rewrite is valid only when the far side has **no predicate other than on
the joined key**. `ancestors.id == X` qualifies; `ancestors.level.id == "PR"`
does not, and must keep the join. So this is a narrow peephole, not a change to
how to-many hops compile.

**One caveat worth stating rather than glossing:** the `EXISTS` form also
requires the ancestor row to *exist*, and the collapsed form does not. They are
equivalent only under referential integrity between `ancestor_ids` and
`node_id` — which the writer maintains (it bakes the closure) but nothing
asserts. If that rewrite lands it should come with a property test over
generated hierarchies comparing the two forms row-for-row, in the style of
`tests/unit/test_properties_query_hcode.py`.

The same shape applies to `code.ancestors` / `concept.ancestors` /
`category.ancestors` / `metadata_attribute.ancestors` — every `ancestor_ids`
edge in `_edges.py` carries `member_of=1`.

## 2. `.ids()` selects every column and discards all but one

```sql
-- .ids()
SELECT s0.* FROM sdmx.hierarchy_node s0 WHERE ...
-- .select(q.hcode.id) — what .ids() could compile to
SELECT s0.node_id AS node_id FROM sdmx.hierarchy_node s0 WHERE ...
```

`.ids()` already knows it wants one column. On this table `s0.*` drags
`name`/`description` `MAP(VARCHAR, VARCHAR)` columns through the scan for
nothing — which is also the memory concern #348 raises, since those are the
widest values in the row. Same for `.count()`, where the projection is
discarded entirely.

## Why this is worth doing

#348's consumer measured us at 1.38 s where their SQL took 0.015 s and
concluded the library was in the way. Most of that gap has closed for other
reasons, but the remaining 2-3x is real and is ours — they were not measuring
noise. A 3.6x on the two commonest hierarchy shapes is also the difference
between "use the DSL" and "drop to `conn.execute`", which is the decision #325
turned out to be about.
