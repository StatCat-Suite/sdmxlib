**Phase 2.** Extend `tests/support/xsd_facts` to extract *required child elements*, and check the model against them directly — no generation involved.

## Why this one first among the extractors

Four of milestone 10's ten findings were `minOccurs≥1` violations: `Metadataflow.targets`, `ProvisionAgreement`'s two edges, MSD `ConceptIdentity`, and 2.1's required `ComponentMap`. Each was found by generating an artefact and reading a schema error. This is by far the highest-yield of the four unextracted constraint kinds, and it is what produces the 24 pairs in #227.

## The extraction

```python
@functools.cache
def required_children(version: SchemaVersion) -> dict[str, tuple[str, ...]]:
    """Complex type -> child elements that must appear."""
```

**The nesting is the hard part, and a naive version gets it wrong.** An element is only strictly required if `minOccurs != 0` *and* no ancestor between it and the type is an `xs:choice` or a group with `minOccurs="0"`. It must also follow `xs:extension` bases, since SDMX puts most cardinality in `…BaseType`.

A prototype that skipped the choice/group walk reported `Categorisation` as requiring `Source` and `Target`. It does not — a categorisation with neither serialises to valid 3.0. That false positive is the reason this issue exists as its own step rather than being folded into the fixes: **an extractor that over-reports produces refusals for documents that are fine**, which is precisely the mistake made once already in !231, where a grep-built table refused four map types the 2.1 writer had always emitted correctly.

So: the extractor's output must be verified behaviourally before anything acts on it. Choice-aware counts to reproduce (complex types carrying ≥1 strictly-required child): 2.1 → 213, 3.0 → 124, 3.1 → 125.

## The conformance test

For each modelled artefact, compare the schema's required children against the model fields that are optional (`default is not attrs.NOTHING`). A required child backed by an optional field is a candidate defect — it means a caller can build an artefact with no valid serialisation.

Some of those are legitimate: the model deliberately keeps fields optional so a partially-assembled artefact stays *storable*, with the write boundary doing the refusing. That is the existing `check_serialisable` / `validate` split. So the test's output is a list to triage, and the triage result belongs in a table with reasons — not an assertion that every required child maps to a required field.

## Done when

`required_children` is extracted, choice-aware, spot-verified against at least three hand-checked types, and every modelled artefact's required children are either enforced at the write boundary or listed with a reason.
