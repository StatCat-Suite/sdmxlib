# Issue #354: Category and CategoryScheme annotations are dropped by every SDMX-ML writer

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |

Found while building the 3.0/3.1 writer parity guard in #346.

`_write_category_scheme` / `_write_category` call `write_annotations` in **none**
of the three writers (2.1, 3.0, 3.1). A `CategoryScheme` or `Category` carrying
annotations round-trips through any of them and comes back with none.

## Why nothing caught it

The parity guard added in #346 compares what the 3.0 writer emits against what
the 3.1 writer emits. That finds a field one writer drops. It is structurally
blind to a field *both* drop — the vocabularies match, so there is nothing to
report. XSD validation is blind for the same reason it was blind to the ten
annotation sites #346 restored: annotations are optional, so emitting none is
conformant.

The round-trip tests do not catch it either, because the fixtures do not
annotate a category.

## Fix

Add the `write_annotations` call to the category and category-scheme writers in
all three format packages, and annotate a `Category` in the round-trip fixtures
so the read side is checked too.

Then extend the count guard: `test_every_annotation_site_is_reached` in
`tests/unit/test_ml3_writer_parity.py` asserts the 3.0 writer's
`write_annotations` site count equals the marker count in `_kitchen_sink`, so
the new sites need markers there — which is the guard doing its job.

## The general shape

Worth a broader sweep than the two elements: the question "which model fields
does a writer never read" is answerable mechanically, and a parity comparison
between two writers cannot answer it. A field-coverage check against the attrs
`__attrs_attrs__` of each artefact would find the whole class at once.

## Comments

### 2026-08-20

**This issue's premise is wrong. Closing it — the reported bug does not exist.**

`Category` and `CategoryScheme` annotations round-trip correctly in 2.1, 3.0 and
3.1. Verified by writing a fully-annotated category scheme through each and
reading it back: `scheme.annotations=['CATS-ANN']`,
`category.annotations=['CAT-TOP-ANN']` in all three.

**How I got it wrong.** I grepped the three per-version `writer.py` files for a
`_write_category_scheme` with a `write_annotations` call, found none, and
concluded no writer emits them. But category writing is not in those files —
it is shared, in `WriterHelpers.write_category` / `write_category_scheme` in
`formats/sdmx_ml/_common.py`, and both call `write_annotations`. The search
could not have found what it was looking for, and I read the empty result as
evidence of absence.

The general point the issue made still stands, and is now built: a
parity-between-writers check is structurally blind to a field both writers
drop, and the answer is to compare against the *model* rather than against the
other writer. That is `tests/unit/test_field_coverage.py`, and it found ~50 real
losses per format — none of which were this one.
