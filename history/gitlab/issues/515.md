# Issue #515: REST observations: an unpushable filter fetches the whole flow; the design says refuse

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-20 |
| Closed | 2026-10-21 |
| Milestone | %26 Found by the docs audit: correctness and refusals |
| Labels | `data`, `dsl`, `needs-design`, `priority::medium` |

For an observation query over REST, the design and the code disagree on what happens to a filter the endpoint can't push.

- **Design** (`docs/design/data-plane-pushdown.md` step 4, `test_data_bounding.py`'s docstring): a predicate that can't be pushed into the data key, on a scan the key does not bound, raises `PushdownError`, as the structural planner does.
- **Code:** `RestRegistry._fetch_data_for` calls `data_request_for`, drops the leftover predicates, and never asks `is_bounded`. A measure-only filter fetches `/data/…/all`, the whole flow, and filters locally. `test_rest_observations.py::test_a_measure_filter_reaches_the_wire_as_nothing` pins this behaviour.

The structural side refuses the equivalent query. Which one is right for data?

1. Refuse, matching the structural planner and the design.
2. Allow, since a data flow is bounded by construction (one dataflow), and update the design doc and the docstring.

Labelled `needs-design`.

Found in !665.

## Comments

### 2026-10-21

Decision: **allow if bounded.** A predicate the key can't push runs locally after the fetch when something else bounds that fetch (a pushed key slot or a time period). A query whose whole fetch would be unbounded (`/all` with no period) raises `PushdownError`, naming what to push. Update the design doc to match.
