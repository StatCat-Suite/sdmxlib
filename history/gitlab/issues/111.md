3.1 model audit follow-up (post-MR !63). Surfaced while re-evaluating the model through the \"Python semantics, not XML syntax\" lens.

## Inconsistency

Two enumerated fields in the model are typed as \`str\` despite carrying only a small, fixed set of legal values. Compare to \`AttachmentLevel\` (already a proper \`enum.Enum\`):

\`\`\`python
# Stringly-typed today:
Attribute.usage: str        # \"mandatory\" | \"optional\"
DataConstraint.constraint_type: str  # \"Allowed\" | \"Forbidden\"

# Existing precedent:
Attribute.attachment: AttachmentLevel = AttachmentLevel.OBSERVATION
\`\`\`

Effects:
- No autocomplete on the legal values.
- No \`match\` exhaustiveness checking.
- A typo (\`\"Manadatory\"\`) becomes a runtime mystery instead of a type error.

## Action

Introduce two enums in their respective modules:

\`\`\`python
# model/datastructure.py
class AttributeUsage(enum.Enum):
    MANDATORY = \"mandatory\"
    OPTIONAL  = \"optional\"

# model/constraint.py
class ConstraintType(enum.Enum):
    ALLOWED   = \"Allowed\"
    FORBIDDEN = \"Forbidden\"
\`\`\`

Migrate the two fields. Update the serializers (string-from-enum, enum-from-string). Update any test that compares against literal strings — should be small.

This is per the no-back-compat policy: change the field type, migrate all call sites, done.

## Out of scope

The other \`str\` fields in the model that look enumerable (\`Code.parent_id\`, dimension ids, etc.) are open-ended references, not enums — leave alone.

## Done when

- [ ] Two enums introduced.
- [ ] Fields migrated, callers updated.
- [ ] Serializers round-trip both unchanged on the wire.
- [ ] No existing test regresses.
