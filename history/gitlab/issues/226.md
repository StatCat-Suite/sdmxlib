# Issue #226: Six wire-conformance defects on the map, constraint and metadata paths

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-20 |
| Labels | `bug` |

Found by completing the #223 spec-coverage matrix — the last eight artefact kinds gained generative, schema-validated round-trip coverage, and every one of these six had never been exercised by a fixture.

## Fixed in the same MR

1. **AttachmentConstraint dropped silently by 3.0, 3.1 and SDMX-JSON.** SDMX 3.0 removed the artefact (no `<AttachmentConstraints>` child of `<Structures>`, no counterpart in the JSON schema), folding its role into DataConstraint. Every upgrade path lost it with no error. Now refused — the #225 defect in the opposite direction.

2. **SDMX-ML 2.1 emitted `<str:DataStructureMap>` / `<str:DataflowMap>`.** Neither element exists in 2.1; `StructureSetType` names exactly one such child, `StructureMap`. The 2.1 reader looked for the same two invented names, so writer and reader agreed and the output round-tripped cleanly through sdmxlib while failing XSD validation for every other consumer.

3. **`ConceptSchemeMap` emitted `conceptMaps`**; the schema expects `itemMaps` of `SingleValueMappingType`.

4. **`CategorySchemeMap` emitted `categoryMaps`**; same — `itemMaps`.

5. **`ComponentMap` emitted `sourceId`/`targetId`**; `ComponentMapType` requires `source`/`target` as arrays with `minItems: 1`.

6. **DataConstraint accepted two CubeRegions with the same `include`.** `DataConstraint_CubeRegionInclusion` is an `xs:unique` identity constraint in 3.0/3.1, absent from 2.1. Easy to miss: identity constraints sit beside the element declaration rather than in the type.

## Still open: SDMX-ML 2.1 cannot carry a StructureMap

Fixing (2) exposed a modelling gap rather than a writer bug. 2.1's `StructureMapType` requires at least one `ComponentMap`, and each component `<Ref>` is a `LocalComponentListComponentRefType` requiring **`containerID`, `class` and `package`** — which component list the id lives in, and whether the component is a Dimension, an Attribute or the PrimaryMeasure.

`ComponentMap` carries only `source_id` and `target_id`. The writer cannot supply the rest without guessing, and guessing wrong emits confidently incorrect metadata. So `structure_maps` is refused for 2.1 rather than serialised invalidly.

To lift it, `ComponentMap` needs to carry the component kind (and the container it belongs to). 3.0 does not need this — its component references are plain local ids — so the information would exist purely to serve the 2.1 downgrade. Worth doing only if a 2.1 consumer actually needs component-level structure maps.

## Note

None of the six was reachable from any fixture in the tree. That is the same structural blind spot as #225: a round-trip test compares an author-written list of fields, and these paths were never on anyone's list.

### 2026-08-20

**Closing — verified complete.**

Audited against current `main`.

The issue's own burn-down list is empty: `KNOWN_INVALID` in
`tests/unit/test_wire_conformance_gate.py` is `{}`, and that file's docstring
says the milestone closes when it is. Entries there are asserted *still broken*,
so an empty dict is positive evidence rather than an absent list.

The one item left open in the description — "SDMX-ML 2.1 cannot carry a
StructureMap" — was resolved by #242. `model/validation.py` records the reason
in place:

> `structure_maps` was here until #242. The reason given was that 2.1's
> ComponentMap `<Ref>` needs a class/package/containerID "that ComponentMap does
> not carry" — true of the model, false of the message: all three are
> recoverable from the structure the map names. `_check_structure_map_in_21` now
> refuses only the maps whose structure is genuinely out of reach.

So the modelling gap this issue identified turned out not to be one, and the
narrower refusal that replaced the blanket one is in place.

The closing note in the description — that none of the six was reachable from
any fixture, "the same structural blind spot as #225" — is the thread that led
to #354's field census and the real-world corpus in !407. That blind spot is now
guarded generally rather than per-defect.
