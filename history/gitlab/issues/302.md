Four DSLs compile the same filter language to SQL. Two of them are tested differentially against an independent oracle; one has four properties and no oracle; one has nothing.

| DSL | statements | properties | oracle |
| --- | --- | --- | --- |
| `code_query` | 376 | 48 | `tests/support/oracle.py` |
| `hierarchy_query` | 394 | 47 | `tests/support/hierarchy_oracle.py` |
| `artefact_query` | 339 | 4 | none — compares against a resolved Python list |
| **`metadata_query`** | **289** | **0** | **none** |

`metadata_query` has 22 hand-written unit tests and nothing generative. That is the same order of size as the two files CLAUDE.md singles out for differential testing, and the reasoning there applies unchanged: it compiles a filter DSL to SQL and runs it in DuckDB, so an expected-result assertion is read off the implementation while an oracle is derived independently.

## Why this is worth doing now rather than as a general "more tests" wish

The gap has already cost something twice, both times found only by accident:

1. **#222.** `metadata_query` picked up the new case ladder through the shared emitter and got only two hand-written assertions. Nothing generative covers `.caseless` there.
2. **!292, this week.** `artefact_query`’s one label property drew needles and labels from the same single-case vocabulary, so `.lower()` on both sides was a no-op. It went on asserting the *pre*-#222 case-insensitive semantics after #222 removed them, stayed green through a 20x run, and was caught only because a probe was pointed at it by hand.

The second is the important one: a property that exists is not a property that discriminates. Whatever is written here has to be measured, per rule 4.

## What the oracle has to model

`metadata_query` is not a third copy of the other two. Its row is a *reported attribute value*, and its shape is genuinely different:

- `path` — a dotted attribute path, filtered with `starts_with` in the documented idiom (`QUALITY.`). Hierarchical, so prefix matching has real semantics rather than being incidental string work.
- `value` **and** `value[lang]` — a scalar column and a localised one, selected by a `value_kind` discriminator. A query reading one silently misses half the rows; `test_scalar_and_localised_values_are_separate_fields` pins this by example only.
- `sibling_index` — repetition is expressed as sibling entries with the same id, never a values list. There is no counterpart in the other two DSLs.
- `set_urn`, `kind`, `target` — `target` reaches a side table, so it is a non-`ColumnRef` and cannot be ordered or projected (#259).
- No tree. There is no `parent_id`, no `depth`, no `ancestor_ids` — so the bake-checking side effect that makes the other two oracles doubly valuable does not apply, and the oracle is correspondingly simpler.

## Rules that carry over

From CLAUDE.md, and each was paid for:

1. **No shared code with `metadata_query`, and none with the two existing oracles.** Restate the lookalike parts. Two oracles sharing a helper can be wrong the same way — the one failure mode differential testing cannot catch.
2. **Model what the library does, not what it should.** Where it surprises, cite the issue. The annotation-style existence scoping and the `value` / `value[lang]` split are the likely candidates.
3. **Every predicate kind gets a property, and the count is asserted** — a `test_every_predicate_kind_is_covered` enumerating `Predicate` subclasses off the module, as both existing files carry.
4. **Measure that the strategy discriminates before trusting the green.** Concretely, given !292: draw case-mutated needles, make `sibling_index` actually vary, and make generated paths share prefixes so `starts_with` can distinguish. A strategy where every path is unique makes prefix matching equivalent to equality.

## Scope question to settle first

Whether `artefact_query` is in scope. Its four properties compare the SQL against filtering a resolved Python list, which is a weaker oracle than the other two have but not nothing, and !292 has just fixed its one known blind spot. Doing both together would let the two new oracles be written by the same reading of the rules — which rule 1 says is exactly what to avoid. Probably: `metadata_query` here, `artefact_query` separately if at all.
