# Issue #243: enumeration_format is written and read only in 2.1, silently dropped elsewhere

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Milestone | %12 Cross-version conversion: convert what converts, refuse only what cannot |
| Labels | `bug` |

`Component.enumeration_format` was added in !239 and wired into the **SDMX-ML 2.1** reader and writer only. The 3.0, 3.1 and SDMX-JSON paths neither read nor write it, so the value is silently dropped on those targets.

This is an unfinished change of mine, not a format limitation. It was wired for 2.1 because that is where the document-fidelity harness pointed — the ECB data structure carries fourteen of them — and the other formats were never done.

## Evidence

```
grep enumeration_format src/sdmxlib/formats/sdmx_ml30/{writer,reader}.py
grep enumeration_format src/sdmxlib/formats/sdmx_json/_structure_dto.py
    (no matches)
```

and the cross-version measurement, where it is the entire remaining loss on the two fixtures that survive the trip:

```
ecb_data_structure.xml   2.1 -> 3.0 -> 2.1:  14 lost <EnumerationFormat>, 1 changed
```

## The formats all support it

`RepresentationType` is `TextFormat | (Enumeration, EnumerationFormat?)` in 2.1, 3.0 and 3.1 alike. SDMX-JSON declares `enumerationFormat` on five representation types:

```
ConceptRepresentationType, MeasureRepresentationType,
MetadataAttributeRepresentationType, AttributeRepresentationType,
SimpleDataStructureRepresentationType
```

So nothing here is a downgrade hazard or a modelling question — it is the same field, in four places, three of which were skipped.

## Work

1. `formats/sdmx_ml30/writer.py::_write_representation` takes the facet and emits `<str:EnumerationFormat>`; the 3.1 writer shares that shape. The 2.1 side already routes through `WriterHelpers.write_text_format(..., tag="EnumerationFormat")`, which is reusable.
2. The 3.0/3.1 readers call `WriterHelpers.read_enumeration_format`, which already exists and is already used by 2.1.
3. SDMX-JSON: add the field to the representation DTOs and both directions of the conversion.
4. Extend the generative round-trip property so a component carrying *both* an enumeration and a format is generated — the strategies currently produce one or the other, which is why nothing caught this.

Point 4 is the one that matters beyond this fix: the same-version harness did not catch the 3.0 gap because no generated artefact had the pairing, and no 3.0 fixture carries one either.
