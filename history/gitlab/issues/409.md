# Issue #409: scan_csv requires the DSD the file already names — no path from an SDMX-CSV message plus a registry to a Dataset

| | |
| --- | --- |
| State | closed |
| Opened | 2026-09-28 |
| Closed | 2026-09-28 |
| Labels | `api`, `data`, `enhancement`, `usability` |

An SDMX-CSV 2.0 message names the dataflow it belongs to, in every row:

```
STRUCTURE,STRUCTURE_ID,ACTION,AREA,TIME_PERIOD,OBS_VALUE
dataflow,AGENCY:DF(1.0.0),I,CA,2020-01,1.0
```

The reader already reads it — `_peek_dataflow_id` pulls `STRUCTURE_ID` off the
first row and builds an unresolved `Ref[Dataflow]` from it. But `scan_csv`
requires the `DataStructure` as a positional argument, so a consumer has to know
which DSD the file needs *before* opening it. The file's own answer is only
available after you have supplied it.

## Repro

```python
import inspect
import sdmxlib as sl, sdmxlib.polars as slpl
from sdmxlib.formats.sdmx_csv.reader import _peek_dataflow_id

inspect.signature(slpl.scan_csv)
# (source: 'str | Path | bytes', structure: 'DataStructure') -> 'Dataset'

_peek_dataflow_id("data.csv")
# 'AGENCY:DF(1.0.0)'   <- the file knows

reg = sl.InMemoryRegistry()
sl.read("structures.xml", registry=reg)
# ...and the registry knows how to resolve that, but scan_csv takes no registry.
```

## What a consumer ends up writing

Holding a structure message and a directory of SDMX-CSV files, the join between
them has to be restated by hand:

```python
ds = slpl.scan_csv(out / f"{flow_id.lower()}.csv", message.dataflows[flow_id].structure())
```

The `flow_id -> filename` convention is the consumer's own, which is fine — but
`flow_id -> DataStructure` is not; it is in the file and in the registry, and
the library can do it. With five flows this is mild. It stops being mild when
the files come from somewhere that does not follow your naming convention, or
when you are handed one file and asked what it is.

## Suggested fix

```python
slpl.scan_csv(path, registry=reg)      # resolve STRUCTURE_ID -> Dataflow -> DSD
slpl.scan_csv(path, structure=dsd)     # unchanged
```

`structure` becoming optional when a `registry` is given. Errors worth
distinguishing: no `STRUCTURE_ID` column (SDMX-CSV 1.0 `DATAFLOW`, or neither),
a `STRUCTURE_ID` the registry cannot resolve, and a resolved `Dataflow` whose
`structure` is `None`.

`STRUCTURE` also carries the reference kind — `dataflow`, `datastructure` or
`dataprovision` per the spec — so a complete resolver would honour that column
rather than assuming a dataflow. Today only `dataflow` appears to be
considered.

## Smaller, related

`write_sdmx_csv` takes `structure_id` as a pre-formatted string, so every caller
writes the short URN by hand:

```python
structure_id=f"{flow.agency_id}:{flow.id}({flow.version})"
```

`artefact_urn` gives the long form and there is no short-form helper in the
public API. Either `write_sdmx_csv` could accept the `Dataflow` directly, or a
`short_urn(artefact)` would be generally useful — the same string is what
`STRUCTURE_ID` is parsed back out of by `parse_dataflow_id`, so the format is
already owned by the library on the read side.
