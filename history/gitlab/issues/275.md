# Issue #275: q-2: projection and aggregation — why sdmx.code is hand-queried 29 times despite having a DSL

| | |
| --- | --- |
| State | closed |

`sdmx.code` has a query DSL and is still the most hand-queried table in the consumer repos — **29 sites**. The reason is not that the DSL is missing; it is that `collect()` returns whole `Code` objects and `ids()` returns one column, and there is nothing between.

## What consumers write instead

```sql
-- projection: two columns, no object construction
SELECT code_id, depth FROM sdmx.code WHERE codelist_urn = ?

-- projection with a label fallback
SELECT c.codelist_urn, c.code_id, COALESCE(c.name[?], c.code_id) AS label

-- aggregation
SELECT level_id, COUNT(*) AS n FROM sdmx.hierarchy_node GROUP BY level_id ORDER BY n DESC
SELECT codelist_urn, COUNT(*) AS n FROM sdmx.code GROUP BY codelist_urn

-- facet counts: the canonical catalog-search query
SELECT c.code_id, COUNT(DISTINCT d.identifier) AS cnt FROM ... GROUP BY c.code_id

-- array aggregation
SELECT c.code_urn, list(a.title) FROM sdmx.code c JOIN sdmx.annotation a ...
```

`collect()` on a 50k codelist to count by level builds 50k `Code` objects to produce one integer.

## Proposal

Two capabilities, in this order:

**Projection.** `select(...)` returning frames rather than objects — a Polars `DataFrame` is the natural result given `sdmxlib.polars` already exists:

```python
cl.codes.select(code.id, code.depth)                  # -> pl.DataFrame
cl.codes.select(code.id, code.name["en"])
```

**Aggregation.** `count()` as the minimum, `group_by(...).agg(...)` as the shape:

```python
len(cl.codes)                                # already exists
h.nodes.group_by(node.level).count()         # -> pl.DataFrame
```

`len()` already runs `SELECT COUNT(*)`, so the plumbing exists for the scalar case; what is missing is grouping and projection.

## The design question this forces

`CodeQuery` is a frozen record with fixed slots — `predicates`, `sort_keys`, `limit_n`, `annotation_types`. That works because the shape is fixed: `Limit(Sort(Filter(Scan)))`. **Adding `Project` and `Aggregate` breaks it**, because an aggregate changes the *type* of the result and what may follow it: you cannot `sort_by(code.name)` after grouping by level, and `collect()` no longer returns `Code` objects.

That is exactly where a record stops paying and a node tree starts, and it is the concrete evidence #273 was waiting for. Do not design the IR to accommodate this in the abstract — implement it and let the shape of the difficulty decide.

A cheaper intermediate worth pricing first: return a `pl.DataFrame` from a terminal `select`/`agg` and forbid further composition after it. That keeps the record, gets applications off raw SQL, and defers the tree. It may be enough.

## Test gates

- Differential: projection returns the same values the oracle reads off the artefact; aggregation matches a Python `Counter` over it.
- `select()` emits only the requested columns — assert against the emitted SQL, since the point is not building objects.
- No behaviour change to `collect()` / `ids()` (`sql_corpus` diff empty for existing cases).
- Benchmarks: counting by level on a 10k codelist must not be within an order of magnitude of `collect()`-then-count, or it has not solved the problem.
- **Cookbook**: a section on projections and counts, driver-tested. This is the most-bypassed table in the repos; the documented example is what determines whether applications stop writing SQL.
