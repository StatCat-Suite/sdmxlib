# Issue #257: dsl-7: structural AST invariants over every emitted SQL (DuckDB runs multi-statement input)

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-10 |
| Milestone | %13 Query DSLs: properties and mutation for the half the suite skipped |
| Labels | `dsl`, `tests` |

Every SQL string the library emits should satisfy a handful of invariants regardless of which query produced it. We assert none of them today.

## The motivating measurement

DuckDB's `execute()` accepts multiple statements and runs them all:

```python
>>> c = duckdb.connect(":memory:"); c.execute("CREATE TABLE obs(geo VARCHAR)")
>>> c.execute("SELECT 1; DROP TABLE obs")
>>> "obs" in [r[0] for r in c.execute("SHOW TABLES").fetchall()]
False
```

That turns "one query in, one statement out" from ceremony into a real invariant, because `local/data_store._build_query` interpolates three caller-supplied strings verbatim:

```python
cols_sql = ", ".join(columns) if columns else "*"
sql = f"SELECT {cols_sql} FROM {plan.from_clause}"
...
sql += " WHERE " + " AND ".join(fragments)
sql += f" ORDER BY {order_by}"
```

`order_by: str | None` is on the public `DataStore.query` protocol, documented as "Optional SQL ORDER BY clause". `parse_components`'s own docstring says "The HTTP layer is expected to have already split the URL slice" — so sdmxlib is designed to sit behind an HTTP server, and a server forwarding a `sort=` query param into `order_by` has a statement-injection hole, not merely a value-injection one.

The `columns` / `where` interpolation is documented as caller-composed and is a deliberate escape hatch. `order_by` is not obviously in the same category, and the docstring does not say it is.

## Scope

Add `sqlglot` to the `dev` dependency group (test-only — it must not reach the runtime deps) and a `tests/support/sql_ast.py` with a small set of corpus-wide assertions:

- **`assert_single_statement`** — `len(sqlglot.parse(sql, dialect="duckdb")) == 1`. The one motivated by the measurement above.
- **`assert_no_literals_in_predicates`** — no `exp.Literal` anywhere under `exp.Where`. Every user value must arrive as a bind parameter. This is the injection suite in its strongest form: the assertion is not "the value was escaped" but "the value never reached the SQL text."
- **`assert_only_known_tables`** — table names under the tree are a subset of an allowlist. Catches identifier interpolation and schema-remapping bugs (`ctx.schema()` is a documented remap point).

Drive all three from the existing generative strategies: `forest_codelists`, `forest_hierarchies`, `codelist_with_hierarchy`, plus the data-plane filters from #258. `to_sql()` exists on `CodeQuery`, `HierarchyNodeQuery` and `ComponentFilter`, so the corpus is cheap to assemble.

## What NOT to take from the proposal this came from

The proposal argues that parsing with sqlglot "is itself the primary assertion: if `parse_one` raises, the builder emitted garbage." That is *weaker* than what the query DSLs already have — #248/#249 **execute** every generated query against real DuckDB, and executing subsumes parsing. Do not re-motivate this work as a parse check; its value is the three structural invariants above, and `assert_single_statement` is the one that pays for the dependency.

Likewise: no SQL golden files, normalised or otherwise. `norm()`-and-compare has the same failure mode as a golden file — it passes when the semantics are wrong — and the differential properties already cover semantics far better.

## Relationship to #250

#250 (hostile filter values) proposed a narrower version of the literals check: build the same query with a benign and a hostile value and assert the emitted SQL is byte-identical. That works and needs no dependency, but only proves the *one* value under test didn't leak. The AST form generalises it to "no literal anywhere in any WHERE we can generate."

Do #250 first — it is the semantic half (hostile values must still *match correctly*, which the AST check says nothing about) — then fold its structural assertion into this one rather than keeping both.

## Test gates

- The three invariants run over every query the existing strategies can produce, in both structural DSLs and the data plane.
- A decision recorded on `order_by`: either it is documented as trusted-caller-only in the same terms as `columns` / `where`, or it is validated. Silence is the current state and is the actual defect.
- `sqlglot` appears in `dev` only; `just check` confirms it is absent from the runtime dependency set.
