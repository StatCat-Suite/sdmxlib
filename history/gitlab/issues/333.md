# Issue #333: InMemoryRegistry claims Registry conformance it does not need

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-18 |
| Closed | 2026-08-19 |
| Labels | `design` |

`InMemoryRegistry`'s docstring says it "satisfies the `Registry` Protocol via
`get(urn)`". It is not a source of artefacts — it is **the interning table the
format readers use while parsing**, so that `Ref`s within one message point at
the same objects:

```python
# formats/sdmx_ml21/reader.py, formats/sdmx_json/reader.py
def read(data: bytes, *, registry: InMemoryRegistry | None = None) -> StructureMessage
```

`formats/` takes it **concretely**, not through the Protocol, so the
conformance claim buys nothing and is never exercised.

## Why it matters

It is most of what makes the read seam look like a heterogeneous catch-all.
The implementers of `RegistryReader` / `SupportsGet` currently read as
"a store, a service, a router, an identity map, and a dict" — which invites the
conclusion that the seam is shaped by its weakest member. Drop the claim and
they are a store, a service, and a router.

Surfaced while working through `docs/design/registry-and-catalog.md` §5.10,
where the objection was raised directly: the SDMX IM is universal, so why is
the source layer a catch-all? Largely because of this one line.

## Change

- Drop the Protocol claim from the docstring, and any `RegistryReader`
  annotation that relies on it.
- Keep `get` / `get_all` — the readers use them; they just are not a registry.
- Consider whether the name should say what it is (an interning table).
- `RestRegistry.registry` and `Registry.to_registry()` hand one out; check
  whether either caller wants a source or an interning table.

## Comments

### 2026-08-19

**Closing as invalid — the premise does not hold.** Checked against the code
before acting, per the lesson recorded on #335.

The issue's supporting argument is true but narrower than its conclusion. It is
correct that `formats/` takes `InMemoryRegistry` **concretely**:

```python
def read(data: bytes, *, registry: InMemoryRegistry | None = None) -> StructureMessage
```

so the reader path does not exercise the Protocol. But the reader path is not
the only caller, and the conformance is exercised elsewhere — as a real
capability, not a test artefact:

* **As a federation source.** `FederatedRegistry.__init__` declares
  `routing: dict[str, RegistryReader]`, and `tests/unit/test_federated_registry.py`
  passes `InMemoryRegistry()` as a routed source throughout — including the
  composition test where one federation is a source inside another. An
  in-memory artefact set is the natural way to stand up a federation without a
  database or a network, and dropping the claim would remove that.
* **As a user-facing registry.** `docs/cookbook/local_files.md` loads files
  into one and calls `reg.get(urn)` — registry behaviour, documented.
  `docs/api.md` groups it with `RestRegistry` and `FederatedRegistry` for the
  drift methods.

So the docstring's "Satisfies the `Registry` Protocol via `get(urn)` and
`__contains__(urn)`" is accurate and load-bearing.

## What survives

The *concern* behind the issue — that the read seam reads as a heterogeneous
catch-all — is fair, and §5.10 in the design doc is where it belongs. But the
answer is not "`InMemoryRegistry` is not a registry", because it demonstrably
is one: it stores artefacts by URN, answers `get`, and can be routed to. If the
seam is too wide, the case has to be made about the seam rather than about this
member.

The naming question the issue raises last ("consider whether the name should
say what it is") is likewise unaffected: it is *both* an interning table and an
in-memory registry, and the current name says the half that is public API.

Not closing #334, which is unrelated and unexamined.
