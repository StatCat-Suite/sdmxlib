# Issue #264: dsl-14: no offset or cursor — pagination is only reachable via the raw-SQL escape hatch

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `dsl`, `needs-design`, `type::feature` |

Both query DSLs have `limit(n)`. Neither has `offset` — so there is no way to ask for the second page of anything.

This is already acknowledged in the codebase, as a reason to leave the DSL:

> `local/sql.py`: "This module is the supported escape hatch for consumers that build their **own** SQL against the store's DuckDB connection (per-value `printf` formatting, Hive-partition-pruning filters, wide pivots, **Range pagination** — things the high-level query methods don't express)."

So the gap is known and the current answer is "drop to raw SQL". This issue is to decide whether that is the right answer, not to assume it is not.

## The case for building it

`CodeQuery.__getitem__(int)` already emits `LIMIT 1 OFFSET ?`, so the capability exists in the module — it is just not reachable from the composable surface. A large codelist (CL_GEO-scale) behind an HTTP endpoint is the obvious consumer, and it is precisely the case where dropping to raw SQL means the caller re-implements table naming, the sidecar join and the URN scoping that `QueryPlan` exists to encapsulate.

## The case against, which needs answering first

`OFFSET` is the wrong pagination primitive at scale — cost grows with the offset, and rows shift under concurrent writes. **Keyset pagination** (`WHERE (sort_key, id) > (?, ?) ORDER BY sort_key, id LIMIT n`) is the standard answer, and it composes badly with an arbitrary user-supplied `sort_by` chain unless the sort keys are constrained.

Both DSLs already append a deterministic tiebreak — `c.position NULLS LAST, c.code_id` for codes, `hn.node_id` for nodes — which is exactly the stable total order keyset pagination needs. That is a meaningful head start and worth noting when weighing the options.

So the decision is:

- **A. `offset(n)`.** Trivial, matches `limit`, honest about its cost. Adequate for a UI paging through a few hundred codes, which is the realistic size of a codelist.
- **B. Keyset / cursor pagination.** Correct at scale, more API surface, and needs a rule about which sort keys are permissible.
- **C. Neither — document the escape hatch as the answer** and cross-reference `local/sql.py` from the query DSLs' docstrings, which today do not mention it.

Codelists and hierarchies are bounded artefacts — thousands of rows, not millions — so A is probably right for the structural DSLs and B is the question for the data plane, where `DuckDBDataStore.query` sits in front of observation tables that genuinely are large. Splitting the answer by layer is a legitimate outcome.

## Scope

- Decide A / B / C, per layer, and record the reasoning.
- If A: `offset(n)` on both `CodeQuery` and `HierarchyNodeQuery`, parameterised (`OFFSET ?`) like `limit` already is — see the comment on `limit` about `int()` casts standing in for bind parameters.
- Whichever way it goes, cross-reference the escape hatch from the DSL docstrings. A reader of `CodeQuery` has no way to discover `local/sql.py` today.

## Test gates

- If A: `limit(n).offset(m)` is the `[m : m+n]` slice of the unlimited ordered query — stated as a slice rather than a length, so an `OFFSET` applied before the `ORDER BY` fails.
- Offsets past the end return empty, not an error.
- Interaction with `sort_by` asserted, since the tiebreak is what makes the page boundary stable.
- Composition semantics agreed with #260, which is settling the same question for `limit` (last-wins today, undocumented).

## Comments

### 2026-08-10

## Decision (recorded from the design review)

**A for the structural DSLs, B stays a data-plane question, and the composition law is `max`.**

### A vs B, settled by measurement

DuckDB, `sdmx.code` with the real schema, median of 40 runs, 50-row pages:

| rows | page 1 | mid page | last page | keyset last |
| --- | --- | --- | --- | --- |
| 1 000 | 322 us | 357 us | 397 us | 326 us |
| 10 000 | 402 us | 460 us | 467 us | 377 us |
| 100 000 | 1 232 us | 2 263 us | 2 464 us | 864 us |
| 1 000 000 | 2 725 us | 7 745 us | 10 519 us | 538 us |

OFFSET only diverges past ~100k. At 10 000 rows — above NUTS (~2 000) and most product classifications — the last page costs 90 us more than keyset. Codelists, hierarchies, the artefact spine and reported metadata are all bounded well below that, so **A**. Keyset (**B**) remains the right question for `DuckDBDataStore.query` over observation tables, which genuinely reach millions; that is not this issue.

### Composition: `max`, not accumulate, not last-wins

The issue asked to agree this with #260 (`limit` is a cap). The reasoning turned out to depend on a question nobody had asked: **is this DSL a pipeline or declarative?** Measured:

```
sdmxlib  q.filter(even).limit(3) -> [C0, C2, C4]
sdmxlib  q.limit(3).filter(even) -> [C0, C2, C4]     same
polars   lf.filter(ev).head(3)   -> [C0, C2, C4]
polars   lf.head(3).filter(ev)   -> [C0, C2]         different
```

Every method here contributes a clause to one `SELECT`; call order never matters. polars wraps the previous frame. So `limit(5).limit(10) == 5` agreeing with polars was a **coincidence** — ours is a cap constraint, theirs is a pipeline stage.

Given that, the window model is: a query owns `[start, start+length)`, and

```
offset(n):  start  <- max(start, n)     raises the floor
limit(n):   length <- min(length, n)    lowers the ceiling
```

Both monotone, both idempotent, both order-independent. `max` is the unique law under which `offset` refines *and* stays order-independent. The cursor reading (accumulate) is the pipeline reading, and we measured we are not a pipeline.

Prior art, all verified rather than recalled — the split is by **API shape**, not by library:

| library | spelling | composition |
| --- | --- | --- |
| Django 6.1 | `qs[5:15]` | accumulates; **but `qs[:5,:10]` clamps to 5** |
| elasticsearch-dsl | `s[5:15]` | accumulates |
| polars 1.43 | `.slice(5, 3)` | accumulates |
| ibis 12 | `.limit(n, offset=m)` | accumulates (nests a subquery) |
| SQLAlchemy 2.0 | `.offset(n)` | last-wins |
| peewee 4.3 | `.offset(n)` | last-wins |

Slice-shaped APIs accumulate; setter-shaped APIs replace. Nobody uses `max`. But Django — the largest declarative builder in Python — **clamps its limit exactly as #260 does**, so SQLAlchemy is the outlier on last-wins, not us. Its `.offset()` is a slot on a statement object, not a considered composition law; the tell is `where(None)` compiling to `AND NULL`.

Slicing (`q[5:15]`) was considered and rejected: it is the only pipeline-flavoured spelling in an otherwise declarative surface, and `q["FR"]` already means something else.

### Scope

`offset(n)` on **all four** query classes, not the two the issue names — #276 added the artefact spine and #281 the metadata values, and the catalogue is the paging case the issue actually motivates. Parameterised `OFFSET ?`, guarded like `limit` (`check_offset`).
