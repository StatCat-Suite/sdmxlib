# Issue #321: a timezone-aware valid_from/valid_to round-trips to a different instant, naive

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-17 |
| Closed | 2026-08-17 |
| Labels | `storage`, `type::bug` |

Found by the derived round-trip guard (#316) on its first run.

```python
Codelist(..., valid_from=datetime(2021, 2, 3, 4, 5, 6, tzinfo=UTC))
# stored, then read back:  2021-02-02 23:05:06   (naive)
```

Two things go wrong at once, and the second hides the first:

1. **The instant changes.** DuckDB's `TIMESTAMP` has no zone, so a tz-aware
   value is converted to the *session's* local time on write. On this machine
   (UTC-5) `04:05:06Z` came back as `23:05:06` the previous day.
2. **`tzinfo` is dropped**, so the value that comes back is naive and compares
   unequal to what went in without announcing why.

Because the conversion uses the *session* timezone, the same database read on a
machine in another zone yields a different answer. That is worse than a
constant offset: it is not reproducible across readers.

## Affected

Every maintainable — `valid_from` and `valid_to` are on the base. 34 of the 231
fields across the persistable types are one of these two.

## Options

- `TIMESTAMPTZ` (DuckDB has it) plus a schema migration. Stores an instant and
  returns one; the honest fix.
- Normalise to UTC on write and re-attach UTC on read. No schema change, but it
  silently rewrites a caller's zone, and a naive input then means something
  different from a UTC one.
- Refuse a tz-aware value. Cheapest, and wrong — SDMX `validFrom` is an
  `xs:dateTime`, which permits an offset.

The first looks right. Worth checking what the readers/writers of the wire
formats do with the offset first, so all three agree.

## Gates

Round-trip a tz-aware value, a naive value and a non-UTC offset, and assert the
instant is preserved in each case. The #316 guard covers the first once fixed.
