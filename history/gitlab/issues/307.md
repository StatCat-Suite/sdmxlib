# Issue #307: Concept.parent is parsed and silently dropped — nested concept schemes come back flat

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-13 |
| Closed | 2026-08-14 |
| Milestone | %17 Query DSL: a second backend, and the evidence the first one lacks |
| Labels | `bug`, `model`, `storage` |

SDMX-ML 2.1 and 3.0 both allow `<str:Parent>` on a `Concept` (2.1: `common:LocalConceptReferenceType`; 3.0: `common:SingleNCNameIDType`, both on `ConceptBaseType`). We parse the element and throw it away.

## What happens

```python
# a scheme where PRICES is a child of ECON
msg = sl.parse(xml)
[c.id for c in msg.concept_schemes[0].concepts]   # ['ECON', 'PRICES']
# ...and nothing on either concept records the parent — Concept has no such field
```

So a scheme whose concepts nest comes back flat, on read **and** on round-trip write.

## Why it looks half-implemented rather than deliberate

`sdmx.concept` already has a `parent_id` column. The writer hardcodes `None` into it (`put_concept_scheme`), nothing reads it back, and `Concept` has no parent field. The DDL implies a capability the model never gained, which is how this went unnoticed — an un-populated column is an absence, and absences do not fail tests. Found by inventory while sweeping for un-wired traversals (%306), not by anything failing.

## References

- **sdmx1** models it: `Concept` inherits `Item`, which has `parent`/`child`.
- **pysdmx** flattens it: `Concept` has no parent at all.

We currently sit with pysdmx, but by accident rather than by decision, and the silent drop is a defect under either reading.

## Scope

- `Concept` gains a parent field (`parent_id`, matching `Code`/`Category`, rather than nesting — the storage column already assumes that shape)
- both format readers (`formats/sdmx_ml/_common.py`, `formats/sdmx_json/_structure_ingest.py`) and both writers
- writer populates `concept.parent_id`; add `depth`/`ancestor_ids` to the bake if the tree paths are wanted
- then `q.concept` can wire `parent`/`children` (+ `ancestors`/`descendants` once baked) like `q.code` and `q.category`

Until then, `concept.parent_id` is listed in `NOT_EDGES` in `tests/unit/test_query_edges.py` with this reason, and `docs/design/query-tree-paths.md` §7 records it.

## Note

`_Concept` had acquired `ancestors`/`descendants`/`children` annotations copied from `_Code` — no edges, no binding, so they type-checked and raised `AttributeError`. Removed in 366b6a9; not part of this issue.
