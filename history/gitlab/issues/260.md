#248 / #249 asserted the algebraic laws that need no oracle: filter idempotence, commutativity, ordered-subset, roots/non-roots partition, ancestor/descendant inversion, hop-bound monotonicity. Three more are cheap now that the strategies exist, and each targets a distinct bug class the current set does not.

## The laws

**1. Neutral element — `filter(p)` on an unfiltered query equals `filter(p)`.** Trivial as stated, but the real content is the *zero-predicate* case: a query with no predicates must compile to a `WHERE` containing only the artefact-urn scope, not to `WHERE` with a dangling `AND`, and not to `WHERE TRUE AND ...`. Bad neutral-element folding is the classic empty-conjunction bug and nothing currently pins it.

**2. `In(d, [c])` ≡ `Eq(d, c)`.** For the data plane: a one-element OR-set and an equality must select the same rows. Builders routinely special-case the single-value path for an index-friendly `=` and let it drift. Belongs with #258.

**3. `limit(n).limit(m)` — decide what it means.** Today it is last-wins:

```python
def limit(self, n: int) -> CodeQuery:
    return attrs.evolve(self, limit_n=n)
```

so `q.limit(5).limit(10)` returns ten rows. The docstring says "Return a new query capped at `n` rows", which reads as a cap and would imply `min(n, m)`. Both are defensible — last-wins matches `attrs.evolve` semantics and is what a builder usually does; `min` matches the word "capped" and is what a caller composing two independently-written narrowings would expect. What is not defensible is that neither the docstring nor a test says which.

Same question for `sort_by`, which *does* accumulate (`sort_keys=(*self.sort_keys, sk)`) — so the two composition operators on the same class behave oppositely and neither documents it.

## Scope

- Add laws 1 and 3 to `tests/unit/test_properties_code_query.py` and `test_properties_hierarchy_query.py`; law 2 to the data-plane properties (#258).
- Resolve law 3 as a documented decision, then pin it. Prefer changing the docstring over changing the behaviour unless there is a reason — but say so either way.
- While in there: `with_annotations()` also replaces rather than accumulates. Same question, same answer required.

## Explicitly not included

The proposal that prompted this also lists `Not(Not(x)) ≡ x` and De Morgan. Neither query DSL has a `Not` combinator — negation is a per-field flag (`_Eq(negate=True)`), not a wrapping node — so there is nothing to apply them to. The only `__invert__` in the codebase is `model/expr.py`'s `ItemPredicate`, which filters in memory and never becomes SQL; double-negation and De Morgan for *that* belong to #251.

## Test gates

- The three laws asserted as properties, over the existing strategies.
- `limit` and `with_annotations` composition semantics documented on the methods and pinned by an example test, so the docstring and the behaviour cannot drift apart again.
