`code.id == "A"` exists. There is no way to say `code.id in ("A", "B", "C")`.

## The gap

Neither query DSL has a set-membership operator. `grep` for `is_in` / `one_of` / `in_` across `code_query.py` and `hierarchy_query.py` returns nothing. The available operators on a string ref are `==`, `!=`, `contains`, `starts_with`, `ends_with`, `is_null`, `is_not_null` — all single-valued.

Selecting a handful of codes is *the* everyday SDMX filter. Today the options are:

- run one query per code and union in Python, losing the lazy `SqlRelation` composition that `CodeQuery.to_sql()` exists to provide;
- abuse `contains`, which is wrong (and accent-folded on the codelist side, per #255);
- drop out of the DSL and write SQL against `store.connection`.

The data plane already has this: `ComponentFilter` treats a list as an OR-set and emits `col IN (?, ?, ...)`. The structural DSLs, which are the ones users are pointed at in `CLAUDE.md`'s "Common patterns", do not.

## Why this is separable from #262

Full `And` / `Or` / `Not` composition is a design question with a real prerequisite (#254 — annotation predicates must stop emitting JOINs before anything can go under an `OR`). `is_in` needs none of that: it is a single predicate compiling to one `IN (...)` fragment, conjunctive like every other predicate, and it composes with the existing `filter()` chain unchanged.

It also covers the majority of what people reach for `Or` to do. Land it first.

## Scope

- `_StringRef.is_in(values: Sequence[str]) -> Predicate` on both DSLs, plus the numeric `_DepthRef`.
- New `_InSet` predicate kind; emitters in both compilers. Note both files' `test_every_predicate_kind_is_covered` will fail until it has a property — that is the guard working.
- **Decide the empty case before writing the emitter.** `is_in([])` must not emit `IN ()`, which DuckDB rejects — the same defect as #256, and the decision should match whatever #256 settles on. Get #256 decided first, or decide both together.
- `is_in` on an annotation field goes through the same JOIN as `==` today, so it inherits #254's row duplication. Sequence after #254 or accept that the xfail covers it.
- Consider accepting a `SqlRelation` as well as a list, mirroring `ComponentFilter` — `code.id.is_in(other_codelist.roots())` compiling to `IN (<subquery>)` is the composition the `SqlRelation` protocol was built for.

## Test gates

- Differential property against the oracle: `is_in(vs)` selects exactly the codes whose id is in `vs`, for generated `vs` including empty, single, all, and values not present.
- **`is_in([c])` ≡ `== c`** — the law that catches a divergent single-value special case (#260 lists it).
- `is_in` of every id ≡ no filter.
- Empty case pinned by an example test, executing, not just compiling.
- If `SqlRelation` is accepted: params from the subquery splice in at the right position, asserted by the placeholder/param-count property from #258.
