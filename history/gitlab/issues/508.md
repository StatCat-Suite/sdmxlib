# Issue #508: add accepts artefacts every writer refuses (attachment=None, enumeration-format sentinel)

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-20 |
| Closed | 2026-10-21 |
| Milestone | %26 Found by the docs audit: correctness and refusals |
| Labels | `bug`, `conformance`, `model`, `needs-design`, `priority::medium` |

Two artefacts are accepted by the constructor and by `add`, then refused by every writer. That contradicts #419 ("`add` refuses what no format can write"):

1. `sl.Attribute(..., attachment=None)` in a DSD: `InMemoryRegistry.add_all` accepts it, and `to_xml` raises `ValidationError`.
2. A sentinel value on an `enumeration_format` facet: accepted, then refused by `check_serialisable`.

Whatever `check_serialisable` refuses for *every* format belongs in the construction-time rules (#492), so a store can never hold an artefact it cannot write.

**Fix:** move both rules to construction. Then add a test asserting that a rule `check_serialisable` applies to every target is also a construction rule, so the two lists can't drift.

Found in !665.

## Comments

### 2026-10-20

!670 fixed the sentinel half: a sentinel on an enumeration or coding format is now refused as the artefact is built.

**The attachment half is left open for a decision.** I measured moving `_check_attachment_stated` (an attribute or metadata-attribute usage with `attachment=None`) into the construction rules:

- `Attribute.attachment` and `MetadataAttributeUsage.attachment` default to `None`, so every hand-built attribute that doesn't state one would be refused as its DSD is built.
- That breaks 60+ tests, the whole `test_ml3_writer_parity` corpus, two doc pages (`federation.md`, `rest_facade.md`) and the `test_component_role` fixtures. Readers always set an attachment, so parsed data is unaffected; only hand-built DSDs are.

The options:
1. **Refuse at construction.** Consistent with #419 and #492, but it's the most breaking option: `attachment` effectively becomes required.
2. **The model holds a default meaning**, as #503 and #507 did: `None` becomes `AttachmentLevel.DATASET`. This reverses #421's decision to refuse rather than assume a relationship nobody stated.
3. **Leave it at write time.** The current behaviour: the store can hold a DSD that no writer will write.

Labelled `needs-design`.

### 2026-10-21

Decision: **attachment is required.** `Attribute.attachment` and `MetadataAttributeUsage.attachment` get no default, so building one without it is a `TypeError` at the call. Hand-built fixtures and doc pages gain an explicit attachment.
