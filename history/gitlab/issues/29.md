# Issue #29: Design: partial resolution caching in Session

| | |
| --- | --- |
| State | closed |
| Opened | 2026-04-01 |
| Closed | 2026-08-21 |
| Labels | `design` |

## Problem

`reg.get(sl.DataStructure, agency="ECB", id="ECB_EXR1").resolve(sl.Codelist)` always makes a fresh HTTP request. The `Session` only tracks two states per artefact:

- `_map` — ingested (any resolution depth)
- `_resolved_map` — ingested with `references=all`

Partial resolutions (`references=codelist`, `references=conceptscheme`, etc.) are intentionally not cached today — writing them to `_resolved_map` would be a bug (a subsequent `resolve()` call would return a partially-resolved object thinking it was fully resolved).

## Design challenge

We need a way to record *which* reference types were fetched for a given artefact, so that:

1. `resolve(sl.Codelist)` on a DSD is served from cache on repeat calls
2. `resolve()` (full) still correctly bypasses a partially-cached entry and fetches fresh

## Approaches to consider

**Track a set of resolved reference types per URN**

```python
_partial_map: dict[str, set[str]]  # urn_key -> {"codelist", "conceptscheme", ...}
```

A subsequent `resolve(sl.Codelist)` hits the cache if `"codelist" in _partial_map[key]`. A subsequent `resolve()` still fetches — unless all possible reference types are present, which is hard to know in advance.

**Track the references string used at fetch time**

Simpler: store the `references` string alongside the artefact. Cache hit only when the exact same references string is requested again. Misses for `resolve()` after `resolve(sl.Codelist)` even though the codelists are already in the session — but those are in `_map` anyway.

**Immutability makes merging hard**

The deeper issue: even if the session has both codelists (from a `references=codelist` fetch) and concepts (from a `references=conceptscheme` fetch) cached separately, the DSD objects from each fetch are different immutable instances. There is no way to return a single DSD object where both sets of refs are resolved without re-fetching with `references=all` or reconstructing the object graph.

This suggests the most practical cache key is the exact `(urn, references_string)` pair, not a smarter merged view.

## Current behaviour

Partial resolutions fall through to a fresh server fetch on every call. Correct but not cached. Documented in `Registry._fetch_one` docstring.

## Related

Introduced as a known limitation when implementing `GetQuery.resolve(reference_type)` and `Registry._fetch_one`.

## Comments

### 2026-08-20

**Audit note — the description is stale, the want survives, and there is a
second axis it did not know about.**

### What changed underneath it

The design here is written against `_map` + `_resolved_map`. `_resolved_map` no
longer exists: #344 replaced the boolean with an ordered `Completeness`
(`UNRESOLVED < PARTIAL < FULL`) on `api/session.py`, because a `detail=full`
fetch and a `detail=referencepartial` one set the same flag and the second was a
cache hit on the first. Reads go through `get_at_least(urn, completeness)`,
which returns `None` when what is held is shallower than what was asked.

So the *specific* trap this issue warned about — "writing partials to
`_resolved_map` would be a bug, a later `resolve()` would think it was fully
resolved" — is now structurally impossible. `FULL` satisfies a request for
`PARTIAL`; `PARTIAL` does not satisfy `FULL`.

### What is still missing

`Completeness` is a **depth**, not a **set**. It cannot express "codelists were
fetched but concept schemes were not", so `resolve=[sl.Codelist]` on a DSD still
does not hit a cache populated by an earlier identical call. That is this
issue's original ask and it is unaddressed. The `_partial_map: dict[str, set[str]]`
sketch in the description is still the obvious shape; it would sit beside
`_completeness` rather than replacing the thing the description names.

### A second axis, found while auditing #153

`completeness_of(detail=…, references=…)` keys on `references` first, so
`detail=allstubs, references=none` and `detail=full, references=none` both record
`UNRESOLVED`. That is right for the question `Completeness` asks — how deep were
references followed — and says nothing about whether the artefact's *own* content
was trimmed. A stub codelist and a full one are indistinguishable to the session.

The query layer does not rely on this: `Query._fetch_for` keys its own fetch on
the derived detail, and its docstring names the exact failure that guards
against. But a caller mixing `reg.get()` with the query path on one session has
no such protection.

So there are two independent axes the session flattens — *which reference types*
(this issue) and *stub versus full* (new). Worth solving together if either is
solved, since both are "what do we actually know about this URN".

### 2026-08-21

Closing as stale — the design this asks for shipped in #344, under a different shape than proposed.

The issue is written against `reg.get(sl.DataStructure, agency=…, id=…).resolve(sl.Codelist)` and against `Session._map` / `_resolved_map`. None of those exist now:

- `get()` collapsed `fetch()`, `resolve()` and the `GetQuery` into one entry point, and **partial resolution is a parameter**: `reg.get(urn, resolve=[sl.Codelist])`.
- `_resolved_map` — the boolean this issue identifies as unable to represent a partial resolve — was replaced by `Completeness`, an ordered `IntEnum`. Its docstring states the problem in this issue's own terms: it *"recorded that a URN had been fetched with its references and not how completely, so a `detail=referencepartial` fetch and a `detail=full` one set the same flag and the second was a cache hit on the first."*
- Compared with `>=`, so `FULL` satisfies a request for `PARTIAL` and not the reverse — which is the "record which reference types were fetched" requirement, answered as a level rather than a set.

Verified on `main` (`api/session.py`), not taken from the changelog.
