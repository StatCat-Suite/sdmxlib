# Issue #92: Design: TZ-aware storage of materialized_at / bound_at

| | |
| --- | --- |
| State | closed |
| Opened | 2026-05-31 |
| Closed | 2026-06-01 |

Standalone design issue — **not part of the Cleanup follow-ups milestone** (user wants to think about the shape first).

## Problem
\`DataflowBinding.materialized_at\` and \`bound_at\` are currently stored in DuckDB as \`TIMESTAMP\` (naive). The model side accepts naive datetimes; round-trip through storage strips any tzinfo.

The post-audit cleanup attempted a sweep to make test fixtures \`tzinfo=UTC\`-aware (drops a handful of \`# noqa: DTZ001\`), but the round-trip equality assertions broke because storage normalises to naive. The sweep was reverted; the DTZ001 ignores stayed.

\`grep -rn \"DTZ001\" tests/\` shows 16 sites — all the same shape:
\`\`\`python
materialized_at=datetime(2026, 4, 30, 12, 0),  # noqa: DTZ001
\`\`\`

## Design questions
1. **Schema:** migrate \`materialized_at\` / \`bound_at\` to DuckDB \`TIMESTAMPTZ\` (UTC-anchored)? Bumps \`SCHEMA_VERSION\` (drop-and-rebuild).
2. **Model:** does \`DataflowBinding\` constructor coerce naive → UTC, or require tz-aware? CLAUDE.md "no defaults" preference suggests require tz-aware.
3. **API impact:** federated catalog cookbook examples build bindings with \`datetime(...)\` literals; those would need \`tzinfo=UTC\`. Small ergonomic hit.
4. **Backwards compat:** binding records in user-built local registries would need a migration path or a rebuild.

## Out of scope (for now)
- \`valid_from\` / \`valid_to\` on maintainable artefacts are *spec*-level (SDMX validity period). These are documented as ISO8601 in the SDMX standard, which technically permits offsets but everyone uses Z. Same question applies but probably separate.

## Acceptance (when this is taken on)
- Schema bump.
- All \`# noqa: DTZ001\` in tests/ removed.
- Bindings round-trip a tz-aware datetime exactly.
- Cookbook and llms.txt updated.

## Comments

### 2026-06-01

Closed in MR !102.

Implemented with a model-layer-only fix rather than the schema migration originally contemplated:

- DuckDB's `TIMESTAMPTZ` Python read path requires `pytz`, which we didn't want as a hard dep.
- Model now requires tz-aware datetimes via a converter that raises on naive.
- Storage stays `TIMESTAMP` (unchanged schema): writer normalises to UTC + strips tzinfo; reader re-tags with UTC. Round-trip is exact for UTC inputs and instant-preserving for any tz-aware input (the original zone label is dropped, but the instant is preserved).
- All 16 `# noqa: DTZ001` sites in binding fixtures swept.
- Cookbook + module docstring updated.
