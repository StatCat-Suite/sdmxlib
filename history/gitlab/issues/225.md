# Issue #225: SDMX-ML 2.1 writer silently dropped metadataflows, MSDs and hierarchy associations

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-07 |
| Milestone | %10 Testing: audit, properties, and mutation |
| Labels | `bug` |

Found by the #223 spec-coverage matrix: a `StructureMessage` carrying a metadataflow, written as SDMX-ML 2.1, came back with none. No error, no warning — and the emitted document was schema-valid, so nothing downstream noticed either. The same held for `metadata_structures` and `hierarchy_associations`. The 3.0 writer emits all three.

## Done in !231

`check_serialisable` now **refuses** rather than losing them, so `serialize(msg, version="2.1")` raises with the field named and 3.0 suggested. Silent loss is the worst failure mode a serialiser has; turning it into a question the caller can answer is the priority fix.

The refusal list is justified behaviourally by `test_unwritable_in_21_lists_exactly_what_the_writer_drops`, which round-trips one artefact per entry through the raw writer. An earlier version of the list was assembled by grepping the writer for field accesses and wrongly named all four map types — the 2.1 writer emits every one of them.

## Still open

Two of the three are **unimplemented, not unrepresentable**. SDMX-ML 2.1's `<Structures>` has first-class `<Metadataflows>` and `<MetadataStructures>` children, so both can be lifted by writing the emitters:

- [ ] `<str:Metadataflows>` in the 2.1 writer + reader
- [ ] `<str:MetadataStructures>` in the 2.1 writer + reader

`hierarchy_associations` is different: 2.1 models the same information as `<HierarchicalCodelists>`, a different shape, so it needs a translation rather than an emitter. Lower value — 2.1 hierarchy consumers are rare and the mapping is lossy in both directions.

Removing an entry from `_UNWRITABLE_IN_21` without implementing the emitter will fail the behavioural test above, which is the intent.

## Comments

### 2026-08-07

Closed by !231 (stop the silent drop) and !238 (implement the 2.1 emitter).

**`<str:Metadataflows>` — done.** 2.1's `MetadataflowType` is a plain StructureUsage, so writer and reader mirror the existing Dataflow ones. Identity, name, description, annotations, validity dates and the MSD reference all round-trip. What 2.1 cannot carry is `targets` — it has no `<Target>` element, which 3.0 added and made mandatory — recorded in `KNOWN_GAPS` and asserted in both directions.

**`<str:MetadataStructures>` — the premise was wrong.** This issue recorded it as "unimplemented, not unrepresentable — lift by writing the emitter". It is not an emitter. 2.1's `MetadataStructureComponents` is `minOccurs="1"` and requires both a `<MetadataTarget>` and a `<ReportStructure>`, with the target requiring one of five target-kind children — the reporting layer SDMX 3.0 deleted and this model does not carry. Writing one means inventing a target kind and a report structure and discarding them on read.

Split into two follow-ups rather than left here, because they are different questions:

- #235 — writing: 3.0 → 2.1 → 3.0 is not an identity for an MSD. A modelling question; refusing is a legitimate answer.
- #236 — reading: a 2.1 document containing an MSD is silently discarded today. A present-tense defect with a clear fix, independent of #235.

`hierarchy_associations` stays refused for 2.1 as originally described: `<HierarchicalCodelists>` is a different shape needing a translation, and 2.1 hierarchy consumers are rare.
