### Re-run benches & compare to baseline

- [ ] Run the `bench/` suite from #77 against the fix branch.
- [ ] Compare to `bench/baselines.json`:

### Documentation

- [ ] `docs/concurrency.md` — new page:
  - **Read safety**: `Registry.get`/`get_all`/`codelist`/`code_map` and `DataStore.query_stream` are safe to call from multiple threads concurrently.
  - **Write safety**: `add`/`drop`/`replace` are single-threaded. Don't call them from multiple threads against the same `Registry`. The library does not guard against this.
  - **Cache model**: resolver cache uses FIFO eviction with lock-free reads. Hit/miss counters are approximate under concurrency.
  - **Known trade-off (punt from #78)**: FIFO instead of LRU. At realistic working-set sizes this should not matter, but if `resolve_cache_info()` ever reports poor hit rates against a hot working set that fits in cache, revisit and consider a lock-free LRU variant (e.g. clock-pro, or copy-on-write snapshot). File a fresh issue if observed.
  - **DuckDB connection-level ceiling**: even with per-call cursors, DuckDB serialises some internals at the connection level. Per-`Registry` throughput is bounded; deploy with one `Registry` per worker process for high concurrency. A connection-pool variant is not currently provided.
  - **`resolve_cache_size=0` escape hatch**: disables caching entirely; for users hitting unforeseen contention.
- [ ] Link the new page from the appropriate spot in `mkdocs.yml` and from the `Registry` class docstring.
- [ ] CHANGELOG entry under the next release: "Concurrent reads are now safe (#75). Writes remain single-threaded — see docs/concurrency.md."
