Blocks #271. Found while designing the value-set primitive there; the divergence is live today, not a consequence of that feature.

## Three handles, on one thread

```
reg.connection            0x10deda7b0     <- what local/sql.py tells callers to use
_query_common.cursor_for  0x104e07a30     <- what every DSL query executes on
storage.lazy._cur         0x10dfc5170     <- a SECOND thread-local cache, own cursor
```

`storage/lazy.py` keeps its own `_thread_local` + `_cur` alongside `_query_common`'s. Same purpose, two implementations, two cursors per thread — the duplication shape #267 existed to remove, missed because nothing depended on the two agreeing.

## They already disagree

Not hypothetical:

```
reg.connection    search_path='sdmx'
cursor_for        search_path=''
lazy._cur         search_path=''

after `SET search_path='main'` on cursor_for:
  reg.connection  'sdmx'      cursor_for  'main'      lazy._cur  ''
```

So custom SQL on `reg.connection` may write `code` unqualified, while the same SQL on a cursor needs `sdmx.code`, and a `SET` reaches exactly one handle. Registrations behave the same way — registering on any one handle is invisible to the other two.

Uncommitted writes are also invisible across handles, so a caller mixing custom-SQL transactions with DSL reads gets stale results with no signal.

## The docs point at the wrong one

`local/sql.py` documents `store.connection.execute(sql, [...])` as the supported custom-SQL path. That is the shared, non-thread-local object — the one #75/#80 stopped the library itself using. [DuckDB is explicit](https://duckdb.org/docs/current/guides/python/multiple_threads): `DuckDBPyConnection` is not thread-safe, use `.cursor()` per thread.

Measured, for the record: cursors from one connection **do** run concurrently (4 parallel queries = 1.32x a single one), so per-thread cursors cost no parallelism. A claim to the contrary circulates in search results and is wrong for 1.5.3.

## What peers provide that we do not

| library | mechanism | API | cleanup |
| --- | --- | --- | --- |
| SQLAlchemy | `scoped_session` | `.remove()`, `.configure()` | explicit, wired to request teardown |
| SQLAlchemy | `QueuePool` | `pool_size`, `max_overflow`, `timeout` | bounded, recycled |
| SQLAlchemy | `PoolEvents` | `connect` / `checkout` hooks | — |
| Django | thread-local `connections` | `close_all()`, `close_old_connections` on signals | explicit, signal-wired |
| sqlite3 | a guard, not a pool | `check_same_thread` -> `ProgrammingError` | n/a |
| **ours** | two thread-locals | none public | none |

## Scope

- **One handle** per (thread, store). Fold `storage.lazy._cur` into `cursor_for`.
- **A setup hook** — the `PoolEvents.connect` equivalent. Anything that must hold for *every* cursor (search_path, settings, registered relations) has nowhere to live today. This is the real #271 blocker, more than the threshold.
- **Explicit release**, so a thread-per-request server does not accumulate handles each holding state.
- **A misuse guard**, because the divergence is currently silent — sqlite3's `check_same_thread` is the model.
- **Observability**: how many handles are live.
- Repoint `local/sql.py` and decide what `reg.connection` means afterwards.

## Test gates

- One handle: `cursor_for(c) is lazy._cur(c)` on a thread.
- Session state (`search_path`, a `SET`, a registration) applied by the hook is visible to every query path.
- Release drops the thread's handle and a subsequent call builds a fresh one.
- Existing DSL behaviour and the `sql_corpus` output unchanged.

### 2026-08-11

## Design, settled

### `reg.connection` stays as it is

Stress-testing the obvious answer — make `reg.connection` thread-local, Django-style — found a hard objection: **`reg.connection` is currently a stable, capturable object and this repo depends on that.**

```
src/sdmxlib/local/data_store.py:207:   instance._conn = registry.connection
```

Make the property thread-local and a `DuckDBDataStore` built on the main thread captures the main thread's cursor and then executes on it from a worker — reintroducing the unsafe sharing #75/#80 removed. `SchemaInspector(conn)` captures too, and the docs tell callers to pass `catalog.data.connection` into builders.

The two things have different lifetimes, and only one is safe to hold:

| | `reg.connection` | the thread handle |
| --- | --- | --- |
| lifetime | the store's | the thread's, or narrower |
| capture into a field | correct | a bug |
| pass across threads | yes, as a base to resolve from | no |

A property cannot say "do not hold this". A scoped context manager can.

### The shape

```python
reg.connection                    # unchanged: base, stable, capturable
reg.execute(sql, params)          # one-shot custom SQL; no handle exists to capture
with reg.session() as s:          # scoped handle
    s.execute(...)
    with s.value_set(ids) as w:   # #271 rides on this
        codes.filter(sl.code.id.is_in(w)).collect()
reg.on_connect(fn)                # setup hook, applied to every handle at creation
reg.open_sessions                 # observability
```

Prototyped; all of it runs. Notes from building it:

- **Nesting must refcount.** A library function opening a session inside a caller's session must not release the caller's handle on exit. Only the outermost block releases. `scoped_session` has the same problem and the same answer.
- **The handle must BE `cursor_for`, not a new cache.** My first prototype kept its own thread-local and silently became a *fourth* handle — value sets registered on it were invisible to `CodeQuery.ids()`. Reproducing the bug by accident is the argument for consolidating rather than adding.

### Naming: `session`, decided on evidence

`cursor` is honest about the implementation and misleading about the semantics:

```
type(conn.cursor()) : DuckDBPyConnection        # duckdb's "cursor" IS a connection
DBAPI methods present: execute, fetchone, fetchall, fetchmany, description, rowcount, close
```

Enough DBAPI-cursor surface that a Python reader imports DBAPI expectations — per statement, cheap, discarded. Ours is one per thread, long-lived, stateful: **same word, opposite lifetime**, which is the "same name, different law" hazard this milestone has spent its time removing. Second collision: `duckdb_conn.cursor()` returns a *fresh* handle per call; `reg.cursor()` would return the same one.

`session` is DuckDB's own word for precisely this scope:

```
SET SESSION default_null_order='NULLS FIRST'
  this handle    -> NULLS_FIRST
  sibling handle -> NULLS_LAST          # one handle == one session
```

The state the object exists to hold is what DuckDB SQL calls session state. "Session" meaning connection-scoped state is also the database-wide norm (Postgres, Oracle, MySQL); SQLAlchemy's ORM `Session` is the outlier. The docstring will say *database* session — connection-scoped state, explicitly not a unit of work — so the SQLAlchemy reader is corrected on arrival.

Principle applied: a public name describes semantics, not implementation, and should signal what callers get wrong. Here that is lifetime and state-sharing. `cursor` gets both backwards.

### Implementation order

1. Fold `storage/lazy._cur` into one cursor function — the consolidation, standalone.
2. `Session` / session machinery, with the setup hook and refcounted nesting.
3. Default hook aligning `search_path` so every handle agrees.
4. `Registry.session()` / `.execute()` / `.on_connect()` / `.open_sessions`.
5. Repoint `local/sql.py` and the federation cookbook.
6. `value_set` (#271) on the session.
