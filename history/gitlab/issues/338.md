# Issue #338: `latest` breaks first-hit-wins: the chain's two caches have opposite policies (design §5.16)

| --- | --- |
| State | closed |

Design §5.16, in `docs/design/registry-and-catalog.md`. Blocks §6 step 9 — the
chain cannot be promoted from *description* to *mechanism* while its layers
disagree about what a `latest` URN means.

## The finding, in one function

`RestRegistry._fetch_one` consults two caches in a row, and they have
**opposite** `latest` policies. Both are deliberate; neither is aware of the
other (`api/registry.py:494`):

```python
elif references == "none":
    cached = self._session.get(urn)        # serves `latest` — Session._latest exists for it
    if cached is not None:
        return cached
    from_local = self._local_cache_lookup(urn)   # refuses `latest`, explicitly
```

`_local_cache_lookup` (`:455`):

```python
if self._materialise_to is None or urn.version == "latest":
    return None      # "(latest) URN — must always re-fetch"
```

`Session.get` (`api/session.py:92`):

```python
if urn.version == "latest":
    latest_key = f"{urn.artefact_class}:{urn.agency}:{urn.id}"
    return self._latest.get(latest_key)      # a whole index maintained for this
```

So the layer that persists to disk treats a cached `latest` as unsafe, and the
layer in front of it — which the request reaches *first*, so it always wins —
treats it as fine.

## Measured, not asserted

A `MockTransport` where the provider publishes 2.0 between two calls:

| scenario | HTTP requests | second call returns |
|---|---|---|
| **A.** one registry, `latest` asked twice | **1** | `1.0 'first'` — **stale** |
| **B.** `materialise_to`, two registries, `latest` | 2 | `2.0 'SECOND'` — correct |
| **C.** `materialise_to`, two registries, pinned `1.0` | 1 | served from cache (control) |

B and C together show the local store's policy works and is doing real caching.
A shows the Session in front of it serving a version the provider has
superseded.

## Why "session-scoped" is not the defence it looks like

`Session` documents itself as a *"session-scoped identity map"*, and within one
unit of work an identity map returning a stable object is correct — arguably
required. The problem is lifetime: `RestRegistry` holds one `Session` for its
entire life, and the deployment this library is being shaped for (§4.1 of the
design, and #336's fix, is a FastAPI facade) holds one `RestRegistry` for the
life of the process. "Session-scoped" collapses to "process-scoped", and a
server that ran for a week would serve a week-old `latest`.

`Session._map` / `_latest` are also unbounded and never invalidated — the same
defect #336 fixed for `_fetched`, one layer up. Worth noting here rather than
filing separately, since any fix touches the same code.

## What has to be decided

§1.3 states the chain rule with **no version qualifier**, which is why this is a
design question and not just a bug. Three candidate rules, and the design should
pick one and say so:

1. **Per-version rule.** Pinned URNs cache at every layer; `latest` goes to the
   authority. Consistent with `_local_cache_lookup` today; costs an identity
   guarantee inside a request (two `get(latest)` calls could return different
   objects).
2. **Resolve `latest` first.** A `latest` URN is resolved to a pinned URN once,
   then the chain runs on the pinned one. Keeps first-hit-wins intact and keeps
   the identity map honest; costs one extra round-trip per distinct artefact,
   and needs a rule for *when* the resolution itself goes stale.
3. **Time-bounded `latest` entries.** A TTL on the `_latest` indices only. Least
   invasive, but introduces a duration nothing else in the library has, and
   `docs/design/caching.md` asks for invalidation tied to a *lifecycle* rather
   than to a clock.

(2) looks closest to how the rest of the library is built — the URN is the
identity, and resolving an ambiguous one to a definite one before caching is
what `_local_cache_lookup` is groping toward. But it needs the staleness rule
for the resolution step, which is the same question one level up, so it should
not be adopted without answering that.

## Acceptance

- one stated rule for `latest`, in §1.3, applying to *every* layer of the chain
- the two call sites in `_fetch_one` agree with it
- a test that publishes a new version between two calls and asserts what the
  second one sees — the table above, as a regression guard
- `Session`'s indices bounded, per `docs/design/caching.md`
