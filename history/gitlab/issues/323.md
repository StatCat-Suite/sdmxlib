# Issue #323: storage: Dataflow.dimension_constraint is written but read back as the default

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-17 |
| Closed | 2026-08-17 |
| Labels | `storage`, `type::bug` |

Found by the derived round-trip guard (#316), which is now four defects into
its first run.

```python
Hierarchy(..., has_formal_levels=True)   ->  read back False
Dataflow(..., dimension_constraint=("FREQ",))  ->  read back ()
```

Both are declared on the model, both write without complaint, and both come
back as their default. The artefact validates and is not the one that was
persisted — the shape !303, #307 and #309 all had.

## Why they matter

`has_formal_levels` is what distinguishes a hierarchy whose levels are
*declared* from one where they are inferred from depth, so losing it changes
how the hierarchy should be read, not merely a label.

`dimension_constraint` is the subset of a DSD's dimensions a dataflow actually
uses. Losing it makes a dataflow look as though it uses the whole DSD, which is
exactly the question `#276`-style catalogue discovery asks.

## Why nothing caught it

The usual reason: both default to a falsey value (`False`, `()`), and no
fixture set them — so a reader that never populates them is indistinguishable
from one that works. That is the argument for **distinguishable** sentinels
rather than merely valid ones, which #316's guard now applies.

## Gates

The #316 guard covers both; delete their `KNOWN_LOSSES` entries when fixed and
it will fail if they regress.
