# Issue #343: FederatedRegistry.get takes no resolve=, so a federation cannot ask for a resolved fetch

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-19 |
| Closed | 2026-08-19 |
| Labels | `design` |

Found while executing the fenced blocks of `docs/cookbook/federation.md`
(!388). Its end-to-end example was written as:

```python
dsd = fed.get(sl.DataStructure.urn_for(agency="ESTAT", id="CPI"), resolve=True)
# TypeError: FederatedRegistry.get() got an unexpected keyword argument 'resolve'
```

Corrected on the page by dropping the argument and reaching for the routed
source directly. This is about whether that is the right answer.

## The three `get`s disagree

| type | signature |
| --- | --- |
| `RestRegistry` | `get(target, *, resolve=False, partial=True)` |
| `LocalRegistry` | `get(urn, *, eager=False)` |
| `FederatedRegistry` | `get(urn)` |

`SupportsGet` declares `get(urn, /) -> T | None`, so all three satisfy the
protocol and none of them take the same keywords.

## Why it is defensible as-is

#340 settled that resolution depth is a choice about **how many requests to
make**, which is why `LocalRegistry` refuses `resolve=` rather than ignoring
it: a local store has already paid for every hop, so there is nothing to
decline. A federation does not know in advance which source will answer a
given URN — `default=` is frequently a `LocalRegistry` — so `resolve=True`
would mean "deep, if the source happens to be REST, otherwise vacuous". That
is the silent-no-op the `LocalRegistry` refusal exists to prevent.

## Why it might not be

Routing is by *agency*, and the agency is in the URN, so the source **is**
known before the call — `FederatedRegistry._route(urn)` picks it with no I/O.
"Which source will answer" is not actually uncertain here.

And the workaround the page now shows is worse than the problem:

```python
dsd = fed.get(urn)                # via the federation
resolved = estat.get(urn, resolve=True)   # …but reach past it for depth
```

A caller who holds a federation precisely so they do not have to know which
registry owns `ESTAT` must now know it in order to ask for a resolved fetch.
That defeats the type's purpose for what is a very ordinary request.

## Options

1. **Forward it.** `get(urn, **kwargs)` passed through to the routed source.
   Cheapest, and worst: `eager=` and `resolve=` become interchangeable typos
   whose acceptance depends on routing, and the error a caller gets names a
   type they did not mention.
2. **Accept `resolve=` and translate.** Forward to a `RestRegistry`, ignore it
   for a `LocalRegistry` (which already resolves unconditionally, so the
   *result* is what was asked for either way — only the request count differs,
   and it is zero). This makes the argument mean the same thing at every call
   site: "I want the references followed."
3. **Leave it, and say so.** Add the refusal to `upgrading.md`'s existing
   `resolve=`-is-`RestRegistry`-only note, which currently names only
   `LocalRegistry`.

Option 2 looks right, on the reading that `resolve=` describes the *artefact
the caller wants* rather than the transport it takes to get there — which is
also what makes it harmless on a local store. Worth deciding rather than
inheriting.

## Also unresolved

`partial=` has the same shape and is not mentioned above. Unlike `resolve=`
it has no local meaning at all: a store holds whatever was written to it, so
`partial=False` cannot be honoured or usefully refused after the fact.
