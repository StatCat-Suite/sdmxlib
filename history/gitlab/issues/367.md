# Issue #367: Artefact ids are never checked against IDType, so an invalid id serialises silently to SDMX-JSON

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-21 |
| Closed | 2026-08-22 |

Noticed while resolving #365's id-pattern question.

## The gap

`src/` contains **no** pattern check on any artefact id:

```
$ grep -rn 'A-Za-z0-9_@\$' src/sdmxlib/
(nothing)
```

SDMX constrains ids tightly. From the vendored XSDs, identically in 2.1 and 3.0:

| Type | Pattern |
| --- | --- |
| `IDType` | `[A-Za-z0-9_@$\-]+` |
| `NestedIDType` | `[A-Za-z0-9_@$\-]+(\.[A-Za-z0-9_@$\-]+)*` |
| `NCNameIDType` | `[A-Za-z,A-Za-z0-9_\-]*` |
| `NestedNCNameIDType` | `[A-Za-z,A-Za-z0-9_\-]*(\.[A-Za-z,A-Za-z0-9_\-]*)*` |

So `Code(id="A.B")` is invalid SDMX. We accept it, store it, and serialise it.

## Why it matters unevenly

- **SDMX-ML**: caught, but only by the XSD, and we only run the XSD *in tests*. A user writing 2.1 in production gets a non-conformant document with no error.
- **SDMX-JSON**: not caught at all. JSON-Schema validation is test-only too, and the JSON schemas carry the same pattern (`parent` in the data schema is `^[A-Za-z0-9_@$-]+$` — literally `IDType`).

Confirmed by writing a codelist with a dotted code id and validating: the 2.1 XSD rejects both the `Code/@id` and the parent `<Ref>/@id` on the pattern facet.

## Why it is filed rather than fixed

It interacts with `model/validation.py`, which already owns "what a given wire version refuses" (`_UNWRITABLE`, `check_writable`, `_PRIMARY_MEASURE_ID_21`). An id check plausibly belongs there rather than as a converter on every `id` field — a converter would reject at construction time, which is wrong for a *reader* parsing someone else's non-conformant document.

Open questions:

1. **Where** — `validate()` / `check_writable` at write time, or a model-level converter? Write time is more likely right: reading a malformed document and refusing to represent it is worse than round-tripping it.
2. **Which type per artefact** — the four patterns are not interchangeable. `CodelistType/@id` is `NCNameIDType` (the XSD says so explicitly, because codelist ids become XML type names), while a `Code`'s id is the looser `IDType`. A single check would be wrong in both directions.
3. **Refuse or warn** — #225 established that silent drops are the enemy; an id we cannot write should probably raise like the other `check_writable` cases.

No known instance of this biting in practice: real registries publish conformant ids. It is a latent correctness gap, not a live bug.

## Comments

### 2026-08-22

**Closing — this issue is wrong, and it was my error.** No code change; nothing is broken.

## What is actually there

`model/validation.py` has carried id-pattern checking since #221, with the three-way distinction the issue asks for and a 30-line comment explaining it:

```python
_ID_PATTERN     = r"^[A-Za-z0-9_@$-]+$"
_NCNAME_PATTERN = r"^[A-Za-z,A-Za-z0-9_-]*$"
_AGENCY_PATTERN = r"^[A-Za-z,A-Za-z0-9_-]*(\.[A-Za-z,A-Za-z0-9_-]*)*$"
```

Verified on `main`, through the public entry points rather than by reading:

| | |
| --- | --- |
| `sl.validate(codelist)` with `Code(id="A.B")` | raises |
| `serialize(msg, version="2.1")` | raises |
| `serialize(msg, version="3.0")` | raises |
| `serialize(msg, version="json")` | raises |

And I looked for the gap the issue claims rather than assuming: for every maintainable, item and component class in the maximal fixture, probed with `1ABC` / `A@B` / `A$B` — **there is no id the XSD rejects that `serialize` accepts**. Thirteen classes, zero gaps.

## Why I got it wrong

The issue's evidence is one command:

    $ grep -rn 'A-Za-z0-9_@\$' src/sdmxlib/
    (nothing)

That command finds three matches, one of them `validation.py:89` — the pattern itself. I recorded a null result for a grep that does not return null, and built the rest of the issue on it. Inferring absence from a single grep is the exact failure mode I had been flagging elsewhere in the same session.

## The part that stings

The three open questions I filed had all been answered already, in the code, with a defect behind each answer. `_NCNAME_ID_MAINTAINABLES` is **three** classes, not "all maintainables", and the comment says why:

> The over-application made sdmxlib refuse the ECB's own dataflow document, whose categorisation ids are UUIDs.

A false refusal on real registry output — which is worse than the over-permissiveness it was guarding against. I re-derived that same map from the schemas this morning and was about to propose the *over*-application as new work.

## One thing worth keeping

While checking, I re-derived the class → id-type map empirically by mutating ids in the maximal fixture and asking the XSD, because my first attempt — walking the `@id` declaration through the extension chain — got `AgencyScheme` wrong. `test_xsd_conformance` already derives `_NCNAME_ID_MAINTAINABLES` from the schemas by the chain method. It agrees with the empirical result today, and the three fixed-id schemes it might disagree about are pinned by `_FIXED_SCHEME_IDS` anyway, so nothing is riding on it. Recording it in case that guard is ever widened.
