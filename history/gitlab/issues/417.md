## Summary

`model.version.check_writable` (#319) refuses a version the target grammar
cannot express. Only the SDMX-ML writers call it (`sdmx_ml/_common.py:1191`,
`sdmx_ml/_v3_writer.py:205`). The SDMX-JSON writer applies **no** version
check, so a version that 3.0 refuses is written to JSON and fails the
schema:

| version | SDMX-ML 2.1 | SDMX-ML 3.0 | SDMX-JSON (structure) |
|---|---|---|---|
| `1.2.3.4` | written ✅ | refused ✅ | **written, schema-invalid** |
| `1.03` | written ✅ | refused ✅ | **written, schema-invalid** (same pattern) |
| `1.0.0-draft` | refused ✅ | written ✅ | written ✅ |

The `1.2.3.4` → JSON case was measured on `main` @ `6cf7bc5`, and the
document fails `sdmx-json-structure-schema.json`. The `1.03` row follows from
the pattern below.

## The JSON structure schema *does* constrain the version

Both vendored structure schemas (`tests/schemas/sdmx_json/2.0/` and `2.1/`)
define `VersionType` as an `anyOf` over the same two patterns SDMX-ML 3.0 uses:
legacy `^(0|[1-9]\d*)(\.(0|[1-9]\d*))?$` and semantic
`MAJOR.MINOR.PATCH[-prerelease]`. So the JSON structure grammar **is** the 3.0
grammar.

Two places in the codebase say otherwise:

- `model/validation.py`, the comment above `_SEMVER_RE`: "*its structure
  schema states no pattern at all*".
- The note closing #188: "*the structure schema states no pattern at all*".

The schema's own `description` text adds to the confusion. It still carries
the 2.1 prose ("*an unlimited set of numeric components … 1.3 and 1.03 would be
equivalent*"), while its patterns forbid both. Read the pattern, not the prose.

(The metadata schema is stricter again: semver only. Its own
`"default": 1.0` is a number and fails its own pattern. #234 already handles
the metadata side.)

## Proposed fix

- The JSON structure writer calls `check_writable(version, "3.0", ...)`.
  The JSON grammar is the 3.0 grammar, so it needs no new grammar entry; a
  `"json"` alias of `"3.0"` would make the call site self-explanatory.
- Correct the `_SEMVER_RE` comment, and note on #188 that its closing
  reasoning was wrong.
- `validate()`'s docstring still says "*version format (digits separated by
  dots)*", which is the pre-#319 rule. It now accepts either grammar.
- Add a property test: for every version `compliance()` returns, the JSON
  writer's acceptance matches the JSON schema's.

This is the immediate bug. Whether the store should hold a version no
3.x format can carry is the design question in the version-and-finality issue
in this milestone.
