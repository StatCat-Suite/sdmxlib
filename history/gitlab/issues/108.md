3.1 model audit follow-up (post-MR !63).

## Semantic gap

\`HierarchyAssociation\` is a top-level \`MaintainableArtefact\` in 3.0 / 3.1 that binds a \`Hierarchy\` to an identifiable artefact (typically a \`Dimension\` in a \`DataStructure\` or \`Dataflow\`) within an optional context. We don't model it at all.

## Why it matters

The Hierarchy itself is structure-agnostic — it just defines a code tree. The association says \"this hierarchy applies to **that** dimension of **that** dataflow.\" Without modelling the association, we can't:

- Pick the right hierarchy when rendering a coded dimension.
- Validate that a hierarchy's codes are a subset of the bound dimension's codelist.
- Round-trip a 3.0 / 3.1 message that carries hierarchy-dimension bindings.

## Shape

Per \`SDMXStructureHierarchicalCodelist.xsd\` \`HierarchyAssociationType\`:

\`\`\`
- linked_hierarchy: Ref[Hierarchy]      # which hierarchy
- linked_object: Ref[<identifiable>]    # what it binds to (usually Dimension)
- context_object: Ref[<identifiable>] | None  # optional context (Dataflow / DSD)
- plus MaintainableArtefact fields (agency, id, version, name, description, valid_from, valid_to)
\`\`\`

## Action

- Add \`HierarchyAssociation\` class to \`model/hierarchy.py\` (or a new \`model/hierarchy_association.py\`).
- Add \`hierarchy_associations: ArtefactList[HierarchyAssociation]\` slot to \`StructureMessage\`.
- Add to public exports.
- 3.0 / 3.1 writer + reader: emit / parse the \`<str:HierarchyAssociations>\` container.
