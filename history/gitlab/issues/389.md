# Issue #389: the default ORDER BY is 35x the scan it decorates, and only stream() can decline it

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-28 |
| Closed | 2026-09-05 |
| Milestone | %19 Data plane: the first profile of 1.14 billion observations |
| Labels | `data`, `design`, `dsl`, `perf` |

Split from %19's profile. Distinct from #388 — a different clause, a different
fix, and unlike the join this one is *deliberate*. The question is whether a
caller can decline it.

## Measured

`GEO_LEVEL='CensusDivision'`, 4,261,081 rows, two columns out:

| | ms |
| --- | --- |
| base table only, no join, no order | **3** |
| + the sidecar join (#388) | 5 |
| + the default `ORDER BY` | **104** |
| both, which is what the DSL emits | 119 |

The ordering is **35x** the scan it decorates, and it dominates once #388's
join is removed.

Every observation query carries it, on all six key components:

```sql
ORDER BY s0.FREQ NULLS LAST, s0.REF_AREA NULLS LAST, s0.CHARACTERISTIC NULLS LAST,
         s0.GENDER NULLS LAST, s0.STAT_MEASURE NULLS LAST, s0.TIME_PERIOD NULLS LAST
```

## Why it exists, and why that is right

A default order is a real contract: it is what the rows mean when nobody has
said. `Query.default_order`'s docstring makes the distinction carefully — a
caller's `order_by` is a decision the refinement laws govern, a default is not.
And for SDMX specifically, key order is the natural reading of a dataset.

This issue is **not** a proposal to drop it.

## What is missing is the opt-out

`to_sql(ordered=False)` exists and works — the unordered SQL is emitted
correctly. No terminal exposes it. `frame()`, `collect()` and `select().collect()`
all sort; a caller who does not care cannot say so.

`stream()` already declines it, and **that is verified rather than assumed**:
its SQL carries no `ORDER BY`, and the boundedness its docstring claims holds
at real scale —

| 4.26M rows, 27 columns | time | peak RSS |
| --- | --- | --- |
| `stream(50_000)` | 365 ms | **+81 MB** |
| `frame()` | 1152 ms | **+4518 MB** |

So the machinery is all there. `stream()` is the proof that an unordered read
is expressible; it is simply the only terminal that can ask.

## Directions

1. **A terminal-level opt-out** — `frame(ordered=False)` / `collect(ordered=False)`,
   mirroring `to_sql`'s existing parameter. Smallest, and matches a spelling
   that already exists.
2. **A query-level `unordered()`** refinement, so the choice composes and is
   visible in the plan rather than at the last call.
3. **Nothing** — argue that a caller who cares about 100 ms on 4M rows should
   use `stream()`, which is already unordered and already bounded. Defensible,
   and it is the honest baseline the other two have to beat.

(3) is a real option and should not be dismissed: `stream()` is faster *and*
56x lighter here, so "use the streaming terminal for large results" may simply
be the right advice. The counter-argument is that `frame()` on a 4M-row
partition is not an unreasonable thing to want, and 100 ms of it is a sort
nobody asked for.

## Not to be confused with #330

#330 is about physical **write** layout — storing observations sorted so scans
prune and sorts get cheaper. It concluded that a stream should not ask the
engine to sort, which is the state `stream()` is already in. This issue is
about the **read** side: whether the other terminals can say the same.

## Acceptance

- Whatever is chosen, a caller can obtain a large unordered frame without
  dropping to `reg.sql()`, or the documentation says plainly that `stream()` is
  how you do that.
- If an opt-out lands: a test that the default is unchanged, asserted on the
  SQL, since a default quietly becoming unordered is a silent change to what
  every existing caller receives.

## Comments

### 2026-09-05

Landed in !454 as `order_by(None)`.

**Two corrections to the framing above**, both of which changed the fix:

1. **It is not `default_order`.** `Observations` never sets one, and no test does. The clause is the unconditional root-key tiebreak in `_order_sql`, whose stated justification is *paging stability* (#264), not "key order is the natural reading of a dataset". That distinction is what makes an opt-out safe to offer, and it also rules out the tempting fix: making every terminal use `_is_ordered()` — the rule `stream()` already applies — fails 18 unit tests, including `test_an_unsorted_query_is_still_ordered` and the grouped/`unique()` stability properties. The default is unchanged.

2. **Direction (1), a terminal-level `ordered=False`, has no precedent anywhere.** Checked against source and docs: no Python query or dataframe library puts an ordering knob on a materialisation call — not SQLAlchemy `.all()`/`.first()`/`Session.execute()`, Django `list()`/`.iterator()`/`.values()`, ibis `.to_pandas()`/`.execute()`, polars `.collect()` (checked against installed 1.41.1), DuckDB `.fetchall()`/`.to_arrow_table()`, PySpark `.collect()`, or Dask `.compute()`. The one counter-example found is pyarrow `write_dataset(preserve_order=)` — a write sink, defaulting to unordered.

   The reset is universally *the same builder method with an empty or `None` argument*: SQLAlchemy `order_by(None)`, Django `order_by()`, peewee `order_by()`. Nobody invents a verb — so direction (2)'s `unordered()` was out on the same evidence.

**What shipped** — three states, the middle one unchanged:

```python
q.order_by(q.code.id)   # sort by id, then the tiebreak
q.order_by()            # clear the keys, keep the tiebreak
q.order_by(None)        # no ORDER BY at all
```

Measured through the public API on the `CensusDivision` partition (4,261,081 rows), best of three warm:

| | before | after | |
| --- | --- | --- | --- |
| `select(2 cols).collect()` | 337 ms | **75 ms** | 4.5x |
| `frame()` — 27 columns | 1061 ms | **495 ms** | 2.1x |

Same row count either way.

`limit`, `offset`, `after` and `page` raise on an unordered query — declining the tiebreak and then paging would reintroduce #264 silently, so the two are exclusive rather than documented apart. The reducing terminals (`count`, `exists`, `one`, `one_or_none`, `preview`) are unaffected; `first()` returns an arbitrary match, as SQLAlchemy's does.

Both acceptance criteria are met: a large unordered frame without `reg.sql()`, and `test_the_default_is_unchanged` asserts on the SQL that the default did not move.
