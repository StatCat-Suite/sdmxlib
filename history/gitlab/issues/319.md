# Issue #319: version validation implements SDMX-ML 2.1's grammar, but the library reads and writes 3.0 — the two disagree in both directions

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-16 |
| Closed | 2026-08-16 |
| Labels | `model`, `needs-design`, `type::bug` |

Noticed while fixing #311. `_check_version` uses

```python
_VERSION_PATTERN = r"^\d+(\.\d+)*$"
```

which is **exactly** SDMX-ML 2.1's `VersionType`:

```xml
<!-- tests/schemas/sdmx_ml21/SDMXCommonReferences.xsd -->
<xs:pattern value="[0-9]+(\.[0-9]+)*"/>
```

So this is not a typo — it is 2.1's rule, faithfully. The problem is that
3.0 replaced that pattern with a **union**, and this library reads and writes
both formats:

```xml
<!-- sdmx_ml30 / sdmx_ml31 -->
LegacyVersionNumberType     (0|[1-9]\d*)(\.(0|[1-9]\d*))?
SemanticVersionNumberType   (0|[1-9]\d*)(\.(0|[1-9]\d*)){2}(-<prerelease>)?
```

## The disagreement runs both ways

Measured against the vendored schemas:

| version | we accept | 3.0 XSD | |
| --- | --- | --- | --- |
| `1.0.0-draft` | ✗ | ✓ | **we reject what 3.0 permits** |
| `1.0.0-alpha.1` | ✗ | ✓ | " |
| `1.0.0-rc-1` | ✗ | ✓ | " |
| `01.0` | ✓ | ✗ | **we permit what 3.0 forbids** |
| `1.03` | ✓ | ✗ | " |
| `1.2.3.4` | ✓ | ✗ | " (four parts) |
| `1`, `1.0`, `1.10`, `1.0.0`, `0.0.1` | ✓ | ✓ | agree |

The rejections are the ones with teeth: a 3.0 registry publishing
`1.0.0-draft` cannot be stored at all — `Registry.add` raises
`ValidationError` — so a perfectly conformant artefact is unusable.

## Why it needs a decision rather than a wider regex

Three readings, and they are not equivalent:

1. **Union of both.** Accept anything either schema allows. Never rejects a
   conformant artefact; also never catches a malformed one that the *other*
   format would have refused, so `1.2.3.4-draft` sails through.
2. **Version-aware.** Validate against the format the artefact came from or is
   destined for. Most correct, and the most machinery: `validate()` currently
   takes an artefact and nothing else, and an artefact does not know which
   wire format it will be written to.
3. **3.0 only, since it is the current standard.** Rejects `1.03` and
   `1.2.3.4`, which 2.1 registries may legitimately publish — this library
   still reads 2.1, so that would be a regression for those users.

(1) is the smallest and probably right for now, but it should be a decision
with the trade written down rather than a widened regex.

## Related

- #311 baked a version sort key. `model/version.py` deliberately follows the
  looser 2.1 reading — a key that mis-sorts a version some registry still
  publishes is worse than one that is generous — and says so.
- #188 is the mirror image: our *default* `"1.0"` fails the metadata JSON
  schema's stricter `VersionType`.

## Gates

- A test that every version string the vendored 2.1 **and** 3.0 schemas accept
  round-trips through `validate()` — derived from the schema patterns rather
  than a hand-written list, so a schema refresh moves the test with it.
- The reverse: something both schemas reject is still rejected.
- Whatever is chosen, `model/version.py`'s `sort_key` must order every
  accepted form; it currently does, including prereleases.

### 2026-08-16

## Proposal: classify at the boundary, do not tag the artefact

From discussion — the shape asked for was "note compliance at parse, tag the artefact, error on write". The error and the reason are right; the tag is the part to drop, and the reason is worth writing down.

**Compliance is a pure function of the version string.** `compliance("1.03") == {"2.1"}` wherever it is asked. Storing that on the artefact stores something derivable, which is the drift this codebase keeps paying for — three facet column groups, `_hops_available`, seven orphaned `_COMMUTATIVE_FIELDS` entries. A tag can disagree with the string beside it; a function cannot.

**And the check does not need parse-time knowledge.** What it needs is *(version string, target format)*, and both are present at the write boundary. The one thing only the parser knows — which format an artefact *arrived* in — is genuine provenance, but it is not what the error is about: writing a 2.1-sourced artefact to 3.0 fails or succeeds on the version string, not on where it came from.

### So, two boundaries rather than a tag

1. **`validate()` accepts the union** — anything either schema permits. The store is format-agnostic, so rejecting `1.0.0-draft` there (today's behaviour) refuses a conformant 3.0 artefact for no reason the store cares about. This is the bug.
2. **Each format writer refuses what its format cannot express**, naming the version, the format, and the fact that the two grammars are not nested. `sdmx_ml21` rejects `1.0.0-draft`; `sdmx_ml30` rejects `1.03` and `1.2.3.4`.

### Evidence the writer is the right boundary

The XSD round-trip tests already validate emitted XML against the vendored schemas, so a 3.0-only version written into a 2.1 document **already fails today** — as a schema violation in a test, with no message a user would ever see. Moving the check into the writer turns an existing test-only failure into a runtime error that names the problem. That is the same shape as `assert_valid_sdmx_ml` catching writer bugs pure round-tripping cannot.

### The behaviour change to be deliberate about

A 3.0 → 2.1 conversion of an artefact versioned `1.0.0-draft` will raise where it currently emits invalid XML. That is correct — the version genuinely cannot be expressed in 2.1 — and it is a change: some pipeline may be relying on the silently-wrong output. Per the project's rule it should raise and name the fix ("re-version to 1.0.0, or write 3.0").

### Sketch

```python
# model/version.py, beside sort_key
def compliance(version: str) -> frozenset[str]:
    """Which SDMX-ML grammars accept this version — {"2.1"}, {"3.0"}, both, or neither."""
```

Derived from the vendored XSD patterns rather than hand-written, so a schema refresh moves it. Gates as already listed on this issue.

### Not affected

`sort_key` needs no change either way: it is deliberately more generous than both grammars (prereleases, leading zeros, up to eight parts), so whichever reading is chosen, ordering already covers it.
