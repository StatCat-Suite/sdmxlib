# Issue #266: dsl-16: no misuse tests — is_in("CA") shipped because the oracle shared the bug

| | |

| Milestone | %13 Query DSLs: properties and mutation for the half the suite skipped |

`code.id.is_in("CA")` silently meant `is_in(["C", "A"])` — a filter that type-checks, runs, and returns wrong rows. It shipped in #261 and was found by comparing the API to polars, not by any test. Worth understanding why, because the reason generalises.

## Why nothing caught it

**The strategies only generate well-formed input.** `st.lists(st.sampled_from(ids), unique=True)` produces lists, always. The properties explore the *value* space; a bare string is a wrong *argument shape*, which no value-space generator reaches.

**The type checkers were correct to allow it.** `str` genuinely satisfies `Iterable[object]`. There was nothing for basedpyright or pyrefly to flag.

**The oracle shares the misconception, so the differential property would have passed regardless.** Measured:

```
oracle.in_set("CA")  ->  ['C', 'A']      # identical to what the SQL returned
```

Even had the strategy drawn a bare string, both sides would have agreed and the test would be green.

That last one is the important part, and it is a **structural limit of differential testing**, not a defect in this oracle. The technique catches divergence between two implementations; it is blind to a mistake both make. CLAUDE.md's rule 1 — an oracle shares no code with the module under test — exists to reduce exactly this, but sharing *Python's iteration semantics* is not sharing code, so the rule did not bite.

What did find it was a third implementation that does not share those semantics. polars rejects `is_in("CA")` (it reads a bare string as a column name and raises `ColumnNotFoundError`); the disagreement was visible the moment the two APIs were put side by side.

## Scope

**1. A misuse-test category.** We have no tests that assert *wrong* calls fail. Add them where a plausible wrong call currently succeeds:

- collection parameters handed a bare `str` / `bytes` (the `is_in` class — now guarded, but nothing stops the next one)
- predicate builders handed a predicate where a value belongs, or vice versa (`filter(code.id)` rather than `filter(code.id == "A")`)
- `sort_by` handed a `Predicate` rather than a ref
- `is_in` handed a `dict` (iterates keys — same silent-wrong-answer shape)

These are cheap, and each one is a `pytest.raises` with a message assertion.

**2. A guard against the class, not just the instances.** `is_in` was the only public parameter typed `Iterable[str]` / `Sequence[str]` / `Collection[str]` at the time of writing — confirmed by grep. A test that walks the public API and asserts no such parameter accepts a bare string would keep it that way, and would have caught #261 the day it landed.

**3. Write the limitation down.** `CLAUDE.md`'s "Differential properties and the oracles" section states four rules that make the oracles trustworthy. It should also state what they cannot do: a shared misconception is invisible, and the mitigation is a comparison against an implementation outside the shared assumptions — which for the query DSLs means polars, SQLAlchemy or the database itself.

## Not in scope

Making the strategies generate ill-typed values. Hypothesis is the wrong instrument for argument-shape errors — the type is fixed at the call site, so a generator would just be a parametrised list of bad literals, which is a misuse test written awkwardly.

## Test gates

- A misuse test per item in the list above, each asserting the raised message names the fix rather than only the problem.
- The public-API sweep for bare-string-accepting collection parameters.
- The CLAUDE.md paragraph.
