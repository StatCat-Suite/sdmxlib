# Issue #335: An unfiltered structural scan is never bound-checked — the widest request is the one nothing refuses

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-18 |
| Closed | 2026-08-18 |
| Labels | `bug` |

`is_bounded` exists to stop a backend call that "a user could not reasonably
issue". Its docstring is explicit that the check belongs to **every scan**:

> §5's rule, and the reason it is a function of a single `Push` rather than of
> the program: a rewrite that bounds the *outer* scan by a set computed from an
> unbounded *inner* one satisfies any whole-program check while having moved
> the catastrophe one step down… **So every scan carries the bound on its own
> terms.**

The only call site does not do that (`query/_pushdown.py:766`):

```python
if (residual or memberships) and not is_bounded(push, capability):
```

A query with **no** residual and **no** membership skips the check entirely.

## What that means on the wire

Probed:

```
reg.query(sl.q.dataflow)                          -> [('all', 'all', 'full', 'none')]
reg.query(sl.q.dataflow).filter(agency == "ECB")  -> [('ECB', 'all', 'full', 'none')]
```

`GET /structure/dataflow/all/all/latest?detail=full` — every dataflow from every
agency at full detail — is the **widest request the surface can issue**, and it
is the one case nothing refuses. Adding a filter makes the request *narrower*
and simultaneously makes it eligible for refusal.

So the guard is not just incomplete, it is inverted with respect to cost.

## Why it was not noticed

The refusal was designed against the case it was written for — a residual that
must be evaluated locally over a fetched set — and "no residual" reads like
"nothing to be careful about". It is the opposite: no residual means the fetch
*is* the whole answer, so its size is entirely the request's.

## Fix

Consult `is_bounded` for every push, not only where a residual or membership
exists. The message already names what would make the query admissible
(`_refuse`), so the fix is the guard, not the diagnostics.

Check while doing it: whether any legitimate query becomes refused that should
not be — a deliberate "fetch me every dataflow" is a real thing to want, and if
so it needs the same explicit opt-out the data plane is getting
(`docs/design/registry-and-catalog.md` §5.2).

Found while reviewing that design doc (§5.12). Pre-existing on `main`,
independent of anything that document proposes.

## Comments

### 2026-08-18

**Closing as invalid. This is deliberate, documented behaviour and I filed it
without checking.**

`docs/design/query-pushdown.md` §5 has a subsection titled *"The table
over-states it, and the code is right"*:

> Read strictly, the third row refuses `reg.query(q.codelist)` with no filter
> at all… The implemented rule does not: it refuses an unbounded scan
> **carrying a residual**, and lets a bare unbounded scan through. The §10
> survey is what surfaced the difference.
>
> The code is right and this table is the loose statement. `query(q.codelist)`
> with nothing else is a caller asking for every codelist, in as many words; it
> returns what it says and the caller can see the cost in the query they wrote.
> `query(q.codelist).filter(name.contains("price"))` is a caller asking for
> *three* codelists, and the fetch-everything is invisible in the text of it.
> The rule exists for the second, and a refusal that also caught the first
> would be refusing a query nobody is confused about.

And `tests/unit/test_query_rest_survey.py` pins it with the reason attached:

```python
# Allowed deliberately: a caller asking for every dataflow said so, and
# the cost is visible in the query they wrote. See §5's amendment.
"every dataflow, unfiltered": "PUSHED",
```

## Where the reasoning went wrong

I described the guard as "inverted with respect to cost" — a filter making a
request narrower while making it eligible for refusal. That is true and it is
not the point. **The rule is about the *visibility* of cost, not its
magnitude.** A bare scan is expensive and says so. A residual scan looks narrow
and is not, and the fetch-everything is invisible in the text of the query.
Refusing the first would refuse a query nobody is confused about.

## The process failure worth recording

The finding came from a design review, and I verified it with a probe:

```
reg.query(sl.q.dataflow)  ->  [('all', 'all', 'full', 'none')]
```

That confirmed the *mechanism* and I read it as confirming the *defect*. The
probe could not have told the difference — the behaviour is identical whether
it is intended or not. The check that would have caught it was reading the
design doc for the module being changed, which existed and answered it
directly.

Implementing the "fix" is what surfaced this: one test failed, and it was the
test carrying the rationale.
