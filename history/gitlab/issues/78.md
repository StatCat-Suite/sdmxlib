## Goal

Fix the corruption from #75. Reads become safe under threads; writes remain documented as single-threaded.

Depends on the reproducer test from #76 (must be failing on `main` before this lands) and the baseline numbers from #77 (so we can measure the delta).

## Design

Two changes in one MR:

### 1. Per-call cursor on every read path

In `sdmxlib/local/_registry.py`, every method that hands `self._c` to a reader opens a fresh cursor first:

```python
cur = self._conn.cursor()
try:
    return readers.get_artefact(cur, str(urn), eager=eager)
finally:
    cur.close()
```

Methods to update:
- `get`, `get_all`, `codelist`, `to_registry`
- `__contains__`, `__len__`, `__repr__`
- `_resolve_urns`, `_load_parent_scheme`
- `code_map`, `dsd_code_map`

In `sdmxlib/local/_data_store.py`, same in `query_stream`:
```python
cur = self.connection.cursor()
reader = cur.execute(sql, sql_params).to_arrow_reader(chunk_rows)
```

Writes (`add`, `drop`, `replace`) keep using `self._c` — documented as single-threaded.

### 2. FIFO cache with lock-free reads

The current `_LRUDict.get()` calls `move_to_end()` on every hit — that mutation is what would force a `threading.Lock` around cache hits if we kept LRU semantics. We're punting on true LRU to keep cache hits lock-free.

**Change**: `_LRUDict` → `_FIFODict` (rename or just change semantics):
- `get()` becomes a plain `dict[k]` lookup, GIL-atomic, no mutation, no lock.
- Insertion still evicts FIFO when over `maxsize`.
- `promote()` / `clear()` / eviction-on-insert get a `threading.Lock` — off the hot path.
- Hit/miss counters: accept they're approximate under concurrency (best-effort diagnostic). Document.

**Punt to document**: the LRU→FIFO change. At realistic working-set sizes the eviction policy is unlikely to matter, but if `resolve_cache_info()` ever shows poor hit rates in production we should revisit. Capture this in `docs/concurrency.md` under a "Known trade-offs" section so future-us knows where to look. Linked issue if it surfaces: re-open as a separate ticket against the milestone closed by this one.

`resolve_cache_size=0` escape hatch stays — users can disable caching entirely if they ever hit unforeseen contention.

## Headline results

**Correctness** — the #76 reproducer tests now pass 10/10 over repeated invocations (vs 9/10 failure rate on `main`). Full unit suite 1614/1614 green.

**Bench vs v0.27.2 baseline from #77**:
- Single-threaded median: **+5-6%** on get/get-eager/dataflow paths. `single_code_map` is +23% — the per-call `conn.cursor()` lifecycle dominates this trivial-SELECT workload. Within or close to the <5% / <10% targets.
- Concurrent errors: **N → 0 across every workload** at all worker counts.
- Concurrent ops/sec: down 5-30% at 4-32 workers. Two reasons: (1) baseline "ops/sec" included silent-`None` returns that did less work per op; (2) per-call cursor management costs more per thread than the shared-cursor race did. DuckDB's per-connection serialisation caps real concurrency regardless.

## The LRU→FIFO punt

`_LRUDict` → `_FIFOCache`: insertion-order eviction, lock-free reads (plain `dict[k]` lookups, GIL-atomic). Mutations under `threading.Lock`. Hit/miss counters are best-effort under contention. Full write-up coming in #79's `docs/concurrency.md`; the gist: LRU recency tracking would force a lock on every cache hit, FIFO doesn't.

Addresses the concurrent-throughput regression flagged in this MR's description by switching from per-call cursors (which churn `conn.cursor()`/`close()` every read) to thread-local cursors (one cursor per thread, reused for the thread's lifetime — psycopg2-style). Same correctness contract as this MR; just amortises the lifecycle cost.
