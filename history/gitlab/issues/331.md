# Issue #331: an ordered stream at bounded memory: read partitions in key order, sort within

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-17 |
| Closed | 2026-08-17 |
| Labels | `data`, `design`, `perf` |

Follows #330. The question was whether sorting per partition — as Iceberg and Delta do — gives repeatable returns and fixes streaming. **It does, but the fix is the read pattern, not the storage.**

## Measured, 4M rows

| approach | peak RSS | globally ordered |
| --- | --- | --- |
| global `ORDER BY` | 116.5 MB | yes |
| **per-partition reads, unsorted storage** | 51.5 MB | **yes** |
| **per-partition reads, sorted storage** | **25.4 MB** | **yes** |
| plain scan of sorted storage | 23.7 MB | yes — *only while `preserve_insertion_order` is true* |
| plain scan, `preserve_insertion_order=false` | 24.5 MB | **no** |

And the peak tracks *partition* size, not table size:

| partitions | rows each | peak |
| --- | --- | --- |
| 4 | 1,000,000 | 104.2 MB |
| 20 | 200,000 | 51.7 MB |
| 200 | 20,000 | 39.2 MB |
| — (global sort) | — | 160.3 MB |

## What this means

**Sorted storage alone does not give repeatable order.** Row 4 above is the trap: it looks ordered, and the ordering is an artefact of a setting that a caller turns off for exactly this workload.

**Reading partitions in key order, with an `ORDER BY` inside each, does.** The order is then *guaranteed* rather than incidental, because every row's position is decided by an explicit sort — and the sort buffer is one partition instead of the table. That is the same trick a merge-ordered scan plays in a partitioned format, and it needs no engine support.

**Sorted storage then makes each per-partition sort nearly free** — 51 MB to 25 MB at 20 partitions, because sorting nearly-sorted input is cheap. So #330's `sort_by` and this compose: one bounds the memory, the other lowers it.

**Requirement**: the partition key must be a **prefix of the requested order**. Partition by `REF_AREA` and sort by `(REF_AREA, TIME_PERIOD)` and reading partitions in `REF_AREA` order yields global `(REF_AREA, TIME_PERIOD)` order. Ask for an order that does not start with the partition key and this cannot help.

## Proposal

`stream()` currently drops the `ORDER BY` when the caller asked for none (!345), which is bounded but unordered. This adds the third option:

* caller asks for no order -> unsorted scan, bounded, cheapest (today);
* caller asks for an order **compatible with the partition layout** -> partition-ordered reads, sorted within, **ordered and bounded**;
* caller asks for anything else -> a global sort, ordered and unbounded, as now.

The middle case is the one worth having and the library can detect it: the binding already declares `partition_layout`, and #330 added `sort_order`.

Open questions:

* **Where does the plan live?** This is several statements behind one reader, so `stream` would return a chained reader rather than a single cursor's. `pa.RecordBatchReader.from_batches` can present the concatenation as one reader, so the caller's contract does not change.
* **Partition sizing becomes a memory knob** — a user-visible consequence of a layout choice. Worth documenting where `partition_layout` is declared, since the table above is the only place the relationship is written down.
* **Does DuckLake's own partition pruning already do most of this?** Not measured. The numbers here are on a plain DuckDB table; a partitioned DuckLake table might narrow the gap between rows 1 and 2 on its own.

## Comments

### 2026-08-17

**Checked DuckLake first, and it does not close the gap.** Measured on a real partitioned DuckLake table (`ALTER TABLE … SET PARTITIONED BY (GEO)`), 4M rows, 20 partitions:

| storage | read | files | peak RSS | globally ordered |
| --- | --- | --- | --- | --- |
| partitioned | global `ORDER BY` | 20 | 126.3 MB | yes |
| **unpartitioned** | global `ORDER BY` | 20 | **125.8 MB** | yes |
| partitioned | plain scan | 20 | 25.8 MB | **no** |
| partitioned | **per-partition reads** | 20 | **39.7 MB** | **yes** |

Three things follow.

**Partitioning does nothing for a sort.** 126.3 against 125.8 MB — identical within noise. DuckLake prunes files for a `WHERE`, and an `ORDER BY` still sorts the whole result, exactly as on a plain table. No read-in-order, as expected.

**A partitioned lake scan is not ordered.** Unlike an in-memory table, where `preserve_insertion_order` made a sorted scan *look* ordered, the lake returns rows unordered even though each file holds one partition. That is better for us, not worse: the misleading accident does not exist here, so nothing tempts a consumer into relying on it. But both storage kinds are supported, so the guidance has to assume the in-memory case where it does mislead.

**Per-partition reads still win: 39.7 MB and guaranteed ordered, against 126 MB for the global sort** — 3.2x, on the real storage rather than the plain-table proxy. Close to the plain-table figure (51.5 MB), so the proxy was sound.

So the proposal stands unchanged, and one open question is answered: DuckLake's partitioning is a *pruning* feature, and ordering plus bounded memory has to come from the read pattern. Remaining open: whether `pa.RecordBatchReader.from_batches` can present the chained readers as one, so `stream()`'s contract does not change.
