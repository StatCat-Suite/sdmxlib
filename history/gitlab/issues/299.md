# Issue #299: export hygiene: types named in public signatures outside the query DSLs are not importable

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-21 |
| Labels | `design`, `type::docs` |

Split out of #265, which fixed this for the filter-DSL chain and scoped the rest out deliberately.

`test_public_surface.test_every_type_in_a_public_signature_is_importable_from_sdmxlib` covers the six query classes. Run over **every class `docs/api.md` renders**, the same check flags more. Ours, excluding stdlib (`Callable`, `Optional`, `Iterable`, `Literal`) and polars (`Expr`, `LazyFrame`, `DataFrame`):

| type | appears in |
| --- | --- |
| `SupportsUrn` | `InMemoryRegistry.add`, `.add_all` |
| `AncestorMap` | `LazyHierarchy.ancestor_at` |

Two, not a flood — which is why folding them into #265 would have produced a guard that is mostly allow-list, and a guard nobody maintains.

## The question, which is not simply "export them"

`SupportsUrn` is a Protocol: a caller satisfies it structurally and never needs to name it *unless* they are writing their own generic helper. `AncestorMap` is a type alias for a returned mapping — naming it is more plausible, since a caller stores the result.

So the decision per type is whether a *caller* has reason to write the name, not whether it appears in a signature. #265 answered that for the DSL chain by observing that `sl.code.id` is a leaf a user never names while `ColumnRef` is the base they do.

## Scope

- Decide per type: export, or leave and accept that the signature names something unimportable.
- If exporting, widen the guard in `test_public_surface.py` from `_DSL_CLASSES` to the full rendered set and shrink the `foreign` allow-list to third-party names only.
- Check whether the stdlib/polars names should be rendered at all — mkdocstrings has nothing to link `Callable` to either, and that is the same reader-facing complaint #265 opened with, one level down.

### 2026-08-20

**Audit note — still valid; here is the measured list.**

Enumerated by walking every class in `sdmxlib.__all__`, resolving type hints on
its public methods, and collecting `sdmxlib`-owned types that are not themselves
exported. Seven distinct types, all outside the query DSLs:

| Type | Reached through |
|---|---|
| `AncestorMap` | `LazyHierarchy.ancestor_at` |
| `AnyAgg` | `Agg.desc` |
| `ApiVersion` | `DataStructure.key_slot_ids` |
| `ComponentRole` | `DataStructure.role_of` |
| `ObsQuery` | `DuckDBDataStore.observations`, `FmrRegistry.observations` |
| `SupportsUrn` | `InMemoryRegistry.add`, `InMemoryRegistry.add_all` |
| `ValueSet` | `Session.value_set` |

A caller cannot name any of these to annotate a variable holding one, without
importing from a private path.

They are not all the same kind of problem, which matters for how they get fixed:

* `SupportsUrn` is a Protocol used as a parameter bound — arguably *should* be
  exported, since a caller implementing it needs to name it.
* `ComponentRole` and `ApiVersion` are enums that appear in return positions,
  so a caller matching on one has to spell the value rather than the member.
* `AncestorMap`, `ObsQuery` and `ValueSet` are returned objects a caller holds
  and calls methods on — the strongest case for exporting.
* `AnyAgg` is query-DSL adjacent and may be intentionally internal.

The check above is ~15 lines and could become a test, which would stop the list
regrowing. That is probably the better first move: freeze the current seven as a
known set, fail on an eighth, then work the list down.
