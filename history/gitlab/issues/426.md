### 2026-10-08

## Measured, and the query-shape half landed (!514)

Profiled in isolation on a census-shaped flow (18 enumerated dimensions), per `docs/design/caching.md` rule zero. The cost reproduced: `get(flow)` 4.0 ms, `get(dsd)` 6.2 ms, `binding_for` 2.0 ms, `binding_for` + `dsd` 12.1 ms.

**The slow line is the statement count, not the work.** `binding_for` + `dsd` issued 16 statements; 11.2 of the 12.1 ms was in SQL, and every statement was a primary-key lookup returning a few rows. DuckDB has a fixed per-statement floor: `SELECT 1` is 130–180 µs, and a PK lookup on a 22-row table is 380–440 µs. Thread count barely moves it (threads=1 saves ~50 µs). The #411 pandas probe adds ~50 µs per bound parameter on top.

**Two lookups were repeated on every artefact:**
- `get_artefact` read the type from the spine row, then every reader read the same row again;
- name and description were two `localized_text` queries.

The lazy facades also opened a cursor and ran `SET search_path` on every construction.

**!514 removed those:** the spine is read once and handed to all 24 readers, name and description come from one query, and the facades reuse the caller's cursor.

| | before | after |
|---|---|---|
| `get(flow)` | 6 stmts, 4.0 ms | 4 stmts, 3.0 ms |
| `get(dsd)` | 7 stmts, 6.2 ms | 5 stmts, 5.2 ms |
| `binding_for` | 3 stmts, 2.0 ms | 2 stmts, 1.5 ms |
| **`binding_for` + `dsd`** | **16 stmts, 12.1 ms** | **11 stmts, 9.8 ms** |
| lazy codelist construction | 6 stmts | 2 stmts |

`tests/unit/test_get_statement_count.py` pins the exact count per kind, with the resolver cache warm. All five tests fail on the old readers.

**Folding further does not help.** One statement for spine + name + description measured *slower* than two simple ones: 2.3 ms as a `LEFT JOIN … FILTER`, and 4.7 ms with correlated subqueries, against 1.1 ms. DuckDB's per-statement cost grows with plan complexity. The remaining 11 statements each do necessary work.

## Deferred

- **A per-flow cache** (options 1/2) is the only way to most of the remaining ~10 ms, and it is deliberately *not* done now. It would need invalidation on add/remove of the flow, DSD or binding, and a decision about shared mutable artefacts (copies vs. a do-not-mutate contract). Revisit with a consumer measurement if ~10 ms still matters after 0.66.2.
- **Option 3 (rebind a root to the current thread)** is not done either. It is an API addition rather than a cache, and goes with the cache decision.
- **Option 4 (mark pandas absent)** stays rejected, for the reasons in #411. The fix belongs upstream in duckdb-python.

Leaving this open for the cache decision.
