# Issue #254: Annotation filters duplicate rows: one item, two annotations of a type, two results

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-09 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `bug`, `dsl`, `tests` |

Found by the #248 differential properties, on a generated hierarchy whose single node carried two annotations of the same type.

## The defect

Annotation predicates in both query DSLs compile to `JOIN sdmx.annotation`. A join multiplies rows, so an item carrying *n* matching annotations of the requested type is returned *n* times:

```python
repeated = Annotations([Annotation(type="note", title="x"), Annotation(type="note", title="x")])
h = Hierarchy(..., tree=[HierarchicalCode(id="A", annotations=repeated)])

lazy.nodes.filter(node.annotations["note"] == "x").ids()
# ['A', 'A']   — expected ['A']
```

Measured on both DSLs and on all three materialisers:

| Call | Result |
| --- | --- |
| `HierarchyNodeQuery.ids()` | `['A', 'A']` |
| `HierarchyNodeQuery.collect()` | two `HierarchicalCode` objects, same id |
| `len(HierarchyNodeQuery)` | `2` |
| `CodeQuery.ids()` | `['A', 'A']` |

Two annotations of one type on one item is legal SDMX — the model stores `Annotations` as a list and repetition is how SDMX expresses multi-valued reported metadata. This is not a pathological input.

It also breaks a law the DSL otherwise obeys: `filter()` must return an ordered *subset* of the unfiltered query. `test_filter_result_is_an_ordered_subset` asserts exactly that, and had to have annotation predicates excluded from its draw to stay green.

## Why it was not fixed in #248

The join is not an implementation detail. `sdmxlib.sql.CompileContext` is exported at the top level as `sl.CompileContext` and its documented contract is that annotation predicates append to `ctx.join_sqls` / `ctx.join_params` and dedup through `ctx.join_aliases`:

> The implementation may add to ``ctx.join_sqls`` / ``ctx.join_params`` via `join_aliases` dedup as a side effect of compilation.

`code_query.Predicate.to_sql` repeats it, and the whole point of that seam is that pinaxlib composes its predicates with sdmxlib's in one compilation pass. Changing how annotation predicates compile is a change to a published cross-library contract, and does not belong inside a test-coverage issue.

## The fix

Compile annotation predicates as a correlated `EXISTS` rather than a join:

```sql
EXISTS (SELECT 1 FROM sdmx.annotation ann
        WHERE ann.owner_urn = hn.node_urn
          AND ann.annotation_type = ?
          AND ann.title = ?)
```

and, for `annotations[type,lang]`, the same with `annotation_text` joined *inside* the subquery.

This is semantics-preserving for the question the predicate asks. The existing behaviour is already existence-scoped — the join is inner, so an item with no annotation of that type is absent from the result even under `!=` — and `tests/support/hierarchy_oracle.py` documents that scoping as the modelled semantics. `EXISTS` states it directly instead of achieving it as a side effect of a join, and cannot multiply rows.

Note `contains`/`starts_with`/`ends_with` need the `ESCAPE '\'` clause carried into the subquery; the #222 fix applies inside `EXISTS` exactly as it does outside.

## Scope

- `model/hierarchy_query.py`: `_emit_eq` and `_emit_string_match` annotation branches; `_ensure_annotation_join` / `_ensure_annotation_text_join` become dead and the `join_sqls` / `join_params` / `annotation_join_aliases` plumbing threaded through six functions goes with them.
- `model/code_query.py`: the same two branches and the same two helpers, but the plumbing stays — it reaches `CompileContext`, which is public.
- Decide and document what `CompileContext.join_sqls` means once sdmxlib no longer writes to it. Emitting nothing is compatible with every consumer that splices an empty list, so this is a docs question rather than a breaking change — but leaving the docstring claiming a side effect that no longer happens is worse than either.
- `_emit_subquery_predicate` in both modules raises `NotImplementedError` for annotation predicates inside `.any(...)`, on the grounds that they "would require annotation joins inside the EXISTS subquery". With `EXISTS` there is no such requirement, so that restriction lifts. Remove the guard and cover the newly working case, or keep it deliberately and rewrite the message — do not leave an unreachable raise.

## Test gates

- `test_annotation_filters_do_not_duplicate_rows` in `tests/unit/test_properties_hierarchy_query.py` is `xfail(strict=True)` against this issue; it must flip to passing, and the marker comes off.
- `test_annotation_predicates_agree_with_oracle` compares sets today, with a comment pointing here. Restore it to the exact list comparison every other differential property uses.
- Restore annotation predicates to the draw in `test_filter_result_is_an_ordered_subset`.
- Add the equivalent duplicate-row coverage on the `code_query` side.
- Assert the emitted SQL for a two-annotation-type filter contains no `JOIN sdmx.annotation`, so a future change back to a join is caught at compile time rather than by row counts.
