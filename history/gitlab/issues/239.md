# Issue #239: SDMX-ML 2.1 container artefacts lose their identity: StructureSet and HierarchicalCodelist

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Labels | `bug` |

SDMX-ML 2.1 groups certain artefacts inside a *container* that is itself a maintainable, with its own id, agency, version and name. SDMX 3.0 removed both containers and promoted their contents to top-level artefacts. sdmxlib follows 3.0, so on reading 2.1 it keeps the contents and discards the container's identity — and on writing 2.1 it invents a replacement.

This is the last remaining fidelity gap in the checked-in corpus (#237). With it resolved, every 2.1 fixture round-trips.

## What is actually lost — smaller than it looks

The fidelity harness reports 42 differences across three fixtures, but that count is misleading: the container's id appears in the path of every descendant, so changing it makes every child path mismatch. The **contents are intact**. Verified element-by-element:

```
minimal.xml        StructureSet   in : id=SS_TEST  name='Test Structure Set'
                                  out: id=SS_SYNTHETIC name='Synthetic structure-set wrapper'
                                  children in and out: CodelistMap(MAP_FREQ)   ← identical

complete.xml       StructureSet   same substitution

with_hierarchy.xml HierarchicalCodelist
                                  in : id=HCL_GEO name='Geographic hierarchy'
                                  out: id=HCL_GEO name='Canada → provinces → cities'
```

So the loss is exactly: **the container's `id` and its `name`**. For `HierarchicalCodelist` the id survives by coincidence — the fixture gives the inner `<Hierarchy>` the same id as its container — and only the name is replaced, by the inner hierarchy's own name.

Two containers are affected:

| 2.1 container | contents sdmxlib keeps | what is lost |
| --- | --- | --- |
| `<StructureSet>` | `CodelistMap` → `RepresentationMap`, `ConceptSchemeMap`, `CategorySchemeMap`, `StructureMap` | container id, name, and the grouping (which maps travelled together) |
| `<HierarchicalCodelist>` | `Hierarchy` (0..n) | container id, name, and the grouping |

The **grouping** is the part worth thinking about beyond the two scalars. A `StructureSet` says "these four maps belong together"; flattening loses that association even when every map survives, and re-emitting puts all maps into one synthetic set regardless of how the input divided them. A document with two structure sets comes back as one.

## Why this is not the same as #235

#235 is about a container SDMX 3.0 *requires* (`MetadataStructureComponents` with its `MetadataTarget`/`ReportStructure` layer) that our model cannot fill, so writing means inventing mandatory content. Here the container is **2.1-only** and its contents map cleanly onto 3.0 artefacts we already model; what is missing is a place to put the container's own identity. That makes it a smaller and more optional problem.

## Options

1. **Accept and record.** Add `KNOWN_GAPS` entries for `structureset.id`, `structureset.name`, `hierarchicalcodelist.name` and the grouping, with the reasoning above. Zero code. Honest, but it is user-supplied data being dropped, which is exactly what #237 sets out to stop — so this only holds if the data is judged not worth carrying.

2. **Carry the container identity on the contained artefacts.** A `container_id` / `container_name` on `RepresentationMap`, `StructureMap`, `ConceptSchemeMap`, `CategorySchemeMap` and `Hierarchy`, populated on 2.1 read and used to reconstruct the grouping on 2.1 write. Restores all three losses including the grouping, costs five optional fields, and adds a 2.1-shaped concept to a 3.0-shaped model — which is the cost worth arguing about.

3. **Model the containers as first-class 2.1-only artefacts.** Faithful, and much heavier: two new maintainables, message fields, storage, and a decision about what `to_xml(version="3.0")` does with them.

4. **Refuse on read.** Disproportionate here. Refusing to parse any 2.1 document containing a `<StructureSet>` would reject the project's own `complete.xml` fixture and, presumably, a good deal of real 2.1 output, in order to preserve an id and a name.

Option 2 looks like the best ratio: it is the smallest change that satisfies the criterion, and the fields are inert for anyone working in 3.0. Option 1 is defensible if the answer is "nobody round-trips 2.1 structure sets".

## Note on the reported count

If option 1 is chosen, the harness needs the container id excluded from path construction, or the three real losses will keep presenting as 42 and drown later findings. That is a comparator change, not a code change, and should be made either way once the decision is recorded — the current number overstates the problem by an order of magnitude.
