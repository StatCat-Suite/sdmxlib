# Issue #514: Path-keyed trees: broader(id) returns None where depth_of(id) raises

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-20 |
| Closed | 2026-10-21 |
| Milestone | %26 Found by the docs audit: correctness and refusals |
| Labels | `bug`, `model`, `needs-design`, `priority::medium` |

Since #439, `Hierarchy`, `CategoryScheme` and `MetadataStructure` are keyed by **path**. A bare id is refused by some verbs and silently answered by others:

```python
h.depth_of("ON")   # KeyError: 'ON' is not a path in Hierarchy
h.broader("ON")    # None, silently
```

Code written before #439 (`h.broader("OTTAWA")`) keeps running and returns `None`, as if `OTTAWA` were a root. That's the stale-call shape #439 was meant to surface.

**Fix:** every path-taking verb (`broader`, `narrower`, `*_transitive`, `get`, …) should treat an unknown path the way `depth_of` does. The exception is `get`, which documents `None` for "absent". Check each verb on all three trees, plus the lazy `LazyHierarchy`.

Found in the docs audit (!662 / !665).

## Comments

### 2026-10-20

I looked at this before changing it, and the premise needs correcting. The behaviour is **uniform**, not inconsistent. Probed on main, every tree form treats an unknown key the same way:

| | `broader` | `narrower` | `*_transitive` | `depth_of` |
|---|---|---|---|---|
| `Codelist` (id-keyed) | `None` | `[]` | `[]` | `KeyError` |
| `Hierarchy` (path-keyed) | `None` | `[]` | `[]` | `KeyError` |
| `LazyCodelist` | `None` | `[]` | `[]` | `KeyError` |
| `LazyHierarchy` | `None` | `[]` | `[]` | `KeyError` |

The walks document "empty for an unknown path" (`_tree.py`). `depth_of` raises only because it has to return an `int`.

The hazard the issue names is still real. Code written before #439 that calls `h.broader("OTTAWA")` with an id gets `None` silently. Fixing it is a cross-cutting API decision, though:

1. **Every walk raises on an unknown key**, in all four forms. This catches stale id calls. It's breaking, and the lazy forms need an existence check per call (one more query), because a SQL filter naturally answers empty.
2. **Path-keyed trees only raise**, when the key isn't a path but *is* some node's id: "'ON' is a node id; did you mean 'CA.ON'? Use `by_id`". This catches exactly the #439 migration mistake and leaves "absent means empty" alone. Codelists are unaffected.
3. **Keep the current behaviour**, and document the #439 hazard in `upgrading.md`, which already says hierarchies are keyed by path.

I'd lean towards (2). It's narrow, catches the real mistake, and doesn't change what "absent" means. I haven't implemented anything. Labelled `needs-design`.

### 2026-10-21

Decision: **option 2.** Path-keyed trees raise when a key isn't a path but is some node's id, naming the path(s) it could mean and `by_id`. Absent still means empty, and codelists are unaffected.
