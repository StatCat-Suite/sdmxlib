# Issue #240: A <Ref> without @package is silently dropped, though the schema makes it optional

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-21 |
| Labels | `bug` |

`WriterHelpers.ref_el_to_urn` requires both `package` and `class` on a `<Ref>` element and returns `None` without them. The caller then stores `None`, so the reference vanishes — no exception, no warning, and a document that validates against the XSD.

## The schema makes them optional

```
RefBaseType      class=optional   package=optional
ConceptRefType   class=optional fixed="Concept"      package=optional fixed="conceptscheme"
```

Across the 2.1 schemas, `package` is **optional on 81 ref types and required on 10**. On the typed refs it is `fixed`, which is XSD's way of saying "you may omit this; the schema supplies the value". A producer that relies on that is emitting valid SDMX-ML, and sdmxlib drops the reference.

## Reproduction

```xml
<str:ConceptIdentity>
  <Ref agencyID="AG" maintainableParentID="CS" maintainableParentVersion="1.0" id="CONTACT" class="Concept"/>
</str:ConceptIdentity>
```

Schema-valid — `package` is optional and fixed on `ConceptRefType`. Parsed, the containing attribute's `concept` is `None`.

Found while building the 2.1 MetadataStructure fixture for #236: the fixture omitted `package`, every attribute came back with no `ConceptIdentity`, and the write boundary then refused the artefact for a reason that had nothing to do with the actual defect.

## Why it has not bitten in practice

The checked-in ECB fixtures all emit `package`, and so, apparently, do the registries sdmxlib has been tested against. That is luck rather than design — nothing in the format requires it.

## The fix is not one line

`resolve_ref` already knows the artefact class the caller expects (`Concept`, `Codelist`, …) and could supply the missing values, which is exactly what the schema's `fixed` does. But the model only carries `sdmx_package` / `sdmx_class` on **maintainables**:

```
ConceptScheme: package='conceptscheme' class='ConceptScheme'
Concept:       package=None            class=None
Codelist:      package='codelist'      class='Codelist'
Code:          package=None            class=None
```

Item classes have neither, and item refs are precisely the case that fails (a `ConceptIdentity` names an item). So the fix needs either those class variables added to the item classes, or an explicit item-class → (package, class) table. The former is more consistent with how maintainables already work.

## Scope

Applies to every `<Ref>` in every SDMX-ML version, not just 2.1 or just concepts. Worth a targeted test per ref *kind* rather than one example, since the failure is silent and the surface is wide.
