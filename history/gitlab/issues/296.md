# Issue #296: dsl-27: filter()/sort_by() after limit()/offset() is ambiguous and answers silently

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `bug`, `design`, `dsl` |

Measured:

```
sdmxlib  q.filter(even).limit(3) -> [C0, C2, C4]
sdmxlib  q.limit(3).filter(even) -> [C0, C2, C4]     same
polars   lf.filter(ev).head(3)   -> [C0, C2, C4]
polars   lf.head(3).filter(ev)   -> [C0, C2]         different
```

We answer the first reading — filter the whole set, then cap — because every clause lands in one `SELECT` and `WHERE` runs before `LIMIT`. That is well-defined. It is **not unambiguous**: someone writing `.limit(3).filter(p)` in that order plausibly meant "of the first three, the ones matching p", and gets a different answer with no signal.

Being well-defined and being unambiguous are not the same thing, and the DSL currently trades on the confusion.

## Django refuses, and is right to

```
qs[:5].filter(is_active=True)  ->  TypeError: Cannot filter a query once a slice has been taken.
qs[:5].order_by("id")          ->  TypeError: Cannot reorder a query once a slice has been taken.
```

The largest declarative query builder in Python treats exactly this combination as an error rather than picking a reading.

## We are better placed to refuse than Django is

Django's error can only say "don't". Ours can point at the other reading, because it is already expressible and already tested:

```python
q.limit(3).filter(even)                                # today: [C0, C2, C4]
q.filter(code.id.is_in(q.limit(3).select(code.id)))    # the other reading: [C0, C2]
   .filter(even)
```

Verified — the nested form returns polars' answer. So the guard is not a capability removal; it is a demand that the caller say which of two available things they meant.

## Contrast: where Django got this wrong and we already got it right

`values()` / `annotate()` in Django is order-dependent and silent:

```
values("is_active").annotate(n=Count("id"))  ->  SELECT is_active, COUNT(id) AS n
annotate(n=Count("id")).values("is_active")  ->  SELECT is_active
```

Different SQL, no error. Our equivalent already raises (`group_by() cannot follow sort_by()/limit()`). So raising here is consistent with the guard we already have, not a new kind of behaviour.

## Scope

- `filter()` and `sort_by()` raise `ValueError` when the query already carries `limit` or `offset`, on all four query classes.
- The message names the fix: put the clause before `limit()`, or nest with `is_in(...)` for the other reading. Both spellings in the message.
- Guard reachable from the refinement principle (#293) rather than argued afresh: the pair is not order-independent under either reading, so it is not a legal composition.

## Test gates

- Both orders of every affected pair, on all four DSLs.
- The message names `is_in`, and the spelling it names actually runs — asserted, not just matched as a string.
- The legal orders are unaffected: `filter().limit()` and `sort_by().limit()` keep working and keep their current results.

## Comments

### 2026-08-10

Pulled forward into #293 and implemented there.

Not a scope decision — the property #293 asks for **proved the principle is false without this guard**, on its first run:

```
q.limit(1)                    ['0']
q.limit(1).filter(id != '0')  ['1']    <- a row the query being refined did not contain
```

So this is a hard violation of monotonicity, not merely an ambiguity as the issue framed it. #293's deliverable is "write the principle down and enforce it", and the principle could not be written down truthfully while this composition was allowed. Landing them separately would have meant shipping a stated principle the code contradicts, which is the failure #293 exists to prevent.

Implemented as `reject_after_slice` in `_query_common`, called from `filter()` and `sort_by()` on all four query classes. `descendants_of` is covered because it delegates to `filter`. `limit`/`offset` after a slice stay legal — they are refinements, and paging is made of them. `with_annotations` is unguarded: it changes what is hydrated, not which rows.

The message names both fixes, and `test_the_message_recommends_a_spelling_that_actually_runs` executes the `is_in` nesting it suggests rather than string-matching it.
