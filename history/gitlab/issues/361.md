# Issue #361: Model Process / ProcessStep — the IM's pipeline and provenance artefact

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-10-21 |
| Milestone | %23 Full information-model coverage: every maintainable artefact type |

`Process` is the SDMX artefact for "this thing was produced from those things,
by this step". We do not model it. Raised because it is the right home for
pipeline metadata — recording that a codelist was derived, by what, from what.

## What the schema gives you

Identical in 2.1, 3.0 and 3.1 apart from namespace and the usual 3.x
`urn`/`Link` additions — one shape, three targets.

| Type | Contents |
|---|---|
| `ProcessType` | Maintainable + `ProcessStep*` |
| `ProcessStepType` | Nameable + `Input*`, `Output*`, `Computation?`, `Transition*`, nested `ProcessStep*` |
| `InputOutputType` | Annotable + `ObjectReference` + `@localID` |
| `ComputationType` | Annotable + `Description+` + `@localID`, `@softwarePackage`, `@softwareLanguage`, `@softwareVersion` |
| `TransitionType` | Identifiable + `TargetStep` (local step ref) + `Condition+` + `@localID` |

`ObjectReference` is a reference to **any** SDMX artefact — 2.1 spells it
`ObjectReferenceType` (a `<Ref>` substitution head), 3.x spells it
`UrnReferenceType` (URN text). That is the same 2.1-vs-3.x split
`_helpers.resolve_ref` already handles everywhere else.

So "codelist A was transformed into codelist B by a pandas script" is a
`ProcessStep` with `Input` → A's URN, `Output` → B's URN, and a `Computation`
carrying the description plus `softwarePackage="pandas"`,
`softwareVersion="2.2"`. `Transition` adds conditional branching between steps,
which makes it a graph rather than a list.

## What we already have, and why it is not this

Two mechanisms in the model describe derivation *declaratively*:

* **`CodelistExtension`** (3.0) — codelist + inclusive/exclusive code selection
  + prefix. "B is A minus these codes, prefixed." Modelled.
* **`RepresentationMap` / `StructureMap` / `ConceptSchemeMap`** — code-to-code
  and structure-to-structure mappings, with per-mapping validity. Modelled.

Both say *what the relationship is*. Neither says *how it was produced, by
what software, in what order*. `Process` is the provenance one.

The third neighbour is **VTL** (`TransformationScheme`, `Transformation` =
`Expression` + `Result` + `@isPersistent`, and `VtlMappingType` which binds VTL
aliases to a Dataflow, Codelist or Concept). That is executable transformation
rather than recorded provenance, and it is also unmodelled — six of our
remaining gaps. pysdmx models that family in full if we ever want a reference.

## Scope

Following the path `HierarchyAssociation` took, which is the closest comparable
maintainable added after the initial model:

* `model/process.py` — `Process`, `ProcessStep`, `InputOutput`, `Computation`,
  `Transition`. One recursive `ItemList`-ish tree; `ProcessStep` is Nameable,
  not maintainable, so it follows `HierarchicalCode` rather than `Codelist`.
* `model/message.py` — a `processes` slot, plus `all_artefacts`.
* `model/__init__.py`, `sdmxlib/__init__.py` — exports.
* Readers and writers ×3 (`sdmx_ml21`, `sdmx_ml30`, `sdmx_ml31`), with the
  shared parts in `sdmx_ml/_common.py` — the section already has a fixed
  position in every `StructuresType` sequence (after `Constraints` in 2.1).
* SDMX-JSON: `_structure_dto.py`, `_structure_ingest.py`, `writer.py`,
  `reader.py`.
* `storage/`: `_kinds.py` (`ArtefactKind`), `schema.py` DDL, `writers.py`,
  `readers.py`. The recursion needs a parent-id column like the hierarchy
  tables use.
* `query/accessors.py` + `_edges.py` if it should be queryable.
* Tests: `tests/support/maximal.py` (which then makes the #354 census cover it
  automatically), round-trip + XSD fixtures per version, storage round-trip.

Sixteen source files and roughly a dozen test files, on a well-trodden path.

## The honest caveat

**Nobody publishes it.** Probed: Global Registry 404, OECD 501, ECB/BIS/IMF
404. And neither pysdmx nor sdmx1 models it — it is one of the five artefacts
both reference implementations skip.

So this would be implemented against the XSD with no interoperability partner
to test against. That is fine for writing our own pipeline metadata into our
own store and reading it back — the round-trip guards in #354/#359 would cover
it properly — but nobody else will consume it, and no live cassette can prove
we read theirs correctly.

Worth doing if pipeline provenance is a real requirement. Not worth doing for
IM-completeness alone, on this evidence.
