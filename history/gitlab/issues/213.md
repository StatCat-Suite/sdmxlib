**Phase 1**, independent of everything else — it needs only the suite as it stands.

Coverage says the line *ran*. Mutation says a test *noticed*. We have 91% and no idea which.

## Why this is worth doing here specifically

Ad-hoc mutation testing was used three times in the suppression-audit milestone and changed the outcome each time:

- The #210 section-binding guard: de-genericising the factory (the one edit that silently restores the old unchecked behaviour) made the test fail — proving the guard was real rather than decorative.
- In !207 and !208, running new tests against `main`'s source separated *behaviour-change* tests from *documented-behaviour* tests, which is the same question at coarser grain.

Formalising it is the natural next step. Only **5 of 94** test files use mocks, so mutants will be caught by real behaviour rather than by assertion-on-a-mock — the condition under which a mutation score actually means something.

## Scope: a bounded pilot, not a rollout

Do **not** attempt the whole codebase. 12,790 statements → a five-figure mutant count. Pilot on a slice that is pure, fast, and already claims high coverage, so the mutation score directly interrogates the coverage number:

| Module | Statements | Line cov |
| --- | --- | --- |
| `model/urn.py` | 52 | **100%** |
| `model/istring.py` | 50 | 98% |
| `model/expr.py` | 41 | 88% |
| `model/representation.py` | 61 | **100%** |
| `model/collections.py` | 197 | 92% |
| `model/validation.py` | 254 | 97% |

~655 statements. The two at 100% are the sharpest question in the milestone: **is a 100% covered module actually pinned?**

## Feasibility notes measured today

- Suite is 50 s, but **33 s is two concurrency tests**. Deselect those (see #test-2) and a full run is ~17 s — the number that decides whether mutation testing is tractable at all.
- mutmut 3.x selects tests per mutant from coverage data, so per-mutant cost should be far below a full-suite run. Verify this in the pilot rather than assuming it.

## Deliverables

- `mutmut` in the dev group with an upper bound, per the CLAUDE.md checker-pinning rule.
- Config committed (`setup.cfg` / `pyproject.toml`) scoping paths and the test command.
- `just mutate` recipe. **Local only** — CI is manual and cost-constrained, so this must never become an always-on job.
- **A written report in the MR**: mutation score per module, wall-clock, and — the actually useful part — a list of *surviving mutants that represent real test gaps*, separated from equivalent mutants.

## The decision this issue exists to inform

Whether mutation testing earns its place. Record the answer either way; a well-evidenced "not worth it at this cost" is a successful outcome and feeds #test-8. Note briefly whether `cosmic-ray` would fit better, but do not evaluate it in depth unless mutmut fails.

## Test gates

- Pilot completes and reports a score for each of the six modules.
- Every surviving mutant triaged: *real gap* / *equivalent* / *won't fix*, with reasons.
- No change to production code in this issue — findings become follow-ups.

## Comments

### 2026-08-06

Pilot complete — see !219.

**807 mutants, ~11 min at 1.2/s. Mutation score 78%** (552 killed / 153 survived / 69 timeout / 26 segfault / 7 no-tests).

**The question this was scoped to ask came back yes.** `urn.py` and `representation.py`, both at 100% line coverage, produced **zero** surviving mutants; `expr.py` too. Those modules are genuinely pinned.

Survivors, all in three modules: `validation.py` 123, `collections.py` 27, `istring.py` 3. Roughly a third sit in `__repr__`/`__hash__`/`_format` — formatting and diagnostics, where a survivor says little. The rest are real; the clearest is `validate_references` surviving `type(artefact).__name__` → `None`, meaning nothing asserts the class prefix in the issue paths it emits. 97% line-covered, diagnostics unpinned.

Two setup findings recorded in the config, both of which cost time:

- `source_paths` must be the import root (`"src"`), not the package dir — mutmut inserts it into `sys.path`, so `"src/sdmxlib"` makes `sdmxlib/_duckdb.py` shadow duckdb's own `_duckdb` extension. I first called that a latent sdmxlib footgun; **it was my misconfiguration**, corrected.
- `mutate_only_covered_lines = true` is unusable here: its coverage pass runs pytest in-process and leaves duckdb unimportable. Off, with the cost documented — uncovered lines get mutants too, so 78% is a floor.

Local only, never CI. `just mutate` / `mutate-results` / `mutate-show`.

Baseline recorded for the #218 re-run after the Hypothesis work.
