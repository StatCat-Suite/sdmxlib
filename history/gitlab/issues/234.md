# Issue #234: MetadataMessage was serialised without validation, and emitted invalid 3.0 headers

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-21 |
| Labels | `bug` |

Found by completing the #223 spec-coverage matrix. `MetadataSet` and `MetadataProvisionAgreement` were its last two rows, and neither is a `StructureMessage` field — they ride in `MetadataMessage`, the other envelope sdmxlib serialises, which the field-keyed coverage guard cannot see.

That envelope had no generative coverage and **no schema validation of emitted XML at all**. No new compiler was needed: `SDMXMessage.xsd` is the entry point for the whole version, `<mes:GenericMetadata>` included. The schema was compiled and sitting there the whole time; nobody had ever pointed a metadata document at it.

## Fixed

1. **`serialize` never validated a `MetadataMessage`.** It returned early for that envelope, so metadata payloads reached the wire with no check of any kind — neither well-formedness nor writability. Every finding below was reachable only because this did not exist.

2. **The 3.0 header put a metadataflow URN in the MSD slot.** `GenericMetadataStructureType` is a *choice* of three elements, each restricted to one artefact kind by a pattern facet:

   | element | carries |
   |---|---|
   | `<com:Structure>` | a MetadataStructure URN |
   | `<com:StructureUsage>` | a Metadataflow URN |
   | `<com:ProvisionAgreement>` | a ProvisionAgreement URN |

   The writer always emitted `<com:Structure>`. It first tries to resolve the set's structure ref through to its MSD, so a fully-resolved graph happened to produce the right URN — but any unresolved ref fell back to the ref's own URN in the MSD slot, emitting a document every 3.0 consumer rejects. The element is now chosen from the URN's artefact class, and a class with no header slot (an unresolved `MetadataProvisionAgreement` — the choice offers only the *data* `ProvisionAgreementReferenceType`) is refused rather than mis-filed.

3. **A `MetadataSet` must name at least one target.** `MetadataSetType` sequences choice(flow|provision), `Target` (1..n), `Attribute` (1..n). SDMX-JSON agrees. The model defaulted `targets` to empty, so a set that reported metadata about nothing serialised silently.

4. **`MetadataSet.version` defaulted to a value with no SDMX-JSON form.** The metadata schema pins `VersionType` to strict semver (`x.y.z`); the *structure* schema states no pattern at all, which is why this bites only here. `version` is **optional** in that schema — the SDMX-TWG's own `constructed-sample.json` omits it and validates — so our reader defaulting the absent field to `"1.0"` and the writer then emitting it turned a valid input into an invalid output. The default is now `"1.0.0"`, and the JSON reader reads the fallback back off the model rather than restating the literal, so the two cannot drift.

## Recorded, not fixed

SDMX-ML 3.0 carries a reported value as element text with **no type marker** — the type comes from the MSD, which the message does not carry — so `int`, `float` and `bool` all read back as `str`. SDMX-JSON has native types and preserves all five. That is a genuine format asymmetry rather than a reader bug, so it is in `KNOWN_GAPS` with the citation.

## Coverage added

- `metadata_sets()` and `reported_attributes()` strategies, the latter generating **non-unique sibling ids** (repetition is sibling attributes sharing an id, never a values list) and **recursive children**, since those are the two shapes the model is explicit about.
- A schema-validated round-trip property over both formats comparing the whole attribute *tree*, not just top-level ids.
- A `MetadataMessage` completeness guard, mirroring the `StructureMessage` one.
