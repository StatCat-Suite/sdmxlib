## Surfaced by

MR !87 (hierarchy execution test coverage). Worth flagging as a usability gap distinct from the coverage work.

## Behaviour today

The hierarchy query DSL exposes \`node.annotations[type] == value\` for filtering. The SQL emitter binds the comparison to the \`annotation.title\` column (\`src/sdmxlib/model/hierarchy_query.py:686\`):

\`\`\`python
if isinstance(field, _AnnotationField):
    alias = _ensure_annotation_join(...)
    return f\"{alias}.title {op} ?\", [pred.value]
\`\`\`

\`Annotation\` has two value-bearing fields:

- \`title: str | None\` — plain string
- \`text: InternationalString\` — the localised value, SDMX convention

The DSL only sees \`title\`. A user who follows the SDMX convention and puts the value in \`text={\"en\": \"Province\"}\` (no title) gets **zero matches with no error or warning**.

## Why this matters

This is the SDMX convention: localised values go in \`text\`, plain identifiers in \`title\`. Most upstream SDMX-ML / SDMX-JSON payloads carry their meaningful annotation data in \`text\`. Users who roundtrip a real payload and then try to filter by it silently see nothing.

## Proposed shape of a fix

Either:

1. **Extend the DSL** to support \`node.annotations[type,\"en\"] == value\` — language-tagged predicate against \`text\`. The SQL would join the existing \`annotation\` table plus the localised-text table the writer emits to.
2. **Auto-fallback**: if a node has no \`title\` but has \`text\`, the title predicate transparently matches against text language values. Risk: surprising semantics.
3. **Document and raise**: keep the current behaviour but raise a clear error if a node has \`text\` but no \`title\` and a predicate is built. Worse UX but prevents silent failure.

(1) is the cleanest match for the existing \`node.name[\"en\"]\` shape — same accessor pattern, language-tagged.

## Acceptance

- A test that exercises \`node.annotations[type,\"en\"] == \"Province\"\` matches a node whose annotation has \`text={\"en\": \"Province\"}\` and no \`title\`.
- The existing title-based filter continues to match.

## Comments

### 2026-06-01

**Audit follow-up**: this same bug exists in `code_query.py` — the Codelist filter DSL.

`src/sdmxlib/model/code_query.py:761`:
```python
return f"{alias}.title {op} ?", [pred.value]
```

And the `_AnnotationField` docstring there even says "`code.annotations[type]`" — same pattern, same gap. `code.annotations[type] == value` only sees `Annotation.title`, not `Annotation.text`.

Any fix to this issue should cover both DSLs since they share the predicate shape.

## Wider audit findings (no other silent-failure sites)

Surveyed all istring-bearing fields across the model + format layers:

- `name[lang]` accessors on both `code` and `node` DSLs **correctly require a language tag** at the call site — no silent failure path.
- `name.get(lang)` with id fallback (used by polars, code_map, dataset labelling) follows the `get(lang) or id` pattern consistently — graceful, not silent.
- `_to_istring` attrs converter accepts `dict[str, str] | InternationalString` — passing a bare `str` would later raise `AttributeError` on `.get(lang)` calls, which is noisy.
- JSON writer's `_istring_dict()` correctly materialises every present language; empty istrings produce empty dicts (cosmetic, not silent).
- Storage layer correctly persists both `Annotation.title` (column) and `Annotation.text` (per-language rows) — the gap is purely in the query DSL surface.

The annotation-title-vs-text asymmetry is the **only silent-failure site** the audit found.
