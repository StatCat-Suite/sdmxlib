# Issue #309: DataProvider.contacts and MetadataProvider are declared in the model and never persisted

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-14 |
| Closed | 2026-08-14 |
| Milestone | %17 Query DSL: a second backend, and the evidence the first one lacks |
| Labels | `bug`, `model`, `storage` |

Two organisation-side storage gaps, both found by inventory during the %306 coverage pass rather than by anything failing.

## 1. `DataProvider.contacts` is dropped on write

```python
DataProviderScheme(..., providers=[DataProvider(id="ECB", contacts=[Contact(name={"en": "Desk"})])])
# the contact is gone
```

`sdmx.agency_contact` is keyed by `agency_urn`, there is no `data_provider_contact` table, and `put_data_provider_scheme` never reads the field — it writes `(provider_urn, scheme_urn, provider_id, name, description)` and stops. `Agency.contacts` **is** persisted, so the two halves of one concept behave differently.

Same class of defect as #307 (`Concept.parent`): a model field with no storage behind it, silent on read and on round-trip.

Guarded meanwhile by `test_query_contact.py::test_a_data_providers_contacts_are_not_persisted`, which asserts the current behaviour so a fix flips a test rather than passing unnoticed.

### Scope

Either widen `agency_contact` to a polymorphic `organisation_contact(owner_urn, ...)`, or add a sibling table. The first is probably right — `Agency` and `DataProvider` are both `Organisation` in the IM and the contact shape is identical — but it changes an existing table, so it wants a decision.

## 2. `MetadataProvider` is not persisted at all

`sdmx.metadata_provision_agreement.metadata_provider_urn` points at a relation that does not exist. SDMX 3.0 has `MetadataProvider` and `MetadataProviderScheme`; this schema has neither a table nor a writer, so the column holds a urn nothing can resolve.

The data twin is fine — `provision_agreement.data_provider` resolves to `sdmx.data_provider` — so the asymmetry reads as a missing accessor when it is a missing table. `q.metadata_provision_agreement` therefore exposes `metadataflow` and no provider hop, with the reason in `NOT_EDGES` and in `test_query_msd.py::test_the_metadata_provider_is_not_reachable`.

### Scope

- `MetadataProviderScheme` writer + `metadata_provider` table, mirroring `data_provider`
- then `Edge("metadata_provider", "metadata_provision_agreement", ...)` and the accessor hop

Note the `data_provider` edge was itself mis-declared against `artefact.urn` until 54a009c — worth pointing the new one at the item table from the start.

## Comments

### 2026-08-14

Split. The two halves are different kinds of thing and were holding each other
up.

**Part 1 — `DataProvider.contacts` dropped on write.** A bug, and fixed; MR to
follow. Narrower than the issue assumed: all three format readers and writers
already carry the field correctly, so *only storage* dropped it.

Took the polymorphic option this issue leaned toward — `agency_contact` →
`organisation_contact(owner_urn, …)` — because `Agency` and `DataProvider` are
both `Organisation` in the IM with an identical `contacts` field. A sibling
table would have been a fourth copy of one shape, which is what the facet work
in !303 had just finished removing. Writer and reader each share one helper now
instead of one having the code and the other having nothing.

Two things surfaced by *running* the queries rather than reading the code:

- **A pre-existing duplication bug.** `_delete_artefact_cascade` deleted the
  `agency` rows *before* the contact cleanup that subqueries them, so the
  subquery matched nothing and contacts accumulated — one extra set per
  re-add, silently, because nothing counted them. Re-adding a scheme is the
  ordinary path, not an edge case. Fixed, and part 1 would otherwise have
  extended it to providers.
- **The polymorphic edges have to be `optional`.** A contact's `owner_urn`
  matches an agency *or* a provider, never both, so selecting both hops with
  inner joins returned **zero rows**. Both are `optional=True`; each contact
  now resolves to its owner with `NULL` for the other.

**Part 2 — `MetadataProvider`** is now #315. It is not a bug: the class does
not exist anywhere in `src/` except two comments explaining its absence. No
model, no `MetadataProviderScheme`, no format support, no table. Building it is
a feature of comparable size to #307, and leaving it here keeps a closeable bug
open behind it.

Worth noting the two halves *do* connect, in the fixer's favour: #315 will need
somewhere to put a metadata provider's contacts, and part 1 has just made
`organisation_contact` polymorphic, so that is already there.

Suggest closing this once part 1's MR merges.
