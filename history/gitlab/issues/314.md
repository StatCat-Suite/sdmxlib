Split out of #304. **Root-caused — see below. What is open is the fix, not the
diagnosis.**

## The cause

**polars' rayon thread pool does not survive `fork()`.** Sampled a hung child:

```
duckdb .pl()
  → DuckDBPyRelation::ToPolars
    → polars from_arrow_record_batches
      → rayon_core::ThreadPool::install
        → rayon_core::latch::LockLatch::wait_and_reset
          → _pthread_cond_wait          ← forever
```

`fork()` copies the parent's memory but only the calling thread. rayon's pool
state comes across; its workers do not. The child calls `install()` and waits
on a latch nothing will ever signal.

mutmut runs its stats pass **in the parent** before forking, so any test
selection containing a polars-executing test poisons every subsequent child.

### Reproduced in 20 lines, no mutmut

```python
reg.query(q.code).select(q.code.id).collect()   # parent: initialises rayon
pid = os.fork()
if pid == 0:
    build().query(q.code).select(q.code.id).collect()   # child: deadlocks
```

Warm the parent with `.ids()`, or with nothing, and the child exits cleanly.
Only `Frame.collect()` — the polars path — poisons the fork. Raw duckdb `.pl()`
outside sdmxlib does not reproduce it on a 20-row table; the pool has to have
been used for real work first.

### It explains every observation

| selection | `Frame.collect()` calls | result |
| --- | --- | --- |
| `test_query_compile` + `test_query_trimming` | 0 | 48 s, 0 timeouts |
| `test_query_select` | 13 | deadlock, 0% CPU |
| `test_query_group_by` | 5 | deadlock, 0% CPU |
| 14 files at once | many | 205 "timeouts" in 706 |

Those 205 were deadlocked children later killed by `RLIMIT_CPU`, which is
indistinguishable from a slow child — so this also reframes part of #303.

## What does not fix it

- `POLARS_MAX_THREADS=1`, `RAYON_NUM_THREADS=1`, or both. rayon builds a pool
  regardless and a one-worker pool deadlocks identically.
- Making mutmut spawn: `os.fork()` is hardcoded at
  `mutmut/__main__.py:1472`, no config knob.

## What works, and what it costs

Polars-free test selections run clean. Five groups over `_compile.py`, 1266

| --- | --- | --- | --- |

Zero timeouts throughout, 400–650% CPU sustained.

But the 453 survivors are not scattered — they are the excluded region:

```

 47 _window               28 _agg_body_from        24 compile_page
 26 _check_distinct_order 18 compile_select        16 _agg_subquery
```

The projection and aggregation compiler, top to bottom, plus keyset paging.
**Publishing 813/1266 as this module's mutation score would be worse than
publishing nothing**: it reads as a measurement of `_compile.py` and omits the
half most likely to break under #312's IR restructure.

## Options, in the order worth trying

1. **Upstream mutmut: fork → spawn.** This bug hits anyone whose tests touch
   polars, pyarrow, or any rayon-backed extension. Worth filing upstream
   whatever we do locally.
2. **`os.register_at_fork(after_in_child=...)`** in `tests/conftest.py`.
   Cheap to falsify: rayon exposes no reinit, so this probably cannot work,
   but ruling it out is minutes.
3. **Keep polars out of the parent only.** A conftest hook that makes the
   polars conversion a no-op when `MUTANT_UNDER_TEST` is unset would leave the
   stats pass clean and let children do the real thing. Test-only branching
   near library code is a real cost — and it is the only option here that
   measures the projection compiler.

### 2026-08-17

Fixed in !328 (`bb8678e`). The diagnosis in this issue was right about rayon and wrong about the source, in two ways that changed the fix.

**The polars use is on the write path, not the query path.** The child hangs inside `validate()` → `_check_item_ids`, which vectorises its regex check above 64 items. So *any* test that adds a decent-sized codelist poisons the fork — not just the 18 that call `Frame.collect()`. Warming the parent with `.ids()` poisons it too, and `.ids()` touches no polars at all; the table above reads as a `Frame.collect()` count because that is what was varied, not because that is what mattered. Option 3 — no-op the Frame conversion when `MUTANT_UNDER_TEST` is unset — would therefore not have worked.

**One row is enough.** `pl.Series(["A"]).str.contains(...)` in the parent hangs the child; the pool does not have to have done real work first. Importing polars is still fine, and that asymmetry is what makes a fix possible at all.

Option 2 (`register_at_fork`) ruled out as predicted: polars exposes `thread_pool_size` and nothing that resets a pool.

**The fix** is `tools/mutmut_forksafe.py`: the parent keeps the imports and runs mutmut's three parent-side test phases (stats, clean, forced-fail) in a forked child, so it never executes a polars operation. Only the stats pass returns more than an exit code, and mutmut already serialises exactly that — the child `save_stats()`, the parent `load_stats()`.

One trap worth recording: after mutmut's mutant-generation `multiprocessing.Pool`, a forked child that *dlopens* pyarrow aborts. Stock mutmut never meets it because its parent has imported everything by then, so the tool preloads duckdb/polars/pyarrow — but deliberately **not** `sdmxlib`, which would put the real modules in `sys.modules` and have every child test unmutated code from `src/`.

**Measured**, same module and test selection:

| | killed | survived | timeout |
| --- | --- | --- | --- |
| stock mutmut | 3 | 0 | **3** |
| fork-safe | 5 | 1 | **0** |

And the run this issue says could not be done at all now completes — `_compile.py` against the three projection test files: **1290 mutants, 588 killed, 389 survived, 0 timeouts**, 7.84 mutants/second. The projection and aggregation region is measurable; triaging those 389 is #304.

`tests/unit/test_mutmut_forksafe.py` pins the three polars facts the tool rests on, each in a fresh subprocess. If polars becomes fork-safe, the middle one fails and the tool can be deleted.
