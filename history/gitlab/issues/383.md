Found decomposing `get(H_CP_GEO_FED, eager=True)` after #376 landed, asking how
much of the remaining 8.84 s is object construction. Only 34% is:

| | ms |
| --- | --- |
| nodes — lazy get + `materialize()` | 2972 |
| the codelist the refs drag in (#378) | 2195 |
| **ref walk + assignment** | **3670** |

This is one piece of that 3.67 s.

## The double walk

`_refshape.walk_fields(Hierarchy)` is:

```
('maintainer', 'levels', 'tree', '_codes')
```

and `_codes` is built by `Hierarchy.__attrs_post_init__` as
`_flatten_nodes(self.tree)` — **the same node objects**, flattened for O(1)
lookup. So a `Ref`-hunting walk reaches every `HierarchicalCode` twice: once by
recursing through `tree`, once through the flat index.

The `walked` set means the second visit returns immediately, so this is not a
correctness problem and not quadratic. It is 499,138 wasted function calls on
`H_CP_GEO_FED`, and cProfile shows it: `_collect_refs` runs **1,996,559 total
calls for 499,139 primitive** ones.

## Why `_refshape` cannot fix this on its own

`walk_fields` reads declared types, and `_codes: ItemList[HierarchicalCode]`
declares exactly what `tree` does. Nothing in the *type* says one is derived
from the other. The knowledge that `_codes` is a view rather than an
independent edge is semantic, and lives on `Hierarchy`.

That makes this the first case where the per-class shape needs an input the
class's annotations do not carry — worth noting, because #148's public
`outbound_refs()` will need the same distinction and for a better reason: a
server walking outgoing references must not emit the same node twice.

## Options

1. **A marker on the field.** `attrs` metadata — `field(metadata={"derived":
   True})` — read by `_refshape` and skipped. Local, explicit, and the
   information sits next to the thing it describes. Every other derived index
   (`_flat`, `_parent_of`, `_codes`, `_codelist_cache`) could carry it, which
   is either a virtue or a second convention to keep in step.
2. **Skip private fields by name.** `_codes` starts with an underscore, and
   CLAUDE.md's rule 1 says a private field on a domain artefact "should be a
   cache or an index, or it probably belongs on a different class". So
   `_`-prefixed *artefact* fields are derived almost by definition. Cheapest,
   and rests on a convention rather than a declaration — which is exactly the
   kind of thing that is true until it isn't.
3. **Do nothing.** It is ~0.2–0.3 s on the largest hierarchy in the bundle and
   zero on anything without a flat index. Worth measuring the actual saving
   before spending an API decision on it.

(2) is tempting and (1) is more honest. Measure first: if the saving is under
100 ms the answer is (3).

## Acceptance

- The walk visits each `HierarchicalCode` once, asserted as a **count** of
  `_collect_refs` entries per node, not wall time.
- Whichever option is taken, the reason `_codes` is skipped is written where
  someone adding the next derived index will read it.
- The saving is measured on the bundle and recorded, including if it turns out
  not to be worth the change.
