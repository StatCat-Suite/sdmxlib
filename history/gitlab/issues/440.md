## Summary

Every `datetime` field (`valid_from`/`valid_to`, `ReferencePeriod`, `HierarchicalCode` validity) holds a naive **or** an aware value depending on the source text, so an artefact read from a document is not equal to the same artefact read back from the store.

Found by the registry sweep (!516): `BIS:CPI_A_YOYCHG_FROM1950(1.0)` parses with `valid_from=datetime(1950, 1, 1)` and comes back from `LocalRegistry` as `datetime(1950, 1, 1, tzinfo=UTC)`. OECD 1,517 constraints, BIS 3 constraints + 24 HCLs + 22 hierarchies.

## Which side is wrong

The store follows `_time.py` exactly (#321: "naive in → `+00:00` out, same wall time, now labelled"). The inconsistency is upstream: `formats/_coerce.py:57-63` (`to_datetime`, a bare `datetime.fromisoformat`) returns a naive value for an unqualified `xs:dateTime`, and the model fields accept either form.

## Fix direction

Normalise in the model: one shared attrs converter on every `datetime` field (naive → `replace(tzinfo=UTC)`, aware → `astimezone(UTC)`), so `parse(...) == get(...)`. Writers will then emit `+00:00` where the source had no zone, which under `_time.py` is the same instant. Making `from_storage` return naive instead would bring back the ambiguity #321 removed.
