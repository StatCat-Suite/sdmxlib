**Phase 1** — no dependencies. The largest untested surface in the library, and the cheapest to close because the technique is already proven next door.

## The asymmetry

`model/hierarchy_query.py` is 504 statements at 90% line coverage with **zero** property tests. Its sibling `model/code_query.py` is 509 statements at 93% with 14 oracle-backed properties (`tests/unit/test_properties_code_query.py`). The two modules share a shape: `_FieldExpr` subclasses, a `Predicate` hierarchy, `_Ref` accessors that build predicates via operator overloads, and a compiler that emits SQL against a DuckDB table.

#217 scoped both modules explicitly — "Over 1000 statements … `model/code_query.py` 509 / `model/hierarchy_query.py` 504". Only the first was delivered. This issue finishes it.

Existing coverage for the module is example-based: `tests/unit/test_hierarchy_query.py` (148 lines) and `tests/unit/test_hierarchy_execution.py` (421 lines).

## Why the hierarchy side is *harder*, not easier

`hierarchy_query` has a strictly larger field set than `code_query`:

- `node_id`, `depth`, `parent_node_id` — the `code_query` analogues
- `name[lang]`
- `level` — hierarchy levels have no codelist equivalent
- `code` — the URN of the code a node points at, i.e. a **join** to another artefact
- `annotations[type]` and `annotations[type,lang]`
- `broader_transitive(depth).any(pred)` / `narrower_transitive(depth).any(pred)` — recursive CTEs with an optional depth bound

A hierarchy node is not a code: it has identity separate from the code it references, the same code may appear at several nodes, and levels are a parallel axis to depth. An oracle that assumes codelist semantics will be silently wrong.

## Scope

- Extend `tests/support/oracle.py` — or add `tests/support/hierarchy_oracle.py` if the shapes do not share cleanly — with a pure-Python evaluator over `Hierarchy` nodes. Same discipline as the existing oracle: naive, readable in one sitting, **no code shared with `hierarchy_query`**, and it re-derives depth and ancestry from `parent_node_id` rather than reading baked columns.
- Add `hierarchy_query`-shaped strategies to `tests/support/strategies.py`. `hierarchies()` already exists (line 533) — check whether it generates enough structural variety (multi-level, repeated codes across nodes, annotations) or needs a `forest_hierarchies()` sibling the way `forest_codelists()` was added for codes.
- `tests/unit/test_properties_hierarchy_query.py`, mirroring the code_query file's four sections:
  1. **Differential** — every predicate kind vs the oracle.
  2. **Algebraic** — filter idempotence, order independence, ordered-subset, roots/non-roots partition, ancestors and descendants inverse, no node is its own descendant, leaves cover the childless.
  3. **Baked-vs-traversed** — `depth` and `ancestor_ids` as written by the storage layer must equal a fresh traversal. This is the guard `docs/design/caching.md` implies for baked data and nothing currently enforces on the hierarchy side.
  4. **Oracle self-consistency** — the oracle's own ancestry must be coherent, so a failure is attributable.
- One property asserting the DSL path is actually SQL-backed (`test_the_dsl_path_is_sql_backed` has the pattern), so a silent fallback to Python iteration cannot make the differential tests pass vacuously.

## Risks

- **Oracle drift.** When a property fails, decide which side is wrong before editing either. An underspecified DSL is the most interesting third outcome and gets its own issue (that is how #222 surfaced).
- **DuckDB round-trips per example.** `test_properties_code_query.py` handles this with `_EXAMPLES = max(5, settings.default.max_examples // 5)`. Reuse the same scaling rather than inventing a second convention, so `HYPOTHESIS_PROFILE=deep` still explores hard.
- **`code` field means a join.** Generating a hierarchy whose nodes reference codes in a generated codelist is more strategy work than the codelist case. Build both in one composite strategy.

## Test gates

- A differential property for every predicate kind `hierarchy_query` dispatches over — count them in the compiler, do not estimate.
- Algebraic laws asserted without reference to the oracle.
- Baked `depth` / `ancestor_ids` compared against traversal.
- Any divergence triaged as *SQL bug* / *oracle bug* / *underspecified DSL*.
- Property runtime reported in the MR description alongside the existing code_query property runtime.
