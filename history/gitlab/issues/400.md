## Comments

### 2026-09-10

## Not a version problem — every DuckDB reads it the same

Ran the repro across seven builds, isolated envs, same file:

| duckdb | `artefact_type = 'Codelist'` |
| --- | --- |
| 1.5.0 / 1.5.1 / 1.5.2 | 1 of 19 |
| 1.5.3 (was installed) | 1 of 19 |
| 1.5.4 / 1.5.5 (latest) | 1 of 19 |
| 1.6.0.dev379 (nightly) | 1 of 19 |

So upgrading does not fix it, and the "1.5.3 regression" hypothesis in the
description is **wrong** — the fault is in the file, and every reader honours
it. The floor moved to `duckdb>=1.5.5` anyway, on its own merits, with a
comment saying it is not the fix for this.

## Where the damage is

`pragma_storage_info('artefact')` on the affected file:

```
rg 0  artefact_type  VARCHAR  start 0  n 733  Dictionary
      [Min: Categori, Max: Metadata, Max String Length: 20]
```

One dictionary-compressed segment, 733 slots for 698 live rows (rowids run
34…732 — the gaps are deletes). The pushdown scan returns rowid 696 alone
where 696 and 699–716 all hold `'Codelist'`. The rows are intact; the metadata
the scan prunes with is not.

Not repairable in place by the obvious means — `CHECKPOINT`, `FORCE
CHECKPOINT` and reopening all leave it lying. `CREATE TABLE … AS SELECT * FROM
artefact` comes back correct, which confirms the rows are fine and it is the
stored segment that is wrong.

## sdmxlib does not appear to cause it

Could not reproduce from our own write path: a fresh write, three re-ingests,
and six rounds of add-30 / delete-26 churn across close-and-reopen all stay
clean, checked over every distinct value of `artefact.artefact_type`,
`concept.scheme_urn` and `code.codelist_urn`. So this is not the delete-then-
insert cascade, and I have no minimal repro to send upstream — a bug report
whose attachment is a 911 MB file is not worth much.

## The bundle can be repaired from itself, losslessly

**This is the actionable part.** The read only loses rows because it is
*filtered*; disable pushdown for the read and the rebuild is exact:

```python
cur = duckdb.connect(src, read_only=True)
cur.execute("SET search_path='sdmx'")
cur.execute("SET disabled_optimizers='filter_pushdown'")   # the whole point
urns = [r[0] for r in cur.execute("SELECT urn FROM artefact ORDER BY urn").fetchall()]
arts = [readers.get_artefact(cur, u, eager=True, lazy_conn=cur) for u in urns]
```

Verified against the real bundle — every table matches:

| table | source | rebuilt |
| --- | --- | --- |
| artefact | 698 | 698 |
| code | 582,977 | 582,977 |
| concept | 349 | 349 |
| annotation | 585,675 | 585,675 |
| hierarchy_node | 1,876,557 | 1,876,557 |
| metadata_attribute | 56 | 56 |

Contrast the same rebuild *without* that line: `concept` 349 → 0,
`metadata_attribute` 56 → 0, `annotation` 585,675 → 583,898. So no StatCan
refetch is needed — ~50 s, and it lands on schema 2.19 as a side effect.

`just ci` is green on duckdb 1.5.5 against a bundle repaired this way, with
all 13 structural bundle assertions running rather than skipping.

## Correction to this issue's description

It says the bundle holds 699 artefacts; it holds **698**. The unfiltered spine
read was right all along, so !477's "698 artefacts" needs no correction — only
!476's "627 MetadataSets", which is 628, because that one filtered on
`artefact_type`.

### 2026-09-10

Compacted, verified, and swapped: **1.66 GB → 0.81 GB, 51 % smaller** — and
smaller than the damaged original it replaces (911 MB).

The repair had to copy the file and let the 2.18 → 2.19 migration rebuild only
`sdmx`, so that `pinax` survived; DuckDB reuses freed blocks but never shrinks
a file, so the dropped schema's blocks stayed in it. `COPY FROM DATABASE`
carries schemas, tables, constraints, indexes, sequences and views across in
one statement, so neither schema's DDL had to be restated anywhere.

Nothing was swapped until the new file matched the old on every one of these:

| | before | after |
| --- | --- | --- |
| tables (`sdmx` + `pinax`) | 72 | 72 |
| rows | 4,949,279 | 4,949,279 |
| constraints | 267 | 267 |
| indexes | 45 | 45 |
| sequences / views | 2 / 1 | 2 / 1 |
| schema version | 2.19 | 2.19 |
| #400 scan probe | passes | passes |

`just bench-bundle-assertions` against it: **21 passed**, the full tier
including the observation half.

The 1.66 GB intermediate is gone — keeping it would have made a compaction
that saved no disk. What is left in the bundle directory:

* `meta.duckdb` — 808 MB, repaired, compacted, on 2.19
* `meta.duckdb.2.18.bak` — 911 MB, **the original damaged file**, untouched

That backup is the only copy of the file this issue is about. Worth keeping
until #400 is settled upstream or abandoned — it is the only artefact anyone
could send to DuckDB — and it is 911 MB whenever you want it gone. It cannot
be opened by sdmxlib either way: `ReadOnlySchemaError` refuses it on the
version, and `check_scan_integrity` would refuse it after that.
