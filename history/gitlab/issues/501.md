## What happened

The registry sweep re-run on 2026-10-19 (cache from 2026-10-09, `main` at 15ec20a) refuses **all 99 of IMF's 3.0 hierarchies** (12,279 nodes):

> `<HierarchicalCode>: node … names level …, which its hierarchy does not define`

On 2026-10-15 the same hierarchies were read, and only each node's `Level` was dropped. !626 (#458) made `_common.node_level` refuse instead, because both readers used to drop such a reference **silently**.

## IMF's data

Each hierarchy has `hasFormalLevels="false"` and defines no levels at all. Every node carries `<structure:Level>` holding a bare number (`0`–`5`). The 3.0 XSD says `Level` "references a formal level defined within the hierarchy", so this is IMF's defect. The numbers are not derivable either: only 3,417 of the 12,279 equal the node's nesting depth.

## Decision

Read the hierarchy, drop the dangling reference, and **record it as a read loss** (`StructureMessage.lost`, a `LOSSES` row in `formats/sdmx_ml/_losses.py`):
- `strict=False` keeps the tree;
- `lossless=True` refuses it;
- nothing is silent.

This is how other content the model cannot hold is handled. Refusing cost everything else a hierarchy says, for one unresolvable reference per node.

## Done when

- `node_level` returns no level for an undefined one.
- A `LOSSES` row per SDMX-ML generation counts exactly the dangling references (2.1's `<Ref>` form and 3.x's text form), with an injection in `test_read_losses.py`.
- The two reader tests that pinned the refusal pin the loss instead.
- The sweep summaries are refreshed, and IMF's hierarchies read.
