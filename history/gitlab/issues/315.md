# Issue #315: MetadataProvider is not modelled at all — the MPA's provider urn points at a relation that does not exist

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-14 |
| Closed | 2026-08-21 |
| Milestone | %17 Query DSL: a second backend, and the evidence the first one lacks |
| Labels | `model`, `storage`, `type::feature` |

Split out of #309, whose first half — `DataProvider.contacts` dropped on write
— is a bug and is fixed. This half is not a bug: it is an SDMX 3.0 class the
library does not model at all, and building it is a feature.

## What exists today

Nothing, except two comments explaining the absence:

```
src/sdmxlib/query/_edges.py:468       # There is no `metadata_provider` table…
src/sdmxlib/query/accessors.py:1372   …nothing persists one
```

No model class, no `MetadataProviderScheme`, no format reader or writer, no
table. `MetadataProviderScheme` **is** in the vendored 3.0 XSDs
(`SDMXStructureOrganisation.xsd`, and referenced from `SDMXStructure.xsd`), so
this is real spec surface rather than something the standard leaves open.

## The visible symptom

`sdmx.metadata_provision_agreement.metadata_provider_urn` is `TEXT NOT NULL`
and holds a urn nothing can resolve. The model types the field
`Ref[object]` — deliberately, "mirroring `ProvisionAgreement.data_provider`" —
and the writer stringifies whatever urn it is given:

```python
provider_urn = str(mpa.metadata_provider.urn) if mpa.metadata_provider is not None else ""
```

So the column is populated and dangling. The **data** twin is complete —
`provision_agreement.data_provider` resolves into `sdmx.data_provider` — which
is exactly why the gap reads as a missing accessor when it is a missing
relation.

## Why it went unnoticed

Same shape as #307 and #309's first half, one level up: a column that points
somewhere, and nothing to point at. An unresolvable urn is not a crash, it is
an absence, and absences do not fail tests.

## Scope

1. `MetadataProvider` + `MetadataProviderScheme` in `model/organisation.py`,
   mirroring `DataProvider` / `DataProviderScheme`. Both are `Organisation` in
   the IM, so `contacts` comes along — and #309 just made
   `organisation_contact` polymorphic on `owner_urn`, so there is already
   somewhere to put them.
2. Both SDMX-ML readers and writers, plus SDMX-JSON.
3. A `metadata_provider` table mirroring `data_provider`, its writer and
   reader.
4. `Edge("metadata_provider", "metadata_provision_agreement", …)` and the
   accessor hop.
5. Narrow `MetadataProvisionAgreement.metadata_provider` from `Ref[object]` to
   `Ref[MetadataProvider]` once the class exists.

**Point the edge at the item table, not the spine.** The `data_provider` edge
was mis-declared against `artefact.urn` until 54a009c and matched zero rows —
a provider's urn lives in `sdmx.data_provider`, never in `sdmx.artefact`. The
same trap is waiting here.

## Test gates

- Round-trip through every format and through storage, in one test rather than
  per-leg: #307 showed a per-leg test passes throughout such a bug's life.
- `test_query_msd.py::test_the_metadata_provider_is_not_reachable` flips from
  asserting the gap to asserting the hop.
- The `NOT_EDGES` entry for `metadata_provision_agreement.metadata_provider_urn`
  is removed rather than reworded.

## Comments

### 2026-08-20

**Audit note — still valid, and more visible after #362.**

Confirmed against current `main`: no `MetadataProvider` model class, no
`MetadataProviderScheme`, no reader, writer or table. The two comments the
description cites are still the only trace.

What changed is the surrounding context. #362 wired
`MetadataProvisionAgreement` into `StructureMessage` and gave it 3.0 / 3.1 /
SDMX-JSON readers and writers — it had been modelled and storable but with a
`msg_field` naming a slot no message had, so nothing could produce one.

That makes this gap load-bearing rather than theoretical. An MPA now round-trips
through three formats, and `metadata_provider` is `Ref[object]` pointing at a
class the library cannot resolve — so the reference survives as a URN and
`ref()` can never return anything. #362 also added
`_check_metadata_provision_refs`, which *requires* the provider ref to be
present for 3.0/3.1, because `MetadataProvisionAgreementType` declares it
`minOccurs=1`. So every conformant MPA we write names an artefact we do not
model.

The XSD pins the scheme id, which is worth recording for whoever implements
this: `MetadataProviderReferenceType` matches
`.+\.base\.MetadataProvider=.+:METADATA_PROVIDERS\(.+\).+` — the scheme is
always `METADATA_PROVIDERS`, exactly as `AGENCIES` and `DATA_PROVIDERS` are
fixed for their schemes.

Demand evidence, from the IM-coverage audit: `metadataproviderscheme` 404s on
the SDMX Global Registry, and none of OECD / ECB / BIS / IMF publishes one.
pysdmx and sdmx1 both model it. So it is real spec surface with no live
publisher — same position as most of the unmodelled artefacts.
