## Context

The scale benchmark (`just bench-compete-scale`) shows pysdmx reading SDMX-JSON codelists about 5× faster than sdmxlib: UNSD `CL_COMMODITY`, 68,191 codes, 97 ms against 478 ms. That was measured before !592 (lazy losses).

Most of that gap is fidelity, and stays. pysdmx keeps one name string per code, with no parent, no links and no uri, and does no validation or loss accounting. Its model is also `msgspec.Struct`, created in C, where ours is attrs. Changing that would be an architecture decision, not this issue.

This issue covers the cheap part: **work the JSON read path does twice per item**.

## Candidates (from reading the code; each to be measured first)

1. **Converters re-checking converted values.** `from_code` (`_structure_ingest.py`) builds each field, then `Code`'s attrs converters run on every field anyway (`_to_istring` ×2, `_to_annotations`, `to_links`).
2. **Two scans of the same `links` list.** `read_uri` and `read_links` each walk a code's `links`, once for the `describedby` uri and again for everything else. One pass can give both.
3. **The XML-character check runs twice.** `ingest_istr` rejects text XML cannot hold on read. Then `refuse_invalid` → `_check_name` → `_first_xml_incompatible` checks every name again.
4. **Repeated attribute lookups**, if the profile shows them, for example `ingest_annotations` on codes with no annotations.

## Approach (as for the rest of %22)

- Profile UNSD `CL_COMMODITY` JSON (68k codes) and a synthetic 500k-code codelist on current `main`.
- Attribute by ablation, not by the profiler alone.
- Only make changes that leave the code as clear as it was.
- Guard each change with a count, not a clock (`tests/unit/test_read_cost.py`).

## Done when

Each candidate is either fixed, with a measured gain and a count guard, or shown not to matter. The output is unchanged: the round-trip, census and loss tests stay green.

## Comments

### 2026-10-15

**Measured on current `main`** (after !591–!595), SDMX-JSON read of UNSD `CL_COMMODITY` (68,191 codes, 30 MB), medians of 7:

| part | time |
| --- | --- |
| `parse`, total | **265 ms** (478 ms before !592's lazy losses) |
| read-time validation (`refuse_invalid`) | 52 ms |
| typed `msgspec` decode | 30 ms |
| DTO → `Code` for every code (`from_code`) | 153 ms |
| — of which, constructing the attrs `Code`s alone | 77–89 ms |
| — of which, the ingest helpers (names, links, uri, annotations) | ~65 ms |
| pysdmx `read_sdmx(validate=False)`, total | 80 ms |
| pysdmx constructing its `Code`s alone (`msgspec.Struct`) | 6.6 ms |

**Reading of it:**
- **This issue's target** is the ~65 ms of ingest helpers, plus whatever of the 52 ms of validation repeats checks the read already made (the XML-character check).
- **Out of scope here:** constructing an attrs object costs about 12× a `msgspec.Struct` (77 vs 6.6 ms for 68k codes), and that's the largest single part of the gap. Changing it means moving the model off attrs, an architecture decision for its own issue if wanted.
