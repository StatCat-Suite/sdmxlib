**Phase 3** — depends on #test-5. The most valuable Hypothesis target in the codebase, and the one that needs a technique other than round-tripping.

## Why these two modules

| Module | Statements | Line cov |
| --- | --- | --- |
| `model/code_query.py` | 509 | 93% |
| `model/hierarchy_query.py` | 504 | 90% |

Over 1000 statements — among the largest in `src/` — that **compile a filter DSL to SQL and execute it in DuckDB**. Two properties of that shape make it the ideal property-testing target:

1. **A pure-Python oracle is easy to write.** `codelist.codes` is an in-memory `ItemList`; any filter expressible in the DSL is also expressible as a Python predicate over that list. Generate a codelist and a filter, run both, compare. This is *differential testing*, and it is far stronger than asserting an expected result set, because the oracle is independent of the SQL emitter.
2. **The DSL composes**, so it has algebraic laws worth asserting directly:
   - `filter(a).filter(b)` equals `filter(a & b)`
   - `filter(a).filter(b)` equals `filter(b).filter(a)` (order independence)
   - `filter(x)` is idempotent
   - `partition(p)` yields disjoint halves whose union is the input
   - a filter's result is always a subset of the input
   - `descendants_of(x)` never contains `x`; ancestors and descendants are inverse relations

## Hierarchy properties specifically

`model/hierarchy.py` (253 statements, 99%) and the query layer encode a tree. Trees have strong invariants that fixtures test one shape at a time:

- no cycles reachable via `parent_id`
- `depth` equals the length of `ancestor_ids`
- `ancestor_ids` is exactly the path to the root, in order
- a node is its own ancestor's descendant
- `_applicable_hierarchies` is stable under codelist reordering

`depth` and `ancestor_ids` are **baked at build time** (per the CLAUDE.md caching rule, which prefers baking over runtime caching). Baked data can go stale relative to the structure it summarises — a property comparing baked values against a fresh traversal is exactly the guard that rule implies but nothing currently enforces.

## Scope

- `tests/support/oracle.py` — a pure-Python evaluator for the subset of the DSL under test. Deliberately naive; it is a specification, not an implementation, and must not share code with `code_query`.
- Differential properties: generated codelist + generated filter, SQL result equals oracle result **as a set and as an order** where the DSL promises order.
- The algebraic laws above, as standalone properties.
- Hierarchy invariants, including baked-vs-traversed `depth` / `ancestor_ids`.

## Risks

- **Generating valid filters is the real work.** A strategy over DSL expressions needs to produce well-typed queries against the generated codelist — a filter on a nonexistent annotation type is a different test. Build the codelist and the filter together in one composite strategy.
- **Oracle drift.** If the oracle is wrong, properties fail for the wrong reason. Keep it small enough to read in one sitting, and when a property fails, decide which side is wrong *before* editing either.
- **DuckDB round-trips per example are slow.** Reuse one in-memory connection across examples and measure; if it dominates, cut `max_examples` for these specific properties rather than dropping them.

## Test gates

- Differential property covering every predicate kind the DSL supports — `_emit_predicate` dispatches over 11, so all 11.
- Algebraic laws asserted independently of the oracle.
- Any divergence triaged as *SQL bug* / *oracle bug* / *underspecified DSL*, with the third being the most interesting outcome and worth its own issue.
- Runtime for these properties reported separately; they will be the slowest in the suite.
