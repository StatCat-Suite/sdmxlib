`CompileContext` is the public cross-library compile seam. Four of its five fields are currently dead in `src/`, and the reasons differ — one was real and got obsoleted, two were never used. Worth writing down before anything else is built on it.

## Measured, on `main`

| | |
| --- | --- |
| `CompileContext` constructed in `src/` | **1 place** — `code_query._compile` |
| `hierarchy_query` uses it | **never** |
| `ctx.next_alias()` called in `src/` | **never**, in its entire history |
| `ctx.schema()` called in `src/` | **never** |
| `ctx.join_sqls` / `join_params` / `join_aliases` written | **never, since #254** |
| `SqlRelation` used | **yes** — produced by `CodeQuery.to_sql`, consumed by `ComponentFilter` |

## How each got here

**The join accumulators were real, and #254 retired them.** From `0fa6baf`, the commit that created `sdmxlib.sql`:

> `CompileContext` — state threaded through one compilation pass: row alias, accumulated joins, join-alias dedup map. **Same pattern as the existing `annotation_join_aliases` in code_query** — lifted up so pinaxlib reuses it (multiple `has_code` filters on the same codelist share one join).

They existed because annotation predicates compiled to `JOIN sdmx.annotation`, and two predicates on the same type had to share one join alias. #254 converted those to correlated `EXISTS`; each is self-contained, so there is no join to share and nothing to dedup. This is a traceable consequence of a deliberate change, not drift.

**`next_alias` was speculative.** From `1d6b4a8`:

> Predicate compilers (sdmxlib's CodeQuery internals, pinaxlib's filter classes, future cross-library compilers) all need a way to generate unique SQL aliases for correlated subqueries.

Checked every commit that touched it: zero callers outside `sql.py`, ever. The emitters derive aliases positionally instead — `f"{row_alias}_anc"`, `f"{row_alias}_ann"` — which is deterministic, self-documenting, and nests correctly (`c_desc_anc`). The counter was never reached for.

**`schema()`** is the same shape: logical-to-physical remapping for federation that has not arrived.

## What would revive them

**`join_sqls` — annotation-valued `sort_by`, which is live in #259.**

```python
q.sort_by(code.annotations["geo_level"])
# NotImplementedError: Annotation-typed sort keys aren't supported
```

`EXISTS` cannot serve this: `ORDER BY` needs a *value*, not a boolean, so reaching a side table for sorting requires a real `LEFT JOIN` — and the dedup need returns the moment a caller sorts by two annotation types. If #259 closes that gap by implementing rather than by making it unrepresentable, the accumulators are live again.

**`next_alias`** would revive if aliases stop being derivable from `row_alias`. The positional scheme has survived nesting so far, including the `.any()` subqueries #262 builds on, so this is not imminent.

**`schema()`** would revive if federation spans catalogs with differing schema names.

## What to decide

Not "delete the dead fields". The point is that each should carry a written reason for existing in its current state, so the next person neither prunes something one feature away from being needed nor assumes `join_sqls` works and finds it silently empty.

- Document each field with: currently unused, what used it, what would revive it.
- Decide whether `Predicate` (the Protocol) should keep advertising a join side effect no sdmxlib predicate performs — #254 softened the wording; this issue is whether the contract should say more.
- Reconcile with #267's `RowKind` work, which parameterises `CompileContext`. That change should land on a seam whose purpose is stated rather than inferred, which is why this is filed first.

## Not in scope

Deleting `CompileContext` or collapsing it into `RowKind`. It carries `row_alias`, which is genuinely used, and the join accumulators are one #259 decision away from mattering again.
