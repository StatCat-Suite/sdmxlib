# Issue #330: store observations sorted at ingestion — for pruning and cheaper sorts, not to skip the sort

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-17 |
| Closed | 2026-10-19 |
| Labels | `data`, `design`, `perf` |

Came out of asking how `chunk_rows` should be sized for `stream()` (!345). The measurements say something more useful than the sizing rule.

## Measured, DuckDB 4M rows x 3 columns

Peak RSS above the loaded table, streaming through `to_arrow_reader(50_000)`:

| storage | query | `preserve_insertion_order` | peak | output in key order |
| --- | --- | --- | --- | --- |
| shuffled | plain scan | true (default) | 41.6 MB | **no** |
| **sorted** | plain scan | true (default) | **36.2 MB** | **yes** |
| **sorted** | plain scan | **false** | 36.3 MB | **no** |
| sorted | `ORDER BY` | true | 102.4 MB | yes |
| shuffled | `ORDER BY` | true | 250.6 MB | yes |

Three conclusions:

1. **Sorting at ingestion does not let DuckDB skip a sort.** It has no read-in-order optimisation for base tables. But it makes the sort **~2.5x cheaper** (251 -> 102 MB), because sorting nearly-sorted input is nearly free.
2. **A plain scan of a sorted table came back in key order — but only because `preserve_insertion_order` defaults to true.** Set it false, which is exactly what you would do for a very large result, and the ordering vanishes while memory is unchanged. So the free ordering is a side effect of a setting, **not a property to build an API contract on**.
3. Sorted storage also scans slightly cheaper (36 vs 42 MB), from compression and locality.

## What other systems do

Worth knowing which group DuckDB is in, because it decides whether "store it sorted" can ever remove the sort:

* **ClickHouse** — the table's `ORDER BY` *is* the primary index, and `optimize_read_in_order` lets a query sorted by a prefix of it stream with no sort at all. The gold standard for this exact problem.
* **Postgres** — an index scan yields rows in index order, so `ORDER BY indexed_col` needs no sort; `CLUSTER` aligns heap order for locality.
* **Iceberg / Delta** — declare a **sort order** (Iceberg `sortOrder`, Delta `OPTIMIZE ZORDER BY`) as a *layout* property. Its job is file pruning and compression; engines generally still sort for a query's `ORDER BY`, though Spark can exploit bucketing plus sortedness in some plans.
* **BigQuery** — clustering prunes, does not eliminate sorts.
* **Parquet** — row-group metadata can declare `sorting_columns`; most readers ignore it.
* **DuckDB** — measured above: no read-in-order. Same group as Iceberg/BigQuery.

The consistent industry answer is the split this issue proposes: **physical sort order is a write-time layout decision for pruning and compression; a stream should not ask the engine to sort.**

## Proposal

1. **Add a sort order to `DataflowBinding`.** It already declares `partition_layout` ("drives partition pruning at query time") and has no counterpart for ordering — Iceberg carries both, and for the same reasons. Natural default for SDMX: the series key then the time dimension, which is also the common access path.
2. **Sort in `write_observations`** to match it.
3. **Do not** change what `stream()` emits: it stays unordered unless asked (!345), because conclusion 2 says the incidental ordering cannot be relied on.
4. Consider `preserve_insertion_order=false` for the streaming cursor — it did not move memory in this test, so measure before adopting rather than assuming the DuckDB guidance applies here.

## Not in scope

Whether the *structural* tables should be sorted. They are small, and the `__key__` tiebreak there costs nothing measurable at codelist sizes.

## Comments

### 2026-08-17

Implemented in !346. `DataflowBinding.sort_order` declares it, `write_observations(sort_by=…)` does it, SCHEMA_VERSION 2.11 → 2.12.

**Ingestion cost, measured** (source rows deliberately unsorted):

| rows | plain write | sorted write |
| --- | --- | --- |
| 1M | 9 ms, 34.5 MB | 23 ms, 110.9 MB |
| 4M | 33 ms, 131.6 MB | 82 ms, 341.6 MB |

≈2.5x wall clock and ≈2.6–3.2x peak RSS. The sort buffer is the whole table, so the write peak scales with the write size — which is the case *against* doing it unconditionally, and why `sort_by` is opt-in rather than driven off the binding automatically. A load that is already memory-constrained should decline it; DuckDB will spill rather than fail, but spilling a large sort is its own cost.

Against that, from the query side: `ORDER BY` at 102 MB instead of 251 MB, scans at 36 MB instead of 42 MB, and better pruning. Pay once at write for every read.

**Not implemented, and worth its own issue if it matters:** sorting *within partitions* rather than globally. Iceberg and Delta both sort within files precisely because a global sort's buffer scales with the table while a per-partition sort's scales with a partition. `partition_layout` is already on the binding, so the machinery to do it per partition is half there — one INSERT per partition value, each sorted. That would keep most of the pruning benefit at a bounded write cost, and is the obvious next step if ingestion memory ever becomes the binding constraint.

### 2026-10-19

Done in 171a2aa (2026-08-17): every point of the proposal landed.

1. `DataflowBinding.sort_order` is declared beside `partition_layout` (schema 2.12; `storage/schema.py`, `readers.py`, `writers.py`).
2. `write_observations` sorts to match, via `sort_by` (`local/data_store.py`). It is opt-in rather than automatic, because sorting on write cost about 2.5x time and 2.6x peak memory at 4M rows. The measurements are in the docstrings.
3. `stream()` still emits unordered rows, and a test pins it.
4. `preserve_insertion_order=false` was measured: the ordering goes and the memory does not move.

Sorting *within* partitions, and compaction after appends, were left as separate questions in that commit.
