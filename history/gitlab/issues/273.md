# Issue #273: dsl-22: formalise the IR/SQL boundary — what the design brief gets right, and what it does not

Umbrella for formalising the boundary between *what the caller asked for* and *what we emit*. Prompted by an external design review brief; this issue records what of it applies, what does not, and what was decided.

## The actual problem

`CodeQuery` is simultaneously the fluent user-facing object **and** the intermediate representation. There is nowhere to stand between the two, which means:

- **Canonicalization has no home.** #270 needs a form where `filter(a).filter(b)` and `filter(b).filter(a)` are the same value. Doing that at construction makes the IR stop being a faithful record of what the caller wrote; doing it at compile needs a pass that does not exist.
- **Nothing between the ends is testable.** We test IR→SQL by equivalence (`tests/support/sql_corpus.py`) and IR→results differentially (the oracles). There is no third representation to test *to*, so any optimisation has to be justified by end-to-end behaviour alone.
- **Optimisations have nowhere to live.** #271's registered-relation path and #270's canonical ordering are both rewrites, and both currently have to be smuggled into either construction or emission.

The staging discipline the brief argues for is the transferable idea, and it is a better argument than any of its performance claims:

```
surface DSL  →  logical IR  →  normalized IR  →  SQL text
  (partial)      (total)         (total)          (total)
```

## What of the brief applies, and what does not

**Applies.**

- Total functions from IR onward — already tracked as #259 (15 raises remain on the emit path).
- A normalization pass as a separate, individually-testable stage, with `normalize(normalize(q)) == normalize(q)` as a law.
- Two of its six named rewrites are real here: `In(d,[]) → False` (**done**) and `In(d,[c]) → Eq(d,c)` (**not done** — we emit `IN (?)`).

**Does not apply, and forcing it would be a mistake.**

- The brief assumes one builder and it is an OLAP builder — scans, joins, aggregates, rollup selection, partition pruning. `code_query` / `hierarchy_query` are *filter* DSLs over a single relation: `Filter + Sort + Limit + Project` over one `Scan`, with no joins and no aggregation. Four of its six rewrites (filter pushdown below Project/Join, projection pruning, limit pushdown, subquery flattening) have nothing to act on.
- Its `Having` vs `Filter` and `GroupBy` vs `Aggregate` failure mode cannot occur here: there is no aggregation.
- The CTE-chain emission strategy (§8) is pure overhead for a `Filter+Sort+Limit` shape.
- The cache-key section is written for a consumer that has a cache. sdmxlib has none; it lands here as a *requirement from downstream*, which is #270.

**Where the brief's sharpest sections actually land** is a surface it never mentions: the data plane. `ComponentFilter.to_where_clauses` returns SQL *fragments*, and `local/data_store._build_query` concatenates strings with caller-supplied `where` / `order_by` / `columns` spliced in. That is the syntax-modelling failure mode it describes, and it is where joins, aggregation and DuckLake actually live. Any IR work should start there or explicitly declare it out of scope — not silently apply data-plane reasoning to the structural DSLs.

## Decided

**We build our own SQL from our own IR. Not Ibis.**

The structural DSLs are roughly 120 lines of emitters over a single table with no joins and no aggregates; taking a large dependency to express `WHERE code_id = ?` is not a trade worth making, and the SDMX-specific lowering (hierarchy walks over baked `ancestor_ids`, annotation `EXISTS`, the label folds) is the substance rather than the wrapper. Revisit only if the data plane grows real aggregation, and revisit *for the data plane*, not for these.

## What this issue is for

Sequencing and scope, not implementation. The concrete work is #270 (canonical form), #271 (relation threshold), #272 (literal typing), #259 (total functions). This issue decides:

- Whether a named IR type separate from `CodeQuery` is worth introducing, or whether canonicalization at construction is enough. **#270 should be attempted first without a new IR** — if it lands cleanly, this issue may close with no further structure.
- Whether the data plane gets the same treatment, and whether it shares the representation.
- Where normalization sits if it is introduced, and what its laws are.

## Not in scope

Test coverage (%13 owns it), and code changes here — this issue is a decision record.

### 2026-08-09

## Prior art, measured — and it changes the recommendation in this issue

| | order-preserving surface | canonical form |
| --- | --- | --- |
| **polars 1.41** | expression (`meta.eq` → **False**) | optimized plan — **identical** for both orders |
| **SQLAlchemy 2.0** | SQL text — differs | cache key — **also differs; no canonicalization** |

**polars implements exactly the staging this issue is about**, and independently of the design brief: the expression is a faithful record of what the caller wrote, and a separate optimize pass produces a canonical plan. Both `filter(a).filter(b)` and `filter(b).filter(a)` converge on one optimized plan while remaining distinct as expressions.

That is a working existence proof from a library under the same constraints, and it resolves the open question in #270 — canonicalize **in a pass**, not at construction, so the IR keeps the caller's intent for error messages and debugging.

**It therefore reverses the recommendation above.** This issue currently says #270 should be attempted first without introducing a named IR stage, on the grounds that a sort key at construction might be enough. polars suggests that is the wrong shape: construction-time canonicalization buys the cache key by destroying the faithful record, and the library that has actually solved this kept both.

Revised sequencing: #270 lands *with* a normalization stage, not before one. The stage can be minimal — one rewrite (canonical predicate ordering) plus the idempotence law — and grow if #271 or `In(d,[c]) → Eq` justify it.

SQLAlchemy is the counterexample worth keeping in view: it caches compiled statements built by the same code path in the same order, so order-sensitivity costs it nothing and it has never bothered. The reason we cannot copy that is the consumer's cache is result-shaped and HTTP-fed, not statement-shaped.

### 2026-08-10

## Decided: no separate IR for the structural DSLs

Recorded durably in `docs/design/query-composition.md` rather than only here — a decision record in a comment is the "written down nowhere" failure this milestone keeps hitting.

### The test this issue set, run

> #270 should be attempted first without a new IR — if it lands cleanly, this issue may close with no further structure.

It lands. Predicates are frozen attrs: hashable, and sortable by a derived key `(type name, fields)` — not by `<`, so it needs an explicit key function, but that is a sort key rather than a redesign. Nothing but the emitted clause order reads predicate order, so canonicalizing at construction costs no fidelity that anything consumes. The one complication the issue anticipated — order-sensitive sort keys — dissolved when #294 made `order_by` replace; details on #270.

### The coverage evidence needs correcting

The self-correction comment above rests on a survey taken before #275 (projection + aggregation), #276 (artefact spine) and #281 (reported metadata). Re-measured by attempting each named consumer shape against today's DSL: **13 of 18 are expressible.**

Notably `"find dataflows using concept X"` — called the most common discovery query in an SDMX catalog, and credited with most of the 21+22+8 `dsd_component`/`dataflow`/`concept` sites — is now `artefact.uses_concept(...)`. So "2 of 16 tables and ~33% of sites" understates current coverage substantially.

The five remaining gaps are **not rewrites an IR would enable** — they are node kinds we do not have, each a feature decision of its own:

| gap | needs |
| --- | --- |
| `COALESCE(name[?], id) AS label` | expression-valued projection |
| `list(annotation.title)` per code | array aggregation over a side table |
| cross-schema join | joins over caller tables |
| `PIVOT` | a reshaping node |
| `ROW_NUMBER() OVER` | window functions |

The array-aggregation one is a *refusal*, not a gap: annotations reach the row by correlated `EXISTS` (#254), and aggregating them means the join `EXISTS` exists to avoid.

### The data plane: same problem, different answer

Confirmed as described. `local/data_store._build_query` interpolates caller-supplied `where`, `columns` and `order_by` as SQL text, and `ComponentFilter.to_where_clauses` returns fragments — syntax-modelling, an injection surface (#257 chose to document rather than validate), and where joins and aggregation actually live.

**It should not share a representation with the structural DSLs.** Their safety property is that they never accept SQL text at all: a caller supplies field references and literals, and since #272 even the literals are type-checked. Merging would give the safe surface a text-accepting path it does not have. Out of scope here; it wants its own issue framed as an injection-surface problem rather than an IR problem.

### Normalization

No home needed until a second rewrite exists. One of the brief's six is done (`In(d, []) -> False`), one is outstanding (`In(d, [c]) -> Eq(d, c)` — we still emit `IN (?)`), four have nothing to act on. When it is worth a pass it belongs between construction and emission, with `normalize(normalize(q)) == normalize(q)` as the law and `sql_corpus` as the equivalence check.

Closing: the structural question is answered and the remaining work is the concrete issues (#270, #271) plus feature decisions that an IR would not have made easier.
