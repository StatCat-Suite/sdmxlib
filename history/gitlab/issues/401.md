## Comments

### 2026-09-10

!481 — took option 1, and the count turned out to be cleaner than expected.

`collect()` builds one object per row and `frame()` builds none, so the tax is
the calls `collect()` makes that `frame()` does not, over rows:

| | `frame()` | `collect()` | `collect(annotations=False)` |
| --- | --- | --- | --- |
| `q.code` 579,951 | 838 calls | +26.14/row | +15.33/row |
| `q.hcode` 499,143 | 843 calls | +35.00/row | +35.00/row |

**Identical to the second decimal across three runs**, on a machine doing
other things — against 22.7 / 12.9 for the same quantity measured on the
clock. Bounds ~30 % above, per accessor rather than shared: a `Code` is
cheaper to build than a `HierarchicalCode`, and `q.hcode`'s two figures
coincide because those nodes carry almost no annotations while half of
`q.code`'s collect is the annotation read.

Sabotage-checked — six trivial calls a row takes `q.code` from 15.33 to 21.14
and trips it.

**One thing the issue did not anticipate.** Subtracting `frame()`'s calls only
measures construction while `frame()` itself does no per-row work. It does not
today — 838 calls for 579,951 rows — but that is a property of the polars path,
not a guarantee, and if it ever regained one the subtraction would quietly
cancel the very cost it exists to measure. So `test_frame_builds_nothing_per_row`
is new, bounding `frame()` flat at 5,000 calls whatever the row count, because
the claim is precisely that the number does not scale. Sabotage-checked at
1.002 calls per row.

Option 3 (widen the bound) is worth recording as rejected on evidence rather
than on taste: 22.7x observed against 16x means the next bump is guesswork,
and the count shows the true figure never moved at all — the bound was never
the problem.

Side effects: the tier is **~15 % faster** (113 s against 128 s), since
min-of-three wall timing ran each terminal nine times per case and profiling
runs three. `_timed` and both `COLLECT_OVER_FRAME` constants are gone with
their only caller. Three consecutive full-tier runs green, 23 assertions
rather than 21.

The wall figures still exist in `test_query_codes` and
`test_query_hierarchy_nodes`, which report rather than assert — and that is
also the honest answer to what a call count cannot see, namely work that gets
slower without getting more numerous. The docstring says so rather than
implying the guard is total.
