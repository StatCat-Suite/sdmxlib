# Issue #372: Hierarchy descent: the layering, not just the seam — a (dataflow_urn, code_id) relation

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-24 |
| Closed | 2026-08-25 |

> **Rewritten.** The first version asked "how does pinax rebuild hierarchy descent
> without `Predicate`" and leaned toward a relation constructor over code ids. Having
> gone back through why the old seam was shaped the way it was, that framed the wrong
> question and picked an option that cannot answer it. The layering argument below is
> the thing worth deciding.

## The original split, and why it was not arbitrary

pinaxlib's `q.has_code(dim, code)` supports hierarchy descent — "datasets using any
descendant of `CA` on `REF_AREA`". pinaxlib commit `27d0a64` implemented it in two
halves, deliberately:

- **explicit `hierarchy=`** — sdmxlib's job, through `sl.compile_code_predicate`, a
  helper written on `feat/compile-code-predicate` specifically so pinax would not own
  SDMX traversal SQL.
- **`hierarchy=None`** — pinax's job, because resolution happens *per dataflow*,
  correlated to each candidate row, and the seam could not express that.

So #306 did not remove an accident. It removed a purpose-built seam, and the half pinax
still owns is the half that never fit through it. That distinction matters, because
"pinax already owns some descent SQL" is not an argument for pinax owning the rest —
which is roughly what my first version of this issue talked itself into.

## Where the boundary actually falls

Three separable concerns:

| Concern | Domain |
| --- | --- |
| Is code X under code Y in hierarchy H? | pure SDMX |
| Which hierarchy applies to dimension D of dataflow F? | pure SDMX — `HierarchyAssociation` is a 3.0 artefact |
| For each row of `pinax.dataset`, correlate to its dataflow | pinax |

By that cut **both** descent branches are sdmxlib's, and pinax's only genuine concern
is the correlation. Today's split is not a domain boundary — it is a workaround for an
API that resolves one dataflow at a time in Python.

sdmxlib already owns the second row: `LocalRegistry.applicable_hierarchies(dataflow,
dim_id)` and `unique_hierarchy(dataflow, dim_id)`. pinax's two `LEFT JOIN`s to
`hierarchy_association` plus the `CASE`/`COALESCE` dispatch are a **reimplementation of
those semantics in SQL**, existing only because the Python versions take one flow.

## The duplication has already drifted

Given a dimension with two applicable unscoped `HierarchyAssociation`s:

- **sdmxlib** — `unique_hierarchy` raises. Ambiguity is an error.
- **pinaxlib** — silently answers "true if *any* applicable hierarchy contains the
  descent", via `COALESCE(scoped, unscoped)` inside an `EXISTS`.

Same question, two answers, today, on both mainlines. That is the cost of the
duplication, and it is the thing that gets worse if pinax simply absorbs the rest.

## Proposal: invert the direction

Rather than restoring a correlated predicate seam, let the correlation key travel
*inside* the relation. `SqlRelation` is already a multi-column join input —
`AncestorMap` is `(node_id, rollup_id)` — so nothing new is needed at the protocol
level, only a producer:

```python
reg.descendant_codes_by_dataflow(
    dim_id: str,
    root_code: str,
    *,
    hierarchy: "Hierarchy | Ref[Hierarchy] | str | None" = None,  # None => per-flow HA resolution
    include_self: bool = False,
    scope: "SqlRelation | None" = None,   # optional 1-col dataflow_urn relation, to narrow
) -> SqlRelation  # columns: ("dataflow_urn", "code_id")
```

pinax then splices it uncorrelated:

```sql
EXISTS (SELECT 1 FROM (<relation sql>) r WHERE r.dataflow_urn = d.sdmx_dataflow_urn)
```

Properties that make this work, and which I would want held:

1. **Lazy.** Returns a relation, never rows. The whole point is that a 50k-node
   geography walk stays one statement.
2. **No dataflow list up front.** `scope` is a *narrowing* optimisation, not a
   requirement. If it were mandatory, pinax would have to enumerate candidate
   dataflows client-side first — exactly what `27d0a64` was written to avoid, and
   what kills the pure relation-over-code-ids shape.
3. **Same connection.** Topology B already guarantees `sdmx.*` and `pinax.*` are
   visible together, which is why the splice is legal at all.

The HA-vs-parent-chain fallback lives inside, so sdmxlib's existing resolution becomes
the single implementation and the divergence above disappears by construction.

Whether this is best expressed through the path language (`q.dataflow.dsd.dimensions`
and the `HierarchyAssociation` row kind both exist in 0.60, and `union` is exported) or
as hand-written SQL is entirely your call — I care about the returned shape and the
laziness, not the mechanism.

## Two semantics that need deciding, not defaulting

- **Ambiguity.** With >1 applicable hierarchy: raise (matching `unique_hierarchy`),
  or take any (matching pinax today)? A relation cannot raise lazily at a natural
  point, which may itself argue for one answer.
- **Self-inclusion.** 0.50 made this an explicit flag for `ancestor_at`. Same question
  here. pinax's `within()` docstring claims self-inclusive while its SQL is
  strict-descendants — we are fixing that on our side regardless, and would rather
  match whatever you pick.

## What pinax does meanwhile

Not blocking. pinax's 0.60 upgrade (pinax!76) ships a stopgap that absorbs the explicit
`hierarchy=` branch into pinax alongside the branch it already owns — marked as a
stopgap, with the divergence documented. `q.within(dim, root, hierarchy=…)` and
`q.has_code(dim, "LITERAL")` keep their signatures under every option here, so
adopting this later is an internal swap with no public API movement.

Related: #370 — pinax calls `LocalRegistry.get(urn_str, eager=True)` in three places.

## Comments

### 2026-08-24

Went through this against the code rather than from memory. The layering argument holds, and there is a defect underneath it that the issue does not name — which changes what I would build.

## Verified, on 0.60

**1. `q.hierarchy_association.linked_object` does not resolve for a Dimension.** The edge joins `linked_object_urn → sdmx.artefact.urn`, and an item URN never appears in `sdmx.artefact` — only maintainables do. On a store with one HA linking `REF_AREA`:

```
q.linked_object.id   → null
q.linked_object.urn  → the dimension URN   # works only because the compiler trims the
                                           # join and reads the FK column directly
```

Same failure mode `_edges.py` already records against `DataProvider` ("the join matched zero rows"). So **there is no join path from an HA to the component it links**, which is exactly why pinaxlib carries:

```sql
replace(df.dsd_urn, '.DataStructure=', '.Dimension=') || '.' || ?
```

That is sdmxlib's URN grammar reimplemented in pinax SQL, and it breaks silently if item-URN spelling changes. It is the sharpest instance of the ownership problem this issue is about, and it is fixable on its own.

**2. Descent already works.** `reg.query(q.hcode).filter(q.hcode.ancestors.any(q.hcode.id == "CA"))` returns the descendants, strict. The "is X under Y in H" half needs no new machinery — only the HA half is missing.

**3. The divergence is real**, as described: `_partition_associations` (`model/hierarchy.py:460`) is the Python semantics, pinax's two `LEFT JOIN`s + `COALESCE` restate them in SQL, and they disagree on ambiguity.

## On the proposed API

Agreed on the domain cut; not on the shape.

- `descendant_codes_by_dataflow` puts the correlation concern — the half this issue assigns to pinax — into the name of an SDMX call.
- `scope: SqlRelation | None` is redundant: the return value is already an `SqlRelation`, so a consumer narrows by joining. Two narrowing mechanisms, unmeasured.
- Bundling descent + HA resolution + correlation into one entry point is what produces "a relation cannot raise lazily." The problem is manufactured by the bundling.
- A hand-written SQL producer would be a sixth bespoke compiler, months after #306 deleted four. If this cannot be said in the path language, that is a finding about the path language.

## Plan

**Stage 1 — make the HA→component hop real.** Bake `linked_object_urn` into parsed columns at write time (`docs/design/caching.md` puts physical layout ahead of everything else), add the edge to `dsd_component`. Worth doing even if the rest is rejected: it is a defect with a downstream workaround already built on it.

**Stage 2 — one implementation of "which hierarchy applies".** Express `applicable_hierarchies` as a relation over `(dataflow_urn, component_id, hierarchy_urn, rank)`, and have the Python functions read from it. Differentially tested against `_partition_associations`, same shape as the two query oracles. The divergence then goes away by construction rather than by agreement.

**Stage 3 — deferred.** With 1 and 2 done, the descent is a path-language expression over two things sdmxlib owns. Whether that deserves a named API or a documented recipe is a decision worth making when it can be written both ways and compared — not now.

## The two semantics

**Ambiguity: dissolved rather than answered.** Emit every applicable hierarchy with a precedence rank (scoped first, then URN order — `applicable_hierarchies`' existing contract) and let the consumer take `rank = 1`. Nothing raises lazily because nothing needs to, and sdmxlib never silently picks. `unique_hierarchy` stays the strict Python door.

**Self-inclusion: strict, explicit.** Match `q.hcode`, which already excludes self, with an explicit `include_self` — the precedent 0.50 set for `ancestor_at`.

Stages 1 and 2 agreed; stage 3 deferred by that decision.

## What a consumer gets now

```python
a = sl.q.hierarchy_applicability
reg.query(a).filter(a.rank == 1).select(flow=a.dataflow.id, comp=a.component.id, hier=a.hierarchy.id)
```

A `Frame`, which is already an `SqlRelation` — splice it into a correlated `EXISTS` and join on `dataflow_urn`, no `COALESCE` at the call site and no special-casing of unscoped associations, since they are expanded per flow.

**Ambiguity is dissolved rather than decided**, as proposed above: every applicable hierarchy is a row and precedence is a `rank` column, so nothing has to raise lazily. `unique_hierarchy` still raises, and now only within the *winning tier* — a scoped association beating an unscoped one is a resolution, not a conflict. The divergence this issue opened with is gone by construction, not by agreement.

**The fetch expands.** A view has no endpoint, so a root declaring `__derived_from__` becomes one request per source relation (`hierarchyassociation`, `dataflow`, `datastructure`), bounded by one agency — which is why the view projects `agency_id`. So this is not a local-only root; my earlier framing of that was wrong.

## Stage 3 is still open, and still needs its own relation

Measured rather than assumed: the path language refuses to project across a to-many edge by design —

> `'hierarchy.hcodes.code'` crosses a to-many edge, so it has no single value per row.

which is correct, because `(dataflow_urn, code_id)` is a join product rather than a projection. So the composed descent relation needs a second view or a relation producer whichever way stage 2 had gone. Worth deciding now whether it is wanted at all: with applicability resolved, the remaining work in pinax is one join to `hcode`, and that may read better at the call site than behind an API.

## Two notes for the downstream side

- `''` → `NULL` is breaking for SQL that compares against the empty string. `IS NULL` there was never matching anyway, so the fix should be a simplification rather than a port.
- Nothing in the public API moved, so `q.within(...)` / `q.has_code(...)` keep their signatures, as anticipated.

### 2026-08-25

Stage 3 is answered, and not by building what this issue proposed.

!442 (#373) added `where=` to every aggregate, which was a gap well beyond hierarchies — *"the dimensions of each DSD"* had no spelling either. With it, the correlated descent is a path expression:

```python
a, h = sl.q.hierarchy_applicability, sl.q.hcode

reg.query(a).filter(a.rank == 1).select(
    dataflow_urn=a.dataflow.urn,
    codes=a.hierarchy.hcodes.code.id.list(where=h.ancestors.any(h.id == "CA")),
)
# CPI_FLOW    ['ON', 'TOR']
# TRADE_FLOW  []
```

That is the `(dataflow_urn, codes)` relation this issue asked for — a `Frame`, so already an `SqlRelation` — and a consumer joins it without unpacking:

```sql
JOIN (<frame sql>) r ON r.dataflow_urn = d.sdmx_dataflow_urn WHERE d.geo = ANY(r.codes)
```

`unnest(r.codes)` gives one row per pair where that shape is wanted.

**So no `descendant_codes_by_dataflow`.** Every property the proposal asked to hold, holds — lazy (a relation, never rows), no dataflow list up front, same connection — and none of it needed a bespoke producer. The two things the proposal bundled that I argued against are simply absent: there is no `scope=` parameter, because narrowing is a join; and there is no ambiguity decision to make, because `rank` carries precedence and every applicable hierarchy is present.

Closing. The layering argument in this issue was right and is what drove all four changes:

| | |
| --- | --- |
| !439 | an association reaches the component it binds (schema 2.16) |
| !440 | an absent reference is NULL, not `''` (schema 2.17) |
| !441 | `q.hierarchy_applicability` — the resolution rule, once (schema 2.18) |
| !442 | `where=` on every aggregate (#373) |

What pinaxlib owns after this is the correlation and nothing else: no URN grammar, no HA precedence, no descent SQL.
