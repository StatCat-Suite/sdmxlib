# Issue #308: q-6: constraints need a role-filtered junction edge — the attachment lives in artefact_ref

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-13 |
| Closed | 2026-08-14 |
| Labels | `dsl`, `needs-design`, `type::feature` |

Blocks `q.data_constraint`, and `hierarchy_association` after it. Found while working the %306 coverage pass.

## The shape

A `DataConstraint` attaches to a dataflow, a DSD, a provision agreement or a data provider. None of that is on `sdmx.data_constraint`, which carries only `(urn, constraint_type)`. The attachment is written into the polymorphic ref table:

```
artefact_ref(source_urn, target_urn, role, ordinal)
  role in ('attachment_dataflow', 'attachment_dsd',
           'attachment_provision', 'attachment_data_provider')
```

So `q.data_constraint.dataflow` is **a to-one hop through a junction, filtered by a role column** — constraint → artefact_ref (source_urn, role='attachment_dataflow') → artefact (target_urn).

## Why neither existing mechanism covers it

- **`Edge`** is one foreign key with no predicate. It can express constraint → artefact_ref and artefact_ref → artefact, but nothing filters `role`, so every attachment kind would collapse into one hop returning all four.
- **`Facet`** does carry a discriminator (`component_type` for `dimensions`/`attributes`/`measures`), but it refines a **fan-out** and yields a to-many. An attachment is to-one.

`group_dimension` looked similar and is not: it is an unfiltered junction, so the compound path `("dimensions", "dimension")` already handles it (see `test_query_group.py`). The missing piece is specifically *the role filter on an intermediate hop*.

## Sketch, not a decision

Either give `Edge` an optional `where: tuple[str, tuple[str, ...]]` — the same shape `Facet` and `__constraint__` already use — or generalise `Facet` to refine a to-one. The first looks smaller and would make `__constraint__`, `Facet` and this one instance of a single idea; worth checking whether `Facet` then becomes a special case of it.

Cardinality must stay **derived**. A filtered edge is to-one only if the key plus the filter is unique, which key constraints alone cannot see — the same exception `member_of` already carries, so it needs the same treatment: read off the declaration, guarded by a test that says so.

## Blocked on this

- `q.data_constraint` + `q.cube_region` + `q.key_value` (`sdmx.region_key_value`) — the availability cluster, which `builders/contentconstraint.py` is built over
- `hierarchy_association` — three ref columns, same pattern
- any future accessor over `artefact_ref` itself

## Unrelated finding, recorded here so it is not lost

`sdmx.metadata_provision_agreement.metadata_provider_urn` points at a **relation that does not exist** — there is no `metadata_provider` table, so a `MetadataProviderScheme`'s items are never persisted. Storage gap rather than a query one; needs its own issue if confirmed.

## Comments

### 2026-08-14

Resolved, and **not** by building the mechanism this issue proposed.

Two things turned out to be wrong in the original reading.

**`hierarchy_association` was never blocked.** Its three slots — `linked_hierarchy_urn`, `linked_object_urn`, `context_object_urn` — are already columns on its extension table. It needed ordinary edges and nothing else.

**`data_constraint` did not need a new edge kind either — it needed the same layout.** `put_provision_agreement` already writes `dataflow_urn` and `data_provider_urn` as *columns* on its extension table **and** as `artefact_ref` rows: queries join on the columns, the generic inbound-reference index keeps reading the rows. `data_constraint` now does the same for its four attachment slots.

So the fix was four nullable columns, not a predicate on `Edge`:

```sql
attachment_dataflow_urn, attachment_dsd_urn,
attachment_provision_urn, attachment_data_provider_urn
```

Cardinality goes back to being **derived** — an ordinary nullable FK is to-one because the target key is unique — so the `member_of` exception stays the only declared-cardinality fact in the graph. The query language gained nothing it has to maintain, which is the outcome worth having: a fixed four-slot structure is layout, so it is fixed in the layout.

## What shipped

`q.data_constraint`, `q.cube_region`, `q.key_value`, `q.hierarchy_association`, plus the `dataflow.constraints` and `hierarchy.associations` inverses. The availability question is now four hops:

```python
reg.query(q.dataflow).filter(
    q.dataflow.constraints.constraint_type == "Actual",
    q.dataflow.constraints.cube_regions.key_values.value == "EU",
)
```

## One small addition that was needed

`_DataConstraint` is the first spine-rooted accessor exposing a column of its *own* extension table (`constraint_type`). Declared with `col()` it carries an empty path and binds against the artefact alias, which DuckDB rejects with `Referenced table "s1_1" not found`. `extcol()` declares it with the identity split as its path. Small and general; every future extension column can use it.

## Left open

The one thing this issue raised that is still true: **there is no way to express a to-one hop through a junction filtered on a discriminator.** Nothing in the schema needs it now. If a case appears, the sketch here still stands — but prefer the layout fix first, because it also keeps cardinality derivable.

The `metadata_provider` note has moved to #309.
