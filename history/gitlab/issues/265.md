# Issue #265: dsl-15: the whole accessor chain is typed in private names, and sort_by(key: _Ref) is in the published docs

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `design`, `dsl`, `needs-design`, `type::docs` |

Every intermediate value in the documented filter-DSL chain has an underscore-prefixed type, and one of those types appears in a signature we publish.

## What a user actually gets

```
sl.code.id                         -> code_query._IdRef
sl.code.name                       -> code_query._NameAccessor
sl.code.name["en"]                 -> code_query._NameLangRef
sl.code.annotations["x"]           -> code_query._AnnotationRef
sl.code.broader_transitive()       -> code_query._BroaderTransitiveSubRef
sl.code.id == "A"                  -> code_query._Eq
```

`sl.code` itself is a public name bound to a private class (`_CodeAccessor`). The *leaves* of the chain are fine — `contains()` and friends return `Predicate`, which is public and is the type `filter()` takes. It is everything in between that is unnameable.

Ten public accessors in `code_query` and ten in `hierarchy_query` are annotated with a private return type. Two are worse than the rest:

```python
def sort_by(self, key: _Ref, *, ascending: bool = True) -> CodeQuery: ...
def sort_by(self, key: _Ref, *, ascending: bool = True) -> HierarchyNodeQuery: ...
```

`docs/api.md` renders both `CodeQuery` and `HierarchyNodeQuery` through mkdocstrings, so the published API reference shows a parameter typed `_Ref` — a name the reader is being told, by convention, not to use, and which mkdocstrings has nothing to link to.

## What is *not* the problem

The predicate classes are correctly private and should stay that way. `_Eq`, `_StringMatch`, `_IsNull`, `_HasAncestor`, `_IsAncestorOf`, `_HasNoNarrower`, `_AnyAncestorMatches`, `_AnyDescendantMatches`, `_IsDescendantOf`, `_InHierarchy` are compiler implementation detail — a user never names one, they construct predicates through the accessor and the resulting class is the compiler's business. `Predicate` is the boundary, it is public, it carries the documented `to_sql(ctx)` hook, and pinaxlib composes against it. `__all__` on the module is `["CodeQuery", "Predicate", "code"]`, which states the same boundary.

That those classes are private is also load-bearing for the roadmap: #254 just changed how two of them compile, #261 adds an `_InSet`, and #262 would add `_And` / `_Or` / `_Not` and probably retire `_Eq.negate`. As private names those are free changes; as public names each is a compatibility argument.

## Why `__all__` does not settle it

`__all__` governs `import *` and what documentation tooling picks up by default. It does not stop `from sdmxlib.model.code_query import _StringMatch`, and it says nothing to a *reader* about whether a name is safe to depend on. The underscore is the signal that survives; `__all__` is the one that does not. This is the point CLAUDE.md's rule 4 already makes.

## Options

- **A. Private *module*, public names — CLAUDE.md rule 4 applied properly.** Move the compiler internals (field expressions, predicate classes, emitters) into `model/_code_predicates.py` / `_hierarchy_predicates.py` with plain names, and let the ref/accessor hierarchy carry public names in the module users import from. The underscore then marks the module rather than every type in a chain users are encouraged to write.
- **B. Narrow fix: a public type for the sort key only.** Give `sort_by` a public `SortKey` Protocol (or make the ref base public as `Ref`— name already taken by `model.ref.Ref`, so it would need care). Fixes the published signature; leaves "what type is my variable" unanswered.
- **C. Do nothing, and document that intermediates are deliberately unnameable.** Defensible for a purely fluent API where no one stores an intermediate — but note the ecosystem does not do this: polars exposes `pl.Expr`, SQLAlchemy exposes `ColumnElement`, precisely because users annotate intermediates and IDEs display them.

A is the most work and the most consistent with the rule already written down. B is the minimum that stops shipping a private name in the docs.

## Two honest caveats

**The tests reach past the barrier constantly.** `test_hierarchy_query.py` imports `_AnnotationField`, `_AnyAncestorMatches`, `_CodeUrnField`, `_Eq`, `_IsNull`, `_LevelField`, `_NameField`, `_NodeIdField`, `_ParentNodeIdField` and `_StringMatch` directly, and both property files import the module to enumerate `Predicate` subclasses. That is fine and intended — it is why SLF001 is off — but it means the underscore buys less isolation in practice than it appears to, and any reshuffle has a test-side cost.

**This overlaps #259.** That issue is about `sort_by` accepting refs it cannot compile, and the fix there is to give the ref hierarchy a shape that makes unsupported sort keys unrepresentable. That reshaping and this naming question want to be decided together — doing #259 first and then renaming would touch the same classes twice.

## Test gates

- No private name appears in the signature of anything rendered by `docs/api.md`. Worth a mechanical check rather than an eyeball: walk the documented classes' public methods and assert no annotation resolves to an underscore-prefixed name.
- Whatever the decision, `Predicate` stays public and the predicate subclasses stay private.
- `tests/docs/` continues to execute the DSL examples unchanged — the user-facing chain syntax must not move.
