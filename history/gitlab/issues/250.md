**Phase 2** — best after #dsl-1 and #dsl-2, because it reuses their strategies and applies a different generator to them.

## The class of bug

Document fuzzing exists (`tests/unit/test_fuzz_readers.py`) and covers readers. Nothing fuzzes the DSLs, and the analogue for a query compiler is not a mutated document — it is a **hostile predicate value**.

We already have one confirmed instance. #222 (`code_query`: id equality is case-sensitive but `contains()` is not) is one half of it; the other half is recorded in `test_properties_code_query.py` as a regression test with its own section header:

> `# ── Regression: LIKE metacharacters in filter values (#222) ──────────────────`
> `def test_underscore_in_a_filter_value_is_matched_literally(fragment: str)`

An underscore in a user-supplied filter value reached a SQL `LIKE` unescaped and behaved as a single-character wildcard. It was found late and fixed with one targeted test covering one metacharacter in one predicate. `code_query` and `hierarchy_query` between them have on the order of a dozen string predicates, and the fix's coverage is not systematic.

SDMX ids are constrained, but the values *users pass to filters* are arbitrary strings, and so are lang codes and annotation types used as accessor keys.

## Scope

- A `hostile_strings()` strategy in `tests/support/strategies.py` covering at minimum: `%`, `_`, `\`, `[`, `]`, single and double quotes, backtick, semicolon, `--`, newline, NUL, the empty string, whitespace-only, very long strings, and non-ASCII (combining marks, RTL, astral-plane).
- Apply it to **every** string-valued position in both DSLs, not just `contains`: `==`, `!=`, `contains`, `starts_with`, `ends_with`, and — importantly — the *accessor keys* `name[lang]`, `annotations[type]`, `annotations[type,lang]`, `level(level_id)`, which flow toward identifier or join positions rather than value positions.
- The core assertion is differential, reusing the oracles from #dsl-1 / #dsl-2: a hostile value must produce the same result as literal Python matching. That catches wildcard leakage without anyone having to enumerate which characters are special in DuckDB's `LIKE`.
- A second assertion for injection specifically: no hostile value may change the *structure* of the emitted SQL. `to_sql()` returns `(sql, params)` — assert the value lands in `params` and the `sql` string is byte-identical to the same query built with a benign value.
- Round out the empty/degenerate cases while there: empty codelist, single node, `limit(0)`, filter matching nothing, filter matching everything.

## Risks

- **Escaping in the wrong layer.** If a fix lands by escaping at the call site rather than in the compiler, the next predicate added reintroduces the bug. Fixes belong where the `LIKE` pattern is built.
- **Non-ASCII may surface DuckDB collation behaviour rather than a bug in our code.** When a property fails on a combining mark, establish whether the oracle or DuckDB is defining "equality" before changing anything — and if the answer is that the DSL is underspecified about case and normalisation, that is a #222-shaped finding and gets its own issue.
- NUL bytes may be rejected at the driver layer; that is an acceptable outcome if it is a clear error rather than silent truncation.

## Test gates

- Every string-valued DSL position covered by the hostile-value strategy in both modules.
- Structural-SQL-invariance assertion for every one of them.
- The existing #222 regression test either subsumed by the generative property or kept deliberately as a named regression, not both by accident.
- Any newly found escaping defect fixed in the compiler, with the property left in place as the guard.
