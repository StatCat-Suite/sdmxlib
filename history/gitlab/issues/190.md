# Issue #190: Support wildcard (WildcardUrnType) targets in DSD→MSD metadata derivation

Follow-up to #162.

## Context

SDMX 3.0 Metadataflow / MetadataProvisionAgreement targets may be
**wildcarded** `WildcardUrnType` references — e.g.
`Dataflow=ESTAT:CPI(*)`, `Dataflow=IMF:*(*)`, or fully open — declaring
that the metadata product applies to any matching artefact. FMR models
targets as a weak, possibly-wildcarded connection.

`model/metadataflow.py` already stores targets as raw strings precisely
because they can contain wildcards.

## Scope

The v1 derivation (#162) and the declared-targets follow-up (#189) match
targets by **exact URN equality** only. This issue adds wildcard
resolution:

1. A `WildcardUrnType` matcher: given a wildcard URN pattern and the set
   of concrete dataflow URNs in the lake, return the matches (agency /
   id / version wildcards, per the SDMX URN wildcard rules).
2. Wire it into `build_dsd_metadata_map` so a wildcarded Metadataflow/MPA
   target expands to every matching dataflow → its DSD.
3. Tests: agency-wildcard, id-wildcard, version-wildcard, fully-open;
   and a guard that a non-matching wildcard yields no association.

## Note

Until this lands, `build_dsd_metadata_map` covers concrete targets only —
the boundary is documented and asserted in
`tests/unit/test_builders_metadata_annotation.py`. Keep the "no silent
caps" contract: if wildcard targets are skipped, that must remain visible.
