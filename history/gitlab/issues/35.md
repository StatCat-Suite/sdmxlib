# Issue #35: Expose public URN builder for SDMX artefacts

| | |
| --- | --- |
| State | closed |
| Opened | 2026-04-12 |
| Closed | 2026-04-28 |

## Problem

`sdmxlib.model.registry._artefact_urn` is the only way to compute a canonical SDMX URN string for a given artefact (Dataflow, DataStructure, Codelist, etc.). It is used internally by `sdmxlib.storage.writers` to compute the primary key written to the `artefacts` and `dataflows` tables.

External libraries that share the same DuckDB connection (e.g. cataloglib) need to compute the same URN to use as a foreign key when linking their own records to sdmxlib's tables. Currently the only option is to import the private function (`from sdmxlib.model.registry import _artefact_urn`) or to hand-construct the URN string manually, both of which are fragile against future refactors.

## Request

Expose a public function such as:

```python
def artefact_urn(artefact: MaintainableArtefact) -> str:
    """Return the canonical SDMX URN string for a maintainable artefact."""
    ...
```

This could live in `sdmxlib.model.registry` or a new `sdmxlib.urn` module. The return value must match the URN written as the primary key by `sdmxlib.storage.writers`.

## Context

cataloglib uses `sdmxlib.storage.schema.create_tables(conn)` and `sdmxlib.storage.writers.ingest_registry(conn, registry)` to write SDMX structural metadata into a shared DuckDB connection. The catalog's `StatisticalDataset` records then link to sdmxlib's `dataflows` table via `sdmx_dataflow_urn`. To set that field correctly on ingest, we need the same URN that sdmxlib will use as the PK — hence the dependency on `_artefact_urn`.
