## Comments

### 2026-09-05

Landed in !456.

**Decisions**, with the two open ones settled by measurement rather than by argument:

1. **Weight is item count.** O(1) — the length of an already-built `ItemList`, never a traversal and never a query. `tracemalloc` on the bundle, in one process (an earlier pass used `ru_maxrss` and charged every artefact a one-time 4.4 MB of warm-up, which is what made a 28-node hierarchy look like 4.5 MB):

| artefact | items | retained | bytes/item |
| --- | --- | --- | --- |
| `CL_GEOGRAPHY` (`Codelist`) | 579,951 | 404.5 MB | **731** |
| `H_CP_GEO_FED2023` (`Hierarchy`) | 499,143 | 913.1 MB | 1,918 |
| `H_CP_GEO_ADMINISTRATIVE` | 63,404 | 130.6 MB | 2,061 |
| `H_CP_GEO_HCCSS` | 28 | 0.07 MB | — |
| `DF_CP_2021` (`Dataflow`) | 0 | 0.08 MB | — |

Linear *within* a class; the spread *across* classes is **2.9x**, not 10,000x.

2. **Default 1,000,000 items** = 0.7 GB of codes to 2.0 GB of nodes. Holds either of the bundle's two largest artefacts outright, not both.

3. **Floor of 64 items**, picked by the table rather than as a round number: a zero-item artefact retains 0.00–0.08 MB, about what 64 items weigh. It is also what a lazy artefact weighs, correctly — a `LazyCodelist` holds a URN and a connection, and asking its `codes` for a length would run SQL.

4. **Over-weight entries are refused**, not admitted-then-evicted. Caffeine's behaviour here would mean one over-budget read evicting the whole working set on its way to evicting itself. `refused` is reported so "why does this never cache" is distinguishable from a cold cache.

## A correction to the description above

> #378 ... is why the remaining entries are uniformly "big artefacts"

Not on this bundle. Ordinary reads leave the cache holding **floor-weight entries only** — a `Metadataflow`, a `MetadataStructure`, a `LazyHierarchy`, 64 apiece. #378 rerouted item resolution to a targeted by-URN read, so resolving a `Ref[Code]` no longer drags in the whole codelist.

The large-entry route is what remains of the old path: `_items_from_loaded_scheme`, kept for a `Concept` and for a `version="latest"` item URN whose stored `code_urn` carries a concrete version and cannot be matched directly. That case still loads the parent scheme eagerly and promotes it — verified end to end in `test_a_version_latest_ref_puts_a_whole_scheme_in_the_cache`.

So the 4.4 GB figure is reachable, by that route rather than by the default read path. The bound is worth having either way: an entry count could not describe even the floor-weight state above, and how large an entry turns out to be is not something a cache gets to assume.

## Breaking

`resolve_cache_size` → `resolve_cache_items` (the units changed; silently reinterpreting the number would be worse than the error). `resolve_cache_info()` now returns `entries`, `weight`, `max_items`, `hits`, `misses`, `refused`.

## Acceptance

All five met. 17 tests on the reported weight rather than wall memory, `docs/design/performance.md` §Layer 3 and `docs/design/caching.md` both updated — the latter's "bounded" requirement now reads *bounded in a unit that corresponds to what you are bounding*, with the ecosystem table showing which side of that axis a new cache sits on.

**Also worth recording:** the bundle bench tier caught the rename that `just ci` could not — it is not part of that gate, and `tests/bench/test_bundle_reads.py` builds its registry with this keyword. A rename in this API is invisible to the standard gate.
