# Issue #371: 30 model fields declare tuple[...] with no converter, so a list stays a list

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-22 |
| Closed | 2026-09-10 |

Found by type-checking `tests/support` for #347.

## The lie

```python
>>> dp = sl.DataProvider(id="P", contacts=[sl.Contact(name={"en": "c"})])
>>> type(dp.contacts).__name__
'list'          # declared: tuple[Contact, ...]
```

There is no converter, so the value is stored exactly as given. The annotation says `tuple`, the object holds a `list`, and nothing anywhere notices.

**30 fields across the model** are in this shape:

```
Agency.contacts                     Contact.emails / faxes / phones / uris / x400s
DataProvider.contacts               MetadataProvider.contacts
CubeRegion.keys                     DataKey.values
DataConstraint.regions / data_keys  AttachmentConstraint.data_keys
Codelist.extensions                 CodeSelection.members
Dataflow.dimension_constraint       Metadataflow.targets
MetadataProvisionAgreement.targets  MetadataStructure.targets / report_structures
ReportStructure.attribute_ids / target_ids
StructureMap.maps  RepresentationMap.maps  ConceptSchemeMap.maps  CategorySchemeMap.maps
StructureSet.maps / related_structures
HierarchicalCodelist.hierarchies / included_codelists
```

(Full list reproducible with an `attrs.fields` walk filtering `str(f.type).startswith("tuple[") and f.converter is None`.)

## Why it is worth fixing

1. **The type is wrong**, which is the plain version. `isinstance(dp.contacts, tuple)` is `False` for an object whose annotation promises otherwise, and `dp.contacts + (x,)` raises.
2. **The immutability it implies is not there.** `tuple` was presumably chosen over `list` to say "this does not change after construction". A stored list can be mutated by whoever passed it in, after the fact — including through a `@frozen` container, since `@frozen` is shallow (see #290's discussion).
3. It is invisible today because `tests/` is unchecked, and inside `src/` the fields are usually populated from readers that already build tuples. It surfaced the moment `tests/support` was type-checked, from fixture code passing the list literal that reads more naturally.

## The fix

`converter=tuple` on each, mirroring how the `ItemList` / `Annotations` fields already use converters (`converter=_to_annotations`, `converter=_to_item_list`). That makes the annotation true and costs one call per construction.

Worth checking as part of it whether any of the 30 are *meant* to stay ordered-mutable, in which case the annotation should become `list[...]` instead — the point is that the two agree, not that tuple wins.

## Related

Same family as #307, #309 and #315: a declaration and an implementation that disagree, where the disagreement produces no error and so no test. Different mechanism — this one is a converter that was never added rather than a field that was never persisted.

## Comments

### 2026-09-10

!484. Re-ran your `attrs.fields` walk first — exactly the 30 listed, none
optional, so `converter=tuple` covers them. Zero remain.

**Two the survey as written could not see:**

* **`KeyValue.values`** declares `frozenset[str]` and had no converter either.
  Same defect, one type over; the filter was `str(f.type).startswith("tuple[")`,
  so it was invisible. Widening the walk to `frozenset[`/`set[` found this one
  and only this one.
* **`DataKey.values`** is `tuple[tuple[str, str], ...]`, the model's only
  nested declaration. `converter=tuple` fixes the outer sequence and leaves the
  pairs as lists — the same lie one level down. `DataKey(values=[["FREQ","A"]])`
  was `(['FREQ', 'A'],)`; it now gets `_to_key_pairs` and is `(('FREQ','A'),)`.

**On "check whether any are meant to stay ordered-mutable":** none are. Grepped
every one of the 30 field names for in-place mutation across `src/` — `append`,
`extend`, `insert`, `remove`, `pop`, `sort`, `clear` — and found none. So
`tuple` wins for all thirty and no annotation had to relax to `list[...]`.

**A helper I wrote and then deleted.** I started with
`to_tuple[T](Iterable[T]) -> tuple[T, ...]`, reasoning that bare `tuple` widens
the generated `__init__` to `tuple[Any, ...]` and would let a list of the wrong
element type through. Measured against basedpyright: both forms give
`xs: Iterable[str]` and both reject `list[int]`. The helper bought nothing, so
the builtin stands — which is also what `binding.py` already does.

**The guard is a walk.** The fix is one converter per field and the failure
mode is forgetting one on a field added later, so thirty assertions would all
pass while the thirty-first went unconverted. It enumerates the model and
asserts the property of everything it finds, plus a floor of ≥30 fields so a
walk that silently goes blind is not mistaken for a clean model.
Sabotage-checked: dropping one converter fails naming `Agency.contacts`.

The behavioural half is asserted too — including your point 2, which is the
one that never looks like a type error. `@frozen` is shallow, so before this a
caller could keep their list and append to it after construction; that is now a
test.

`just ci` green — 6,535 unit.
