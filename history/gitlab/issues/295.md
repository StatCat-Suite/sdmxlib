Follow-up to the naming point in the `sort_by` semantics issue. Deliberately separated: mechanical, 74 call sites (17 src / 46 tests / 11 docs), and it should land *after* the semantics change so the two are not entangled in one diff.

`sort_by` is borrowed from polars at the wrong level. polars has no frame-level `sort_by`: frames have `sort` (a pipeline stage, last-wins), and `sort_by` is an **expression** method — `pl.col("a").sort_by("b")` — meaning "sort this expression by another", which is not what we do.

Every declarative peer says `order_by`: SQLAlchemy, Django, ibis. That is also the SQL clause name, which is the register the rest of our surface already uses (`limit`, `offset`, `select`, `group_by`, `having`).

Counter-argument, for the record: `filter` stays `filter` rather than becoming `where`, because Django is declarative, uses `filter`, and ANDs — the one composition law that is unanimous. So the register is not purely SQL, and `sort_by` is not obviously wrong on consistency grounds alone. The case rests on the polars name collision, not on register purity.

Pre-stability, so a straight rename with no alias.
