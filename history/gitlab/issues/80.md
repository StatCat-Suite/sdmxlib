## Goal

Replace the per-call cursor lifecycle introduced by #78 with a **thread-local cursor**, lazily created on first use per thread and reused for that thread's lifetime. Same correctness guarantees as #78 (no cursor sharing across threads), but the cursor create/close cost amortises across the thread's many calls instead of per call.

This is a perf follow-up to #78. Order: lands **after** the v0.28.0 release from #79 — ship correctness first, perf claw-back as v0.28.1 / v0.29.0.

## Why

#78's bench showed:

- **Single-threaded** `single_code_map` +25% slower than v0.27.2 baseline (per-call `conn.cursor()` dominates a trivial-SELECT workload).
- **Concurrent** ops/sec down 15–30% at 8–32 workers (cursor lifecycle on the hot path).

Best-in-class DB libraries (SQLAlchemy, psycopg, asyncpg) don't recreate a cursor per statement. The two common patterns are connection pools (SQLAlchemy) and thread-local cursors (psycopg in worker-thread setups). DuckDB's docs say "separate cursors for concurrent use" — they require isolation, not lifecycle churn. Thread-local satisfies isolation while amortising the cost.

## Design

`Registry` gets a `threading.local()` holding the per-thread cursor. The `_read_cursor()` context manager becomes a property-style accessor that returns the calling thread's cursor (creating it on first call):

```python
class Registry:
    def __init__(self, ...) -> None:
        ...
        self._thread_cursors = threading.local()

    def _read_cursor(self) -> duckdb.DuckDBPyConnection:
        cur = getattr(self._thread_cursors, "cur", None)
        if cur is None:
            cur = self._require_open().cursor()
            cur.execute("SET search_path = 'sdmx'")
            self._thread_cursors.cur = cur
        return cur
```

Call sites change from `with self._read_cursor() as cur:` to `cur = self._read_cursor()` — flatter, no context manager. Cursor lives for the thread's lifetime.

Same change in `_cur(conn)` helpers (`lazy.py`, `code_query.py`, `hierarchy_query.py`). These get a `_per_thread_cursor(conn)` helper backed by a module-level `WeakKeyDictionary[duckdb.DuckDBPyConnection, threading.local]` so we can key by the registry's connection without leaking when registries get GC'd.

`DataStore.query_stream` similarly switches to the thread-local cursor.

## Lifecycle / leak handling

`threading.local()` storage is cleaned up automatically when a thread terminates — Python's GC drops the per-thread data, and DuckDB closes the cursor via its finaliser. So the natural lifecycle handles thread death without manual tracking.

For the WeakKeyDictionary path (lazy facades): when a `Registry`'s connection is closed/GC'd, the entry vanishes from the dict and the `threading.local()` for that connection's per-thread cursors becomes unreferenced. Cursors close.

Edge case to handle: `Registry.close()` should explicitly drop the `threading.local()` and close any live cursors on it — don't wait for GC. The thread-local storage is process-wide, so a registry reopen needs to start fresh.

## FastAPI / uvicorn — can we observe thread lifecycle from outside sdmxlib?

**No, and we don't need to.** Quick rundown:

- FastAPI `def` route handlers run via `anyio.to_thread.run_sync()` on a bounded threadpool (default 40 threads in anyio).
- Threads in that pool are **long-lived workers**, parked between tasks. They are not recycled per-request.
- The pool size only changes on explicit `anyio.to_thread.current_default_thread_limiter().total_tokens = N` calls, or on process shutdown.

Implication: on a typical FastAPI deployment, a `Registry` ends up with ~40 thread-local cursors per process, stable for the process lifetime. No churn, no leak, no per-request overhead. The exact case thread-local was designed for.

Sdmxlib can't subscribe to anyio's thread events, but it doesn't matter — Python's threadlocal storage handles cleanup itself, and `Registry.close()` handles the shutdown side.

We can optionally expose a diagnostic `Registry.cursor_pool_info() -> dict[str, int]` returning `{"thread_cursors": N, "current_thread_has_cursor": bool}` for ops dashboards. **Optional**; gate on whether it's wanted.

## Ergonomics — single-developer vs web-app use

sdmxlib should serve two use cases well:

**Single-developer analysis** (notebook / one-off script — single main thread):
- One thread = one cursor, created on first read, reused forever.
- No per-call cursor cost. Same behaviour as pre-#78 from the user's point of view.
- No API surface change. Win.

**Long-running web app** (FastAPI/Flask/etc. — pool of worker threads):
- ~N threads = ~N cursors, each created lazily on first read in that thread.
- Bounded by pool size. No per-call churn after the first warm-up call per thread.
- Concurrent reads remain isolated (each thread has its own cursor). Same correctness as #78.
- Cleanup is automatic on thread death; `Registry.close()` cleans the rest.

**The two use cases land on the same code path** — no opt-in flag, no special handling. That's the API-ergonomics win over a pool-based design (which would force every caller through a `with reg.connection() as conn:` boundary even in the single-thread notebook case).

## TL;DR

- **It works correctly**: 1614 existing unit tests pass + 6 new lifecycle tests pass + #76 repro tests pass 10/10 over repeated invocations.
- **Perf claw-back vs main (#78): ~5%** on single-threaded reads (5-run median 923µs vs 972µs).
- **Not the dramatic claw-back the issue targets aimed for** — those targets compared to v0.27.2's baseline (~829µs), which represented zero per-call cursor work because reads went through the registry's single persistent cursor. Thread-local still does the cursor lifecycle once per thread, plus a `getattr` + WeakKeyDictionary lookup per call. Lower cost than per-call, not zero.

## Design as implemented

- `Registry._read_cursor()` returns a per-thread cursor via `self._thread_local`. `close()` replaces the threadlocal so reopen starts clean.
- Lazy facades (`storage/lazy.py`, `model/code_query.py`, `model/hierarchy_query.py`) use a module-level `threading.local()` holding a `WeakKeyDictionary[Connection, Cursor]`. Connection GC drops entries automatically — no stale-cursor hazard from `id()` reuse.
- `readers.code_map` / `code_map_for_dsd` use the same WeakKeyDictionary-backed thread-local.
- `DataStore.query` switches to thread-local; `query_stream` stays per-call (a generator can be iterated alongside a fresh `query_stream` on the same thread, and aliasing a cursor would break both).
- FastAPI/uvicorn deployment story unchanged from the doc page: ~N cursors per process where N is the threadpool size, created lazily, stable for the process lifetime.

## Lifecycle invariants pinned by `tests/unit/test_cursor_lifecycle.py`

- 1 thread × N reads → 1 cursor (not N).
- N threads × M reads → N cursors total (not N*M).
- `close()` drops the threadlocal; reopen creates a fresh cursor.
- Lazy-facade WeakKeyDictionary releases entries when a Registry closes and is GC'd.
- 200 ephemeral threads doing one read each don't pin cursors past thread death.
