# Issue #360: Reader fabricates related_measure="OBS_VALUE" for 3.0 observation attributes

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-21 |

Surfaced by #359 while triaging the `related_measure` limit.

SDMX 3.0's `AttributeRelationshipType` has no measure reference — the choice is
Dataflow / Dimension / Group / Observation, and `<Observation/>` is
`common:EmptyType`. So an observation-level attribute says *that* it is
observation-level and nothing about which measure.

Our 3.0/3.1 readers and the SDMX-JSON ingest all return:

    return AttachmentLevel.OBSERVATION, None, "OBS_VALUE", None

`related_measure="OBS_VALUE"` is invented, not read. It is a reasonable guess —
most DSDs name their measure `OBS_VALUE` — but it is presented as though it came
off the wire, and it is wrong whenever the DSD's measure is named anything else.
The #354 fixture has a measure called `MEAS`, and round-tripping it through 3.0
yields an attribute claiming to relate to a measure the DSD does not contain.

`attachment=AttachmentLevel.OBSERVATION` already carries the fact that survived
the wire, so the fabricated id adds nothing a caller could not derive, and
subtracts the ability to tell "the document said OBS_VALUE" from "the document
said nothing".

Options:

1. Return `None`. Honest, and `attachment` still says observation-level.
2. Resolve to the DSD's measure id when it has exactly one, `None` when
   ambiguous. Recovers the useful case without inventing anything — 3.0 permits
   multiple measures, so the ambiguous branch is real.
3. Keep it, and document that it is synthesised.

(2) is probably right but needs a decision about the multi-measure case. Filed
rather than fixed because it is a semantics choice, not a defect with one
obvious answer.

Registered meanwhile as `data_structures.attributes[1].related_measure` in
`tests/unit/test_field_coverage.py` and declared in `gaps.py`.
