# Issue #413: Observation columns have no string-matching predicates, so SDMX-REST's c[] co/nc/sw/ew filters can't use the DSL

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-05 |
| Closed | 2026-10-06 |
| Labels | `dsl`, `enhancement` |

Found moving sdmxlib-rest's `/availability` onto the query DSL (sdmxlib-rest #6).
This is the gap that blocks it outright.

## The gap

SDMX-REST 2.2.2's component filters carry operators: `c[GEO]=co:Census` (contains),
`nc:` (does not contain), `sw:` (starts with), `ew:` (ends with), alongside
`ne/lt/le/gt/ge`. Every SDMX-REST service built on sdmxlib has to support them on
`/data` and `/availability`.

The comparison operators are expressible — `obs.filter(obs.col("TIME_PERIOD") >= "2020")`
works. **The four string operators have no form at all.** A `Col` offers `==`,
`!=`, `<`, `<=`, `>`, `>=`, `is_in` and the null checks; there is no `LIKE`,
contains, starts-with or ends-with. `ComponentFilter` carries equality and
membership only (`dimensions` / `attributes` as `list[str] | SqlRelation`), so it
cannot help either.

`reg.sql(...)` is not a way round it, and correctly so: `raw.py` makes it a
deliberately *terminal* escape hatch that cannot be spliced into a structural
query's `filter`. So a consumer that needs one `co:` filter today cannot use the
DSL for that query at all.

## What that forces

sdmxlib-rest has two choices for `/availability`, both bad: drop `co/nc/sw/ew`
(a functional regression — they work today), or keep a hand-written SQL path for
requests that use them alongside the DSL path for the rest — more code than now,
which is the opposite of the migration's point. So #6 waits on this. `raw.py`'s
own docstring says the escape hatch exists to show what to build next; this is
one of those.

## What would close it

String predicates on a column, with **the DSL owning the escaping**. sdmxlib-rest
currently escapes `%`, `_` and `\` itself and appends `ESCAPE '\'`
(`data/params.py::like_pattern`); that is easy to get subtly wrong, which is the
argument for it living in one place. Something like:

```python
obs.col("GEO").contains("Census")      # LIKE '%Census%'  ESCAPE '\'
obs.col("GEO").starts_with("Census")   # LIKE 'Census%'
obs.col("GEO").ends_with("Province")   # LIKE '%Province'
~obs.col("GEO").contains("foo")        # NOT LIKE …
```

`observations.py` already names this slice — typed columns, "`obs.num(...)` /
`obs.text(...)` will use it". If string predicates belong on `obs.text(...)` rather
than the permissive `Col`, that is fine for us; the consumer need is the operators,
not their spelling.

Comparison operators on text compare lexically, which is right for `TIME_PERIOD`
in its ISO forms and worth keeping as-is.
