# Issue #153: browse() then get().fetch() returns the cached identity stub instead of the full artefact

| | |
| --- | --- |
| State | closed |
| Opened | 2026-06-18 |
| Closed | 2026-08-20 |

## Summary

After `RestRegistry.query(...).browse()` populates the registry with identity stubs, a subsequent `get(...).fetch()` for one of those artefacts returns the **cached stub** (incomplete — missing annotations/components) instead of fetching the full artefact from the REST service. `resolve()` does **not** have this problem.

This is surprising given the documented contract — `fetch()` is described as returning "full artefacts, Refs unresolved" — so callers reasonably expect a complete artefact. Instead they silently get a partial one, with no error.

## Reproducer

```python
import sdmxlib as sl

URL = "https://api.statcan.gc.ca/ccei-ccie/sdmx/rest"
DFID = "DF_25100079"

def types(df):
    return sorted({a.type for a in (df.annotations or [])})

# A) fresh registry — get().fetch() returns the full dataflow
with sl.RestRegistry(URL, api="2.1", timeout=120.0) as reg:
    print("A fresh  get().fetch():  ", types(reg.get(sl.Dataflow, agency="STC", id=DFID).fetch()))

# B) browse() first, then get().fetch() on the same registry
with sl.RestRegistry(URL, api="2.1", timeout=120.0) as reg:
    reg.query(sl.Dataflow, agency="STC").browse()    # caches identity stubs
    print("B browse -> get().fetch():  ", types(reg.get(sl.Dataflow, agency="STC", id=DFID).fetch()))
    print("C browse -> get().resolve():", types(reg.get(sl.Dataflow, agency="STC", id=DFID).resolve()))
```

Output:

```
A fresh  get().fetch():    ['COMBINED_CONCEPTS', 'DEFAULT', 'EXT_RESOURCE', 'LAYOUT_CELL_ALIGN', 'LAYOUT_COLUMN', 'LAYOUT_ROW', 'NOT_DISPLAYED', 'NonProductionDataflow', 'UNIT_MEASURE_CONCEPTS']
B browse -> get().fetch():    ['NonProductionDataflow']
C browse -> get().resolve():  ['COMBINED_CONCEPTS', 'DEFAULT', 'EXT_RESOURCE', 'LAYOUT_CELL_ALIGN', 'LAYOUT_COLUMN', 'LAYOUT_ROW', 'NOT_DISPLAYED', 'NonProductionDataflow', 'UNIT_MEASURE_CONCEPTS']
```

So after `browse()`, `fetch()` returns only the stub's `NonProductionDataflow` annotation and drops the rest (incl. `LAYOUT_ROW`/`LAYOUT_COLUMN`/`DEFAULT`); `resolve()` returns the full set.

## Impact

Code that reads `dataflow.annotations` (or, presumably, other component/detail fields) after having called `browse()` on the same registry silently sees an incomplete artefact. In our case we were reading `LAYOUT_ROW`/`LAYOUT_COLUMN`/`DEFAULT` annotations to reconstruct the Data Explorer default view, and an earlier `browse()` to enumerate ids made every later `fetch()` look unannotated — a confusing, silent wrong result.

## Possible directions (for your call)

- `fetch()` could fetch the full artefact and upgrade/replace a cached browse stub, rather than returning the stub.
- browse stubs could be flagged "partial" so `fetch()` knows to re-fetch.
- At minimum, document that `fetch()` may return a `browse()` stub and that `resolve()` (or a fresh registry) is required to get full detail after a browse.

## Environment

- sdmxlib 0.41.2, Python 3.13
- Endpoint: `https://api.statcan.gc.ca/ccei-ccie/sdmx/rest`, `api="2.1"`

## Comments

### 2026-08-20

**Closing — the API this describes no longer exists.**

The reproducer is `reg.query(...).browse()` followed by `get(...).fetch()`.
Audited against current `main`:

* `get()` was collapsed to a single method returning `T | None` in
  `a8ef0e8 refactor(api)!: one get(), with resolution depth as a parameter`.
  There is no `.fetch()` to call on its result — the only `fetch()` left in
  `api/` is on the *data* query, which returns a `Dataset`.
* `RestRegistry.query` now takes a path root (`query(root: QueryCols[R])`) and
  returns a `Query`, which has no `browse()`. The REST-side browse is gone;
  `browse()` survives only on `LocalRegistry`, over dataflow bindings.

So neither half of the reproducer compiles today.

**The underlying concern is now handled structurally**, which is the reason to
close rather than rewrite. `Query._fetch_for` keys its fetch on the *derived
detail*, not just the plan, precisely so a stub fetch and a full fetch are
different questions:

> `full` subsumes `allstubs`: everything a stub carries is in a full artefact,
> so a narrow ask after a wide fetch is pure waste. The reverse does not hold,
> which is what the key is for.

and it names this exact failure as what that guards against — `select(id).ids()`
fetching stubs, then `collect()` finding the key present and resolving artefacts
whose items were never retrieved.

**One thing this audit did find**, filed separately rather than left here: the
`allstubs`-vs-`full` distinction is *not* visible to `Session`. `completeness_of`
keys on `references` first, so `detail=allstubs, references=none` and
`detail=full, references=none` both record `UNRESOLVED`. That is correct for the
question `Completeness` answers (how deep were references followed) and says
nothing about whether the artefact's own content was trimmed. The query layer
compensates with its own key; a caller mixing the two paths on one session would
not. Tracked in the audit note on #29, which is the issue about exactly this
axis.
