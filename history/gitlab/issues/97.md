## Comments

### 2026-05-31

Partial correction surfaced during MR !69 (ValueMap variants):

The original audit description said `DataConstraint role=Forbidden` is untested. That's incorrect — the SDMX XSDs (both 2.1 `ContentConstraintTypeCodeType` and 3.0 `ConstraintRoleType`) only define **`Allowed` and `Actual`** for the type/role attribute. There is no `Forbidden` enum value. The 'forbidden' semantic is expressed elsewhere, via `CubeRegion @include="false"`, not via the constraint type.

Now-correct scope for this issue:

- **AttachmentConstraint (2.1 only)**: still a real gap. The 2.1 `Constraints` container allows both `ContentConstraint` (which we model as `DataConstraint`) and `AttachmentConstraint` (which we don't model at all). `AttachmentConstraint` is a different artefact type with no exact 3.0 / 3.1 analogue.
- **DataConstraint role=Actual (all versions)**: untested. We've only ever round-tripped `role="Allowed"`.
- **CubeRegion \@include=false**: this is what 'Forbidden' actually maps to semantically. We do model `CubeRegion.include: bool`; round-trip of `include=false` may or may not be tested — needs a fixture check.

Renaming the issue to reflect this would help the next implementer.
