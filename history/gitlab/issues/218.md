## The decision

Given the pilot's measured mutation score and wall-clock, choose one:

- **A. Adopt broadly** — extend to the rest of `model/`, then the format layer.
- **B. Adopt narrowly** — keep mutation testing for a named set of high-risk modules, run on demand when they change.
- **C. Drop it** — record why, with the numbers. A well-evidenced no is a real outcome and saves the next person from re-litigating it.

Do not default to A because the tooling works. The question is whether surviving mutants keep pointing at *real* gaps once the obvious ones are fixed, or whether the signal decays into equivalent-mutant triage.

## What the pilot's numbers should be re-read against

Whichever way it goes, the interesting comparison is **before vs after the Hypothesis work**. If #test-6 and #test-7 land first, re-running the pilot answers a question worth knowing on its own: *do property-based tests kill more mutants than example-based ones?* Same modules, same mutants, different suite. If they do, that is the strongest available argument for spending effort on properties rather than more examples — and if they do not, that is worth knowing before writing more of either.

Sequence the re-run deliberately for that reason: pilot (#test-3) -> properties (#test-5..7) -> re-run here.

## Constraints that are not negotiable

- **No always-on CI job.** Not for cost — the constraint that actually holds is *time*: the pilot took 11 minutes against a 16 s suite. Mutation testing is an investigative tool you point at code you are changing, not a gate. If it runs in CI at all it is a manual, scheduled job over a bounded scope.
- **No mutation-score gate on merge.** A score threshold as a merge gate produces test-writing aimed at the score. The pilot's per-mutant triage — *real gap* / *equivalent* / *won't fix* — is the useful artifact, not the percentage.

## If A or B

- Document the workflow in `CLAUDE.md` or `docs/design/`: when to run it, how to triage, and how to record an equivalent mutant so it is not re-triaged every time.
- A `just mutate <module>` recipe scoped to a path, so it is usable on the module you just changed rather than only as a whole-codebase ritual.
- Capture the *baseline* score per adopted module so drift is visible.

## If C

Write the reasoning down — cost per useful finding, the equivalent-mutant rate, the wall-clock — in a place the next person will find it. `docs/design/` has precedent for recording rejected approaches with their measurements (`performance.md` keeps the cattrs and dataclass numbers that justified *not* using them).

Five of the six modules are a controlled comparison — only the test suite changed. `validation.py` is confounded: it gained 50 lines in the #221 charset fix, which accounts for the 18 extra mutants.

## Why, and why it is still worth knowing

The 153 survivors are concentrated in `validation.py`'s reference-diagnostics and in `__repr__` / `__hash__` / `_format`. The properties written for #215–#217 target URNs, `InternationalString`, collections, serializer round-trips and the query DSL. **The two sets barely overlap.**

Property tests kill mutants *in the code they exercise*. They are not a general-purpose mutant killer, and the milestone's working assumption that they might be is now measured rather than assumed. That is the useful outcome even though the number did not move.

The counter-evidence matters just as much: over the same period the properties found **five real bugs** — `LIKE` metacharacter escaping (#217), `parse()` misrouting structure messages (#220), eager reads dropping `has_formal_levels` (#214), the SDMX-JSON `minItems` emission (#216), and XML-incompatible text (#221). Mutation testing found none of those, because none of them is a surviving mutant in a module the pilot covered.

**So the two techniques find disjoint things.** That is a better argument for keeping both than a score improvement would have been.

## What "narrow" means here

- **Not a merge gate**, and not a score threshold. A percentage target produces tests written to move the percentage.
- **Not CI.** 11 minutes against a 16 s suite; it is an investigative tool, not a gate. `just mutate` is local.
- **Run it on the module you are changing**, when that module is logic rather than formatting. The signal was strong in `collections.py`'s lookup paths and absent in `_format`.
- **Do not chase the `__repr__` / `_format` survivors.** Roughly a third of the 153 live there, and killing them means asserting on diagnostic strings — which #214 has just finished arguing against.

## The remaining honest gap

`validation.py`'s 123 survivors include real ones: `validate_references` survives `type(artefact).__name__` → `None`, so nothing asserts the class prefix in the issue paths it emits. Worth a targeted pass on that function specifically — which is exactly what "narrow" is for.

Baseline recorded for future comparison: **78%, 153 survivors, 825 mutants, ~14 min at 0.95/s.**
