# Issue #236: Reading a 2.1 MetadataStructure silently discards it

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Labels | `bug` |

Reading a schema-valid SDMX-ML 2.1 document that contains a `<str:MetadataStructures>` section returns a `StructureMessage` with **zero** metadata structures. No exception, no warning. The artefact is gone — id, name and attribute tree included.

## Reproduction

A hand-built 2.1 document, first validated against the vendored XSD so the input is known-good:

```
fixture: schema-valid SDMX-ML 2.1 ✓
parse() returned StructureMessage — no exception raised
metadata_structures recovered: 0
```

The cause is simple: `formats/sdmx_ml21/reader.py` has no `<str:MetadataStructures>` handling at all. The section is not skipped deliberately — it was never written.

## Why this is a defect and not a scope boundary

Nine of 2.1's twenty-one `<Structures>` children are unread. Eight of those nine are artefact types sdmxlib **does not model at all** — ReportingTaxonomy, Process, CustomType, VtlMapping, NamePersonalisation, Ruleset, Transformation, UserDefinedOperator — where ignoring the section is defensible because there is nowhere to put the result.

`MetadataStructures` is the only unread section whose artefact sdmxlib **does** model. That is what makes it a bug rather than a boundary.

## Against the read-side criterion

#237 proposes the rule: for a document `D` in format `F`, `serialize(parse(D), F)` must carry the same information as `D`, or the loss must be declared. This case fails it in the strongest possible way — the artefact does not survive `parse` at all, so nothing can be re-emitted.

Note that fixing *this* issue does not by itself satisfy the criterion for 2.1 MSDs. Reading the attribute tree makes `parse` faithful to what the model can hold, but re-emitting to 2.1 needs the `MetadataTarget` / `ReportStructure` layer back, which the model has nowhere to put — that is #235. The two are worth keeping separate:

| | today | after this issue | after #235 |
| --- | --- | --- | --- |
| `parse` a 2.1 MSD | artefact silently lost | attribute tree recovered | unchanged |
| re-emit it as 2.1 | nothing to emit | refused (per `_UNWRITABLE`) | round-trips |

So this issue moves the failure from *silent* to *explicit*, which is worth doing on its own even if #235 is never acted on — and it is the direction anyone importing existing 2.1 reference metadata actually needs.

## Suggested shape

1. Read `<str:MetadataStructures>`, flattening `ReportStructure/MetadataAttribute` into `MetadataStructure.attributes`.
2. Follow whatever #237 settles on for announcing the discarded target layer, rather than inventing a local answer.
3. Cover it with a checked-in fixture. The round-trip properties cannot reach this: the 2.1 writer refuses MSDs, so nothing generates a 2.1 document containing one — which is precisely why the gap survived.

## Note on measuring this

The "nine of twenty-one" figure came from grepping the reader for section names, and that method is **not reliable** — applied to the 3.0 and 3.1 readers it reported `ConceptSchemeMaps` and `CategorySchemeMaps` as unread, and both round-trip perfectly well. The claim above is confirmed behaviourally, with the document shown. Any wider survey should be done the same way.
