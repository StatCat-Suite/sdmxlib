# Issue #294: dsl-25: sort_by appends, so a caller's sort is silently a no-op

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `bug`, `design`, `dsl` |

`sort_by` accumulates keys, so the **first** caller's key dominates:

```python
q.sort_by(code.depth).sort_by(code.id)   # ORDER BY depth, code_id, <tiebreak>
```

A helper that sorts by a unique column makes a caller's later `sort_by` a **silent no-op** — the tiebreak never fires. Nothing errors; the caller just gets the wrong order and no signal.

## Why this slipped through

It was modelled on the refinement principle (#293) by symmetry with `limit`. That was a category error: refinement is a statement about **which rows come back**, and ordering does not change the row set. Appending is only "narrowing" in a sense that does not apply.

## What the peers do — measured, not recalled

| library | `order_by("a").order_by("b")` | reset |
| --- | --- | --- |
| SQLAlchemy 2.0 | append -> `ORDER BY a, b` | `order_by(None)` |
| Django 6.1 | **replace** -> `ORDER BY b` | `order_by()` |
| ibis 12 | **prepend** -> `ORDER BY b, a` | — |
| polars 1.43 | `sort` is a pipeline stage -> last sort wins | rebuild |

Two of three make the later call dominant. Only SQLAlchemy appends — and it is the only one of the three that provides a reset, which is what makes appending survivable there. We append **and** have no reset, which is the worst pairing available.

## Decision

- `sort_by(*keys)` takes **varargs** and **replaces**, matching Django's `order_by` and polars' `sort("a", "b")`. A caller stating an order gets the order they stated.
- `sort_by()` with no arguments **clears**, matching Django exactly.
- The compiler-appended deterministic tiebreak (`position NULLS LAST, code_id` for codes, `node_id` for nodes) stays regardless, so ordering is always total and page boundaries stay stable — which #264 depends on.
- `ascending` becomes per-key rather than per-call, since one call can now carry several keys.

## Test gates

- `sort_by(a).sort_by(b)` orders by `b` alone (plus tiebreak), asserted on a fixture where the two disagree — a fixture where `a` and `b` induce the same order cannot tell replace from append.
- `sort_by()` clears back to the default order.
- Multi-key `sort_by(a, b)` matches the old `sort_by(a).sort_by(b)` result, so the capability is not lost, only its accidental spelling.
- Ordering is total in every case: two rows never compare equal on the full key list.

## Naming, deliberately deferred

Every declarative peer calls this `order_by`; polars has no frame-level `sort_by` at all (it is an **expression** method, `pl.col("a").sort_by("b")`, meaning something else entirely). So our name is borrowed from the wrong level. Once the law here is `replace`, it matches Django's `order_by` and polars' `sort` alike, and the name is a smaller issue. Filed separately rather than bundled — 74 call sites.
