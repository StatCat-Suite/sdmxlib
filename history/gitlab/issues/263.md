`hierarchy_query.py`'s module docstring opens with a worked example that raises:

```python
Example:
    h = local.hierarchy(geo_h_urn)
    h.narrower("CA").filter(node.level == "Province").ids()
    h.nodes.filter(node.depth <= 2).collect()      # <- TypeError
```

```
TypeError: '<=' not supported between instances of '_DepthRef' and 'int'
```

`_DepthRef` inherits only `_Ref`, which defines `__eq__` and `__ne__`. There are no `__lt__` / `__le__` / `__gt__` / `__ge__` anywhere in either query DSL, so depth — the one genuinely ordered field either DSL exposes — supports equality alone.

`code_query._DepthRef` carries a comment acknowledging it:

```python
class _DepthRef(_Ref):
    ...
    # Numeric comparisons (mirror code_query._DepthRef shape if extended).
```

(That comment is in `hierarchy_query` and points at `code_query`, which does not have them either.)

## Why it matters beyond the docstring

"Everything down to level N" is the natural way to slice a hierarchy and the reason `depth` is baked into the table in the first place. Without inequalities the only route is `depth == 0 | depth == 1 | depth == 2`, which needs #262, or three queries unioned in Python. The column is a `SMALLINT` and the comparison is free; nothing about this is hard, it was just never added.

## Scope

- `__lt__` / `__le__` / `__gt__` / `__ge__` on `_DepthRef` in both DSLs, producing a new `_Cmp` predicate carrying the operator.
- Emit `{alias}.depth <op> ?`. Keep the operator in the predicate as a symbol chosen from a closed set, not interpolated from user input.
- Both files' `test_every_predicate_kind_is_covered` will fail until the new kind has a property — that is the guard working as intended.
- Decide whether the comparison operators belong on `_Ref` (available to every field, string comparisons included — SQL allows them and they are occasionally useful for ids) or only on `_DepthRef`. Narrower is the safer default; say which and why.
- Fix the docstring either way. If any part of this is deferred, the example must stop claiming a syntax that raises.

## Test gates

- Differential property against the oracle for all four operators, over generated depths including 0 and beyond the deepest node.
- `depth <= n` ≡ `depth < n+1` and the other adjacency identities, as laws.
- `depth < 0` returns nothing; `depth >= 0` returns everything (no node has a NULL depth — assert that too, since the emitters would otherwise inherit the three-valued-logic caveat from #262).
- The module docstring example runs. Consider covering it under `tests/docs/`, which already executes documentation examples.
