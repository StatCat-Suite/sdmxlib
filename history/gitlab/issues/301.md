# Issue #301: is_in: should a wide set register automatically?

Split out of #271, which built the explicit primitive (`session.value_set`) and deliberately stopped there.

## What #271 established

The cost of an eager `is_in` is **parameter binding in DuckDB's Python client, ~48 us per value** — not statement size, plan quality or key size, which is how the issue originally framed it. A 5000-code filter spends ~180 ms binding and ~1 ms querying; registering the set instead is ~1.4 ms end to end.

`register` is flat (~48 us for 100 values or 1,000,000, because it hands over an Arrow pointer), so the crossover against the bind path is at about **four** values.

## Why "a threshold" is not the obvious follow-up it sounds like

The original scope said "a threshold above which an eager `is_in` registers its values instead of expanding … roughly 100 is the conventional figure". At a crossover of four, a threshold is not a tuning knob — it is **always**, and "always register" is a much larger behavioural change than a heuristic:

- **`to_sql()` breaks.** Registering at execution means a caller handed our compiled SQL receives a reference to a relation that does not exist. That is the contract #271 preserved by making the caller own the window, and it is the reason ibis's `to_sql()` output cannot be executed outside ibis.
- **The lifetime returns.** The explicit form has no gap between register and free. An implicit one has to choose: free after execution (so `to_sql()` cannot work) or never (a leak per query).
- **`canonical_key` (#270)** currently keys `InSet.values` as a set of literals. A registered relation would key as a generated name unless treated specially, and two identical queries would stop sharing a key.

So the honest options are narrower than "pick N":

- **A. Leave it explicit.** Document the value set as the default for `is_in` (done in #271). Costs adoption; keeps every contract.
- **B. Register on the materialising paths only** — `ids`, `collect`, `len`, frame `collect` — leaving `to_sql()` binding as today. Fast by default for the common case; `to_sql()` stays slow and self-contained; the lifetime is one function call so there is no gap. The middle option, and the one worth costing first.
- **C. Register everywhere**, and accept that `to_sql()` output is no longer standalone. Matches ibis. Breaks the pinaxlib seam.

## Prerequisite

Measure how consumers actually reach `is_in` with a wide set — via `ids`/`collect` (B helps) or via `to_sql` splicing (only A helps). #273's consumer survey is the place to look, and its coverage table was already out of date once.
