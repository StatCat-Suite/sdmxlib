## Comments

### 2026-05-01

Refinement: the streaming query should accept hierarchy-traversal results as a **SQL relation**, not just a Python list, when the result is large.

Real-world driver: \"all dissemination areas in Ontario\" resolves via `Codelist.narrower_transitive(\"<ontario>\")` to ~50k REF_AREA codes. Translating that to `WHERE REF_AREA IN (?, ?, …×50000)` works (DuckDB will handle it), but it's gross and there are parameter-bind limits in other backends. `LazyCodelist` already compiles `narrower_transitive` into a SQL subquery — the data-store query should be able to consume that directly:

```python
# Either of these should work:
filter.dimensions[\"REF_AREA\"] = catalog.codelist(geo_cl).narrower_transitive(\"ON_CODE\")  # eager list
filter.dimensions[\"REF_AREA\"] = catalog.lazy_codelist(geo_cl).narrower_transitive(\"ON_CODE\")  # SQL relation
```

The streaming-query SQL builder should detect a `LazyCodelist` query object (or whatever its concrete type is) and emit `WHERE REF_AREA IN (<subquery>)` against the same DuckDB connection, instead of materialising and re-binding 50k parameters.

This is also relevant to the upcoming `ComponentFilter` (see comment on #56) — both dimension and attribute filter values should accept either form.

Not a blocker for the issue as filed; just flagging so the API shape doesn't paint us into the eager-list-only corner.
