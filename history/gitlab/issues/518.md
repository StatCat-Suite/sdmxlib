# Issue #518: REST: a measure the DSD leaves untyped is fetched as text, so it can't be compared as a number

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-21 |
| Closed | 2026-10-21 |
| Milestone | %26 Found by the docs audit: correctness and refusals |
| Labels | `data`, `needs-design`, `priority::medium` |

Found while building #511 item 9.

`column_types` (now in `local/data_store.py`) forces every measure whose DSD declares no numeric `Facet` to `VARCHAR` when a REST fetch or a file scan creates its table. Many real DSDs leave `OBS_VALUE` untyped, so over REST:

- `obs.col("OBS_VALUE") > 1.1` was a raw DuckDB binder error before #511, and is now a `TypeError` naming the fix;
- `obs.num("OBS_VALUE")` is refused ("stored as VARCHAR").

The fix the refusal names, declaring a `Facet` in the DSD, is not one a caller can make for a provider's DSD.

Options:
1. **Let DuckDB infer an untyped measure** (leave it out of the forced `types=`). `column_types`' own docstring calls inference "tolerable for measures", since a wrong guess is recoverable. A fetch whose values are all numeric then becomes `DOUBLE`, and the column's kind comes from the table once fetched. Before the first fetch the kind is unknown, so the check is permissive.
2. **Treat an untyped measure as numeric** (`DOUBLE`). That is wrong for a measure that really is text (rare, and SDMX 3.0 allows a non-numeric measure).
3. **Keep `VARCHAR`** and document `.str` / text comparison as the way to filter such a measure.

Labelled `needs-design`.

## Comments

### 2026-10-21

Decision: **option 1.** A measure the DSD leaves untyped is left out of the forced types, so DuckDB infers it on fetch or scan, and its kind comes from the table.
