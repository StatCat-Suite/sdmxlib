# Issue #402: Mutation runs die silently when a test reads a path mutmut does not copy — twice now

| | |
| --- | --- |
| State | closed |
| Opened | 2026-09-11 |
| Closed | 2026-09-11 |
| Labels | `tests` |

Mutation testing has now reported `0 killed, 0 survived` for an unknown length
of time, twice, because a unit test read a file mutmut does not copy. Both
times it was found only when someone next sat down to run mutation, and both
times the run had been silently dead in between.

## The two instances

**#284.** `tests/unit/test_count_any.py` imported `tools/count_any.py` at
module scope. `tools/` is not copied, so collection failed and the whole run
died. Its docstring records the fix and the lesson:

> `tools/` is outside the trees mutmut copies into `mutants/` (it takes
> `src/`, `tests/`, `pyproject.toml` and `uv.lock`), so a plain
> `from tools.count_any import ...` makes the whole mutation run fail at
> collection — which is exactly what #284 did, unnoticed, because mutation
> testing is not in `just ci`.

**#324, installment 2.** `tests/unit/test_data_format.py` read
`docs/cookbook/data.md` through `Path(__file__).parents[2]`. `docs/` is not
copied either, so the **stats phase** returned 1:

```
failed to collect stats. runner returned 1
1610 mutants   killed 0   survived 0   no-coverage 0
```

Fixed in !485. Note the failure mode is worse than #284's: collection failing
is at least loud in the output, while this reported a full-looking summary with
every number at zero.

## Why it keeps happening

`just ci` cannot catch it, because `just ci` runs the suite in the *real* tree
where the file is there. The only thing that exercises the copied tree is a
mutation run, and mutation runs are hours and deliberately out of the gate. So
the check that would catch this is excluded from the gate by the same reasoning
that makes the failure invisible.

## The current inventory — eight call sites, all sound

Every test reaching outside its own directory, and what it reads:

| test | reads | status |
| --- | --- | --- |
| `test_count_any` | `tools/` | module-level skip guard |
| `test_check_indexes` | `tools/` | module-level skip guard |
| `test_check_docstrings` | `tools/` | module-level skip guard |
| `test_data_format` | `docs/` | in-test skip guard (!485) |
| `test_ml3_fork_drift` | `src/` | copied — fine |
| `test_registry_naming` | `src/` | copied — fine |
| `test_sql_ast_invariants` | `pyproject.toml` | copied — fine |
| `test_query_order` | `tests/` | copied — fine |

So the tree is clean *today*. This issue is about the ninth one.

## Options

1. **A static inventory test**, the shape `test_query_edges.NOT_EDGES` already
   uses. Enumerate every `Path(__file__).parents[...]` / `.parent.parent.parent`
   under `tests/`, resolve what each expression reaches, and require the target
   to be under `src/`, `tests/`, `pyproject.toml` or `uv.lock` — or the file to
   carry a skip guard. Cheap, runs in `just ci`, and fails on the *shape* rather
   than waiting for a mutation run. Its weakness is the usual one for a static
   check: a path built some other way (a fixture, a helper, an env var) slips
   past.

2. **A smoke run against the copied tree** — `just mutate-smoke`: build the
   `mutants/` tree, run `pytest --co -q` and a fast subset there, assert exit 0.
   Catches anything however the path is built, because it is the real thing.
   Cost unmeasured; mutant *generation* alone was ~8 s in the #324 run, and
   collection is ~1 s, so it is plausibly gate-able, but the copy and a subset
   run are not free and nobody has timed it.

3. **Make mutmut copy more.** Worth ten minutes to check whether the copied set
   is configurable before building anything — if `docs/` and `tools/` can be
   included, both instances so far disappear and the guards can go. It does not
   solve the general case (the tenth thing will be outside whatever set is
   configured) but it would make the class much rarer.

(1) and (3) are complementary and neither excludes the other. (2) is the only
one that is actually *true*, which is an argument for it if the timing works
out.

## Not in scope

Putting mutation testing in `just ci`. That is a much larger question — hours
per run — and this is about the cheap check that the *runner still works*, not
about running it.

## Comments

### 2026-09-11

!486 — and the issue as I wrote it was wrong in a way worth recording.

**A guard already existed.** `tests/unit/test_suite_is_relocatable.py`, from
#252, scans for working-directory-relative reads and points at
`tests.support.repo.ROOT` — a helper that walks *past* `mutants/` to the real
checkout. Its docstring already tells this story, including a **third** prior
instance (#265, `test_public_surface.py`) that I did not know about when
filing.

So this is the **fourth** occurrence, not the second, and the interesting
question is not "why is there no guard" but **why the guard missed it twice**.

**Because there are two spellings and it only knew one.** #252's offenders were
`Path("docs/api.md")` — working-directory-relative. #284 and #324 were

```python
Path(__file__).parents[2] / "tools" / "count_any.py"
```

which is *anchored*, and still wrong: under mutmut `__file__` is inside
`mutants/tests/unit/`, so two levels up is `mutants/`. It looks like the fix.
That is why it survived the #252 cleanup and came back twice.

**So none of my three proposed options were right.** The fix is the one already
in the repo — anchor to `ROOT` — plus teaching the existing scan the second
spelling. Both now live in the file that owns the rule, because they *are* one
rule enforced over half its surface.

Eleven sites anchored: the four we knew about, plus seven the new scan turned
up that nobody had looked at (`tests/docs/*`, `test_ml3_fork_drift`,
`test_registry_naming`, `test_query_order`, `test_sql_ast_invariants`). The
three skip guards are gone with their cause — a test that skips itself in the
mutation tree is a test mutation cannot use, which is the same hole one level
quieter.

**Option 3 (`also_copy`) is actively wrong, and the repo caught me.** mutmut
does have the setting and `["docs", "tools"]` does populate the tree — I shipped
it, ran the suite in `mutants/`, and `find_root` started returning the *copy*,
because it tells checkout from copy by looking for a directory holding both
`pyproject.toml` and `docs/`. Copying `docs/` destroys that discriminator.
`test_the_root_helper_finds_the_checkout_not_the_mutants_copy` failed
immediately. It is recorded in the module docstring so nobody repeats it.

**Verified the only way that counts:** the full unit suite run inside a freshly
built `mutants/` tree — **6,539 passed, 0 failed**, with no `also_copy` and no
skip guards.

Option 2 (`mutate-smoke`) is still the only thing that would be *true* rather
than a scan of spellings, and is still unbuilt. The scan now covers both known
spellings and the `ROOT` helper makes the right thing the easy thing, which I
think retires this issue; reopen if a fifth instance finds a third spelling.
