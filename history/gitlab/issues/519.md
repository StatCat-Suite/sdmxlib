# Issue #519: write_observations fails on duckdb 2.0: a view over a Python object cannot be stored in a database file

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-21 |
| Closed | 2026-10-21 |
| Labels | `data`, `priority::high`, `status::needs-triage`, `storage`, `type::bug` |

`DuckDBDataStore.write_observations` fails under **duckdb 2.0.0**, which a fresh resolve now picks because `pyproject.toml` declares `duckdb>=1.5.6` with no upper bound.

```
_duckdb.InvalidInputException: Invalid Input Error: Cannot create the view
"__sdmxlib_write_obs_708ac18e2d50": it reads a Python object, which lives only in this
process and cannot be stored in a database file. Use register() for a view that reads it
in this session.
```

## Cause

`src/sdmxlib/local/data_store.py`, in `write_observations`:

```python
view_name = f"__sdmxlib_write_obs_{id(source):x}"
rel = _as_relation(conn, source)
rel.create_view(view_name, replace=True)
```

When `source` is a Polars/Arrow/pandas object, the relation scans a Python object. `create_view` makes a view in the connection's default catalog, and when the store is backed by a database file DuckDB 2.0 refuses to persist a view over a process-local object. duckdb 1.5.6 allowed it.

## Fix

Bind the source for the session only, as the error suggests: `conn.register(view_name, source)` paired with `conn.unregister(view_name)` in the `finally` (in place of `DROP VIEW`), or a temporary view. Separately, consider an upper bound (`duckdb>=1.5.6,<3`) so the next major is a deliberate bump. Downstream, pinax is capping `duckdb<2` until this lands (pinax-suite/pinax#131).

## Repro

Found by pinax's suite on Python 3.14.8 + sdmxlib 0.69.0 + duckdb 2.0.0. These pass on duckdb 1.5.6 and fail on 2.0.0:
- `tests/test_catalog_folder.py::TestPathStyleOpen::test_write_observations_through_lake`
- `tests/test_catalog_folder.py::TestDataPathOverride::test_redirects_to_custom_local_dir`

Minimal shape: a file-backed `LocalRegistry` with a DuckLake attached as `lake`, then `store.data.write_observations(schema="s", table="t", source=pl.DataFrame({"a": [1]}))`.

There is no other duckdb 2.0 breakage on the pinax side. Note that 2.0 also removed `Relation.fetchone()` ("Relations no longer have fetchone()"), which is worth a grep here.

## Comments

### 2026-10-21

Fixed by https://github.com/StatCat-Suite/sdmxlib/pull/6 (the move to DuckDB 2.0): `write_observations` now registers its source for the session instead of creating a view over a Python object. Released versions before that cap `duckdb<2` (0.69.1). Development of sdmxlib continues at https://github.com/StatCat-Suite/sdmxlib.
