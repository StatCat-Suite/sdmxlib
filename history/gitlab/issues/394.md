# Issue #394: all_artefacts() serves validation and storage with one list, and fails both

| | |
| --- | --- |
| State | closed |
| Opened | 2026-09-06 |
| Closed | 2026-09-06 |
| Labels | `design` |

`StructureMessage.all_artefacts()` has two kinds of caller and cannot satisfy
both as written.

- **Validation** wants *every* artefact in the message. It gets 21 of 23 slots,
  so `validate_references` never sees a `StructureSet` or a
  `HierarchicalCodelist` — and those two carry four of the five
  container-of-`Ref` fields #392 taught the walkers to resolve. #392's test had
  to assert on `_collect_refs` directly for exactly this reason.
- **Storage** wants only what it can persist. It gets the same 21, four of
  which have no `ArtefactKind`, so `add_all(msg.all_artefacts())` raises.

## The storage half is a live bug

`formats/sdmx_ml21/reader.py`, its three siblings and `api/registry.py` all
run `registry.add_all(msg.all_artefacts())`. Four yielded types have no
storage kind:

```python
>>> msg = StructureMessage(codelists=[cl], structure_maps=[sm])
>>> [type(a).__name__ for a in msg.all_artefacts()]
['Codelist', 'StructureMap']
>>> reg.add_all(msg.all_artefacts())
TypeError: Unsupported artefact type: StructureMap
```

So `parse(xml, registry=...)` refuses an entire message because one artefact
in it is not persisted yet. It fails **atomically** — nothing is written — so
there is no corruption, only a refusal that names no fix.

`AttachmentConstraint`, `ConceptSchemeMap` and `CategorySchemeMap` are the
other three.

## The omission was not what I assumed when filing

The first version of this issue guessed the two missing slots were protecting
storage. They are not, and the list is not storage-shaped: it already yields
four types storage cannot take. Adding the two would extend that from four to
six.

Nor are the six "2.1 junk". `StructureMap`, `ConceptSchemeMap` and
`CategorySchemeMap` are **3.0 artefacts**, siblings of `RepresentationMap`,
which *is* stored. `storage/schema.py` says why:

> Currently only RepresentationMap (the 3.0 successor to the 2.1 CodelistMap)
> is persisted — the other map kinds (ConceptSchemeMap, CategorySchemeMap,
> StructureMap) have no caller-driven storage need yet.

A deliberate deferral, then, and a reasonable one. What it did not anticipate
is that "not persisted yet" reaches a user as a `TypeError` on a legitimate
parse. Whether the kinds should now exist is #395; this issue is about the
behaviour either way.

## No silent dropping

The obvious fix — have storage filter `all_artefacts()` to what it can take —
is silent data loss on ingest, and this project already argues against it one
layer up. `formats/gaps.py`:

> **Dropping is the one that burns an author.** A refusal is visible; a drop is
> not.

So storage should keep refusing. What has to change is that the refusal says
what it refused, why, and what to do.

## The taxonomy this belongs to

`gaps.py` gives the wire formats three outcomes — **refused / dropped /
downgraded** — and makes them answerable in advance via
`unrepresentable(artefact, "3.0")`. Storage is a third target with the same
three outcomes and no table at all. Sorted by what the *information* is:

| | artefacts | today |
| --- | --- | --- |
| storable, round-trips to 2.1 and 3.0 | the other 19 | fine |
| storable, but the information is **2.1-only** | `StructureSet`, `HierarchicalCodelist`, `AttachmentConstraint` | writing them to 3.0 already refuses — verified — but `unrepresentable()` **records nothing**, so the refusal is not answerable in advance |
| genuinely unstorable | **none** | the six lack a kind; none is unstorable in principle |

The 2.1-only containers are `MaintainableArtefact`s holding a name and a list
of refs, which is what `sdmx.artefact` and `artefact_ref` already hold. Nothing
about them resists storage.

## Acceptance

- `all_artefacts()` yields all 23 slots, **or** the split is made explicit with
  a second accessor and each caller uses the one it means. Whichever lands, a
  test compares the method against `StructureMessage`'s field list so a *new*
  slot cannot be added without a decision — the shape
  `test_the_plan_holds_the_question_and_the_query_holds_the_binding` uses for
  `Plan`.
- `validate_references` sees `StructureSet` and `HierarchicalCodelist`, with a
  test that fails against today's source.
- Storage still refuses an artefact it cannot persist — **never drops it** —
  and the refusal names the type, says it is not persisted rather than
  malformed, and points at the fix (`parse` without `registry=`, or #395).
- The 2.1-only artefacts are recorded in `gaps.py`, so
  `unrepresentable(structure_set, "3.0")` answers instead of returning nothing
  while `to_xml(..., "3.0")` refuses.

## The decision this issue left open answered itself

"Complete the list, or split it" turned out not to be a coin flip. The omission
was **not** protecting the storage callers — it was a silent drop:

```python
>>> msg = StructureMessage(hierarchies=[h], hierarchical_codelists=[hcl])
>>> [type(a).__name__ for a in msg.all_artefacts()]
['Hierarchy']
>>> reg.add_all(msg.all_artefacts())   # the container simply ceased to exist
```

A `HierarchicalCodelist` named "Geographic hierarchy" vanished on
`parse(xml, registry=…)` with no error — the name #239 added the container to
stop losing. Completing the list turns that into a visible refusal, which is
the rule `formats/gaps.py` already states: *a refusal is visible, a drop is
not.*

So: 23 slots, `validate_references` sees both types, and storage refuses six
where it refused four.

## The refusal now says what it is

    HierarchicalCodelist is not persisted by this registry — an SDMX 2.1
    container; 3.0 promoted Hierarchy to top level (#395). It was parsed and is
    valid; only storage cannot hold it. Refused rather than skipped so the
    artefact is not lost silently: read the message without `registry=` to keep
    it in memory, or drop it from the message before adding.

against `Unsupported artefact type: HierarchicalCodelist`, which reads as
*malformed* and is not. `_NOT_PERSISTED` in `storage/writers.py` is the single
place a row goes away as #395 lands kinds.

`add_all` is one transaction, so the refusal is atomic — a caller who catches
the `TypeError` is not left with half a message. Asserted rather than assumed.

## One acceptance item was wrong and is not done

I asked for the 2.1-only artefacts to be recorded in `gaps.py` so
`unrepresentable()` answers for them. That contradicts the module's contract:

> Does **not** report what would be *refused* — an unrepresentable version, or
> a 2.1 DataStructure with no measures. Those raise at `write` with a message
> of their own … This is for the losses that make no sound.

Writing a `StructureSet` to 3.0 **refuses** — verified, `to_xml(msg, "3.0")`
raises while 2.1 writes cleanly — so `unrepresentable(structure_set, "3.0")`
returning nothing is correct, not a gap. And after this change there is no
storage *drop* left to record either: the two that were dropped are now
refused. Nothing to add to the table.
