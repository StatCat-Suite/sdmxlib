# Issue #297: data-plane: _build_query interpolates caller SQL text — model it, or fence it

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-10 |
| Closed | 2026-08-17 |
| Labels | `data`, `design`, `needs-design` |

Split out of #273, which decided the *structural* DSLs need no intermediate representation and identified the data plane as the place the same reasoning actually lands.

## The surface

`local/data_store._build_query` takes `where: list[str]`, `columns: list[str]` and `order_by: str` and interpolates all three **as SQL text**. `ComponentFilter.to_where_clauses` returns fragments rather than values. DuckDB runs every statement in a multi-statement string, so `order_by` in particular is a statement-injection surface — and it is the parameter an HTTP layer is most likely to populate from a request.

#257 looked at this and decided to **document rather than validate**. That decision is recorded in the docstring and stands; this issue is about whether it is still the right one now that the structural side has moved so far in the other direction.

## Why it is worth revisiting

The two halves of the library now have opposite safety properties:

- **Structural DSLs**: never accept SQL text. A caller supplies field references and literals, and since #272 the literals are type-checked against the column type read from the DDL.
- **Data plane**: accepts SQL text for three of its parameters and splices it.

A consumer moving between them has no way to tell which is which from the call shape.

## Not simply "give it the same IR"

#273 considered and rejected sharing a representation. The structural DSLs are safe *because* they have no text-accepting path; merging would give them one. Whatever this becomes should be its own thing.

It is also a genuinely harder problem: the data plane has joins (sidecar `LEFT JOIN`), aggregation, DuckLake, and caller-supplied tables the library does not own — the OLAP node set the #273 brief proposed, which did not fit the structural side but may fit here.

## Options, none costed yet

- **A. Keep documenting.** #257's answer. Defensible while consumers are first-party.
- **B. Fence the text.** Validate `order_by` / `columns` against the binding's known columns via `SchemaInspector`, which already reflects the schema and caches `DESCRIBE`. Rejects injection without modelling anything.
- **C. Model it.** A small typed filter/projection/order vocabulary for the data plane, with the raw-text path kept as an explicit escape hatch rather than the default.

B is probably the cheap win: the column list is already known, and it turns a documented hazard into a rejected call without inventing a query language.

## Prerequisite

Measure first, as #273's premises had to be. Specifically: how many consumer call sites pass a non-constant `where` / `order_by` / `columns`, and how many of those derive it from user input. If the answer is "none, they are all literals in application code", A stays right and this closes.

### 2026-08-17

**Step 4 sizing turned up a fourth coupling the design doc's probes missed**, fixed in !338 (`b4576f4`) before it got expensive.

Sixteen sites read a root's identity off its **class** — `type(root).__table__`, `__key__`, `__id__`, `__constraint__`. Correct and invisible for every structural accessor, since each is a singleton whose relation is a property of its type. Not correct for a dataflow: the observation table comes from a *binding*, so two roots of the same class name two different tables. The alternative — synthesising a class per binding with `type()` — exists and is worse. Reading the instance costs the singletons nothing and 5,227 tests did not move.

Steps 1–3 are done: root qualification (!335), the `USING` join form (!336), numeric aggregates (!337, with #327 for what is left).

**Two design questions step 4 must answer, and neither is in the doc yet:**

1. **What is an observation's `__key__`?** The compiler uses it for keyset paging and for the resolver. Observations have no surrogate key — but SDMX says they are keyed by their dimensions, so `binding.dimension_column_map.values()` in DSD order is the natural answer, and it makes paging work rather than special-casing it.
2. **What is `__id__`, and which terminals survive?** There is no single id column, so `ids()` and `urns()` have no meaning here. They should refuse with a message saying so, rather than return something invented. `collect()`, `frame()`, `count()` and `exists()` are the ones that mean something.

Also unresolved and now blocking the *shape* of `obs["GEO"]`: **what column type does a dynamically named column have?** The static answer must be one type, and the runtime one could be several. `SchemaInspector` can DESCRIBE the table and knows the physical types, so a runtime-typed `Str`/`Num` is available — but statically `obs["X"]` is one signature, and a column typed `Str` statically will not accept arithmetic even when the runtime object is `Num`. That interacts with `docs/design/phantom-generics.md` and wants its own decision.

### 2026-08-17

Option C, landed, and the escape hatch is a whole statement rather than
fragments.

`observations()` (!3xx, #297 step 4) modelled the vocabulary; #332 gave it
the sidecar join; #329 deleted `query` / `query_stream`, `_build_query` and
`_fence`. There is no longer a text-accepting parameter on the data plane —
`where` / `columns` / `order_by` are `filter()` / `select()` / `order_by()`
over named components, every value bound.

**The fence went with them, which is the part worth recording.** Option B
shipped first and was measured: a *table* allow-list breaks relation-valued
filters and `Session.value_set`, which reach other tables on purpose, and a
*column* allow-list rejects `columns=["a AS x"], order_by="x"`, which is
correct SQL. Both failures said the same thing — composition across tables and
expressions is the feature, so no property of the *text* separates use from
abuse. What was left, statement-count, only ever guarded an assembled
statement. With nothing assembled there is nothing to guard, and
`catalog.sql(text, **params)` takes one complete statement checked against
DuckDB's own parse, the same rule `Registry.sql` uses.

The prerequisite measurement is what decided it: one of six consumers passed
`where`, and it built it from **HTTP query parameters** — with its own operator
table, column allow-list and LIKE-metacharacter escaping. So A was not right;
the application was compensating for the library.

Two consequences are in `docs/design/data-plane-query.md` §8: `DataStore` is
now a write-side Protocol (reading needs a compiler, which a Protocol cannot
require of an arbitrary backend), and an unprojected result had to learn about
root joins — `s0.*` is right for a path hop and silently wrong for a sidecar.

Still open, tracked separately: §6.2's `Query`/`KeyedQuery` split, so `ids()` /
`urns()` are *absent* on an observation query rather than failing at the
database; §6.3's typed columns from the DSD; and #326 / #327 on the aggregate
set.
