# Issue #352: edge() resolves targets by class-definition order, so 17 paths dead-end at _Maintainable and file order is public API

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |
| Labels | `design`, `dsl` |

Raised by an independent audit of the query language, verified here.

`edge()` takes a **concrete class object**, evaluated in the class body:

```python
codelist: _Maintainable[R] = edge("codelist", _Maintainable)   # accessors.py:661
```

A target class defined *later* in the file cannot be named, so the edge falls
back to `_Maintainable` and the path stops there. Which edges get their real
type is therefore decided by where 63 classes happen to sit in one 1584-line
file.

## The demonstration

```
definition lines: _Maintainable 388, _Concept 479, _Component 640, _Codelist 1020

q.dsd.components.concept    -> _Concept        (defined before _Component — typed)
q.dsd.components.codelist   -> _Maintainable   (defined after  _Component — truncated)
```

**Same relation, one hop, two different outcomes**, and nothing about the
domain explains the difference. A user cannot predict which sibling continues.

Measured: 17 edge declarations across 9 names — `artefact`, `codelist`,
`constraint`, `dsd`, `hierarchy`, `metadata_set`, `msd`, `representation_map`,
`scheme` — resolve to `_Maintainable`. Some are genuinely polymorphic
(`categorisation.artefact` really can point at anything). Most are not.

Queries this blocks, all run:

```
q.dsd.components.codelist.codes.id == "FR"   AttributeError: '_Maintainable' has no attribute 'codes'
q.code.codelist.<anything beyond the spine>  AttributeError
q.hcode.hierarchy.hcodes.id                  AttributeError
q.concept.scheme.concepts.count() > 2        AttributeError
q.metadata_attribute.msd.attributes.id       AttributeError
```

## It is not cycle-breaking

The obvious defence would be that truncation stops infinite paths. It does not
— a cycle is already reachable:

```python
q.dataflow.dsd.dataflows          # resolves fine
```

So the truncation buys nothing structural. It is an artefact of the mechanism.

## Why this is worse than the individual gaps

The test suite says the quiet part out loud — *"That is paid for by definition
order rather than machinery."* Two consequences:

1. **Reordering the file for readability silently changes the public language.**
   Nothing asserts which edges got the good type, so a refactor that moves
   `_Codelist` above `_Component` would *add* API, and one that moves `_Concept`
   below would remove it. Neither would fail a test.
2. **Every future edge inherits the hazard.** This is not a list of 17 things to
   fix once; it is a property of `edge()`.

## Scope

- Make `edge()` take a target **name**, resolved lazily on first access —
  `__set_name__` plus a module-level registry, or a string forward reference
  resolved at first attribute access.
- Add a test asserting every `_edges.EDGES` entry's accessor target type, so the
  language's shape is pinned rather than inherited from line numbers. That guard
  is the durable half; without it the same drift returns.
- Keep `_Maintainable` where the edge really is polymorphic, and make that a
  *declared* choice rather than a fallback — the two are indistinguishable today.

Cheapest large win available in the query layer: one mechanism change turns 17
dead ends into live paths.

## Comments

### 2026-08-20

Fixed in !397. `edge()` now names its target and resolves it on first read
via `__set_name__`; fifteen edges point at a concrete accessor and five stay
`_Maintainable` because they really are polymorphic — now a declared choice
rather than a fallback indistinguishable from one.

`test_query_edges` carries the durable half: no edge may land on
`_Maintainable` without being listed, and no listed edge may have since been
given a concrete target. Verified it discriminates — reverting one edge names
exactly the four accessors that regressed.

One thing worth recording, because it changes the issue's premise slightly.
`test_a_component_still_stops_at_the_maintainable_surface` asserted the
truncation was *deliberate* for `_Component.dsd`, and its reasoning was sound
for the mechanism it was written against: `_Dsd.components` needs
`_ManyComponent` needs `_Component` needs `_Dsd` — a mutual recursion no
reordering resolves, and unlike `flows` there was no base class to weaken.

Deferring the target dissolves it anyway: `_Component` can say `"_Dsd"` before
`_Dsd` exists. So that case was *also* the mechanism rather than the domain,
which is what its docstring said it wanted pinned so as not to be mistaken
for. Inverted, with the reasoning kept.
