# Issue #507: to_json writes a DSD its own reader refuses (time dimension with no representation)

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-20 |
| Closed | 2026-10-20 |
| Milestone | %26 Found by the docs audit: correctness and refusals |
| Labels | `bug`, `conformance`, `json`, `priority::high`, `sdmx-json` |

`sl.to_json` writes a DSD that `sl.parse` then refuses. The DSD's `TimeDimension` has `representation=None`, so it is written with no `localRepresentation`, and the reader refuses it: "the schema requires a conceptIdentity and a localRepresentation format".

```python
dsd = sl.DataStructure(..., time_dimension=sl.TimeDimension(id="TIME_PERIOD", concept=...), ...)
sl.parse(sl.to_json(sl.StructureMessage(concept_schemes=[cs], data_structures=[dsd])))
# SdmxConformanceError: 1 artefact refused
```

Either the writer must supply what SDMX-JSON 2.0 requires for a time dimension (its default `ObservationalTimePeriod` format), or the model must refuse a time dimension that no JSON can carry. The writer side is the likely fix: SDMX-ML defaults the time format, and the JSON schema requires it to be stated.

The doc fixture `_inspectable_dsd` hits this, which is why the serialisation cookbook avoids round-tripping that DSD through JSON.
