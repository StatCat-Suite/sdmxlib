# Issue #235: MetadataStructure has no faithful SDMX-ML 2.1 form: 3.0 -> 2.1 -> 3.0 is not an identity

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-07 |
| Closed | 2026-08-07 |
| Labels | `bug` |

Split out of #225 so it does not block milestone 11. Nothing here is urgent — the current behaviour is a clean refusal, not a silent loss — but the decision behind that refusal is worth revisiting deliberately rather than inheriting.

## Current behaviour

`serialize(msg, version="2.1")` **refuses** a message carrying `metadata_structures`, via `validation._UNWRITABLE["2.1"]`. It does not drop them (that was the #225 bug) and does not emit an invalid document (that was the pre-!231 behaviour). A caller who needs 2.1 gets a message naming exactly what cannot be represented.

`Metadataflow` was the other half of #225 and **is** now implemented in 2.1 (!238). This issue is only about the MSD.

## Why it is not just a missing emitter

SDMX-ML 2.1 and SDMX 3.0 model reference metadata differently, and 3.0 is the *smaller* model. 2.1 requires a reporting layer that 3.0 deleted outright, and sdmxlib follows 3.0.

What 2.1 requires, read out of the vendored XSDs:

```
MetadataStructureType
  └── MetadataStructureComponents          minOccurs=1   (required)
        ├── MetadataTarget                 1..unbounded  (required)
        │     └── exactly one of:
        │           KeyDescriptorValuesTarget   → LocalRepresentation (required)
        │           DataSetTarget               → LocalRepresentation (required)
        │           ConstraintContentTarget     → LocalRepresentation (required)
        │           ReportPeriodTarget          → LocalRepresentation (required)
        │           IdentifiableObjectTarget    → LocalRepresentation (required), @id required
        └── ReportStructure                1..unbounded  (required)
              ├── @id                      required
              ├── MetadataAttribute        1..unbounded  (required)
              └── MetadataTarget           1..unbounded  (required, references the targets above)
```

What sdmxlib's model carries:

```
MetadataStructure(id, maintainer, version, name, description, is_final,
                  annotations, valid_from, valid_to, attributes)
MetadataAttribute(id, concept, representation, min_occurs, max_occurs,
                  is_presentational, children, annotations)
```

So the model has the attribute *tree* and nothing at all corresponding to a **MetadataTarget** (what kind of thing the metadata is reported against, with its own local representation) or a **ReportStructure** (a named grouping of attributes bound to a set of targets).

Writing a 2.1 MSD therefore means **inventing** both: picking one of five target kinds, synthesising a `LocalRepresentation` for it, and wrapping the attribute tree in a `ReportStructure` with an id nobody supplied. On read-back all of it would be discarded, because the model has nowhere to put it.

**The round-trip is the concrete symptom.** A 3.0 → 2.1 → 3.0 pass would not return what it was given: the invented target and report structure would appear in the intermediate document and vanish again, and two different 3.0 MSDs could serialise to the same 2.1 document. That is why this is refused rather than best-effort — the same call as 2.1 component maps needing a `class`/`package` the model does not carry (#226).

## Options, roughly in increasing cost

1. **Leave it refused.** Zero risk. 2.1 reference metadata is rare, and a caller who needs it is better served by an explicit refusal than by a document that quietly means something else. This is the status quo and a legitimate final answer.

2. **Emit a canonical single target + single report structure**, documented as lossy, and refuse to read 2.1 MSDs back (or read them dropping the layer). Cheap, but it makes `to_xml(version="2.1")` produce a document sdmxlib itself cannot faithfully re-read, which no other artefact currently does.

3. **Model the 2.1 layer.** Add `MetadataTarget` and `ReportStructure` as optional model concepts, populated when reading 2.1 and used when writing it, ignored by 3.0/3.1 and SDMX-JSON. Faithful in both directions, and the only option under which a 3.0 → 2.1 → 3.0 round-trip is an identity. Costs a model change carried purely to serve an older format.

Option 3 is the only one that makes the round-trip honest. Whether that is worth carrying depends on whether anyone actually needs to *emit* 2.1 reference metadata — reading it, if a 2.1 MSD ever needs importing, is a separate and easier question that could be done first.

## Not blocking

The conformance gate is green either way: a refusal satisfies "valid or refused with a reason". No `KNOWN_INVALID` entry, no silent loss.

## Verify before acting

The cardinalities above came from `tests/support/xsd_facts.required_children("2.1")` and `required_choices("2.1")`. Re-derive them rather than trusting this issue if the vendored schemas have been refreshed since it was written.

## Comments

### 2026-08-07

Closed by !244, which took **option 3** — model the 2.1 layer.

`MetadataTarget` and `ReportStructure` are now first-class, and **a 2.1 MetadataStructure round-trips losslessly**. The layer is held as a peer that references `MetadataStructure.attributes` by id rather than copying them, matching the decision made for `StructureSet` in #239: one copy of the fact, no way for duplicates to disagree.

## What this issue predicted, and what happened

It said *"no option makes 2.1 → 3.0 → 2.1 exact, because the intermediate cannot hold the layer"*. That is exactly how it turned out:

| | before | after |
| --- | --- | --- |
| 2.1 MSD, same version | refused | **lossless** |
| 2.1 → 3.x → 2.1 | blocked | blocked — **settled, not pending** |
| 3.x-shaped MSD → 2.1 | blocked | blocked, with a message naming what to populate |

So the same-version rule (#237) is satisfied and the cross-version hop is a permanent boundary, now recorded as *fundamental* in the cross-version harness (#246) alongside the grouping containers rather than sitting in a to-do table.

The refusal did not disappear — it became conditional. An MSD carrying no reporting layer still has no 2.1 form, which is correct: synthesising one would invent a target kind and a report grouping nobody supplied.

## Three schema details worth recording

Each only surfaced on writing the thing, and each is now enforced or handled:

- **A MetadataTarget has two ids** — the `<MetadataTarget>` carries one that report structures reference, and the kind element inside carries another. Collapsing them made the round-trip reference the wrong target.
- **`TargetObjectTextFormatType` permits four text types**, not `DataType`'s forty-four: a target names what *kind of thing* is described, not a value domain.
- `MetadataStructureComponents` needs *both* a target and a report structure; neither alone is valid.

Option 1 (leave it refused) and option 3 (synthesise on conversion) were not taken: the first leaves a same-version refusal that #237 rules out, and the second produces valid 2.1 that means something the caller never said.
