# Issue #350: ~col.is_in(subquery) returns nothing when the subquery has a NULL — the anti-join is broken

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-21 |
| Labels | `bug`, `dsl` |

Found by an independent audit of the query language; reproduced and verified
here before filing.

`~col.is_in(subquery)` — the anti-join — returns **no rows** whenever the
subquery's column contains a NULL. It is not an error and not a partial
result: it is empty.

```python
# CL_FREQ and CL_GEO are used by a dimension; CL_UNUSED is not.
# TIME_PERIOD is a dimension with no codelist, so codelist_urn is NULL.
used = reg.query(q.component).select(urn=q.component.codelist.urn)

reg.query(q.codelist).filter(q.codelist.urn.is_in(used)).ids()
# ['CL_FREQ', 'CL_GEO']          correct

reg.query(q.codelist).filter(~q.codelist.urn.is_in(used)).ids()
# []                             WRONG — expected ['CL_UNUSED']
```

## Why

`_compile.py:302` emits `IN` and lets `Not` wrap it:

```sql
WHERE (... AND NOT (s0.urn IN (SELECT s0.codelist_urn AS urn FROM sdmx.dsd_component s0 ...)))
```

SQL's `NOT IN` over a set containing NULL is UNKNOWN for **every** row, so the
predicate selects nothing. Classic three-valued-logic trap.

## The fix already exists thirty lines away

`_row_in` emits `NOT EXISTS (SELECT 1 FROM (...) alias WHERE ...)`, which is
null-safe — and that is why `Query.difference()` gets the right answer on the
same data:

```python
reg.query(q.codelist).difference(
    reg.query(q.codelist).filter(q.codelist.urn.is_in(used))
).ids()
# ['CL_UNUSED']                  correct
```

So the library already knows how to do this; the negated `InRelation` path just
does not route through it. Guarding the subquery by hand also works
(`.filter(q.component.codelist.urn.is_not_null())` → `['CL_UNUSED']`), but a
caller has no reason to know they must.

## Why it matters more than it looks

`is_in(subquery)` is the documented workaround for relations the edge graph
exposes in only one direction — "codelists nothing uses", "dataflows with no
constraint", "concepts no component cites" are all anti-joins, and all of them
are exactly the shape that hits a nullable FK.

The cookbook is careful about three-valued logic at the *column* level ("a row
whose column is NULL satisfies neither `p` nor `~p`") and silent about this,
which is categorically worse: not "some rows drop" but "all rows drop".

## Scope

- Route a negated `InRelation` through `_row_in`'s `NOT EXISTS`.
- No test covers the negated form at all. Add a differential property over a
  generated relation with a nullable column, in the style of
  `tests/unit/test_properties_query_code.py` — the oracle discipline here would
  have caught this had it been pointed at negation.
- Check the same question for `is_in` over a literal list containing `None`.

### 2026-08-21

Already fixed — closing as stale.

Landed in `c34e3b0` (2026-08-20), *"fix(query)!: the anti-join was empty, and version.max() said 1.9 > 1.10"*, which fixed this and its sibling together. The MR did not use a closing keyword, so the issue stayed open.

Verified on `main` before closing, not taken on trust:

- **#350** — `_compile.py` now has a `Not(part=InRelation())` case routing to `_anti_join`, which emits `NOT EXISTS (SELECT 1 FROM (…) AS alias(value) WHERE …)`. Guarded by `tests/unit/test_query_anti_join.py` (8 passing). The `IS NOT NULL` sits on the *left* side deliberately, so `is_in` and `~is_in` still partition.
- **#351** — `_compile.py:796` special-cases `min`/`max` when `sort_column != column`, emitting `arg_max(value, key)` so the answer comes back in the column's own terms rather than as its sort key. Guarded by `tests/unit/test_version_ordering.py`.

Both scope items in the descriptions were done, including the tests each issue noted were missing.
