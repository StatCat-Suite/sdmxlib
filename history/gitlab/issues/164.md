## Idea (speculative — not scheduled)

Today `SchemaInspector.plan(binding)` returns a `QueryPlan` that describes only
the **FROM side** of a query — `main`, `sidecar`, `join_keys`, `from_clause`.
Consumers building custom SQL splice their own `SELECT` / `WHERE` / `ORDER` /
`LIMIT` onto `from_clause`. This is deliberate: the projection/filters are the
easy part they want full control of; the binding→tables+join derivation is the
hard, coupled part the plan hands them. (See #163 and the follow-up that removed
a stranded `QueryPlan.columns` field for the reasoning.)

**Design-B** is the more ambitious alternative: make `QueryPlan` a *full
statement descriptor* — a composable query object rather than a FROM-side
fragment. Roughly the SQLAlchemy `Select` / Ibis-expression direction:

```python
plan = insp.plan(binding, columns=[...], where=[...], order_by=..., limit=...)
plan.columns      # projection
plan.where        # WHERE fragments (+ params)
plan.order_by / plan.limit
sql, params = plan.to_sql()          # render the whole statement
plan_variant = plan.evolve(limit=100)  # tweak one part, re-render
```

`DuckDBDataStore._build_query` would then be refactored to *render from* the
plan (`plan.to_sql()`) instead of hand-assembling the string — so `query()` /
`query_stream()` become thin wrappers over the same plan object consumers see,
and there is exactly one place that knows how a binding becomes SQL.

### Why it's NOT scheduled

- **This seam's own consumers wouldn't use the projection/filters.** They drop
  to custom SQL *precisely because* they want expressions `query()` can't
  emit (`printf`, wide pivots, Hive-partition pruning, Range pagination). Even
  with a full descriptor they'd still write their own `SELECT`/`WHERE`. The
  value they extract is the FROM-side derivation, which Design-A already gives.
- **Real added surface:** `where`/`order_by`/`limit` fields, a `to_sql()`
  renderer, an `evolve()`-style API, param threading, and tests — for a
  composability nobody has asked for yet.
- **Speculative until a concrete need appears** (e.g. a consumer that wants to
  take the store's default query and modify one clause, or a second data-plane
  backend that benefits from a backend-agnostic plan object).

### Revisit when

- A consumer genuinely wants to start from `query()`'s statement and tweak a
  single clause, rather than rebuild from `from_clause`.
- We add a non-DuckDB `DataStore` and want a shared, renderable plan
  representation across backends.

Filed off the #163 quality audit as a deliberate "known future direction, not
half-built now."

## Comments

### 2026-08-20

**Closing — superseded by the query DSL.**

The description opens "speculative — not scheduled", and what it speculates
about has since been built in a different place.

Design-B asked for `QueryPlan` to become "a composable query object rather than
a FROM-side descriptor". That object exists: `query/query.py::Query[R]` is a
`Plan` plus its binding, strictly lazy and refining, with `filter`, `select`,
`group_by`, `limit`, `offset`, `after`/`cursor`, the set operations, and
`collect` / `ids` / `count` / `first` / `frame` as terminals. `query/_plan.py`
holds the `Plan` — what a query *says* — split from how it runs, which is the
separation Design-B was reaching for.

`SchemaInspector.plan(binding)` and its `QueryPlan` still exist and are
unchanged, deliberately. They serve the **custom-SQL seam**: a caller who wants
to write their own `SELECT` and needs the binding→tables+join derivation done
for them. That is a different consumer from the one Design-B imagined, and
`reg.sql()` plus `sl.schema` now serve the raw-SQL case explicitly. Growing
`QueryPlan` into a statement descriptor would duplicate `Query` for the smaller
audience.

So the direction is settled and it is not this one. Reopening would need a
concrete case where `Query` cannot express something and splicing onto
`from_clause` can — worth filing fresh if that turns up, since it would be an
argument about `Query`'s limits rather than about `QueryPlan`'s shape.
