# Issue #478: SDMX 3.x un-versioned artefacts: the model holds them as 1.0

| | |
| --- | --- |
| State | closed |
| Opened | 2026-10-16 |
| Closed | 2026-10-20 |
| Milestone | %21 Conformance evidence: what the green checks do not prove |

Found by the #474 census.

**What the schema says.** In SDMX-ML 3.0 and 3.1, `VersionableType/@version` is optional with no default: *"If not supplied, artefact is considered to be un-versioned."* (2.1, by contrast, defaults it to `1.0`.) 3.x additionally *prohibits* `@version` on organisation schemes and, in 3.1, on `Categorisation` — those are versionless by the standard.

**What happens.** The model's `MaintainableArtefact.version` is a `str`, so an un-versioned 3.x artefact is read as `1.0`. Since #474 that is recorded on `msg.assumed` (`ASSUMPTIONS` row `@version`) rather than passing silently, and `lossless=True` refuses it — but the artefact still claims a version the document never gave it, and writing it back emits `version="1.0"`.

**Exposure.** In our 3.x fixtures, 10 of 125 maintainables carry no `@version`; all but the hand-written Categorisations are organisation schemes (versionless by the standard, not an assumption).

**Question.** Model un-versioned artefacts (`version: str | None`, a URN without `(…)`, store and query support) or keep the recorded assumption. The former is an IM change across model, URN, storage and every writer; worth checking how sdmx1 and pysdmx hold it first.

## Comments

### 2026-10-20

**Decision (2026-10-20): keep `1.0` and the recorded assumption.** The model will not hold an un-versioned artefact.

**Measured** across the sweep's raw SDMX-ML 3.0 responses from BIS, ESTAT, IMF, OECD and SDMX: 686,633 maintainable artefacts. **31 have no `@version`, and every one is an organisation scheme**, the type whose `@version` 3.x prohibits:

| registry | type | without `@version` |
| --- | --- | --- |
| BIS | AgencyScheme | 2 / 2 |
| BIS | DataProviderScheme | 1 / 1 |
| OECD | AgencyScheme | 24 / 24 |
| SDMX | AgencyScheme | 1 / 1 |
| SDMX | DataConsumerScheme | 1 / 1 |
| SDMX | DataProviderScheme | 2 / 2 |

All 31 still carry `(1.0)` in their URN. So the registries call them `1.0` too.

The readers already handle that case. `_VERSIONLESS_30` (SDMX-ML) and `_VERSIONLESS` (SDMX-JSON) read these types as `1.0` with nothing assumed. The `@version` assumption, and the refusal under `lossless=True`, fire only for an artefact of another type with no version. Nobody we sweep publishes one.

`version: str | None` would change the type across URNs, `Ref`, storage, sorting, the query language and every writer, for zero observed artefacts. pysdmx holds versions the same way we do (`version: str = "1.0"`). If an un-versioned artefact ever appears, the read records it, so it cannot pass silently.
