# Issue #272: dsl-21: code.id == 1 builds and binds an int against a VARCHAR column

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Closed | 2026-08-10 |
| Milestone | %14 Query DSLs: say what the docs already claim |
| Labels | `bug`, `dsl`, `validation` |

Nothing checks that a literal matches its column's storage type:

```python
>>> code.id == 1
Eq(field=_IdField(), value=1, negate=False)
```

`code_id` is `VARCHAR`. That predicate builds, type-checks (`__eq__` takes `object`), compiles, and binds an integer. DuckDB will either coerce it or return nothing, depending on the comparison — and returning nothing is the bad case, because it looks like a legitimately empty result.

## Why `object` and not `str`

`Ref.__eq__` must take `object` — it overrides `object.__eq__`, and narrowing the parameter is unsound and rejected by both checkers. So the type system cannot help here through the dunder, which is exactly why it needs saying somewhere else.

## Scope

Three options, in increasing cost:

- **A. Validate at construction.** Each field expression knows its storage type; `Eq`/`InSet`/`Cmp` reject a literal that cannot be compared against it. Catches it at the call site with a good message. Cost: a per-field type declaration, and a judgement about what counts as compatible (is `int` acceptable for `depth`? yes. for `code_id`? no).
- **B. Coerce at construction.** Silently `str()` a non-string for a VARCHAR column. Convenient and wrong — it makes `code.id == 1` mean `code.id == "1"`, which may not be what the caller meant.
- **C. Document and leave.** Defensible if the surface is considered internal, which it is not — `sl.code` is the documented entry point.

A is the right answer if a field can cheaply name its storage type. It probably can: `RowKind` already names the columns, and adding their types is a small extension of the same table.

## Related

Same shape as #261's bare-string trap (`is_in("CA")` iterating into characters), which was found by comparing the API against polars rather than by any test. Both are "the value is the wrong *kind* of thing and nothing says so", and #266 (misuse tests) is where the guard against the class belongs.

## Test gates

- A misuse test per field kind: a literal of the wrong type raises, with a message naming the column and the expected type.
- The valid cases are unaffected — `code.depth == 2` and `code.depth == "2"` should not both work, and deciding which is the point.
- No change to emitted SQL for well-typed queries (`sql_corpus` diff empty).
