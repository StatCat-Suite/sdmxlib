## The model question, answered

Five fields hold `Ref`s in a plain container, and all five are genuine
references that should resolve: `MetadataSet.targets`,
`HierarchicalCodelist.hierarchies` and `.included_codelists`,
`StructureSet.maps` and `.related_structures`.

**The sixth row above is wrong.** `Metadataflow.targets` is *already*
`tuple[str, ...]`, and so is `MetadataProvisionAgreement.targets` — the model
and the reader agree, and #362's reasoning (a declared target may be a wildcard
URN) is reflected in both. Nothing was out of step. It appeared in the survey
for an unrelated reason, which turned out to be its own bug:

**`_refshape` read `...` as an unreadable annotation.** The ellipsis in
`tuple[X, ...]` is a shape marker carrying no type, and `_classes_in` fell
through to its "I cannot tell" branch. Every homogeneous tuple field was
therefore conservatively walkable. `walk_fields(Metadataflow)` is now
`('maintainer', 'structure')`. The differential guard accepts the narrowing —
it forbids the static shape being narrower than *reflection*, and reflection
does not find a tuple of strings interesting either.

## The traversal, and the write-back problem the issue did not anticipate

"The traversal fix is easy once it is answered" was not quite right: both
walkers write resolution back with `setattr(owner, field_name, …)`, and a `Ref`
inside a container has no such address — two of the five fields are tuples,
which cannot be written to at all.

The resolver does not need one. `intern_resolution(ref, obj)` is the existing
package-internal primitive for resolving a ref *object*, and its docstring
already states the property that makes this sound: resolution propagates to
every holder rather than to one field of one owner. Container refs are recorded
with `None` for the field name and resolved that way.

The in-memory interner needs the opposite, since its purpose is that one URN
yields one `Ref` **object**: it replaces, assigning into a list or rebuilding a
tuple, and only when something actually changed.

## Cost, by call count as asked

The first working version asked `isinstance(item, Ref)` of every element it
iterated — **+580,332 calls on `CL_GEOGRAPHY`**, one per code, for a question
the class already knew the answer to. `ref_container_fields` moves the branch
to the class, and `walk_plan` folds it into the lookup the walk was already
making.

| eager read | before | after | |
| --- | --- | --- | --- |
| `CL_GEOGRAPHY` (579,951 codes) | 16,905,525 | 16,906,152 | +0.004% |
| `H_CP_GEO_FED` (499,138 nodes) | 60,019,535 | **59,520,860** | **−0.8%** |
| a `MetadataSet` | 15,909 | 19,987 | the new work |

The hierarchy read is *cheaper* than before the fix. Fitting the new branch
under the complexity limit meant reading the loop, and
`elif attrs.has(type(value)) and not isinstance(value, type)` turned out to
duplicate the pair `_collect_refs` opens with — it only decided whether the
early return happened at this frame or the next.

`can_reach_ref` still short-circuits the large schemes, which is what this
issue asked be confirmed.

## Two things found on the way

**The defect was on both read paths.** There is no `LazyMetadataSet`, so a
plain `get()` reads the whole artefact and resolves it. The eager read this
issue measured was not the only one affected.

**`StructureMessage.all_artefacts()` omits `structure_sets` and
`hierarchical_codelists`.** So the two artefact types carrying this shape are
invisible to `validate_references` for a reason unrelated to #148 or this —
worth its own issue.

It also repaired one of !458's tests, which passed a `Ref` into
`Metadataflow.targets` and agreed with the code for the wrong reason; it only
passed because of the ellipsis bug fixed here.
