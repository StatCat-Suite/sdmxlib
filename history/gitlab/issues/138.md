# Issue #138: perf: internal inbound-Ref index on InMemoryRegistry for O(1) applicable-* queries

| | |
| --- | --- |
| State | closed |
| Opened | 2026-06-09 |
| Closed | 2026-09-10 |

## Context

v0.34 added `reg.applicable_hierarchies(df, dim_id)` and
`reg.unique_hierarchy(df, dim_id)` on `InMemoryRegistry` and
`local.Registry` (issue #137). Today both methods scan
`get_all(HierarchyAssociation)` and filter by the HA's outgoing
`linked_object` / `context_object` URNs.

The IM never carries reverse-pointers from the targets (Dim, Dataflow,
Hierarchy, Codelist) back to the artefacts that reference them, so
enumeration is the only IM-honest path. **But the registry could keep an
internal reverse-URN index** that turns "find HAs whose `linked_object`
points at this Dim" into an O(1) dict lookup, without changing the
public API.

## Proposed shape

On `InMemoryRegistry`, alongside `_store` / `_refs` / `_by_type`:

```python
self._inbound: dict[str, set[str]] = {}  # target-urn → {referrer-urns}
```

`_walk_refs` already visits every outgoing `Ref` on `add()` — at each
visit, record the inverse edge:

```python
self._inbound.setdefault(str(ref.urn), set()).add(urn_str)
```

Then `_applicable_hierarchies` and friends become:

```python
referrer_urns = self._inbound.get(str(dim_urn), ())
has = [self._store[u] for u in referrer_urns if isinstance(self._store[u], HierarchyAssociation)]
```

For `local.Registry` (DuckDB), the equivalent is a column index on
`hierarchy_association.linked_object_urn` (one line of DDL in
`storage/schema.py`).

## Why it's worth doing as a primitive (not feature-specific)

The same `_inbound` map answers every "what points at me" question:

- HAs binding this Dim (today)
- ProvisionAgreements binding this Dataflow
- Constraints attached to this DSD
- Dataflows referencing this DSD
- MetadataSets targeting this artefact

So you're paying for a primitive that makes the whole forward-reference
graph navigable in both directions internally.

## Why deferred from v0.34

Public API doesn't change between scan-backed and index-backed.
Callers can't tell. So getting the API shape right first (#137) keeps
the optimisation purely additive — and current call sites (predicate
compile time, discovery, drift checks) aren't hot paths, so the win is
theoretical until we either:

1. Measure a slow path, or
2. Add a 3rd/4th `applicable_*` method where the index starts amortising
   across multiple callers.

## Tasks

- [ ] Add DuckDB index on `hierarchy_association.linked_object_urn` in `storage/schema.py`
- [ ] Document the invariant: `_inbound` must stay consistent with `_store` under `add` (and `remove` if/when supported)
