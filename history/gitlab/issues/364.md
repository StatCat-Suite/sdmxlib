# Issue #364: SDMX-JSON: vendor the 2.0 structure schema, validate what we emit, and support 2.1

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |

Split out of #358, whose decision I nearly got wrong for exactly the reason this
issue exists.

## The gap

`tests/schemas/sdmx_json/` vendors, per version:

| version | data | metadata | structure |
|---|---|---|---|
| 1.0 | ✅ | — | — |
| **2.0** | ✅ | — | ❌ |
| 2.1 | ✅ | ✅ | ✅ |

The only **structure** schema in the tree is 2.1's — and we do not emit 2.1. The
version we do emit, 2.0, has no structure schema vendored, so **nothing has ever
validated our SDMX-JSON structure output against the version it claims to be.**

The XML side has had this since the beginning: `tests/support/xsd.py` plus
`assert_valid_sdmx_ml` in the writer round-trip tests, and it is what caught
#345, #356 and #357. SDMX-JSON has no counterpart.

## What it cost, concretely

While triaging #358 I validated our output against the vendored schema and
reported the result as settled — that `isFinal` made our documents invalid. It
did not. That schema's own `description` reads *"SDMX-JSON 2.1.0 Schema for
SDMX 3.1 structure messages"*, and against the 2.0.0 schema the same document
has **zero** errors. The pile of other violations I found alongside it were
version mismatch too.

A vendored 2.0 schema and one `assert_valid_sdmx_json` would have answered the
question in one line instead.

## Work

1. **Vendor the SDMX-JSON 2.0.0 structure schema** —
   `sdmx-twg/sdmx-json` at tag `v2.0.0`,
   `structure-message/tools/schemas/2.0.0/sdmx-json-structure-schema.json`.
   Also the 2.0 metadata schema if it exists. Update `tests/schemas/VERSION`
   and the README's table.
2. **Add `tests/support/json_schema.py`**, mirroring `tests/support/xsd.py`:
   an `assert_valid_sdmx_json(payload, schema)` over `jsonschema` (already a
   dev dependency, 4.26). **Enable the format checker** — without it every
   string fails `meta.prepared`'s `oneOf: [date-time, date]`, because `format`
   is annotation-only by default and both branches reduce to `type: string`.
   That is a schema quirk affecting any producer, not a defect of ours, and it
   makes naive validation useless.
3. **Validate in the round-trip guard**, the way `_XSD_VERSION` already drives
   `assert_valid_sdmx_ml` there — so every case validates, not one hand-written
   example.
4. **Add SDMX-JSON 2.1 support**, and validate that output against the 2.1
   schema already vendored.

## What 2.1 will find

2.1 is not 2.0 with additions — it **closes the object model**
(`unevaluatedProperties: false`, 134 occurrences; 2.0 has none). Every key we
emit that the schema does not define becomes an error. Validating the #354
maximal message against 2.1 today reports violations across data structures,
hierarchies, metadata structures and metadata provision agreements. Most are
2.0-vs-2.1 differences rather than bugs — but they are the work of the 2.1
port, and they are invisible until a validator runs.

`isFinal` was the first of them, found by accident. Step 4 should not begin
before steps 1–3.

## Also worth deciding here

We emit **no `meta.schema` key** — `meta` carries only `id`, `prepared`,
`sender`. Nothing requires it, but it means a document does not say which
SDMX-JSON version it is, so a consumer cannot tell 2.0 output from 2.1 and a
validator cannot pick a schema automatically. Once both versions are emitted,
that stops being cosmetic.

Refs #358.

## Comments

### 2026-08-20

**Correction to this issue's premise, before the work lands.**

I wrote that "SDMX-JSON has no counterpart" to `tests/support/xsd.py`. It does:
`tests/support/json_schema.py` has existed all along, with
`compile_json_schema(kind, version)` across structure / metadata / data and
`assert_valid_sdmx_json`. It even already documents the format-checker point I
presented here as a discovery — its comment says enabling it is what makes the
`oneOf` over `{date, date-time}` discriminate.

I found that out by overwriting the file with my own version and breaking six
test modules that import it. Restored, and the change is now the two lines it
should always have been.

**What was actually missing**, narrower than written:

1. The 2.0 **structure** schema was not vendored — only its data schema — so
   `_KINDS_BY_VERSION` said 2.0 had `{"data"}` and a caller asking for a 2.0
   structure validator got a `ValueError`. The only structure schema in the
   tree was 2.1's, which is the mismatch that misled me on #358.
2. Nothing pointed any of it at the **maximal fixture**, which is the one input
   that reaches every field.

Both fixed. Steps 1–3 of the plan above are done; step 4 (2.1 support) is not,
and remains this issue's remaining scope.
