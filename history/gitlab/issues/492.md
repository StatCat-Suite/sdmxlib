## Comments

### 2026-10-18

**Correction to the mutability inventory above.** It says no current path needs mutable artefacts. That is wrong. `InMemoryRegistry` interning still replaces `Ref` fields on artefacts: `_intern_ref_field` does `setattr(obj, name, interned)`, and `_intern_container` does `value[:] = merged`. Its docstring gives the reason: "interning has to *replace*, not resolve in place, because its whole purpose is that one URN yields one `Ref` object."

**History.** The model started fully frozen (`@dataclass(frozen=True, slots=True)`, 2026-03-29). #30 then redesigned the registry as the in-memory SDMX graph. In that design, `add()` interns one shared `Ref` per URN onto every holder, so a target added later resolves every existing reference to it. e559224 (2026-04-01) dropped frozen from all artefacts and from `Ref` to allow this: "immutability by contract not force". So mutability was a deliberate choice, made for late resolution.

**What stage 2 actually requires.** Late resolution needs a mutable `Ref`. That is permanent, and `Ref._resolved` is legitimately mutable state. Mutable *artefacts* follow only from interning by field replacement. Freezing artefacts therefore means redesigning interning in one of two ways:

- **Intern at birth.** Readers build references through the registry's canonical table (#30 planned "readers accept optional Registry — interns Refs at parse time"). Only user-built artefacts passed to `add()` would still need the swap, or would have to be rebuilt (`evolve`) holding the canonical refs.
- **Index instead of intern.** Keep a URN → [every held `Ref`] index and resolve each `Ref` in place. Nothing is swapped, at the cost of one index entry per reference held rather than one shared object per URN.

`LocalRegistry`'s eager resolution (`_assign_ref`) can resolve the held `Ref` in place with `intern_resolution`, as its container branch already does.

Stage 1 (A becomes types, and every boundary runs validation) does not depend on any of this.

### 2026-10-18

## Stage 2 design options: immutable artefacts with late binding

Late resolution means an empty reference becomes resolved when its target arrives. That is the reason the model went mutable (e559224, #30). Functional programming and databases have well-understood ways to get the same behaviour while keeping things immutable.

### Prior art

1. **Write-once cells** (I-structures, Arvind, Nikhil and Pingali 1989; Haskell `IVar`/`MVar`; promises; LVars, Kuper and Newton 2013). A cell starts empty and is filled once, and everything else stays immutable. The only change is monotonic (empty, then full), so it is safe under concurrency. **Our `Ref` is an IVar**, with one exception: `withdraw_resolution` (#419) empties it again when a reader refuses the target.
2. **"Tying the knot"** (Haskell). A cyclic immutable graph is built from lazy thunks. In Python this would mean a `Ref` holding a closure, which is awkward to serialise and does not fit attrs.
3. **References as keys, resolved against a context** (Datomic's entity API, normalised Redux state, relational foreign keys). Objects hold only ids, and navigation is a lookup in a database *value*: `(d/entity db id)` follows references lazily through an immutable snapshot. Late binding comes for free.
4. **ORM identity map plus lazy loading** (SQLAlchemy `Session`, Hibernate proxies). An instance is bound to a session, and touching a relationship loads it through the session on first access. `RestRegistry` and `LocalRegistry` already work this way, except that ORM instances are mutable.

Our interning is hash-consing: one canonical object per value. That is an optimisation on top of family 1, not a binding strategy of its own.

### The options, measured

Measured on uv's CPython 3.14.8 build, 100,000 URNs:

| design | how a reference resolves | artefacts frozen? | memory | speed |
| --- | --- | --- | --- | --- |
| today: intern by swapping fields | `add()` walks every field, swaps in the canonical `Ref`, then fills it once | no | 38 B per URN table entry + 72 B per shared `Ref` | one write resolves every holder; `add()` pays the walk |
| intern at birth | readers take `Ref`s from the canonical table, so nothing is swapped | yes | same as today (the minimum) | no walk; one write per URN |
| index | the registry lists every held `Ref` per URN and fills each one | yes | +126 B per held `Ref` at 1 holder per URN, falling to +20 B at 10 per URN | 20 ns per holder on resolve; retains every `Ref` unless weakly referenced |
| **lookup on access** (families 3/4) | `ref()` looks its URN up in its registry on each access | yes, and `Ref` too | no table and no index | **34 ns per unwrap, against 29 ns today** |

Lookup on access costs about 5 ns more per unwrap than today's stored pointer, because `str(urn)` is cached and a dict lookup takes 14 ns. Nothing mutates, there is no interning table to grow and no index to retain, and late binding is automatic.

Its costs are semantic:

- A `Ref` must carry or find its registry, either as a pointer to the `Registry` protocol (which the model layer may know) or through a context variable.
- A `Ref` can outlive its registry, for example after the DuckDB file is closed, and then fails on access.
- What a `Ref` names can change over time, where Datomic resolves against a fixed snapshot. That is harmless for pinned versions, since a final `CL_X(1.0)` never changes. For `latest` it is the existing pointer semantics.

### As the backend for a full registry (OECD, StatCan CODR)

None of the options blocks this use, and two help it.

- **The serving path is already lookup-shaped.** `LocalRegistry` builds artefacts per request from the DuckDB store, with lazy codelists and a bounded FIFO resolve cache. The interning question concerns `InMemoryRegistry`, which is not the server path.
- **Immutability makes the shared cache safe by construction.** Concurrent requests share cached artefact objects. Today, a handler mutating one, or eager resolution writing `_assign_ref` into one, is a cross-request race guarded only by "immutability by contract".
- **The index design suits a server badly.** It retains every `Ref` it has ever served, so memory grows with traffic. The interning table grows by about 110 B per URN ever seen, roughly 110 MB per million: fine for one bundle, unbounded for a long-running registry fed by many sources. Lookup on access has neither problem.
- **Stage 1 is what a registry's write path needs anyway.** Structure submissions are refused at ingest, and externally built bundles are validated on read.
- **SDMX's rules map onto store operations, not object mutation.** A final version is immutable, and a draft is replaced in the store.
- **Garbage-collector cost.** A server materialising large hierarchies pays the collector's cost on every read. `gc.freeze()` on long-lived cached artefacts removes them from the collector's scans entirely, and is safe with threads where pausing collection is not. That is tracked separately.

### Recommendation

For stage 2, **lookup on access**. It is the only option in which neither artefacts nor `Ref`s mutate, it costs about 5 ns per access, and it matches the serving path `LocalRegistry` already has. Open questions:

- How does a `Ref` find its registry: a carried pointer or a context variable?
- What should accessing a `Ref` whose registry is closed raise?
- Should `withdraw_resolution` (#419) become "the registry does not hold it", which falls out of lookup naturally?
