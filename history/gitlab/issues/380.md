# Issue #380: 22% of a collect() is DuckDB turning two MAP columns into Python dicts, before any object exists

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-27 |
| Closed | 2026-08-27 |
| Milestone | %18 Read-path performance: what the synthetic benchmarks could not see |
| Labels | `design`, `perf`, `storage` |

Found decomposing `q.code…collect()` after #377 landed, asking whether the
remaining 3.3 s was *our* cost or the price of 580k Python objects. Most of it
is neither — it is spent before a single domain object is built.

## The measurement

`SELECT code_id, parent_id, depth, name, code_urn, description FROM sdmx.code
WHERE codelist_urn = ?` over `CL_GEOGRAPHY` (579,951 rows), best of 3:

| how the rows leave DuckDB | ms |
| --- | --- |
| `.fetchall()` — what every reader does | **916** |
| same SELECT **without** `name` / `description` | **169** |
| `.to_arrow_table()` | **71** |
| `.to_arrow_table().to_pylist()` | 2430 |
| `.to_arrow_table()`, per-column `.to_pylist()` | 2306 |

`name` and `description` are `MAP(VARCHAR, VARCHAR)`. Converting those two
columns into Python dicts is **~750 ms — 22% of the whole collect** — and it
happens inside `fetchall()`, before `map_to_istring` is called, before an
`InternationalString` exists, before `Code.__init__` runs. None of the object
layer can reach it.

For context, the rest of that 3.47 s: 259 ms annotation SQL, 850 ms annotation
grouping in Python (#381), 642 ms building the 579,951 `Code` objects, ~600 ms
assembly. **SQL execution proper is ~430 ms — about 12%.** The query plan is
not the problem and this issue is not about it.

## The trap, stated up front

The obvious read of the table is "switch the readers to Arrow, 916 → 71 ms."
That is wrong, and the two `to_pylist` rows are in the table to stop it being
tried: **Arrow is 13x faster only while the data stays columnar.** The moment
you need a Python value per row it is 2.5x *slower* than `fetchall`, because
`fetchall` builds one tuple per row while `to_pylist` builds a dict per row and
re-boxes every map.

So Arrow is the right answer for `.frame()` (161 ms for the same 579,951 rows
— it is already what `.frame()` does) and the wrong answer for `.collect()`,
whose whole job is per-row Python. Any fix here has to be about *not paying for
the maps*, not about the transport.

## Directions, none chosen

1. **Don't select them unless something reads them.** A `Code` whose
   `name`/`description` are lazy — backed by the codelist urn + code id, read
   on first access. Removes 750 ms from every collect that never looks at a
   label, which the #348 consumer survey suggests is most of them ("we want
   ids; we get fully-built nodes"). Costs a second query for the ones that do,
   and puts a connection reference inside a domain object, which the
   `model/` purity rule in CLAUDE.md would have something to say about.
2. **A cheaper column representation.** `MAP(VARCHAR, VARCHAR)` → a JSON
   `VARCHAR`, or two columns for the common single-language case. Moves the
   cost from DuckDB's map decoder to a parse we control, which may or may not
   be cheaper — **measure before believing it**, since a JSON parse per row is
   not obviously better than a map decode per row.
3. **Accept it and route scale to `.frame()`.** Document that `.collect()` is
   for object graphs and `.frame()` for volume, which is true today and costs
   nothing. This is the honest baseline the other two have to beat.

(1) is the biggest win and the biggest design question. (3) is free and should
probably happen regardless — see #382.

## Acceptance

- A benchmark in `tests/bench/test_bundle_reads.py` that isolates the fetch
  from the build, so this 750 ms is visible rather than buried in a collect.
- Whatever is chosen, the Arrow asymmetry above is written down where the next
  person looks — a comment at the fetch site, not only in this issue.
- If (1): a test that a `collect()` which never reads a label issues no
  label query, asserted by **count** of SQL round-trips per CLAUDE.md.
