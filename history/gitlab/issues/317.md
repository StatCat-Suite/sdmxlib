# Issue #317: Writer: 43 SQL statements per artefact — a type-blind cascade and a per-value pandas probe

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-16 |
| Closed | 2026-08-16 |

Measured while deciding materialise-vs-query-through for %17 (see
`docs/design/query-pushdown.md` §12). Storing an artefact costs **8.4 ms**,
and almost none of it is necessary.

Payload: ECB's `/dataflow/ECB?references=datastructure` — 183 artefacts,
102 Dataflows and 81 DataStructures, 2.2 MB.

```
183 artefacts, 7936 SQL calls (43 per artefact), 1.53 s

  DELETE    6588 calls   614 ms   63%
  INSERT    1272 calls   271 ms   28%
  other       76 calls     6 ms   <1%
```

## 1. The cascade is type-blind (63 % of the time)

`_delete_artefact_cascade` runs ~36 `DELETE`s across every table in the
schema for **every** artefact, whatever its type. Writing a Dataflow deletes
from `code`, `concept`, `category`, `hierarchy_node`, `metadata_attribute`,
`value_map` and thirty others it can never have rows in.

Fix: run only the statements the artefact's type can own. Ordering must be
preserved — contacts are deleted through their owner, and getting that
backwards is #309, which silently duplicated rows on every re-add.

## 2. `executemany` probes for pandas per *value*

DuckDB's `executemany` checks each parameter value for pandas nulls with a
lazy `import pandas`. pandas is not installed (and should not be), Python
does not cache failed imports, so **every probe re-walks `sys.path`**:

```
executemany  20000 rows:  4.90 s   pandas lookups = 160,000
arrow table  20000 rows:  0.03 s   pandas lookups = 1
```

160x. `_execute_bulk_insert` already does the Arrow ingestion; one site
(`_put_artefact_localized_text`) still uses `executemany`, and it accounts
for 8 lookups per artefact — 21,573 across this payload.

## Why it matters beyond the writer

§12 concluded "materialise per agency, query through only for a single
lookup", with a break-even of ~3 queries. That threshold is a property of
this writer, not of SDMX. At ~1 ms per artefact it falls below one round
trip and the decision stops existing.

## Gates

- Re-add test per artefact kind: write, re-write, assert no duplicated or
  stale rows. #309 is the failure this must catch.
- The per-kind table set is **derived in the test**, not enumerated twice:
  instrument a write, collect the tables it inserts into, assert the
  cascade covers them. A writer that gains a table then fails here rather
  than leaving stale rows in production.
- Re-measure and record the new ms/artefact in §12.
