**Phase 3.** Empty the `KNOWN_INVALID` table from #227, using the extraction from #228.

Eleven artefact kinds can be built in a state with no valid serialisation, and 24 (artefact, format) pairs currently emit an invalid document rather than saying so. Each one is the same shape as `Metadataflow.targets` and `ProvisionAgreement`, both fixed in !232: the model makes a field optional so partial artefacts stay storable, and nothing checks at the write boundary.

## Work

For each entry, decide which of three it is — the decision matters more than the code:

1. **A write-boundary rule.** The artefact is legitimately incomplete and the fix is a `check_serialisable` rule naming the missing piece. This is the default and covers most of the 24.
2. **A writer bug.** The information is present on the model and the writer fails to emit it. Fix the writer. (`ConceptSchemeMap`'s `itemMaps` and the 2.1 `StructureMap` element name were both this.)
3. **A modelling gap.** The schema needs information the model does not carry, so no writer can be correct. Refuse, and file the modelling question separately — as was done for 2.1 component maps needing `class`/`package`/`containerID` (#226).

Do not guess between them. Confirm against the vendored XSD by hand before attributing a failure to one side.

## Known specifics

- `data_structures` → 2.1 raises a non-`ValidationError` exception. A third outcome the invariant forbids; diagnose before batching it with the rest.
- `data_provider_schemes` and `metadata_structures` fail **only** in SDMX-JSON, which suggests a `minItems` on an array rather than a missing XML child. Different fix shape.
- `attachment_constraints` → 2.1 is the only remaining format that can carry it at all (3.0 removed the artefact), so a 2.1 gap there has no fallback target.

## Done when

`KNOWN_INVALID` is empty and the #227 gate passes with no exemptions, or every surviving entry has been converted into a documented refusal.
