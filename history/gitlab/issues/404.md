# Issue #404: validate_references expands item URNs for ConceptScheme only — every Code, Category and Dimension ref reads as broken

| | |
| --- | --- |
| State | closed |
| Opened | 2026-09-25 |
| Closed | 2026-09-28 |
| Labels | `api`, `bug`, `model` |

`validate_references` builds its known-URN set from `_collect_known_urns`
(`model/validation.py:707`), which expands **item**-level URNs for
`ConceptScheme` and nothing else. Every other item reference in the model —
`Code`, `Category`, `Dimension` — therefore fails to resolve against a message
that plainly contains its target, and the check reports it as broken.

The message is not malformed: it serialises to SDMX-ML 3.0 and round-trips.

## Repro

```python
import sdmxlib as sl
from sdmxlib.model.urn import SdmxUrn

A, V = "AGENCY", "1.0.0"

cl = sl.Codelist(
    id="CL_AREA", maintainer=A, version=V, name={"en": "Area"},
    codes=[sl.Code(id="CA", name={"en": "Canada"}), sl.Code(id="ON", name={"en": "Ontario"})],
)

def code_urn(code_id: str):
    return SdmxUrn.make(sl.Code, package="codelist", artefact_class="Code",
                        agency=A, id=cl.id, version=V, item_id=code_id)

hier = sl.Hierarchy(
    id="HR_AREA", maintainer=A, version=V, name={"en": "Area hierarchy"},
    tree=[sl.HierarchicalCode(id="CA", code=code_urn("CA"),
                              children=[sl.HierarchicalCode(id="ON", code=code_urn("ON"))])],
)

msg = sl.StructureMessage(codelists=[cl], hierarchies=[hier])
assert sl.to_xml(msg, version="3.0")          # serialises fine
sl.validate_references(msg)                   # raises
```

```
ReferenceValidationError: 2 broken references:
  Hierarchy:HR_AREA.tree[CA].code -> urn:sdmx:org.sdmx.infomodel.codelist.Code=AGENCY:CL_AREA(1.0.0).CA
  Hierarchy:HR_AREA.tree[CA].children[ON].code -> urn:sdmx:org.sdmx.infomodel.codelist.Code=AGENCY:CL_AREA(1.0.0).ON
```

Both codes are in `cl.codes`, in the same message.

## Scope

Verified failing, with the target artefact present in the message:

| Reference | Target | Notes |
| --- | --- | --- |
| `Categorisation.target` | `Category` | **2.1-era and ubiquitous** — every categorised dataflow has one |
| `HierarchicalCode.code` | `Code` | the documented shape of a 3.0 `Hierarchy` node |
| `HierarchyAssociation.linked_object` | `Dimension` | binding a hierarchy to the dimension it organises |

`Categorisation` is the one that makes this more than a 3.0-hierarchy edge
case: it is how a category scheme is attached to a flow, it predates 3.0, and
it is item-referencing by definition.

The 3.0 pair is not avoidable either — a `HierarchicalCode` *must* point at a
`Code`, and a `HierarchyAssociation` *must* point at the component it
organises. Any project that models 3.0 hierarchies cannot use
`validate_references` at all.

## Measured on a real message

An SDMX 3.0 model of an IPPI price extract — 9 codelists, 3 `Hierarchy`
artefacts with formal levels, 8 `HierarchyAssociation`s, 5 DSDs, 5 dataflows:

```
1388 issues: 1380 Code, 8 Dimension
Code refs whose target is NOT in a message codelist: 0
```

Every one is a false positive. There is no true positive mixed in to find,
which is the part that makes the check unusable rather than merely noisy — a
caller cannot filter, because the signal is empty.

## Cause

`model/validation.py:707-744`:

```python
def _collect_known_urns(msg: StructureMessage) -> set[str]:
    known: set[str] = set()
    for artefact in msg.all_artefacts():
        if isinstance(artefact, MaintainableArtefact):
            ...
            known.add(str(urn))                      # scheme-level URN

            if isinstance(artefact, ConceptScheme):  # <-- items, for exactly one class
                for concept in artefact.concepts:
                    ...
```

The docstring states the limit ("Includes both scheme-level URNs and
item-level URNs for concept schemes") but reads as a description of what was
needed at the time rather than a deliberate exclusion. `_collect_refs` on the
other side of the check already walks into items correctly — #383 and #392
both hardened that walk — so the two halves now disagree about what an item
is.

## Suggested fix

Table-drive the item expansion rather than special-casing one class, so a new
item-bearing scheme is a row rather than an `isinstance` branch:

```python
_ITEM_SOURCES = [
    (Codelist,            "codelist",       "Code",          "codes"),
    (ConceptScheme,       "conceptscheme",  "Concept",       "concepts"),
    (CategoryScheme,      "categoryscheme", "Category",      "categories"),
    (AgencyScheme,        "base",           "Agency",        "agencies"),
    (DataProviderScheme,  "base",           "DataProvider",  "providers"),
    (DataStructure,       "datastructure",  "Dimension",     "dimensions"),
    (DataStructure,       "datastructure",  "Measure",       "measures"),
    (DataStructure,       "datastructure",  "DataAttribute", "attributes"),
    (MetadataStructure,   "metadatastructure", "MetadataAttribute", "attributes"),
]
```

Two details worth settling in the fix:

- **Nested items.** `Category.categories` and `MetadataAttribute.children`
  both recurse, so a flat `for item in getattr(scheme, accessor)` misses every
  descendant. `Code` is flat (`parent_id`), so codelists are unaffected — the
  accessor column above cannot be applied uniformly without a recursive
  variant for those two.
- **Cost.** This adds an item-URN render per item, and `CL_PRODUCT` in the
  message above has 9,000 codes. Given #383's finding that the ref walk was
  already visiting hierarchy nodes twice, it may be worth building the known
  set lazily, or keying on `(scheme_urn, item_id)` tuples rather than rendering
  a URN string per item.

## Workaround

Reimplement the check. ~40 lines: `_collect_known_urns` with the table above,
then reuse `_collect_refs` unchanged. Reaching into a private function to do
it, which is the other reason to fix this upstream.
