# Issue #445: SDMX-JSON reader silently ignores keys it does not expect

## Summary

#436 made the SDMX-ML readers closed-world: an element the schema allows nowhere refuses its artefact. The SDMX-JSON reader is not covered. msgspec's typed decode drops any key a DTO does not declare, so a misspelled or misplaced property disappears silently, the same failure mode #436 removed for XML.

## Why it was left out

msgspec decodes a whole document at once. `forbid_unknown_fields=True` on the DTOs would fail the *document*, not the artefact, which undoes #435's per-artefact refusal.

## Options

- Decode each artefact separately: the envelope first with artefacts as `msgspec.Raw`, then each artefact with `forbid_unknown_fields`. The refusal then goes through `build_each` like the XML loops.
- Or compare each artefact's raw keys against the JSON schema's `properties`, derived like #436's table (the vendored 2.0 and 2.1 structure schemas close every object with `unevaluatedProperties: false` / `additionalProperties`).

Either way, measure the cost (#436's XML check is 9–14% of parse time) and run it over the cached registry JSON before deciding.

Follow-up to #436.

## Comments

### 2026-10-15

Closing: since #422 the SDMX-JSON reader no longer ignores an undeclared key silently. `formats/sdmx_json/_losses.undeclared` walks each artefact's raw JSON beside its struct and reports every key no DTO declares as a `ReadGap` in `msg.lost`, named `<Struct>.<key>`; a section no struct reads is refused entry by entry. Refusing the artefact instead (the #436 policy for XML elements) was considered on 2026-10-15 and not taken: reporting is the decided behaviour for JSON.
