# Issue #353: the oracle's strip_accents model disagrees with DuckDB on 527 characters — a property fails at 20x on main

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-20 |
| Closed | 2026-08-20 |
| Labels | `bug`, `dsl`, `tests` |

`just test-properties` fails on `main` (59a0de3). Verified pre-existing — it
reproduces with unrelated work stashed. It does **not** fail at default width;
you need 20x to draw a rare enough character, which is what that recipe is for.

```
FAILED tests/unit/test_properties_query_code.py::test_name_predicates_agree_with_the_oracle
  Draw 2 (target)  : 'ા'          U+0ABE GUJARATI VOWEL SIGN AA
  Draw 4 (op)      : 'contains'
  assert [] == ['0']
```

## Root cause

`tests/support/oracle._label_norm` claims to restate DuckDB's
`strip_accents(x)` as *"decompose-and-drop-combining-marks"*:

```python
decomposed = unicodedata.normalize("NFD", value)
stripped = "".join(ch for ch in decomposed if not unicodedata.combining(ch))
```

`unicodedata.combining()` returns the **canonical combining class**, which is
`0` for a large family of marks that are nonetheless marks — every spacing
combining mark (`Mc`), and many non-spacing ones. DuckDB drops them. Python
keeps them.

```
U+0ABE GUJARATI VOWEL SIGN AA   combining() == 0   strip_accents -> ''
```

## Size

Scanned every non-control, non-symbol character in U+0020..U+2FFF (8,025):

| Python model | disagreements with `strip_accents` |
| --- | --- |
| `not unicodedata.combining(ch)` — today | **527** |
| `unicodedata.category(ch)[0] != "M"` | **0** |

A sample of the 527: `U+034F COMBINING GRAPHEME JOINER`, `U+0488 COMBINING
CYRILLIC HUNDRED THOUSANDS SIGN`, the whole Thaana vowel range `U+07A6..U+07B0`,
Devanagari and Gujarati vowel signs.

So the fix is one predicate:

```python
stripped = "".join(ch for ch in decomposed if unicodedata.category(ch)[0] != "M")
```

which agrees with DuckDB on all 8,025.

## Why this is worth more than the one-line diff

This is an **oracle bug**, the second of the three kinds CLAUDE.md names for
triaging a property failure, and it is the kind that quietly costs the most:
the oracle is the specification these properties check the compiler against, so
where it is wrong it is either raising false alarms (here) or — more dangerous —
agreeing with a compiler bug for the wrong reason.

It also sits exactly where CLAUDE.md says differential testing is weakest.
Rule 1 keeps the oracles from sharing code, but both this oracle *and*
`hierarchy_oracle` restate the same fold, so if the other one has the same
line, the two agree with each other and disagree with the database — which is
the shape rule 1 cannot catch. **Check `hierarchy_oracle` for the same
predicate while fixing this.**

Worth noting the docstring is honest about intent and still wrong; nothing
short of running both against real characters would have found it, and only at
20x width. That is an argument for running `just test-properties` on a schedule
rather than on touch, since this has been latent long enough to predate the
work that found it.

## Scope

- Fix `_label_norm`; check `tests/support/hierarchy_oracle.py` for the same.
- Consider a direct guard: a test asserting the oracle's fold equals
  `strip_accents` over a fixed character sweep, so the model is pinned to the
  function rather than to a description of it. That is cheap and would have
  caught this without needing Hypothesis to find the character.
