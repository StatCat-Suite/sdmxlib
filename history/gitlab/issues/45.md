Follow-up from #43 / #44.

## Context

As of v0.14.0 the sdmxlib reference-metadata pipeline (model + storage +
SDMX-ML 3.0 GenericMetadata + SDMX-JSON metadata schema + parse/write
auto-discrimination) is fully implemented and unit-tested. We can also
parse real-world MSDs (the Global Registry serves \`IAEG-SDGs:SDG_MSD\`)
and an empty MetadataMessage envelope (IMF).

What's missing is **end-to-end validation against a live provider that
actually serves a populated MetadataSet payload**. As of 2026-04-28, no
public SDMX 3.0 endpoint we know of returns a non-empty
\`<mes:GenericMetadata>\` document:

- SDMX Global Registry (\`registry.sdmx.org/sdmx/v2/\`): MSD only, no flows
- BIS (\`stats.bis.org/api/v2/\`): 4 flows defined, all return "100 No Results"
- IMF (\`api.imf.org/external/sdmx/3.0/\`): structure exposed, empty payload

## What this issue tracks

When any of these (or a new) provider lights up an actual reference-metadata
endpoint with populated data:

1. **Add a live integration test** that fetches a real MetadataSet and
   verifies sdmxlib parses it without errors.
2. **Validate the URL convention** for the deferred
   \`reg.metadata(metadataflow).attached_to(urn).fetch()\` helper —
   specifically whether \`?attachedTo=URN\` is the right query param,
   whether the path is \`/metadata/metadataflow/...\` or
   \`/metadata/metadataset/...\`, and whether providers differ.
3. **Build the helper** with confidence based on the validated URL
   pattern, plus a Provider-specific override mechanism if conventions
   diverge across BIS / IMF / etc.
4. **Validate observation-key target URN encoding** — SDMX 3.0 allows
   metadata to be attached to observation keys; the URN syntax for that
   needs spec confirmation against a real example.

## Re-probe schedule

Worth re-probing BIS and IMF every few months. FMR 11+ supports the
reference-metadata REST API; once providers load reports, the
infrastructure is in place to serve them.
