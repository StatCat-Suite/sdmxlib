## The gap

`tests/support/oracle.py` exposes nine predicate constructors:

`id_eq`, `id_contains`, `id_starts_with`, `parent_is_null`, `parent_eq`, `depth_eq`, `has_ancestor`, `has_no_narrower`, `name_contains`.

`code_query`'s public DSL is roughly two and a half times that:

| Operation | Modelled by the oracle |
| --- | --- |
| `id ==` / `!=` / `contains` / `starts_with` | partly — `!=` and `ends_with` are not |
| `id.ends_with(...)` | no |
| `id.is_null()` / `is_not_null()` | no |
| `depth ==` (and other comparisons) | equality only |
| `parent_id` predicates | `is_null` / `eq` only |
| `name[lang].contains(...)` | yes |
| `name[lang]` starts/ends/null forms | no |
| `annotations[type]` | **no** |
| `annotations[type,lang]` | **no** |
| `level(level_id)` | **no** |
| `hierarchy(h)` | **no** |
| `descendants_of(..., depth=n)` | untested at depth |
| `broader_transitive(depth).any(pred)` | **no** |
| `narrower_transitive(depth).any(pred)` | **no** |
| `sort_by(key, ascending=)` | **no** |
| `limit(n)` | **no** |
| `with_annotations(*types)` | **no** |
| `get(code_id)` | **no** |

The unmodelled set is not the easy remainder. It contains **every operation that compiles to a recursive CTE** (`broader_transitive` / `narrower_transitive` with a depth bound, `descendants_of(depth=…)`) plus the two operations that compile to a **join** (`annotations`, `level`). That is the hardest SQL in the library, tested today only by hand-written examples.

`code_query.py` sits at 93% with 35 uncovered statements, and the missing ranges cluster in exactly this region — 689-706, 1022-1029, 1073-1080, 1244-1248.

## Scope

- Extend the oracle to every operation in the table above. Keep it a specification: naive traversal, no shared code with `code_query`, readable end to end.
- `sort_by` and `limit` need **order-sensitive** assertions, not set equality. The existing differential properties compare as ordered subsets where the DSL promises order; extend that promise explicitly — including what the DSL guarantees for ties, which may turn out to be underspecified.
- `with_annotations` changes the *shape* of returned `Code` objects rather than the row set. Assert both: same ids as the unprojected query, and annotations present iff requested.
- `get(code_id)` must agree with `filter(code.id == code_id).collect()` for every generated id, and return `None` for ids not in the codelist.
- A composite strategy that draws a **random well-typed DSL expression** against a generated codelist, rather than one property per operation. Per-operation properties are the floor; an expression generator is what finds compositional bugs (`filter(a).sort_by(x).limit(n)` interactions).

## Risks

- **Well-typed generation is the real work** (#217 flagged this and it is still true). A filter on a nonexistent annotation type is a different test from a filter on a present one — generate the codelist and the expression together so both cases are reachable and distinguishable.
- **Ties under `sort_by`.** If the DSL does not define tie order, a differential property will flap. Discover that, then decide whether to specify the order or weaken the assertion — and record which.
- **Depth-bounded transitive closure is easy to get right in SQL and wrong in the oracle.** Write the oracle's bounded traversal against the *definition* (n hops), not against what the SQL appears to do.

## Test gates

- Every operation in the table has differential coverage.
- Coverage of `code_query.py` reported before and after; the recursive-CTE and join line ranges named above should close.
- Order-sensitive operations asserted on order.
- Any underspecified corner of the DSL filed as its own issue rather than encoded into the oracle.
