# Issue #206: idea: can the URN-keyed stores recover T without a suppression? (7 sites)

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-05 |
| Closed | 2026-10-21 |
| Labels | `design`, `typing` |

**An idea, not a decision.** Filing so it is written down rather than re-derived; no commitment implied, and "leave it as is" is a perfectly good outcome.

Noticed while doing #195. The remaining `type: ignore` sites fell into four groups, three of which are structural — the code deliberately does something the type system cannot express, and no rewrite removes them:

* operator overloading for the query DSL (`__eq__` returning a predicate) — 7 sites
* attrs `@frozen` assignment inside `__attrs_post_init__` — 3 sites
* reading attrs' runtime-generated `__attrs_attrs__` — 1 site

The fourth group is different, and is what this issue is about.

## The sites

```
api/session.py:91,94,101,104        Session.get[T] / get_resolved[T]
model/in_memory_registry.py:106,110 InMemoryRegistry.get[T] / get_all[T]
local/registry.py:610               Registry.get[T]
```

All are the same shape — a URN-keyed store whose value type is wider than the `T` the caller asked for:

```python
self._map: dict[str, object]                  # Session
self._store: dict[str, SupportsUrn]           # InMemoryRegistry
self._by_type: dict[type, list[SupportsUrn]]

def get[T](self, urn: SdmxUrn[T]) -> T | None:
    return self._store.get(str(urn))          # object/SupportsUrn is not T
```

The key is a URN *string*, so at runtime nothing proves the stored value matches the caller's `T`. `T` exists only in `SdmxUrn`'s phantom parameter.

## Why these are not obviously necessary

CLAUDE.md explicitly sanctions this shape — *"localize the one unsafe `object -> T` step to the accessor"* — and it is what buys typed reads everywhere else in the library. So the status quo is defensible and these are not defects.

But unlike the other three groups, they are **consequences of a storage design**, not of a language limit. A store that carried the artefact class alongside the URN — or was keyed per artefact type, as `_by_type` already partly is — could plausibly narrow without an escape hatch.

## Things to weigh, if anyone picks this up

* `InMemoryRegistry` already keeps `_by_type: dict[type, list[SupportsUrn]]`, so the class *is* available at write time. Whether it can be threaded to the read path without duplicating state is the open question.
* `get_all[T](artefact_type: type[T])` receives the class as an argument and still cannot narrow the stored list — that one looks the most tractable.
* `Session`'s stores are `dict[str, object]`, deliberately the widest of the three. Narrowing them touches the identity-map design, which has concurrency and interning constraints (see `docs/concurrency.md`).
* `local/registry.py:610` is only superficially similar — its pyrefly code is `no-any-return-explicit`, and the value arrives from `readers.get_artefact`, whose `Any` return is documented as justified (#204). It probably cannot move until that does, if ever.
* Any change here is API-shaped and would need to keep `Registry.get` / `Session.get` ergonomic for callers. Six suppressions is a small prize for a large refactor — the honest cost/benefit may well say no.

## Not in scope

This is not a suppression-count issue. #195 already made these attributable — each names the specific rule of the specific checker that reports it. The question is only whether the underlying design could make them unnecessary, and whether that is worth doing.
