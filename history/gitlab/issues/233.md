# Issue #233: A 'latest'-version Ref serialises to a URN SDMX-ML 3.0 rejects

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-06 |
| Closed | 2026-08-11 |
| Milestone | %11 Wire conformance: no artefact serialises to an invalid document |
| Labels | `bug` |

`SdmxUrn.version` defaults to the sentinel `"latest"`, which stringifies with **no `(version)` part at all** — and SDMX-ML 3.0 requires one on every URN reference. So any outgoing `Ref` built without an explicit version serialises to a document the schema rejects.

## Reproduction

```python
urn = DataStructure.urn(agency="AG", id="DSD")          # version defaults to "latest"
df  = Dataflow(id="DF", maintainer="AG", version="1.0",
               name={"en": "n"}, structure=Ref[DataStructure].unresolved(urn))
serialize(StructureMessage(dataflows=[df]), version="3.0")   # emits invalid XML, no error
```

| | `version="1.0"` | `version="latest"` |
|---|---|---|
| URN string | `…DataStructure=AG:DSD(1.0)` | `…DataStructure=AG:DSD` |
| SDMX-ML 2.1 | valid | valid |
| SDMX-ML 3.0 | valid | **invalid** |

2.1 tolerates it because its references are `<Ref>` containers with separate `id`/`agencyID`/`version` attributes, and version is optional there. 3.0 switched to URN strings, whose pattern facets require the parenthesised version — `MaintainableUrnType` is `.+\)`, and the metadata `Target` type is `.+\)(\.\*(\.\*)*)?`.

## Why it has never been caught

Every strategy in `tests/support/strategies.py` passes an explicit version when building a reference, so the `"latest"` path is generated nowhere. No fixture exercises it either. Found while writing the MetadataSet strategy for #223 — the first target URN drawn used the default, and both the XSD and the JSON schema rejected it.

## Scope

This is **not** metadata-specific. It applies to every outgoing reference on every artefact, which is why it was not fixed inside the #223 MR: the blast radius is every `Ref` in the codebase, and a write-boundary rule refusing `"latest"` on 3.0/3.1/json targets would need its effect on existing callers measured first.

## Options

1. **Refuse at the write boundary** — a rule in `check_serialisable` walking outgoing refs, rejecting `"latest"` for 3.0/3.1/json. Consistent with how every other unrepresentable state is handled. Needs the existing-caller impact measured.
2. **Resolve at write time** — substitute the referenced artefact's actual version when the message carries it. Silently changes the reference, which is worse than refusing.
3. **Reconsider the sentinel.** `"latest"` is meaningful in a *query* (`GET …/latest`) and meaningless in a *serialised reference*. The two uses may want different types rather than one string that is valid in one context and unrepresentable in the other.

Option 1 is the smallest correct step; option 3 is the question worth asking afterwards.

## Suggested guard

Add `"latest"` to the version strategy so the generative round-trip properties cover it, once the behaviour is decided. Until then it would fail every 3.0 property, which is the honest signal.
