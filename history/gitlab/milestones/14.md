# Milestone %14: Query DSLs: say what the docs already claim

| | |
| --- | --- |
| State | closed |
| Opened | 2026-08-09 |
| Due | — |

The filter DSLs can express less than their documentation implies, and where they agree on a concept they often disagree on what it means. This milestone closes the expressiveness gaps and settles the semantics; %13 measures the result.

Every item here was found by pointing a generative test at a module that already reported high line coverage. That is worth stating because none of it was visible from the code: `rest.py` is at 100%, `code_query.py` was at 93%, and the gaps below sat inside both.

## What is actually missing

| Gap | Evidence |
| --- | --- |
| No set membership | `grep` for `is_in` / `one_of` / `in_` across both DSLs returns nothing. "Codes A, B or C" is inexpressible. |
| No disjunction | No `Or` node, no `__or__`. Combined with the above, there is no route to it at all. |
| Partial negation | A `negate: bool` flag on 2 of 10 predicate kinds. `_StringMatch` has none, so `~id.contains("X")` cannot be written. |
| No ordered comparison | `_DepthRef` has `__eq__` / `__ne__` only. `node.depth <= 2` — from `hierarchy_query`'s own module docstring — raises `TypeError`. |
| No pagination | `limit` but no `offset`. `local/sql.py` names "Range pagination" as a reason to leave the DSL. |
| 18 unreachable states | `NotImplementedError` on the `to_sql()` path for field × operation pairs the types permit. |

## Semantics that two DSLs answer differently

- **Label matching** (#255): `code_query` folds accents and punctuation; `hierarchy_query` emits a plain `ILIKE`. `name["en"].contains("Montreal")` finds *Montréal* on a codelist and nothing on a hierarchy holding the same label.
- **The empty OR-set** (#256): `parse_components` treats `[]` as "no constraint" (match everything); constructing `ComponentFilter` directly emits `IN ()`, which DuckDB rejects. The natural reading — match nothing — is neither.
- **Composition** (%13 #260): `limit()` is last-wins while `sort_by()` accumulates, on the same class, neither documented.

## Order

**1 — unblock the compiler.** #254 is the prerequisite for disjunction, not merely a bug fix: annotation predicates compile to `JOIN sdmx.annotation`, and a JOIN filters before the `WHERE`, so a row lacking the annotation cannot satisfy *either* branch of an `OR`. Rewriting them as correlated `EXISTS` fixes the row duplication and makes boolean composition possible in the same change.

- #254 — annotation predicates: JOIN → `EXISTS`

**2 — settle the semantics.** These are decisions, not patches, and they come before the tests in %13 that would otherwise encode today's inconsistency by accident.

- #255 — label-matching asymmetry between the two DSLs
- #256 — the empty OR-set, in both directions

**3 — fill in the operators.** Independent of each other; #261 is the highest value per line of code.

- #261 `dsl-11` — `is_in`, including the `SqlRelation` form
- #263 `dsl-13` — ordered comparison on `depth`, and a docstring that stops lying
- #262 `dsl-12` — real `And` / `Or` / `Not` (needs #254)

**4 — tidy the surface.**

- #259 `dsl-9` — make `to_sql()` total; the 18 raises become unrepresentable or implemented
- #264 `dsl-14` — decide pagination: `offset`, keyset, or document the escape hatch

## Constraints

- **`sl.CompileContext` and `Predicate.to_sql(ctx)` are public**, and pinaxlib composes its own predicates against them. New predicate *kinds* are additive; changing how existing ones compile is not. #254 is the one item here that touches that contract, which is why it was filed separately rather than folded into the test work that found it.
- **Both DSLs move together or the divergence gets worse.** Every gap in the table above exists in both, and #255 exists *because* one of them was extended and the other was not.
- **`test_every_predicate_kind_is_covered`** in both property files enumerates predicate kinds off the module and will fail on every new one until it has a property. That is the guard working; do not weaken it to land a feature.

## Why not simply "add operators"

Two of these are decisions with no obviously right answer — NULL semantics under `~` (#262: `p | ~p` does **not** return everything, measured) and what an empty filter set means (#256). Shipping operators without settling those produces a DSL that is more expressive and less predictable, which is worse than the current state.
