Follow-up to the #163 custom-SQL seam, applying the four consensus findings from the post-merge quality audit (two independent reviewers agreed). All changes bring the just-shipped code in line with the repo's own written standards.

## Findings applied

1. **Remove `QueryPlan.columns` (+ the `plan(columns=)` param).** It was never read anywhere — the projection is the consumer's job, or `_build_query`'s own `cols_sql`; echoing it back diluted the FROM-side abstraction and even contradicted the module's own docstring. Also collapses the duplicated two-path `QueryPlan(...)` construction. The full statement-descriptor alternative is tracked as **#164 (Design-B)**, deliberately not built now.
2. **`columns()` / `shared_columns()` return `tuple[str, ...]`** instead of handing out the mutable cached `list` — a caller could otherwise corrupt the shared cache (a regression vs the old fresh-list `_describe_columns`). Matches the repo's tuple convention (`join_keys`, `DataflowBinding.partition_layout`).
3. **Single-flight the DESCRIBE cache** (build lock + double-check) and guard the store's lazy `inspect()` init the same way. The read path is concurrent (per-thread cursors, #75/#80) and the inspector is shared, so the plain dict violated `docs/design/caching.md`'s *"concurrent reads are safe and do not duplicate work."* Mirrors `LazyCodelist.code_map`.
4. **Test hygiene**: type `_CountingConn._real` as the real connection to drop an avoidable `# type: ignore[attr-defined]`; add a **single-flight concurrency guard** (8 threads race a cold cache → exactly 1 DESCRIBE).

Docs (`llms.txt` / `llms-dsl.txt`) updated to drop `plan.columns` and reflect the tuple return types.
