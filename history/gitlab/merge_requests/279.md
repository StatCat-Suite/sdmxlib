## The law, and the rework

The composition law turned on a question nobody had asked: pipeline or declarative? Measured — declarative. `q.limit(3).filter(p)` and `q.filter(p).limit(3)` are the same query here; polars' equivalents differ.

The first cut took `offset` as `max` over a `(start, length)` window — dual to `narrow_limit`, order-independent, idempotent. **A test asserting the refinement invariant falsified it:**

```
base = q.offset(5).limit(10)   ->  C05..C14
base.offset(8)                 ->  C08..C17   <- three rows base excluded
```

Holding the length fixed slides the window rather than shrinking it — a caller undoing a helper's cap, exactly what `narrow_limit` exists to prevent. Narrowing, idempotence and commutativity are not simultaneously available; SQL's `LIMIT n OFFSET m` buys commutativity by making `n` a length from `m`, which is what slides.

Now `[start, end)` with the ceiling held fixed. Narrowing and idempotent; `limit`/`offset` no longer commute, which is the only order-sensitive pair in the DSL and is pinned by a test explaining the trade. Django reaches the same place from the other side — relative slices, then it forbids filtering or reordering a sliced query.

## Two pre-existing defects found

Both latent under `limit` alone, both about to be inherited:

- **`to_sql()` dropped `ORDER BY`** for subquery use. Fine for an unbounded set; for a sliced one the order decides *which* rows, so `is_in(q.limit(3))` returned whatever the plan produced. Now dropped only when unsliced.
- **`len(q.limit(3))` returned the full count** — `COUNT(*) ... LIMIT 3` counts every row then limits the one-row result. Now wraps when sliced, stays a bare aggregate when not.

Also verified rather than assumed: DuckDB **rejects** the `LIMIT -1 OFFSET n` that SQLite and SQLAlchemy emit, and takes a bare `OFFSET`. The first version asserted the opposite in a comment and failed.
