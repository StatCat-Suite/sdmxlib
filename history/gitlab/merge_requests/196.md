## Why docstrings rather than a per-file ignore

These are public API, not internals:

* `LazyCodelist` and `LazyHierarchy` are exported in `sdmxlib.__all__`
* `readers.get_artefact` returns a **`LazyCodelist` by default** — it is the object users actually hold when reading from a local registry

`help(LazyCodelist)` showed twenty bare properties. Now it shows all twenty documented.

## The issue's rationale for option 1 didn't check out

#197 justified the per-file-ignore route as *"these are protocol-conformance properties whose meaning lives on the protocol, not the implementation."* That isn't so — `Codelist.id` has no docstring either, and `Codelist`'s class docstring has no `Attributes:` section. The meaning doesn't live anywhere.

The **real** reason D102 fires only here is mechanical: domain types use attrs *fields*, the facades use `@property`, and D102 only inspects properties. That is a better argument for option 1 than the issue's own — but it justifies leaving undocumented precisely the object `get_artefact` hands back, which is why option 2 won on the merits.

## Two claims softened before shipping

My first draft asserted things about `levels` that the code does not guarantee:

| draft | shipped |
| --- | --- |
| "The declared levels, **outermost first**. **Empty when `has_formal_levels` is False**." | "The `Level` definitions declared by this hierarchy, in stored order." |

`Level` documents no ordering semantics, and nothing enforces the emptiness relationship. Writing either into published docs would have created a promise the library doesn't keep — the same failure mode as #197's own rationale, which is what prompted me to check.
