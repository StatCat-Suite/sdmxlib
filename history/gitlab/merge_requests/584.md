Closes #451.

SDMX-ML 3.x lets a codelist extension's member value hold the `%` wildcard. SDMX-JSON's `MemberValueType` is a plain id. The JSON writer emitted the pattern anyway, so the document failed the SDMX-JSON schema, and nothing was declared.

## What changes

- **Expansion:** the JSON writer writes each `%` member as the codes it matches in the extended codelist, keeping the member's cascade. The extended codelist comes from a resolved reference, or else from the message, with its own extensions applied. The output now validates against SDMX-JSON 2.0 and 2.1.
- **Declared gap:** `extensions[].selection.members[].value` for `json`. A code added to the extended codelist later is not picked up by the written selection.
- **Refused:** a pattern whose extended codelist cannot be found, or one that matches no code. The refusal names which.
- **API:** `Codelist.expand_wildcards(available)` and `wildcard_misfits(codelist, available)`. `LazyCodelist` redirects to `.materialize()`, as it does for `apply_extensions`.
- SDMX-ML 3.x keeps the wildcard as it is.
