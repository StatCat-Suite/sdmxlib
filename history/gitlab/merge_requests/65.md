## #105: \`Hierarchy.has_formal_levels: bool\`

Per the SDMX 3.1 audit lens, the existing \`is_leveled\` property — derived from \`len(self.levels) > 0\` — was **semantically wrong**. A hierarchy can carry levels as descriptive metadata without those levels being load-bearing on the tree. 3.1 expresses this distinction via the required \`@hasFormalLevels\` boolean; SDMX 2.1 uses \`@leveled\` (default false) for the same concept.

Replaced \`Hierarchy.is_leveled\` (property) with \`Hierarchy.has_formal_levels\` (explicit field, default \`False\`). Storage column \`hierarchy_meta.is_leveled\` renamed to \`has_formal_levels\`; \`LazyHierarchy\` slot + constructor kwarg renamed. The 2.1 writer emits \`@leveled\` when the field is True; reader parses it.

## #106: \`Level.coding_format: Facet | None\`

3.1 (and already 2.1) \`LevelType\` carries an optional \`<CodingFormat>\` with character/length constraints codes at that level must follow. **Reuses the existing \`Facet\` value type** so we have one constraint vocabulary across the model — no new shape introduced just to mirror the XSD.

The 2.1 \`CodingTextFormatType\` is a restriction of \`SimpleComponentTextFormatType\` exposing only \`textType\` / \`isSequence\` / \`interval\` / \`startValue\` / \`endValue\`, with a narrower \`textType\` enum (\`Alpha\` / \`AlphaNumeric\` / \`Numeric\`). Writer emits the overlapping subset; other \`Facet\` fields are silently dropped on \`CodingFormat\` (they aren't permitted there per the XSD restriction).

## #110: \`HierarchicalCode.valid_from\` / \`valid_to\`

Per-node temporal validity, independent of the underlying Code's own validity. Already supported by the 2.1 XSD (\`HierarchicalCodeType\` \`@validFrom\` / \`@validTo\`); 3.1 keeps the same shape. Wired through the 2.1 writer + reader.

## Bonus: Level chain flattening on read, re-nesting on write

The XSD encodes the level chain as a recursive \`<Level><Level><Level>...\` sequence (one root, each holding the next). Our model carries the same concept as a flat ordered \`ItemList[Level]\`. The serializer is now the **only** place this syntax difference lives — model consumers see one flat list root-first. Per your guidance on the audit (\"don't encode XML-isms in the model\"), this is exactly the right split.
