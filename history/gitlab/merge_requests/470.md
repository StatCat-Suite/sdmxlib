## What was measured

The issue reports that `LocalRegistry.get` accepts a `str` its signature denies
and disagrees with `RestRegistry.get`. Probing all four entry points found that,
plus a worse one the issue does not mention:

| entry point | declared | `SdmxUrn` | `str` | `Ref` |
| --- | --- | --- | --- | --- |
| `InMemoryRegistry.get` | `SdmxUrn[T]` | yes | yes, undeclared | **silently `None`** |
| `LocalRegistry.get` | `SdmxUrn[T]` | yes | yes, undeclared | **silently `None`** |
| `RestRegistry.get` | `SdmxUrn[T] \| Ref[T]` | yes | `AttributeError` | yes |
| `FederatedRegistry.get` | `SdmxUrn[T]` | yes | `AttributeError` | yes |

One mechanism explains both columns. The local registries end their lookup in
`self._store.get(str(urn))`. `str` of a `str` is itself, so a bare string worked
there by accident — and a `Ref` stringifies to `Ref(CL [unresolved])`, so it
missed and returned `None` with no error. **Traversal code that worked against a
`RestRegistry` found nothing against a `LocalRegistry`.**

The docs were already right, incidentally: `docs/upgrading.md` has said "`get`
takes **identity** — a URN or a `Ref`" since the 0.61 rewrite. Two
implementations just did not.

## The decision

Option 1 from the issue, chosen as the `get`-contract question the issue says to
settle first: **all four take `SdmxUrn[T] | Ref[T]`, and refuse `str`.**

```python
reg.get(urn)             # ✓ everywhere
reg.get(ref)             # ✓ everywhere  (was: silent None on two of them)
reg.get("urn:sdmx:...")  # ✗ TypeError:
#   get() takes an SdmxUrn or a Ref, not str — build one with
#   SdmxUrn.parse(text) for a URN string, or with
#   <ArtefactClass>.urn_for(agency=..., id=..., version=...)
```

Consistent with #338's argument that a bare string is not an artefact identity.
One `target_urn` helper in `model/ref.py` does the normalisation; it is narrower
than the existing `urn_of` in both directions — it refuses the artefact itself,
and it *recovers* `T`, which `urn_of` erases to `object` (`get` returns
`T | None`, so the phantom has to survive).

**Positional-only**, which is what actually makes the four interchangeable: they
did not agree on a parameter name either — three said `urn`, `RestRegistry` said
`target`. No call site anywhere passed one by keyword, so nothing broke for it.

## `__contains__` too

All three had the identical gap: `ref in reg` answered `False` for a *present*
artefact. Aligned the same way, and also made positional-only — basedpyright
flagged the name mismatch as a Protocol violation the moment `RegistryReader`
was touched, which is a naming constraint no caller of `in` benefits from.

`__contains__` keeps `object` and answers `False` for an unrelated value rather
than raising: `in` is a question.

## Call sites

The 21 that passed a `str` all traced back to helpers that built a URN with
`urn_for(...)` and then wrapped it in `str()`. They are shorter now.

## Two things this turned up that were not the subject

* **`tests/bench` passed `str` URNs and the checker could not see it.** `Shapes`
  held stringified URNs read out of SQL, and the `registry` fixture parameter was
  unannotated — with `reportMissingParameterType` off for that directory (#347),
  every `.get()` on it went unchecked. `just check` stayed green; the bundle tier
  caught it, which is exactly what #390 added that tier for. `Shapes` now holds
  parsed `SdmxUrn`s and the fixtures are annotated. Verified by re-introducing a
  `str` field: it is now a static error.
* **`Query.collect()` is declared `list[object]`** — the row type is erased at the
  terminal, so `q.hcode` rows come back untyped. Narrowed at the one use site with
  an assertion rather than assumed. The declaration is left alone; worth its own
  issue.
