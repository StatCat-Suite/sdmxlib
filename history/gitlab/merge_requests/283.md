Closes #272.

`code.id == 1` built, type-checked and compiled. `__eq__` overrides `object.__eq__` and cannot narrow its parameter, so no checker sees it.

## The measured behaviour is worse than the issue predicted

The issue expected DuckDB to coerce or return nothing. It does neither — it casts the **column** to meet the literal:

```
all-numeric codelist    code.id == 1  ->  matches
one non-numeric code    code.id == 1  ->  ConversionException: Could not convert string 'A' to INT32
```

The same query is fine or fatal depending on which codes happen to be stored, and the error names a cast the caller never wrote. Data-dependent failure from a static mistake.

## The fix

Each ref declares what its column holds (`_holds`), read off the DDL rather than assumed, and `__eq__` / `__ne__` / `is_in` check the literal. Eight of ten mistyped spellings probed were unguarded; `contains(1)` and `depth > "1"` the checkers already caught.

The check runs **after** `_coerce` — a `Level` or `Ref[Code]` is not a `str` until the hook has turned it into one, so checking first would reject the convenient spellings the DSL advertises.

`bool` is excluded from `int` and vice versa, symmetric rather than a special case, same reasoning `check_limit` uses.

## A second defect of the same family

`code.parent_id == None` returned nothing, silently — `= NULL` is never true in SQL. Same guard, message names `is_null()`.

## is_in checks the first member only, deliberately

Checking every member costs **~110 us on a 5000-element set** (measured), roughly doubling the compile on the path #271 flags as hot. O(1), and the gap is stated rather than hidden: a *mixed* set slips through, and every realistic version of this mistake is homogeneous.

## Verification

- **A/B benchmark**: 5000-element `is_in` unchanged (114.4 vs 114.7 us), confirming the O(1) choice. Single-predicate construction ~+3.5% (~0.09 us), slightly above the ~1.8% noise floor — recorded rather than rounded away.
- **SQL corpus byte-identical** against `main`.
- `_holds` is checked against `information_schema`: a wrong declaration would restore the defect and nothing else would notice, since guard and query would agree. Verified discriminating by mis-declaring `depth`.
