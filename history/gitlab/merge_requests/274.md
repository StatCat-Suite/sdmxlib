## `limit` was undecided, and silently widened

`q.limit(5).limit(10)` returned **ten** rows. The docstring said *"capped at
n"*, which reads as a cap and implies five. Neither the prose nor a test said
which, so the behaviour was whatever `attrs.evolve` happened to do.

Both readings are defensible and the two obvious references **disagree**:

| | `limit(5).limit(10)` |
| --- | --- |
| polars — `head(5).head(10)` | **5** — composes |
| SQLAlchemy — generative setter | **10** — replaces |
| ours, before | **10** |

So this was a decision to make, not a fact to look up.

**Decided: a cap. Composing never widens.**

```
filter   -> fewer rows
sort_by  -> more keys
limit    -> lower ceiling
```

Beyond symmetry, it closes a real hazard: last-wins silently discards a
*safety* cap, so a helper returning `q.limit(100)` had that undone by a
caller's `.limit(10_000)`. That is the wrong direction for a mistake to run.

Applied to **all five** query classes — each implements `limit` on its own
record, so a decision applied to one is not applied to the others by
construction.

### The two neighbouring questions, answered explicitly

`with_annotations` gets the **opposite** answer, with the reason on the method:
it selects what to *hydrate*, not which rows to select, so the narrowing
invariant does not apply — and replacing is what makes clearing it possible,
which is what passing no types is for.

`sort_by` accumulating while `limit` narrows reads as an inconsistency until
you notice **each mirrors its own SQL clause**: a statement has many ORDER BY
keys and exactly one LIMIT. Now pinned together so the pairing is deliberate
rather than an accident of two implementations.

## The three laws

**Neutral element**, stated where it can actually fail. "filter(p) on an
unfiltered query equals filter(p)" is trivially true of the *rows*; the content
is the shape of the emitted `WHERE`. A query with no predicates must compile to
the artefact scope alone — no trailing `AND`, no `WHERE TRUE AND …`.
Empty-conjunction folding is the classic bug here. Asserted for both structural
DSLs.

**`In(d, [c])` ≡ `Eq(d, c)`** on the data plane, dimension *and* attribute
side. The builder does not special-case singletons today; the law pins that if
anyone adds the index-friendly `=`, it stays equivalent — including that it
keeps excluding NULLs, which an `IS NOT DISTINCT FROM` spelling would not.

**Limit composition**, stated as a law rather than an example so the order of
the two calls cannot matter — last-wins passes `limit(10).limit(5)` and fails
`limit(5).limit(10)`.

Verified to discriminate: reverting `limit` to last-wins fails two immediately.

## Not included

`Not(Not(x))` and De Morgan, which the originating proposal listed. Neither DSL
has a `Not` combinator — negation is a per-field flag, not a wrapping node — so
there is nothing to apply them to.

## Breaking

`limit()` now narrows instead of replacing. Any caller relying on a later
`.limit()` to *raise* an earlier cap gets the lower one. Per the project's
pre-stability stance, no shim.
