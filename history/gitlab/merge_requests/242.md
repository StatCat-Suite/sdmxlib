# Merge request !242: feat: convert AttachmentConstraint to DataConstraint instead of refusing

**Closes #244.** SDMX 3.0 did not delete `AttachmentConstraint` — it *unified* it, folding 2.1's two constraint artefacts into one `DataConstraint` with a `role`. sdmxlib refused it on 3.0, 3.1 and SDMX-JSON with the advice *"use a DataConstraint"* — advice that could not be followed, because `DataConstraint` had nowhere to put the key set until #241.

Every field of an `AttachmentConstraint` is also a field of a `DataConstraint` — attachment, key set, identity, validity — so the conversion loses nothing. `to_data_constraint()` is on the model (so callers get it too) and the three writers apply it. `_UNWRITABLE` loses the entry on all three targets.

## Cross-version effect

| fixture | before | after |
|---|---|---|
| `ecb_data_structure.xml` | 14 lost, 1 changed | **0 lost, 1 changed** |
| `ecb_dataflow.xml` | 14 lost, 1 changed | **0 lost, 1 changed** |
| `complete.xml` | blocked (`structure_sets`) | blocked — *fundamental* |
| `minimal.xml` | blocked (`structure_sets`) | blocked — *fundamental* |
| `with_hierarchy.xml` | blocked (`hierarchical_codelists`) | blocked — *fundamental* |
| `with_metadata_structure.xml` | blocked returning to 2.1 | blocked — #245 |

The 14 losses were #243, fixed in the previous MR. What remains on the two surviving fixtures is the single `uri` difference (#238), and the four blocks are the grouping containers plus the MSD reporting layer — the boundaries #242 identified as fundamental rather than ours.

## The return trip is deliberately not exact

A 3.0 `DataConstraint` carrying only a key set could have been either 2.1 artefact, and the document does not record which — so writing it back as 2.1 yields a `ContentConstraint`. **The content survives; the artefact kind does not.**

That is option 1 of the three the issue laid out, chosen because the alternative (a discriminator annotation in the intermediate document) writes non-SDMX into output other tools read. The asymmetry is *asserted* via `_CONVERTED_ON_WRITE` rather than left to be discovered, and it belongs to the cross-version harness (#246) rather than `KNOWN_GAPS` — the latter records a field lost on one target, where this is a kind that changes across a version hop.

## Controls

Five mutations verified to fail. A sixth — dropping the attachment during conversion — **initially passed**: `ConstraintAttachment` is optional, so the output stays schema-valid and only an explicit comparison sees the loss. The property now checks it.

Two existing tests asserted the old dropping behaviour and were updated; `test_constraint_json_roundtrip` expected only the data constraint to come back, which encoded the drop.
