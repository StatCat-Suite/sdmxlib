## The loss

SDMX 3.0 added a fifth child to `AnnotationType` — **`AnnotationValue`**, the *non-localised* body, distinct from `AnnotationText`'s language map. It is the right home for a machine-read payload (an ordinal, a flag, a numeric weight) where a language map means nothing. SDMX-JSON carries it as `annotation.value`.

`Annotation` had no field for it, so it was parsed, discarded, and nobody told:

```python
# <com:AnnotationValue>239</com:AnnotationValue>
Annotation(id=None, title=None, type='ORDER', url=None, text=InternationalString(en='t'))
# -> "239" survived nowhere
```

**Why the census could not catch it.** The field census diffs the fields the model *has*. A field nobody modelled cannot be observed missing — so the guard built for exactly this class of loss was structurally unable to see it. Adding the field is what made it visible, 39 paths at once.

## Two things that fell out, neither of them the field

**The population guard was blind to `Annotation` entirely.** `_walk_populated_fields` recursed into `list | tuple | ItemList | ArtefactList`, and `Annotations` is none of those — so *no* annotation field was ever checked for population. The fixture could leave one unset and every round-trip check over it would be vacuous, which is exactly what happened to `value`. Fixed, and verified by unsetting it and watching the guard fail with `Annotation.value`.

**Annotation languages came back in plan-dependent order.** The `annotation_text` LEFT JOIN had no `ORDER BY` on `lang`. Adding a column shifted DuckDB's plan, flipped `en, fr` to `fr, en`, and failed #316's store/load guard (which compares `repr` deliberately). Latent before this change, not caused by it — confirmed by stashing. Nothing records insertion order, so a canonical order is the only reproducible answer.
