## The SQL corpus, rebuilt

#306 deleted `tests/support/sql_corpus.py` along with the `FrameQuery` /
`CodeQuery` / `HierarchyNodeQuery` it imported — which left the compiler about
to be rewritten with **no** equivalence check. Rebuilt over the path language:
82 cases across scalar predicates, hop shapes, combinators, clauses and
projection, dumping normalised `(sql, params)` for `diff`.

**With the guard the original lacked.** It hand-listed its cases, and a
hand-listed corpus goes stale exactly when it matters: a predicate kind added
later is absent, the diff stays empty, and the empty diff reads as proof. The
covered set is now *derived* off `_expr`, so a new `Pred` subclass fails until
it has a case. Mutation-checked — removing the `ArrayHas` case fails naming it.

Two more properties the diff depends on, neither of which holds by itself:
determinism (two dumps byte-identical, so alias allocation leaking between
compiles shows up here and nowhere else) and that no literal is interpolated.

## `_plan.py`: 110 killed, 0 survivors

The first run left 5 survivors, all in `_hops_available`, and all one kind:
each produces a **wrong suggestion list** in a `PathError` — inverting
`e.source == table` offers the hops of every relation *except* the one you are
on. Nothing noticed, because the tests asserted that `PathError` was raised and
never what it said.

Worth closing rather than waiving: `resolve_path`'s docstring says "a caller
who mistyped a hop needs the alternatives more than the rule", so the list *is*
the feature. Three tests closed all five. The discriminating half is asserting
that *other* relations' hops are absent — a superset still contains everything
an equality check looks for, so without it the inverted-filter mutants survive.

## `tools/mutate_union.py`, and why `_compile.py` is not here

| 1 file | 334 | 209 | 0 | 62% — not a module score |

| 2 files (group 1 of 7) | 356 | 187 | 0 | correct, 48 s |

The narrow survivors are mostly killed by the other thirteen files; the broad
run's timeouts are `RLIMIT_CPU` kills, not hangs. So the method is several
*light* selections, unioned — a mutant survives only when no group killed it.
Group 1 verifies it: 356 + 187 + 723 = 1266 exactly, zero timeouts.

Group 2 then deadlocked — 12 processes at ~0% CPU for 15 minutes where group 1
sustained 750%. That is #314, a third mutmut failure mode alongside #303 and
the stale-cache churn, and it is why `_compile.py` is not in this MR.
`only_mutate` is deliberately untouched: the blocker is mutmut hanging, not the
scope being too narrow.

Three bugs of mine in the tool before it worked, all fixed and commented — the
middle one produced a confident wrong answer rather than a crash, reporting 910
survivors, because `mutmut results` omits killed mutants and parsing it for
`killed` yields an empty set.
