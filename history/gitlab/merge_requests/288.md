Closes #300. Unblocks #271.

Three handles existed on a single thread — `reg.connection`, a thread-local in `_query_common`, and a **second** thread-local in `storage.lazy` — and they disagreed. Measurably, about `search_path`: the base had `'sdmx'` and both handles had `''`, so `SELECT ... FROM code` worked on the one `local/sql.py` documents and needed `sdmx.code` on the one every query actually runs on. A `SET` reached exactly one of three.

Nothing depended on them agreeing, which is why it survived #267. #271 is the first feature needing per-connection state and found half the query paths could not see it.

## `reg.connection` stays as it is

The obvious fix — make it thread-local, Django-style — is wrong here. It is a **stable, capturable** object and the codebase depends on that: `DuckDBDataStore.from_registry` stores it in a field. A thread-local property would let a store built on one thread execute on another thread's handle, reintroducing the sharing #75/#80 removed.

The two have different lifetimes and only one is safe to hold. A property cannot say "do not hold this"; a `with` block can.

```python
reg.connection            # base, stable, capturable — setup, DDL, derivation
reg.execute(sql, params)  # one-shot; no handle exists to capture
with reg.session() as s:  # scoped handle, shared with the DSL
reg.on_connect(fn)        # setup hook — every handle, existing and future
reg.open_sessions         # live handles for this store
```

Mixed into `Registry` **and** `DuckDBDataStore`; a registry-derived store resolves the same handle, which is the payoff for keeping the base capturable.

## Named "session" on evidence

`duckdb_conn.cursor()` returns a `DuckDBPyConnection` and carries most of the DBAPI cursor surface, so a reader imports DBAPI expectations — per statement, cheap, discarded. Ours is one per thread, long-lived, stateful: same word, opposite lifetime. Meanwhile `SET SESSION default_null_order=...` applies to one handle and not its sibling, so *session* is DuckDB's own word for this scope. Docstring says **database** session, explicitly not a unit of work.

## Two bugs found while building it, both pinned

- The prototype kept its own thread-local cache and became a **fourth** handle — value sets registered on it were invisible to `CodeQuery.ids()`, the exact bug being fixed.
- The first implementation tracked handles in one **global** set, so a newly opened store's default hook was applied to every handle in the process including closed ones: **23 tests failed** with "Connection already closed". Handles are now per base connection, like the hooks.
