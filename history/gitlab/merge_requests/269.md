Closes #266. Part of %13.

`is_in("CA")` silently meant `is_in(["C", "A"])` and shipped in #261. The suite
had no category of test that could have caught it, and the reason generalises:
**every test we had explores the value space, and this was a wrong argument
shape.**

Three layers declined it, each correctly:

- the strategies only generate well-formed input — `st.lists(...)` makes lists;
- both checkers were right to allow it, since `str` satisfies `Iterable[object]`;
- and the differential oracle **shared the misconception**, so even a lucky
  example would have passed. Measured at the time: `oracle.in_set("CA")`
  returned `['C', 'A']`, identical to the SQL.

That third one is a structural limit of differential testing, not a defect in
the oracle. Rule 1 — an oracle shares no code with the module it tests — exists
to reduce it, but sharing *Python's iteration semantics* is not sharing code.
What found it was a third implementation outside the shared assumptions: polars
rejects the same call.

## Three live instances, found by probing rather than by reasoning

| misuse | before |
| --- | --- |
| `is_in({"A": 1})` | **returned `['A']`** — a dict is iterable and yields keys |
| `limit("5")` | **reached DuckDB and worked** |
| `limit(-1)` | `BinderException` from inside execution |

The dict case is the notable one: same shape as the original, and it survived
the original's fix **because that fix named `str` rather than the class of
mistake.** Both now go through one `check_in_values`.

And a family that failed uselessly — `filter(code.id)` raised
`'_IdRef' object has no attribute 'to_sql'`; `sort_by(code.id == "A")` raised
`'Eq' object has no attribute '_field'`. Technically failures, practically
useless: they name a private attribute and leave the caller to guess.

All four DSLs now share `check_predicate` / `check_sort_key` / `check_limit`,
and each message carries a worked example in *that* DSL's accessor — a codelist
example in a hierarchy error would send the reader the wrong way. Generators,
tuples and sets are still accepted: the rule is "iterable but means something
else", not "not a list".

## The part that guards the class

`test_no_unreviewed_collection_parameter` is a static inventory of public
parameters annotated as a collection a bare `str` satisfies. A new one fails
until someone reviews it, guards it, and lists it — which is what would have
caught #261 the day it landed.

It earned its keep immediately, flagging two internal `compile_frame`
parameters typed `Sequence[str]` / `Sequence[object]`. **Reviewed and listed
rather than guarded**: the only caller passes tuples the module just computed,
and a check on every compile to catch a call that cannot happen is not worth
the frame.

The first version called each candidate with `"AB"` and crashed descending into
builtins. A static read needs no instance of the receiver and cannot be
defeated by a parameter on a class it does not know how to build.
