# Merge request !385: fix(query)!: n_unique counts a null as a value, as polars does

Closes #326.

`unique()` compiles to `list(DISTINCT x)`, which keeps a null; `n_unique()` compiled to `count(DISTINCT x)`, which does not count one. **DuckDB's two functions disagree with each other** and the language inherited both, so `len(unique())` and `n_unique()` differed by one on any nullable column — with nothing in either name to say why.

Both names are polars', where a null *is* a value and the two agree always. `list()` already keeps nulls here too, so `n_unique` was the odd one out on both counts. CLAUDE.md's rule is to check a DSL decision against polars where there is a counterpart; this was the case where the **name was taken and the semantics were not**.

Verified against polars on all four shapes:

| | polars | before | after |
|---|---|---|---|
| empty | 0 | 0 | 0 |
| all null | 1 | 0 | 1 |
| null + values | 2 | 1 | 2 |
| no nulls | 2 | 2 | 2 |

## Two things measuring found that the issue had not

**The empty relation.** The obvious expression — `count(DISTINCT x) + CAST(bool_or(x IS NULL) AS INT)`, which the issue proposed — answers **NULL** rather than 0 over no rows, because `bool_or` of nothing is NULL. Both halves are `COALESCE`d.

**Two compile sites, not one.** The windowed form spells this aggregate separately, and my first fix left it behind: `n_unique()` said 2 while `n_unique().over(...)` said 1. A rule that holds in a `SELECT` and not in an `OVER` is *worse* than the original disagreement, because the caller has no name to tell them apart. Caught by the test written for exactly that.

## The test that predicted this

`test_unique_is_null_aware_and_n_unique_is_not` asserted the gap *"so the day it changes this test says so"*. This is that day. It is now `test_unique_and_n_unique_agree_about_null`, and a second test states the invariant as a **comparison** over every codelist rather than as two numbers, so a fixture change cannot quietly stop testing it.

## A different divergence, filed not fixed

**#341**: an empty fan-out collects to `NULL` where polars gives `[]`, so the restored invariant needs `or []` at the call site for an empty group. The neighbouring test already hedges `assert ... in ([], None)` — which is what an open question looks like written down, and it has a real argument on both sides (`None` and `[None]` mean different things; polars cannot express that). Normalised at the one call site here rather than settled.
