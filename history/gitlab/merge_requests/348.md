# Merge request !348: fix(data): labelling silently did nothing, and observations now project by id

| | |
| --- | --- |
| State | merged |
| Opened | 2026-08-17 |
| Merged | 2026-08-17 |

Working out where `with_labels=` should live on the typed path turned up
a bug in the one it already had.

`sdmxlib.polars.label` matches components by **SDMX id**. Both data-plane
read paths return **physical** column names. So for any binding that
renames its columns — `REF_AREA -> GEO`, which is what a binding is for —
`catalog.query(with_labels=True, lang=…)` matched nothing, returned the
frame unchanged, and reported success.

Nobody noticed because `DataStore.query`'s docstring asserted the
precondition: "Columns are named on the SDMX side (mapped from physical
via the binding)". Nothing did that mapping. A false docstring is worse
than none, and this is what it cost.

Three changes, and the first is the one that matters:

**`label` refuses a frame no component names.** Labelling nothing is
never what a caller meant. Skipping *some* components stays as it was —
a projection or a CSV carries fewer columns than a DSD has, and extra
columns are ordinary — so only the total miss raises, naming both sides.
The existing test asserted the no-op; it is split into the case it meant
to cover and the case it was accidentally blessing.

**An observation column projects as its SDMX component id.** A structural
column projects as the physical column it reads, so a caller replacing a
hand-written `SELECT code_id …` needs no renaming. The same rule points
the other way for observations: the caller wrote `obs.col("REF_AREA")`,
and returning `GEO` leaks the binding's layout — as well as making
labelling impossible. An explicit alias still wins.

**The docstrings say what is true.** `DataStore.query` records what it
actually returns and why the old claim was expensive; `with_labels`
states the precondition it needs.

`projected_name` returns `self.column` rather than the slot, because
`Label` overrides that property to append the language — caught by the
cookbook driver, which asserts `select(name["en"], name["fr"])` gives
`name_en` and `name_fr` rather than two columns called `name`.
