Closes #477.

## The defect

`ComponentBaseType` makes a component's `@id` optional in SDMX-ML 2.1, 3.0 and 3.1, and SDMX-JSON 2.0 does the same. The XSD documents the default:

> If this identifier is not supplied, then it is assumed to be the same as the identifier of the concept referenced from the concept identity.

The readers read the omission as `""`. Measured on the maximal message:

- dimensions, attributes and metadata attributes were **refused** for the empty id, so a conformant DSD or MSD was refused;
- 2.1's measure dimension was **kept with id `""`**;
- a 3.x measure read as **`OBS_VALUE`** (2.1's fixed primary-measure id) whatever its concept;
- in SDMX-JSON the DTOs required `id`, so these were refused.

## The fix

- One rule per format: `component_id` (SDMX-ML) and `component_id_of` (SDMX-JSON). Each returns the stated id, else the item id of the component's `ConceptIdentity`, else refuses the artefact ("…and this one has no ConceptIdentity").
- Applied to every component: dimensions, attributes, measures, 2.1 measure dimensions, and metadata attributes, nested ones included. 2.1's `TimeDimension`, `PrimaryMeasure` and `ReportingYearStartDay` keep their schema-*fixed* ids.
- This is the standard's own answer, not an assumption, so nothing goes on `msg.assumed`.

## Exposure

None on live data: of 3.1 million components in the DSDs and MSDs of all ten registry/version sweeps (BIS, ECB, ESTAT, IMF, OECD, SDMX), **0** omit `@id`. Like #476, this is correctness for conformant documents nobody serves yet.
