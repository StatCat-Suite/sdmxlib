## The defect

A `HierarchyAssociation` exists to bind a hierarchy to a **dimension**, and that was the one thing you could not follow. `linked_object` is declared against the spine (`linked_object_urn -> artefact.urn`), but a Dimension URN is an *item* URN and only maintainables live in `sdmx.artefact`:

```
q.hierarchy_association.linked_object.id   -> None
q.hierarchy_association.linked_object.urn  -> the dimension URN   # FK column, no join
```

Every existing test in `test_query_hierarchy.py` linked a *Dataflow* — maintainable, resolves fine. The fixtures exercised the exception rather than the rule, which is why the hole sat behind a wired-looking edge.

Downstream, pinaxlib pays for it in the worst currency available — sdmxlib's URN grammar, reimplemented in SQL:

```sql
replace(df.dsd_urn, '.DataStructure=', '.Dimension=') || '.' || ?
```

## The fix

Schema **2.16** bakes `linked_object_urn` into the two halves a join can use (`linked_object_owner_urn`, `linked_object_item_id`), and a new `component` edge joins them to `dsd_component`'s `(dsd_urn, component_id)`:

```python
reg.query(q.hierarchy_association).select(
    comp=q.hierarchy_association.component.id,        # REF_AREA
    dsd=q.hierarchy_association.component.dsd.id,     # CPI
    h=q.hierarchy_association.hierarchy.id,           # GEO
)
```

The inverse is bound too — `q.component.hierarchy_associations`, "which hierarchies apply to this dimension".

`caching.md` puts physical layout ahead of runtime work, and the parse is one the writer already does in the other direction: `_split_item_urn` is the inverse of `_make_item_urn` and sits beside it, because a grammar split across modules is how a third spelling ends up downstream.

## Two decisions worth a look

**The composite is load-bearing.** `REF_AREA` is unique within a DSD, not across a store, so a single-column join on the item id would answer for every flow and look right on any fixture with one DSD. `test_the_component_hop_is_scoped_by_the_dsd_not_the_id_alone` uses two.

**Unmapped item classes split to `None`, not to a guess.** `_ITEM_OWNER_CLASS` places the DSD component classes, `Code`, `Concept` and `Category`; anything else leaves both columns NULL. A wrong owner would bind an association to the wrong component silently, which is worse than an unresolved hop.

`linked_object` keeps its contract, now stated in a test: it reads the URN and nothing else, so a reader who gets `None` from `linked_object.id` finds the reason instead of concluding the write is broken.
