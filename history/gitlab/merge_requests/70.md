Closes **#108**. SDMX 3.0 / 3.1 \`HierarchyAssociationType\` binds a Hierarchy to an identifiable artefact within an optional context (e.g. \`REF_AREA\` Dimension uses a geography Hierarchy in the context of Dataflow \`DF_GEO\`). Real domain content — without it, callers can't pick the right hierarchy when rendering a coded dimension.

## Latent bugs fixed (the 3.0 \`<Hierarchy>\` writer path was unvalidated)

Adding the first fixture to exercise 3.0 \`<Hierarchy>\` through XSD validation surfaced four pre-existing bugs:

1. **\`@hasFormalLevels\` missing** — 3.1 made it a **required** attribute on \`HierarchyType\` (3.0 has the same attr, also required). Writer now emits it mirroring the model's \`has_formal_levels\` field; reader populates it.
2. **\`HierarchicalCode\` emitted \`<Name>\` and \`<Description>\`** — same XSD violation #95 fixed for 2.1. The 3.0+ element only allows Annotations + \`<Code>\` + nested \`<HierarchicalCode>\` + optional \`<Level>\`.
3. **\`<Code>\` emitted as wrapped \`<Ref/>\`** — but 3.0 \`CodeReferenceType\` is URN-text. Switched to \`_write_urn_text\`.
4. **\`<Level>\` emitted as \`<Ref id=\"...\"/>\`** — 3.0+ \`<Level>\` inside a HierarchicalCode is just the level id as text (\`IDType\`). Switched to \`element.text = level.id\`. Reader accepts both forms for legacy tolerance.

These were inert in 2.1 (which has separate writers for \`HierarchicalCodelist\`) but broke 3.0 XSD validation the moment any fixture used Hierarchies. Now caught and fixed.
