This is #515, "allow if bounded" as decided. `RestRegistry.obs` now refuses an unbounded fetch instead of downloading the whole flow.

**The rule:** a predicate the data request can't carry (a measure, say) stays residual and runs locally. That is still fine when something else narrowed the fetch: a key slot, a period, or a `c[…]` component. When nothing did, the request would be `/data/{flow}/all`, every observation the provider holds, so it now raises `PushdownError` **before any request**:

```
this filter cannot be sent to the provider (OBS_VALUE), and nothing else narrows the fetch,
so it would download all of EXR to filter it here. Add a filter the data key carries —
FREQ, CURRENCY, TIME_PERIOD — or read the flow unfiltered with .frame() / .stream() and filter that.
```

An unfiltered query is not refused: it is an explicit request for everything.

This is the rule `is_bounded` already encodes for the `/data` capability (`bounding={DATA_ROOT: frozenset()}`, so any pushed constraint bounds the scan). `RestRegistry` lowers with `data_request_for` directly, so it applies the rule to the request it built, through `DataRequest.narrows`. The design doc's three "declared but not applied" notes now say it is applied.

**Tests:**
- `test_a_measure_filter_reaches_the_wire_as_nothing`, which pinned the old behaviour, is replaced by: the refusal (no request sent); an unpushable filter beside a key slot or beside a period runs locally on the narrowed fetch; and an unfiltered query is answered.
- `test_a_measure_keeps_its_declared_type` gains a key filter, since its subject is the measure's type, not bounding.
- Sabotage checks: with the refusal off, the refusal test fails; with a period not counted as narrowing, the period case fails.
