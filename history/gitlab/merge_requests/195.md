## Why they disagree

`T_co` appears exactly twice in `model/urn.py` — the TypeVar declaration and the class header. It is a **pure phantom**: never used in the class body, no field, no method signature.

So variance inference has nothing to infer *from*, and the tools fall back differently:

* **basedpyright** treats an unused parameter as covariant → accepts
* **pyrefly** treats it as invariant → rejects `SdmxUrn[Codelist]` where `SdmxUrn[object]` is wanted

```
ERROR Argument `SdmxUrn[Codelist]` is not assignable to parameter `u` with type
      `SdmxUrn[object]` in function `consumer` [bad-argument-type]
```

That rejected assignment is exactly the one `9234d27` made covariant to fix a real latent defect. Both defaults are defensible readings of an unused parameter; the disagreement is the point, not a bug in either.

The issue's premise — *"PEP 695 infers variance, so this may come out covariant on its own"* — was half right. It does infer, and one checker does come out covariant. It just isn't unanimous, and this repo gates on both.

## Method

The probe was validated against a **known-invariant control first**, so a pass could not be mistaken for a checker that simply wasn't looking:

```
invariant TypeVar (control)  ->  basedpyright ERROR   # probe detects invariance
covariant TypeVar (current)  ->  basedpyright OK      # baseline
PEP 695 inferred             ->  pyrefly ERROR        # the finding
```

Without the control this experiment would have proved nothing — the same trap I hit earlier in !189, where a "non-vacuous" check turned out to be methodologically wrong.

## No regression test

The property is already load-bearing in `src/`. Making `SdmxUrn` invariant produces **4 basedpyright errors** (`ref.py:163` among them), so `just check` guards it. A dedicated test would only restate what the call sites already enforce — and tests aren't type-checked in the default gate anyway, so it couldn't guard variance even if written.
