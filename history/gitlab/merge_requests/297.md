Closes #233. First of the three remaining issues in %11.

## The defect

`SdmxUrn.version` defaults to the sentinel `"latest"`, which stringifies with **no `(version)` part at all**:

```
DataStructure.urn(agency="AG", id="DSD")   ->  ...DataStructure=AG:DSD
DataStructure.urn(agency="AG", id="DSD", version="1.0")  ->  ...=AG:DSD(1.0)
```

SDMX-ML 2.1 tolerates the first: its references are `<Ref>` containers with a separate, optional `version` attribute. 3.0 switched to URN *strings* whose pattern facets require the parenthesised version. So the same artefact wrote a 2.1 document consumers accept and a 3.0 document the schema rejects — silently.

Verified against the vendored XSD rather than taken on trust:

| | 2.1 | 3.0 XSD |
| --- | --- | --- |
| `version="1.0"` | valid | **valid** |
| default (`"latest"`) | valid | **INVALID** |

## Refuse, do not substitute

#233 lists resolving the reference to the artefact’s real version at write time as an option. That is worse than refusing: it silently changes *which artefact the document names*. `"latest"` is a question — "whatever is newest when you read this" — and a serialised reference has to be an answer.

## Blast radius, measured before choosing

The issue asked for this explicitly. Adding the check breaks **zero** existing tests across unit + integration. That is also the other half of the story: nothing in the suite exercised the sentinel on a write path, which is exactly why it survived this long.

## Both entry points

`check_metadata_serialisable` is a *separate function* from `check_serialisable`, so the structure-side fix does not reach MetadataSet targets — they needed the rule added explicitly. There is no 2.1 exemption there at all, since SDMX 3.0 dropped the v2.1 MetadataReport layer, so every wire form a MetadataSet has is a 3.x one.

## The generative guard is not the one the issue suggested

#233 proposed adding `"latest"` to the shared `versions()` strategy. That would be wrong now the behaviour is decided: artefact versions and *reference* versions are different things, and seeding the shared strategy would fail every unrelated 3.0 round-trip property rather than cover this path. Instead there is a dedicated property that draws the sentinel where the assertion knows what to expect, and drives **both** branches — so it cannot pass merely because `serialize` is broken outright.

(It also flushed out a strategy misuse of my own: `sdmx_ids()` generates `"0"`, which is a valid id but not a valid *agency* id under `NestedNCNameIDType`. Now uses `agency_ids()` / `ncname_ids()`.)
