Every SDMX-CSV 2.0 row carries `STRUCTURE` and `STRUCTURE_ID`, and this reader
already parsed them — then required the `DataStructure` as a positional argument
anyway, so the file's own answer was available only *after* you had supplied it.
A consumer holding a structure message and a directory of CSVs restated the join
by hand:

    slpl.scan_csv(out / f"{flow_id.lower()}.csv", message.dataflows[flow_id].structure())

Two shapes now, because the ecosystem uses both:

    slpl.scan_csv(path, registry=reg)   # resolve whatever the file names
    slpl.scan_csv(path, flow)           # a Dataflow, unwrapped for you
    slpl.scan_csv(path, dsd)            # unchanged

sdmx1's CSV reader takes either a dataflow or a structure and unwraps the flow
itself; pysdmx reads the file with no structure at all and joins it against a
structure message handed over separately. Checked both rather than inventing a
third shape — `registry=` is ours because we have a registry concept, and
accepting a `Dataflow` is sdmx1's, and it is the smaller of the two fixes: it
alone deletes the consumer's line.

## All three kinds, and the vocabulary was wrong

`STRUCTURE` names the reference kind, and only `dataflow` was considered.
`datastructure` now resolves directly and `dataprovision` through its dataflow —
the same second hop a dataflow makes to its structure.

The spec's field guide says, verbatim, "The first column contains: `dataflow`,
`datastructure` or `dataprovision`". **Two of our docstrings said
`provisionagreement`** — that is SDMX-JSON's RFC 5988 *link relation*, a
different vocabulary — so a caller following them wrote a file no conformant
reader accepts, and nothing refused it. `write_sdmx_csv` now validates the value
against `STRUCTURE_KINDS`. Confirmed three ways before changing it: the field
guide, sdmx1's independent CSV reader (`{"dataflow", "dataprovision",
"datastructure"}`), and the issue.

## A wart the kind column makes fixable

`Dataset.dataflow` was built from `STRUCTURE_ID` whatever `STRUCTURE` said, so a
`datastructure` file came back claiming a dataflow whose id was really a DSD's.
Reading the kind is what makes that distinguishable; it is None now for a file
that does not name a flow.

## short_urn, and the writer that needed it

`AGENCY:ID(VERSION)` is the form `STRUCTURE_ID` carries.
`parse_dataflow_id` has always owned *reading* it while every caller *wrote* it
by hand — five f-strings in `src/` alone. `sl.short_urn(artefact)` is the public
half; pysdmx exposes the same concept as `Dataset.short_urn`, though its form is
class-prefixed where this column's is bare, so ours matches the column it is
parsed from.

`write_sdmx_csv(structure_id=...)` now takes the artefact as well as the string,
and reads the kind off it — so the available mistake, a `DataStructure` passed
with `structure="dataflow"`, is no longer reachable.

## Guards

17 tests. Four distinguishable failures, as the issue asked: neither argument
given, a file naming nothing, an id the registry lacks, an unknown kind — plus a
dataflow with no structure and an agreement with no dataflow. A `TypeError`
rather than `ValueError` for a URN resolving to the wrong *kind* of artefact,
which is a different fault from absence.

Discrimination: passing a `DataStructure` positionally behaves exactly as before,
and `STRUCTURE_KINDS` is asserted to be the spec's three so a fourth value has to
be a deliberate edit. The end-to-end test writes with the artefact and reads back
through the registry, so neither side formats nor parses the short URN by hand.

## For the consumer

The `flow_id -> DataStructure` half of the join goes away; the
`flow_id -> filename` half stays yours. `structure_id=f"{flow.agency_id}:..."`
becomes `structure_id=flow`.

Closes #409.
