## Why the widening cannot mis-join

The old docstring's worry was that a wrong owner would silently join an
association to the wrong component. That is about a *wrong* mapping, not a
complete one — and the argument is now asserted rather than reasoned about.

`hierarchy_applicability` joins these two columns to
`dsd_component(dsd_urn, component_id)`. An owner URN that is not a
`DataStructure` cannot equal a `dsd_urn`, because the class differs inside the
URN — so every row the widening adds is inert for the one consumer and
informative for anything reading the column directly.
`test_a_widened_owner_cannot_join_a_dsd_component` writes both links and
asserts the dimension one joins while the node one does not. The dimension half
is the discrimination check: without it the test would pass on the view being
empty for an unrelated reason.

All three guards were watched to fail — forcing every item class to be owned by
`DataStructure` breaks both placement cases and the inertness case.

## No schema bump, deliberately

`SCHEMA_VERSION` stays at 2.19. The only DDL edit is a comment, nothing pins
the DDL text (the schema tests read columns through DESCRIBE), and the change
is to stored *values* for a case that does not arise in practice — an HA whose
linked object is a hierarchy node rather than a component.

That restraint is worth stating because a bump is not free here:
`local.registry` refuses a store whose version differs and the bundle tier
refuses to run when it moves, so bumping would have invalidated a 2.6 GB
bundle for a change that alters no structure. A bundle written before this
keeps NULL where a new write puts a value, and the only consumer reads both
identically — which the inertness test is what establishes.
