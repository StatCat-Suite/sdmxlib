Closes #295.

`sort_by` was borrowed from polars at the wrong level. polars has no frame-level `sort_by`: frames have `sort` (a pipeline stage, last-wins), and `sort_by` is an **expression** method — `pl.col("a").sort_by("b")` — meaning something else entirely.

Every declarative peer says `order_by` (SQLAlchemy, Django, ibis), and it is the SQL clause name matching the register the rest of the surface uses. Since #294 made the law *replace*, ours matches Django's `order_by` exactly — the name was the only thing left out of step.

## A split, not a search-and-replace

`ItemList`, `ArtefactList` and `Query[T]` **keep `sort_by`**. They sort in Python, take a key function or attribute name, and mirror `sorted(key=, reverse=)` down to the `descending=` flag that the SQL side replaced with a per-key `.desc()`:

```python
dsd.dimensions.sort_by(lambda d: d.id, descending=True)   # in memory
cl.codes.order_by(sl.code.id.desc())                      # compiled to SQL
```

A test asserts **both** directions — checking only that the SQL side gained `order_by` would let an alias creep back; checking only the in-memory side would miss a well-meaning rename there.

The vocabulary is renamed coherently inside the SQL modules, not just the method (`sort_keys` → `order_keys`, `SortKey` → `OrderKey`, the helpers, the messages). Leaving `order_by()` building a `SortKey` into `sort_keys` is the half-renamed drift this milestone exists to remove.
