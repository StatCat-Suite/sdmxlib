# Merge request !328: fix(tools): run mutmut's parent-side test phases in a forked child (#314)

`mutmut run` forks one child per mutant off a parent that has already run
the test suite in-process — three times: stats, "clean tests", and the
forced-fail check. polars does not survive that fork, so the children
hang at 0% CPU until RLIMIT_CPU kills them, and mutmut books each as a
*timeout*. 205 of 706 verdicts in #303 were this.

The recorded diagnosis was right about rayon and wrong about the rest,
in two ways that changed the fix:

* **The polars use is on the write path.** The child hangs inside
  `validate()` → `_check_item_ids`, which vectorises above 64 items — so
  any test adding a decent-sized codelist poisons the fork, not just the
  18 that call `Frame.collect()`. `.ids()` in the parent poisons too,
  and it touches no polars at all. The issue's option 3 — no-op the
  Frame conversion under mutmut — would not have worked.
* **One row is enough.** Not "the pool must do real work first":
  `pl.Series(["A"]).str.contains(...)` does it. Importing polars does
  not.

That asymmetry is the fix. The parent keeps the imports and delegates
every execution to a forked child; a child's rayon init happens in its
own memory, so the parent stays forkable. Only the stats pass returns
more than an exit code, and mutmut already serialises exactly that —
the child calls save_stats(), the parent load_stats().

Preloading the third-party extensions is not incidental: after mutmut's
mutant-generation Pool, a child that *dlopens* pyarrow aborts outright.
Stock mutmut never meets it because its parent has imported the world by
then. `sdmxlib` is deliberately not preloaded — that puts the real
modules in sys.modules and every child then tests unmutated code from
src/. It failed loudly (forced-fail could no longer fail), which is the
only reason it was caught; silently it would have reported a perfect
score measuring nothing.

Measured, same module and selection:

    stock      179 mutants   killed 3   survived 0   timeout 3
    fork-safe  179 mutants   killed 5   survived 1   timeout 0

The three timeouts were deadlocks; they resolve into two more kills and
one real survivor. And the selection #314 could not run at all now
does: `_compile.py` against the three projection test files — 1290
mutants, 588 killed, 389 survived, **0 timeouts**, 7.84 mutants/second.
Triaging those survivors is #304.

The new test asserts the three polars facts the tool depends on, each in
a fresh subprocess because this suite has itself used polars by then. If
polars ever becomes fork-safe, the middle one fails and the tool can be
deleted.
