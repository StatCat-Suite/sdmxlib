Closes #275. Part of %15.

`collect()` returns SDMX artefacts — right when the next step is navigation,
wrong when it is analysis. The %15 consumer survey found **113 hand-written SQL
statements against `sdmx.*`** across six applications that already depend on
sdmxlib, and the most common shape was not a filter: it was "two columns as a
frame" or "count these by that". Those callers dropped to a raw DuckDB cursor
because the DSL could only return whole artefacts.

Both structural DSLs gain frame-shaped branches. **Everything stays lazy** —
`collect()` is the only call that executes:

```python
n = sl.code.id.count().alias("n")

(cl.codes
   .filter(sl.code.depth > 0)        # WHERE
   .group_by(sl.code.parent_id)
   .agg(n)
   .filter(n > 5)                    # HAVING
   .sort_by(n, ascending=False)      # ORDER BY the count
   .limit(10)
   .collect())                       # one statement, one round-trip
```

### Design decisions worth reviewing

**Lazy, not terminal.** `group_by()` returns a restricted `GroupBy` — mirroring
polars' `LazyGroupBy`, and the point at which the row kind changes — and
`agg()` returns a query over the new rows. Returning a frame instead cost three
concrete things: a second materialisation point in a DSL whose contract is
`collect()`; `HAVING` and top-N pushed to the client (the first cut's own
cookbook idiom fetched every group to show ten); and `SqlRelation` composition,
since a one-column projection is exactly the subquery `is_in` wants.

**Columns referenced by object, never by name — no `col()`, not even as a
fallback.** polars resolves post-aggregation columns by name, so the same
expression means different things either side of the boundary:

```python
lf.group_by("g").agg(pl.len().alias("n")).filter(pl.len() > 1)
# keeps every group — post-agg pl.len() is the frame's length, not the group's
```

No error, just the wrong answer, which is why polars needs both `having()` and
`filter()`. Object-reference has no boundary, so **one** `filter` covers both
roles, an unprojected aggregate can be restricted on, and a typo is a type
error. Binding to a variable is optional — nodes compare structurally, so
repeating the expression refers to the same aggregate. Adding names later would
drag `having` back in, so this is a deliberate one-way door.

**Ref/node split is not stylistic.** `AggregateRef` carries the operators;
`Aggregate` is the stored node. Collapsing them was measured: a
predicate-building `__eq__` on a node inside a frozen query record makes tuple
comparison call it and then `bool()` it, so **any two queries compare equal** —
silently breaking `attrs.evolve` round-trips, tests, and any future
canonical-form cache key (#273).

**`HAVING`, not a wrapping `SELECT`.** DuckDB plans both identically (checked
via EXPLAIN — same operator tree), but only `HAVING` can restrict on an
aggregate that is not projected. A wrapper becomes necessary when window
functions arrive, and that is the point to add one, for those predicates only.

**Naming is the contract.** `code.id` → `code_id`, so a frame from the DSL and
one from the SQL it replaces are interchangeable. Labels carry the language
(`name_en`). Aggregates are the type-agnostic five plus `code.len()` for
`COUNT(*)`; no `sum`/`mean`, since the only numeric field is `depth`.

### The enabling refactor

`select` needs "field → SQL column", and five predicate emitters per DSL each
carried their own copy — ten `isinstance` chains, the duplication that made
#248's hop bound parseable-but-dropped in four separate emitters. `RowKind`
gained `column()`: one implementation per relation, used by the emitters and by
the projection. A downstream row kind gets both for free.

### Performance

Medians vs `main`, ~1.8 % noise floor:

| | main | branch | Δ |
|---|---|---|---|
| compile, single predicate | 2.06 µs | 2.52 µs | **+22 %** |
| compile, predicate chain | 8.45 µs | 9.95 µs | +18 % |
| compile, annotation | 2.52 µs | 2.59 µs | +2.4 % |
| execute, single predicate | 206 µs | 209 µs | +1.6 % |
| execute, chain | 467 µs | 474 µs | +1.6 % |

Three rounds of tightening held it there: `NamedTuple` rather than frozen
dataclass for `ColumnSql` (158 ns → 81 ns), skipping the params splice when a
column binds nothing, and splitting `_where` from `_scan` so only the
projection path pays for an immutable record. A `functools.partial` for the
per-DSL wrapper would have saved a frame and **was rejected** — it erases the
row-kind parameter, which is the check #267 exists to provide.

Accepted rather than cached away: compile is ~1 % of a query, so +0.5 µs
against a 206 µs execute is **+0.25 % end to end**, and no execute benchmark
moved beyond noise. `test_compile_single_predicate` reads +22 % at one fixture
size and +18 % at the other *on identical code*, so ≤5 pp on these is drift.
Recorded with its reasoning in the bench module.

### Tests

- **`test_query_projection.py`** — 35 unit tests. Three assert nothing executes
  before `collect()`; one asserts filter+group+restrict+order+limit is a
  **single** statement; one pins that two different frame queries compare
  unequal (the `__eq__` hazard above); one checks an alias containing a quote,
  since aliases are quoted identifiers and cannot be binds.
- **Five differential properties** — `select` against `collect()`, and
  "grouping partitions the matched rows". Projection binds `name[?]` in the
  select list, which binds *before* the WHERE clause — a parameter-order path
  nothing previously exercised.
- **`sql_corpus`** — predicate section byte-identical to `main`; 20 frame cases
  added now that a projection has a `to_sql()` to capture.
- **`docs/cookbook/structures_as_frames.md`** + driver executing every block,
  including one that pins the polars behaviour the page cites, so the suite
  reports it if polars changes rather than the reader discovering it (#278).
