# Merge request !233: test(matrix): cover the metadata envelope; four conformance fixes

| | |
| --- | --- |
| State | merged |

| Merged | 2026-08-06 |

**Closes #223.** `MetadataSet` and `MetadataProvisionAgreement` were the matrix's last two rows, and neither is a `StructureMessage` field — they ride in `MetadataMessage`, the other envelope sdmxlib serialises, which the field-keyed coverage guard cannot see.

That envelope had no generative coverage and **no schema validation of emitted XML at all**. No new compiler was needed: `SDMXMessage.xsd` is the entry point for the whole version, `<mes:GenericMetadata>` included. The schema was compiled and sitting there; nobody had ever pointed a metadata document at it.

Four defects, detailed in #234, none reachable from any fixture:

1. **`serialize` never validated a MetadataMessage** — it returned early for that envelope. Every finding below was reachable only because of this.
2. **The 3.0 header put a metadataflow URN in the MSD slot.** `GenericMetadataStructureType` is a choice of three, each restricted to one artefact kind by a pattern facet; the writer always emitted `<com:Structure>`.
3. **A MetadataSet must name at least one target** — `MetadataSetType` requires `Target` (1..n), and SDMX-JSON agrees.
4. **`MetadataSet.version` defaulted to a value with no JSON form.** The metadata schema pins `VersionType` to semver where the structure schema states no pattern; the field is *optional* there — the SDMX-TWG's own sample omits it — so our reader defaulting to `"1.0"` and the writer emitting it turned valid input into invalid output.

Recorded rather than worked around: SDMX-ML 3.0 carries reported values as untyped text (the type lives in the MSD, which the message does not carry), so `int`/`float`/`bool` read back as `str`. SDMX-JSON keeps all five. Now in `KNOWN_GAPS`.

## Left out deliberately

A fifth finding is **filed as #233, not fixed here**: a `Ref` built without an explicit version carries `SdmxUrn`'s `"latest"` sentinel, which stringifies with no `(version)` at all — and SDMX-ML 3.0 requires one. It is not metadata-specific; it applies to every outgoing reference on every artefact, so the blast radius needs measuring before a rule lands. Found because the first MetadataSet target URN I generated used the default and both schemas rejected it.

## Coverage added

`metadata_sets()` and `reported_attributes()` strategies — the latter generating **non-unique sibling ids** (repetition is siblings sharing an id, never a values list) and **recursive children**, the two shapes the model is explicit about — plus a schema-validated round-trip over both formats comparing the whole attribute *tree*, and a `MetadataMessage` completeness guard mirroring the structure-side one.
