#159 added `isFinal` to the SDMX-JSON writer and reader. The format has no such
field — SDMX-JSON encodes the SDMX 3.0 information model, which removed
`isFinal` from every maintainable, and no version of its structure schema
defines one. We were writing a key the standard does not have, readable only by
us.

## Why now rather than never, and why not "it's invalid"

Under SDMX-JSON **2.0.0**, which is what this library emits, objects are open —
a document carrying `isFinal` validates with **zero** errors. Under **2.1.0**
they are closed (`unevaluatedProperties: false`, 134 occurrences; 2.0 has none)
and the same key fails outright.

2.1 support is planned (#364), so this is removed for what it costs on that
upgrade rather than for what it breaks today.

**I reported the opposite first and want that on the record.** I validated
against the vendored schema and called it settled — "empirically proven",
"invalid, not merely non-standard". That schema's own `description` reads
*"SDMX-JSON 2.1.0 Schema for SDMX 3.1 structure messages"*. The version we emit
has no structure schema vendored at all, so nothing in the suite has ever
validated our JSON against it. #364 fixes that and is a prerequisite for the 2.1
work; the comments in this MR state the version-dependent truth rather than the
claim I made.

## Changes

* Writer and reader stop carrying `isFinal`.
* `gaps.TARGETS` gains `json` — it had none, so an SDMX-JSON limit had nowhere
  to be declared, which is part of how this one came to be emitted instead.
* `is_final` declared for `json` alongside 3.0/3.1. The field-coverage register
  *shares* 3.0's list rather than restating it, so they cannot drift.
* `KNOWN_GAPS` gains the json entry, and the cross-check that maps it to
  `declared_gaps()` gains `json` in its serializer table — otherwise the entry
  would have been skipped silently.
* Four tests reversed, each carrying why.
