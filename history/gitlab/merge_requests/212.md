Found while auditing the **SDMX-JSON msgspec migration** milestone (see the milestone note below — all four of its open issues turned out to be already done).

`docs/design/json-and-parsing.md` still described the read side as an open problem:

> The place a recursive JSON type *does* still pay off is the **read/parse** side — `msgspec.json.decode(...) -> Any` (untyped decode) navigated to construct domain objects […] See the parse-boundary work (issue #176): prefer a `TypedDict` per SDMX-JSON section.

All three parts of that are now wrong:

- The untyped decodes are gone. **Every** `msgspec.json.decode` in `src/` carries `type=` (verified by grep, not memory).
- #176 is closed.
- The `TypedDict`-per-section approach it recommends was **rejected**, not implemented.

## What the rewrite records

Two conclusions worth keeping, because the obvious answer was wrong both times:

**The TypedDict proposal became a downgrade.** It was right when the seam was `orjson.loads -> Any`. Once the sections were Structs, a `TypedDict` would only *annotate* a shape that typed decode already *validates* — strictly less checking for the same syntax.

**Typing an envelope changes error behaviour, so it needs its own verification.** Hand-navigation surfaces a malformed message as whatever the first bad subscript raises — in practice `AttributeError: 'list' object has no attribute 'get'`, twice, one of them violating a documented `Raises: ValueError`. Round-tripping valid fixtures cannot see any of that; all 33 valid cases came back identical. Only a diff of *malformed* inputs found it.

Also fixes `metadata.py`'s module docstring, which credited `msgspec.convert` on read — it decodes with `type=` now.

`just ci` green; docs build clean.
