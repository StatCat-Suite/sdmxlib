Closes #256.

`sl.ComponentFilter(dimension_ids=["GEO"], dimensions=[[]])` emitted `geo IN ()`, which DuckDB rejects with a parser error. Reachable from the public constructor, in a module sitting at **100% line coverage** — because nothing executed the fragments it emitted.

Underneath the crash was a semantics contradiction: `parse_components` *dropped* empty lists ("no constraint", match everything), while the literal reading of an empty OR-set is match nothing. Same input, two answers, one of them invalid SQL.

## The decision: match nothing

Not a taste call — four independent reasons pointed the same way.

**`None` already means "no constraint".** `build_component_availability` writes `None` to lift a component's restriction. Reading `[]` the same way gives the library two spellings for one meaning, while the literal reading of one of them is the opposite. They are now distinct and each means the obvious thing.

**Prior art agrees**, measured rather than recalled:

| | empty set | result |
|---|---|---|
| polars 1.41 | `pl.col("a").is_in([])` | empty frame |
| SQLAlchemy 2.0 | `col.in_([])` | `WHERE geo IN (NULL) AND (1 != 1)` |
| SQLAlchemy 2.0 | `col.notin_([])` | `... OR (1 = 1)` — the exact complement |

SQLAlchemy had this argument years ago, used to emit a warning about it, and settled on contradiction.

**It is the relational definition.** `x IN S` is `∃y∈S: x = y`, false for empty `S`.

**It fails safe.** Under "no constraint", a dynamically-computed code list that comes back empty silently returns the entire dataset.

## The change

- `_emit_in_clause` emits `FALSE` for an empty list. SQLAlchemy's extra `IN (NULL)` term buys cross-dialect portability we do not need.
- `parse_components` stops dropping empty lists, so both doors give the same answer.
- The dotted-key merge needs no change and now says why: it is a set *union*, so merging `c[GEO]=` onto `CA.M.2021` leaves `{CA}` alone — it neither widens to everything nor narrows to nothing.
- `is_wildcard` already reported `False` for an empty list, which is correct: it is a constraint, the one that admits nothing. Now documented as such.

## Tests

One test asserted the old drop (`test_parse_drops_empty_attribute_value_lists`) and now asserts the new behaviour. Added: the contradiction on both the dimension and attribute paths, the `None` vs `[]` distinction stated directly, and the union no-op on a dotted key.

The end-to-end test goes through **`DuckDBDataStore.query`** rather than composing a SELECT in the test, so what runs is the production concatenation of binding, where clauses, component filter and binds — not a hand-rolled approximation. The attribute case puts the filtered column on the sidecar, so it also proves the contradiction survives the LEFT JOIN.

That choice is also why this MR adds **no** `# noqa: S608`. Tests deliberately keep S608 on (only `S101` / `S311` are skipped in `ruff.toml`) so each SQL-composing site justifies itself; three existing sites carry a line suppression. Routing through the real query path means this one composes no SQL at all.

## Follow-on

**#261** (`is_in`) explicitly deferred its empty case to this decision — `code.id.is_in([])` should compile to `FALSE` on the same reasoning. Worth noting when that lands, since it is a second emitter with the same trap.

One thing left open, noted in #256 and not addressed here: `_emit_in_clause`'s `SqlRelation` branch will still emit `IN ()` if a relation's `to_sql()` returns an empty string. That is a malformed `SqlRelation` rather than a legal input, so it is arguably caller error — but nothing rejects it, and the generative guard in #258 is where it would surface.
