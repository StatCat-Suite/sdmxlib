Decided on #420: version refusals are `ValidationError`s.

`VersionFormatError(ValueError)` was kept apart on the reasoning that a version one format cannot carry is no defect in the artefact. That is equally true of a multi-measure DSD refused for 2.1, which was always a `ValidationError`. The two rules met in the wire gate over populated artefacts (!517), which had to accept both kinds of exception as a refusal.

## Changes

- **The check moves into `check_serialisable`** (`_check_artefact_versions`), beside every other refusal: accumulated across the message, before any bytes are written, with the field named in `.issues` (`Codelist:CL.version`).
- **The writers keep the same check** for a caller that writes without `serialize`. It is now `model.validation.check_writable` and raises `ValidationError` too.
- **`model/version.py` keeps the grammar.** `unwritable(version, target)` returns the reason or None. It gains 3.1 as a named target, so a 3.1 refusal says 3.1 rather than 3.0.
- **`serialize` rejects an unknown format before validating.** The writability checks have no answer for a format that does not exist; without this, the unknown-format path hit a `KeyError`.
- **The populated gate counts only `ValidationError` as a refusal.**

## Breaking

- Catch `ValidationError` where `VersionFormatError` was caught.
- `model.version.check_writable` is now `model.validation.check_writable`.

## Tests

- `test_a_version_refusal_is_a_validation_error_naming_the_field` replaces the test that asserted the old split.
- `test_serialize_refuses_every_bad_version_at_once_before_writing`: two bad versions produce two issues. The writer-level check alone would stop at the first, so this test fails without the new check.
