Phase 1 of milestone %13. Closes #248 and #249.

`hierarchy_query.py` had 504 statements and no property tests; `code_query.py` had an oracle modelling nine of the DSL's ~25 operations. Both gaps are closed, and the properties found four defects on the way.

## What's here

**A second oracle.** `tests/support/hierarchy_oracle.py` deliberately restates rather than imports the parts that resemble `tests/support/oracle.py`. Two oracles sharing code can be wrong the same way, which is the one failure mode differential testing cannot catch. A node is not a code in any case: it has an id *and* a code reference, levels run parallel to depth, and parentage lives in the tree rather than in a field.

**`tests/unit/test_properties_hierarchy_query.py`** — 27 tests: all eight predicate kinds, the algebraic laws, baked-vs-traversed depth, and oracle self-consistency. `test_every_predicate_kind_is_covered` counts the kinds off the module, so a ninth cannot be added untested.

**The codelist oracle grows from 9 predicates to 24**, and the code_query property file picks up the operations that are not plain columns: both annotation fields (JOIN), both hierarchy-aware predicates (second artefact, second ancestry graph), the depth-bounded transitive walks (correlated subqueries), and the query-level operations `sort_by` / `limit` / `with_annotations` / `get`.

**Two strategies.** `forest_hierarchies` populates the fields the DSL can filter on — a strategy leaving name/level/code/annotations unset makes every predicate over them trivially empty. `codelist_with_hierarchy` pairs the two artefacts with the hierarchy re-parented into a spine unrelated to the codelist's forest, and node ids deliberately unequal to the code ids they reference, so a compiler assuming `node_id == code_id` fails rather than passes.

Checked that the cross-artefact strategy is not vacuous: over 300 examples, 134 gave a proper subset for `code.hierarchy(h)` and 180 had hierarchy ancestry differing from intrinsic ancestry.

## Four defects

**Fixed here — `.any(depth=n)` bounds were parsed and dropped.** Both sub-refs accepted a `depth`, stored it on the predicate, and were compiled by emitters that never read it, so `narrower_transitive(depth=1).any(p)` matched at any distance. Four emitters across the two DSLs. All four now bound the hop count as a difference of the baked `depth` column. Regression test in each property file, on an `A → B → C → D` chain where the right answer for *n* hops is exactly the *n* nodes above the match.

**Fixed here — two oracle bugs, both found only at 20× width.** A negative slice (`chain[len(chain) - hops:]`) that dropped the root when the hop bound exceeded the chain length; and modelling `code_query`'s label matching as a plain `ILIKE` when it deliberately folds accents and punctuation. Hypothesis found the second with a name fragment of `":"` — a needle made only of punctuation folds to the empty string and matches every non-null label, which no hand-written example would have tried.

**Filed, not fixed — #254.** Annotation predicates compile to an inner `JOIN`, so an item carrying two annotations of one type is returned twice by `ids()`, `collect()` and `len()`, in both DSLs. The fix is a correlated `EXISTS`, but the join is part of the published `sl.CompileContext` contract that pinaxlib composes against, so it does not belong in a test-coverage change. Pinned by `xfail(strict=True)` in each property file; the issue lists exactly what to restore when it lands (two set comparisons back to list comparisons, one strategy draw restored).

**Filed, not fixed — #255.** `code_query` folds accents and punctuation in label search; `hierarchy_query` does not. `name["en"].contains("Montreal")` finds *Montréal* on a codelist and nothing on a hierarchy holding the same label. That is a semantics decision, not a patch — and it should probably be taken before #250/#251, whose tests would otherwise encode the inconsistency by accident. The issue also records that the `"St Johns" ~ "St. John's"` example in the `_LABEL_NORM_REGEX` comment does not hold.
