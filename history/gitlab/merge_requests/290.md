The issue reported 15 KB of SQL and 5001 binds for a 5000-code `is_in`, blaming statement size, plan quality and cache-key size. Measured, it is none of those — it is **parameter binding in DuckDB's Python client, ~48 µs per value**:

```
SELECT 1, no params                          51 µs   fixed per-call cost
5000 bound params                       245,765 µs
same-length SQL, inline literals          3,574 µs   69x faster, same text size
EXPLAIN (binds, never executes)         254,811 µs   not parsing, not planning
one list param `= ANY(?::VARCHAR[])`    241,110 µs   per *value*, not per placeholder
```

```python
with reg.session() as active, active.value_set(ids) as wanted:
    codes.filter(sl.code.id.is_in(wanted)).collect()

5000 ids:  180,004 µs  ->  1,438 µs
```

`register` is flat — the same ~48 µs for 100 values or 1,000,000 — because it hands DuckDB an Arrow pointer instead of marshalling objects one at a time. **Crossover is at about four values**, not the ~100 the issue guesses, so the docs now present a value set as the default for `is_in`.

## No change to `is_in`

It has accepted a `SqlRelation` since #261; what was missing was a way to make one from a list. A constructor, not a new DSL path — hence the **byte-identical SQL corpus**.

## The reserved design question dissolves under scoping

#271 called "registration needs a lifetime" the real content. All three failure modes — outliving the query, a fixed name letting callers clobber each other, a lazy query separating registration from execution — come from a *gap* between register and free. A block has no gap: generated name, relation exists only inside, `finally` frees it on error.

And inside the block `to_sql()` is **self-contained**, so a compiled query naming the relation can be handed to pinaxlib and executed. An automatic threshold registering at execution could never offer that. The automatic path is filed separately as #301, where the crossover of four makes "a threshold" really mean "always" — a much larger change that breaks `to_sql()` and interacts with #270's key.
