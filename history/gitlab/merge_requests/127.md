## Summary

First batch of the #159 **Table B** follow-ups: closes the DuckDB storage
gaps the property guard exercises. These are fields the storage *writer*
received but the schema had no column for, so they were silently lost on
`put_artefact -> get_artefact`.

## Closed

- **Concept `core_representation` Facet detail** — `min_value`,
  `max_value`, `decimals`, `pattern`, `is_sequence`, `start_value`,
  `end_value`, `is_multi_lingual`. The `concept` table previously stored
  only `text_type`/`min_length`/`max_length`.
- **DSD component Facet `is_multi_lingual`** — the `dsd_component` table
  had every other facet field but this one.
- **Attribute relationship** — `related_dimensions` (SERIES),
  `related_measure` (observation), `related_group` (GROUP). The first two
  had no column; `related_group` was computed then written as `NULL`.
- **Contact `faxes` / `x400s`** — `agency_contact` carried
  phones/uris/emails only.

## How

Add the columns (schema `2.2 -> 2.3`), wire the writer and reader, and
remove the now-closed entries from `KNOWN_GAPS` in the round-trip
property guard. The guard's `xfail(strict=True)` markers **proved** each
gap closed: after the fix they XPASSed (strict → failure), which is the
signal to delete the marker.

Guard is back to green: `75 passed, 12 xfailed` (was 68/19). Added
`test_storage_facet_relationship.py` to pin the relationship variants the
guard doesn't exercise (GROUP / observation attachment) and the full
component Facet.
