First group worked down from #355. One bug turned out to be four, in both
directions, plus one fact about 2.1 that dissolved a dozen more register
entries.

## Writing it where the schema forbids it

* **3.0/3.1 have no `isFinal`.** `gaps.py` declared this a limit back in #159
  and `write_maintainable_attrs` set the attribute regardless. A
  `CategoryScheme` with `is_final=True` produced a document the 3.0 XSD rejects
  outright. Nothing caught it because no test combined the flag with XSD
  validation — fixtures that set it were not validated, validated fixtures did
  not set it.
* **2.1 pins it to `false` on the organisation schemes** (`fixed="false"` on
  AgencyScheme / DataProviderScheme / DataConsumerScheme). Writing `true` fails
  validation just as surely, and is easier to miss because the attribute *is*
  there. A genuine limit, now declared.

## Not reading it back where it does exist

* **2.1, eleven of seventeen maintainables.** The writer emitted it for
  everything; the reader read it for six. An `isFinal="true"` codelist
  round-tripped and an otherwise identical concept scheme came back `false`.
* **SDMX-JSON, seven ingest functions.** Same shape, same fix.

## One XSD fact wearing fifteen hats

2.1 derives `Hierarchy`, `RepresentationMap`, `StructureMap`, `ConceptSchemeMap`
and `CategorySchemeMap` from **`NameableType`, not `MaintainableType`** — they
are not maintainable artefacts in 2.1 at all. The containing
`HierarchicalCodelist` or `StructureSet` is, and carries the version and
validity. SDMX 3.0 promoted all five, which is why the model gives them these
fields.

`is_final`, `valid_from` and `valid_to` across those five looked like fifteen
separate bugs and are one sentence about the 2.1 information model. Declared in
`gaps.py`.

**Register: 2.1 51 → 46, SDMX-JSON 29 → 23.** Every surviving `is_final` entry
is now a declared format limit rather than an unexplained loss.

## Deliberately not done

SDMX-JSON emits an `isFinal` key the official structure schema does not define —
zero occurrences, against twelve each for `validFrom`/`validTo`. Dropping it is
defensible and was half-written here before I reverted it: #159 added it on
purpose, four tests encode that decision, and it is a behaviour change that
should be chosen rather than arrive as a side effect of a different fix. #358
asks the question. What this MR does instead is make the existing choice
*consistent* — writer for all, reader for some was defensible under neither
answer.

## A correction to !407

Its real-world `KNOWN_LOSSES` had forty entries and tolerated nothing. Measured:
every message in the corpus round-trips with **zero** differences. I had copied
the list from the unit register assuming real data would hit the same bugs, and
real publishers simply do not populate those fields — the BIS hierarchy carries
`is_final=False` and unnamed nodes.

That list was worse than none: it read as forty known losses when there were
none, and it would have swallowed a regression introducing any of them. It is
now empty and the assertion is strict.

The honest bound is now stated in the file: it catches a regression in any field
the corpus populates (deleting `Code.description` fails three cases) and cannot
catch one in a field no provider fills. The unit census covers those. Neither
replaces the other.
