## The field never carried information — in any version

| Version | What the wire carries | What we stored |
| --- | --- | --- |
| 2.1 | `<PrimaryMeasure><Ref id=…/>`, but the XSD **pins `@id` to `OBS_VALUE`** and permits exactly one measure | `"OBS_VALUE"` — a constant |
| 3.0 / 3.1 | nothing: the `AttributeRelationshipType` choice is `Dataflow \| Dimension+ \| Group \| Observation`, and `<Observation/>` is `common:EmptyType` | `"OBS_VALUE"` — fabricated |
| SDMX-JSON | nothing (follows the 3.0 IM) | `"OBS_VALUE"` — fabricated |

Every 3.0/3.1/JSON reader returned a hard-coded `return AttachmentLevel.OBSERVATION, None, "OBS_VALUE", None`, presenting an invented id as though it had been read. Round-tripping a DSD whose measure is named `MEAS` yielded an attribute relating to a measure that DSD does not contain.

2.1 looks like the case that justifies keeping it, but `validation._PRIMARY_MEASURE_ID_21` already encoded the rule: 2.1 fixes the id. So the value is a constant restating `AttachmentLevel.OBSERVATION`.

Constant where it was real, fabricated everywhere else. The issue offered three options and all three assumed the field should exist; the measurement says it should not.

## Both reference implementations agree

Neither stores a measure id **even for 2.1**:

- **sdmx1** — field-less marker classes (`v21.PrimaryMeasureRelationship`, `v30.ObservationRelationship` are `pass` bodies) and reconstructs from `dsd.measures[0].id` when writing 2.1, with a literal `"(not implemented)"` fallback.
- **pysdmx** — collapses 2.1's `<Ref id="OBS_VALUE"/>` and 3.0's empty `<Observation/>` to the same `attachment_level = "O"`.

pysdmx's SDMX-JSON writer *does* hard-code `mr = ["OBS_VALUE"]`, ignoring the DSD's actual measure ids and disagreeing with its own XML writer — that is the same defect this MR removes, not a convention to follow.

## What changes

Removed: the model field, `dsd_component.related_measure`, the `q.dsd_component.related_measure` accessor, and the `gaps.py` entry — a declared 3.0 limit that no longer describes anything, because nothing is lost.

The 2.1 writer still needs a measure ref and now emits `_PRIMARY_MEASURE_ID_21` imported from `model.validation`, rather than a local literal falling back off the artefact. One source of truth: `validate` already refuses a 2.1 DSD whose measure is named anything else, and two copies of the constant could drift into disagreeing about what 2.1 permits.

`SCHEMA_VERSION` 2.12 → 2.13. Neither the SELECT nor the INSERT names the column any more, so an existing store stays readable — which is precisely why the bump is needed, or the dead column would never be rebuilt away.
