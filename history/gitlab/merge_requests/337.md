The aggregate set was count / n_unique / list / unique — enough for
counting artefacts, useless for measuring observations. Both surveyed
consumers hand-write `f"{agg_func}(OBS_VALUE)"` for exactly these four.

Named for polars like the rest of the set, so `mean` compiles to SQL's
`avg` the way `n_unique` compiles to `count(DISTINCT …)`.

**`min` and `max` are not numeric aggregates**, which is why they are
usable on structural metadata where `sum` and `mean` are not: SQL and
polars both order text, so `children.id.min()` is a code's
alphabetically first child.

Two behaviours pinned rather than assumed:

*Nulls are skipped, not counted as zero* — the mean of [10, NULL] is 10.
SQL and polars agree here, which is worth asserting precisely because
#326 records a case where they do not, so "they agree" stays a fact
about this operation rather than a rule to lean on. A facet's
`max_length` is the nullable numeric column that can show it.

*A windowed aggregate totals its partition and does not accumulate.*
`sum(v) OVER (PARTITION BY g ORDER BY v)` is a running total, so the
four join the existing aggregates in emitting no window ORDER BY —
otherwise `x.sum() / x.sum().over()`, the percent-of-total shape %15
asks for, would be a share of a prefix. The exclusion set is now a named
constant with that reasoning attached.

Summing text is refused by DuckDB, not by us: the compiler carries no
column types. Stated in the docstring, the page and a test rather than
left for a user to discover, and #327 keeps the question of whether we
should know better.
