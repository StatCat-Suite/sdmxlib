## Decisions (asked)

SDMX 3.1's `AvailabilityConstraintType` extends `AnnotableType`. It has no id, agency, version or name: one attachment (exactly one of DSD, Dataflow or PA), one cube region, and optional `seriesCount` / `obsCount`.

- **Model:** `DataConstraint` keeps its role. A new `AvailabilityConstraint` value class, not maintainable, is held in a new `StructureMessage.availability_constraints` slot. It is outside every artefact list and outside `all_artefacts()`.
- **Actual → 3.1:**
  - **Fits** (one attached structure/flow/agreement, one included region, no data keys): written as an `AvailabilityConstraint` via `to_availability_constraint()`. Its identity is a declared `sdmx_class` gap, and it reads back as an AvailabilityConstraint.
  - **Doesn't fit:** still refused, and the message now names why (`availability_misfits()`).
- **AvailabilityConstraint → 2.1 / 3.0 / JSON / store:** left out and declared. `dropped()` names each one by its target, since it has no URN. SDMX-JSON 2.1 has `availabilityConstraints`, but JSON 2.0 doesn't, and our output validates against both.

## How

- **3.1 reader:** `read_availability_constraints` builds or refuses each element alone, refusals named by position (`AvailabilityConstraint[n]`). The read-accounting guard skips that container, since its elements have no identity to account by.
- **v3 writer:** new `availability_constraint` generation flag (3.1 only), an `<AvailabilityConstraints>` section, and the conversion. The writer leaves out what its own target lacks: `without_dropped(msg, gen.target)`.
- **gaps.py:** the 3.1 `constraint_type` row becomes `sdmx_class` (identity lost on conversion), and a new `AvailabilityConstraint` row covers 2.1, 3.0, JSON and storage.
- **validation:**
  - `_check_constraint_in_31` refuses only an Actual constraint that doesn't fit;
  - new `_check_availability_in_31` covers attachment and inclusion.
