Closes #319.

`_check_version` implemented SDMX-ML 2.1's `VersionType` verbatim while the library reads and writes 3.0 too, and the two grammars are **not nested** in either direction:

    both      1.0   1.10   1.0.0   0.0.1
    2.1 only  01.0  1.03   1.2.3.4
    3.0 only  1.0.0-draft   1.0.0-alpha.1

So a conformant 3.0 artefact versioned `1.0.0-draft` could not be stored at all, and a 2.1 artefact versioned `1.2.3.4` was written into 3.0 documents that fail their own schema.

## No tag on the artefact

The original proposal was to classify at parse and carry the result. Dropped, because compliance is a pure function of the version string — storing it stores something derivable, the drift this codebase keeps paying for. The check needs *(version, target format)*, both present at the write boundary. What only the parser knows — which format an artefact arrived in — is provenance, and is not what the error is about.

## So the enforcement splits

- **`validate()` takes the union.** A store is format-agnostic. Deliberately looser than either grammar — it accepts `1.2.3.4-draft`, which conforms to nothing — and that is the trade, because the writer is where the question has an answer.
- **Writers refuse what their format cannot express**, naming the version, the format, and the format that *can* express it.

```
cannot write Codelist A:CL as SDMX-ML 2.1: version '1.0.0-draft' is not valid
there — it conforms to SDMX-ML 3.0; write that format instead, or re-version
the artefact.
```

This follows precedent rather than inventing one: `sdmx_ml21/writer.py` already raises "...has no measures, which SDMX-ML 2.1 cannot represent — Add a measure, or serialise to 3.0".

The writer is demonstrably the right boundary: the XSD round-trip tests already failed on this, as a schema violation in a test with no message a user would ever see.

## Details

- `VersionFormatError` is its own type, not a `ValidationError`: a conformant artefact being unconvertible is not a defect in it.
- The patterns are literals in `src` because the XSDs are test-only and excluded from the wheel, so `test_the_patterns_match_the_vendored_schemas` re-derives them from the vendored schemas and compares.
- Two things caught while wiring: `ReaderHelpers` and `WriterHelpers` share an `__init__` docstring so the first edit landed on the reader; and 3.0/3.1 carry their own `_write_maintainable_attrs` beside the shared helper.

## Behaviour change

Converting a `1.0.0-draft` artefact to 2.1 now raises where it previously emitted invalid XML.
