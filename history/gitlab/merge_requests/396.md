Two silent wrong answers, found by an independent audit of the query
language and verified before either was believed. Neither had a test.

**#350 — `~col.is_in(subquery)` returned nothing.** `NOT IN` over a set
containing one NULL is UNKNOWN for every row, so the anti-join selected
no rows at all — not wrong by a few, empty. The positive form was correct
on the same data, so nothing looked broken.

    is_in(used)   -> ['CL_FREQ', 'CL_GEO']   correct
    ~is_in(used)  -> []                      expected ['CL_UNUSED']
    .difference() -> ['CL_UNUSED']           correct, on identical data

`difference()` was right because `_row_in` already emitted `NOT EXISTS`;
the negated `InRelation` path just never reached it. Now compiled as
`NOT EXISTS (SELECT 1 FROM (…) AS alias(value) WHERE …)`. The subquery's
column is renamed by `AS alias(value)` rather than parsed out of its SQL.

The `IS NOT NULL` guard is on the **left**, deliberately. A NULL in the
subquery is what the rewrite fixes. A NULL on the left is the separate
question, and the answer is the one the cookbook already documents for
columns: a row whose value is NULL satisfies neither `p` nor `~p`.
Without it the two forms would stop partitioning in the other direction.

This matters more than the shape suggests: `is_in(subquery)` is how you
ask what the edge graph exposes in only one direction — "codelists
nothing uses" — and those run against nullable foreign keys by nature.

**#351 — `agg(version.max())` answered `1.9` over `1.10`.** The aggregate
took the raw text column while `order_by`, `desc()` and `rank()` route
through the baked `version_sort`, so the library contradicted itself
about which version was latest. #311's fix reached three sites and missed
the fourth. Now `arg_max(version, version_sort)` — the version, not its
sort key, since that is what the caller asked for. Narrow by construction:
only a column whose `sort_column` differs from itself is rerouted, so
plain text aggregates are untouched.

"The latest version of each artefact" is the commonest query a versioned
catalogue has, and `group_by(id).agg(max(version))` is the first thing
anyone writes for it.

Tests are differential where a second implementation exists: the anti-join
against `difference()`, `version.max()` against `order_by(version.desc())`
— two independent answers to "which is largest", whose only useful
assertion is that they converge. Both suites verified to fail against the
un-fixed compiler.

Found on the way and filed, not fixed: #352 (edge targets resolve by
class-definition order, so 17 paths dead-end and file order is public
API) and #353 (the oracle's `strip_accents` model disagrees with DuckDB
on 527 characters, failing a property at 20x on main — pre-existing).
