`uri` was read by nothing and written by nothing, so every round-trip dropped it. Found by the document-fidelity harness: the ECB's data structure links to the bank's statistics vocabulary, and that link was the last non-structural difference left in the corpus.

It is declared on SDMX's `IdentifiableType`, not `MaintainableType`, so this is forty model classes rather than one field. Doing only the maintainables would have closed the two observed losses while leaving item-level uris silently dropped, so this does the whole surface.

The seams worth reviewing:

- **SDMX-JSON has no `uri` field.** External pointers go in `links`, whose `rel` is an RFC 5988 relation, and `self` is reserved for the artefact's own URN. `@uri` is documented as *"a link to a resource with additional information about the object"* — exactly `describedby`, which the SDMX-JSON schema lists among the permitted relations. The writer's `rel="metadata"` back-links now **append** to that array rather than replacing it, which would have dropped the uri.
- **`ReportedAttribute` carries the field and no format can write it** — `AttributeType` extends `AnnotableType`, not `IdentifiableType`. Noted at the writer rather than left looking like an oversight.
- **DuckDB storage carries it on the artefact spine only.** Item and component tables would each need a column, and the store is a cache with a drop-and-rebuild migration rather than a wire format — so the boundary is deliberate and `KNOWN_GAPS` asserts it. Schema 2.4 -> 2.5.

Guarded three ways: the generative strategies do not draw a uri (adding one to forty strategies would state the property where it is least likely to be read), so new properties set it explicitly on every registered artefact, on items, and on DSD components, across all four formats. Both fidelity harnesses' `@uri` entries are gone — `_KNOWN_LOSSY` is now empty and the four ECB cross-version hops convert.
