## Typed

- **`StructureMessage.all_artefacts()` / `MetadataMessage.all_artefacts()`** →
  `list[MaintainableArtefact]`. Public API that returned `list[Any]`, so every
  caller's loop variable was untyped from a *typed* method.
- **`writers.py`, ~19 sites** → `list[list[object]]` for the DuckDB
  bulk-insert rows. Values go in, the batch goes to pyarrow, nothing reads back.
- **`sdmx_ml21.writer`** — the map-collection list is
  `list[MaintainableArtefact]`, `_write_level_chain` takes `Sequence[Level]`.

### Typing the writer rows found a latent bug

`_to_arrow_array` narrowed the column's first non-null **sample** to `dict`,
then called `.items()` on every **element**. A mixed column type-checked and
failed with an `AttributeError` from inside pyarrow, nowhere near the artefact
responsible. Narrowing per element turns that into a named error.

## Documented, with the measurement behind it

- **`readers.py`, 10 sites.** Converting the row tuples to
  `tuple[object, ...]` produced **36 errors**, every one a value needing a
  narrowing on its way into a constructor parameter the *schema* already
  guarantees. Those narrowings would restate the schema in Python and go stale
  against it. Now written at the module.
- **The two section tables.** Each entry pairs a getter and a writer at a
  *different* artefact type; storing them in one list erases it. Python has no
  existential types, so `Sequence[Any]` is the honest encoding — and
  `section_entry[T]` keeps the halves consistent at construction, where it
  matters. Bounding `T` to `MaintainableArtefact` was **tried and rejected**:
  one 2.1 section legitimately passes the *message* itself, since 2.1 wraps
  hierarchies in a single container.
- **`_data_common.py`** already carried its reason.
