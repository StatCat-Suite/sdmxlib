MR-1 of the SDMX-JSON conformance work. Pure infrastructure — no writer / reader / fixture changes. Sets up the schema-based validation foundation that MR-2 (issue #128) will use to land actual conformance fixes.

## Summary

- Vendors the official SDMX-JSON 2.1 schemas (structure / metadata / data) from \`sdmx-twg/sdmx-json\` at tag \`v2.1.0\`, under \`tests/schemas/sdmx_json/2.1/\`. Single self-contained JSON Schema documents per message kind (draft 2019-09), ~340 KB total.
- Adds \`tests/support/json_schema.py\` with \`compile_json_schema()\` + \`assert_valid_sdmx_json()\` — mirrors the existing \`tests/support/xsd.py\` helper for SDMX-ML.
- Uses jsonschema's \`FORMAT_CHECKER\` so \`oneOf\` over \`{format: date, format: date-time}\` actually discriminates by format. Without this, the upstream sample fails to validate against its own schema due to overlapping format matches.
- Vendors the upstream constructed sample at \`tests/schemas/sdmx_json/2.1/samples/\` so the smoke test pins the validator to a known-good payload (regression net for the support helper).
- Adds \`jsonschema>=4.21.0\` to dev deps.

## What this MR does *not* do

Wire validation into the existing JSON writer round-trip test matrix. Doing so today would surface 14–25 errors per fixture — real conformance bugs, but not the right scope for a vendoring MR. Filed as **#128**: writer + reader + fixtures fix together.

Surface-level summary of the bugs found:

- **\`items\` vs named arrays**: schema wants \`codelist.codes\`, \`conceptScheme.concepts\`, etc.; we emit \`items\` everywhere.
- **\`isFinal\`**: emitted by the writer but not present in the SDMX-JSON 2.1 spec at all.
- **\`name\` vs \`names\`**: spec splits the istring into \`name\` (string) + \`names\` (i18n dict); we conflate them.
- **\`dataStructureComponents\`**: DSD components shape doesn't match the JSON spec.
- Plus a latent fixture bug (\`name_fr\` field in \`with_groups.json\`).

See #128 for the full breakdown and the proposed fix shape.
