**Phase 3 of milestone 11 — closes #229.** The conformance gate's `KNOWN_INVALID` is **empty**: every artefact sdmxlib models, in every wire format, either produces a schema-valid document or is refused with a reason.

## The triage split 6 / 18, and the split matters

The two halves need opposite fixes, which is why #229 asked for the decision before the code.

**Six were writer bugs** — an element or JSON key that is *itself optional*, emitted empty instead of omitted:

- `<ConstraintAttachment>` is `minOccurs="0"` in all three SDMX-ML versions **and** requires one of its target elements when present. So an attachment naming nothing must be left out; the writers emitted a bare wrapper. (4 pairs)
- SDMX-JSON's `dataProviders` and `metadataStructureComponents` are optional but carry `minItems`, so an empty scheme or MSD must omit the key rather than write `[]`. (2 pairs)

No new refusals for these: the artefacts are perfectly legal, they were just written wrongly. Had I treated them as missing rules — the obvious reading of "schema rejects a bare artefact" — sdmxlib would now refuse six things it should happily emit.

**Eighteen were missing write-boundary rules**, now a table in `validation._REQUIRED_CONTENT`: a hierarchy with no codes, a DSD with no dimensions, a map with no source or target, a hierarchy association with no links.

## Rules stated in src, verified against the schemas

`_REQUIRED_CONTENT` has to live in `src/` — the vendored XSDs are test-only and `sdmxlib.model` may not depend on them. So the direction of trust runs the other way: `test_required_content_rules_agree_with_the_schemas` checks the table against `xsd_facts.required_children` and `required_choices`, **in both directions** — a rule the schema does not support fails, and so does a schema requirement no rule covers.

That check earned itself immediately, finding three errors in my first draft: two rules that excluded 2.1 where the schema requires them anyway, and a `RepresentationMap` rule citing elements that type does not have. A RepresentationMap is written as a 2.1 `<CodelistMap>` with `Source`/`Target` ends but a 3.x `<RepresentationMap>` with a `SourceCodelist|SourceDataType` choice — same model field, two entries, different elements.

It replaced the cross-check against `KNOWN_INVALID`, which was the right anchor while that table had entries and became **vacuous** the moment this change emptied it. A test that passes because its input is empty is worse than no test.

## Controls

Five mutations, each verified to fail: drop a writer's guard, drop a rule, narrow a rule's versions, widen them, revert the JSON omit-when-empty.
