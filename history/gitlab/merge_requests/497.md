`Dataset.validate` is documented as returning a report of coded values outside
their component's codelist, and both its docstring and the `Dataset` class
example reached it through `scan_csv`. That path cannot produce a non-empty
report: `scan_csv` builds the schema from the DSD, so an enumerated component is
a `pl.Enum` over its codelist and a bad value is a **parse error on read**. The
report came back empty or the call raised.

Worse, the raise is *partial* — it stops at the first bad value, so a file with
400 bad codes across three columns tells you about one.

    slpl.scan_csv(path, dsd).validate()
    # ComputeError: could not parse `XX` as dtype `enum` at column 'AREA'

    slpl.scan_csv(path, dsd, coded_as="string").validate()
    # [{'column': 'AREA', 'invalid_value': 'XX', 'count': 2},
    #  {'column': 'AREA', 'invalid_value': 'YY', 'count': 1}]

Both source kinds, path and bytes, which is how #408 reported it.

## Why a third name rather than a borrowed one

`coded_as` lives on `slpl.schema` — where the `pl.Enum` is made — and both
`scan_csv`s forward it, so there is one decision site rather than two.

Polars has no fitting name to borrow, checked rather than assumed:
`ignore_errors` **nulls** unparseable values, which loses the thing the report
is about, and `strict` is cast vocabulary, not read vocabulary. Naming ours
after either would mean something else to a polars reader. `coded_as` names the
decision it makes, and extends if a third typing ever earns its place.

The default does not move. The two answer different questions and #408 is right
that both are wanted: `"enum"` asks *is this file usable at all* — cheap,
fail-fast, correct for a pipeline — and `"string"` asks *what exactly is wrong
with it, and how much*, which is what you need when a supplier sends a bad
extract and you have to tell them what to fix.

## The docs half

* `Dataset.validate` now says its report is vacuous after a default `scan_csv`,
  which was the path its own docstring used, and names the option that fixes it.
* The `Dataset` class example gains the `coded_as="string"` line for the same
  reason.
* The wrapper's "For full options see `scan_csv`" pointed at *itself* —
  mkdocstrings resolved it to the wrapper, so it rendered as a working link to
  the function you were already reading. It now names
  `sdmxlib.formats.sdmx_csv.reader.scan_csv` and says what that one has which
  this does not.

## Guards

9 tests, and the ones that matter are the negatives: the default still raises,
the default schema is still `pl.Enum`, and a *clean* file reads identically
under both settings — that last is the discrimination check, since `coded_as`
must change the dtype and not the data. Sabotage-checked by ignoring the
parameter: five of the nine fail.

Two assertions are on docstrings, which is unusual and deliberate. The
self-reference defect is invisible in rendered docs — it renders as a working
link — so a text assertion is the only thing that can see it.

## Observed, not changed

`validation_report`'s row order is not specified: two reads of the same file
came back in different orders. The tests compare sets. Worth knowing before
anyone writes a doctest against it, and worth its own decision rather than
riding in here.
