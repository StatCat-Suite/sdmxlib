The API-shape issue found while assessing release readiness (#363), plus the
escape it needs.

## The change

```python
reg.query(q.codelist).select(q.codelist.id, q.codelist.agency).collect().columns
# before: ['resource_id', 'agency_id']
# after:  ['id', 'agency']
```

29 distinct accessor/column mismatches across the 34 roots, concentrated on
`id` (17 relations) and `type` (17), plus `position → ordinal`,
`role → component_type`, `source → source_value`.

`AnyCol.projected_name` had argued for the old rule — someone porting a
hand-written `SELECT code_id …` gets a frame needing no renaming. The deciding
argument against it is that **`ObsCol` already overrode the same property in the
opposite direction**, and said why: *"the physical name is an implementation
detail of the binding … getting back a column called `GEO` leaks the layout"*.
Two conventions on either side of one `select()`. Now one.

`reg.sql()` and `sl.schema` still name physical columns — that is what that seam
is for.

## `alias()`

Not a nicety — it is what makes the rename safe. Two columns projecting to one
name are refused (already true, now more reachable). At a `select()` the keyword
form resolves it. Inside `Many.list()` it could not: positional by design, and
its struct fields take the columns' projected names, so two `id`s were a
`BinderException` with no way out.

```python
codes.list(codes.id, codes.parent.id.alias("parent"))   # fields: id, parent
```

## What was considered and rejected, with the evidence

**Auto-namespacing by path** (`parent_id`, `dsd_id`). Fails twice: one segment
does not disambiguate — `dsd.dimensions.concept.id` and
`dsd.attributes.concept.id` both end in `concept` — and for the motivating case
there is no segment at all. `codes.parent.id` and `codes.id` share the path
`('codes',)`, because the parent hop *trims* to a same-row column. The
`parent_id` that reads naturally there is the storage name, which is what we are
removing.

**`.name.prefix/suffix`.** Measured on polars 1.41.1: it exists because one
polars expression can expand to many columns, where `.alias()` is impossible —
`pl.all().alias("z")` raises `DuplicateError`, `pl.all().name.prefix("x_")`
works. On a single column the two are identical. Every projectable thing here is
exactly one column (`select` refuses an accessor, refuses a bare aggregate), so
a rule could only ever be a longer spelling of `alias`. Adding it would be
deviation dressed as alignment.

polars' answer to a duplicate is `DuplicateError` + `alias`. That is now this
API's answer too.

## Fallout

36 unit tests moved. All but six were expectation updates; the six are real
collisions the rename surfaces, each resolved by naming one side — including one
in the SQL corpus, which now carries `alias` as well as the shape.

Docs updated where they taught the old rule: `structures_as_frames.md` and
`discovery.md` both explained the storage-name convention as deliberate, and
`upgrading.md` gains a section — this is the change most likely to bite an
upgrader, because column access is string-keyed and fails at runtime rather than
at type-check.
