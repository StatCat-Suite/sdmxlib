## `unique()` was impossible on any collection with a natural order

`Frame.to_sql` already dropped the row-level **default** order for a grouped frame, with a comment explaining exactly why — `position` is not a group key, so carrying it into a `GROUP BY` is a binder error rather than a preference. `unique()` fails identically and had not been given the same treatment:

```python
cl.codes.select(sl.q.code.depth).unique()   # PathError
```

and there was **no spelling that worked**: `order_by()` with no arguments clears the *caller's* keys and falls back to that same default. Fixed by extending the existing condition to `group_keys or distinct` rather than adding a second rule.

Scope: this needed a root carrying a `default_order`, and only a collection like `cl.codes` has one. `reg.query(q.code).select(...).unique()` always worked. Nothing REST-specific.

An order the caller *asked* for is still refused, and its message already names the fix — so both halves are tested: the default order is dropped, a decision is not.

**Found by writing the page.** The snippet I wrote first was the obvious one, it did not run, and the driver said so — which is the argument for executable cookbook entries stated in #278, arriving on schedule.

## `unique()`'s no-arguments decision, documented with its reason

A subset form would not commute with `filter` (`filter(keep).unique(agency)` and `unique(agency).filter(keep)` differ), and it leaves which row of each group survives unspecified. Polars takes `keep=` for exactly that reason, and a lazy query has nowhere to put the choice. `group_by(...)` is the answer, and the page points there.

## Also: §11's projection claim, run rather than asserted

Everything backing §11 was a boolean — `can_project()` said a projection *would* be servable. `test_projection_and_aggregation_work_over_rest` runs one: `select`, `unique` and `group_by` over a REST-fetched store, **one request**, computed locally. Added while checking whether the `unique()` bug was REST-specific; it was not, but nothing asserted that projection worked over REST at all.
