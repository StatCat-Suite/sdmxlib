Closes #397. Options 1 **and** 2 from the issue — they turned out to be
complementary rather than alternatives.

## The defect

```python
h = reg.get(sl.Hierarchy.urn_for(agency="AG", id="H"))
h.codes          # type-checks as Hierarchy.codes — AttributeError at runtime
```

`get` is generic over the URN's phantom, so `SdmxUrn[Hierarchy]` gave
`Hierarchy | None` while a `LazyHierarchy` came back — and that class has no
`codes`, `tree` or `descendants` at all. The codelist half is the same shape and
milder: `codes` exists on both and differs only in *type*, so `len(cl.codes)`
type-checked and raised.

## Both halves

**Overloads** — three: the two roots that come back lazy, plus the generic form
every other artefact still takes.

```text
reg.get(cl_urn)              # LazyCodelist | None   (was: Codelist | None)
reg.get(cl_urn, eager=True)  # Codelist | None
reg.get(h_urn)               # LazyHierarchy | None  (was: Hierarchy | None)
reg.get(dsd_urn)             # DataStructure | None  — unchanged
```

`eager=` selects between them, which is *why* overloads rather than a changed
return type: the flag decides the class, and one declaration could not describe
both branches. A `Ref` reaches the same overload a URN does, so traversal is not
typed differently from a lookup.

**Refusal by name** — `__getattr__` on both lazy classes answers a
materialised-only member with the counterpart to use, mirroring what a `Query`
already does for `len()`:

```text
>>> reg.get(h_urn).codes
AttributeError: a lazy hierarchy has no `codes` — it is a plan, not a
materialised tree. Use `.nodes` for the query over every placement, or
`.materialize().codes` for the ItemList.
```

A genuine typo still gets the ordinary message.

## One interaction that nearly cancelled the change

A `__getattr__` a type checker can **see** makes *every* attribute resolve to its
return type — so `h.codes` type-checked again and the overloads bought nothing.
The two halves silently cancelled. It sits under `if not TYPE_CHECKING` for that
reason, verified by re-running the must-not-type-check cases:

```
error: Cannot access attribute "codes" for class "LazyHierarchy"
error: Cannot access attribute "tree" for class "LazyHierarchy"
error: Cannot access attribute "descendants" for class "LazyHierarchy"
error: Cannot access attribute "add" for class "LazyCodelist"
```

The source comment says so, and `test_the_refusal_is_live_at_runtime` stops the
method being deleted as apparently-dead code.

## Guards

`tests/unit/test_lazy_return_types.py` (15 tests) compares each real class
against its lazy one in **both** directions: a member added to `Codelist` /
`Hierarchy` and not to the lazy class fails unless it is refused by name or
listed as class-level-only, and an entry in the refusal table that stops being
missing fails too (it would silently never fire).
`tests/typing/probe_local_get.py` carries the static half.
