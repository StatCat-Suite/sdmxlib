## Fixed — all 2.1, all one-sided

Each was a writer and a reader disagreeing about a field the schema plainly
allows, which is exactly why none showed up as invalid output:

| Field | What was wrong |
|---|---|
| `MetadataAttribute.is_presentational` | reader read it, **no writer emitted one** |
| `MetadataAttribute.enumeration_format` | writer emitted it, **nothing read it back** |
| `Level.min_value` / `max_value` | writers emit them since #354/#364; the 2.1 reader never asked |
| `HierarchicalCode.level` | handled by 3.0 and 3.1, by neither half in 2.1 |

The last needed care: `<Level>` goes **last** in `HierarchicalCodeType`'s
sequence, after the nested codes, and 2.1 wraps the reference in a `<Ref>` where
3.0 uses text — the same split as `Parent`. The reader resolves it against the
hierarchy's own levels, as 3.0 always has, so a node carries the `Level` object
rather than a dangling id.

## Declared — both 2.1

`CodelistType` is a restriction admitting only Annotations / Name / Description
/ Code, so `Codelist.extensions` (a 3.0 feature) has nowhere to go. 2.1's single
`PrimaryMeasureType` admits only Annotations / ConceptIdentity /
LocalRepresentation, so a measure's `concept_role` has none either — roles on
measures arrived with 3.0's several measures.

## One entry remains and it is not a defect

`MetadataAttribute.children[].representation` is
`_ComponentMixin.__attrs_post_init__` inheriting the concept's
`core_representation` — SDMX's own rule. It appears because the fixture's
concept `Ref` is unresolved while the reader's is resolved, so the inheritance
fires on one side only. Nothing was lost on the wire, and it is listed with that
reasoning rather than declared as a gap.

## #355 is done

**4 defects → 1**, and that one is documented as not being one.
