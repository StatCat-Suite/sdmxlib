| --- | --- |
| State | merged |

Closes #221 — the asymmetry noted in !221. SDMX string types **are** XSD types, so a value XML cannot represent has no valid SDMX-ML form in any version. The library accepted such values in two places and only complained at the very end.

| Boundary | Before |
| --- | --- |
| SDMX-ML read | rejected by lxml (`XMLSyntaxError`) |
| **SDMX-JSON read** | **admitted** |
| direct construction | admitted |
| **`validate()`** | **did not notice** |
| `serialize()` (validates by default) | validate passed, then a raw lxml `ValueError` with no field path |

So the same logical message was loadable as JSON and not as XML, and an artefact built in code failed only at XML-write time with an error naming nothing.

## Two boundaries, catching different inputs

**`validate()`** — checks every name on every `NameableArtefact`, alongside the existing "name is required" rule. The lever: `serialize()` runs `validate_message()` by default, so an lxml stack trace becomes a `ValidationError` naming artefact, field and language — for *every* format, including the nastier case of data that writes as JSON and could never be written as XML at all.

**`ingest_istr`** — rejects on the SDMX-JSON read path, restoring parity with the XML reader (which lxml already enforces). Strict at the read boundary, as #190 established for non-conformant references; `SdmxConformanceError` is the existing type for exactly this.

They are not redundant: a surrogate can only arrive by construction, and a malformed producer payload only arrives by reading.

## The ban set is derived, not transcribed

`test_forbidden_set_matches_lxml` asserts our constant against **what lxml actually accepts**, across every code point below 0x100 plus the surrogate and noncharacter boundaries. So the constant and the XML spec cannot drift.

That check earned its place immediately: **DEL (U+007F) and NEL (U+0085) are legal in XML.** A "not printable" rule — the obvious implementation — would have rejected valid SDMX documents. The set is exactly XML 1.0's, no stricter.

## What the properties found

Stated over the *whole* forbidden range rather than a few sentinels, and that paid off on the first run: **lone surrogates are not encodable as UTF-8**, so no SDMX-JSON payload can carry one and no reader can ever see one. `json.dumps` and our own JSON writer both raise `UnicodeEncodeError`. They reach the model only by direct construction — which makes `validate()` their *sole* boundary.

The reader properties are therefore scoped to the wire-reachable subset, with the reason recorded next to the strategy rather than left as an unexplained exclusion.

## Cost

Measured before choosing the read boundary, since it is a hot path: **~150 ns per string; 22 ms for the 78k-code StatCan geography codelist** — noise against parsing it. `frozenset.isdisjoint` short-circuits, and only allocates the offending character on failure.

## Verification

**Non-vacuous by mutation**: neutering `_first_xml_incompatible` to `return None` fails 4 of the new tests. A charset test that passes whether or not the check runs would have been worthless here.
