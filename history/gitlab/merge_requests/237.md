**Phase 4 of milestone 11 — closes #230.** Three findings, all in the one blind spot nothing else in the suite can see.

## Why the prohibited half matters most

A prohibited attribute must be **dropped** by any correct writer, so the output validates *because* the value was discarded. Schema validation is satisfied. A round-trip only compares fields somebody thought to list. So this class of bug is invisible to every check the project already had — which is the argument for enumerating them from the schema rather than waiting to trip over one.

## Findings

**1. Organisation-scheme version was silently lost in 3.0 and 3.1.** `OrganisationSchemeBaseType/@version` is `use="prohibited"` in both, so the writers correctly omitted it and the reader supplied `"1.0"`. Our own error message for the 2.1 case claimed the loss was *"valid in 3.0 and 3.1"* — exactly backwards: 2.1 merely **fixes** the attribute where 3.x **forbid** it. Now refused in every SDMX-ML version; SDMX-JSON has no such restriction and round-trips it.

An existing test asserted the wrong belief and passed, because `serialize` did succeed — it never checked whether the value survived.

**2. A Level's CodingFormat lost facets in 2.1 that the schema permits.** `CodingTextFormatType` prohibits only `decimals` and three time facets; `minLength`, `maxLength`, `pattern` and the value bounds are all allowed — and the 3.0 writer had been emitting them all along. The 2.1 writer dropped them behind a comment asserting they "aren't permitted". They are. 2.1 is now at parity, and only `decimals` is recorded as lost.

**3. `CodingFormat/@textType` accepted any `DataType`.** It is `SimpleCodeDataType` — Alpha, AlphaNumeric, Numeric — in every version, because a coding format describes the *shape of a code*, not a value domain. Emitting `String` there produced a document all three schemas reject.

## How 2 and 3 were actually found

Not by the extraction — by **a control that would not fire**. Mutating the 2.1 writer to emit `maxLength` changed nothing observable. Chasing that showed the `KNOWN_GAPS` entry I had *just written* was wrong about what the schema prohibits, and fixing the fixture to be otherwise-valid then exposed the `textType` restriction.

## The inventory

All 82 prohibitions are classified: three map to a model field, the rest are grouped into named type families with a written reason each. Grouped rather than enumerated because each family is mechanically uniform — the same attribute prohibited across a dozen sibling restrictions — and sixty identical sentences would bury the three that matter. A family still has to be *named*, so an unfamiliar type from a schema refresh fails the check.

## Controls

Six mutations, each verified to fail — **after clearing `__pycache__` every time**. `git checkout` restores an older mtime, so Python reuses bytecode compiled from the mutated source and a control silently reports a false result. That happened twice here before I noticed it, and both affected controls were re-run.
