# Merge request !345: perf(query): an unordered stream is bounded — 441 MB to 5 MB (#329)

Breaking down `stream`'s memory to answer "how do we size chunk_rows"
found that chunk_rows was the wrong question.

Measured on 4M rows of three columns, peak RSS above the loaded table:

    collect()                       441 MB
    stream(chunk_rows=1_000)        210 MB   <- before this change
    stream(chunk_rows=50_000)       210 MB
    stream(chunk_rows=500_000)      236 MB
    raw SQL, sorted,   50_000       212 MB
    raw SQL, unsorted, 50_000         5 MB

Chunk size did nothing across two orders of magnitude. **The `ORDER BY`
was the entire floor**: a sort materialises the whole result before the
first batch can leave, so an ordered stream is unbounded — 85 MB at 1M,
210 MB at 4M, 368 MB at 8M, growing about 46 MB per million rows.

And the sort was ours, not the caller's. Every query carries a key
tiebreak so `limit`/`offset` paging is stable — a scan order that changes
between calls silently skips and repeats rows. A stream reads everything
once, so it buys nothing there. `stream` now drops it unless the caller
asked for an order or sliced, the latter because *which* rows a `limit`
returns depends on the order.

    stream(), unordered, 4M          5 MB
    stream(), unordered, 8M          5 MB

Flat in row count, which is what bounded means, against `collect()`
roughly doubling. So `chunk_rows` should be sized for the consumer — a
writer's batch, an HTTP chunk — and 10k to 50k costs nothing measurable.

The docstring carries the table, because the number a caller sizes a
container on has to be the measured one. Two earlier attempts at
measuring it are worth not repeating: `tracemalloc` sees only Python
allocations and reported 0.02 MB for both paths, and building the
fixture from 400k model objects put peak RSS at 1 GB before the query
ran, so the query never moved it.
