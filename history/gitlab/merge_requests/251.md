Closes #254.

An item carrying two annotations of one type came back twice — from `ids()`, `collect()` and `len()`, in **both** query DSLs. Found by the #248 differential properties on a generated hierarchy whose single node carried two annotations of the same type. Two annotations of one type on one item is legal SDMX, not a pathological input.

## The change

Annotations live in a side table, so reaching them needs a second relation. It was an inner `JOIN`, which multiplies rows. It is now a correlated `EXISTS`:

```sql
EXISTS (SELECT 1 FROM sdmx.annotation c_ann
        WHERE c_ann.owner_urn = c.code_urn
          AND c_ann.annotation_type = ?
          AND c_ann.title = ?)
```

**No row membership changes.** The behaviour was always existence-scoped — the join being inner meant an item with no annotation of that type was absent from the result even under `!=` — so `EXISTS` states directly what the join achieved as a side effect. `tests/support/oracle.py` and `hierarchy_oracle.py` already modelled it that way, which is why the differential properties pass unchanged.

## Three consequences

**The join plumbing is gone.** `join_sqls` / `join_params` / `annotation_join_aliases` threaded through six functions per module to serve the only three emitters that used them. No emitter needs them now, so `_emit_predicate` and its callees lose three parameters each, and `hierarchy_query._compile` no longer splices a FROM-clause segment. Net −384/+400 lines with the tests included; the compilers are smaller.

This also dates part of the `# noqa: C901` rationale on `_emit_predicate`, which argued a dispatch table would force three dead parameters onto eight emitters. That is no longer true and the comment now says so — the suppression stays on the remaining argument, not the retired one.

**Annotation predicates now work inside `.any(...)`.** The guard in `_emit_subquery_predicate` rejected them because "they would require annotation joins inside the EXISTS subquery". Not true any more, and an unreachable `raise` carrying a false explanation is worse than either fixing or keeping the restriction. Removed, with a test that a node matches on its *parent's* annotation and does not self-match.

**`CompileContext` needed saying out loud.** `sl.CompileContext` is public and pinaxlib composes against it; its documented contract was that annotation predicates append joins. sdmxlib now writes to none of the accumulators. `_compile` still splices `ctx.join_sqls` — another producer sharing the pass may add joins, and splicing an empty list is a no-op — and `sql.py` now documents that sdmxlib contributes nothing, with an explicit "do not read an empty `join_sqls` as *compilation did not run*".

This is backward compatible for consumers: anyone splicing the accumulators keeps working, they just receive an empty list from our predicates.

## Tests

The obligations #254 listed, all of them:

- Both `xfail(strict=True)` guards flip to real tests — repo-wide xfailed goes 6 → 4.
- The two annotation properties return to exact list comparison from the set comparison that was covering for the duplication.
- Annotation predicates go back into the draw in `test_filter_result_is_an_ordered_subset`.
- New per DSL: a structural test asserting no `JOIN sdmx.annotation` survives, that there is one `EXISTS` per annotation predicate, and that the annotation *type* is bound rather than inlined.
- New per DSL: coverage of the newly-possible `.any(...)` nesting.

Two existing tests asserted the old contract directly (`..._records_join_in_ctx`, `..._shares_ctx_across_multiple_predicates`) and now assert the new one. The second surfaced something worth keeping: two annotation predicates differing only in type produce **byte-identical SQL**, because the type is a bind parameter — which is precisely the invariant #257 proposes to assert corpus-wide.

## Follow-on

This was the prerequisite for **#262** (real `And` / `Or` / `Not`): a join-filtered row set cannot be placed under an `OR`, because the join has already dropped the rows the other branch would need. With `EXISTS` it composes. That unblocks the %14 phase-3 work.
