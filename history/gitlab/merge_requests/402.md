Follow-up to !401, from asking what the status of `valid_from`/`valid_to`
actually was rather than assuming exposing the column finished the job.

End to end it was fine — parsed from 2.1 and 3.0, stored, queryable,
read back, round-tripped both ways, declared lost nowhere. But the same
field read two ways disagreed:

    reg.get(urn).valid_from                     -> tz-aware UTC
    query(...).select(valid_from).collect()     -> naive

which neither compare nor subtract, and both look like the right answer.

The store is UTC-naive by convention and `readers` re-attach the zone on
the way out — `storage/_time.py`'s round-trip table says so explicitly:
*naive in, aware out, same wall time, now labelled*. The projected frame
handed back the raw column and skipped that.

Labelled in polars rather than in SQL because `AT TIME ZONE 'UTC'` yields
a TIMESTAMPTZ that DuckDB renders in the *session's* zone — measured:
`2020-01-01 00:00:00` came back as `2019-12-31 19:00:00-05:00`, which is
exactly the machine-dependence #321 exists to remove. `replace_time_zone`
labels without moving the value, which is what the convention says.

`Temporal` as a column class, which is the part I got wrong first time
round. These were declared `Num` — correct for comparing and ordering,
and carrying no way to tell a frame that a value is an instant, which is
the whole difference. I had written that a temporal class was "worth
having when something needs date arithmetic"; something needed it sooner,
for a reason I had not thought of.

It derives from `Num` so the ordering operators come with it, and had to
move below `Num` in the file to say so — the same definition-order
constraint #352 was about, met from the other side.

Guarded on the null path too: most artefacts state no end, so `valid_to`
is null for nearly all of them, and a column-wide operation is where
nulls get dropped.
