## Summary

Phase 5 of #75. Replaces #78's per-call cursor design with a thread-local cursor — lazily created on first call per thread, reused for the thread's lifetime (psycopg2-style). Same correctness contract as #78 (no cursor sharing across threads), but the cursor lifecycle cost amortises across the thread's many reads instead of recurring per call.

Recommended release: **v0.28.1** (internal change, no public API surface moves).

## What changed

- **`Registry._read_cursor()`** — plain method (not contextmanager) returning the calling thread's cursor via `self._thread_local`. `__init__` initialises the threadlocal; `close()` replaces it so reopen starts fresh. All call sites flattened from `with ... as cur:` to `cur = self._read_cursor()`.
- **Lazy facades** (`storage/lazy.py`, `model/code_query.py`, `model/hierarchy_query.py`) — module-level `threading.local()` holds a per-thread `WeakKeyDictionary[Connection, Cursor]`. WeakKeyDictionary keying lets entries GC automatically when a Registry's connection becomes unreachable — no stale-cursor hazard from `id()` reuse.
- **`readers.py`** — same WeakKeyDictionary-backed thread-local for `code_map` / `code_map_for_dsd` (which can be called with either a cursor or a connection — both work as weakref keys).
- **`DuckDBDataStore`** — `query` switches to thread-local; `query_stream` stays per-call because the generator can be iterated alongside a fresh `query_stream` on the same thread (aliasing a cursor would break both streams).
- **Test infrastructure** — `_instrument` in `test_storage_query_bounds.py` clears the registry's `_thread_local` so `CountingCursor` sees subsequent reads.
- **`docs/design/concurrency.md`** — rewrites Read safety + Performance notes for the thread-local model; new Cursor lifecycle subsection covering the invariants tested in `test_cursor_lifecycle.py`.

## Lifecycle invariants pinned by `tests/unit/test_cursor_lifecycle.py`

- 1 thread × N reads uses exactly 1 cursor.
- N threads × M reads create N cursors total, not N×M.
- `close()` drops the threadlocal; reopen creates a fresh cursor.
- Lazy-facade `WeakKeyDictionary` releases entries when a Registry closes and is GC'd.
- 200 ephemeral threads doing one read each don't pin cursors past thread death.

The result that matters and that motivated #80:

| workload | main (#78 per-call) | this branch | delta vs main | vs v0.27.2 baseline |
|---|---:|---:|---:|---:|
| **`code_map`** | **278 µs** | **232 µs** | **-16.5%** | **main: +26% → branch: +6%** |
| `reg.get(df_urn)` | 965 µs | 920 µs | -4.7% | +16% → +11% |

**The +25% `single_code_map` regression flagged in #78 is essentially closed** — branch is now +6% over baseline, down from +26% on main. That was the workload most sensitive to per-call cursor lifecycle (trivial SELECT, cursor open/close dominated), so it's also the workload thread-local helps most.

`reg.get` improves more modestly because cursor lifecycle is a smaller share of its total per-call work. DuckDB's connection-level serialisation still caps real concurrent throughput; pushing further would need a connection pool (separate ticket if it ever comes up).

### Concurrent throughput — bench too noisy to claim

I tried to measure `concurrent_cache_hit_32w` and initially reported a +9% improvement, but a re-read of the same bench output gave very different numbers (the harness swings 50%+ run-to-run on a busy laptop). On this hardware the workload isn't measurable cleanly enough to claim a directional change either way. Errors stay at 0 across the board, which is the important invariant.
