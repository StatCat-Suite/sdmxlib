Closes #279.

`Dimension.concept` is declared `Ref[Concept] | None`, and attrs accepts a bare `Concept` at runtime. The writer's

    str(x.urn) if isinstance(x, Ref) else None

read as "no reference" and meant "no reference **or** something I did not recognise", so passing the item itself stored `concept_urn = NULL`. The artefact validated, round-tripped, and had simply lost the edge — concept-driven discovery then answered `[]` against a catalogue that plainly used the concept. It bit a fixture in this repo while writing the REST executor tests.

## The audit answered a question the issue could only guess at

The issue said *"`representation` may have it too"*. It does not, and the reason is the general rule:

- A converter **can** wrap a bare *maintainable*, whose urn is self-contained. `representation` does exactly that with a `Codelist`, so it never had the bug.
- It **cannot** wrap a bare *item*: a concept's or a code's urn needs the parent scheme the field does not carry, so those converters pass an item straight through and the writer met it holding something it could not turn into a urn.

So the surface is precisely the item-valued fields — `Component.concept` and `HierarchicalCode.code` — and both now raise. The `representation` arm is kept as a backstop for a genuinely wrong type, with a comment saying it is not the bug. (I first wrote a test asserting it *should* raise; the test failing is what surfaced the converter.)

## One field deliberately left alone

`RepresentationMap.source` / `.target` accept a `MapDataType`, which is legitimate and dropped **knowingly** (#131). Folding it into the check would have turned a documented gap into an exception.

## The message

    Dimension.concept must be a Ref or None, got Concept. Writing it would store
    NULL and lose the reference silently. Build one with Ref[T].unresolved(urn) —
    an item's urn needs its parent scheme, e.g. SdmxUrn(package=...,
    artefact_class='Concept', agency=..., id=<scheme id>, version=...,
    item_id=<item id>).

The reason a caller passes the item is usually that they *have* it and the `Ref` looks like ceremony — and for an item it genuinely is not obvious, since the urn needs a parent scheme that is nowhere in scope at the call site.

The distinction restored is *absent* versus *malformed*: `None` is still a real answer, and a test says so.
