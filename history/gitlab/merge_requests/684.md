Step 5b of #516: **`reg.scan_json(source) -> ObsQuery`**, on `LocalRegistry` and `RestRegistry`. It is the SDMX-JSON counterpart of !683's `scan_csv`.

**How it reads a message:**
- **Either version.** The new `formats/sdmx_json/data.py` tells 1.0 from 2.0 by the envelope: 2.0 nests everything under `data`, 1.0 keeps `dataSets` / `structure` at the top level. Only that key is decoded (`msgspec.Raw`).
- **Finding the dataflow.** It is the message's `rel="dataflow"` link: on the dataSet, where our writers put it, otherwise on the structure block, where some providers put it. The data DTOs now decode `links`. `data_v1` / `data_v2` gain `read_observations(source) -> (frame, dataflow urn)`, and `read_sdmx_json_data` now goes through it.
- **Resolving it.** Same as `scan_csv`. `LocalRegistry` uses `get`. `RestRegistry` makes one "dataflow + descendants" fetch and reuses the flow if it already holds it (the REST test checks there is only one request across a CSV scan and a JSON scan).
- **Loading the rows.** JSON doesn't stream, so the rows are decoded and loaded once as a table in `sdmx_scans`. They are cast with the same `column_types` as a CSV's view, so a measure sent as `"10"` compares as a number.
- **Refusals:** a message with no dataflow link, or one naming a dataflow the registry doesn't hold.

**Tests** (now in `test_scan_registry.py`, renamed from `test_scan_csv_registry.py`, 25 in total):
- a JSON message reads as its CSV does, for both versions × path/bytes;
- a link on the structure block is found;
- a measure sent as text is typed;
- both refusals.

Two sabotage checks: without the cast, the text-measure test fails; without the structure-block fallback, both structure-link tests fail.
