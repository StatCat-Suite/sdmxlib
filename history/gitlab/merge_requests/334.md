`list` keeps duplicates and `n_unique` counts them away to a number.
Neither answers *which* values a fan-out holds, so that one question had
to leave the language: collect everything, dedupe in polars afterwards.

`unique()` is the third corner, on a column and on a fan-out accessor,
mirroring `list()` in both places — single column gives a plain list,
several give a list of structs deduplicated over the whole struct. It
frames with `.over()` like the other aggregates, and joins `count`,
`n_unique` and `list` in taking no window ORDER BY, since an aggregate
given one acquires a running meaning.

Both names are polars': `Expr.unique()` and `DataFrame.unique()` divide
values from rows exactly as `Col.unique()` and `Projection.unique()`
now do. That split is imported rather than invented, which is also why
`n_unique` stays — polars keeps both, because `count(DISTINCT x)` is one
pass and counting a materialised distinct list is not.

Checking it against polars found something else, and it is filed as #326
rather than smoothed over: polars counts a null as a value, so
`len(s.unique()) == s.n_unique()` holds there. Ours inherits DuckDB's
two rules, which disagree — `list(DISTINCT x)` keeps the null and
`count(DISTINCT x)` does not count it — so the two answers differ by one
on any column with nulls. `unique()` did not create that; it made it
visible. The test asserts today's behaviour and cites the issue.

The cookbook's aggregate table said "exactly three" and its driver
asserted it, which is the guard working: both now name four, and the
new driver case runs the table's three claims rather than restating
them.
