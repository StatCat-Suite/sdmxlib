## The duplication, removed by construction

"Which hierarchy applies to this component, in this dataflow's context" had two implementations: `_partition_associations` walking objects here, and two `LEFT JOIN`s plus a `COALESCE` in pinaxlib. They already disagreed on ambiguity — we raise, it silently takes any.

Schema **2.18** states the rule once, in the DDL:

```sql
CREATE VIEW hierarchy_applicability AS ...
  row_number() OVER (PARTITION BY dataflow, dsd, component
                     ORDER BY scoped DESC, association_urn) AS rank
```

`LocalRegistry.applicable_hierarchies` and `unique_hierarchy` read it, so SQL and Python are the same rows by construction. The differential test stays, because `InMemoryRegistry` still walks objects — two backends is exactly when that check earns its keep.

```python
a = sl.q.hierarchy_applicability
reg.query(a).filter(a.rank == 1).select(flow=a.dataflow.id, comp=a.component.id, hier=a.hierarchy.id)
# CPI_FLOW    REF_AREA  GEO_CPI     ← scoped association wins
# TRADE_FLOW  REF_AREA  GEO_STD     ← inherits the unscoped default
```

## Ambiguity: dissolved, not decided

Every applicable hierarchy is a row; precedence is a `rank` column. So a relation never has to raise lazily — `rank = 1` is the winner and a caller who wants the conflict can see it. `unique_hierarchy` still raises, now only within the **winning tier**: a scoped association beating an unscoped one is a resolution, not a conflict.

## The fetch expands (as agreed)

A view has no endpoint. A root declaring `__derived_from__` becomes one request per source relation — `hierarchyassociation`, `dataflow`, `datastructure` — all bounded by the same agency. That is why the view projects `agency_id`: the alternative was making a caller reach through the dataflow hop for the one equality that bounds all three. Previously the planner refused the root with advice written for *item* relations ("root the query at the owner"), which is nonsense for a derived one.

An unbounded derived scan is still refused, and there is a test for it.

## Four things a view broke

Each a real assumption, not a nuisance:

- **The tiebreak guard.** DuckDB cannot declare a key on a view. Not exempted — `VIEW_TIEBREAKS` names a test proving uniqueness on data built to break it (two flows sharing a DSD, two associations on one component, a second DSD repeating the component id), plus a test that the pointer still resolves.
- **`ALL_TABLES`** split from a new `ALL_VIEWS` rather than widened — a view declares no constraints and is never written to.
- **`_table_names`** read `information_schema.tables`, which lists views, so the view read as a *missing table*. Filtered to `BASE TABLE`.
- **The value-set leak check** counted every non-internal view to prove a temp view was freed. It was asserting "no views exist", true only by accident. Scoped to `_sl_values_%`.
