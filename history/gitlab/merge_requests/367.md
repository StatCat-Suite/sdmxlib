§6 step 7 of `docs/design/registry-and-catalog.md`. Scheduled as a tidy-up; it turned out to be a **regression fix**.

## What was broken

Step 3 made an observation query project by component id. The writers still read their column order off the *binding's* physical names, so any renamed binding raised:

```
KeyError: Record batch is missing column(s) ['geo', 'v'] declared by the binding.
          Available columns: ['REF_AREA', 'OBS_VALUE']
```

— naming columns the batch was correct not to have.

**No test failed.** Every writer fixture in the suite used an identity binding, where the physical name and the component id coincide. The absence of a renamed-binding fixture is the whole reason this shipped.

## The change

The structure is now the single source of both the column order and the envelope's component ids, so the two cannot disagree.

- `write_sdmx_csv(batches, dsd, …)`
- `write_sdmx_json_data(batches, dsd, dataflow_ref, …)` — the ref only for the dataflow link and display names, which is all the binding was consulted for there
- `_data_common.resolve_columns(dsd)`, `dataflow_link(Ref[Dataflow])`, `display_names(dataflow, dsd, lang)`
- `polars.sink_json` stopped synthesising an identity binding it built purely to hand over a column map that was the identity map anyway

## Guard

Two tests in `test_registry_data_plane.py`, whose fixture already renames `REF_AREA`→`geo` and `OBS_VALUE`→`v`:

- one pins the writer against a renamed binding
- one streams the query into the writer, so the halves are checked *joined* — neither half alone would have caught the break, since the query's own tests assert its column names and the writer's fixtures never renamed anything

Both kill a reordered-columns mutant and a lowercased-ids mutant. Verified they fail against the pre-change signature.
