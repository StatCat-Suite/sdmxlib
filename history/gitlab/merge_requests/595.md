Closes #465.

**The problem.** pysdmx 1.20.0 refused every structure message sdmxlib wrote ("Cannot parse input as SDMX-JSON"), although each was valid SDMX-JSON 2.0. pysdmx recognises a JSON message by `meta.schema` alone, and reads only the **first 350 characters** to find it. Our structure writer left the field out. It's optional in 2.0, but BIS, FMR and pysdmx all write it, and so does our own data writer.

**The change.** The writer puts the 2.0.0 structure schema's URL first in `meta`. `schema` is now the first field of the shared `Meta` struct, so it falls inside a reader's window.

**Which URL, for review:**
- **This MR uses the schema's own `$id`,** `https://raw.githubusercontent.com/sdmx-twg/sdmx-json/master/structure-message/tools/schemas/2.0.0/…`. That matches how our data writer cites its schema.
- **That URL no longer resolves:** the repository's `master` dropped its versioned folders.
- **The resolvable copy is at `https://json.sdmx.org/2.0.0/sdmx-json-structure-schema.json`.** It still declares the GitHub `$id`, and it's what **FMR itself writes**. pysdmx accepts either.
- Switching to `json.sdmx.org` is a one-line change if that's preferred. The data writer would then follow, for consistency.

**Tests** (`tests/unit/test_json_meta_schema.py`), all three failed against the old writer:
- the value equals the vendored schema's `$id`;
- it lies within pysdmx's 350-character window;
- with pysdmx installed (the `bench-compete` group), pysdmx reads what sdmxlib writes. It ran in this `just ci`.
