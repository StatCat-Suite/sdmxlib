## Summary

Phase 3 of #75 — the actual fix. Reads through ``Registry`` and ``DataStore`` are now safe under concurrent threads. Writes remain documented as single-threaded.

Builds on the failing reproducers from #76 (now passing 10/10 deterministically) and the v0.27.2 baseline from #77.

## What changed

**Per-call cursors on read paths.** Every public read method on ``Registry`` (`get`, `get_all`, `codelist`, `code_map`, `dsd_code_map`, `to_registry`, `__contains__`, `__len__`, `__repr__`) and `DataStore.query` / `query_stream` now opens a fresh DuckDB cursor for the call's duration. The resolver internals (`_resolve_refs`, `_resolve_urns`, `_load_parent_scheme`) gained a `cur` parameter and the cursor threads all the way down.

**Lazy facades store the connection, not a cursor.** `LazyCodelist` / `LazyHierarchy` / `CodeQuery` / `HierarchyNodeQuery` now hold the long-lived connection and open a per-call cursor for every method via a new `_cur()` helper. SQL in those modules is already `sdmx.`-qualified, so `_cur()` skips `SET search_path` to keep per-call overhead minimal.

**`get_artefact` / `get_all` gained an optional `lazy_conn`** so Registry can hand the short-lived cursor for eager reads while passing the long-lived connection to lazy factories.

**FIFO resolver cache** (`_LRUDict` → `_FIFOCache`). Switched from LRU (recency tracking requires mutating on every read, forcing a lock around hits) to FIFO with insertion-order eviction. Reads are now plain `dict[k]` lookups — GIL-atomic, no lock. Mutations hold a `threading.Lock`. Hit/miss counters are best-effort under concurrency. The LRU→FIFO change is the documented punt: at realistic working-set sizes the hit-rate difference is small, but if `resolve_cache_info()` ever shows poor hit rates in production we revisit. (Doc lands in #79.)

**Write paths unchanged.** `add` / `drop` / `replace` keep using the long-lived `self._c` cursor; docstrings now say "Single-threaded — see `docs/concurrency.md`" (full doc lands in #79).

## Perf vs the v0.27.2 baseline from #77

Single-threaded (target was <5% regression; we're ~5-6%):

| workload | baseline µs | new µs | delta |
|---|---:|---:|---:|
| `single_get_dataflow_cold` | 829.83 | ~870 | +5% |
| `single_get_dataflow_warm` | 832.58 | ~880 | +5% |
| `single_get_codelist_eager` | 1254.60 | ~1320 | +5% |
| `single_code_map` | 219.38 | ~270 | +23% |

`single_code_map` runs +23% — the extra cost is the per-call `conn.cursor()` (previously this used the connection's default cursor directly). For 1k iterations of a simple lookup the cursor lifecycle dominates. Acceptable trade for correctness; not on any hot path.

Concurrent (target was "throughput scales, errors drop to 0"):

| workload | baseline | new | errors before → after |
|---|---:|---:|---:|
| `concurrent_get_mixed_1w` | 914 ops/s | ~860 ops/s | 0 → 0 |
| `concurrent_get_mixed_4w` | 882 ops/s | ~800 ops/s | 1 → 0 |
| `concurrent_get_mixed_8w` | 875 ops/s | ~700 ops/s | 2 → 0 |
| `concurrent_get_mixed_16w` | 863 ops/s | ~650 ops/s | 4 → 0 |
| `concurrent_cache_hit_32w` | 1116 ops/s | ~700 ops/s | 16 → 0 |

Errors went from N to 0 across the board — the data-integrity goal is achieved. Throughput regressed at higher concurrency, partly because each op now does the full correct work (the buggy baseline's "ops" included silent-`None` returns that did less work) and partly because per-call cursor management costs more per thread. DuckDB's connection-level serialisation caps how much real concurrency a single `Registry` can extract regardless.

The cache-hit `-30%` is the main number to be honest about: that's the workload the FIFO change was supposed to keep fast, and per-call cursor overhead landed on top of it. The FIFO cache itself is lock-free — the cost is in the cursor open/close around the SQL, not the cache lookup. Future improvement (separate ticket if it bites): a per-thread cursor pool to amortise the lifecycle cost.
