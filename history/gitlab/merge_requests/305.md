Closes #307.

SDMX-ML 2.1 and 3.0 both allow `<str:Parent>` on a `Concept` — the XSD calls it
*"the semantic relationships between concepts which occur within a single
concept scheme"* — and this library parsed the element and threw it away. A
scheme whose concepts nest came back **flat**, on read and on round-trip write.

## Why it survived, which is the part worth reading

`sdmx.concept` had a `parent_id` column from the start. The writer put a
constant `NULL` in it, nothing read it back, and `Concept` had no parent field
at all. The DDL implied a capability the model never gained — and **an
un-populated column is an absence; absences do not fail tests.** Every
individual leg looked fine on its own. It surfaced from an inventory of
un-wired traversals during %306, not from anything going red.

So the fix crosses every leg, and so does the test: a check of any single hop
would have passed throughout the bug's life.

## What lands

| | |
| --- | --- |
| model | `Concept.parent_id` — *flat with a reference*, like `Code` |
| SDMX-ML | both readers (shared `read_parent_id`), both writers |
| SDMX-JSON | DTO field + ingest |
| storage | constant `NULL` replaced; `depth` / `ancestor_ids` baked |
| query | `q.concept.parent` / `children` / `ancestors` / `descendants` / `depth` |

The issue said "matching `Code`/`Category`", but `Category` **nests** while
`Code` uses `parent_id`. The 2.1 XSD declares `Parent` as a
`LocalConceptReferenceType` *reference*, so `Code`'s shape is the correct one —
and the storage column already assumed it.

The 2.1 `<Ref>` / 3.0 text split is now read by one helper shared with
`Code.Parent`. It was inline in `read_codelists` and concepts had no equivalent
at all, so the next item type to gain a parent cannot quietly get a different
one.

Ancestry is baked at write time like the other three trees, which is what makes
`ancestors` a declared edge rather than a verb — this language does not emit
recursive CTEs. `q.concept.parent.id` trims to the local column, so there is no
join and exactly one spelling.

## The ordering trap

`Parent` sits on `ConceptBaseType` and `CoreRepresentation` on the extension,
so the XSD sequences **Parent first**. The first cut of this emitted them the
other way round — producing a document this library's own reader accepts and
every validator rejects, which is precisely the writer bug pure round-trip
testing cannot see. `test_concept_parent.py` validates against both XSDs with
both elements present.

## Two stale records corrected

- `NOT_EDGES` called `concept.parent_id` "dead" and explained that we flatten
  concepts like pysdmx.
- `docs/design/query-tree-paths.md` §7 said fixing it was "not done".

Both were accurate when written and are now wrong, so both are updated rather
than left to mislead. The `_Concept` accessor's three annotated tree names —
copied from `_Code` before any of this, binding nothing, raising
`AttributeError` when used — are correct for the first time.

## Breaking

- `Concept` gains a `parent_id` field, so positional construction after
  `core_representation` shifts.
- `SCHEMA_VERSION` 2.6 → 2.7; the store is a cache and rebuilds.
