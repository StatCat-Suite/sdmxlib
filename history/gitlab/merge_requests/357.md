Step 4 of `docs/design/data-plane-pushdown.md`. It got *smaller* once the
standard was consulted rather than reasoned around.

## The standard already has an opinion

SDMX-REST defines **413 "Request entity too large"** and **414** as response
codes, and `/data/{flow}/all` is a legal request. So request size is the
**server's** call, with a defined way to say no.

That makes a client-side bound ours to justify, and what it justifiably catches
is narrow: the plan that pushes **nothing** and would fetch a whole dataflow to
filter locally. A plan that pushed something has a fetch the caller named, and
the provider caps the rest.

## Which dissolved the `bounding` problem

`bounding` is a conjunction, and data seemed to need a disjunction — "any key
constraint bounds this". Neither DNF nor wildcard shapes turned out to be
needed. What was needed is a distinction the code did not draw:

```python
required = capability.bounding.get(root_key(...), frozenset())   # before
```

That collapsed **not declared** into **declared as requiring nothing**, so a
backend could say the first and never the second. Three states now:

| state | meaning |
| --- | --- |
| absent | nothing bounds this root — every residual refused |
| present, empty | *any* pushed constraint bounds it — the `/data` case |
| present, non-empty | all of these shapes must be pushed — unchanged |

## Two defects found on the way

**`root_key` read the class, not the instance.** `type(root).__table__` while
every other consumer uses `root.__table__`. Invisible while every root was a
module singleton; wrong for `Observations`, the first root built per binding,
which got the class default — the empty string, **shared by every dataflow**.
Fixed, plus `__resource__` so an observation root names itself `"data"` rather
than being keyed by one dataflow's table.

**A provider's size refusal was discarded.** `raise_for_status()` gave a bare
`HTTPStatusError`: no mention that the fix is narrowing the query, and no way
to catch *this* rather than every HTTP failure. `ResponseTooLargeError` names
the status, the remedy, and the URL — the last because a plan issues several
requests and "which one" is not otherwise recoverable. Anything that is not
413/414 keeps httpx's own error; there is nothing this layer can add to a 500.

The two refusals stay deliberately distinct: `PushdownError` is ours and fires
before a request, `ResponseTooLargeError` is theirs and fires after. Same
remedy, different authority.

## Guards

Mutation-checked: collapsing absent back into empty, admitting an empty push
under the empty bound, and letting 413 fall through are each caught. The
structural capability's bound is asserted unchanged, so the new middle state
cannot reach it.
