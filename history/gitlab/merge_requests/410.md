`MetadataProvisionAgreement` was half-wired: a `MaintainableArtefact`, exported
from `sdmxlib`, with an `ArtefactKind` so the DuckDB store could hold it — and a
`msg_field` naming `metadata_provision_agreements`, a slot no message had.

So `StructureMessage.containing()` raised for it, no structure reader could
produce one, and `Session.ingest` could never intern one. The only code in
`formats/` that mentioned it was the *metadata-message* path, a different
envelope.

## The guard first

`tests/unit/test_message_slots.py` pairs every `MaintainableArtefact` subclass
against the slots the two message types declare, **both directions**: a class
naming a slot that does not exist fails, and a slot no class claims fails too.

Either side alone looks fine. Only comparing them finds a half-wired artefact —
which is exactly why this one survived an audit that enumerated message slots.
It had none, so it was invisible to the method.

## The wiring

SDMX-ML 3.0, 3.1 and SDMX-JSON. **Not 2.1** — `<Structures>` there has no
`<MetadataProvisionAgreements>` child at all, because reference-metadata
provisioning arrived in 3.0. That makes it a refusal, so it joins
`validation._UNWRITABLE` rather than `gaps.py`, which is for silent drops and
says so explicitly.

`targets` changes from `list[Ref[object]]` to `tuple[str, ...]`: the XSD types
them `WildcardUrnType`, so a target may name a whole *class* of artefacts and no
resolvable reference can express that — the same reason `Metadataflow.targets`
is already a string tuple. basedpyright caught the two storage sites still
treating them as refs, which is the checker earning its keep.

## Four other guards fired, each correctly

Adding it to `tests/support/maximal.py` put it under the #354 census, and then:

* `test_ml3_writer_parity` counted a 28th `write_annotations` site against 27 markers;
* `test_xsd_conformance` wanted it mapped to its XSD type, and its two required children mapped to model fields;
* `test_properties_roundtrip` wanted it covered or excused;
* `test_wire_conformance_gate` found that a **bare** one serialises to a document 3.0 and 3.1 reject — `MetadataProvisionAgreementType` requires both `<Metadataflow>` and `<MetadataProvider>`.

`KNOWN_INVALID` is empty, that milestone having burned down, so the last one is
**fixed rather than recorded**: `_check_metadata_provision_refs` refuses it,
mirroring `_check_metadataflow_targets`.

Worth noting how well that worked. Adding one artefact triggered five
independent guards, each naming exactly what it wanted and why. None of them
needed me to remember anything.

## A correction to the census

`_round_trip` now clears what a target *refuses* before writing, reading the
list from `validation._UNWRITABLE` rather than a copy. That removed
`hierarchy_associations` from the 2.1 register, where I had recorded it as a
silent whole-artefact loss. It is not — it is a declared refusal with its own
guard. Declared-unwritable and silently-lossy are different facts with different
mechanisms, and the register is only for the second.

Verified the new paths discriminate: dropping the 3.0 writer's `Metadataflow`
ref, or the JSON reader's `targets`, each fails the census.
