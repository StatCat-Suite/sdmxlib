Closes #290.

## The false claim

`ItemList.__hash__` and `ArtefactList.__hash__` were `hash(self._items)` — which worked for the **empty** list and raised `TypeError: unhashable type: 'Code'` for every populated one. Every domain item is an attrs `@define` class, so mutable, so unhashable. The classes advertised a capability they could not deliver for any type they are actually parameterised with.

`__hash__` is now `None`. The refusal is the declaration, and the error names the collection rather than blaming an item type that is unhashable by design.

## Not hashing the ids

The other option on the issue, and it needs the `__eq__` question answered: it satisfies the contract on paper — equal lists have equal ids — and fails in practice. The items are **mutable**, so a list used as a dict key would keep its hash while `__eq__` changed underneath it, and the dict would stop finding its own entry. `list` is unhashable in Python for exactly this reason. A collection is only as hashable as its contents.

## The messages carried the same claim

Found while checking the blast radius, and fixing only the collections would have left it *worse*. `StructureMessage` and `MetadataMessage` are `@frozen`, so attrs generated a `__hash__` — deliverable only while the message was empty. Left alone they'd have become uniformly unhashable but reported `unhashable type: 'ArtefactList'`, telling a caller about a class they never mentioned.

Both now declare it themselves via `@frozen(unsafe_hash=False)`. `@frozen` is here for immutability, which still holds; hashability was only ever its side effect.

## Two tests changed, both wrong in ways worth naming

- **`test_itemlist_hash` asserted `hash(a) == hash(b)` and passed** — because the `Item` double in that module is a `@dataclass(frozen=True)`. It confirmed behaviour that does not exist for any type the class is used with. Same vacuous-fixture shape as the `<xs:choice>` work in #359.
- **`test_itemlist_hash_raises_for_every_domain_item_type`** pinned the bug deliberately, so the fix would be a visible diff here. It is.

The empty case is asserted alongside the populated one: *"empty hashes, populated raises"* was the inconsistency, and a fix leaving the empty list hashable would have preserved it.

## Approved suppression, with the repro inline

basedpyright rejects `__hash__ = None` in every spelling, including the fully annotated `ClassVar[Callable[..., int] | None]`:

```python
class A:
    __hash__: ClassVar[Callable[..., int] | None] = None
# error: "__hash__" overrides method of same name in class "object" (reportIncompatibleMethodOverride)
```

It is the documented idiom (CPython, `dataclasses`, `attrs`) and the **only** one that makes `isinstance(x, Hashable)` answer `False`. The type-checkable alternative — a `__hash__` that raises — passes the checker and then lies:

| form | `isinstance(x, Hashable)` |
| --- | --- |
| `__hash__ = None` | `False` ✅ |
| raising `__hash__` | `True` ❌ |

Measured, not assumed. pyrefly accepts the idiom, so only basedpyright needed telling; four sites, each carrying the repro.

## Breaking

`ItemList`, `ArtefactList`, `StructureMessage` and `MetadataMessage` are no longer hashable. Nothing in `src/` hashed them, and the only case that ever worked was an empty collection.
