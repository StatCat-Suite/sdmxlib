Step 0 of milestone %20 (tracking #423): the measuring instrument, and the first baseline. Every later %20 MR into `feature/m20-3x-native` runs `just sweep-delta <REGISTRY>` and pastes what moved.

## What it is

`bench/sweep/` (README there). For each registry, every bulk structure query its 2.1 and/or 3.0 API names is fetched into a gitignored cache. Each document then goes through:

- `parse`;
- `validate()`;
- `LocalRegistry.add` + read-back, diffed against the original;
- `check_serialisable`, `unrepresentable()`, the writer, and XSD / JSON-schema validation, for each of 2.1, 3.0, 3.1 and JSON.

Two comparisons need no list of what to look for:

- **`read_lost`**: element paths in the source vs our re-write in the same format. This is the read-side register #422 asks for.
- **`cross_api`**: the 2.1 and 3.0 readings of the same artefact, diffed field by field. Each registry records its engine (NSI or FMR), so a difference can be read either as a translation loss or as ours.

Findings are reduced to rule keys (values stripped) so that runs can be compared.

|---|---|---|

`just sweep` / `sweep-run` / `sweep-show` / `sweep-delta`. It is never in `just ci`: it needs the network, and the raw cache is about 7 GB. The instruments have 24 unit tests in `tests/unit/test_sweep.py`, each showing it can report a finding, not only stay quiet.

## Running it on a real machine

- **Sized to what is free now** (`capacity.py`): idle cores (cores minus load, minus one) and 60 % of *available* memory, read from `vm_stat` or `/proc/meminfo` + cgroup at start and printed as the run's first line. Each job starts only while its memory estimate fits beside the running ones. `--jobs N` overrides.
- **Large documents in chunks** (`split.py`): above 256 MB a document is cut once into ~96 MB chunks of whole artefacts, kept until the document is re-fetched, and each chunk is its own job. Chunk counts merge in order to exactly the whole-document counts (unit-tested, and checked on IMF against its earlier unchunked run).
- **Results do not depend on scheduling**: BIS, OECD and IMF give the same summaries in parallel as sequentially.

| registry | wall | peak per process |
|---|---|---|
| IMF | 18 min / 8.0 GB → 7.4 min | 2.7 GB |

## Baseline: what the registries say, sorted by milestone issue

### #424 / #420: version and finality

- `is_final` disagrees between the 2.1 and 3.0 readings at every registry that serves both. OECD: 835 of 841 codelists, 1,532 of 1,548 dataflows, 423 of 427 DSDs, 265 of 268 concept schemes. FMR: 126 of 140 codelists, 81 of 111 dataflows. This is the `legacy_is_final` case.
- Eurostat's 3.0 API returns nothing for `+` (latest stable). None of its artefacts has a final semver version; all are legacy `1.0`, which #424 reads as drafts. Its 8,146 dataflows read identically from both APIs.
- The 2.1 projection of IMF writes 3.x version strings into 2.1 `Ref@version` / `@maintainableParentVersion`: 20,983 schema-invalid attributes (hierarchies 12,007, concept schemes 6,536, DSDs 2,327). These look like wildcard or range references (#422 row), still to confirm.

### #422: 3.x content lost on read, silently (all rows confirmed on live data)

- `MetadataAttributeUsage` in DSDs: 4,176 (IMF).
- `HierarchicalCode/Level`: 12,279 (IMF).
- Code annotations' `AnnotationText`: 26,823 (IMF). This is not in #422's table; it needs a look.
- `Link` on items: 37 (BIS).
- `MeasureRelationship`: BIS 91, FMR 124.
- MSD `@maxOccurs`: IMF 11,128, BIS 74, FMR 44, OECD 17.
- `Measure/@usage`: OECD 427, BIS 27, FMR 23.
- `DataConsumerScheme` is read as no artefacts at all, with no error (FMR, both APIs).

### #419: ingest, store, and the reader's strictness

- **The FMR reference registry's 3.0 `datastructure` document fails to parse as a whole.** One component enumerates a ConceptScheme (a 2.1 MeasureDimension carried over), and `SdmxConformanceError` loses all 23 DSDs. A reader should refuse per artefact and report, not fail per document.
- The store loses `DataConstraint.regions[].keys` (OECD, 1,453) and `data_keys` (ECB 84, FMR 2). It also changes `valid_from` (OECD 1,517 constraints; BIS 3 constraints, 24 HCLs) and component `enumeration_format` (every registry).
- The store crashes with a DuckDB primary-key violation on one BIS MSD and one Eurostat CategoryScheme.
- Duplicate hierarchy node ids are refused at `add`: IMF 31, ECB 27, OECD 22, BIS 6. Not yet clear whether these are bad registry data or a wrong rule; to check against FMR's own validation.
- Eurostat's 3.0 AgencyScheme uses `str:Name`; the reader drops it silently and `validate` then refuses the scheme.

### #421: union shapes

- Multi-measure DSDs, or a measure not named `OBS_VALUE`, are refused for 2.1: 59 (IMF).
- MSDs without the 2.1 MetadataTarget/ReportStructure layer are refused for 2.1: IMF 31, BIS 4, OECD 1, FMR 1.
- MeasureDimension DSDs are refused for 3.0, 3.1 and JSON: 3 (FMR).
- HCLs are refused outside 2.1: OECD 212, BIS 48, ECB 36, FMR 3.

### Defects outside the milestone's catalogue (new)

- **OECD constraints**: `KeyValue/TimeRange` (1,453) and `CubeRegion/Attribute` (758) are lost on read. The writers then emit empty `KeyValue`s, which are schema-invalid in 2.1 and 3.0.
- **OECD 2.1 HCLs** in the `CodeID` + `CodelistAliasRef` form lose their codes on read (8,297 `HierarchicalCode`s), and every writer emits invalid output.
- **Code `Parent` written to 3.0** fails the 3.0.0 XSD pattern `[A-Za-z,A-Za-z0-9_\-]*` (e.g. `_T`): OECD 18,562, FMR 1,479, IMF 433, BIS 50. The same values are valid in 2.1 and 3.1, so this is probably a 3.0.0 schema erratum; it should be refused or declared, not emitted.
- Categorisations are written schema-invalid in all four formats: 209 (BIS).
- DSD `TextFormat@textType` is written invalid in 3.0, 3.1 and JSON: 54 (IMF).

Each of these will get its own issue, linked from #423, once this lands.

### Noise, not loss

Eurostat sends ~830,000 empty `<AnnotationURL />` elements (DSDs and codes), which we drop on read. They show as `read_lost` but carry nothing. If they get in the way of a delta, the census can treat an empty element as derivable.
