The three remaining API-shape questions, settled together before the freeze —
each is cheap now and a second migration later.

## #341 — an empty fan-out collects to `[]`

SQL's answer is `NULL`, and this language usually takes SQL's. Not here: it
takes polars' *names* for these aggregates, and #326 established that adopting a
name without its semantics is the thing to avoid. The concrete cost of `NULL`
was that `len(unique()) == n_unique()` needed `or []` at every call site.

**The issue's argument for keeping `NULL` turned out to be wrong.** It said
`None` vs `[None]` distinguishes "no rows" from "rows, all null" and that polars
cannot express the difference. Measured — it can, as `[]` vs `[None]`:

```
CL_EMPTY   unique=[]         n_unique=0     ← no rows
CL_ROOTS   unique=[None]     n_unique=1     ← rows, all null
CL_AREA    unique=[None,'W'] n_unique=2
```

So the distinction survives and nothing was traded for it. The test #341 named
stops hedging with `in ([], None)`, and its own name — "collects to empty not
missing" — becomes true.

## #342 — a to-many projection refuses where you write it

`select(...).filter(...)` always refused at the call; a to-many projection
returned a `Frame` and raised at `collect()`. One rule now. `select`'s docstring
already claimed this.

**It runs no query** — `resolve_path` reads the declared edge graph and touches
no connection. Held by a test that counts SQL statements: `select()` executes
zero, refusing or not.

Both sites share one message; the compiler keeps its copy as the backstop for
paths reaching projection without passing through `select` (a `group_by` key, a
rebased predicate).

## #327 — `sort()` / `sort_by()`

`list()` returned whatever the scan produced — the hazard `__key__` already
removes from `ORDER BY`. Ordering is now a property of the expression, so it
composes with whichever aggregate follows:

```python
codes.id.sort().list()                                  # ['CA','MX','US','W']
codes.id.sort_by(codes.position, descending=True).list()
codes.id.list()                                         # scan order, unchanged
```

Default deliberately unchanged: an `ORDER BY` inside every aggregate is a sort
nobody asked for.

`unique()` can only be ordered by itself — a DISTINCT aggregate collapses the
rows another key would have come from, so there is no "which duplicate's key".
DuckDB refuses it (*"In a DISTINCT aggregate, ORDER BY expressions must appear
in the argument list"*); this refuses first, naming `sort()` as the fix.

The sort key joins `__canonical__` — `list()` and `sort().list()` are different
questions and a cache keyed alike would serve one for the other. An **alias**
deliberately does not, since renaming a column does not change which rows come
back.
