## What was missing

The SDMX-JSON data writers emitted **no annotations at all** — not on a value, not on a component. That is a whole channel, not one field: it is how the format carries everything beyond `id` and `name`, and without it a consumer's value ordering falls back to first-seen order.

Split out of #365, where `order` was proposed as the companion to `parent` and turned out to be the wrong field. `value.order` is schema-legal and **nothing reads it** — the .Stat Explorer takes its sort position from an annotation of type `ORDER`:

```js
// rules/src/get-values-enhanced.js
const orderAnnotation = R.find(R.propEq('ORDER', 'type'), annotations) || {};
```

which feeds `__indexPosition`, the key both hierarchisation paths sort on.

## Pooled, not repeated

The schema types `dimensions[].annotations` and `values[].annotations` as `array of integer`, and only `structure.annotations` as objects. So `AnnotationPool` owns that one array and is **shared** by the dimension and attribute tables — an index is meaningless without knowing which array it indexes, and there is exactly one.

Passing the pool is a **required keyword**: a table quietly constructing its own would emit well-formed-looking indices into an array that never reaches the message. (That requirement immediately caught a direct construction in an existing test, which is the point.)

Interned on the *rendered* form — `Annotation` is `@define`, so it has value equality but no hash, and what matters on the wire is whether two annotations serialise identically.

```json
"annotations": [
  {"type": "ORDER", "text": "2", "texts": {"en": "2"}},
  {"type": "NOT_DISPLAYED"}
],
"dimensions": {"observation": [
  {"id": "FREQ", "keyPosition": 0, "annotations": [3],
   "values": [{"id": "A", "parent": "TOTAL", "annotations": [0, 1]},
              {"id": "Q", "parent": "TOTAL", "annotations": [1]}]}
]}
```

## No filtering by type — the IM says there is no taxonomy

> "AnnotationType is used to distinguish between annotations designed to support various uses. **The types are not enumerated**, as these can be specified by the user or creator of the annotations."

— every SDMX-ML version, and quoted verbatim in the SDMX-JSON schema.

So `ORDER` / `NOT_DISPLAYED` / `LAYOUT_ROW` are a **.Stat convention, not SDMX vocabulary**. An allow-list would hard-code one publisher's private vocabulary into a general library and be wrong for the next. The writer emits everything the observed codes carry, and a test asserts an invented type survives.

## Both schema slots, not one

Values **and** the component objects. Leaving the second empty is exactly how the first went unnoticed — the structure writer had emitted the same data for years before #365 surfaced the value-level gap as a user-visible bug.

## Costs nothing when there is nothing to say

No pool, no index arrays, no keys on an unannotated message. And nothing is walked eagerly: component annotations resolve at construction from the DSD, value annotations in `position()` from the code already looked up — so the census-scale no-eager-walk tripwire (`test_init_does_not_walk_full_codelist`, guarding against a 579k-code codelist blowing up a `limit=2` response) still holds.

## Verification

Guarded on the **referential** properties rather than field presence, since a dangling or mis-numbered index is what this design invites — including one test that walks every index the message emits, across both levels and both component kinds, and asserts each resolves. Verified by planting both failure modes:

- each table keeps its own pool → **9 failures**
- interning disabled → **2 failures**, caught only by the shared-pool test

`just ci` green (5850 passed).

## Known limit

SDMX 3.0's `AnnotationValue` is not modelled, so an emitted annotation can never carry `value` — the *non-localised* field, which is the more correct home for a machine-read ORDER. Read and silently dropped today; filed as **#368** with an empirical repro. It caps what this change can deliver for publishers who use it.
