#404 and #405 fixed the *consuming* side of item references: the readers index
every item kind and `validate_references` resolves them. Producing one had no
equivalent. `ConceptScheme.ref_to` was the only builder in `src/`, so authoring
a 3.0 `Hierarchy` — where `HierarchicalCode.code` must name a `Code` and
`HierarchyAssociation.linked_object` must name a component — meant assembling
the URN from six keyword arguments, three of which restate the parent.

    cl.ref_to("CA")            # Ref[Code]
    cats.ref_to("GDP")         # Ref[Category] — nested ones too
    msd.ref_to("EMAIL")        # Ref[MetadataAttribute] — likewise
    scheme.ref_to("ESTAT")     # Ref[Agency]
    dsd.ref_to("TIME_PERIOD")  # Ref[object] — dispatched across six lists

Seven schemes, one implementation: `_items.item_ref` builds the URN from
*self*'s agency, id and version, so it cannot name a parent that does not
exist. That is the whole failure mode — a hand-built URN takes those three as
separate arguments and nothing stops them naming a different artefact.
`ConceptScheme.ref_to` moved onto the same path rather than staying a copy.

## DataStructure dispatches, and the model now says why

`dimensions`, `time_dimension`, `measure_dimension`, `measures`, `attributes`
and `groups` are six item lists under one maintainable, so #407 asked whether
`ref_to` should dispatch or take an explicit role. The codebase already
answered: `storage.schema` declares ``PRIMARY KEY (dsd_urn, component_id)`` on
`dsd_component`, so a component id has always been unique across the whole
structure here, whichever list it sits in.

That was true of storage and unchecked in the model — a DSD with a dimension
and a measure sharing an id could never round-trip through DuckDB, and the
collision surfaced as a constraint violation on write rather than as a
validation issue on the artefact. `_check_component_ids_unique` closes that,
which is what makes the dispatch unambiguous rather than merely convenient.

`Ref[object]` rather than a six-way union: the class varies, every field that
consumes one is declared `Ref[object]`, and the URN carries the real class.

## Lazy codelists keep pace

`test_lazy_return_types`'s parity guard caught `LazyCodelist` lacking `ref_to`
the moment `Codelist` gained it. It gets a real one rather than a refusal: the
existence check goes through the facade's own subscript — one targeted query,
not a materialisation — reusing the two-path lookup `find_item` already had.

Their `sdmx_package` / `sdmx_class` are now `ClassVar`-annotated, which is what
`SupportsUrn` requires and what every other artefact class already did; a plain
assignment reads as an instance attribute and failed the protocol.

## Guards

18 tests. The one that matters most asserts the two halves *agree*: every URN
`ref_to` builds resolves under `validate_references`, on a message carrying a
hierarchy, an association, a categorisation and a DSD — so the producing and
consuming sides of #404/#405/#407 are checked against each other rather than
separately. Sabotage-checked by making `ref_to` emit a wrong version: five
tests fail.

Discrimination throughout: an absent id raises `KeyError` naming the scheme, a
case-mismatched id (`ca` for `CA`) is absent rather than tolerated, an absent
component names the lists searched, and a valid DSD still validates so the new
uniqueness rule cannot fire on everything.

## For the consumer

The `urns.py` workaround (~60 lines, two functions wrapping `SdmxUrn.make`) can
go. `dsd.ref_to(id)` and `cl.ref_to(id)` replace it, and derive agency and
version from the artefact for the same reason that module did.
