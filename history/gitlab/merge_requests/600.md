Closes #441.

**The cost.** The SDMX-JSON data writers (1.0 and 2.0) resolve the codes a message observed, one codelist per enumerated component. For a DSD from a store, each lookup was **three** statements: codes, annotations and links. The links read arrived after the issue was filed, with #422. So a 1-observation `DF_CP_2021` message, with 18 enumerated components, made **54 statements**.

**The change.**
- `codes_for_all` groups the requests by codelist class and asks each class once, through a new `CodelistLike.codes_for_each`:
  - an eager `Codelist` loops `codes_for`, as before;
  - a `LazyCodelist` groups its requests by connection and reads them with `resolve.codes_by_ids`.
- `codes_by_ids` is one `UNION ALL` of per-codelist branches, each keeping the `codelist_urn = ?` predicate the table is pruned by, plus one annotation read and one link read. A large id set still registers a relation through `value_match`.
- The writer keeps one component table per kind, so a message makes two reads, dimensions and attributes: **6 statements in place of 54**. Merging the two would mean restructuring both writers and the annotation pool's ordering, for 3 more statements.

**Measured against `main`**, `DF_CP_2021`, one observation, matching environments:

| | main | this MR |
| --- | --- | --- |
| default install (pandas not importable) | 39–40 ms | **16.3 ms (−58%)** |
| pandas importable | 79.4 ms | **14.1 ms (−82%)** |
| peak memory per message | 0.08 MB | 0.09 MB |

sdmxlib doesn't depend on pandas, but DuckDB's binding cost changes when pandas is importable (#411). The second row is what a service that installs pandas for its own reasons would see. The output is byte-identical.

**#441's other proposals, measured and not taken:**
- **`IN (?, …)` instead of `= ANY(?)` for small sets:** faster only for one value. For 4–8 values it was 9.7 against 6.0 ms and 11.9 against 7.2 ms on the code read, with and without pandas.
- **Native name columns:** ~0.5 ms.

**Tests:**
- `test_sdmx_json_data_lazy_codelists.py` asserts one batched lookup per component kind, exact on the observed ids, and one code read and one annotation read each. Its old guard spied on the per-component `codes_for`, whose subject moved.
- `test_codes_for_all.py` covers the resolver: several codelists, a branch large enough to register a relation, unknown and empty ids, two requests sharing a codelist, and eager and lazy codelists mixed.

The guards were watched to fail with the old writer path restored.
