## The defect

`urn` was the classmethod *builder*, so `flow.urn` on an instance handed back a
bound method. `ref.py`'s own `SupportsUrn` docstring offered this as the long
form of `Ref.to(cl_freq)`:

```python
Ref.unresolved(cl_freq.urn)
# TypeError: Ref expects a SdmxUrn, got method
```

The library documented a call it could not make, because the name a reader
reaches for first was occupied by the thing that *builds* one. That example now
runs, and there is a test that runs it.

## The change

`.urn` is a property on `MaintainableArtefact`; `urn_for(agency=…, id=…)`
builds one. **449 call sites**, all mechanical — every `.urn(` receiver in the
repo is a class, which I checked before renaming rather than assumed.

**They stay two names because they differ in more than receiver.** `urn_for`
defaults `version` to `"latest"`, which is right for an identity you are
looking *up*; an artefact you hold has whatever version it has. One function
cannot default both ways, and a test pins that.

**The property recovers a type `artefact_urn` cannot.** That takes a
`SupportsUrn` and has nothing concrete to return, so it hands back
`SdmxUrn[Any]` and leans on bivariance. This has `type(self)` and returns
`SdmxUrn[Self]` — so `Ref.unresolved(flow.urn)` is a `Ref[Dataflow]` with no
`Any` in the middle. `artefact_urn` stays for Protocol-typed callers and now
says so.

**Recomputed, not cached.** These artefacts are `@define` and mutable, so a
stored URN goes stale the moment someone assigns `version`. If it ever shows up
in a profile the answer is to hoist it in the loop — `docs/design/caching.md`.

## Items are asymmetric, deliberately

`Concept.urn_for` takes a `scheme`, and a `Code` has no URN of its own at all —
items are identified *within* their scheme, not independently. So the property
is on `MaintainableArtefact` only, and a test asserts a `Code` lacks it, so the
asymmetry is stated rather than discovered.
