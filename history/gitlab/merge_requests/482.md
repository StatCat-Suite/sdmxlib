Filed as a declaration that lies. It is that, and it is also **five public
entry points raising `TypeError`** on any DSD read from a `LocalRegistry`,
because they iterated or took `len()` of something that had become a `Query`:

    polars.schema            polars.validation_report    polars.structure_frame
    Dataset.pivot            Dataset.label

`Dimension.resolved_codelist` follows the component's `Ref`; from a local
registry that resolves to a `LazyCodelist`, not a `Codelist`.

## The shape

The two classes already shared 28 public members. `CodelistLike` declares the
part callers use, and the gaps it exposed were **closed rather than narrowed
around** — `Codelist` gained `code_ids`, `code_map`, `materialize` and
`__len__`, all of which `LazyCodelist` already had in substance. So no caller
carries an `isinstance` branch, and `polars._component_label_map`'s existing
two-branch narrowing collapses to one.

Measured on `CL_GEOGRAPHY`, 579,951 codes, which is what decided the shape:

| | cost |
| --- | --- |
| `code_ids()` | 92 ms |
| `len()` | 22 ms |
| `materialize()` | 2,854 ms |

So "always materialise" was rejected at 31x and 129x — the cost #378 removed.
It survives as `materialize()`, for the two callers that genuinely need each
`Code` (the SDMX-JSON data writer reads annotations and `parent_id`).

`Dimension.codes` keeps working and finally means what it said: it materialises,
because asking for `Code` objects is asking for them to be built. `code_ids()`
is the cheap path beside it, and a **method** rather than a property for the
reason the bug existed — attribute access that can reach the database is what
made `dim.codes` read as free when it was not.

## A second defect, found by testing both classes against one protocol

`LazyCodelist.code_map` **dropped** codes with no label in the requested
language; `Codelist.code_map` falls back to the id, as
`polars._component_label_map`'s in-memory branch always had. The same call
meant two things, and the SQL one silently shrank the map — `Dataset.label`
builds a `replace_strict` from it, so a dropped code became a null column value
rather than a visible failure. Both now fall back to the id.

`test_code_map_missing_lang` asserted the old `{}` and now asserts the
agreement, with the reasoning in its docstring: a caller asking whether a
codelist carries labels in a language is asking a different question and should
get its own answer, not infer it from a map that quietly shrank.

## `name`, `description` and `codes` are absent from the protocol

Not an oversight, and not a judgement about what belongs: basedpyright reads
`Codelist.name` as `InternationalString` for attribute access and as
`__converterDescriptor_name` for protocol matching, so a protocol naming any
attrs converter field does not check even though every read of it does. That is
why `code_ids()` exists as a method rather than the field it wraps.

No suppression — the method shape avoids it, and
`test_name_and_description_are_absent_for_a_reason` fails the day the checker
is fixed so the workaround cannot outlive its cause. Minimal repro in
`tests/typing/probe_codelist_like.py`.

## Guards

`tests/unit/test_codelist_like.py` runs every assertion against **both**
classes off one parametrised fixture, reaching the lazy one the way a user does
— through a DSD read back out of a registry. That is what found the `code_map`
divergence. `tests/typing/probe_codelist_like.py` is the static half.

`sl.CodelistLike` is exported: it is the type of a public property, so a user
annotating their own helper needs to be able to name it — the same reason
`SupportsUrn` and `SupportsId` are exported.

Closes #398.
