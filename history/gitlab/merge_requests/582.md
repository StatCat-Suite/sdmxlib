Part of #421 (provision agreements + metadata providers rows).

SDMX-ML 2.1 has no `MetadataProviderScheme` and no `MetadataProvisionAgreement`, so a 2.1 write refused both. 2.1 provisioned metadata with a plain `ProvisionAgreement` over a metadataflow that names a data provider. Both are now written that way.

## Write (2.1)

- **Providers:** an agency's metadata providers go into its `DATA_PROVIDERS` scheme, the only id and version 2.1 allows.
  - With no data providers of its own, the scheme *is* the metadata provider scheme, marked `sdmxlib:metadata-provider-scheme`.
  - Otherwise each metadata provider is added, marked `sdmxlib:metadata-provider`. The scheme gets `sdmxlib:metadata-providers-merged`, whose text keeps the metadata scheme's name.
- **Agreements:** each `MetadataProvisionAgreement` becomes a `ProvisionAgreement` over its metadataflow, naming the data provider with the same id. Its `targets` are lost, a declared gap.
- **Still refused:**
  - a provider id the data scheme already uses;
  - a scheme property (description, annotations, validity, uri, external-reference) where the two schemes disagree, since they share one element;
  - an agreement with the same agency, id and version as a `ProvisionAgreement` in the message.

## Read (2.1)

- Marked schemes are split back, so 3.x → 2.1 → 3.x is exact apart from the agreement's targets.
- Any 2.1 `ProvisionAgreement` whose `StructureUsage` is a metadataflow is now a `MetadataProvisionAgreement`, with its provider read as the `MetadataProvider` of the same id. It used to be a `ProvisionAgreement` whose `dataflow` Ref held a metadataflow URN.
- Read accounting (`_losses._FOLDED`) now counts these converted elements as built, as it already did for a folded HCL.

## Fixture and guards

- The maximal fixture's metadata provider scheme moves to its own agency, `AG_MD`, so it stays valid for 2.1. The whole maximal message now writes to 2.1.
- Two discrimination tests that expected some refusal now assert the write succeeds.
