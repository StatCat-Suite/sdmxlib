Closes #224 — all seven conformance gaps the schema oracle found when DataStructure became the first artefact type beyond Codelist and ConceptScheme to be generated and schema-validated.

## Writability is now separate from well-formedness

```python
validate(dsd)                 # well-formed? ids, names, refs, bounds
                              #   -> a partial DSD stays storable
                              #   -> Registry.add still accepts it

serialize(msg, version=...)   # validate_message + check_serialisable
                              #   -> refuses what the wire cannot carry
```

That split is the design decision in this MR, and it is load-bearing. `Registry.add` calls `validate`; assembling a DSD across several steps and persisting it mid-way is a legitimate workflow. Putting the ConceptIdentity rule in `validate` would have taken that away — and broke **53 tests across 9 files** when I tried it.

## The seven

| | Gap | Fix |
| --- | --- | --- |
| 1 | `ConceptIdentity` required by all four formats; model defaults it to None, no writer emits one | `check_serialisable` |
| 2 | `DataType` had four members in no schema enum — `Attachment`, `ReportingHour`, `URL`, `Year` | removed from the enum |
| 3 | `XHTML` valid in 3.0/3.1, invalid on a 2.1 component | version check |
| 4 | Facet bounds via `str()` emitted exponent notation `xs:decimal` rejects | `_xsd_num` formats via `Decimal` |
| 5 | `decimals`/`maxLength`/`minLength` are `xs:positiveInteger`; `0` was emitted | `validate` |
| 6 | `isMultiLingual` not allowed on a 2.1 component `TextFormat` | version check |
| 7 | 2.1 has exactly one `PrimaryMeasure`, id fixed to `OBS_VALUE` | version check |

**Items 3, 6 and 7 are downgrade hazards** — valid SDMX 3.0 with no 2.1 representation. They are only checkable when the target version is known, which is why `check_serialisable` takes one.

**#2 removes four public enum members.** Each sat beside its valid counterpart (`URI`, `GregorianYear`, `ReportingYear`), appeared in no schema enumeration, and was used nowhere in the codebase. Pre-1.0, breaking cleanly.

**#7 was worse than first reported.** I initially wrote the rule as "measure id must be `OBS_VALUE`", then found the 2.1 writer emits **one `<PrimaryMeasure>` per measure** — so any multi-measure 3.0 DSD produced structurally invalid 2.1, not merely a mis-named one. The rule now states the real constraint.

## Two of our own artefacts were building unserialisable DSDs

Fixed rather than exempted, because both are the bug rather than collateral:

- **`docs/building_tutorial.md`** taught a DSD whose measure had no concept. The tutorial was demonstrating output no consumer would accept.
- **`test_sdmx_json_writer`'s JSON→2.1 conversion** used the `with_groups` fixture, which carries two measures. That conversion cannot succeed; those five tests now use a fixture list that says so, with the reason.

## The strategies prove the fixes

The workarounds !226 added for items 2 and 4 are **removed** — the full float range and every `DataType` member are generated again, and the round-trip properties still pass. That is the regression handle working as designed: !226 said "when #224 is fixed the restrictions relax and the properties then cover what is broken today", and they do.

The restrictions for 3, 6 and 7 stay, because those artefacts are legal SDMX 3.0 and these properties write one artefact to all four formats.

## Verification

`just ci` green — 2871 unit, 72 docs, 56 integration. 19 new tests pin both halves of the split: a concept-less DSD stays valid and storable, and is refused by all four formats at serialise time.

Closes #224
