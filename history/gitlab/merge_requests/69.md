Closes **#107**. The 3.0 / 3.1 \`ValueMappingType\` allows three semantic operations per \`RepresentationMap\` entry, discriminated by optional attributes on \`<SourceValue>\`. Previously our model collapsed all three into one \`ValueMap(source_value, target_value)\` shape, silently dropping the regex / index discriminators and the per-mapping \`validFrom\` / \`validTo\` dates on read.

Per your guidance on the audit (Python semantics, not XML syntax): **the three variants are different mappings, not one mapping with optional flags** — so they get separate classes.

## New variant types

| Type | Semantic |
|---|---|
| \`LiteralValueMap\` | exact \`source_value\` → exact \`target_value\` |
| \`RegexValueMap\` | \`source_value\` is a regex pattern; \`target_value\` may use \`\\1\` backrefs |
| \`IndexValueMap\` | substring slice from source (1-based, inclusive per SDMX) → literal target |

All three carry uniform \`source_value\` / \`target_value\` fields plus optional \`valid_from\` / \`valid_to\` (\`datetime.date\`, not \`datetime\` — the XSD's \`validFrom\` / \`validTo\` here are \`xs:date\`, not \`xs:dateTime\`).

\`ValueMap\` is now a **type alias** for the discriminated union:

\`\`\`python
ValueMap = LiteralValueMap | RegexValueMap | IndexValueMap
\`\`\`

\`RepresentationMap.maps: tuple[ValueMap, ...]\` keeps its annotation; callers pattern-match on the concrete class when consuming.

## \`translate()\` is variant-aware

\`RepresentationMap.translate()\` now matches **only \`LiteralValueMap\` entries**. Regex / index variants need caller-side handling because the matching semantics differ — translate() is a convenience for the common case, not a polymorphic engine.

## Serializer wiring

- **3.0 writer**: emits the discriminator attrs (\`isRegEx=\"true\"\` for regex, \`startIndex\`/\`endIndex\` for index) on \`<SourceValue>\` and the validity attrs (\`validFrom\`/\`validTo\`) on \`<RepresentationMapping>\`.
- **3.0 reader**: dispatches on those attrs to the right variant class and parses \`xs:date\` strings via \`date.fromisoformat\`.
- **2.1 reader, JSON reader, storage reader**: only support the literal case. The 2.1 \`<CodeMap>\` element has no discriminator slot; storage schema's \`value_map\` table only has source/target columns. The 2.1 / JSON layers silently drop regex / index variants if a model carries them and is downgraded to those wire formats — documented in code comments.
