## The claim worth checking in review

It mirrors `query()`: plan against what `/data` can answer, fetch that,
materialise, then run the **original** query locally. That last clause is
load-bearing, and the tests are built to prove it — **the stub returns every
row whatever the URL says**, so any narrowing in a result came from SQL after
the fetch.

That is what makes an unpushable filter *slow* rather than *wrong*, and it also
means a provider that ignored the key, or whose key means something subtly
different, cannot widen an answer.

## One table per dataflow, holding one question's rows

A different question overwrites it and evicts the first from the memo, so
re-running the first re-fetches rather than reading the second's rows.

Appending would be correct for *filtering* — the original query re-applies
every predicate, so a superset is harmless — and wrong for *counting*, since
two overlapping fetches land the same rows twice. The cost is a re-fetch when
alternating between two queries on one dataflow; the alternative, a table per
question, would make the root's table depend on predicates that are not known
when the root is built.

## Two layering points the linter caught rather than I did

**The write belongs to the store.** `ruff.toml` exempts `local/**` and
`query/**` from S608 and not `api/**` — which was the rule pointing at the
right home. `DuckDBDataStore.write_observations` already validates identifiers
and creates the schema, so `api/` holds no SQL.

**A top-level `scan_csv` import would have defeated a deliberate deferral**
three hundred lines below (`# lazy: defer CSV import`). It stays lazy, with the
same reason attached.

One fixture detail worth noting: the measure needs `Facet(type="Double")`,

as VARCHAR and a numeric filter is a binder error. The design working, but
worth knowing when writing a fixture.
