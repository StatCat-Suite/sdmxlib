## A silent data loss, found by asking what the flags were

Writing a `DataConstraint(constraint_type=ACTUAL)` to SDMX-ML 3.1 emits no
`@role` — correctly, 3.1 removed it — and reading it back gives **`ALLOWED`**,
because that is the model default. `unrepresentable(cc, "3.1")` reported
nothing lost.

`formats/gaps.py` had the sibling field declared. `release_calendar` is removed
from 3.1 for the same reason — both moved to `AvailabilityConstraint` — and
that row's own comment names this exact shape: *"a drop the mechanism built to
answer for drops denied"*. `@role` was missed when it was written.

Now declared, with a `carried` predicate that is "not the default" rather than
"present": `ALLOWED` survives the trip, since it is what an absent `@role`
reads back as, so only `ACTUAL` is a loss. Reporting the default would make
every constraint look lossy.

## The flag set

| flag | 3.0 | 3.1 |
| --- | --- | --- |
| `categorisation_version` | yes | no — `@version` `use="prohibited"` |
| `data_constraint_role` | yes | no — `@role` removed |
| `release_calendar` | yes | no — `<ReleaseCalendar>` removed |
| `dimension_constraint` | no | yes — `DataflowBaseType` adds it |

Booleans rather than a version string, so a call site reads as the capability
it depends on and a 3.2 sets flags instead of adding branches on a literal.

The version *grammar* is deliberately not a flag: `check_writable(v, "3.0")` is
correct for both, because `model/version.py` declares two grammars and 3.1
shares 3.0's. A `"3.1"` there would raise on every artefact.

## The guard is now about agreement, not similarity

`test_ml3_fork_drift.py` compared function bodies. After this it would compare
two modules each holding one forwarding call and pass while saying nothing.

Replaced with three things it could not say before:

* neither package reimplements anything, and each shared class really carries
  the implementation (the reader-half pattern from !487, extended to both);
* **every flag has a matching `formats/gaps.py` row**, and every asymmetric gap
  between 3.0 and 3.1 has a flag. `V3Generation` tells the writer what to emit
  and `gaps` tells a caller what will be lost — two statements of one fact, and
  drift between them is exactly what hid the `@role` loss;
* every flag actually differs between the generations, since one that does not
  is a constant with extra steps.

Sabotage-checked: deleting the new `gaps` row fails naming
`V3Generation.data_constraint_role`, and making `dimension_constraint` agree
fails naming it.

One more guard was silently disarmed and is fixed here:
`test_ml3_writer_parity.test_every_annotation_site_is_reached` counted
`write_annotations` call sites in `sdmx_ml30/writer.py`, which is now 49 lines
— it read 0 against 30 expected markers. It reads the shared module now, which
is also why one count covers both generations.
