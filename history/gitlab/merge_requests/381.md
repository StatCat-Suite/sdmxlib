## The damage

§6 step 6c renamed `sl.Registry` to `sl.LocalRegistry` across 124 files (!372). Mechanical is the point of a rename and also its hazard: the substitution ran through **prose**, and four docstrings had said "Registry" meaning something else.

```
"Copy all artefacts from an in-memory LocalRegistry into this store"
"Load everything into an in-memory LocalRegistry with full Ref interning"
"The domain LocalRegistry populated by every artefact fetched so far"
"this matches the LocalRegistry Protocol semantics for membership"
```

The first three mean `InMemoryRegistry`; the fourth means the `RegistryReader` Protocol. *"In-memory LocalRegistry"* names no type — and it is wrong in the way documentation is worst: confidently naming the wrong type to a reader with no way to tell.

Nothing failed, because prose has no compiler. So `test_registry_naming.py` now fails on the phrases a rename can only produce by running through a sentence, and is **verified to reproduce the original damage** (reinstating one line fails the guard with that line quoted). A second test pins the premise — that the three names are three distinct things — so the check cannot outlive the distinction it enforces.

## #333 closed as invalid

It held that `InMemoryRegistry`'s *"Satisfies the `Registry` Protocol"* claim "buys nothing and is never exercised", because `formats/` takes the type concretely:

```python
def read(data: bytes, *, registry: InMemoryRegistry | None = None) -> StructureMessage
```

That much is true. The conclusion is not:

- **`FederatedRegistry` declares `routing: dict[str, RegistryReader]`** and is routed to an `InMemoryRegistry` throughout its tests, including the case where one federation is a source inside another. An in-memory artefact set is the natural way to stand up a federation without a database or a network.
- **`docs/cookbook/local_files.md`** loads files into one and calls `reg.get(urn)` — registry behaviour, documented. `docs/api.md` groups it with `RestRegistry` and `FederatedRegistry`.

The claim is accurate and load-bearing. The *concern* behind the issue — that the read seam reads as a catch-all — survives and belongs to §5.10; the answer is just not "`InMemoryRegistry` is not a registry", because it demonstrably is one.
