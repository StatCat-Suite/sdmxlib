Part 1 of #309. Part 2 (`MetadataProvider`) is split out as #315 — it is an
SDMX 3.0 class the library does not model at all, so building it is a feature,
not a bug fix, and leaving it here kept a closeable bug open behind it.

`DataProvider.contacts` was dropped on every write. Narrower than the issue
assumed: all three format readers and writers already carry the field
correctly — **only storage** lost it, because `agency_contact` was keyed by
`agency_urn` and there was nowhere to put a provider's.

## The table

`agency_contact` → `organisation_contact(owner_urn, …)`. `Agency` and
`DataProvider` are both `Organisation` in the IM with an identical `contacts`
field, so one relation serves both. A sibling table would have been a fourth
copy of one shape — exactly what !303 had just finished removing from the facet
columns. Writer and reader each share one helper now, instead of one having the
code and the other having nothing.

## Two things found by running the queries, not by reading the code

**A pre-existing duplication bug.** `_delete_artefact_cascade` deleted the
`agency` rows *before* the contact cleanup that subqueries them, so the
subquery matched nothing and contacts accumulated — one extra set per re-add,
silently, because nothing counted them:

```
after 1 add: 1
after 2 adds: 2   (expected 1)
after 3 adds: 3   (expected 1)
```

Re-adding a scheme is the ordinary path, not an edge case. Fixed by ordering
the deletes correctly; without it this change would have extended the same bug
to providers.

**The polymorphic edges must be `optional`.** A contact's `owner_urn` matches
an agency *or* a provider, never both. With inner joins each hop silently drops
every contact of the other kind, and selecting both at once returns **nothing**
— measured. Both edges are `optional=True`, and each contact now resolves to
its owner with `NULL` for the other.

## The guard that caught me, generalised

`test_optionality_matches_the_schema` derives optionality from column
nullability, and `owner_urn` is `NOT NULL` — a contact always *has* an owner;
what it may lack is an owner in *that table*. Rather than special-case it, the
guard gains a second derived category beside the identity split it already had.
Both are "the **row** may be missing, not the column". An edge is polymorphic
when several *named* edges leave one column for different targets.

The rule immediately found four more: `annotation.owner_urn` targets artefact,
code, concept and hierarchy_node. Those are a false positive worth encoding —
all four are `name=None`, reverse-only, so there is no forward hop to traverse
and the fan-out compiles to `EXISTS`, which has no join kind to get wrong. The
`named` qualifier carries that reasoning in the helper.

Mutation-checked: removing `optional` from either new edge fails, naming the
sibling targets.

## Breaking

- `sdmx.agency_contact` → `sdmx.organisation_contact`; `agency_urn` →
  `owner_urn`. `SCHEMA_VERSION` 2.7 → 2.8; the store is a cache and rebuilds.
- `q.contact` is unchanged at the call site and gains
  `q.contact.data_provider` beside `q.contact.agency`.
