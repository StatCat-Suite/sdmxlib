Closes #293. Closes #296.

The four query DSLs had a composition law per clause and no stated principle, so each new clause was a fresh argument. #264 found the laws were already consistent — just never written down, and nothing enforced them.

> **Every row-set composition refines the query. Nothing a later caller adds can undo what an earlier call established.**

Three laws follow, generated over three DSLs: monotonicity, idempotence, and — the strongest usable form — **every ordering either commutes or is refused**. No third category where order silently changes the answer.

## The property falsified the principle on its first run

Which is why #296 landed here rather than after it. Every clause compiles into one `SELECT`, so a `filter` after a `limit` lands in the `WHERE` and runs *before* it:

```
q.limit(1)                    ['0']
q.limit(1).filter(id != '0')  ['1']    <- a row the first did not contain
```

A hard violation of monotonicity, not the ambiguity #296 described. The principle could not be stated truthfully while that composition was allowed, and shipping a principle the code contradicts is the failure #293 exists to prevent.

`reject_after_slice` refuses `filter`/`sort_by` on a sliced query across all four classes. `limit`/`offset` after a slice stay legal — they are refinements and paging is made of them. `with_annotations` is unguarded: it changes what is hydrated, not which rows. Django refuses the same composition for the same reason; unlike Django we can name the other reading, and the test **runs** the `is_in` spelling the message recommends rather than string-matching it.

## Both guards measured for discrimination

- Reintroducing #264's defect (`return max(start, n), length`) **fails** `test_row_set_compositions_only_narrow` — the property catches the bug that actually shipped.
- Adding an unclassified composition method **fails** the census test, naming it.

## Carve-outs, stated rather than assumed

Ordering is not a row-set property (`sort_by` permutes) — applying refinement to it by symmetry was the category error behind #294. `limit`/`offset` deliberately do not commute (#264), asserted as a *non*-law against plain-Python slices.

Docs: the principle in `_query_common`'s module docstring, plus `docs/design/query-composition.md` with the peer comparison — among declarative peers exactly one law is unanimous (`filter` = AND); `order_by` is append/replace/prepend and `limit` is last-wins/clamp/nest across SQLAlchemy, Django and ibis. Nothing to copy, hence an internal principle.
