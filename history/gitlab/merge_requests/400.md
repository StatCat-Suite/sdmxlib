Follow-up to !399, from a question I could not answer without checking:
does refusing an unknown literal remove any query that used to work?

Measured: no, for the values sdmxlib writes. `str.contains`,
`starts_with`, `is_not_null`, `select`, `group_by`, `order_by` and
`is_in` over a subquery are all untouched on those columns — only
literal equality is constrained, and only to values the column can hold.
So `== "Codlist"` and `!= "Codlist"` were predicates with no teeth, and
losing them costs nothing.

I had worried about a store holding a value this build does not know —
an older writer, another tool on the same schema. That worry was wrong,
and the reasoning is worth recording rather than the conclusion:
`artefact_type` holds SDMX IM class names, the IM is fixed, so an
unknown value is a bug rather than a variant. And a store cannot carry a
stale one anyway — `LocalRegistry._initialise_schema` drops and rebuilds
whenever `SCHEMA_VERSION` moves. Constructing the case at all took a
hand-written INSERT past the writer.

What that leaves is one real way for the check to refuse a *legitimate*
query: a writer landing without an `ARTEFACT_KINDS` entry. Then the rows
exist, the query is right, and the language says no. Nothing tested
that. Now two do, against `writers._WRITER_DISPATCH` in both directions
— writable-but-unqueryable, and advertised-but-unwritable — rather than
against a fixture, since a fixture only covers the artefacts someone
remembered to add, which is the same mistake one layer up. Verified by
dropping `Hierarchy` from the registry: the guard fails and names it.

The reasoning is now beside `ARTEFACT_TYPES`, because it is what
licenses refusing rather than passing through to an empty result.
