# Merge request !228: fix: validate() applies the id type the schema actually uses

Closes #221. SDMX has **three** id types and the position decides which applies. `validate()` applied the permissive `IDType` to all of them, so it accepted ids the XSD rejects — while `serialize(validate=True)`, the default, reads as a promise that the output is valid.

```
IDType              [A-Za-z0-9_@$-]+         items: Code, Category
NCNameIDType        [A-Za-z,A-Za-z0-9_-]*   maintainables, components, Concept
NestedNCNameIDType  NCName(.NCName)*         agencyID
```

`NCNameIDType` exists because those ids become XML element and attribute names in structure-specific schemas, so they must be valid XML NCNames — start with a letter, no `@` or `$`.

## Result

| codelist | agency | code | `validate()` | XSD |
| --- | --- | --- | --- | --- |
| `CL_OK` | `AGENCY` | `CODE_OK` | passes | valid |
| `0LEAD` | `AG` | `C` | **rejects** | invalid |
| `A@B` | `AG` | `C` | **rejects** | invalid |
| `A$B` | `AG` | `C` | **rejects** | invalid |
| `CL` | `0AG` | `C` | **rejects** | invalid |
| `CL` | `AG` | `0CODE` | passes | valid |
| `CL` | `AG` | `C@D` | passes | valid |

**Disagreements: 4 → 0.** The last two rows matter as much as the others: item ids genuinely are the permissive form, so this is not "tighten everything". Each position was verified against the vendored XSDs rather than inferred — and that caught a case I would have got wrong by analogy: **Concept ids are NCName, not `IDType`**, because a concept id can become a component id.

## The 25 failing tests were pinning the bug

All in `test_validation.py`, asserting `0`, `CL$FREQ`, `@` and `$` valid as **Codelist** ids. Rewritten to state the distinction rather than deleted: the `IDType` cases moved to a `Code` position where they genuinely are valid, NCName cases added for the maintainable position, and the agency cases `AG@NCY` / `A.B@C` / `0.1` moved from the valid list to the invalid one, where the XSD puts them.

Two assertions matched on the literal word `"invalid"` in the message, which pinned one of the two rules by accident; they now assert on the issue *path*. Same over-detection pattern #214 catalogued — and this is the third time this milestone that an error-text assertion has had to be loosened after a correct change.

## The property the issue asked for

```python
validate(cl)
_round_trip(fmt, StructureMessage(codelists=[cl]))
```

For any generated artefact, `validate()` passing implies the serialisation is schema-valid, in all four formats. That is the invariant #221 was really about, and it is now stated rather than assumed — meaningful because the strategies model all three id types independently of `validation.py`.
