## Summary

Replace stdlib \`json\` with \`orjson\` at the 4 SDMX-JSON call sites (writer, reader, metadata writer, metadata reader).

## Measured impact

ESTAT HICP 3.8 MB fixture, 10-round median wall (laptop):

| | sdmxlib (before) | sdmxlib (after) | pysdmx |
|---|---|---|---|
| Serialize JSON | 5.6 ms | **2.33 ms** | 4.8 ms |

**2.4× faster** vs the stdlib path. Now ~2× ahead of pysdmx on the 3.8 MB fixture; up from being 17% behind pre-swap (per MR !96).

Encode is the dominant cost; orjson is ~9× faster than stdlib on a 1 MB dict. Decode benefits too (~2× faster) though most parsing flows still go through XML — JSON decode is the small fraction.

## Why orjson (not msgspec)

Both are essentially tied at ~0.45 ms encode on a 1 MB payload — within 5% of each other. orjson is the cleaner pick:

- Single-purpose JSON library (no struct/serialization framework surface)
- Widely used in the Python ecosystem (FastAPI, Pydantic v2, Litestar)
- Stable 3.x API (msgspec still 0.x)
- Direct drop-in: \`orjson.dumps(d)\` returns bytes — matches what \`write()\` already returns
- Rust core, conservative deploy

msgspec.Struct features (typed structs, validation, multi-format) aren't relevant here — the SDMX-JSON wire shape diverges from our attrs model enough that the conformance work already projects model → dict explicitly. Adding msgspec.Struct on top wouldn't simplify that.

## API translation handled

- \`orjson.dumps\` returns \`bytes\` directly — drop the \`.encode(\"utf-8\")\` step
- \`ensure_ascii=False\` is the default; non-ASCII passes through raw (output is ~6% smaller than stdlib's \`\\uXXXX\` escape-sequence form)
- \`indent\` becomes \`option=OPT_INDENT_2\` (2-space indent only — fine for our pretty_print use)

## Dep change

\`orjson>=3.9\` added as baseline runtime dep alongside attrs/httpx/lxml/duckdb/polars/pyarrow. CLAUDE.md updated to document this and ban stdlib \`json\` from the sdmx_json subpackage going forward.
