Closes #270.

`to_sql()` was order-dependent, and so was the IR: `filter(a).filter(b)` and `filter(b).filter(a)` matched the same rows while differing in text **and** as values. A downstream cache keying on either lost hits as query diversity grew — a failure that reads as a capacity problem rather than a keying bug. sdmxlib has no cache of its own; this is a requirement from `sdmxlib-rest`.

`canonical_key()` on all four query classes returns a hashable tuple equal exactly when two queries mean the same thing. Determinism across processes is asserted through a real subprocess boundary under three `PYTHONHASHSEED` values — no in-process test can see that failure, since `hash()` is stable within a run.

## Canonical in the key, not at construction — measured

The issue asked for a total order on `predicates` at construction. Implemented that way first:

| | main | at construction |
| --- | --- | --- |
| `is_in`, 5000 members | 115 us | **13.3 ms** (116x) |
| `is_in`, 100 members | 7.6 us | 279 us (37x) |
| chain of predicates | 11.5 us | 59.7 us (5x) |
| single predicate | 2.7 us | 6.7 us (2.4x) |

Every construction paid for a full recursive key build, on the path #271 already flags as hot. Moving it into the key puts the cost on the caller who asks for one: benchmarks now **identical to main**, and the SQL corpus is **byte-identical** — so the non-empty corpus diff I predicted on the issue does not happen, because the design that would have caused it was abandoned.

The trade, stated rather than buried: the stored tuple and the emitted clause order stay as the caller wrote them. Only the key is canonical, and the key is what a cache uses.

## A bug shipped and caught inside this change

The first `canonical_key` keyed query objects **on their own compiled SQL**. `CodeQuery` satisfies the `SqlRelation` protocol — `to_sql` plus `columns` — so a `runtime_checkable` isinstance matched before the attrs branch, and that SQL is emitted with `omit_order=True`. Two queries differing only in `order_by` produced the same key: a cache would have served one page order for another, which is exactly this issue's failure mode reintroduced by its own fix. Caught because the test asserts the order-sensitive case; reintroducing it now fails three tests.

## The boundary, documented and pinned

The key identifies the *question*, not the *answer*. Two stores with the same codelist URN key identically, as does one store before and after a write. That is correct — a connection has no stable cross-process identity, and baking one in would destroy determinism — so a cache key is a pair, `(datasource identity and epoch, canonical_key())`, and we supply only the second half. Filed as #298; `sdmx._meta` has no epoch today.

`order_keys` is deliberately **not** canonicalised. `_COMMUTATIVE_FIELDS` is keyed on `(class, field)` so adding it by carelessness is not a one-word mistake. The issue's third bullet is also stale — #294 made chained `order_by` replace.
