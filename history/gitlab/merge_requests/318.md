Follows !317; the same problem one layer down.

`uri` is declared on `IdentifiableType`, so every item has one, and the store carries it on the artefact **spine** only (#238). Authoring a code with a uri into a registry and reading it back loses it, silently.

`storage` joins `TARGETS`, so `sl.unrepresentable(codelist, "storage")` answers it and `Registry(target="storage")` refuses it — which reads oddly at first and is the useful case: *"hold me to what this store can actually keep"*.

## `level.coding_format` is deliberately not declared

It is a tracked defect (#159 B) — the store *should* persist it — and declaring it would tell an author the loss is permanent and invite designing around a bug someone means to fix. The round-trip guard's cross-check skips non-"by design" reasons for exactly this, and a test pins the exclusion.

## A bug the work produced

Two sites formatted the target into a message and both said "SDMX-ML storage", which is not a thing. `describe()` is the one place now, and it is checked.

## Speed, since this sits on `Registry.add`

Measured on ECB's 183-artefact catalogue, best of 5, repeated:

    target=None    2.560 ms/artefact
    target='2.1'   2.575 ms/artefact   (+0.6%)

With the check monkeypatched out entirely the difference was **-0.93%** — removing it measured *slower*, so the cost is below this machine's noise. Directly: `unrepresentable()` on the largest artefact in the payload is 0.3 us, 0.013% of a 2.5 ms add. With no target it is one attribute load and a compare.

No wall-clock guard added: `caching.md` asks for a count of expensive calls, and there is no expensive call here to count. The numbers are recorded in the commit instead.
