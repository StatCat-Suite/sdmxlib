Partial for #209 — the aliasing half. **531 references rewritten, no behaviour change.**

## What it removes

Each reader and writer rebound every shared helper to a module-level underscore name:

```python
_helpers = make_reader_helpers(com=COM, str_=STR, mes=MES)
_read_istring = _helpers.read_istring
_resolve_ref  = _helpers.resolve_ref
...   # 21 of them, per file
```

So `_read_istring(el)` read like a module-private function when it was a shared helper bound to this module's namespaces. The comment said it was temporary:

> bound here under their **legacy** underscore names so the rest of this module (which uses them extensively) can keep its existing call sites

Scaffolding from the extraction into `_common`, never removed once that settled. Call sites now say where the helper comes from without leaving the line.

## Two dead bindings, found by doing it

`sdmx_ml30/writer.py` and `sdmx_ml31/writer.py` each bound:

```python
_write_representation = _helpers.write_representation
```

*and* defined their own `def _write_representation(...)` later in the same file, shadowing it. **The alias had no effect in either file.**

That is exactly the confusion the aliasing invites — and it was invisible precisely because every helper looked like a local underscore name. It also surfaced as a bug in my first attempt at this change, which rewrote the `def` line; caught by ruff, redone with shadowed aliases excluded rather than rewritten.

## What is deliberately left

The namespace tag builders `_c` / `_s` / `_m` (524 call sites) stay bound. They appear inline in every lookup, and #209's prefixed-path conversion **deletes** them rather than renaming, so converting them now is work undone immediately. The module comments now say so.

## No cost

Attribute access measured at **12.4 ns/call** against **13.0 ns** for a rebound module-level name — if anything faster, and noise either way.
