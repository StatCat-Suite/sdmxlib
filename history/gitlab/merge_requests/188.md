Every site had a type already present in `model/`. That is the line that separated #202 from #203: no Protocol had to be designed, so this is find-the-type-and-write-it.

The four tree-walkers are the clearest — each already declared its **element** type in the `result` parameter one line below its `Any`:

`_write_representation` takes the existing `Representation` alias (`Ref[Codelist] | Facet | None`); the body `isinstance`-checks `Facet` then `Ref` two lines below, so the `Any` was disabling checks over a union the model already names.

`_write_id_pair_maps` keeps its `getattr` reads — `ItemMap`/`ComponentMap` spell the endpoints `source_id`, `ValueMap` spells them `source_value`, so a union plus `getattr` is right — but the locals are now annotated `str` so the `Any` that `getattr` returns dies on that line instead of riding into `.set()`.

## Two defects fell out that were not on the issue's list

**1. `_build_representation` had four wrong annotations.** `min_value` / `max_value` / `start_value` / `end_value` were declared `str | None`. The backing columns are `DOUBLE` and `Facet` declares those fields `float | None`. Nothing ever caught it because **both call sites unpack a raw duckdb row**, so `Any` flowed in and the wrong annotation was inert — a textbook case of `Any` upstream making a downstream annotation unfalsifiable. Corrected to `float | None`.

**2. `_to_float` was a no-op.** Once its input type was honest, pyrefly's `unnecessary-type-conversion` flagged `float(v)` as converting a `float` to a `float`. Checked all twelve backing columns across `concept`, `dsd_component` and `metadata_attribute` — every one is `DOUBLE`, which DuckDB already hands back as a Python float. The function never converted anything. Removed; 8 call sites inlined.

I treated this as in scope rather than filing it: typing the parameter *truthfully* is what the issue asks for, and stopping at an annotation I could see was false would have been the symptom-fix this milestone exists to avoid.
