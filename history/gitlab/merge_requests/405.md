The write-side half of the `sdmx_ml30` → `sdmx_ml31` fork drift. #345 fixed the
read side; this is worse, because it was silently losing data on the way out.

Ten `write_annotations` calls present in the 3.0 writer were absent in the 3.1
one — codes, concepts, dimensions, time dimensions, attributes, measures,
agencies, data providers, hierarchical codes, metadata attributes — plus
`Concept/Parent`, so concept hierarchies serialised flat.

**Nothing failed.** Emitting less is schema-valid: the XSD makes annotations
optional, so XSD validation cannot distinguish "no annotations" from
"annotations dropped", and the round-trip fixtures did not annotate anything
the comparison would have noticed.

## The guard

`tests/unit/test_ml3_writer_parity.py` — one message reaching every
`write_annotations` site in the 3.0 writer, each with its own marker, compared
on emitted **vocabulary** rather than bytes.

It took two rounds of checking the guard against itself before it was worth
having, and both rounds are why I trust it now:

1. The first version matched `marker in document`. `"CODEANN" in "HCODEANN"` is
   True, so the code case passed for a document where the code's annotation had
   been deleted. Now matches `id="{marker}"`.
2. The second version annotated the items but not the schemes, and skipped ten
   artefact kinds. Planting each restored line back out one at a time showed
   **17 of 28 deletions surviving it**. The fixture now covers all 27 sites and
   **all 28 planted mutants die**.

`test_every_annotation_site_is_reached` counts the 3.0 writer's call sites
against the marker list, so a writer growing a 28th site fails here rather than
being guarded by nothing.

## What it cannot see

A field *both* writers drop — the vocabularies match, so there is nothing to
report. `Category` / `CategoryScheme` annotations are exactly that, in all three
writers. Filed as #354, with a note that a field-coverage check against
`__attrs_attrs__` would find that whole class mechanically.
