Closes #257. Part of %13.

Three properties should hold of any statement the library emits, whatever query
produced it. **None was asserted.**

## Not a parse check

The DSLs already *execute* every generated query against real DuckDB
(#248/#249), and executing subsumes parsing — a "does it parse" assertion would
be strictly weaker than what exists. What these add is structural: a statement
can run perfectly and still have a user value welded into its text, or name a
relation nobody intended.

| invariant | catches |
| --- | --- |
| `assert_single_statement` | statement injection — DuckDB runs *every* statement in a multi-statement string |
| `assert_no_literals_in_predicates` | a user value reaching the SQL text at all, rather than "it was escaped" |
| `assert_only_known_tables` | interpolated identifiers, bad schema remaps |

All three run over the generative strategies, both structural DSLs, and every
query shape that reaches a distinct emitter.

## Each was shown to fail

CLAUDE.md rule 4, applied to checks rather than oracles — a green invariant
proves nothing until it discriminates. Five injected defects (second statement,
spliced value, spliced LIKE pattern, unknown relation, remapped schema), each
caught by exactly the invariant that should, with benign counterparts asserted
to pass — including a CTE self-reference, which is a table-shaped node that is
not a table.

The DuckDB multi-statement behaviour is pinned as its own test: if a future
version stops accepting it, someone should be told rather than left with an
invariant that has quietly become ceremony.

## The `order_by` decision

#257 said silence was the actual defect, and it was. `_build_query`
interpolates `columns`, `where` and `order_by` verbatim; the docstrings
described the first two as caller-composed and `order_by` as *"Optional SQL
ORDER BY clause"* — which reads benign. Since DuckDB runs multi-statement
input, a server forwarding a `sort=` parameter has a **statement**-injection
hole, and `parse_components` documents that sdmxlib is designed to sit behind
exactly such a server.

**Decision: document uniformly rather than validate.** All three carry the
identical exposure, so guarding only `order_by` would give false assurance; and
splitting SQL at runtime to find statement boundaries is the hand-rolled
parsing that creates the next defect — with the parser deliberately test-only.
The hazard is now stated in both `DataStore.query` and `_build_query`, with the
measurement, and the invariant is asserted over everything the library emits.

Say the word if you would rather `order_by` were validated instead; the
reasoning is recorded at both sites so it is easy to revisit.

## Folded, not duplicated

#250's byte-identity check is **removed** in favour of the AST form, as #257
asked. Byte-identity proves the one value under test did not leak;
`assert_no_literals_in_predicates` asks whether *any* value is in the text — a
leak preserving the byte count would pass the old and fail the new. #250 keeps
its semantic half, which this says nothing about.

## Dependency boundary

`sqlglot` is dev-only, kept there by two guards: one reads `pyproject.toml`,
one imports `sdmxlib` in a subprocess and asserts the parser is absent from
`sys.modules`. A declaration is a promise; the import is the observation.
