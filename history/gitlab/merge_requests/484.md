    'list'          # declared: tuple[Contact, ...]

Thirty fields declared `tuple[X, ...]` with no converter, so the value was
stored exactly as passed and the annotation was false. `converter=tuple` on
each, matching the shape `binding.py` already uses.

Re-surveyed with the `attrs.fields` walk the issue describes: exactly the 30
listed, none optional, so the builtin covers them. **Zero remain.**

## Two the survey as written could not see

* **`KeyValue.values`** declares `frozenset[str]` and had no converter either —
  same defect, one type over, missed because the survey filtered on `tuple[`.
  Widening it to `frozenset[`/`set[` found this one and only this one.
* **`DataKey.values`** is `tuple[tuple[str, str], ...]`, the model's only
  nested declaration. `converter=tuple` fixes the outer sequence and leaves the
  pairs as lists — the same lie one level down — so it gets `_to_key_pairs`
  instead. Verified: `DataKey(values=[["FREQ", "A"]])` was `(['FREQ', 'A'],)`
  and is now `(('FREQ', 'A'),)`.

## `converter=tuple`, not a generic helper

Wrote a `to_tuple[T](Iterable[T]) -> tuple[T, ...]` first, on the theory that
bare `tuple` widens the generated `__init__` to `tuple[Any, ...]` and lets a
list of the wrong element type through. Measured against basedpyright: both
forms give `xs: Iterable[str]` and both reject `list[int]`. The helper bought
nothing, so it is not here — the builtin matches the existing precedent.

## None of the 30 wanted to stay mutable

The issue asks this explicitly. Checked for in-place mutation of every one of
the field names across `src/` — `append`, `extend`, `insert`, `remove`, `pop`,
`sort`, `clear` — and found none, so `tuple` is right for all thirty and no
annotation needed relaxing to `list[...]` instead.

## The guard is a walk, not thirty assertions

`tests/unit/test_field_converters.py` enumerates the model and asserts the
property of every field it finds, because the failure mode is *forgetting one*
on a field added later — thirty hand-written assertions would all pass while
the thirty-first goes unconverted. It also asserts the walk still finds ≥30
fields, since a guard that silently stops enumerating reports the same green as
a clean model.

Sabotage-checked: removing one converter fails with
`1 field(s) declare an immutable collection and store what they are given:
Agency.contacts`.

The behavioural half is asserted too, including the part that never looks like
a type error — `@frozen` is shallow, so before this a caller could keep their
list and append to it after construction. `test_mutating_the_caller_s_list_
afterwards_cannot_reach_the_artefact` is that, and idempotence is checked
because the readers already pass tuples.

Closes #371.
