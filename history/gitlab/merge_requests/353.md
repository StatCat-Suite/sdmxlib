## 1. `docs/design/registry-and-catalog.md` — the Registry API

Started from a question about the top-level names — is `Registry` vs
`FederatedCatalog` a meaningful divide, and why is mixing sources a second
class rather than a parameter? It is not, and the names are close to inverted:
the spec's word for structures plus registrations plus the data they point at
is *registry*, and `DataflowBinding` is a registration in all but name.

Settles: one family of three types with `FederatedCatalog` deleted; types
rather than a factory, because `sql()` / `write_observations()` / `download()`
must be **absent**, not raising; one compiler, with *admission* varying rather
than compilation; provenance as a source chain, in which `store=` is a position
and `FederatedRegistry` is a source that dispatches by agency; and
`observations()` taking identity while resolving structure locally.

§3 audits the surface against one test — can every entry's presence **and
absence** be assigned by a stated rule? Twelve can; sixteen are a tail with
dispositions; and it says where it is still incomplete.

**Two defects found while checking claims:** `.urn` on an instance is a bound
method, and `ref.py`'s own docstring offers `Ref.unresolved(cl_freq.urn)`,
which raises. The data fetch hardcodes `Accept: text/csv`, so a download's path
extension is decorative and SDMX-ML data cannot be requested at all.

**A clean-room review reopened five questions.** Two decisions rested on false
readings of the source and are rewritten (§5.5's `resolve=` default would have
broken `dsd.dimensions["FREQ"].codelist()`; §5.7's claim that the writers need
only a column order is false — they select by physical name, and the JSON
writers need the dataflow's urn and name). §1.1's central table was backwards
and contradicted its own prose.

## 2. `docs/design/data-plane-pushdown.md` — step 1's design

`observations()` on `RestRegistry` is the step that could still show the
unification is wrong, and none of it exists — `Request.path` is hardcoded to
`structure/`, `Capability` is structural, and nothing maps a `Pred[ObsRow]`
onto a key.

Three findings:

- **The data surface is richer than the structural one.** Structure pushes
  equality on identity and nothing else. Data pushes equality and membership on
  every key dimension via the positional key, a range on time via
  `startPeriod`/`endPeriod`, and on 3.0 membership on *any* component via
  `c[…]`. The library already models `c[…]` from the server side.
- **`Capability` must key shapes by column *role*, not name** — an observation's
  columns come from a DSD, so `column="REF_AREA"` is a fact about one dataflow
  rather than about the backend.
- **The streaming question resolves into a rule**: a fully-pushed query streams
  from the wire, a query with a residual materialises first and streams from
  the store — `Program`'s existing distinction surfacing as a memory property.
  With `explain()` saying which, because it is 5 MB against the whole slice.

It also records **what would falsify the unification**, so it is recognisable
rather than argued about later.
