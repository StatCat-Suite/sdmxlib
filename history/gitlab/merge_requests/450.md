Closes #378, and fixes a second defect found in the same measurement.

## The read was proportional to the codelist, not to the request

Resolving an item `Ref` loaded the item's **entire parent scheme**. That was
the #72 fix — load it once rather than once per ref — right about the fan-out
and wrong about the size. A **28-node** hierarchy cost **3.32 s and 1.28 GB**
because its nodes reference `CL_GEOGRAPHY`, which has 579,951 codes.

Reading only the URNs asked for is **never slower** and up to **178x** faster:

| distinct codes wanted | load the scheme | targeted |
| --- | --- | --- |
| 28 | 2254 ms | **13 ms** |
| 1,660 | 2176 ms | **16 ms** |
| 46,027 | 2187 ms | **198 ms** |
| 63,404 | 2201 ms | **262 ms** |
| 499,138 (86% of the codelist) | 2241 ms | 2271 ms |

They converge only where the caller wants nearly the whole scheme — which is
why there is **no threshold**. A branch that buys nothing at the crossover and
178x nowhere else is a knob with no setting worth choosing.

End to end on the bundle:

| | before | after |
| --- | --- | --- |
| `get(H_CP_GEO_HCCSS, eager=True)` — 28 nodes | 3318 ms / +1283 MB | **60 ms / +65 MB** |
| `get(H_CP_GEO_FSA, eager=True)` — 1,660 | 3385 ms | **83 ms** |
| `get(H_CP_GEO_CMA_CT, eager=True)` — 46,027 | 2997 ms | **765 ms** |
| `get(H_CP_GEO_ADMIN, eager=True)` — 63,404 | 4371 ms | **1115 ms** |
| `get(H_CP_GEO_FED, eager=True)` — 499,138 | 8491 ms | 8522 ms (parity) |

## The resolver cache was defeating itself

Chasing the same measurement turned up a second defect, and it explains why
"warm" reads in %18's numbers were never warm.

`docs/design/performance.md` §Layer 3's cache holds **256 entries**, and every
*item* resolved was promoted into it. Reading a 1,660-node hierarchy left it
holding **256 `Code` entries and no `Codelist`** — the parent scheme it had
just loaded, evicted by the items it had just resolved from it.

So Layer 3 was defeated by its own bookkeeping for any artefact with more than
256 items, which is every artefact the cache exists for, and the codes left
behind were near-useless because the next hierarchy wants different ones. Four
successive eager reads in one process measured **2086 / 131 / 2476 / 2920 ms**.
They are now **62 / 88 / 320 / 752 ms**.

Items now go through `_CallScopedMemo.set_local`: visible for the rest of the
call, never promoted.

## Notes for review

- **Three routes, in cost order** — a scheme already resolved (free, and it
  covers the caller who genuinely wants the whole thing); the targeted batched
  read; and loading the scheme, kept for the two cases the targeted read cannot
  serve: a `Concept` (no batched by-URN reader, and 349 concepts in the whole
  bundle means nothing to win by adding one) and a `version="latest"` item URN,
  whose stored `code_urn` carries a concrete version instead.
- **A rewritten guard, not a renumbered one.**
  `test_resolve_refs_one_codelist_load_for_n_node_hierarchy` asserted
  `cl_loads == 1` — the #72 bound, correct at the time, now **zero**. Rather
  than flip the number, it asserts what the old test was reaching for (no
  per-ref fan-out — exactly one read) *plus* what `cl_loads == 1` could not
  distinguish: that the read is **of the URNs asked for**, not of the codelist.
  That distinction is the whole of #378.
- **The new tests were run against the pre-fix source** and all four fail
  there. `test_resolver_cache_holds_schemes.py`'s fixture is 400 codes for a
  stated reason: at 256 or fewer, nothing is evicted and every assertion in the
  file passes against the broken code.
- **One thing worth knowing** that the cache test documents: reading an
  artefact directly does *not* cache it. The resolver cache holds resolution
  *targets*, so the test puts the codelist there the only way anything gets
  there — as a DSD dimension's representation. My first version asserted the
  wrong precondition and failed.
- **The bundle tier removed its own marker again.** #378's assertion turned
  into an `XPASS(strict)` the moment this landed, so its `xfail` came off in
  this commit. Third time that mechanism has worked as intended rather than
  being forgotten.

## What this leaves

`get(H_CP_GEO_FED, eager=True)` is unchanged at ~8.5 s — it genuinely wants 86%
of the codelist, so parity is the correct outcome. Its remaining cost is the
3.67 s "ref walk + assignment" that #383, #384 and #154's item 2 decompose, and
those are now the largest items in %18.
