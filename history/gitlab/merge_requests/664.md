# Merge request !664: fix(query): a grouped aggregate honours where=

When an aggregate in `Query.agg`, `group_by().agg()` or `having` was over a column that doesn't fan out, its `where=` was **silently dropped**. For example, `cl.codes.agg(n=sl.q.code.id.count(where=sl.q.code.depth == 0))` compiled to a bare `count(*)` and answered 5 where the right answer was 3. The same happened for `count`, `n_unique`, `sum` and `list`. Only the per-row reading, over a fan-out, applied `where=`, and only that reading was tested.

**Fix:**
- The grouped path compiles the restriction in its own scope, as `FILTER (WHERE …)` on every aggregate call. For `n_unique` that means both of its halves.
- The scope joins any to-one route the restriction reaches.
- An empty match gives `0` / `[]`, as it does over a fan-out.

**Tests:** nine new tests in `test_query_filtered_aggregates.py`. All of them fail on the old compiler.
- Every aggregate kind.
- A to-one hop and a to-many edge inside the restriction.
- The empty case, `group_by`, and `having`.
- A Hypothesis property: the grouped and correlated readings of one restriction agree with each other and with Python.

The `sum` case first passed on the old code by coincidence (the excluded row had position 0). It was changed so that it can fail.

`llms-dsl.txt` now shows the form, so the doc test runs it too.
