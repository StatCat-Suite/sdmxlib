## The runner had been dead, and nothing said so

Before a survivor could be read the run had to work, and it did not:

    failed to collect stats. runner returned 1
    1610 mutants   killed 0   survived 0   no-coverage 0

`test_data_format.test_the_cookbook_table_lists_every_member` reads
`docs/cookbook/data.md` through `Path(__file__).parents[2]`. mutmut copies
`src/`, `tests/`, `pyproject.toml` and `uv.lock` into `mutants/` and nothing
else, so that read raised `FileNotFoundError` there and took the **stats
phase** with it. Mutation testing is not in `just ci`, so every run since that
test landed reported zero of everything and nothing said so.

Exactly the trap `test_count_any.py` documents against #284, one directory
over. Two instances now, both found only when someone next tried to run
mutation. The guard is keyed on `docs/` being absent **entirely**, not on the
file, so a deleted cookbook page still fails in a real tree rather than
skipping quietly.

## What they found: a declared branch nothing could reach

The two functions are the same shape twice — absent / one value / several —
and 9 mutants in each sat where no query can go:

**Every declared facet and every declared root constraint carries exactly one
value.** All three `_edges.FACETS` are single, and all twenty `__constraint__`
attributes in `accessors.py` are `("artefact_type", ("Something",))`. The
multi-value `IN (...)` branch is unreachable through `q.*`.

Classified as **dead by declaration, not by design** — a new verdict for this
file, distinct from the two kinds installment 1 recorded. Both docstrings state
the capability ("a facet may cover several stored kinds even when the domain
exposes one name"), and a facet spanning `Dimension` and `TimeDimension` is an
obvious future one. So the branch stays and is pinned directly, rather than
leaving whoever declares that facet to discover whether it works.

The other three per function are reachable and emit SQL that *runs*, which is
why end-to-end tests pass over them: `len(values) == 1` mutated to `!= 1`
routes a single value through the `IN` branch and emits `IN (?)` — different
text, same rows. Only an assertion on the emitted SQL separates those, so the
new tests assert text and params rather than result sets.

`test_no_declared_facet_or_constraint_carries_more_than_one_value` records the
premise as an assertion, so the day a multi-value facet is declared it fails
and says the branch is now live.
