A stream could be bounded *or* ordered, never both: no order meant an
unsorted scan, and any order meant a global sort whose buffer is the
whole result. This adds the third case.

When the requested order begins with the binding's partition columns,
the stream is served one partition at a time, visited in key order and
sorted inside each. The rows are identical to a global sort's, because
partitions are disjoint on those columns — so the order is *guaranteed*
rather than incidental, while each sort covers one partition.

Measured through this API, 4M rows:

    unpartitioned (global sort)      323.1 MB
    20 partitions                     37.6 MB
    200 partitions                    18.2 MB

all globally ordered. Peak tracks the largest partition, so partition
granularity — not `chunk_rows` — is the memory knob.

**DuckLake does not do this for us**, which was worth checking before
building: on a real partitioned lake table the global sort cost 126.3 MB
against 125.8 MB unpartitioned, identical within noise, because
partitioning prunes for a `WHERE` and an `ORDER BY` still sorts
everything. And a partitioned lake scan comes back *unordered*, so there
is no accidental ordering to lean on either.

Three things kept honest:

* **An order the partitions cannot serve falls back to the global sort.**
  `ORDER BY TIME_PERIOD` over a table partitioned on `REF_AREA`
  interleaves partitions; a per-partition plan would silently return
  something else. The fallback matters more than the optimisation.
* **A partition id the binding cannot map is dropped, not guessed** — a
  wrong partition column plans a stream that returns a subset.
* **An empty result falls back**, because a chained reader needs a schema
  and there is no first partition to take one from.

`from_batches` pulls lazily, so the second partition's query does not run
until the first is drained — which is what keeps peak at one partition
rather than their sum — and the caller still gets one thing that is both
an iterator and a context manager.
