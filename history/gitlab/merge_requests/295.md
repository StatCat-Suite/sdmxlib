## `just mutate-module` and `just mutate-scope`

`just mutate` is all-or-nothing over `only_mutate`, and that scope is now **hours**, not the "~11 min" the #213 pilot measured. There was no way to mutate just the module you changed.

```
just mutate-module sdmxlib.model.code_query
just mutate-module sdmxlib.model.validation.x__validate_hierarchy
just mutate-scope
```

mutmut has no path flag, and it does **not** accept a prefix:

```
AssertionError: Filtered for specific mutants, but nothing matches
Filter: ("'sdmxlib.model.validation.x__validate_hierarchy'",)
```

Only exact mutant names work, so `mutate-module` expands the prefix against `mutmut results` first. Worth stating plainly: **the first version of this recipe passed the prefix straight through and silently did nothing useful.** It is now tested against a 14-mutant function and reported as a 93 s scoped run.

`mutate-scope` exists because scope is the one number that decides minutes-vs-hours, and it was invisible — this issue’s own statement counts had drifted ~50% after the shared compiler moved into `_query_common.py`, and nobody noticed because reading the scope meant opening pyproject and counting by hand. Counted with coverage’s parser so it matches coverage.

## The two traps, now written down

Both were paid for during this diagnosis:

- **Editing `[tool.mutmut]` changes the config fingerprint and forces a full stats recollection.** This invalidated one of my experiments: a `--max-children 1` run that appeared to take >10 min was timing the recollection, not the mutants. I then walked into the same trap while documenting it.
- **mutmut forks per mutant and books a dead child as a timeout** — how 356 macOS fork-safety segfaults presented as timeouts (!294).

`CLAUDE.md`’s `~11 min` is corrected to point at the justfile rather than carry a number that will drift again.

## What this does not fix

283 `validation.py` mutants still record as timeouts. They are **not hangs** — verified by applying one by hand: its 53 covering tests all pass in 2.13 s, so it is a *survivor* being mis-booked. Rejected by measurement, in order: mutant hangs, parallel contention (8 concurrent copies of the set finish in 6 s against a 45 s budget), DuckDB thread-pool interaction with `fork()` (forcing `threads=1` changed nothing), and escalation to the full suite (mutmut’s `run_tests` passes only the covering tests, with `-x`).
