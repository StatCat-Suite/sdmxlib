# Merge request !390: feat(api): FederatedRegistry.get takes resolve= and partial=, translated per source

| | |
| --- | --- |
| State | merged |
| Opened | 2026-08-19 |
| Merged | 2026-08-19 |

Closes #343. `fed.get(urn, resolve=True)` was a `TypeError`, so a caller
holding a federation had to know which registry owned ESTAT in order to
ask for a resolved fetch — which defeats the type for a very ordinary
request.

The three `get`s do not share a signature and should not: #340 refuses
`resolve=` on `LocalRegistry` on purpose, because a store has already
paid for every hop. So the federation **translates** rather than
forwards. It can, because routing is by agency and the agency is in the
URN: the source is known before the call, with no I/O.

- `resolve=` is dropped for a source that does not take it. Not a silent
  no-op: a local store resolves unconditionally, so the artefact already
  satisfies `resolve=True`, and `resolve=False` only declined work that
  was not going to happen. The result is what was asked for either way.
- `partial=False` is refused there instead. It has no such reading — a
  store holds whatever was written to it, so it can neither honour
  "untrimmed" nor discover that it has not. Answering it with trimmed
  codelists is the #338 defect exactly, and that one shipped because
  nothing raised. `partial=True` is the no-request value and is dropped.

The refusal is per-URN, not per-federation, which is the point of
routing by agency: `test_a_mixed_federation_refuses_only_the_route_that_
cannot_answer` pins that the same call is fine for ESTAT and refused for
a locally-authored agency.

Which keywords a source accepts is read off its `get` signature and
cached per type. A `runtime_checkable` Protocol cannot express this —
it checks that a method exists, not what it takes, so every registry
would match.

Found on the way, filed as #344 rather than fixed here: `partial=False`
is ignored for a **pinned** URN, on a bare `RestRegistry`. The session's
resolved map is keyed by URN alone, so a `referencepartial` fetch marks
it resolved and the `detail=full` request never goes out.
`tests/unit/test_rest_partial.py` misses it because every test there uses
`latest`. `test_partial_reaching_the_wire_is_a_latest_only_guarantee`
records the wrong behaviour on purpose so the gap is not invisible, and
says to delete itself when #344 lands.
