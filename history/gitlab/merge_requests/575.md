Part of #421 (codelist extension row).

**Decisions:**
- Materialise when the extended codelists resolve, refuse otherwise.
- The materialisation is a public model method, `Codelist.apply_extensions`. It isn't named `materialise`, because `LazyCodelist.materialize()` already means "load eagerly".
- Extended codelists come from a resolved Ref or the same message.
- An inherited code whose parent wasn't inherited becomes a root.

**Semantics:**
- The codelist's own codes come first and win a clash.
- Then each extension, in order; an earlier extension wins a clash. This follows the XSD documentation and FMR's inherited-codelist documentation.
- Each extension contributes its selection: ids, `%` wildcards, and cascade (`true` / `false` / `excluderoot`), inclusive or exclusive.
- The prefix applies to both `id` and `parent_id`.
- A nested extension is applied first. A cycle raises `ValueError`.
