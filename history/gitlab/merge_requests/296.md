## Root cause

The 283 `validation.py` "timeouts" are not hangs. mutmut runs a stats pass — the whole selected suite, **in-process** — then `fork()`s one child per mutant off that parent. Children forked from a parent that has already executed ~3,900 tests are pathological. Same mutant, same 53 covering tests:

```
forked from a LIGHT parent    exit 0, 3.0 s CPU     (correctly: survived)
forked from a HEAVY parent    never completed in 8 min
```

`debug = true` shows how mutmut records that: **`exit code -24`** — SIGXCPU, the `RLIMIT_CPU` kill — booked as a timeout.

## The fix is the harness shape

Narrowing the test selection keeps the parent light, which fixes classification and runtime *together*:

| | mutants | timeouts | wall |
| --- | --- | --- | --- |
| `_validate_hierarchy`, full selection | 14 | **14** | 93 s |
| `_validate_hierarchy`, one test file | 16 | **0** | 7 s |

```
just mutate-area src/sdmxlib/model/code_query.py tests/unit/test_code_query.py

  315 mutants   killed 189   survived 82   no-coverage 44
  70% of covered mutants killed by this test selection
  16 s
```

That is the first mutation data any SQL-compiling module in this repo has produced — the thing #218 and #252 wanted and never got.

## Notes on the tool

- Rewrites `only_mutate` + the test selection, runs, restores pyproject in `finally` so ^C restores it too.
- Drops `mutants/` first: that cache is keyed on the old config and would otherwise report the previous area's verdicts as this one's.
- Tally comes from `export-cicd-stats`, **not** `mutmut results`. The latter lists only survivors and timeouts, so counting its lines reported `survived=82` for an area that had killed 189 alongside them — a healthy result rendered as total failure. The first version of this tool did exactly that; worth knowing before anyone reads a number off `mutmut results` again.
- The report says what a narrow score is *not*: mutants whose covering tests lie outside the selection never run, so it answers "does this test file pin this code", not "what is the module's score".

## Hypotheses rejected along the way

Each was load-bearing at some point, and each died to a measurement: mutant hangs (2.13 s to run its covering set by hand), parallel contention (8 concurrent copies in 6 s against a 45 s budget), DuckDB threads x fork (`SET threads=1` changed nothing), full-suite escalation (read `PytestRunner.run_tests` — it passes only covering tests, with `-x`), fork+DuckDB deadlock (5 ms in isolation), inherited CPU accounting (a forked child starts at 0), and import cost.

## Still true, and recorded on #304

`just mutate` over the full scope remains hours and still produces the spurious timeouts, because its test selection is `tests/unit`. This MR does not change that default — it makes the narrow path the recommended one and explains why in the justfile. Whether to narrow the global default belongs with the scope decision in #304.
