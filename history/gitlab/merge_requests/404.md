# Merge request !404: fix(formats): SDMX-ML 3.1 stops dropping what it never learned to carry

Closes #345. The 3.1 reader and writer both silently lost fields the 3.1
XSD declares, and `gaps.py` — the module whose whole job is answering
"what will I lose" — reported nothing.

Four losses, three of them found while fixing the first two:

* `RepresentationMap` source/target as a primitive `DataType`. The reader
  read only the codelist branch; the writer's docstring claimed *"datatype
  source/target is not exercised by our model"*, which was never true —
  `MapDataType` has been modelled since #131 and the 3.0 writer has always
  emitted it. The claim came over with the fork.
* `Level/CodingFormat` — how codes at a level are shaped. Read and written
  by 3.0, by neither in 3.1.
* **Level annotations**, not in the issue: the 3.1 level writer omitted
  `write_annotations` too, so a level's notes went as well.
* **`DataConstraint.release_calendar`**, also not in the issue and a
  different kind: 3.1 genuinely *removed* `ReleaseCalendar` (declared three
  times in the 3.0 XSD, zero in 3.1), so the drop is correct — but it was
  undeclared, and `gaps.py` said nothing was lost. Now an entry, with the
  reason. The knowledge existed all along in
  `test_cross_version_fidelity._BLOCKED`; it had just never reached the
  module a caller can ask.

**Why nothing caught any of it.** The fixtures were forked and trimmed
alongside the code, so a round-trip compared a document against itself
with the field already absent from both sides — the failure mode that
test cannot see by construction. `CodingFormat` appeared in *no* fixture
in *any* generation, so 3.0's support was unguarded too.

`test_fixture_coverage_parity` is the guard the issue asks for: the 3.0
and 3.1 corpora must exercise the same element vocabulary, and a
difference is a listed decision with an XSD-supported reason rather than
something that happened when a file was copied. It found seven more gaps
beyond `TargetDataType` — `ReleaseCalendar` and its three children, now
exempted with the reason, and `StructureMap`/`ComponentMap`, which turned
out to work in 3.1 and simply had no fixture. Ported.

A stale block goes with it. `("3.0", "3.1", with_representation_map_variants)`
read *"a datatype-target map has no 3.0 form; 3.0 requires TargetCodelist"*
— blaming 3.0, which emits it and always did, for a drop that was the 3.1
leg's. The hop survives now and the test is what said so.

Note the XSD taught me two things while writing fixtures, both worth
having in the corpus: `CodingFormat/@textType` is restricted to
`{Alpha, AlphaNumeric, Numeric}` rather than the full `DataType` set, and
`AnnotationTitle` precedes `AnnotationType`.
