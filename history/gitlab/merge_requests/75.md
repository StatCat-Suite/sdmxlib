Closes **#101**. Both \`ReleaseCalendar\` (2.1 + 3.0) and \`ReferencePeriod\` (2.1-only) were modelled and written, but no fixture exercised them. Adding fixture coverage exposed **three latent XSD-conformance bugs** in the writers.

## Summary
7 files, +139 / −10. CI: **1834 unit + 71 docs** (was 1828; +6 reader/round-trip tests).

## Bugs found

### 1. 2.1 writer emitted ReferencePeriod BEFORE ReleaseCalendar
Per \`ContentConstraintType\` (\`SDMXStructureConstraint.xsd\`), the sequence is \`ReleaseCalendar\` then \`ReferencePeriod\`. XSD-invalid order — would have failed the moment a fixture carried both. **Fixed**: swapped the emit order.

### 2. 3.0 writer emitted ReleaseCalendar AFTER CubeRegion
Per \`DataConstraintBaseType\` / \`DataConstraintType\`, \`ReleaseCalendar\` is in the **base** type (before the extension that adds \`DataKeySet\` + \`CubeRegion\`). XSD-invalid — would have rejected the moment a fixture carried a populated \`ReleaseCalendar\` alongside any cube region. **Fixed**: moved emission to before the cube-region loop.

### 3. 3.0 writer emitted ReferencePeriod at all
SDMX 3.0 dropped \`ReferencePeriod\` from \`DataConstraint\` entirely; the element doesn't exist in the v3.0 namespace. The model field stays (so a 2.1-read constraint with a period can survive in memory) but the 3.0 writer now silently drops it. Documented with a comment so a future reader doesn't try to re-emit.
