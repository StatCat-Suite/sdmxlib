## Two more conformance gaps, same shape as #224's

**Organisation scheme ids are pinned by the schema.** `AgencyScheme.id` is fixed to `AGENCIES` and `DataProviderScheme.id` to `DATA_PROVIDERS` by a `fixed` attribute in **every** SDMX-ML version. A scheme called anything else serialised to XML that failed validation, and nothing stopped you building one. → `validate()`

**2.1 additionally pins their version to `1.0`**, which 3.0 and 3.1 relaxed. A downgrade hazard rather than a bad artefact, so it is checked only when the target version is known. → `check_serialisable`

I found these by **enumerating every `fixed=` attribute in the vendored XSDs** rather than hitting them one at a time. That is worth noting because the full set is larger — `DIMENSION_DESCRIPTOR`, `MEASURE_DESCRIPTOR`, `CONSTRAINT_TARGET` and friends — but those are container element ids the *writer* generates, not values a caller can set wrongly. Enumerating first told me which of the fourteen actually matter; hitting them one at a time would have produced fourteen separate investigations.

## Why these two classes next

**AgencyScheme** because of contacts: `emails` / `telephones` / `faxes` / `uris` each carry `minItems: 1` in the SDMX-JSON schema — the exact constraint that produced the `[]`-emission bug in #216 — and nothing had exercised them. They round-trip correctly, which is a real (negative) result: that bug class was fixed at its root rather than case by case.

**Hierarchy** because it is recursive. The property compares tree **shape**:

```python
def shape(nodes): return [(n.id, shape(n.children)) for n in nodes]
assert shape(back.tree) == shape(h.tree)
```

A flattening bug shows up as the same codes in a different arrangement, which a flat id comparison would pass. The strategy builds the tree from a `code_forests` draw, so acyclicity is structural rather than filtered for.
