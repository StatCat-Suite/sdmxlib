Closes #496.

`jsonschema` skips any `format` it has no library for. None was installed, so no date or date-time we wrote was ever checked. Installing `jsonschema[format-nongpl]` turned up 1,679 failures, and each one was a real format violation.

## What changed

| Found | Decision | Done |
|---|---|---|
| Format checking was silently off | Make it unconditional | dev dep `jsonschema[format-nongpl]`; `test_json_schema_formats.py` checks every format the schemas use through the compiled validator, with an admitted and a refused sample per format |
| Item-map and representation-mapping `validFrom`/`validTo` written as dates (ML 3.0 `xs:date`, JSON `date-time`) | Midnight UTC; refuse any other time | Written as `…T00:00:00Z`. The reader refuses any other instant, a bare date, or a missing zone with `SdmxConformanceError` rather than truncating |
| Constraint period `2025-06-30T00:00:00` (valid `xs:dateTime`, no zone) | Refuse | The 2.0 structure and 1.0 constraint writers raise `ValidationError` naming the path (`_periods.py`) |
| `prepared` on the data writers was a caller string, so it could be zoneless | Take an aware datetime | **Breaking:** `prepared: datetime` on `write_sdmx_json_data` (1.0/2.0), `Dataset.sink_json` and `write_data_json`; a naive one raises `ValueError`, and so does the 1.0 constraint writer |
| TIME_PERIOD value `start`/`end` are zoneless | **Keep, and declare it** | .Stat's [`refineTimePeriod`](https://gitlab.com/sis-cc/.stat-suite/dotstatsuite-components/-/blob/master/src/rules2/src/refineTimePeriod.js) does `parseISO`, then `dateWithTZ` (adds the local offset back), which is correct only for a zoneless value. A `Z` would show 2021-01-01 as 2020-12-31 19:00 in Toronto. NSI WS also writes them zoneless. `is_declared_time_bound` excuses exactly these bounds. A test asserts the excusal is live (the data message's only violations) and that a malformed bound, or a zoneless date-time anywhere else, is not excused |
