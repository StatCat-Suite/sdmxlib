Four more off #355 — and one I got wrong first, which is worth recording because
the same trap has now caught me twice.

## `Agency.parent` is a limit, not a defect

`BaseOrganisationType` declares `<Parent>`, so walking the base chain says an
agency may have one. **`AgencyType` is a restriction that leaves it out** — as
is `DataProviderType` — in all three SDMX-ML versions.

I changed all three writers to emit it and every version's XSD rejected the
document immediately. A restriction *removes*; only the concrete type answers
the question, and the base chain says the opposite.

Second time in this issue: the same reasoning called `ReferencePeriod` a 3.0
constraint element when the name belonged to a registration-query type in a
different file. Both caught by validating rather than by reading more schema —
which is the argument for the conformance checks added in #364.

## `Group.uri` was written by every writer and read by none

The three SDMX-ML readers built `Group(id=..., dimension_ids=...)` and dropped
the attribute sitting right there. SDMX-JSON lost it at both ends.

## A Category's `uri`, at every depth

`CategoryJson` carries a `links` field its builder never filled, and the
recursion meant sub-categories were missing it too. Third such builder after
`LevelJson` and `GroupJson` — a DTO field nothing populates is invisible both to
the type checker and to a round-trip through the same writer.
