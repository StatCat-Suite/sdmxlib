#257 chose to document the text-splicing surface rather than validate
it, on the premise that consumers are first-party and compose these
from constants. #297 made a measurement the prerequisite. The
measurement contradicts the premise.

Across the six consumer repositories, exactly one call site passes
`where` to this API — in an HTTP route — and it builds it from **query
parameters**, with its own operator table, its own column allow-list
resolved through the binding's column maps, and its own LIKE-metachar
escaping. Application code compensating for a library's surface is the
argument for changing the surface, and it is %15's own "every bypass is
a specification" landing on the data plane.

So the assembled statement now goes to DuckDB's own parser before it
runs, and more than one statement raises `UnsafeQueryError`. #257 was
right that hand-rolled statement-splitting is the parsing that creates
the next defect — which is why the connection's parser does it, on the
same handle that will execute the query, exactly as `query/raw.py`
already does for `reg.sql()`. 1.2 µs against a 206 µs query: 0.6%.

**Two stronger fences were built and removed, and both failures say the
same thing.** A table allow-list breaks relation-valued filters, which
reach into `sdmx.code` on purpose, and `Session.value_set`, which exists
to splice a caller's table in by name. A column allow-list — this
issue's option B as written — rejects `columns=["a AS x"],
order_by="x"`, which is correct SQL. Composition across tables and
expressions is the feature here, so no property of the *text* separates
use from abuse.

That is the finding: fencing text can only ever catch the crudest case.
Naming filters, projections and sort keys structurally, so there is no
text to fence, is option C and remains the real answer. Both rejected
fences are kept as tests — they assert the compositions that must keep
working — so the next attempt starts from why they were rejected.
