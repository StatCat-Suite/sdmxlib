Closes #340 (design §5.13). **Also fixes a flake I shipped in !379.**

## The defect

The compiled SQL scanned the whole materialisation store, so an earlier question's rows — or a previous session's, with a persistent `store=` — answered alongside the current fetch:

```
provider serves: ['CL_LIVE']
query answers:   ['CL_LIVE', 'CL_RETIRED']     # withdrawn, still in the store

request: version=latest -> CL_V(2.0)
query:   [CL_V(1.0), CL_V(2.0)]                # store held both
```

What was **not** broken, and what narrowed the fix: a *filtered* query was already correct, because the predicate re-applies locally over the materialised rows. The hole was unfiltered scans and projections.

## A membership table, not a watermark

`WHERE fetched_at >= <the fetch's time>` needs a value that does not exist when the SQL is built — terminals compile first and fetch second, and `to_sql()` is contractually non-executing with output documented as handable to another library. `canonical_key(plan)` **is** known at compile time, so `sdmx.fetch_scope(fetch_key, urn)` needs no reordering and no public signature change.

Three things the build settled that #340 had not:

- **Only maintainable roots need it.** `Capability.scans` is `_maintainable_roots()`, so every REST-backed query is rooted on `sdmx.artefact` keyed by `urn` — the scope is always a set of URNs. The guard on table and key is for `ObsQuery`, which carries a `prepare` hook but has no urn to scope by.
- **Membership must outlive its fetch.** A second terminal over one query skips the fetch, so a scope meaning "rows written just now" returns **empty** — the trap #340 named, now a test.
- **It is replaced, not appended.** A re-fetch is a fresh answer; keeping the old rows would let a withdrawn artefact keep answering, which is the defect being removed.

## A flake from !379, found by this branch

`_require_attached` enumerated `duckdb_databases()` on the **base** connection, which under concurrent observation queries came back empty about one run in three — so every binding was refused with a message confidently reporting *"attached: none"*. `main` reproduces it 3 runs in 6.

Two further attempts were also wrong, and are recorded in the docstring rather than quietly replaced:

1. a per-thread cursor did not fix it;
2. probing the full table name refused every **remote** query, because `RestRegistry.observations` synthesises a binding for a table its fetch has not created yet.

The check now tests the **catalog only**, and **declines to answer rather than guess** when the list comes back empty — a diagnostic check must never turn a working query into a failure.

## One more thing worth naming

The scope clause is schema-qualified from the root's own `__schema__`. `stream()` runs on a cursor of its own — one per reader, so two streams cannot overwrite each other's row buffer — and that cursor does not inherit the handle's `search_path`. Unqualified worked everywhere except there: the shape of bug a terminal-by-terminal test finds and a single happy-path one does not.
