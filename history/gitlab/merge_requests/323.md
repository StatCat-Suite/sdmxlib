# Merge request !323: fix(storage): preserve the instant in a zoneless TIMESTAMP column

| | |
| --- | --- |
| State | merged |
| Opened | 2026-08-17 |
| Merged | 2026-08-17 |

Closes #321.

A tz-aware `valid_from` came back naive **and shifted**: DuckDB's `TIMESTAMP` carries no zone, so the value was converted to the *session's* local time. On a UTC-5 machine `2021-02-03T04:05:06Z` returned `2021-02-02 23:05:06` — not merely a lost `tzinfo` but a different instant, and a different one per reader's machine.

## Not the fix the issue proposed

The issue said "`TIMESTAMPTZ` looks right". The schema already answered it — `dataflow_binding` has stored `materialized_at` as naive UTC since it was written, and its DDL records why: DuckDB's `TIMESTAMPTZ` Python path wants `pytz`, and adding a dependency to store a timestamp is a poor trade.

So #321 was the artefact spine **not sharing a decision this project had already made**. `storage/_time.py` is that decision extracted, so all eight TIMESTAMP columns use one implementation instead of a fifth copy of two lines — the binding calls it too.

    in                 out
    04:05:06+00:00     04:05:06+00:00      identity
    04:05:06+05:00     23:05:06+00:00      same instant, normalised
    04:05:06 naive     04:05:06+00:00      same wall time, now labelled

A naive input is read as **UTC, not local** — local would reintroduce the exact machine-dependence being removed.

## Behaviour change, stated

A naive value now comes home tz-aware. Two tests asserted the old contract and are updated rather than worked around: both readings cannot hold at once, and returning a *shifted* instant is the worse one. Wire-format round-trips are untouched — only the zoneless column needed a convention.

That divergence had a consequence: the shared round-trip guard's `Check` objects serve storage **and** the wire formats, and one expected value cannot be both naive and aware. It now compares datetimes as **instants**, reading naive as UTC — which still catches the original bug, since that one changed the instant.

## The new guard earned its keep again

Deleting #321's `KNOWN_LOSSES` entries made `Codelist` and `Hierarchy` fail — not because this fix is wrong, but because the guard materialises and `materialize()` drops spine fields. That sharpened #322: it is not "annotations are lost" but **`materialize()` drops every spine field the proxy reads** (`uri`, `valid_from`, `valid_to`, `annotations`). One cause, four symptoms, noted on the issue.
