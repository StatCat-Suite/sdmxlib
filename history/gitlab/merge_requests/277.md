Closes #259.

`sort_by(code.annotations["x"])` type-checked, built a query, and raised at `.ids()` — arbitrarily far from the line at fault. The property that decides it ("is this field a column of the row?") is static, so it now lives in the type: `ColumnRef` marks a ref backed by a real column, and `sort_by` / `select` / `group_by` take it. Verified with a basedpyright probe.

`filter` is unchanged and takes any field — an annotation compiles to a correlated EXISTS, a perfectly good WHERE fragment. Only sorting and projecting need one scalar per row, which an annotation cannot provide. `ORDER BY (SELECT title … LIMIT 1)` would compile and silently pick one, so this is a refusal made honest by putting it in the signature.

**The issue counted 18 raises; there are 11.** #275's `field_condition` / `make_column` refactor already collapsed the per-emitter duplication it described. Each survivor is classified in place as BACKSTOP (unreachable from annotated code, kept for untyped callers) or REAL — exactly one is REAL, `reject_unspliced_joins`.

**The field × operation matrix is derived, not prose.** `tests/unit/test_query_totality.py` computes it twice from independent sources — `isinstance(ref, ColumnRef)` and `RowKind.column(...)` — and asserts they agree, so a ref claiming a column it does not have cannot pass. A third hand-written list makes a field crossing the boundary a visible diff; a completeness test fails when a new accessor goes unrecorded.

Found while auditing the matrix and filed as #292 rather than folded in: every annotation predicate is existence-scoped, so "has no annotation of this type" is unreachable by any spelling.
