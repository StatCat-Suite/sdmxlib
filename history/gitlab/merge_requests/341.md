`store.observations(binding)` was the wrong level, and the confusion it
caused is the evidence: it asks a caller to find a binding, which is the
lookup `catalog.query(dataflow_urn, …)` — the API consumers actually use
— does for them in its first stage.

    obs = catalog.observations(flow_urn)
    (obs.filter(obs.col("REF_AREA") == "ON")
        .group_by(obs.col("SEX"))
        .agg(total=obs.col("OBS_VALUE").sum())
        .collect())

Two changes, both from watching the call read badly.

**Keyed by dataflow URN**, like `query`, because that is what a caller
has. `FederatedCatalog.observations` does the binding lookup and
narrows to the DuckDB store — a typed query needs a compiler, so this
narrows rather than widening the `DataStore` Protocol with a method
every other implementation would have to refuse.

**The query names its own columns.** A structural query needs an
accessor beside it and that is fine, because `sl.q.code` is importable
and shared; an observation accessor is built per binding, so a second
object means finding the binding first. `ObsQuery` carries it, and
`attrs.evolve` keeps the concrete class so `.col()` survives every
refinement rather than vanishing at the first `filter`.

`col()` rather than `[]` was forced, and correctly: `Query.__getitem__`
already means *look up a row by id* for a string. Overriding it would
give one spelling two meanings depending on the root — basedpyright
rejected it as an incompatible override, and it would read as a trap in
any query whose root is not obvious.

Also found while demonstrating: percent-of-total —
`col / col.sum().over()` — does not compile, because `/` is on `Num`
rather than the base. Same root cause as #328, now with a second shape
depending on it.
