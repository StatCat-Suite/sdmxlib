`_UNWRITABLE["2.1"]` refused every message carrying a structure map, on the reasoning that 2.1's ComponentMap `<Ref>` needs a class, package and containerID *that ComponentMap does not carry*. True of the map; false of the message — all three follow from the structure the map already names, and the 2.1 XSD fixes the containerID per component kind.

So derive them, and refuse only the three cases that genuinely cannot be written: a map with no ComponentMaps (the XSD requires one), a component id the structure does not define, and a map whose structure is not in the message.

Two things surfaced once the hop ran end to end:

- **3.0 -> 2.1 -> 3.0 still failed over a StructureSet nobody declared.** 2.1 has nowhere to put a map except inside one, so the writer invents a wrapper and the reader reified it as an artefact. It is now annotated `sdmxlib:synthetic-structure-set` and dropped again on read. A *declared* 2.1 structure set still blocks the hop, which is the grouping SDMX really did delete.
- **The 2.1 representation-map writer was falsifying documents.** A regex mapping went out as a literal `<CodeMap>` with the pattern text as the code id — `^M-[0-9]+$` came back as a code by that name, which is not even a valid IDType. A dataType endpoint simply vanished. Both refused now.

Cross-version matrix: 50 hops, 21 converting, up from 19 of 48. Two fixtures gained (there were none anywhere carrying a StructureMap), and two `_BLOCKED` entries were reasoned wrongly — both blamed the grouping when the synthetic wrapper was the obstacle.
