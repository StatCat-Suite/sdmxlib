## The timeouts were not timeouts

The first clean mutation run reported **356 timeouts of ~960**, 353 in `validation.py`. No sampled one had a plausible mutant behind it — the example was `to_itemlist_opt`’s `or` → `and`, which should die instantly.

mutmut forks a child per mutant. On Darwin:

```python
def getproxies():
    return getproxies_environment() or getproxies_macosx_sysconf()
```

`getproxies_macosx_sysconf` reaches into SystemConfiguration, which is **not fork-safe**. Constructing an `httpx.Client` calls it, so `RestRegistry(...)` in a forked child kills the interpreter:

```
Fatal Python error: Segmentation fault
  urllib/request.py       in getproxies_macosx_sysconf
  httpx/_client.py        in _get_proxy_map
  sdmxlib/api/client.py:156 in __init__
  tests/unit/test_rest_registry.py:204 in test_materialise_to_writes_through_with_source_tag
```

mutmut books the dead child as a timeout. The crash is in the harness, not the mutated code, and it lands on any mutant whose covering tests reach `test_rest_registry.py` — which is why the count tracked *how much of the suite a module is reached from* rather than anything about the module. `validation.py` is reached from the registry, catalog and builder tests; `collections.py` mostly is not.

## Fix

Any `*_proxy` variable makes `getproxies_environment()` return non-empty, so `getproxies()` returns before touching the framework. Verified by instrumenting the call:

```
no env set      reaches getproxies_macosx_sysconf: True
no_proxy="*"    reaches getproxies_macosx_sysconf: False
http_proxy=""   reaches getproxies_macosx_sysconf: True   <- empty value does not count
```

`no_proxy` is right on its own terms, independent of mutation: no test in this suite reaches the network, and none should consult a system proxy to decide not to.

## Ruled out on the way, by measurement not argument

- **Import cost** — `validation` and `collections` import in the same ~0.15 s; polars alone is 0.04 s.
- **Per-child startup** — mutmut `os.fork()`s, so children pay none, and the budget `(est + 1) * 15` is ~30x the measured test time (`test_collections.py` runs in 0.03 s against a ~15 s limit).
- **fork + DuckDB threads** — my leading hypothesis on #252, and wrong. An isolated probe forking after a DuckDB query completes in 5 ms.
