Follow-up to closed MR !51.

The previous CLAUDE.md said:
> Always use triple-quoted strings for SQL (\`\"\"\"...\"\"\"\` or \`f\"\"\"...\"\"\"\`),
> including short fragments emitted by query compilers

When phase 2 of the [Cleanup follow-ups](../-/milestones/4) tried to enforce that rule, the result was ~100 single-line SQL strings converted from \`\"...\"\` to \`\"\"\"...\"\"\"\`. A quick check of what the major Python SQL libraries actually do made it clear we were going the wrong way:

| Library | Single-line | Multi-line |
|---|---|---|
| SQLAlchemy | \`\"...\"\` | \`\"\"\"...\"\"\"\` |
| psycopg3 | \`\"...\"\` | \`\"\"\"...\"\"\"\` |
| asyncpg | \`'...'\` | \`'''...'''\` |
| Django ORM | \`\"...\"\` | \`\"\"\"...\"\"\"\` |
| **sdmxlib (after !51)** | **\`\"\"\"...\"\"\"\`** | \`\"\"\"...\"\"\"\` |
| sdmxlib (this MR's rule) | \`\"...\"\` | \`\"\"\"...\"\"\"\` |

Only MySQL Connector/Python advocates universal triple-quoting; nobody else does. PEP 8 and PEP 257 don't address SQL at all.

## Changes
Rewrite the SQL-style section in CLAUDE.md:
- Make the line-count split explicit (multi-line → triple, single-line → plain).
- Document the identifier-interpolation exception (the one legitimate f-string into SQL — table/view/alias names from a validated source).
- Reference !51 so future readers see why the rule changed.

No code changes. The codebase on main already matches the new rule — multi-line SQL is already triple-quoted and the short fragments are already plain-quoted. !51 would have been the only place to violate the new rule, and it never landed.
