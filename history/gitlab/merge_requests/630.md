`just ci` used about 1,300 CPU-seconds and 320–370 s of wall time. Measured stage by stage, 98% of that was the unit tier and the bundle tier. Neither had a slow test to blame. The cost was contention.

## What changed

**DuckDB's thread pools.** Each DuckDB connection starts a pool of one thread per core, so ten xdist workers meant a hundred threads on ten cores. The unit tier now opens connections with one thread by default (`tests/unit/conftest.py`). A caller's own `threads` setting still wins. The bundle tier keeps DuckDB's default on real data.

| DuckDB threads (parallel phase) | wall | CPU |
| --- | --- | --- |
| default (10) | ~105 s | ~590 s |
| 2 | 97–99 s | 470–520 s |
| 1 | 71–87 s | 330–390 s |

Every test passes at each setting. With one thread, the order of an unordered result can no longer vary, which is how a missing `ORDER BY` would show. But unit-test tables are far below the ~120,000-row group at which DuckDB splits a scan, so those tests ran on one thread anyway. `test_unit_tier_duckdb.py` checks that the patch is in force for plain connections, for `LocalRegistry`'s own connection, and that a caller's setting stands.

**The #75 reproducers run as a serial phase.** They race 16 and 32 threads. In the busy pool, each thread waited for a CPU slice to retake the GIL, so a test taking 22 s alone took up to 149 s there and set the tier's wall time. They are now marked `serial`, and `just test` runs them alone after the parallel phase. They keep DuckDB's default threads, which their race needs: with one thread, the sabotage check below failed.

**Repeats.** The mixed-URN reproducer drops from 800 to 200. With the race put back (one cursor shared by every thread), it caught it 30/30 at 200 and 20/20 at 800, and missed 1 in 20 at 50. The new `test_the_mixed_reproducer_still_catches_a_shared_cursor` puts the race back on every run and must catch it within three attempts, so the count can't be cut until the test sees nothing. I watched it fail at 1 repeat. The cache-hit reproducer keeps its 400, because it caught only 22/30 at 100.

**The other thread-racing guards were checked under one DuckDB thread.** The DESCRIBE single-flight and the code-map single-flight each caught their double-check being removed 20/20.

**Not done.** Putting slow tests first: the "slow" tests take 0.2–1.7 s alone and 11–39 s in the pool, so they were victims of the contention, not its cause. The bundle tier is unchanged (about 120 s and a 4.9 GB peak); its slowest test reads the bundle's largest hierarchy by design.
