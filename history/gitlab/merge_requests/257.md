Prerequisite for the rest of #267. Nothing in `tests/bench` touched `code_query` or `hierarchy_query`, so the two largest modules in `src/` had **no performance baseline at all** — and the in-flight refactor moves their whole predicate and ref hierarchy onto a shared generic base, which is exactly the change that costs Python time without altering a byte of SQL.

## Baseline (median, in-memory DuckDB, 10k-code codelist)

| | |
| --- | --- |
| compile, single predicate | 2.0 µs |
| compile, 4-clause chain | 8.3 µs |
| compile, nested `EXISTS` | 2.6 µs |
| compile, annotation `EXISTS` | 2.5 µs |
| **compile, `is_in` × 5000** | **113 µs** |
| execute, single predicate | 216 µs |
| execute, collect 10k | 30.3 ms |

Compile and execute are separate suites because they regress for different reasons. Compile is where a refactor shows up. Execute can only regress if the emitted SQL changes — and for that, the corpus below is a better instrument than a stopwatch.

`is_in` is measured at three widths deliberately: it is the only operator doing per-element work at construction, so a hook added there is invisible at width 1 and O(n) at width 5000, an ordinary SDMX code-set size.

## Two costs it already caught, before they shipped

- A **runtime generic subscript** (`NameField[R](...)`) measures **11× a plain construction** and sits on `_field`, which runs on every predicate — about **20% of a 2 µs compile**. Present in 7 places on the WIP branch; the unsubscripted form type-checks identically, so the fix is free.
- A **per-element coercion hook** in `is_in` would roughly **triple** the 113 µs case.

Neither is visible without a baseline, and neither would fail a single test.

## The sharper instrument

`tests/support/sql_corpus.py` — 61 cases covering every predicate kind, field and query-level operation across both DSLs, dumped as normalised `(sql, params)`:

```
git checkout main   && python -m tests.support.sql_corpus > before.txt
git checkout branch && python -m tests.support.sql_corpus > after.txt
diff before.txt after.txt
```

An empty diff means execution **cannot** have regressed — exactly, rather than statistically.

This is deliberately not the golden-file strategy %13 rejected. A golden file used as the *primary* test passes when the semantics are wrong, which is why the differential properties exist. Used as a *migration equivalence check* it answers a narrower question — did this refactor change anything — and byte-identity is the right answer to it. The docstring says so, so nobody mistakes it for a testing pattern to copy.
