Closes #220. Found while building the #216 round-trip properties, and serious enough to fix before continuing — the properties would keep tripping over a `parse()` that silently drops messages.

## The bug

`parse()` decided structure-vs-metadata by substring-searching the first few KB of raw bytes. A structure message whose **content** contained a sentinel token was misrouted:

| Format | Token in content | Result |
| --- | --- | --- |
| SDMX-ML 3.0 | `GenericMetadata` | **empty `MetadataMessage` — codelist gone, no error** |
| SDMX-JSON | `metadata-schema` | **empty `MetadataMessage` — codelist gone, no error** |
| SDMX-ML 2.1 | `GenericMetadata` | `ValueError: Metadata messages are not supported for '2.1'` |
| SDMX-ML 3.1 | `GenericMetadata` | `ValueError: Metadata messages are not supported for '3.1'` |

Not contrived. A codelist *of SDMX message types*, a concept named `GenericMetadata`, or annotation prose citing the metadata schema all trip it. The two silent cases are the ones that matter: the caller gets an empty message and no indication anything was lost.

The XML branch's own comment said the right thing while the code did something else:

```python
# XML: root element wins.          <- correct rule
chunk = data[:4096].decode(...)
if "GenericMetadata" in chunk:     <- substring search
```

## The fix

**XML** — read the actual root element. `etree.iterparse` with `events=("start",)` returns at the first element, so it reads the root tag and no more; there is no byte window to fall outside of. `_detect_version` now uses that same root element's *namespace* instead of substring-matching namespace URIs, so both detectors share one mechanism.

**JSON** — discriminate on the **values** of `$schema` / `meta.schema` and on the presence of `data.metadataSets`, via a small `msgspec.Struct` probe. That is the natural shape now the envelopes are typed (#200). A payload that will not decode falls back to `"structure"`, so the real reader raises the parse error rather than the probe masking it.

## Verification

**7 of the new tests fail against the previous implementation** — checked by stashing `src/`.

They pin all four formats against all four sentinels, confirm a token placed **beyond the old 4 KB window** is ignored too (that case passed before by luck, not design), and confirm genuine metadata messages still route to metadata — the fix must not overshoot.

The last test is a **property**: for any generated artefact text, `parse(write(msg))` preserves the message kind. That is the shape of check that would have caught this, and it is stated generatively precisely because the failure depended on *what the text said* — a class of bug no fixture set is likely to contain on purpose.

`just ci` green — 2548 unit, 72 docs, 56 integration.

## Also: strategies now generate XML-safe text

Every SDMX artefact must be representable in SDMX-ML, and XML 1.0 cannot carry control characters or lone surrogates. Generating them made every round-trip property fail inside lxml for a reason unrelated to the property.

Fixed at the one place that decides what a valid localised string is, and **recorded rather than hidden**, because the underlying asymmetry is real: sdmxlib does not reject such text at construction. It surfaces late as a raw `ValueError: All strings must be XML compatible` from lxml, while SDMX-JSON accepts and round-trips it — so the same message is writable as JSON and not as XML. Worth its own issue if that ever bites someone; not fixed here.
