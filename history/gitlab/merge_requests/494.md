The two seams `sdmxlib-rest` patches around. Both land; one lands in a
different shape than asked, because the shape asked for is not valid SDMX-JSON.

## 1. The structure writer emits `links[rel="self"]`

`MaintainableJson` carried neither form of an artefact's identity, so a
consumer could not follow a cross-reference inside a response this library had
just written. Downstream that cost a whole module — a post-serialise splice
plus a hand-kept table of 17 collection-key → (package, class) pairs, a copy of
what the model already knows.

**Only the links form, and the asymmetry is the spec's.** #406 asked for a
top-level `urn` property as well, reading SDMX-JSON as accepting either.
Neither vendored schema defines one. Both put the self-URN in `links` and say so
on `IdentifiableType` — *"Also used to specify the URI or the URN to itself"* —
and a link item permits `urn` while requiring no `href`, so the identity rides
alone in one entry. 2.0 tolerates the extra property because its objects are
open; 2.1 closes every object with `unevaluatedProperties` and rejects it, which
`test_wire_conformance_gate` reported as **72 invalid documents** the moment the
property was emitted. `test_no_top_level_urn_property_is_emitted` asserts the
absence, so the reason sits where someone would otherwise re-add it.

The consumer loses nothing: #406 itself records that the .Stat Suite client
reads `links[rel=self].urn` with no fallback to the property, so the form that
is conformant is also the one that works.

## 2. …which surfaced a URN we have never been able to write

Four classes declared `sdmx_package = "structuremap"`. That string is in **no**
SDMX vocabulary: 2.1 spells the package `mapping`, 3.0 and 3.1
`structuremapping`, and the JSON schema's URN pattern enumerates the latter. So
every URN this library would build for a `StructureMap`, `RepresentationMap`,
`ConceptSchemeMap` or `CategorySchemeMap` was unresolvable anywhere.

Nothing pinned it — zero fixtures, zero tests — because nothing put it anywhere
a schema could read it until the self-URN did. Fixed to `structuremapping`,
matching `StructureSet`, which was already right.

`test_item_urn_classes` now checks **maintainables** against the vendored
vocabularies the way it already checked items. That is the guard that would
have caught this, and it is the second time this file has earned its keep.

## 3. `get(..., expect=Class)`

On the four registries that take a URN. `T` binds to `expect`, so #399's
overload ambiguity never arises — no change to `SdmxUrn.parse`, no reordering,
none of option 2's 52 + 27 findings. Not on the `Registry` protocol, which
documents itself as the narrowest read seam and says implementations need not
agree on a keyword; widening it would charge every implementer for a
convenience.

The runtime check is the point rather than a formality. The consumer's two call
sites are a walrus inside an `isinstance` inside a comprehension, because a
stored row may legitimately name something the site cannot use — and before the
filter existed such a row reached the writer and failed there. So the narrowing
and the check are one operation, and `test_expect_is_the_isinstance_the_caller_would_write`
asserts they stay equivalent.

**One sharp edge, documented and pinned:** `local.get(urn, expect=Codelist)`
answers None, because a stored codelist comes back as a `LazyCodelist`. Ask for
what arrives — `expect=LazyCodelist`, `expect=CodelistLike`, or
`expect=Codelist, eager=True`. A caller who did not read the docstring meets
this in `test_local_expects_what_actually_comes_back`.

## What the gate caught that I did not

Two runs, two findings, both guards that already existed:

* `test_get_target_contract` (#370) reads each `get` *implementation* signature
  and requires `SdmxUrn[T] | Ref[T]`, positional-only. `expect=` widens the
  implementation to `SdmxUrn[object] | Ref[Any]`, so it fired — correctly. The
  contract #370 is about is what callers see, which is now the overloads, so the
  guard was **extended rather than exempted**: the widened spelling is legal only
  behind overloads, one of which must still declare the narrow form, and every
  overload's target must stay positional-only. Sabotage-checked by deleting the
  narrow overload.
* `tests/docs/test_upgrading.py` asserts `RestRegistry.get`'s exact parameter
  list. Updated to the true list rather than loosened to a subset — the
  exactness is what makes the next addition a deliberate edit.

## Typing

`Any` ratchet 40 → 48, narrowed first rather than re-baselined: the URN half of
each `expect=` signature is `SdmxUrn[object]`, since `T` comes from `expect` and
the phantom is never recovered — CLAUDE.md's litmus exactly. Only `Ref[Any]`
remains, because `Ref` is invariant by design (#289) and `Ref[object]` would
refuse the `Ref[Codelist]` a caller holds. Eight occurrences, one per signature,
all of them that invariance; `tools/any_baseline.txt` records it.

The four implementations return `object` with the overloads carrying the
caller-visible types, which is what `LocalRegistry.get` already did.

## For the consumer

Both workarounds can go, and neither needs a coordinated release:

* `urn_injection.py` and its 17-qualifier table — the writer now emits the
  `rel="self"` link. The splice is idempotent, so it can stay installed across
  the upgrade and be deleted after.
* The `isinstance(ms := registry.get(...), sl.MetadataSet)` comprehensions at
  `routes/metadata.py:313` and `:401` become
  `registry.get(urn, expect=sl.MetadataSet)`. Those go through a
  `LocalRegistry`, so mind the lazy-root note above — `MetadataSet` has no lazy
  facade, so `expect=sl.MetadataSet` is exactly right there and needs no
  `eager=`.

Also noted and not acted on, per the issue: `catalog.data.inspect()` stays gone
and `LocalRegistry._data_store` stays private.
