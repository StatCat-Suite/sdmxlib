!434's guard compares *function bodies*, and said so about itself: `_SECTIONS`,
`_NSMAP` and `_NS` are outside it entirely. That is the gap #346's own comment
recorded as "the next gap in the net", and it is the one that matters most,
because `_SECTIONS` decides which artefacts a writer emits and in what order.

A section added to 3.0 and forgotten in 3.1 produces a writer that silently
omits a whole container — no exception, valid XML, missing artefacts — and
every existing assertion passes, because no function body changed. That is
#345's shape exactly, one level up from where the guard was looking.

## Cheap, because the two agree

Measured before writing it:

| module | constants | identical | differ |
| --- | --- | --- | --- |
| `reader.py` | `_NS` | yes | — |
| `writer.py` | `_NSMAP`, `_SECTIONS` | yes | — |
| `namespaces.py` | `NS`, `STRUCTURE_ROOT_NS`, `XML_LANG` | yes | `COM`, `MD`, `MES`, `STR` |

So the modules that matter need no allow-list at all, and `namespaces.py` is
asserted rather than skipped — the fork's one real difference is *supposed* to
live there, so a divergence appearing in `reader.py` or `writer.py` means it
leaked out of the module built to hold it.

`_DIVERGENT_CONSTANTS` gets the same staleness check the function lists have:
if 3.1 ever adopted a 3.0 URI, the entry would describe something that no
longer happens and nobody would delete it unprompted.

## Verified as a guard, in both directions

Adding `("NewThing", [])` to the 3.0 writer's `_SECTIONS` alone:

    AssertionError: writer.py: module-level data differs between the forks:
    ['_SECTIONS']. A generation difference outside `namespaces.py` is the thing
    this fork is supposed not to have.

and pointing 3.1's `COM` at the 3.0 URI:

    AssertionError: namespaces.py: ['COM'] are declared as divergent and are
    now identical — delete the entries.

Worth recording that the *first* attempt at that check passed while sabotaged:
the regex I used to insert a section matched `= (` and `_SECTIONS` is
`AnnAssign` with a `[`, so nothing was actually changed and the green meant
nothing. The guard was fine; the check of the guard was not.

## Option 1 is still open, and better measured now

Re-measured while sizing it: **0 reader functions differ, 3 writer functions
differ**. `_common.py` already hosts shared 2.1/3.0/3.1 helpers and all six
modules import it, so a shared v3 core is moving code into an existing seam
rather than building one — parameterised by a namespace triple and a
three-entry "what this generation omits" set, which is what the issue
predicted.

Deferred deliberately, not forgotten: the issue's own trigger is a 3.2, and
these guards are what make attempting it safe when that comes.
