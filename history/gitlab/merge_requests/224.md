#217. Differential properties for the code-query DSL against a pure-Python oracle, plus algebraic laws that need no oracle at all.

**They found a serious bug on the second run.**

## Every filter containing an underscore silently matched nothing

`_ilike_pattern` escaped LIKE metacharacters as `\_` and `\%`, but the emitted clause carried **no `ESCAPE`** — and SQL `LIKE` has no default escape character. The backslash was matched literally:

```python
code.id.contains("REF_AREA")  ->  []      # silently
code.id.contains("A_B")       ->  []
code.id.contains("_")         ->  []
```

Underscores are ubiquitous in SDMX ids — `CL_FREQ`, `OBS_VALUE`, `REF_AREA`, `TIME_PERIOD`. This is a filter that quietly returns nothing rather than erroring, which is the worst failure mode available.

**Nine clauses were affected**: two in `code_query`, seven in `hierarchy_query`. All now carry `ESCAPE '\'`. Confirmed against DuckDB directly before touching anything:

```
'A_B' ILIKE '%A\_B%'                 -> False
'A_B' ILIKE '%A\_B%' ESCAPE '\'      -> True
'AXB' ILIKE '%A\_B%' ESCAPE '\'      -> False
```

Hypothesis found it from a generated codelist whose only code was named `_` — a legal SDMX id, and not something a fixture author would think to write. Regression test parametrised over `_`, `A_B`, `REF_`, `_AREA`; **5 of the 15 tests fail** with the `ESCAPE` reverted.

## The oracle is a specification, not an implementation

`tests/support/oracle.py` shares no code with `code_query` and **re-derives depth and ancestry from `parent_id`** rather than reading the `depth` / `ancestor_ids` columns the storage writer bakes. So every differential property also checks that the baked values agree with a fresh traversal — the invariant `docs/design/caching.md` implies for baked data ("input immutable within a bundle → bake it") but which nothing else enforced.

It is deliberately small enough to read in one sitting. Past that, a failure stops obviously implicating one side.

## Also surfaced — filed, not changed

**`id == "F"` is case-sensitive; `id.contains("F")` is not** (`=` versus `ILIKE`). So `code.id == "cl_freq"` finds nothing while `code.id.contains("cl_freq")` finds `CL_FREQ`. Filed as **#222**; the oracle models the *observed* behaviour so these properties pass against today's implementation, and #222 decides whether that behaviour is right. Changing it silently under cover of a test MR would have been the wrong call.

## The eleven properties

**Differential** — id predicates, structural predicates (roots, leaves, direct children, depth), and transitive ancestry, each compared against the oracle.

**Algebraic**, needing no oracle: filter idempotence and order-independence; results are ordered subsets with no duplicates; roots and non-roots partition the codelist; ancestors and descendants are inverse (checked across `narrower_transitive` and `broader_transitive`, which compile to *different* SQL, so one drifting from the other shows up); a code is never its own descendant; leaves are exactly the childless codes.

**Mutation-tested**, because 11 passing properties on the first run is not evidence of anything:

| Mutant | |
| --- | --- |
| `NOT EXISTS` → `EXISTS` in the leaves clause | **killed** |
| `= ANY` → `!= ANY` in `descendants_of` | **killed** |

There is also a guard that the DSL path is genuinely SQL-backed. My first version of it asserted `duckdb.__version__`, which tested nothing — it now asserts `lazy.codes` is a `CodeQuery` rather than an eager `ItemList`, because if that ever regressed, every differential property would still pass while comparing Python against Python.
