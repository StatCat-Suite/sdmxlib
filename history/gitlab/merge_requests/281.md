Closes #294.

`sort_by` appended, so the **first** caller's key dominated. A helper sorting by a unique column made a caller's later `sort_by` a *silent no-op* — the tiebreak never fired, nothing errored, and the caller got the wrong order.

That came from modelling `sort_by` on the refinement principle by symmetry with `limit`, which is a category error: refinement is a claim about which rows come back, and ordering does not change the row set. #293 states the exclusion; this fixes the code it was excluding.

```python
sort_by(*keys)   # replaces any order already set
sort_by()        # clears, as Django's order_by() does
key.desc()       # per-key direction; an unmarked key is ascending
```

`ascending=` is removed — one call now carries several keys and a per-call flag cannot express them disagreeing ("newest version first, then id ascending"). 22 call sites migrated.

## Why a marker, not a parallel array

polars takes `descending=[False, True]` alongside the keys. SQLAlchemy, ibis and Django all mark the key (`col.desc()`, `t.a.desc()`, `"-a"`). A parallel array puts the direction at a distance from what it describes and drifts silently.

`Descending` is generic over the *key*, not the row kind, so unwrapping returns the ref type back — parameterising on the row would have forced a cast at every use.

## Prior art, and the in-repo precedent

Two of three declarative peers make the later call dominant (Django replaces, ibis prepends). Only SQLAlchemy appends — and it is the only one that also offers a reset, which is what makes appending survivable there. We appended **and** had no reset.

The precedent was already in this repo: `with_annotations` replaces and clears, for the same reason, with a property pinning it. `sort_by` was the odd one out against our own code.
