# Merge request !241: fix: carry enumeration_format everywhere, and DataKeySet on DataConstraint

| | |
| --- | --- |
| State | merged |
| Opened | 2026-08-07 |
| Merged | 2026-08-07 |

Closes **#243** and **#241** — two silent losses, both in the same shape: a field the model could hold, dropped by formats nobody had checked.

## #243 — `enumeration_format` was wired only into 2.1

Added in !239 and connected to the SDMX-ML 2.1 reader and writer alone, because that is where the document-fidelity harness pointed (the ECB data structure carries fourteen). 3.0, 3.1 and SDMX-JSON were never done, so the value was dropped there — it was the *entire* remaining loss on the two 2.1 fixtures that survive a trip through 3.0.

Now carried in all four, and on `MetadataAttribute` too, which every version allows.

Two constraints surfaced while generating the pairing, neither previously enforced:

- **`RepresentationType` is a choice** — `TextFormat` on one side, `Enumeration` + optional `EnumerationFormat` on the other. A format beside a *free-text* facet has no valid encoding anywhere.
- **`CodedTextFormatType` is a restriction, not a copy** — it prohibits `decimals` and narrows the value bounds from `xs:decimal` to `xs:integer`. A `Facet` can say more than an EnumerationFormat may. `_xsd_num` now renders integral values without a fractional part, which `xs:integer` requires and `xs:decimal` accepts.

**Six mutations passed the entire suite before this was finished.** Dropping the field in either direction of any format emits *valid* output — schema validation is satisfied precisely because the value is gone — so nothing saw it. The property now compares the field explicitly, and the strategies generate an enumerated dimension carrying a format, which they never did. That absence is why the gap existed.

## #241 — `DataConstraint` could not hold a `DataKeySet`

`DataConstraintType` is `DataKeySet | CubeRegion`; sdmxlib modelled only the region, so a schema-valid document carrying a key set lost it in every format. Unnoticed because no fixture puts a key set inside a *data* constraint — the only one in the corpus is on an `AttachmentConstraint`, which *was* modelled with the field.

Two version differences surfaced, both producing schema-invalid output when wrong and both invisible to the readers, which tolerate either form:

| | 2.1 | 3.0 / 3.1 |
|---|---|---|
| `KeyValue` / `Value` namespace | common | structure |

Reading only one namespace produced a `DataKey` with no values — populated at the set level, empty underneath. And SDMX-JSON declares `isIncluded` **required**, so it is a non-defaulted DTO field: `WireStruct` omits defaults on encode, which would have dropped the one key the schema insists on.

This unblocks **#244**: the 3.0 refusal of `AttachmentConstraint` advises "use a DataConstraint", which until now could not be done.

## Controls

Six mutations for #243, five for #241 — in both directions of both format families. One JSON mutation initially reported a false pass because `None or (expr)` is a no-op; it was re-run properly.
