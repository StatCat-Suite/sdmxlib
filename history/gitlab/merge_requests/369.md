Closes #336 (design §5.15). Prerequisite for §6 step 9 — the chain cannot be called a mechanism while the thing it runs on races.

## The decision that had to come first

The issue's own follow-up comment was right that this is an **unstated** contract, not a violated one: the local `Registry` documents its thread-safety and meets it; `RestRegistry` said nothing and met nothing. So before adding a lock, the question was whether it is meant to be thread-safe at all.

**Settled yes**, on §4.1 of the design — a FastAPI facade is the shape this API is for, and "nothing" is not an answer a server can build on. The commitment now sits beside the local one in `docs/design/concurrency.md`, in the same words: *concurrent reads are safe and do not duplicate work.*

## Four fixes

1. **One query store.** The lazy `:memory:` store is built under a double-checked lock. Two threads built two, and the loser's was leaked **still open**, holding that thread's fetched artefacts. A query then read an empty store and correctly reported nothing — the worst shape a concurrency bug can take.
2. **One fetch per question.** `_fetched` was a plain unbounded `set`, so eight threads asking one question made eight HTTP round-trips. Now a `SingleFlight` (`sdmxlib/_singleflight.py`): the first arrival fetches, the rest wait on it, completed keys bounded and evicted FIFO. Eviction only costs a re-fetch, which is why the guarded work must stay idempotent — stated on the class.
3. **One question per observations table.** The lock spans the *ingest*, not just the check, so two threads asking one dataflow different questions take turns rather than interleaving two CSVs into one table.
4. **No execution on `.connection`.** `_current_catalog` ran `SELECT current_database()` on the store's base connection — which #300 had already ruled out. Two threads overwrite each other's row buffer (#75), so `fetchone()` returned `None` and a branch commented *"DuckDB always answers this"* raised `RuntimeError`.

**The fourth was not in the issue.** The tests written for 1–3 found it, and the `pragma: no cover` marking it unreachable had been wrong all along. That is the argument for writing the tests before calling the fix done: three fixes came from reading the issue, and the one that produced a user-visible `RuntimeError` did not.

## `SingleFlight`

The sibling of the resolver's `_FIFOCache`: that caches a *value*, this caches the fact that work already happened — which is what a fetch produces, since there is no return value to hand a waiter. Meets the three requirements in `docs/design/caching.md`: single-flight (not just a lock), bounded, invalidation stated.

## Evidence

Every property is asserted as a **count of expensive calls**, per the caching checklist, with a barrier so "arrived together" is a fact rather than a hope.

- Reverting each of the three original shapes fails the new tests: no store lock (3 failures), plain set memo (1), data lock around the check only (2).
- `SingleFlight` mutants killed: naive check-run-record, a plain lock, unbounded, remembered-failures. **One survives** — moving `event.set()` above the record block — and correctly so: a waiter re-checks under the lock, so it costs a spin, not a duplicate run. The comment that claimed otherwise was corrected rather than the mutant papered over.
- Amplification for (4) was **measured, not guessed**: 1 call/thread caught the reverted line on ~1 run in 3, 40 on 2 in 5, 500 on 6/6 — and the file still finishes in 0.6 s.
- A mutant that hung the suite rather than failing exposed an unbounded poll loop in my own test helper; it now has a deadline, so a broken implementation fails fast instead of looking like infrastructure trouble.
