## What it does

`DataRequest` beside `Request`, and `data_request_for(predicates, binding=,
dsd=, api=)` returning a request plus the predicates it could not express.

```
api=2.1  data/ECB,EXR,1.0/M.GBP+USD
         {startPeriod: 2019, endPeriod: 2024}
         residual: OBS_STATUS, OBS_VALUE

api=3.0  data/dataflow/ECB/EXR/1.0/M.GBP+USD.
         {startPeriod: 2019, endPeriod: 2024, c[OBS_STATUS]: A}
         residual: OBS_VALUE
```

Same query, two URLs — #337 arriving in the data plane. The trailing dot on 3.0
is the time slot, empty because a **range** cannot go in a slot and belongs in
the periods on either version.

| role | lowers to |
| --- | --- |
| key dimension, `==` / `is_in` | a key slot, `+`-joined and sorted |
| time, `>=` / `<=` | `startPeriod` / `endPeriod` |
| time, `==` | both bounds — they are inclusive, so one period is `[v, v]` |
| time, `is_in` | a key slot on 3.0; residual on 2.1, where time has no slot |
| attribute, `==` / `is_in` | `c[<id>]=` on 3.0; residual on 2.1 |
| anything else | residual |

## Two design points

**Pushing a superset is always safe**, which is what makes the conflict rule
one line. Two predicates wanting one slot: the first is pushed, the second
stays residual, the server returns a superset and the local filter narrows it.
Pushing the *intersection* would be an optimisation whose correctness depends
on both predicates meaning what we think.

**`DataflowBinding.component_of`** replaces the inverse map `Observations` was
building for itself. A physical column is the only thing a compiled predicate
carries, so that inversion should have one home.

## Guards

The invariant asserted hardest is that **every predicate is either pushed or
returned, never dropped** — per predicate rather than in aggregate, because one
that vanished would return *more* rows with no error. Residuals are checked by
identity, since comparing two predicates raises by design.

Mutation-checked, and the pass produced two findings. Dropping the
second-predicate residual, emitting `c[]` on 2.1, setting only `startPeriod`
for `==` on time, and leaving key values unsorted are each caught.

Allowing strict operators through `_lowerable_values` proved an **equivalent
mutant** — the slot's own check refuses them anyway. Chasing that showed the
two guards cover *different* operators: `>` never leaves the first filter,
while `>=` does (period bounds are inclusive) and is refused at the slot,
because a range is meaningful on time and meaningless on a code. Without the
second guard, `CURRENCY >= "USD"` would put `USD` in the slot and silently drop
the comparison. My first version of that test used `>` and proved nothing.
