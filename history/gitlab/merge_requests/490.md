`_collect_known_urns` expanded item-level URNs for `ConceptScheme` and nothing
else, while `_collect_refs` on the other side of the compare walks into items
correctly (#383, #392) — so the two halves disagreed about what an item is, and
every `Code`, `Category`, `Dimension` and `MetadataAttribute` reference read as
broken against a message that plainly contained its target.

On the SDMX 3.0 message in #404 that was 1,388 issues of which **zero** were
real, which is what makes it unusable rather than merely noisy: with no signal
in the list a caller cannot filter. None of the three shapes is avoidable — a
`HierarchicalCode` *must* point at a `Code`, a `HierarchyAssociation` at the
component it organises, and `Categorisation` is how a category scheme is
attached to a flow in every 2.1-era message there is.

## The declaration, not a table

#404 suggests a table of (scheme, package, item class, accessor) rows. This
takes the other option, because it is the one #148 already took for
`_collect_refs`: the descent comes from the class.

`Code` and `Concept` already declared `sdmx_package` / `sdmx_class` for exactly
this purpose (#240). Fifteen more item classes now do — `Category`, `Agency`,
`DataProvider`, `MetadataProvider`, the six DSD components, `MetadataAttribute`,
`MetadataTarget`, `ReportStructure`, `Level`, `HierarchicalCode` — each pair
taken from the vendored XSDs rather than from the class name, which matters for
`Group`: SDMX calls a group's URN class `GroupDimensionDescriptor`.
`_refshape.item_fields` derives the item-bearing fields per class from that,
cached, and `SdmxItem` is the protocol the pair satisfies.

Two things an accessor column could not have expressed, both of them real
reference targets:

* `DataStructure.time_dimension` and `.measure_dimension` are **single**
  components, not lists — and SDMX gives each its own URN class.
* `Category.categories` and `MetadataAttribute.children` **recurse**, and both
  are self-referential, so attrs hands their declaration back as a string.
  `_declared_types` resolves it; the two nested-item tests are what say that
  half works.

## Version-less references, the same symptom

Folded in on the same report, having turned up while reproducing it. SDMX writes
*no version* for latest, and the known set registered an artefact under the
version it has — so `Dataflow.structure -> DataStructure=AG:DSD1` read as broken
with the DSD sitting at 1.0.0 in the same message. The readers' own resolution
index has always registered both spellings (`_common.index_artefact`); this one
registered neither alias. At the scheme level, so a caller hitting both could
not tell them apart.

Three spellings now resolve, each computed **from the failing reference** rather
than registered per item:

* a nested item by dotted path or by leaf id — a 2.1 `<Ref>` carries
  `maintainableParentID` and a bare `id`, which is the leaf form our own readers
  build;
* a component under either version's class name, `Attribute`/`DataAttribute` and
  `Measure`/`PrimaryMeasure` (`_CLASS_ALIAS_GROUPS`, groups rather than a
  one-way map so the folding cannot go asymmetric);
* any artefact with its version omitted, against the versions the message
  actually carries.

## Cost, and what the guards assert

One `SdmxUrn.make` per (scheme, item class) plus one string per item — the shape
and the reasoning of `storage._item_urn_prefix`. Asserted as an **exact** count:
7 for a message of one 500-code codelist and one full DSD (two scheme URNs, one
`Code` prefix, four component prefixes). A sabotage that builds a URN per item
takes it to 510; a `< 100` bound would have passed that.

Measured at bundle scale, interleaved: a 500,000-code codelist costs 215 to 229
ms over three arms and 69 MB for the length of the call. The arm without item
expansion is 0.1 ms because it registers one URN and answers nothing, so that is
the price of the fix rather than a regression — the same framing
`_walk_elements` carries for #148. The cheaper key (a tuple, or an id set per
scheme) is recorded in the docstring as the lever if a caller ever needs it.

Alias work is proportional to references that just failed, not to items, so
tolerating three spellings costs nothing per code.

Every new resolving test has a discrimination check beside it — an absent code,
an absent category, an absent component, a scheme the message lacks, a different
explicit version — because a fix that accepted anything item-shaped would pass
the resolving half. `tests/unit/test_item_urn_classes.py` adds the guards the
model cannot answer alone: every identifiable non-maintainable declares a pair or
is in `_NOT_AN_ITEM` with a reason, and every declared pair appears in the
vendored 3.0 URN patterns or in 2.1's object types. Three were watched to fail
on their own sabotage (a wrong pair for `Group`, a dropped pair on `Dimension`, a
stale exclusion name); a fourth failed on first writing, which is how the
alias-group assertion ended up stating what is true — the model declares the
class's own name, 2.1's for `Attribute` and 3.0's for `Measure` — rather than
what I assumed. The fifth asserts the two vendored vocabularies are populated,
which is the discrimination check for the other two: a renamed schema file would
otherwise make both vacuous.

Swept the 30 real fixtures that parse into a message: 224 item-level references,
9 issues left, and all 9 are genuinely dangling — a MetadataSet naming a
metadataflow the message does not carry, an MSD with no concept scheme. Both are
the partial-bundle case `validate_references` documents.
