Closes #261.

"Codes A, B or C" — the everyday SDMX filter — was inexpressible in either query DSL. No set-membership operator, and no `Or` combinator either, so the only routes were one query per code unioned in Python, abusing `contains`, or dropping to raw SQL. The data plane had this all along: `ComponentFilter` treats a list as an OR-set.

```python
cl.codes.filter(code.id.is_in(["CA", "US", "MX"]))
h.nodes.filter(node.level.is_in([region, country]))
cl.codes.filter(code.depth.is_in([0, 1]))
```

On every ref, not only string ones — `depth.is_in([0, 1])` is meaningful and was equally unreachable.

## Lazy composition

```python
cl.codes.filter(code.id.is_in(other.narrower_transitive("CA")))
```

Anything exposing `to_sql()` — another `CodeQuery`, a `HierarchyNodeQuery` — compiles to `IN (<subquery>)` with only the relation's own binds spliced into the outer list. This is what the `SqlRelation` protocol exists for, and the property asserts it rather than assuming: two `SELECT`s in the emitted SQL, at most three binds, no parameter explosion.

## The empty set

Matches nothing, compiles to `FALSE`. #261 explicitly deferred this to #256, which settled it for `ComponentFilter` on four grounds: `None` already means "no constraint", polars (`is_in([])` → empty) and SQLAlchemy (`in_([])` → a contradiction) agree, it is the relational definition, and it fails safe. `IN ()` is not valid SQL regardless.

## Per-element coercion

`node.level.is_in([Level(...)])` behaves exactly as `node.level == Level(...)`. Missing that would have made `is_in` the one operator where `_coerce_value` silently did not apply, so it is covered by a property rather than an example.

## Three laws

Each catches a different plausible mistake:

- `is_in([c])` ≡ `== c` — a divergent single-value special case (builders often emit `=` for one value and let it drift)
- `is_in(every id)` ≡ no filter
- `is_in([])` ≡ nothing
