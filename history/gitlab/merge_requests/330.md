# Merge request !330: fix(query): a windowed count counts values, not rows (#304 triage)

| | |
| --- | --- |
| State | merged |
| Opened | 2026-08-17 |
| Merged | 2026-08-17 |

Triaging `_compile.py`'s largest survivor cluster found a defect rather
than a test gap.

`col.count().over(...)` compiled to `count(*)` for every windowed count.
That dropped the counted column from the SQL **while still emitting its
bind parameters**, so `description["en"].count().over(...)` died with
`Parameter argument/count mismatch`, and counting any nullable column
silently included its NULLs.

The comment justified it: the fan-out marker is not a real column, so a
windowed count counts rows. The premise is false — the marker's path is
to-many by construction and `_flat_reference` refuses that before a
window is built, so it cannot reach `_window` at all. Every source here
is a real column.

It survived 1,127 killed mutants because the one test counted `id`,
where `count(*)` and `count(id)` agree.

Once corrected, the `count` branch said exactly what the `else` said,
and two more mutants survived on being unable to tell a branch from its
fall-through. That is a duplicate branch, so it is deleted.

Three windowed forms had no test at all, each with behaviour worth
pinning: `n_unique().over()` (the DISTINCT argument *and* the rename to
`count`, since DuckDB has no `n_unique`), `list().over()` (excluded from
the frame's ORDER BY, which is what stops it becoming a running list),
and `lead(offset)` — indistinguishable from plain `lead` at offset 1,
which is all that was tested.

`_compile.py` against the whole unit suite: 1,127/1,290 killed -> 1,147,
survivors 163 -> 143, no regressions. 18 of the 20 newly killed are in
`_window`, 23 survivors -> 5. The five left are classified in
docs/design/mutation-evidence.md: three equivalent under SQL's
case-insensitivity, one dead fallback whose removal is a bigger change
than a triage should smuggle in.
