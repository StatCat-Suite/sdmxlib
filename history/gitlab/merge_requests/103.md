## Summary

Closes the sdmxlib side of #135 — multi-Hierarchy support over a single Codelist, with the API plumbing callers need to pick *which* parent graph to descend.

Five focused commits:

1. **`feat(code-query): sl.code.descendants_of` with optional hierarchy** — new row-level predicate. Without `hierarchy=`, walks the codelist's flat parent chain via the precomputed ancestor array. With `hierarchy=` (URN string, `Hierarchy` artefact, or `Ref[Hierarchy]`), walks `sdmx.hierarchy_node` and resolves the root through `code_urn` so the common but not-guaranteed `node_id == code_id` convention is never assumed. Mirrored as a `CodeQuery.descendants_of(...)` one-shot.
2. **`feat(hierarchy): default_hierarchy(registry, dataflow, dim_id)`** — resolves the declared default `Hierarchy` for a Dataflow's dimension by scanning `HierarchyAssociation` artefacts. Dataflow-scoped wins over unscoped; ambiguity at the same scope raises. Free function alongside `validate_binding` (the pure-data rule in `CLAUDE.md` rules out threading a registry into domain objects).
3. **`feat(hierarchy): Hierarchy.descendants(root_code_id)`** — pure-Python escape hatch. Speaks code-ids end-to-end. Useful when callers want a small id list to feed directly into `ComponentFilter.dimensions[i] = [...]` without a SQL round-trip.
4. **`test: multi-hierarchy + HA round-trip fixture`** — new `with_multiple_hierarchies.xml` fixture modelling the CL_GEOGRAPHY admin-vs-statistical case from the parent issue: one Codelist (CA/ON/QC/TOR), two Hierarchies giving the same codes different parent graphs (TOR under ON vs TOR a direct sibling of ON/QC), and two HierarchyAssociations on REF_AREA (one dataflow-scoped, one unscoped). Wired into the parametrized SDMX-ML 3.0 writer round-trip so it gets XSD-validated automatically.
5. **`feat(sdmx-json): HierarchyAssociation read/write`** — closes the JSON-side gap on ask #1 of the issue. SDMX-JSON 2.0 `hierarchyAssociations` are now read and written; output validates against the vendored SDMX-JSON 2.1 spec schema (the same parametrized test that the existing ML30 fixture goes through).

## Design notes

- `descendants_of` lives on `sl.code` as a lowercase verb (polars / SQLAlchemy-attribute lineage), not as a `Within(...)` value type — discussed at length pre-implementation. Composes with other predicates inside `CodeQuery.filter(...)` and stays inside the existing DSL.
- `default_hierarchy` is a free function rather than a `Dataflow` method to honour the CLAUDE.md pure-data invariant.
- The hierarchy-aware SQL emission resolves the root via `code_urn` (two JOINs) rather than assuming `node_id == code_id`. Single EXISTS in the emitted plan.
